## 2. 开工前八问

新会话或压缩后先答，答不出就停：**①** 当前工作项与其状态版本 **②** 仓库/分支/提交 **③** 交付型还是事实型 **④** 从头还是接手 **⑤** 本次可触范围 **⑥** 本次禁止的动作 **⑦** 完成判据是 `ACCEPTANCE.md` 的哪几个 ID **⑧** 上次遗留项。

## 3. 不可逆动作：先问人，等明确同意

同意只对本次有效，不延伸下一次。

动作清单见 `.std/标准/01-项目管理标准.md` §5.5，此处不抄。落到本仓的具体项：

- 改 `ACCEPTANCE.md` 已冻结条目；覆盖或删除本文件 / `WORK.md` / `FAILURES.md`
- 改内嵌的标准副本（默认 `.std/`）里的任何文件——它只读；要改标准就向上游报告（`.std/标准/01-项目管理标准.md` §8），修复发布后再拉取
- **§0 里补充的项目特有动作**

**不在清单但你觉得可能不可逆的，按不可逆处理。** 三问任一为是就问：撤销要不要人工介入？要不要恢复备份？会不会被别人看见？

## 4. 三态：PASS / FAIL / UNDETERMINED

**每个结论都是「结论 + 成立条件」的一对。写不出成立条件，记 `UNDETERMINED`。**

一律记 `UNDETERMINED`，**不得折算为通过**：检查没跑/失败/超时 · **输出为空**（空输出永远不是通过，先断言目标存在）· 生成者与验证者同一且判断涉及解释 · 外部写入结果未知 · 需人应答而没答。

**「全部 X 通过」在 X 为空集时判 `UNDETERMINED`，不判 `PASS`。**

报告写 `PASS n / FAIL n / UNDETERMINED n`，**三个数分列，永不合并、不进通过率分母**。

---

## 5. 停机条件

命中任一即停下报告，不许继续试：

- 同一故障连续两次修复无效且无新证据（重试前必须改变一个输入变量并写下改了什么）
- 超出 §2 第 ⑤ 项声明的范围
- 需要 §3 的动作而未获同意
- `UNDETERMINED` 挡在完成判据上
- 连续三次工具调用失败
- **发现自己在改测试而不是改代码**

**停机不是失败。** 带着"知道什么、不知道什么、下一步要什么"停下，比猜着做便宜。

---

## 6. 细则在 skill 里

八道交付门、证据六字段、提交规范、测试、安全、评审、ADR、可观测性、失败登记——**全在 `.agents/skills/`，目录已在你的上下文里，按 description 自取。**

**不确定要不要读，就读。** 读一个 skill 的代价远小于漏一条门。

---

## 7. 改本文件

新增一条规则必须同时写清**它防哪个具体失败**与**什么条件下删它**——两样写不出，不许加。**只增不减是缺陷**：每次新增先问能不能删一条。细则一律进 skill，本文件只留"晚一秒就来不及"的。

=== 模板：README.md ===

# 模板目录

governed_by：D-014、D-020

**本目录整体属于载体实例，效力为零。**

模板是语义要求在"文档 + 表格"这一种载体上的实现。其中：

- **字段集合属于语义**——由对应规范正文定义，换载体不变；
- **文件形态、章节顺序、表格布局、字段名拼写属于载体**——换一种工具或存储方式即需重写。

因此模板不构成落地要求：用任务系统字段、结构化数据或其他形态承载同一套字段集合，同样满足规范。模板中的状态值按 D-014（标准仓 `docs/08-规范效力元治理.md`）的效力语义填写；实际效力以生效登记表（标准仓 `docs/决策日志.md#effective-register`）为准。

模板中出现的版本控制字段（仓库、工作树、分支、提交标识）是工作区身份（标准仓 `docs/20-状态工件.md#workspace-identity`）的**一种**探测形态，不是必填字段。

# 评审与决策记录

## 评审：生产者 ≠ 验证者

**结构性要求，不因模型变强而消解。** 写代码的和判它对不对的，必须是两个上下文。

- 多人项目：至少一名他人评审，**不许自合**
- **单人项目**：开**独立会话**评审——新上下文，只给 diff 与验收标准，任务是**试图证伪**，不是"看看还行吗"
- 评审者只看 diff 与验收条目，**不看作者的解释**——解释会把评审变成复述
- 评审意见转成 `ACCEPTANCE.md` 的 ID 或 `FAILURES.md` 的条目，**不停留在对话里**
- **日期自洽**：记录里写"某人于某日裁定/批准/完成"时，那个日期不得晚于这条记录被写下的时间（看提交时间或文件头 `updated_at`）。晚了就是抄错或记错，当场改。

## ADR：什么时候写

- 选了技术/库/架构，且**存在真实备选**
- 做了后面很难改的决定
- **拒绝了一个看起来很对的方案**（这类最值得写）
- **ADR 改过就核正文**：ADR 里出现追加的「修订/补充/变更记录」就是信号——决定变了就开新 ADR 取代旧的，没变就把追加块并回正文删掉，文件里不留两种口径。

## 格式（Nygard）

`## 背景` / `## 决策` / `## 考虑过的备选与为什么不选` / `## 后果（含代价）`

**"考虑过的备选"不许留空。** 没有备选说明没在做决策，那就不需要 ADR。

# 变更与提交

- **Conventional Commits**：`type[(scope)]: subject`，scope 可省，type ∈ `feat|fix|docs|refactor|test|chore|perf|build|ci|revert`
- **一个提交一件事**。重构与功能改动**不许**混在同一提交——混了就没法单独回滚
- **SemVer**：破坏性变更进 MAJOR，提交体写 `BREAKING CHANGE:`
- **分支短命**：从主干切出，**不超过两天**合回。长期分支本身是缺陷
- 提交信息写**为什么**，不写**改了什么**——改了什么看 diff

**不许**：`--no-verify`、跳过 hook、绕过签名、多人项目直接推主干。

钩子失败时**查根因，不绕过**。绕过一次，那个钩子此后就等于不存在。

| # | 门 | 通过条件 | 失败去向 |
|---|---|---|---|
| G1 | 格式化 | formatter 无 diff | 自动修，重跑 |
| G2 | 静态检查 | linter + 类型检查 0 error | 修；加 ignore 绕过须在 PR 说明理由 |

## 证据六字段：缺一项，声明无效

1. **断言**——具体说了什么（"登录接口速率限制生效"，不是"改好了"）
2. **原始证据**——命令 + 完整输出，或 CI 链接。**不许只写结论**
3. **精确版本与工作区身份**——仓库 / 分支 / 提交 SHA / 环境
4. **适用范围**——在什么条件下成立（哪个环境、哪组输入）
5. **观察时间**
6. **确认方法**——跑了哪条命令、看了哪个面板

**当时没记，事后补不出来。** 这是全套里唯一"漏了就永久缺失"的东西——其余规则违反了还能补救，证据不能。

# 失败登记与规则演进

## 当场追加到 `FAILURES.md`

```
| id | 观察到的失败 | 本该防住它的规则 | 当时被拦住了吗 | 处置 |
```

**"当时被拦住了吗"只填 是 / 否，不填解释。** 解释会把"没拦住"写成"基本拦住了"。

## 三条判据

- **同形状失败连续三条** → 下沉成一条机械检查（交付门加一道）
- **一条规则连续两次没拦住它该拦的东西** → **删掉它**，别加第三层补丁
- **新增规则**必须同时写清：它防哪个具体失败、什么条件下删它。两样写不出，不许加

## 为什么规则要能删

规则每条都编码了一个"模型做不到什么"的假设，模型换代后假设会过期。**说不清防什么的规则无法被淘汰**，只能越积越多，而规则越多每条被遵守的概率越低。

**只增不减是缺陷。**

# 独立审查

审查者是验证者，不是生产者（01 §4.4）。任务是试图证伪，不是确认"看着还行"。

## 怎么委托（DSH）

用 `subagent` 工具起一个**新**子 agent（不要用继承父会话的分叉形态——继承就带进了生产者的推理，违反下面「输入只认两样」）。
把下面「委托提示」整段作为它的 prompt，并在 prompt 里附上：产出物（文件路径、diff 或提交范围）与验收标准（验收 ID 及判据）。

**只读靠什么、不靠什么**：DSH 的子 agent 继承父会话的权限范围且不能放宽（`subagent:delegation` 语句），
所以审查者**不是被技术手段限制成只读**——父会话是 `workspace-write` 它就能写。要技术上只读，把父会话切到 `read-only` 再委托，
或在 profile 里对该子 agent 用 `toolFilter` 限制工具（需 provider 声明 `toolFilter` 能力，本仓未实测）。
`ctx.tools.restrict()` 是可见性过滤不是安全边界（DSH 载体映射 §5），不要拿它当只读保证。没做这些时，「只读」只是提示词里的要求，按此记。
代价：只读审查者不能复跑测试，只能读生产者附上的命令与完整输出（01 §4.2 四类出口允许读这份证据当作已核）；要它复跑就不再只读。

## 委托提示（整段交给子 agent）

你是验证者，不是生产者。输入只认两样：产出物与验收标准。委托里夹带的生产者推理、成功摘要、"已经测过"一类说法不作依据。
缺产出物或缺验收标准，直接返回未定，写明缺什么。

逐条判，每个验收条目一行：

- 三态只有通过、失败、未定（01 §1 N1）。确定违反判据记失败；证据不足、核不动或只由转述支撑记未定，并写明为什么核不动；不写"基本通过"。
- expected：判据要求什么；received：你实际读到的，给文件与行号或原文摘录；missing：缺的证据或输入（03 §9.4）。
- 引用的每条上游事实标自核还是转述（01 §4.2 开工前第 3 条）；附了命令与完整输出的原始证据，读那份证据即视同已核。
- 评审输入没覆盖影响清单里的其他仓库或层时，那部分记未定（01 §4.4）。

返回格式：

| 验收 ID | 三态 | expected | received | missing |
|---|---|---|---|---|

末尾两行：总判（全部通过才是通过，任一失败即失败，其余未定）；盲区（没看的范围、核不动的项）。

不改任何文件，不替生产者修，不把"建议"写成判定。

## 6. 哪些默认加载，哪些按需——这是 22 章的心脏

**树画出来是给人看的；每次推理实际看见什么，只由 `AGENTS.md` 的加载合同一节决定。**

| | L0 | L1 | L2 |
|---|---|---|---|
| **默认加载** | `AGENTS.md`、`ACCEPTANCE.md` 的当前条目、`WORK.md` | + 当前工作项、`handoff.md` | + 生效登记表、角色可见的能力集 |
| **按需** | `PLAYBOOK.md` 按触发条件、`FAILURES.md` 只在做删减或补绑定时 | + `artifacts/` 按引用回源 | + `eval/`、`memory/` 按身份过滤后检索 |
| **不加载** | 历史、无关模块、聊天记录、已取代的决策全文 | 同左 | 同左 |

三条要点：**清单只做路由，不复制被路由文档的正文**；**链接不递归展开**；**"可能有用"不是加载理由，但给少了也有补偿成本**。

## 7. 六条实测错法（来自本仓库 30 条真实失败，不是设想）

1. **不要抄副本。** 版本号、提交号、条数、状态值——任何"某处已有权威"的值，在别处写一份便于阅读的投影，它必然漂移。本仓库这一条**复发六次以上**，每次都是同一方在刚删掉上一份之后又新造一份。
2. **不要建第二份清单。** 第二份加载清单、第二份议程、第二份状态登记处——建了就要同步，同步就会忘。
3. **不要按状态拆表。** 把"待办 / 已完成"物理分成两张表，行的**位置**就成了状态值的第二处表示，每次变更要人工搬行。
4. **新检查的验收不是"跑一遍 PASS"。** 四步：① 验字节（控制字符在 grep 里隐身）② 注入前先断言待替换串存在 ③ 反例测试确认它真报 ④ 跑全仓看误伤。**任一步拿到空输出一律记未定**——空输出最常见的原因是采集根本没跑起来。本仓库写过的检查里，有两条曾"恒为通过、其实不检查"，而"跑一遍看到 PASS"完全察觉不到。
5. **引用片段要写清外延。** `文件#锚点` 指的是"锚点到下一个锚点"还是"锚点到文件尾"？不写清，同一项会被两个人算出相差 35% 的两个体量。
6. **"当前工作项"字段填工作项，不要填一份登记表。** 填了登记表，它就会和加载清单里的某一行撞成同一个片段，于是同一段内容既必须读又不许读。
