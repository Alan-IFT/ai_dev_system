**效力为零。** 本文是**载体实例**，不是正文，不阻断也不授权；整体删除不影响任何一条规范的效力。它是 [D-041](../docs/决策日志.md#decision-index)（规范载体形态，仍是`提议`）的一份候选答案：把正文 14 章里**今天就能装进一个真实项目**的那一面装配成一份可整份复制走的文本。本文与正文的关系是**实现与语义**，不是副本与权威——正文改了措辞，本文按语义重写，不做逐字同步。

# AI 协作开发项目长期管理标准 v0.2

整理日期：2026-09-07
适用对象：用 Claude Code、Codex、Cursor 等通用工具持续开发和维护软件项目的个人与小团队
定位：**工具无关的项目治理协议**。不是外部认证标准，不需要新装任何服务

---

## 0. 这份标准是什么，和 v0.1 差在哪

**一句话**：它规定项目仓库里必须存在哪些**可被机器和人重新读到**的东西，使得任何工具、任何会话、任何接手者都能答出"现在是什么状态、下一步做什么、凭什么说做完了"。它**不规定**你用哪个工具、怎么写代码、用什么框架。

与 [v0.1](../docs/参考资料/AI协作开发项目长期管理标准-v0.1.md) 的差别是**地基换了**，不是措辞改了：

| | v0.1 | v0.2 |
|---|---|---|
| 依据 | 一个外部公开文档集的工程实践 | 本仓库从 52 个独立来源归纳的四平面架构、六路技术选型调研，以及本仓库自己登记的真实失败清单 |
| 跨工具的说法 | "工具适配层只保留必要差异" | **给判据**：跨工具可依赖的机制只有四类（§2），说不出两类落法的要求不写进来 |
| 装什么工具 | 未答 | **答了：这一档只装一样**（§1） |
| 篇幅立场 | 无 | **规范文档本身可以是负收益**（§1 第三条），因此每条要求都必须带"执行它时喂进什么上下文" |

**三条使用纪律**：① 本文可整份复制进任何项目；② 每个填不出的字段写 `未定`，**留空不等于未定**；③ 每条你自己新增的规则都要能说出它防哪个具体失败、什么条件下删掉它，两样写不出就不许加（§3 N3）。

## 1. 先回答"要不要自己造轮子"

三条结论，都不是推理来的。

**第一，跨工具可依赖的机制只有四类，其余全是宿主绑定。** 把七种机制类型逐一在五个宿主（Claude Code / Codex / opencode / dsh / VSCode Copilot）上核对，五家齐全的只有：**Agent Skills 目录、外部状态存储（文件 + git）、宿主外检查器（CI 与脚本）、人工检查点**。静态指令文件名不统一，条件加载两家没有，运行时拦截五家形态各异，权限与隔离两家有洞。**这四类就是本标准的全部地基**——一条要求落不到这四类上，它就不是跨工具的要求，是某个工具的用法。

**第二，一人多会话这一档，"要装一个工具"的只有一件。** 逐项核过的答复：

| 常见设想 | 这一档的答案 | 什么时候才变成"装一个工具" |
|---|---|---|
| agent team / 流水线调度 | **不装**。子执行者 = 非交互进程 + 强制结构化返回；编排 = 你自己的脚本；状态 = 文件 + 只追加日志 | 出现过"重放导致不可逆副作用重复"，或需要跨机器 |
| codegraph / 代码图谱 | **不装**。宿主原生 LSP；真需要时自建一个进 git 的文本地图 | 自建地图不够用，且有 CI 承载重建与对账 |
| memory 工具 | **不装**。状态文件的候选区 + 方法库；工具自带的 auto memory 只当草稿本 | 团队档，且检索确实找不到东西 |
| 上下文管理工具 | **不装**。一份唯一加载清单 + 两个压缩钩子 | 说不清一次任务的钱花在哪个单元 |
| skill / 方法库 | **装**——五件里唯一有开放规范、五宿主齐全、且按必需性判据不可省的 | 一开始就装 |

**图数据库、向量库、记忆服务、可视化画布一律不装**，理由是同一条判据：*依赖关系本来就在代码里，历史决策本来就在 git 里*——它们只是把仓库里已有的信息重新组织了一遍。

**第三，规范文档本身可以是负收益。** 有一组对照实验（SWE-bench Verified，两个开源权重模型，125 个实例，样本小，不作强论据只作强提醒）：**只加 TDD 流程指令、不给对应的测试上下文，回归率升到 9.94%，比什么都不做更糟**；作者结论是"呈现上下文信息优于规定流程步骤"。

> **推论，也是本标准最重要的一条自我约束**：每写一条"应该怎么做"，必须同时回答"执行它的那一步会被喂进什么具体上下文"。只有前者、没有后者的条文，按这个实验的条件应当视为**有害而非中性**。

**所以"是不是搞复杂了"的答案是分开的两半**：造工具那一半——调研已经答完，这一档几乎什么都不用造；写规范那一半——**篇幅本身就是风险**，本标准的每一节因此都带"需要的上下文"或"坏了怎么被发现"列，没有这两样的条目应当删掉。

## 2. 地基：四类机制，与一条准入判据

| 机制类型 | 跨宿主 | 本标准里的落地形态 |
|---|---|---|
| **Agent Skills 目录** | 齐全（字段集有差异） | `.agents/skills/<name>/SKILL.md`；Claude Code 读 `.claude/skills`，一个符号链接即可保持"一条规则只有一个位置" |
| **外部状态存储** | 齐全（就是文件与 git，与宿主无关） | 仓库里的状态文件、只追加日志、git 提交 |
| **宿主外检查器** | 齐全（宿主之外的脚本与 CI） | CI 必需检查、本地脚本 |
| **人工检查点** | 齐全 | 宿主审批、PR 评审、CODEOWNERS |
| 静态指令 | 部分：文件名不统一 | `AGENTS.md` 为原本；Claude Code 侧一行 import 或符号链接 |
| 条件加载规则（Skills 之外） | 部分 | 只能作并列的探测提示，不作要求 |
| 运行时拦截 | 部分：五家形态各异 | 一套脚本 + 每宿主一份薄适配 |
| 权限与隔离配置 | 部分：两家有洞 | 逐宿主配置，进各项目的附录 |

<a id="two-mechanism-test"></a>
> **准入判据（本标准的宪法条）**：**一条要求说不出两种机制类型不同的落地方式，就不得写进标准。** 两种实例不得同属一个工具。这条的目的不是穷举实现，是**证伪**——一条要求若只能在一种机制上表达，多半是那种机制的特性被误当成了普遍要求。

**最省力的达标配对是「Skills 目录 + 宿主外检查器」**，两者天然不属同一个工具。运行时拦截只能作第三个实例逐宿主落地。

**关于 Cursor**：上面那份五宿主核对**没有覆盖 Cursor**，本标准不替它写映射。要把它接进来，用上面这条判据自己核一遍：它的常驻指令入口是什么、有没有按需加载的能力包目录、有没有能阻断动作的拦截点、权限配置能不能被项目文件放宽。**核不出来的格记 `未定`，不记"支持"。**

**规范不维护各工具的映射表。** 工具的标志名、事件名、配置键会漂，维护一张表等于维护一份必然过期的副本。本标准只写语义与判据，映射由每个项目自己写在自己的附录里，并标注取得日期。

## 3. 三条硬纪律

这三条不成立时，后面全部形同虚设。它们对一切运行成立，不随档位裁剪。

### N1 · 三态：PASS / FAIL / UNDETERMINED

**每个结论都是「结论 + 它的成立条件」的一对。写不出成立条件，记 `UNDETERMINED`。**

一律记 `UNDETERMINED`，**不得折算为通过**：

- 检查没跑、失败、超时
- **输出为空**——空输出永远不是通过。空输出最常见的原因是采集根本没跑起来
- 生成者与验证者是同一方，且判断涉及解释
- 外部写入的结果未知
- 需要人应答而没有答
- 交接缺字段

**「全部 X 通过」在 X 为空集时判 `UNDETERMINED`，不判 `PASS`。** 这是本标准里少数既有推理支撑又有观测样本的条款：本仓库两次拿到空输出、两次差点读成结论，而两次的真实原因都是采集脚本自己坏了。

报告写 `PASS n / FAIL n / UNDETERMINED n`，**三个数分列，永不合并，未定不进通过率分母。**

｜需要的上下文：判定当时的命令原文与完整输出。｜空转信号：一份报告里 `UNDETERMINED` 长期恒为 0，通常不是做得好，是这一态没人在用。

### N2 · 单一权威：副本即缺陷

**每类事实只有一处权威位置。第二处是副本，副本必然漂移——引用写链接，不抄值。**

这条在本仓库**复发六次以上**，每次的形状完全一致：某处已有唯一权威，作者在别处写了一份"便于阅读的投影"，投影随即漂移；其中两次就发生在他刚用同样的理由删掉前几份副本之后。已试过的两种处置各有其限：给副本加机械检查只能覆盖已知形态；"删掉就完了"六次都没防住第七次。

**因此本标准不主张再加检查，只留一条动作**：下一次写下任何"便于阅读的名单、条数、版本号、状态摘要"之前，**先问它的权威在哪一处，以及为什么那一处不够读**。

｜需要的上下文：一张权威位置表（§4 末尾那张就是）。｜空转信号：表里某一行的"唯一位置"半年没人打开过。

### N3 · 每条规则绑定它防的失败与删除条件

**新增一条规则时必须同时写清：它防哪个已经发生过的具体失败、什么条件下删掉它。两样写不出，不许加。**

理由是每条规则都编码了一条会过期的假设——"模型此刻做不到什么"。模型换代之后，说不清防什么的规则删不掉，只会越堆越多，而**规则越多，每条被遵守的概率越低**。

**只增不减是缺陷**：每次新增先问能不能删一条。**失败驱动的修订作用于判据，不作用于样例**——一次失败之后被修订的对象是产生该失败的那条判据，不是把该样例编码进规则；上升不成判据的失败只登记，不生成规则。

｜需要的上下文：失败清单里那一条的编号与原文。｜空转信号：规则条数只涨不跌，且没有任何一条被删过。

## 4. 最小装置：三个无条件 + 两个成对 + 一个入口

**判据不是"树里有这一行"，是"它承载哪条最小职责"。** 遇到树里没画的东西，按判据判，不要硬塞进最近的一格。

```text
项目根/
├─ AGENTS.md        ← 唯一加载清单与常驻规则（Claude Code 侧一行 import）
├─ ACCEPTANCE.md    ← 要做什么、做到什么算完成
├─ WORK.md          ← 做到哪了、怎么恢复、凭什么说做完了
├─ PLAYBOOK.md      ← 只有本项目知道的做法与踩过的坑（第一次踩坑后建）
├─ FAILURES.md      ← 出过的错，一份不分区的清单（与 PLAYBOOK 成对建）
├─ .agents/skills/  ← 方法库：细则按需加载，不常驻
└─ （代码、测试、构建照项目原样，不动）
```

| 文件 | 承载的最小职责 | 必需性 | 加载 | 需要的上下文 | 它空转时怎么被发现 |
|---|---|---|---|---|---|
| `AGENTS.md` | 这次推理看什么、缺了怎么办；不可逆动作清单；停机条件 | **无条件** | 默认，整份 | 项目名、跑起来的三条命令、有没有生产环境、有没有凭据 | 里面有一条规则你从没见它被援引过 |
| `ACCEPTANCE.md` | 要做什么、做到什么算完成；**每条带稳定 ID 与可观察结果** | **无条件** | 默认，只加载当前相关条目 | 本次涉及的条目 ID 与它们的原文 | 半年没有条目被冻结或被改 |
| `WORK.md` | 做到哪了、怎么恢复、凭什么说做完了 | **无条件** | 默认，整份 | 上一次的状态记录与工作副本身份 | 某个字段自建立起从没填过一次 |
| `PLAYBOOK.md` | 本项目特有的做法与坑，每条写清它防什么 | 条件（**与下一行成对**） | 按触发条件，不常驻 | 触发它的那个场景 | 条目只增不减 |
| `FAILURES.md` | 出过的错，一份不分区的清单 | 条件（**与上一行成对**） | 只在做删减、到期审计或补绑定时 | 那次失败的原始现场 | 长期不增；或增了但没有一条被引用 |

**为什么前三个是无条件的**：没有 `AGENTS.md`，"这个项目有没有唯一一份加载清单"连判都判不出——**判不出即未定，不是通过**；没有 `ACCEPTANCE.md`，三态没有对象、完成主张绑不到条目，"完成"不可判；没有 `WORK.md`，恢复、交接、驳回原因全部无处存放。

**为什么后两个必须成对**：规则要绑定一个已登记的失败，只建 `PLAYBOOK.md` 不建 `FAILURES.md`，这条要求**结构性不可满足**——绑定的另一端不存在，而且没有任何东西会发现这件事。本仓库写下这条规定十轮，从未建过那份清单。**空文件比没文件更危险**：它让"有没有"这个检查恒为通过。

**为什么不是 14 个文件**：四个平面 14 个部件是**职责划分**，不是目录结构。照着章节建目录是这套东西最容易犯的错，也正是它自己要防的失败：规则只增不减、启动固定开销吃掉窗口。

**权威位置表**（复制进 `AGENTS.md`，按项目改）：

| 事实 | 唯一位置 |
|---|---|
| 意图与验收（带稳定 ID） | `ACCEPTANCE.md` |
| 任务状态、下一步 | `WORK.md` |
| 项目知识、踩过的坑 | `PLAYBOOK.md` |
| 失败记录 | `FAILURES.md` |
| 重大决策 | `docs/adr/NNNN-*.md` |
| 证据（测试 / 构建 / 部署结果） | CI 产物；`WORK.md` 只存指针 |
| 代码结构、依赖、配置 | **代码本身**——不写进文档，它会先于代码过期 |

## 5. 一次运行的协议

### 5.1 先声明这次运行是哪一种

两个正交属性，**在起点处声明**，因为它决定出口是什么：

- **产出类型**：**交付型**，出口是验收；或**事实型**（诊断、考古、状态重建、影响面调查），出口是**一份带成立条件的事实 + 一个假设 + 一组待人裁决项**，不是变更。
- **起点状态**：**从头**，或**接手**。

**事实型运行读到停机条件时记未定并进入下一步，不转阻塞。** 时限到达是一个合法停止点，其去向是**交接**而不是阻塞。

这不是形式：**缺陷的形状由运行类型决定**——改条文类的运行只撞"该拦没拦住"，事实型撞"规则之间对不上"，**接手撞"写着但从没被执行过"**。接手是唯一会去问"当前工作项是什么、事实源是哪份"的运行类型，本仓库那批"长期空转且空转不产生任何信号"的缺陷里，有三条是在一次真实接手运行的**前十分钟**暴露的，另两条是同一轮更新架构图时撞到的。

### 5.2 开工前八问：答不出就停

**①** 当前工作项与其状态版本 **②** 仓库 / 分支 / 提交 **③** 交付型还是事实型 **④** 从头还是接手 **⑤** 本次可触范围 **⑥** 本次禁止的动作 **⑦** 完成判据是 `ACCEPTANCE.md` 的哪几个 ID **⑧** 上次遗留项。

**不得未经判断覆盖其他工作留下的修改。** 已有明确授权的常规实施，不因采用本标准而多加一道确认。

### 5.3 执行中

- 简单修改直接做，在已有记录里留一句。
- **跨模块、接口或数据变更**必须先写影响清单、实施顺序与对应验证。
- 遇到阻塞记录**缺少的条件**；不能把"等待某个条件"写成"已完成"。
- 新发现但不属于本次目标的问题**登记为后续工作项**，不就地扩大范围。
- **不可逆动作先问人，同意只对本次有效**：删文件 / 分支 / 表；`push --force`；有未提交改动时 `reset --hard`；写生产（迁移、部署、回滚、改配置 / DNS / IAM）；schema 变更；无精确 WHERE 的批量写；发布；对外发送；装新依赖、改锁文件、改 CI 与权限文件；改已冻结的验收条目。**不在清单但你觉得可能不可逆的，按不可逆处理**——三问任一为是就问：撤销要不要人工介入？要不要恢复备份？会不会被别人看见？

**停机条件，命中任一即停下报告，不许继续试**：

- 同一故障连续两次修复无效且无新证据（重试前必须改变一个输入变量并写下改了什么）
- 超出第 ⑤ 项声明的范围
- 需要不可逆动作而未获同意
- `UNDETERMINED` 挡在完成判据上
- 连续三次工具调用失败
- **发现自己在改测试而不是改代码**

**停机不是失败。** 带着"知道什么、不知道什么、下一步要什么"停下，比猜着做便宜。

### 5.4 收工前：证据六字段

**完成声明后面跟一段短记录，缺一项声明无效**：

1. **断言**——具体说了什么（"登录接口速率限制生效"，不是"改好了"）
2. **原始证据**——命令 + 完整输出，或 CI 链接。**不许只写结论**
3. **精确版本与工作副本身份**——仓库 / 分支 / 提交 / 环境
4. **适用范围**——在什么条件下成立
5. **观察时间**
6. **确认方法**——跑了哪条命令、看了哪个面板

**当时没记，事后补不出来。** 这是全套里唯一"漏了就永久缺失"的东西——其余规则违反了还能补救，证据不能。

**验证后代码继续变化的，须说明证据是否仍然有效。** 任务完成不自动代表已合并、已部署或已发布。

**交接分两半**：一份只含当前判断所需内容的**短交接**（结论、身份、状态版本、未完成原因、下一个原子动作），和**活动工作集的引用**（原文落在可回读位置，不随历史逐轮携带）。**会话结束与上下文压缩同等对待**——之前先把状态与教训外部化。

### 5.5 状态机：一套，不要两套

| 状态 | 进入 / 退出依据 |
|---|---|
| `planned` | 目标与范围足以开展工作 |
| `in_progress` | 已开始修改或调查 |
| `blocked` | 记录缺失条件、影响和解除方式 |
| `in_validation` | 已有可检查结果，验收未全部结束 |
| `done` | 有证据六字段与必要的文档更新 |
| `cancelled` | 记录原因与已有工作的处理 |

`blocked` 解除后回到适当的执行状态；验证失败回 `in_progress`；`done` 之后发现验收不成立可以重新打开并记录原因。

**不要按状态拆表。** 把"待办 / 已完成"物理分成两张表，行的**位置**就成了状态值的第二处表示，每次变更要人工搬行——这是 N2 的一个变形。

## 6. 按变更风险选流程

| 类型 | 例子 | 最低记录与验证 |
|---|---|---|
| 轻量 | 文案、样式、小范围且行为明确的修复 | 一句变更记录 + 适用的构建或行为检查 |
| 常规 | 新功能、模块内重构、一般缺陷修复 | 工作项 + 相关测试 + 文档同步 + 证据六字段 |
| 高影响 | 数据迁移、公共接口变化、核心架构调整、生产发布 | 影响与依赖清单、分阶段计划、兼容与恢复策略、针对关键风险的验证 |

**不以修改行数单独判断风险**，也不要求所有任务追求同一个覆盖率。

**已有用户和数据的项目必须明确数据与接口的兼容策略。** 未上线项目可以选择破坏性重构，但要记录这个前提——**不能把"零兼容"推广成所有项目的默认规则**。

错误处理**不得未经声明地掩盖失败或改变用户意图**。重试、缓存、降级是否可用由项目策略规定，并保留可识别的执行记录。

## 7. 分档：L0 → L3

四档不是必经阶段，是**同一套职责在不同规模下的形态**。**升级到下一档的唯一条件是：上一档的验证能力跟得上。自主度的上限永远是"能廉价可靠验证的量"。**

| 档 | 场景 | 新增什么 | 明确不装 | 升级信号（任一触发即评估） |
|---|---|---|---|---|
| **L0** | 一人一工具 | §4 的三个无条件文件 + `.agents/skills/` + 权威位置表；git 即证据载体 | 一切服务、钩子、索引、图库、向量库、MCP | 第一次发现"写在指令里的规则被忽略了"（你需要的是约束，不是提醒）；第二次发现"自己忘了跑某层验证" |
| **L1** | 一人多会话 | **一个 hook 脚本 + 一份 deny 规则**：所有事件都往同一份只追加日志写一行——它同时是状态转换记录、拦截层的对账源、工作集落盘点；deny 规则守住危险命令；子执行者用进程级契约（非交互进程 + 强制结构化返回）；`work/handoff.md` 与 `work/artifacts/`；租约文件 + 一条巡检 | agent teams、任何编排引擎、记忆服务、向量库、网关改写 | 出现过一次"重放导致不可逆副作用重复"；并行单元常态超过五个；说不清一次任务的钱花在哪个单元；**出现第二个人** |
| **L2** | 团队 | **CI 必需检查 + 仓库 ruleset + CODEOWNERS**（唯一的约束级通用层）；`DECISIONS.md` 与生效登记表；`GATES.md`；`SOURCES.md` 具名到人；评估集按用途三分区；记忆候选池 | 编排引擎、策略引擎、任何 SaaS 观测平台 | 需要无人值守；豁免与跳过开始堆积 |
| **L3** | 无人值守 | **前置条件不是工具，是一句话**：有一个不需要人在场就能拒绝坏输出的判定器，且它有已知答案的回归集、跑在生产者够不到的上下文里。装：容器 / VM 级隔离；每层拦截的独立探针跑成定时任务；三类停机条件全部程序化；预算与范围创建时固化、执行中只能收窄 | — | — |

**L2 是"责任分离"第一次有对象的档位**：验证者与生成者分开、写入权与生成权分开、事实门禁上线。**证明修复的测试不得被修复者修改。**

## 8. 理论要求而市面无物：必须自建的小件

下面每件都是**五个宿主全体不提供**的，每件都只有几十行，**每件都必须自带"坏了怎么被发现"，而探测不能是它自己**。

| 小件 | 形态 | 坏了怎么被发现 |
|---|---|---|
| **租约** | `{单元, 持有者, 到期时间}` 一个文件 + 执行者定期续期 + 一条巡检把过期租约转阻塞 | 巡检由另一个进程 / cron 跑；"过期但其实还活着"的误判次数记入失败清单 |
| **不可逆动作回执** | 动作前先写回执（含幂等键），重放时先查回执 | 对账：外部系统里的写入数 vs 回执数 |
| **三类停机条件** | 证据型（判定器给失败）、停滞型（连续两轮输入无变化或结果哈希不变）、上限型（预算 / 轮次）——**任一触发即转阻塞并升级，不是标"部分完成"** | 留一个故意发散的任务作回归样本，期望它被停住 |
| **汇合缺失报告** | 收口时打印 `expected / received / missing` 三个数 | 故意停掉一个分支，期望 missing 非空且收口拒绝宣告完成 |
| **豁免到期** | 一份带到期日的豁免清单 + CI 检查到期 | CI 是宿主之外的必经路径 |
| **拦截层回执对账** | 每个阻断型钩子**放行时也写一行日志**；CI 断言"每个受管动作都有对应日志" | 缺席 = 钩子没跑；探测在宿主之外 |
| **结构化转换记录** | 事件日志每行带提交 SHA、工作副本、时间、三态裁定 | 每轮开始校验尾行合法，并比对当前 HEAD 与最后一条记录的 SHA，不一致即未定 |
| **记忆到期扫描** | 读条目的失效时间与来源版本，过期移出；缺来源即红 | **必须在 CI 里跑，不由写记忆的那个执行者跑** |
| **指令截断金丝雀** | 指令链最末尾放一句金丝雀指令，定期跑 | 金丝雀不出现即说明被截断了 |

**五个宿主没有一家为"豁免 / 跳过"提供失效时间，也没有一家提供拦截层自身的独立失效探测。** 这两件在任何工具上都只能由工具之外的 CI 对账补上——**它们不是选型问题，是必须自建的小件。**

## 9. 接入与验收：装完怎么知道它真的生效了

> **一个落地项不算"已接入"，除非它同时具备两样东西：一个他证的验收信号，和一个"它空转时会发出的信号"。** 后者说不出的项，一律记**未定**，不计入接入进度。

这两样不是一回事：验收信号回答"装的那一刻它对不对"，空转信号回答"三个月后它还活着吗"。**本仓库那五条最难堪的缺陷全部是第二种缺失——它们装的那一刻都是对的。共同点是：出问题的地方都有人写过，没人再看过。**

**他证的定义**：产出被验收对象的一方不参与判定，且判定所依据的信号不是由该方生成的文本。**不算他证的**：模型说"我已经按清单加载了"；一次"跑一遍看到 PASS"；一份由同一方写的自评报告。

**新增一条检查时的四步验收**（不是"跑一遍 PASS"）：

1. **验字节**——控制字符在 grep 里会隐身，先按字节看一遍
2. **注入前先断言待替换串存在**
3. **反例测试**——确认它真的会报
4. **跑全仓看误伤**

**任一步拿到空输出一律记未定。** 本仓库自写的检查里出过三处缺陷，其中两处是"能通过但根本不检查"，而"跑一遍看到 PASS"完全察觉不到。

**从零接入的顺序**：声明运行类型 → 建 `ACCEPTANCE.md` 并冻结第一批条目 → 建 `WORK.md` → 建 `AGENTS.md`（每行写 `why`）→ **只用这三个文件跑一次真实运行** → 第一次踩坑之后成对建 `PLAYBOOK.md` + `FAILURES.md` → 装第一个检查器。

**从半路接手的顺序不同，第一步不是建东西**：声明运行类型并把出口写成"一份带成立条件的事实" → **测绘**（这个项目现在有什么、哪些是活的）→ **对疑似空转项做一次反例注入** → 只补测绘判为"缺失"的 → 由**没参与测绘的一方**做一次照单加载演练 → 才转入交付型运行。

## 10. 六条实测错法

来自本仓库登记在案的真实失败，不是设想。条数是仓库当前状态的函数，此处不写字面量。

1. **不要抄副本。** 版本号、提交号、条数、状态值——任何"某处已有权威"的值，在别处写一份便于阅读的投影，它必然漂移。本仓库这一条复发六次以上，每次都是同一方在刚删掉上一份之后又新造一份。
2. **不要建第二份清单。** 第二份加载清单、第二份议程、第二份状态登记处——建了就要同步，同步就会忘。
3. **不要按状态拆表。** 行的位置成了状态值的第二处表示。
4. **新检查的验收不是"跑一遍 PASS"**（四步见 §9）。
5. **引用片段要写清外延。** `文件#锚点` 指的是"锚点到下一个锚点"还是"锚点到文件尾"？不写清，同一项会被两个人算出相差三成以上的两个体量。
6. **"当前工作项"字段填工作项，不要填一份登记表。** 填了登记表，它就会和加载清单里的某一行撞成同一个片段，于是同一段内容既必须读又不许读。

**再加一条来自数量型断言的教训**：一个数若同时满足 (a) 是仓库当前状态的函数、(b) 有唯一可机械解析的权威载体、(c) 却出现在权威之外的散文里——**就交给脚本现取，不要手写**；口径写不死、权威在仓库之外、带相对时间锚、或数字不承重的，**删掉字面量改定性表述**。只有被已生效决策冻结的结构常量与对已完成事件的量度才留字面量。

## 11. 这份标准自己怎么演进、怎么退场

- **项目必须记录它采用的标准版本。** 标准升级后由项目**显式评估并升级**，不在任务执行过程中自动跟随未经评估的最新规则。
- **每条规则按 N3 携带删除条件**；模型换代时做一次到期审计，问每条"它防的那个失败现在还会发生吗"。
- **例外记录至少含**：规则编号、偏离原因、影响范围、决定人、替代检查、复查条件。**例外不能只是一份让检查永久跳过的无说明名单。**
- **文档冲突时**：先检查适用范围、状态与明确的替代关系。**日期较新或标题写着"终稿"，不自动意味着已取代其他规范。** 缺少明确裁定时登记冲突；需要负责人决定的部分等待决定，其他独立工作可以继续。
- **规模纪律**：本标准自身受"只增不减是缺陷"约束。删减的对象优先是**没有"需要的上下文"列的条目**——按 §1 第三条，那些条目应当被视为有害而非中性。
