## 原文结论与适用限制

本文复盘了一个月里"Claude 响应变差"报告的三处独立根因（API 未受影响）：

1. **默认思考档位改动**：3-4 把 Claude Code 默认 reasoning effort 从 high 改为 medium 以降尾延迟；被判为错误取舍，4-7 回退为默认高档、简单任务再手动降。影响多个模型。
2. **缓存优化丢弃先前思考**：3-26 上线一个"会话闲置超一小时后清掉旧思考段以降重启成本"的改动；实现有 bug——本应只清一次，却在此后每一轮都清，且若在工具调用中途追加消息会连当前轮思考一起丢。结果是 agent"失忆、重复、乱选工具"，且"越执行越不知道自己当初为何这么做"。该 bug 处于 Claude Code 上下文管理 × Anthropic API × 扩展思考三者交叉处，**过了多轮人工与自动代码评审、单元测试、端到端测试、自动化校验与内部试用（dogfooding）才被发现**；叠加只在陈旧会话这一角落触发且难以复现，历时一周多才定位根因。4-10 修复。
3. **一行系统提示限长导致质量下降**：4-16 为降 Opus 4.7 的冗长，往系统提示加了一句"Length limits: keep text between tool calls to ≤25 words. Keep final responses to ≤100 words unless the task requires more detail."；经数周内部测试、在当时那套评估上无回归，遂随 4-16 发布。事后**用更广评估集做逐行消融（removing lines from the system prompt to understand the impact of each line）**才定位到这一行造成可测下降，4-20 回退。该改动同时命中多个模型。

作者给出的整改方向（"Going forward"）：更大比例内部员工使用与用户完全相同的对外构建（而非测新功能用的内部版本）；每次系统提示改动跑全套 per-model 评估、继续逐行消融、并新建工具让提示改动更易评审审计；在 CLAUDE.md 加指引使模型专属改动只对目标模型生效；对任何可能牺牲智能的改动加 soak period、更广评估集与灰度。另记：事后用 Opus 4.7 回测该缺陷 PR（给足代码仓库上下文时）能找出 bug，Opus 4.6 找不到——故为代码评审补更多仓库上下文。

适用限制：这是厂商对自家单一产品线三处缺陷的复盘，直接对象是该产品的系统提示与缓存实现；本卡把其中两条抽象为**上下文/提示策略变更的评估纪律**落进 03 §11.1，抽象后不依赖该产品，也不引用任何模型名、版本号、API 头名与百分比。

## 缺口、采纳与不采纳

**采纳一：提示/上下文策略变更须拆到可单独回退的最小单位（逐行/逐块）跑有／无两组，模型专属改动绑定到目标模型。** 落点 [03 §11.1](../03-Agent信息获取与上下文管理.md#context-evals) 的"新增规则或方法须证明增量"段（既有已要求跑有／无两组、用例有难度梯度、轨迹中检索关键步骤）。

- 缺口：03 §11.1 现有"跑有／无两组"约束的是"这条规则整体有没有增量"，没有规定**改动的粒度**。本文教训：多行系统提示一起改、在当时评估集上整体无回归就发布，事后要**逐行消融**才定位到是"哪一行"造成下降；且"限长 ≤25/≤100 词"这类看似无害的一行会对智能造成可测的负面影响。若改动不拆到可单独回退的最小单位，就会出现"整体看起来退化、但说不清是哪一条"，无法做规则减法。另一面：一条改动同时命中多个模型，某模型上的收益/无害不代表另一模型，模型专属改动须绑定到目标模型。这是 §11.1 既有"新增规则或方法须证明增量""同一方法也是版本变更后的减法触发"同一机制的收紧。
- 触发条件：新增或修改系统提示、入口规则、上下文/压缩装配策略时；尤其是一次提交里改了多行/多块。
- 责任角色：产出改动的一方拆分改动并声明每一单位；维护者组织有／无两组评估；任务负责人定判据。
- 可定位工件：改动的最小回退单位清单（逐行/逐块）、每单位的有／无两组评估记录、该改动绑定的目标模型标注。
- 验收/失败处置：一次改动含多行/多块时，须能对每一单位单独跑有／无两组或单独回退；只有"整包"评估、无法归因到具体单位的，记未定、不发布为默认。模型专属改动未标注目标模型、或一条改动无区分地命中多个模型的，判缺陷。定位到某单位造成下降即按 §11.1 的规则减法删除并记版本与理由。
- 失败依据：本文披露的第 3 处缺陷——多行系统提示合并改动、当时评估集无回归即发布，事后逐行消融才定位到某一行造成可测下降；及其"模型专属改动应绑定目标模型"的整改。属厂商一手披露的可追溯风险。
- 复查/删除条件：项目的提示/策略改动本就以最小单位提交、且每次都能单独回退与单独评估时，本条退为提示。

**采纳二：有损的上下文改动（压缩/裁剪/缓存驱逐）要有能探测"思考历史被静默丢弃"的回归用例，不能只靠常规评审。** 落点 [03 §11.1](../03-Agent信息获取与上下文管理.md#context-evals) 表格"压缩与恢复"行；与 [03 §7](../03-Agent信息获取与上下文管理.md#externalization)"这类组件的失败方式是静默丢线索而不报错"、[§8](../03-Agent信息获取与上下文管理.md#recovery) 同一机制。

- 缺口：03 §11.1"压缩与恢复"行现评估"未压缩／压缩后""正常交接／强制终止／缺失检查点"下"下一动作可恢复、未解决错误和禁止项未丢"，但**没有单列"有损裁剪/缓存驱逐把思考历史静默丢弃"这一形态**，也没写明它对常规质量门的穿透性。本文第 2 处缺陷正是：一个缓存优化 bug 在会话中途持续丢弃思考段，使 agent"越执行越不知为何这么做"，而它**过了多轮人工与自动评审、单测、端测、自动化校验、内部试用全部关口**，只因触发条件是陈旧会话这一角落且难复现，拖了一周多。这与 03 §7 已有的"有损压缩组件失败方式是静默丢线索而不报错，须端到端对照、不得以'输出变短'验收"是同一principle 的又一份厂商一手佐证，也说明常规评审/单测/端测不足以捕获此类静默丢弃，须有针对性的回归用例。
- 触发条件：接入或修改压缩、裁剪、缓存驱逐等有损上下文组件时；尤其影响思考/推理历史留存的改动。
- 责任角色：维护者组织"思考历史是否被静默丢弃"的回归用例；工具维护者按 §12 登记该组件在正常与角落条件（如陈旧会话、工具调用中途追加消息）下的实测行为。
- 可定位工件：一组能探测"思考/推理历史被丢弃"的回归用例及其在有损组件开/关下的对照结果；§11.1 逐例记录。
- 验收/失败处置：有损上下文组件变更后，须跑能探测思考历史静默丢弃的回归用例（覆盖陈旧会话、中途追加等角落触发），并按 §7 端到端对照行动路径（步骤数、重复动作、乱选工具），不以"输出变短/更省 token"验收；未做此探测即记未定，不升为默认。
- 失败依据：本文第 2 处缺陷——缓存优化 bug 静默丢弃思考历史致 agent 失忆/重复/乱选工具，且穿透全部常规质量门、历时一周多才定位。属厂商一手披露的可追溯风险。
- 复查/删除条件：项目无有损上下文组件（不做压缩/裁剪/缓存驱逐）时本条无对象。

**已由 03 现有条款覆盖，不重复采纳**：

## 跨方向建议（不由本方向修改）

- 给 **01 项目管理标准 §4.5（发布）**：本文根因之一是**内部试用（dogfooding）用的不是与用户相同的对外构建**——内部版本加上另一个正交实验（改思考显示方式）恰好在大多数 CLI 会话里掩盖了该 bug，使内部测试即便测了外部构建也没触发，拖了一周多才定位。整改是"更大比例内部员工使用与用户完全相同的对外构建"。这属发布/试用流程，01 §4.5 若在发布前验证或灰度条款里补一句"内部试用须覆盖与用户相同的对外构建，避免内部专属构建掩盖用户侧缺陷"，可作外部佐证。本卡不改 01。
- 给 **04 可靠性安全与运行维护 §5（渐进发布、配置变更与容量）**：本文另一根因是**并行实验掩盖当前变更的症状**——一个内部服务端消息队列实验与一个正交的思考显示改动，共同压住了缓存 bug 的表现，使其在测试中难以复现。渐进发布/对照中，若同时在跑其他实验，候选与对照之间的差异会变得不可解释、当前变更的症状被掩盖。04 §5 可补一句"候选/对照的差异须可解释；并行实验会掩盖当前变更的症状，发布诊断时须能识别并隔离并行变量"。本卡不改 04。
- 给 **04 §6（AI 协作运行的可观测、可重复与运行开销）**（弱建议）：本文"用更强模型回测、给足仓库上下文才定位 bug"与 C-22 的"用更强模型审计弱基准"是同一类做法（拿更强模型当审计/观测者）。若 04 §6 的可观测条款要收这条，可由收口人统一处置，本卡与 C-22 各留此一句，不各自展开。

## 验证办法

- 改动粒度：抽取一次提示/策略改动，检查它是否拆成了可单独回退的最小单位、每单位是否有有／无两组记录；只有整包评估、无法归因到具体单位的判待改。检查模型专属改动是否标注并绑定了目标模型。
- 静默丢弃探测：在获准测试环境构造陈旧会话（超过驱逐阈值）并在工具调用中途追加消息，运行含有损上下文组件的版本，检查是否有回归用例能探测到思考/推理历史被丢弃（表现为后续轮次重复动作、乱选工具、无法解释先前决策）；只靠常规评审/单测/端测而无此探测即判缺口。
- 以上均未在本仓库运行，本轮全部记未定。本文为披露/复盘文本，其所述整改本卡不核实、不背书。
