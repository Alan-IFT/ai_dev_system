## 原文结论与适用限制

同一提示词、同一硬件，把温度设为零或锁定随机种子，**都不足以保证输出一致**。确定性要分两层：单独运行重跑一致（run-to-run）与不同并发负载下一致（批次不变性），前者成立不蕴含后者。根因不是请求间互相污染，而是推理引擎为填满硬件、按当次批形状动态改变浮点累加的规约拓扑，而浮点加法不满足结合律。作者按算子逐一说明哪些参数安全（只切空间维度的分块与调度顺序）、哪些破坏不变性（切规约轴的拆分），并给出把规约结构与批形状解耦的做法。三点对本项目有用的元结论：其一，确定性要显式购买——文中把它称为"确定性 ↔ 吞吐"的取舍，锁死拆分意味着放弃一部分并行度；其二，保证的强度分级——有的路径由后端 API 契约保证，有的只是把工作区压到最小以间接逼出单段规约、"无 API 级保证"，有的因闭源库不可见而"都是基于测试的"；其三，开关可能被静默旁路——作者引用的 Issue 指出编译模式下该分发路径缺失，"batch-invariant dispatching is absent here, so it is silently skipped"，且明确"任何关于底层算子行为的绝对保证，都必须严格限定在明确的软件版本与编译配置环境内"。

适用限制：场景是**自建推理服务的基础设施团队**，与"大型软件项目长期维护"只在很窄的一面重合。全文无对照组、无消融、无原始数据；自测现象未给样本数、硬件与版本。所有实现结论绑定 vLLM 某一版本、特定 GPU 架构、特定精度与执行模式，作者本人已声明其时效边界。通过第三方 API 使用模型的项目不掌握文中任何一个开关。

## 缺口

04 §8（原 §6，本轮两次顺延）要求"可复制的运行验收记录"，[01 §5.2/§5.6](../01-项目管理标准.md) 要求测试与闸门给出可复查结论，但四份正文都默认"同样的输入重跑能得到同样的结果"。当 AI 参与产出时这个前提不成立，而标准里没有一处说明**复现在这里指什么、哪些条件可以钉死、钉不死时证据怎么算数**。这直接影响 04 全篇证据的可信度。

## 采纳

- 新增 [04 §6.2 AI 参与产出的可重复性](../04-可靠性安全与运行维护.md#agent-run-observability)。**触发**：把 AI 运行结果当作验收证据、回归基线或复现依据时。**责任**：任务负责人声明本次复现的定义，工具维护者登记可钉死的条件。
- 复现须先声明对象：逐字一致的输出、等价的产物、多次采样落在约定区间三者代价不同，默认不承诺第一种。**失败依据**：把"再问一次模型看是否说同样的话"当复现，会把正常波动记成回归，也会把真实回归当波动放过。
- 相同提示词与相同参数（含温度为零、固定种子）不足以保证一致；并发负载会改变底层规约顺序。因此**输出不一致不能直接推断输入、代码或数据变了，一次一致也不证明后续一致**。**失败依据**：文中自测的"单独请求一致、有并发请求不一致"。
- 可重复性声明绑定模型、推理服务、版本与配置组合，按 [03 §12](../03-Agent信息获取与上下文管理.md#capability-acceptance) 登记，不跨版本沿用；并标注该声明是**契约保证、实测观察还是间接推断**。**失败依据**：文中同一功能在不同精度路径上分别属于这三档，其中一档明写"无 API 级保证"。
- 开关存在不等于生效：确定性配置可能被另一条执行路径静默绕过且不报错，启用后须用反例验证（同一输入在有并发负载与无并发负载下比较），失败按 [01 §5.6](../01-项目管理标准.md) 判检查器故障。**失败依据**：文中引用的编译模式下分发缺失被"静默跳过"。
- 严格逐字可重复需要放弃一部分并行度，是有代价的运行模式，由有权人按场景确认适用范围；不自建推理服务的项目不掌握这些开关，只能把可重复性定义在产物与区间上（后半句为本项目推导，标为设计选择）。

## 不采纳

- 全部 GPU 与算子实现内容：浮点表示与 ULP、Tiling、Split-K、Swizzle、寄存器与共享内存约束、SM80 与 SM90 执行范式、FlashAttention 与 FlashDecoding、NCCL 的 Ring/Tree 与 Channel 切分。属推理引擎工程，不进项目管理标准。
- vLLM 的具体开关、环境变量、代码路径与版本号，以及"建议开启批不变模式"的做法：绑定自建推理服务，绝大多数采用项目无此对象；写进标准会立刻过期。
- 文中出现的全部数字（硬件常量、阈值、切换点、某 PR 标题里的端到端延迟改善）：常量非本项目可复核，效果数字条件不明，均不作为规则论据。
- "确定性是科学进步基石"一类立场表述：不作为规则依据。
- 未展开的 MoE 与 NCCL 深层机制：作者声明未写，本卡不推测。
- **可重复不等于正确**这一条本想写入正文，最终只在本卡记录：它是本项目判断而非该来源结论，且 [04 §8](../04-可靠性安全与运行维护.md#operational-acceptance) 的判据已经要求验收按预先确定的判据判断，正文再写一遍属重复。

## 验证办法

取一个 AI 参与产出的验收项，走查四问：本次复现指哪一种（逐字/产物等价/区间）；声明绑定了哪个模型与服务版本、属契约保证还是实测；有没有做过一次反例比较（有并发负载与无并发负载下同一输入）；声明的复查触发是什么。任一项缺失记未定，不因"上次跑出来一样"就登记为可复现。

## 跨方向建议（不由本方向修改）

- 给 03：§12 的按版本能力验收目前面向"宿主能力是否可用"；建议把"输出可重复性属于哪一档保证"列为该登记表的一个字段，避免 04 §6.2 与 03 §12 各自维护一份版本表。是否合并由主执行者裁决。
- 给 01：§5.2 测试纪律与 §5.6 闸门默认"重跑结果相同"。涉及 AI 产出的闸门（例如以模型判定为检查器）需要说明其判定是否可重复、不可重复时如何取信，本轮未在 01 落地。
