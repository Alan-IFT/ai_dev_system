## 原文结论与限制

作者的解读：该产品把模型接入、工具执行、会话记录、循环本身与界面全部做成插件，其可拆装性建立在一条机制上——组件对共享环境的每一次修改（事件注册、提供服务、挂子组件、定时器/文件监听/子进程/连接等外部资源、状态变更）都通过唯一原语登记，登记时立即执行并交回一个撤销函数，卸载时按后进先出逆序执行；子组件的撤销挂在父组件上，形成递归的级联清理，作者不必单独维护一张"谁依赖谁"的清理表。框架进一步用四条约束保证登记不被绕过（唯一 API 入口、上下文用代理拦截属性读写、已卸载组件上再注册直接报错、模块加载失败整体回滚）。

三点边界声明值得单独记（按本文转述，其论文原文未核实）：

- **系统边界按位置划分**：本系统能独占修改且能恢复原状的位置在边界内，可追踪可恢复；公共文件、别的进程也在写的东西在边界外，框架既不追踪也不声称能恢复。
- **获取与发射两阶段**：打开、分配、派生这类获取动作在边界内可逆；数据一旦离开系统（写出、发送）就在边界外不可逆，只能靠暂缓发射或补偿动作处理，且补偿不再有元理论保证。
- **结构性保证不等于语义性保证**：运行时保证"撤销会被调用"，不保证"撤销写得对"；逆的正确性是组件作者的义务，运行时不验证。恢复的判据是观察等价，不要求物理复原。

另外两处工程细节：工具在多层作用域间按"全局层 → 各祖先层依次覆盖 → 限制规则 → 当前层自注册最优先"遮蔽；某个入口名被硬编码保留，任何插件不得注册或覆盖，理由是"一个在默认部署下看似空闲的名字，一旦某个预设挂载进来随时可能冲突"。

适用限制：对象是一个 JavaScript 插件运行时，其可逆性依赖该语言的原型系统、代理与可卸载模块注册表——作者自己指出这套设计在编译型语言里难以落地。**产品本身很新，本文无运行数据、无对照、无规模验证**；作者自述在写示例插件时把界面搞崩，但该文自带的错误截图显示的是配置校验失败而非热更新回滚失败，作者归因可能不准。文末的仓库数与星数是写作时的参考值。本卡不把该产品的任何设计当作已验证的工程结论，只取其中与架构描述有关、且能在本项目找到对应失败的语义。

## 缺口、采纳与不采纳

02 §3 模块文档记职责、接口、依赖、数据所有权、配置开关，但**不记该模块运行起来后往共享环境里放了什么**；§11 废弃只到"下线日期 + 替代者 + 消费者迁移"，模块被移除后残留的订阅、定时任务、注册名与外部资源没有登记位置。§4 依赖规则管"谁能依赖谁"，不管"多个模块共用一个标识空间时谁的名字算数"。本篇正对这三处。

已观察失败：

- **F-t** 组件的清理代码与创建代码分离时，完整清理难以验证；某编辑器的扩展宿主无法卸载单个扩展，禁用或卸载必须重启整个宿主（本文对既有生态的陈述，二手）。
- **F-u** 名字冲突在组合时才暴露：一个默认部署下看似空闲的入口名，某个预设挂载后与既有入口撞名（本文所述的保留名设计动机，二手）。本项目已有一手同类证据：[A-05](A-05-契约化多端领域模型.md) 记录的规范分发只增不删导致新旧同名命令并存、执行者调用到已废弃的那个。
- **F-v** 一个可选界面插件的配置缺一个字段，整个前端进入加载失败页（该文自带的错误截图）。

采纳（逐条落点）：

1. **模块文档增加"共享环境注册项"**：该模块启动后向共享环境注册或占用的东西及其撤销方式 → [02 §3](../02-项目架构描述规范.md)。绑定 F-t。同时写明"框架能保证撤销动作被调用，不保证撤销写得对"，下线验收要有残留实测，不以"框架会自动清理"代替。删除条件：模块无任何共享环境注册项时该行留空。
2. **共享命名空间的分配与遮蔽规则** → [02 §4](../02-项目架构描述规范.md#dependency-rules)。绑定 F-u。删除条件：项目不存在多方共用的标识空间时无对象。
3. **回退能力按"尚在系统内"与"已越过边界发出"分别声明** → [02 §5.4](../02-项目架构描述规范.md#contract-migration)。绑定 02 §7 已登记的违反症状（重复发货、重复通知）与本文的获取/发射两阶段划分。删除条件：写不出（这是边界事实，与实现无关）。

不采纳：

- Fiber 六状态、`ctx.effect`、代理拦截、依赖注入、热更新事务、工作线程隔离、工具并发判定、预设的两层作用域链、事件日志只追加：**载体绑定**，是某个 JavaScript 运行时的实现，02 不规定被描述系统的实现。
- "everything is a plugin"、核心循环也可替换、没有哪个模块地位特殊：**证据不足**。本文自述该产品只挂了一个循环实现且工厂只允许注册一次，可替换性未被实际验证；作者也承认"效果怎么样还得看这套架构在真实使用里能撑多久"。02 §11 已规定服务化/拆分需以质量场景验证收益，不引入"一切皆可替换"的取向。
- 恢复判据取"观察等价"：**已覆盖**，[02 §6](../02-项目架构描述规范.md#data-migration) 的比对与切换已要求比较记录身份、关键业务字段/聚合与完整性并声明抽样范围与误差判据，已是可操作形式，不再引入抽象表述。
- 事件日志作单一事实源、持久化/上下文/界面三路投影：**已覆盖**，02 §9 派生工件已规定派生物按缓存处理、声明权威。本文作为该条的第二个来源记在此。
- 单个可选插件配置错误导致宿主整体不可用（F-v）：**已覆盖**，[02 §2.2](../02-项目架构描述规范.md#runtime-deployment) 已要求说明故障传播到哪里、由什么机制隔离；本例只作该条的实例。
- 与另一产品的逐项对比、插件生态清单与星数：**证据不足**，写作时快照，且对比维度由作者自定。

跨方向建议（不由本方向改，交主执行者集成）：

- **给 03**：工具/能力在多层作用域下的可见性若由运行时按层计算，则"当前这次推理能看见什么"必须可被打印和核对，不能只靠加载顺序隐式决定。
- **给 03**：执行前置检查、执行、后置处理应是独立注册的阶段，而不是写在被执行体内部；新增一条审批或防护规则不应改动执行链路本身。
- **给 04**：区分可撤销的获取动作与不可撤销的发射动作；对外通知、对外调用与已被消费的消息不能靠回滚恢复，只能补偿，补偿动作本身要登记为工作项并验证。

## 验证办法

- 取一个模块，按其"共享环境注册项"逐条在下线后核对残留：订阅是否解除、定时任务是否停止、注册名是否释放、外部资源是否归还。期望结果是零残留；只有"框架会自动清理"的说法而无实测记为未定。**未定**：本仓库无运行系统，未实测。
- 在共用标识空间里故意注册一个重名对象，检查机械检查能否发现，以及最终生效的是哪一方、是否与声明的遮蔽规则一致。**未定**。
- 取一次已完成的回退演练，核对其回退声明是否区分了系统内变更与已发出效果，已发出部分是否有对应的补偿动作与验证记录。**未定**。
- 本卡对该产品设计论文的引用全部来自本文转述，未读原文，**未定**；本卡结论的独立性：阅读与写卡由同一执行者完成，解释性判断记未定。
