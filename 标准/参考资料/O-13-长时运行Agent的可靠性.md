## 原文结论与适用限制

经本仓库阅读卡与本轮抓取核对，两者一致的结论有四条：

1. **仅靠上下文压缩不足以支撑长任务**。抓取摘要中作者的说法是压缩"并不总能把清晰的指令传给下一个 agent"（经摘要转述），长任务仍会出现半完成、重复劳动或过早宣布完成。
2. **状态必须外置在模型上下文之外**：进度记录文件、特性/验收清单文件、Git 历史与提交、环境初始化脚本。抓取摘要把关键点归纳为"让 agent 在全新上下文窗口开始时能迅速理解工作现状"（经摘要转述），靠的是进度文件加 Git 历史。
3. **每次会话开始前先跑一次基线验证**：抓取摘要记为会话以"在开发服务器上跑一次基本测试以发现未被记录的缺陷"（经摘要转述）开始，并按 `pwd`、读 Git 日志与进度文件、从特性清单里挑最高优先级未完成项的顺序启动。
4. **验证要按真实用户路径做，不只靠单元测试**；并且执行者不得删改测试——抓取摘要提到清单里带有措辞强硬的"不可以删除或修改测试"一类指令（经摘要转述）。作者列出的失败形态包括：过早宣布项目完成、缺陷未被记录、特性在未经真正测试的情况下被标记完成、agent 搞不清应用当前状态。

## 缺口

[04 §6.5](../04-可靠性安全与运行维护.md#unattended-operation)（本方向本波刚建立）已写"准入按能力次序"要求可自动判定的完成条件，但**没有说这个完成条件从哪来、谁能改**——一个由本次运行自己生成或自己修改的完成条件，形式上满足"可自动判定"，实质上等于执行者给自己发验收。§6.5 也没有说**一段无人值守推进开始前要不要先确认起点是好的**：不先跑基线，本段引入的失败与上一段遗留的失败混在一起，[§6.1](../04-可靠性安全与运行维护.md#agent-run-observability) 的三类归因在无人值守场景下退化为无法归因。[03 §8](../03-Agent信息获取与上下文管理.md#externalization) 管的是上下文外置本身，[01 §5.6](../01-项目管理标准.md#gates) 管闸门合同与"检查器自身故障判故障"，两者都不管"连续自动推进的每一段起点验证"。

## 采纳

两条，均并入 [04 §6.5](../04-可靠性安全与运行维护.md#unattended-operation) 已有段落，不新开小节。

- **完成条件与验证用例是运行的输入而不是产物**：它们在运行开始前已存在于运行之外的工件，本次运行不得新增、改写或删除；由执行者自产或自改的完成判据不构成完成。**触发**：任何允许无人值守推进的工作类型。**责任**：工作项负责人持有完成条件，工具维护者保证执行者对这批工件只读或改动可见。**工件**：既有验收条目与测试。**验收/失败处置**：抽一次运行，比对完成条件工件在运行前后的内容摘要值；被改动而未经有权人批准即判本次结果未定，不按通过收口。**失败依据**：该文列出的失败形态包含"过早宣布项目完成"与"特性在未经真正测试的情况下被标记完成"，其对策之一正是在清单里明写不得删改测试——说明执行者改自己的验收依据是已观察到的行为。本标准 [01 §5.5](../01-项目管理标准.md#controlled-actions) 已把"改已冻结的验收条目"列为受控动作，本条是它在无人值守连续推进下的验收表达，不重复定义授权。**复查/删除条件**：若项目改为每段推进都有人当场确认完成，本条随 §6.5 一并记不适用。
- **每段推进先跑基线验证**：一段无人值守推进开始时先在目标环境跑一次约定的基线检查并记录结果，把上一段遗留的失败与本段引入的失败分开；基线不通过时停下报告，不在失败的基线上继续推进。**触发**：同上。**责任**：工具维护者提供基线检查入口，运行负责人定其范围。**验收**：取连续两段运行，能否指出某个失败是哪一段引入的；指不出即记缺口。**失败依据**：该文把"agent 搞不清应用当前状态"与"缺陷未被记录"列为已观察失败，对策是会话开始时先跑一次基本测试以发现未被记录的缺陷。**复查条件**：基线检查本身耗时或不稳定到影响推进时，按 [01 §5.6](../01-项目管理标准.md#gates) 判检查器故障处理，不静默跳过。

## 不采纳

- `init.sh`、`feature_list.json`、`claude-progress.txt`、"每会话一次提交"、启动时 `pwd` → 读 Git 日志 → 读进度文件 → 挑最高优先级未完成项这套顺序：实现样例，绑定该文的全栈 Web 从零建设场景。本仓库既有卡片已判其不是硬规则，本卡沿用。
- "初始化 Agent + 编码 Agent"两段式架构：属编排选型，且作者自认单 Agent 与多 Agent 孰优未定；[03 §9.1](../03-Agent信息获取与上下文管理.md#delegation) 已要求委托拆分须举证，不在 04 立位。
- "每次会话只推进一个可验收功能"：属会话协议与工作项粒度，[01 §4.3](../01-项目管理标准.md#session-protocol) 有主。**跨方向建议见下。**
- "状态外置到进度文件与 Git"作为新增要求：[03 §8](../03-Agent信息获取与上下文管理.md#externalization) 与 [01 §3](../01-项目管理标准.md#doc-tree) 已管权威位置与状态工件，04 不复写。
- "压缩不足以支撑长任务"：[04 §6.1](../04-可靠性安全与运行维护.md#agent-run-observability) 的会话事件行已写压缩有损与留痕要求，不重复。
- 浏览器自动化 / 端到端验证作为指定手段：[04 §1](../04-可靠性安全与运行维护.md#service-objectives) 已有"不得把进程活着或 HTTP 返回成功直接等同业务正确"，[§5](../04-可靠性安全与运行维护.md#progressive-delivery) 已有发布后回读真实运行制品；再指定具体工具形态属实现选择。

## 验证办法

① 取一次无人值守推进的运行，比对完成条件工件（验收条目、测试文件）在运行前后的内容摘要值；有改动而无有权人批准即判该次结果未定。② 故意在起点埋一个已知失败，启动一段推进，确认基线检查在推进任何实质动作之前就报出它并停下。③ 取连续两段推进，指出其中某个失败由哪一段引入；指不出即记缺口工作项。④ 若要把本卡任何结论提升为承重依据，先补一次原文全文阅读并修订本卡的实际阅读范围字段。
