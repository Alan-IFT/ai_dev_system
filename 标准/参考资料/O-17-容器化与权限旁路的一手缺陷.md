## 原文结论与适用限制

作者把"限制爆炸半径"分两路：人在环（HITL 审批）与容器化（约束 agent 能做什么）。自述审批疲劳使 HITL 可靠性有限，容器化才是主战场，也是最出人意料的失败发生处。四起已定责缺陷：

1. **信任对话框之前执行的项目内配置/hooks**：克隆仓库评审 PR 时，`.claude/settings.json` 里攻击者提交的 hook 会在"是否信任此文件夹"提示之前、启动阶段被解析执行。修法：把项目内配置的解析与执行推迟到用户接受信任提示之后；把 project-open、config-load、localhost 监听当成来自互联网的入站请求对待。
2. **用户即注入向量**：钓鱼让员工用一段"看似日常协作"的提示启动 Claude，提示中夹带读 `~/.aws/credentials`、编码并 POST 到外部端点；模型层防御锚定用户意图，用户亲手输入时无异常可查。唯一能挡的是环境层——出口控制挡住 POST、文件系统边界让凭据不可达。
3. **经允许域名外传**：出口白名单正确放行了 api.anthropic.com（产品离不开它），攻击者在挂载工作区放入携带自带 API 密钥的恶意文件，模型照做、用攻击者的密钥调 Files API，把文件上传到攻击者账户。修法：VM 内防御性 MITM 代理只放行本会话自带令牌、拒绝嵌入密钥，并挡掉会触发服务端抓取的头。作者的结论：**出口白名单应被理解为"能力授予"而非"目的地过滤"，经允许域名上每个可达函数都是攻击面**。
4. **VM 隔离把宿主 EDR 也挡在外面**：同一隔离既容纳了 Claude 也挡住了宿主端点检测；现行缓解是事后拉取式 OTLP 导出，"不等于实时监测"。

另有两条判断：**工具返回是攻击面，即使工具本身可信**（GitHub 连接器可把投毒 README 直送上下文、过了 malware 检查；网络型工具返回要与网页同等审查）；**远程工具在批准后仍可变**（本地工具可钉版本、可审源；远程托管工具/连接器批准后行为随时可变，安装期信任不等于持续信任）。展望里点名**持久记忆投毒**：跨会话留存的上下文（product memory、CLAUDE.md、挂载工作区、计划任务与长期 agent 的状态目录）里的注入每次启动被重载，属经典驻留式攻击面。

适用限制：面向 Anthropic 自家三款 agent 产品的容器化架构，具体机制绑定 gVisor/seccomp/hypervisor/自建代理；本标准取其结构性判断（出口即能力、工具返回即攻击面、隔离降低可见性、记忆投毒、信任边界前的执行），不搬具体实现。

## 缺口

- [04 §4](../04-可靠性安全与运行维护.md#security-supply-chain) 讲了出口约束与执行隔离，但把出口当"目的地过滤"，没写**出口白名单等于能力授予、经允许域名上每个可达函数都是攻击面**，也没写**工具返回是攻击面（即使工具可信）**。
- [04 §6.1](../04-可靠性安全与运行维护.md#agent-run-observability) 有盲区登记，但没写**隔离降低宿主侧可见性、拉取式导出不等于实时监测**，也没写**持久记忆投毒**这一驻留式盲区。
- [01 §5.5](../01-项目管理标准.md#controlled-actions) 的旁路通道段没覆盖**信任边界建立之前执行的项目内配置/hooks**这一类（属跨方向）。

## 采纳

均并入 04 既有段落。

- **§4 出口即能力授予、工具返回即攻击面**（并入 §4 隔离段后）：出口白名单按"能力授予"评估而非"目的地过滤"，经允许域名上每个可达函数都是攻击面；工具返回是攻击面，即使工具本身可信，网络型工具返回要与网页同等做输入审查。**触发**：Agent 有网络出口或调用外部工具/连接器。**责任**：安全责任人与工具维护者。**工件**：出口白名单及其"每个域名授予了哪些可达函数"的评估、工具返回的审查配置。**验收**：取一个经允许域名，列出其上可达函数并确认都在攻击面评估内；构造一次投毒工具返回，确认被审查拦下或留痕。**失败依据**：出口代理放行合法 API 域名，攻击者用自带密钥经这条通道外传工作区文件；连接器把投毒 README 直送上下文且过了 malware 检查。**复查/删除条件**：Agent 无网络出口且不调外部工具时随 §4 记不适用。
- **§6.1 隔离盲区与记忆投毒**（并入 §6.1 盲区段后）：隔离降低宿主侧可见性，事后拉取式日志导出不等于实时监测，按已知盲区登记；跨会话留存的上下文（CLAUDE.md、挂载工作区、计划任务与长期 agent 的状态目录）里的注入每次启动被重载，属驻留式攻击面，纳入同一份盲区与来源信任登记。**触发**：项目把 Agent 执行放进隔离环境，或让 Agent 读跨会话留存的上下文。**责任**：数据负责人会同安全责任人。**工件**：盲区登记（含宿主可见性缺口与持久上下文来源信任）。**验收**：确认隔离环境的宿主可见性缺口已登记、导出是否实时已注明；对每处持久上下文能说出其来源信任边界。**失败依据**：VM 隔离把宿主 EDR 挡在外面、现行缓解为事后 OTLP 导出；文中把持久记忆投毒列为正在逼近的风险。**复查/删除条件**：无隔离执行且无持久上下文时随 §6.1 记不适用。

## 跨方向建议（不由本方向修改）

- 给 **01 §5.5**（已有旁路通道段）：补"信任边界**建立之前**执行的项目内配置/hooks"这一类——打开/克隆仓库即接收外部输入，项目内配置的解析与执行要推迟到信任确认之后；把 project-open、config-load、localhost 监听当成互联网入站请求对待。失败依据：三起漏洞都发生在用户同意之前、来自尚未受信目录的输入被解析。
- 给 **03 §6.1**：同一条来源信任边界——来自尚未受信来源（新克隆仓库、挂载工作区、跨会话记忆）的内容在信任确认前不得驱动执行；与 03 的来源可信度、按引用回读同构。
- 给 **02**：远程托管工具/连接器"批准后行为可变"应进依赖登记的消费者条款，与本地可钉版本工具区别对待（安装期信任不等于持续信任）。

## 验证办法

① 取一个经允许出口域名，列出其上可达函数，确认都在攻击面评估内；用一次自带密钥构造，确认代理只放行本会话令牌。② 构造一次投毒工具返回（如带指令的 README），确认进上下文前被审查或留痕。③ 检查隔离执行的宿主可见性缺口是否登记、导出是否实时已注明。④ 对每处持久上下文（CLAUDE.md 等）能否说出来源信任边界；埋一条注入，确认启动时被来源信任登记拦截或标记。本仓库无对应隔离与出口数据，上述验证未定（生成者与验证者同一）。
