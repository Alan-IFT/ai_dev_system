## 三处重点核对的结论

**一、"同类反馈第二次才系统性地改"——只是设定，不是依据。** 教程 §3.2.3 给阈值 2 的全部理由是"1 次是噪声、2 次是信号"，并写"可以调成 3，但建议从 2 开始"；§6.5.1 允许调 1～3。无观察、无数据、无失败记录支持这个数字。更关键的是**作者自己的运行记录否证了它**：2026-08-29 报告里，用户一次强烈反馈（多感叹号）后，作者按"强警告=预下沉信号"在第 1 次就下沉，并在报告中写明这违反其 L1 的严格阈值。也就是说该阈值在其唯一的真实部署中首次遇到真实事件即被破例，作者随后把破例提炼成新规则。**结论：[覆盖与采用检查 §feedback-adoption](../覆盖与采用检查.md#feedback-adoption) "不新增通用晋升次数"是经过考虑后的拒绝，不是缺口**；本材料反而是支持该拒绝的证据。[03 §10.1](../03-Agent信息获取与上下文管理.md#memory-governance) 的候选—入池—批准三段与 §10.3 的置信三级不依赖任何计数，不改。

**二、"输出前自动过五关闸门"——写在记忆与提示词里，无模型控制流之外的执行点。** `delivery_gate` 由 `skill_manage` 创建为一段文字，由写在记忆置顶区的 L1 第④条"你必须"驱动，其验收办法是让 Agent 复述内容（教程 §5.5.1）。这正是 [01 §5.5](../01-项目管理标准.md#controlled-actions)（依据 [M-10](M-10-守卫的执行点.md)）判为"只是提醒，不构成受控"的形态，受控状态按 N1 记未定。教程自己记录了它的静默失效而未识别其性质：§7.1 Q1（L1 写了但不执行，补救是再重申一句、再写进 system prompt）、§7.2 Q7（闸门报告"全部通过"而用户仍发现问题，补救是增加检查项）、§6.3 异常信号表（"Agent 直接开始执行，跳过了清单"）。**唯一的例外在 practice/**：事故后新建的 `git-safety-verify.py` 有真实退出码（非零即停），2026-08-29 报告记录了阻断分支 exit 1 与通过分支 exit 0 的双向实测——这一条满足 [01 §5.6](../01-项目管理标准.md#gates) 的反例测试要求，但只覆盖 git 安全，不覆盖五关闸门。

**三、"记忆存为什么、技能存怎么做"——不是本标准缺的维度。** 该二分是**载体归置约定**，判据是内容形态（原则/步骤），不产生新的可检查动作。[03 §5](../03-Agent信息获取与上下文管理.md#on-demand) 的切分判据问的是"这条规则在它该生效那一刻必须已在上下文里吗"，绑定的是"约束不在场"这一具体失败；形态二分说不出它防的是哪个具体失败。[C-12](C-12-CoALA记忆分类学核对.md) 对 CoALA 四类记忆的核对结论是六项不缺、概念未混用，且已判定"不引入第二套分类，避免与 §10.1 的路由判据形成第二处权威"——本材料的二分同属该结论覆盖范围。该二分在作者自己手里也不成立：教程 §7.1 Q2 在平台无技能工具时改为把步骤写进记忆，等于放弃该边界；2026-08-29 报告首次层级扫描即在 15 条记忆中查出 3 类污染（状态日志、操作步骤、与画像重复）。无执行点的形态约定不能维持。

## 采纳结论

**本轮零采纳到标准正文。** 03 与 01 不因本材料改动一个字。上一版本卡据教程正文作出的判断，在取得 practice/ 原文后全部维持，理由从"教程未证明"加强为"作者自己的运行记录否证"。

唯一的正面价值是**佐证**，集中在一处：2026-07-25 的源码丢失事故（`git branch -m` 导致完整项目源码丢失）中，作者的 5 Why 追到 Why4"规则依赖人工触发而非自动拦截"、Why5"检查未嵌入危险操作的调用流程"，并在同一报告中把"前馈机制虽然存在，但依赖人工触发"标为致命问题、把改进方向写为从建议执行升级为强制执行。这是一个独立个体在真实事故后，从零开始重新推导出 [01 §5.5](../01-项目管理标准.md#controlled-actions) 与 [M-10](M-10-守卫的执行点.md) 已有的判据——**执行点必须在被约束者之外**。该事故涉及的动作（删分支、无备份的破坏性操作、装依赖前须征询）全部已在 01 §5.5 的受控动作清单内。

值得记下的是教程与实践的自相矛盾：教程 §7.3.3 正面回应了"这只是在上下文里给 LLM 加步骤，不算强约束"的质疑，答复是"给 LLM 加步骤本身就是有效的约束……效果不来自硬编码的强制性，而来自持续的结构化引导"，无证据支持；而其 practice/ 记录的唯一一次严重事故，根因恰是该答复所否认的那一点。**采纳教程正文的治理主张会直接削弱 01 §5.5，与既有判据冲突。**

## 已覆盖与不采纳（按组）

- **已覆盖**：前馈预载、层级分离、容量上限、技能版本化、自我终止条件、跨部署一致性。落点见上表，均不重复采纳。
- **场景不适用**：教程对象是**个人使用的通用 Agent**，其适用边界由作者自述为"长期协作 × 高精度需求 × 可归纳规律的任务类型"（§7.3.3），前提是持久记忆、可编程技能与 100k+ 上下文（§2，仅得摘要）。本标准对象是**多人多年维护的大型软件项目**。跨不过差距的是：单一用户的偏好即权威（无归属人、无评审、无冲突裁决）、记忆存活于宿主账号（本标准要求跟项目走）、多 Agent 节共享可写记忆区（本标准要求权限只能收窄、写集不重叠）、以对话指令做维护（本标准要求持久可定位工件）。跨得过的只有一条：守卫需要执行点——而这条本标准已有。
- **类比非证据**：前馈、积分、层级、自监控四概念到 Agent 的迁移是修辞与设计灵感。教程未给出任何一条能独立说出"防的是哪个具体失败"的机制；控制论术语本身不证明该流程具有稳定性保障。凡只由类比支撑的条款一律不采纳。
- **与既有判据冲突**：提示词级五关闸门当作硬闸门（对 01 §5.5／§5.6）、零拦截等同改善（对 01 §5.6）、30 天未访问即删（对 03 §10.4）、多环境定期同步（对 01 G2）。四项均按既有条款处理，不为迁就本材料放宽。
- **效果与平台承诺**：健康度评分、拦截率、下沉转化率、部署耗时、宿主能力矩阵均不由本次阅读证实，只记为该作者在其条件下的自述。
