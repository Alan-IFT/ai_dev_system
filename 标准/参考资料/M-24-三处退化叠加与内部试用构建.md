# M-24 · 三处退化叠加与内部试用构建：内部试用要用对外制品，评审输入要覆盖跨仓库

## 原文结论与适用限制

三个变更，各自影响不同模型、不同流量、不同时间：

1. **默认推理强度从高改中（3-04）**，为消除长尾延迟；用户反馈"变笨"，4-07 回退。作者定性为"This was the wrong tradeoff."——产品取舍，不进标准。
2. **缓存优化 bug（3-26 上线，4-10 修复）**：本意是会话闲置超过一小时后清一次旧推理块以省缓存未命中；实现变成此后每一轮都清，"Claude would continue executing, but increasingly without memory of why it had chosen to do what it was doing"（中译：Claude 继续执行，但越来越不记得自己为什么选择这么做）。原文对它为什么漏过去的自述："This bug was at the intersection of Claude Code's context management, the Anthropic API, and extended thinking. The changes it introduced made it past multiple human and automated code reviews, as well as unit tests, end-to-end tests, automated verification, and dogfooding."（中译：这个 bug 处在上下文管理、API 与扩展思考三者的交界；它引入的改动通过了多轮人工与自动代码评审、单元测试、端到端测试、自动验证和内部试用。）"it took us over a week to discover and confirm the root cause."两个不相关的实验让复现更难：一个内部服务端的消息排队实验，一个显示推理的正交改动"suppressed this bug in most CLI sessions, so we didn't catch it even when testing external builds"（中译：在多数 CLI 会话里压住了这个 bug，所以即便测对外构建我们也没抓到）。事后回测："When provided the code repositories necessary to gather complete context, Opus 4.7 found the bug, while Opus 4.6 didn't. To prevent this from happening again, we are now landing support for additional repositories as context for code reviews."（中译：给到收集完整上下文所需的代码仓库后，Opus 4.7 找到了这个 bug，Opus 4.6 没有；为防再发，我们正在给代码评审加上把更多仓库作为上下文的支持。）
3. **一行系统提示（4-16 上线，4-20 回退）**：为压缩冗长度加的长度限制；"After multiple weeks of internal testing and no regressions in the set of evaluations we ran, we felt confident about the change"（中译：经过数周内部测试、在我们跑的那组评测上无回归，我们对这个改动有信心）；事后用更宽的评测集逐行消融，"One of these evaluations showed a 3% drop for both Opus 4.6 and 4.7."

叠加效应的原文："Because each change affected a different slice of traffic on a different schedule, the aggregate effect looked like broad, inconsistent degradation."（中译：因为每个变更影响的是不同的流量切片、按不同的时间表，合起来看像是广泛而不一致的退化。）"neither our internal usage nor evals initially reproduced the issues identified."（中译：内部使用和评测起初都没复现出这些问题。）

整改项（"Going forward"）：让更多内部员工用"the exact public build of Claude Code (as opposed to the version we use to test new features)"（中译：与对外完全相同的构建，而不是我们用来测新功能的版本）；改进内部代码评审工具并对外发布；每次系统提示变更跑一套按模型分的评测、继续逐行消融、新工具让提示变更易评审易审计；在入口文件里加指引"ensure model-specific changes are gated to the specific model they're targeting"（中译：确保模型专属的改动只对目标模型生效）；对可能牺牲智能的变更"add soak periods, a broader eval suite, and gradual rollouts"（中译：加软着陆期、更宽的评测集与灰度发布）。

适用限制：

- 厂商自述，三个缺陷均已定责，但"通过了哪些评审、跑了哪些测试"只有清单没有细节；"3%"是哪项评测未说。
- 缓存 bug 的回测结论——给了跨仓库上下文后新模型找到、旧模型没找到——**没有说明**在缺跨仓库上下文时新模型是否也找不到；作者的整改是补跨仓库上下文，本卡据此把"输入范围"作为可采纳的语义，把"模型版本"记为不确定。
- 三个变更里第一个是产品决策，本卡不采；第三个的整改多数落 03 §11.1 与 04 §7，本方向只写建议。

## 缺口

[01 §4.5](../01-项目管理标准.md#release-management) 发布已有"允许不相互干扰的变更继续交付，但须能区分各版本暴露范围和异常归因"，这次三处叠加是它的一手失败实例，但 §4.5 没说**内部试用**这项发布前证据要用什么制品——用内部测试版试用得到"未复现"，对对外构建不构成证据；也没说同期并行的其他实验要登记，它们会掩盖症状。[§4.4](../01-项目管理标准.md#review-flow) 评审列了"看什么"，没说评审的**输入范围**——影响清单里写了跨仓库/跨层依赖，评审者手里只有 diff 所在仓库时，那部分实际上没审。[§4.3](../01-项目管理标准.md#change-level)"不以修改行数判断风险"举的例子是契约，没提面向模型的提示或规则文本一行改动也能改变全部产出。

## 采纳（落 01）

- **评审的输入范围须覆盖变更跨越的全部仓库与层**（[01 §4.4](../01-项目管理标准.md#review-flow)"评审看什么"后补一条）。**触发**：影响清单列出跨仓库或跨层依赖。**责任**：交付负责人保证评审者拿到全部相关仓库/层的上下文；评审者声明实际读了哪些。**工件**：评审记录里的输入范围声明。**验收/失败处置**：影响清单里的跨仓库项在评审输入里找不到，该部分按 N1 记未审，不记通过；抽查评审记录能否说出跨层依赖在另一侧的行为。**失败依据**：本文缓存 bug——处在三层交界，通过多轮人工与自动评审、单测、端测、内部试用，事后才定位；作者的整改是给评审补跨仓库上下文。**复查/删除条件**：单仓库、单层项目不触发；若评审工具默认装配全部依赖仓库，本条退为核验该装配真的发生。
- **内部试用须使用与对外相同的制品与配置；同期实验登记**（[01 §4.5](../01-项目管理标准.md#release-management) 发布前核验一条内补）。**触发**：把内部试用/试运行作为发布前或发布后的证据。**责任**：发布负责人。**工件**：发布记录里的制品身份（与 §5.9 环境身份同一字段）与同期实验清单。**验收/失败处置**：内部试用的制品身份与对外制品不一致时，其"未复现"不构成对外构建的证据，按 N1 记未定；同期运行而未登记的实验在事故归因时先补登记再归因。**失败依据**：本文——内部人用的是测新功能的版本而不是对外构建；两个不相关实验掩盖了症状，"即便测对外构建也没抓到"。**复查条件**：项目无内部试用环节时不适用。
- **提示或规则文本一行改动可为高影响**（[01 §4.3](../01-项目管理标准.md#change-level)"不以修改行数判断风险"段补半句，佐证性质）。**失败依据**：本文一行系统提示在更宽评测集上有可测下降，且在原评测集上无回归。**复查条件**：随该段。
- **§4.5"须能区分各版本暴露范围和异常归因"补引本卡**：三处各自影响不同流量与时间表的变更叠加成"广泛而不一致"的退化，事后才拆开。文字不改，加佐证。

## 不采纳

- 默认推理强度取舍与回退：产品决策。
- 具体的 API 头、保留参数、版本号、日期、"3%"：载体与观察。
- "更新模型找到了、旧模型没找到"作为"用更强模型评审"的依据：原文未做"同上下文、不同模型"之外的对照；且 01 §4.4 独立性判据与模型强弱无关。
- 重置用量额度、社交媒体沟通渠道：与标准无关。
- "用户反馈起初难以与正常波动区分"：[04 §6.4](../04-可靠性安全与运行维护.md#agent-run-observability)/§1 的信号判读领域。

## 跨方向建议（不由本方向修改）

- 给 **03 §11.1**（[context-evals](../03-Agent信息获取与上下文管理.md#context-evals)）：① 每次面向模型的提示或规则文本变更跑按模型分的评测并逐行消融——原文的失败正是"原评测集无回归、更宽评测集有下降"，即 §11.1"用于挑选改动的用例集与最终验证用例集分离"与"新增规则须证明增量（有/无两组）"的一手反例；② "模型专属改动绑定到目标模型"是 §11.1"版本变更后的减法触发"的正向形态：为某模型加的条目应标明只对它生效。
- 给 **04 §7 / §5**：① 四样版本记录里的"提示词模板"在这次事故里是产品自身的系统提示，一行改动改变全部产出而代码修订看起来只是文案；② "候选/对照的差异需可解释"——内部试用制品≠对外制品、同期实验未登记，都是差异不可解释的形态；③ 软着陆期 + 更宽评测集 + 灰度是该厂商对"可能牺牲智能的变更"的整改，对应 §5 的分批观察。
- 给 **03 §8 / 04 §6.1**：这个 bug 的表现——执行者"越来越不记得为什么这么做"——是 04 §6.1 会话事件行"压缩有损，不留痕则后段失败无法与任务变难区分"的一个真实形态；它只在会话跨过闲置阈值后出现，是 [M-18](M-18-跨边界的验收观察.md)"边界之后才采集"的又一实例。

## 验证办法

① 取采用项目最近一次跨仓库变更的评审记录，核对评审输入是否含影响清单里列出的另一侧仓库；不含即该部分记未审。② 取最近一次发布记录，比对内部试用的制品身份与对外制品身份；不一致即其"未复现"记未定。③ 查发布记录有无同期实验清单。本仓库无多仓库变更与发布流程，三项均**不适用**。
