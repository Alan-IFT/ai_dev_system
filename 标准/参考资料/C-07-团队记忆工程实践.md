## 原文结论与适用限制

该团队把团队记忆定义为"把真实任务中产生的背景、知识、代码关系和工作方法转化为可检索、可组合、可追溯、可授权、可持续更新的资产，并在后续任务中按需装配"，并明确它与 RAG 的差别在于必须回答"属于谁、在哪个版本成立、谁有权使用、装配给谁、用后如何修正"。工程要点：内容分层保存（原始对话 → 原子事实 → 场景块 → 稳定画像，上层不取代下层）；装配按身份与 ACL 先缩小候选池再做相关性检索，人明确绑定的资产不被相似度排序覆盖；渐进式暴露（先给名称、触发条件与工具入口，确认适用后再取细节）；资产形成分证据切分、候选抽取、作用域绑定、验证后升级四步；资产按置信分强关系、弱关系与只参与召回的背景参考三层，可随新证据升级、降权或撤回；资产跟 Team 走而非跟 Agent 或框架走；任务期间可锁定资产版本。六类工程问题为冲突、新鲜度、权限、溯源、负反馈、成本。

适用限制：这是产品团队对自家在建产品的描述，作者自述"这项工作仍在探索中"。内部数据分析的生产与审计都由模型完成，作者明说"不是人工金标"，是内部自动化分析质量指标而非行业结论。评测结论作者自己限定为"不等于部署后所有任务都会提升"，并列出尚未做的事（固定评测子集、报告样本数与置信区间、区分负迁移、跨仓库跨版本测试）。本卡不引用任何完成率、成本、精确率数字作为规则成立的理由；相关表述一律只作"该团队在该条件下报告的观察"。

## 缺口、采纳与不采纳

03 §10 原为全文最薄的一节（六条要点），有候选来源、批准与失效，但缺条目结构、作用域粒度、置信分级、召回时机与团队／个人载体归属。本篇是本方向唯一的厂商一手记忆工程材料，用来补这五处。落点均在 [03 §10](../03-Agent信息获取与上下文管理.md#memory-governance)，另有一条落在 [§11.1](../03-Agent信息获取与上下文管理.md#context-evals)。

**采纳一：抽象与证据同层保留，抽象条目必须带可回源锚点。** 该团队的分层设计明确"高层记忆负责减少阅读量，低层记忆负责防止抽象在多轮总结后失真"，并要求"每条结论必须回到原文，聚类标签和模型摘要只是索引"。这与 03 §1 原则 5、§8.2"摘要不能自证"同源，但 03 此前没有把它落到记忆条目上。失败依据：多轮摘要后抽象与原文脱节（该团队据此设计分层）；本仓库 §8.2 已有同类失败绑定。复查条件：若项目记忆全部为人工撰写且无模型抽象环节，本条可降为只记来源。

**采纳二：作用域字段与正文同等重要，粒度细到分支、路径与环境。** 该团队报告的具体风险：两份部署方法描述高度相似，实际一个读 `config/prod/`、另一个用 `conf/prod/`；只按语义相似度挑"质量最高"的资产会流畅执行完却写错目录、污染错误环境。这是一个可追溯风险而不是抽象担忧，且现有 03 §10 只要求"来源 ID、版本、敏感度及失效条件"，不足以区分这两条。删除条件：项目只有单一分支、单一环境时可只记版本与时间。

**采纳三：置信分三级，只有强资产可驱动动作。** 该团队把"保留／删除"两态改为强关系、弱关系、只参与召回的背景参考，并规定 Shadow 不自动驱动执行。这与 03 全篇的三态判据（通过／失败／未定）同构，是 03 §10 缺的一层。失败依据：该团队的内部分析显示模型容易判定两个任务"有关系"，却难以判定是否同一问题或可迁移的方法，即关联被误当成可复用。

**采纳四：条目内容须含适用条件、已排除路径与验证方式。** 该团队报告的卡点分布中，"逻辑返工"远多于"缺少上下文"，"已失败的路径被再次尝试"单列为一类，并据此得出"团队记忆不能只做找资料，还要保存决策理由、失败路径、适用条件和验证方式"。03 §10 此前只规定候选来源，不规定条目内容。（本卡不把这些计数当论据，只取失败类型本身。）

**采纳五：召回顺序与合同的关系。** 权限过滤先于相关性检索这一条，03 §6.2 第 1 步已有，不重复写。新增的是：记忆召回不得替换或挤掉 §3 合同的必读项——人明确绑定的约束不参与相似度竞争。这是 03 "只有一份默认加载清单"原则在记忆侧的落点，此前没有写。

**采纳六：任务期内锁定资产版本。** 03 §3.2 第 4 条处理合同／工作项／工作区身份冲突，第 5 条处理切换工作项时的版本递增，但没有覆盖"同一任务前后两次召回读到不同版本的同一条规则"。该团队把版本锁定列为装配层的显式能力。

**采纳七：记忆的权威载体跟项目走，不跟宿主或账号走。** 03 §10 原有"工具自带的自动记忆只当草稿本"，方向一致但只说了"别用"，没说"那权威在哪"。该团队的"资产跟 Team 走、与框架解耦"补上了后半句：宿主、账号或框架更换不应导致项目记忆丢失。

**采纳八：记忆与确定性验证的分工边界。** 访谈结论"Memory 适合提供风险、背景和历史方法；脚本、测试和检查项负责确定性验证；记忆不能替代测试，测试也不能解释历史原因"。03 §10 没有这条边界，容易被读成"记住了就不用测"。

**采纳九（落在 §11.1）：评估记忆与检索时禁止未来信息泄漏。** 该团队在两套环境里都把"目标任务发生后的修复结论不能反过来成为它的历史经验"列为硬约束，并报告时间无效候选为 0。03 §11.1 的"上下文选择"行有"最新／过期"资料对照，但没有这条时序有效性约束；缺它会让记忆评估自证成立。

**不采纳一：四类资产分类（Chat Memory / Wiki / CodeGraph / Skill）与 L0～L3 四层命名。** 03 §2 信息层级、§5 按需层已经按"回答什么问题"划分了模块文档、契约、ADR、runbook、PLAYBOOK、skills，引入第二套资产分类会造成同一事实两处定义。本轮只取"抽象与证据同层保留"这一条机制，不搬分类表。

**不采纳二：五层路由（身份／固定绑定／浮动召回／相关性融合／上下文装配）与 BM25＋向量＋RRF 的检索实现。** 属具体检索架构，绑定该产品实现；03 §6.2 已规定必须先按身份限制候选集，不再规定融合算法。轻量项目按 03 §6.2 的"不要求部署向量库"继续适用。

**不采纳三：协作带宽定义与成本公式、OPC 与三层 AI 组织架构、Spec-driven Development 叙事。** 组织形态论述，不产生可检查的规则；且其证据来自未核对的第三方数据。

**不采纳四：全部数字。** Session／Task／Pair 数量、精确率、卡点计数、SWE-bench 完成率与成本、turn 数降幅一律不进 03 正文，也不作任何规则的成立理由；本卡引用它们时只说明"该团队报告的观察"。

**不采纳五：冷启动的三种入口（历史 Session／文档／代码仓库自动生成资产）。** 与 03 §10"模型自己的推断与输出不作候选"存在张力：自动从历史轨迹批量抽取会把未验证推断送进池子。该团队自己用"验证后升级"缓解，本轮不采纳自动批量入池，保留 03 现有的"绑定状态转换 + 人批准"路径。理由记录在此，供采用项目自行决定。

**跨方向建议：**
- 给 **01 项目管理标准**：该团队访谈报告"方案设计与 Code Review 比写代码更耗时，难点是恢复需求背景、理解方案取舍、确认影响范围、判断是否违反历史约束"。若 01 的评审条款要求评审输入除 Diff 外还包含目标、已排除方案与影响范围，可考虑以此为一份外部佐证。本卡不改 01。
- 给 **01 项目管理标准**：资产的生命周期动作（新增、评审、发布、降权、锁定、过期、删除）与归属人、复核时机的对应，属 01 的周期维护范畴；03 只写记忆侧的判据，不定义组织流程。

## 验证办法

- 作用域粒度：构造两条正文高度相似但路径或环境不同的记忆条目，用只指定其中一个环境的任务触发召回；召回到另一条而未被作用域拦下即判失败。
- 置信分层：抽一批弱／背景条目，检查它们是否出现在任何动作或计划的直接依据里；出现即判失败（应只作线索并回源）。
- 版本锁定：同一任务内在中途更新一条被召回的规则，检查任务前后两次读到的版本是否一致，以及不一致时是否显式报告。
- 时序泄漏：在评估集里放入目标任务之后才产生的结论，检查它是否被当作该任务的历史经验召回；被召回即评估无效，须重建时间过滤。
- 负反馈闭环：标记一条误召回条目，检查后续同类任务的召回是否实际改变；只记录不改变路由判失败。
- 记忆与测试的分工：删除某条记忆后重跑同一任务，验收结果不应仅因记忆缺失而由通过变为通过——若测试本身无法判定该缺陷，说明验证依赖了记忆，须补确定性检查。

以上均未在本仓库运行，本轮全部记未定。
