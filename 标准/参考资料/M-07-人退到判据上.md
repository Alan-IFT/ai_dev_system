## 原文结论与适用限制

作者的贯穿主张是"机器提供事实，人做判断""不信声明，信事实；不信自觉，信机制"。与 01 有关且带具体失败记录的几条：

- **判据的性质决定约束的形态**。作者同一个拦截器里的两条规则待遇不同："禁止读 protocols 目录"判据是路径前缀比对（确定事实），至今硬拦截；"编辑 `.lua` 前必须先读编码规范"判据是扫会话记录看有没有读过（代理指标——读过不等于遵守，且主会话累积的历史 Read 会把"已读"状态污染给之后的子 agent），上线两周后降为警告。结论：**判据是确定事实才能做硬门禁，判据是代理指标最多做提醒。**
- **门禁误报的代价**。两条明知易误报的静态检查规则始终没改成阻断，只要求评审者逐条读源码二次确认、采纳或判误报都要写理由。作者给的理由是：误报会逼人和 AI 为了过检查把代码写得更差（他们改过一条规则，目的写作"不再为了过 lint 把 helper 拆开内联"）。
- **信号要从被验对象之外取**。跑批上有一道硬失败：脚本报告成功、报告文件也生成，但覆盖率 0/0 行即判失败——防的是 AI 把被测函数逻辑抄出来重算再断言这类假测试，"AI 自查也会认为自己做对了，只有从外面看被测函数的行一次都没被执行到，才戳得穿"。
- **失败必须有名字**。入库长期卡在"正在合并"、四次恢复失败，根因之一是普通错误没有对应的失败状态，网关只记日志不改状态，恢复逻辑反复重投同一个空提交；修复后状态机增到七态，最后一态是事故买来的。另一处同型：覆盖率看板把"采集失败"和"没有数据"显示成同一个 0%。作者称同一个判断在一年里犯了四次。
- **补丁式规则可能生来就错**。因模型走错一次而加的"严禁 mock ss，只有一种正确写法"，八天后对着仓库里 529 个存量单测才发现它从落笔那天就与事实相反。
- **一次性工件与沉淀工件寿命不同**。仓库里留了七十多篇设计文档，但"海量的 spec 文档最后被我删掉了，删完项目照跑"；作者的区分是：动手前用来对齐的 spec 用完可以扔，事后沉淀、给下一个改这块代码的人建立心智模型的说明得留。
- **多重独立嵌套环**。AI 的单次产出不可靠，人的单次注意也不可靠；对策是多个独立的环叠加，每个环独立的判据是"触发源和被验对象之间没有因果关系"，否则这个环只是复述上一环的结论。环的接口只许传事实不许传声明；平台用自己的容器独立重跑 AI 交上来的测试，结果摆到审批页上但不阻塞审批。
- **人退到决策点**：人放掉实现，握住判据；作者转引 Robert C. Martin 的边界——agent 写的单元测试不看，验收测试与 QA 流程亲自看。

**适用限制**：单团队单季度自述，多处结论来自一次或少数几次事故，未做对照。文中大量内容绑定其自研测试框架、Lua 技术栈与自建平台，不可移植。文中对某商用 CLI"检测使用者来源并在提示词与工具调用里投毒"的指控，本卡**不核实、不引用、不采纳**，仅记录该说法存在。所有规模性表述（三个月三十多万行、没有一行人写的）是该团队在其条件下报告的观察，不作为任何规则的论据。

## 缺口、采纳与不采纳

01 §5.6 规定了闸门合同要写"怎么发现误阻断与静默失效"，但没说**什么样的判据配得上硬拦截**；§4.4 要求"生产者 ≠ 验证者"，但没给独立性的可检查判据；§2 N3 要求规则绑失败依据，但没防"由一次失败推出的规则与存量事实相反"；§3 的文档树没有区分寿命不同的两类工件。这四处是本篇能补的。

**采纳**

- [01 §2 N3](../01-项目管理标准.md#discipline-n3)：由单次失败推出的"以后必须……"类规则，采用前对存量对象核对它与现状是否一致。触发条件为新增此类规则；责任角色为规则的具名负责人；工件是核对结论；失败处置是与存量不符即不采纳或改判据。失败依据：原文"严禁 mock ss"一条与 529 个存量单测相反。
- [01 §3.1](../01-项目管理标准.md#doc-tree)：区分一次性对齐工件与长期沉淀工件，前者不进文档树、不承担更新义务。风险依据：§7 的文档膨胀衰减；复查条件为该项目文档树不再增长时无需再区分。
- [01 §4.4](../01-项目管理标准.md#review-flow)：独立性的判据——检查的触发源与被验对象之间没有因果关系，复述上一环结论的检查不计为独立证据。
- [01 §4.7](../01-项目管理标准.md#maintenance-budget)：候选区丢弃项记一句理由，作为改上游规则的输入（原表格单元内追加，不新增行）。
- [01 §5.2](../01-项目管理标准.md#testing)：通过声明须伴随独立可回读的执行事实；报告为通过而执行事实为空，按 N1 判失败或未定，不判通过。失败依据：原文覆盖率 0/0 行的假测试。
- [01 §5.6](../01-项目管理标准.md#gates)：判据是确定事实才做硬拦截，是代理指标最多做提醒；已知易误报的规则不做阻断，改为提醒并要求逐条写明采纳或判误报的理由。失败依据：原文两条规则的不同待遇与"为过 lint 把 helper 拆开内联"。
- [01 §5.8](../01-项目管理标准.md#error-observability)：失败要可命名、可定位；"采集失败"与"无数据"不得用同一种表示，这是 N1 的失败与未定之分落在运行数据上的同一条。
- [01 §6](../01-项目管理标准.md#roles)：开头补一句职责边界——AI 承担产出后，人保留的是判据与取舍（验收判据、失败算不算问题、受控动作授权、规则增删），实现与文档落笔可委托，责任不随委托转移。

**不采纳**

- runtime 主权、自建 agent runtime、底座选型（pi agent / DeepSeek Harness / codex）：01 的对象是项目管理过程，工具底座选型属采用项目自己的技术决策，**场景不适用**；01 §7"工具锁定"一行已给出可迁移工件的原则。
- 评测题集构建、变异击杀率、留出集、跑数统计纪律（三遍取均值、6 个百分点噪声线）：对象是 agent 能力评估，属 03，**落点不在 01**。
- "生产者不是写者"（生成侧只提交候选，平台是唯一写者）：01 §6.1 的候选—批准机制与 §4.2"模型自己的推断不作候选"**已覆盖**。
- 产物形态从 Markdown 走向 HTML、划词标注回灌：降低人做判断成本的具体手段，绑定其平台实现，**证据不足**且不可检查，不写进 01。
- 平台的嵌套环、资产生命周期、执行容器池：整体是该团队的平台设计，01 只取其中可独立成立的两条判据（环的独立性、接口只传事实），其余**场景不适用**。
- "模型越强 harness 越薄是想当然"、"harness 之于 agent 犹如 IDE 之于程序员"：观点性表述，无可检查判据，不入正文。
- 对某商用 CLI 的投毒指控：**证据不足**，不采纳、不转述为事实。
- 一切规模与效果数字。

## 跨方向建议（不由本执行者落地）

- 给 **03**：① "环的接口只许传事实不许传声明"与 03 的委托合同、子执行者汇合同构——子任务返回的是可回读产物还是自述结论，可考虑成为汇合验收的判据；② 上下文压缩导致的"203 轮压缩、203 次从头再来"（摘要把生成指令当用户请求，进度与待办两节只剩标题）是 03 压缩与检查点一节的直接反例材料；③ 评测的"用考题练考题"（校准题与正式题库同一批时提升被高估）应进 03 的回归评估；④ "统计 agent 有没有跑过测试只认工具调用记录、不认文字自述"是 03 能力验收的可检查形式。本卡不改 03。
- 给 **04**："失败必须有名字"的完整版——状态机缺失败态导致任务卡在中间态并被恢复逻辑无限重投、替身实现把可选能力实现了所以测试永远绿——是 04 事故与可观测性的具体材料；01 只取其中"采集失败与无数据分开"这一条。
- 给 **02**：无建议。

## 验证办法

在采用项目取 `GATES.md` 的全部闸门，逐条标注其判据属确定事实还是代理指标，核对代理指标类是否仍在做硬拦截；再取近三个月被判失败的记录，抽查有多少最终被判为误报，以及误报是否引发了为过检查而做的改动。对 §5.2 那条，造一例"报告通过但无执行记录"的产物，确认现有流程判它失败或未定而非通过。本仓库无闸门运行数据，上述验证**未定**（生成者与验证者同一）。
