## 原文结论与适用限制

作者把 Agent 操作内部平台的问题分成四层：能操作什么（工具接入）、怎么操作才对（流程编排）、被允许怎么操作（拦截）、规则在哪生效（多平台一致）。与 01 有关的：

- **放弃自建中间代理的两条理由**。最初打算自建一层中间服务，暴露出两个问题：其一，如果新建一个供 AI 调用的控制器并直接调用服务层来绕过原有控制器，那么原控制器上的切面、并发控制、异常处理**全部需要在新入口重做一遍**——"不是简单的调用转发，而是整套横切关注点的二次实现"；其二，独立服务的构建、部署、监控、扩缩容都要额外维护，与被代理的服务不在同一交付单元，版本同步与线上排错各多一层。他的结论不是"做不出来"，而是"值不值得单独维护一个中间代理层"。
- **拦截点在框架独占的调用路径上**。工具调用构造完成后、框架实际发起调用之前，引擎暂停执行流，把工具名与入参交给拦截脚本裁决，返回放行、弹窗确认或拒绝。作者写明"Agent 无法绕开，因为从调用到实际执行的路径被框架独占，拦截是这条路径上的唯一道闸"。
- **规则全部外化，不在拦截脚本里硬编码**：安全分级、字段校验、危险语句模式、环境映射共十八段配置放在一份规则文件里，新增规则只追加配置段，不改主体逻辑。
- **多平台单源管理**：一份共享配置作为唯一源，各平台目录以符号链接指向它，改一处两个平台同时生效；链接机制不可用时脚本回退为复制。
- **一条自己承认放在推理层的约束**："某些写工具必须先走完对应流程才能调用"——作者明确说它"不依赖拦截层的代码拦截，而是在 Agent 的推理层面建立'先走流程、后调工具'的纪律"。
- **不完整写入的防护**：以整体替换语义的更新工具，在入参不完整时先返回提示要求调用对应的查询工具拉取当前状态用于对比，避免用残缺参数覆盖完整数据。
- **四级安全分级**：静默放行、审计、弹窗确认、硬阻断，覆盖查询、审计、写操作、不可逆删除。

**适用限制**：单个插件的设计自述，无对照、无消融。作者自己对流程图 SOP 的效果写明"没有进行量化实验对照，实际使用效果可以感觉到"。规模数字（72 个工具、8 个技能、18 段配置、170KB 拦截逻辑、6 个符号链接）是仓库计数，只说明体量，不说明效果。插件工厂一节作者写明"还在开发验证阶段"。全部机制绑定其内部平台、内部 MCP 市场与两个内部客户端，不可移植。文末对 Agent 群体智慧的追问属开放性思考，不构成结论。

## 缺口、采纳与不采纳

01 §5.5 已规定受控动作的核对执行点必须在被约束者之外（[M-10](M-10-守卫的执行点.md)），§5.7 已规定最小权限与危险动作清单同工具实现分离。**但两处都假定动作走的是同一条被管住的通道**。本篇给出的正是这条假定失效的方式：为 AI 或工具新开一条接入通道（旁路接口、直连服务层、专用网关、专用账号），原通道上的鉴权、限流、并发控制、异常处理与审计并不会跟着过来，而这些控制的缺失在功能测试中不表现为失败——新通道能正常调通。这是本篇能补的唯一一处。

**采纳**

- [01 §5.5](../01-项目管理标准.md#controlled-actions)：为工具或 agent 新开的接入通道（旁路接口、直连服务层、专用网关或专用账号）须逐项核对原通道上的鉴权、限流、并发控制、异常处理与审计是否仍然生效；未确认的按 N1 记未定，不按原通道的控制状态推定。触发条件为新增任何此类通道；责任角色为该通道的维护者与被绕过控制的负责人；工件是控制项的逐项核对记录；失败处置是未确认即不投入使用，或明确记录不适用的理由。风险依据与失效路径：新通道功能可用即视为可用，而控制的缺失不表现为调用失败，只在被滥用或出故障时暴露（原文的横切关注点二次实现问题）。复查条件：该通道退役或并回原通道时关闭。

**不采纳**

- 拦截点在框架独占的调用路径上、Agent 无法绕开、每次调用都过：01 §5.5"核对的执行点在被约束者之外……每次调用都过"（[M-10](M-10-守卫的执行点.md)）**已覆盖**，本篇是同一条判据的第二个独立来源，不重复采纳。
- 四级安全分级（静默放行 / 审计 / 弹窗确认 / 硬阻断）：01 §5.6 现行的"不满足时下一步是否真的无法进行"二分判据**已覆盖**约束与提醒的分界；[M-10](M-10-守卫的执行点.md) 已指出再并列一套分层会造成第二处权威，本轮又据此删去了 §7 表中残留的"四级约束力"，不能反过来引入新的四级分层。
- 规则外化到配置文件、不在拦截脚本中硬编码、新增规则只追加配置段：01 §5.7"危险动作清单与工具实现分离、按环境配置、版本化慢变，模型在会话内不可修改"**已覆盖**。
- 多平台单源管理（唯一配置源 + 各平台符号链接，链接不可用时回退复制）：01 §2 N2 与 §3.4 派生关系（`source_rev` + 机械重建对账）**已覆盖**同一原则；符号链接与复制是载体选择，回退为复制后按 §3.4 的派生对账处理，无需另立条款。
- 拦截后的审计记录与经验条目的存活期：01 §5.5 的拦截层回执、§3.5 的 `review_at`、§4.7 的删除信号**已覆盖**。
- "某些写工具必须先走完对应流程才能调用"：作者自己写明它在推理层而非拦截层实现——按 01 §5.5 现行文字，这类约束的受控状态应记未定而不是已受控。本篇因此**不是新增条款的依据，而是既有条款的一个正面用例**，记录在此，正文不改。
- 以整体替换语义的更新在入参不完整时先拉取当前状态对比、避免残缺参数覆盖完整数据：对象是接口的更新语义（整体替换与部分更新的区别），属 **02** 的契约定义，**落点不在 01**。
- 工具、资源、提示三种原语的加载策略与选型对比、按需拉取避免启动通信风暴与提示词被填满：属 **03**，**落点不在 01**。
- 用流程图替代文字步骤列表描述 SOP：作者自述无量化对照，**证据不足**；且对象是指令的表达形式，属 03。
- 条件链字段校验模型（分层触发的必填校验、批量元素级校验）、九步流水线：是其拦截脚本的实现设计，**场景不适用**。
- 从 API 规范自动生成插件的四阶段流水线、按 HTTP 方法自动安全分级：作者写明仍在开发验证阶段；且"按方法名自动定级"与 01 §4.3"不以修改行数判断风险"、[M-13](M-13-执行点冗余与自评级.md) 本轮采纳的"级别由执行者提出、由负责人确认"方向相反，**证据不足且与既有规则冲突**。
- 全部规模数字。

## 跨方向建议（不由本执行者落地）

- 给 **03**：① 工具、资源、提示三种原语的加载策略对比（启动时批量注册并注入系统提示 vs 惰性按需拉取 vs 参数化模板）是 03 加载合同的一手材料，尤其"大量结构化参考数据走按需拉取而不是塞进系统提示"这一条；② 拦截点的三个事件位（调用前拦截、调用后审计、会话开始注入上下文）与 03 的会话协议对应；③ 同一套规则在两个不同客户端上的脚本实现语言不同但必须行为一致，是 03 工具差异适配层的具体形态。本卡不改 03。
- 给 **02**：以整体替换语义的更新接口，在消费者只提供部分字段时会静默清空未提供的字段——这是契约语义必须写明的一项（整体替换还是部分更新），02 的契约登记表可考虑把它列为必填项。本卡不改 02。
- 给 **04**：为 AI 新开的接入通道绕过原通道上的鉴权、限流与审计，是 04 安全与供应链一节的具体风险形态；01 只承接"逐项核对"这一条管理动作。本卡不改 04。

## 验证办法

在采用项目列出所有供工具或 agent 使用的接入通道（旁路接口、直连服务层的入口、专用网关、专用账号），对每条通道逐项回答原通道上的鉴权、限流、并发控制、异常处理与审计是否生效，统计"未确认"的条数；再对其中一条造一次应被限流或应被审计的调用，确认它确实被限住或留下了记录。本仓库无此类通道，上述验证**未定**（生成者与验证者同一）。
