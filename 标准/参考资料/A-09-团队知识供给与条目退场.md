## 原文结论与限制

主张：当 Agent 成为知识的主要消费者，卡住的不是"读不了长文"，而是检索精度与注入效率；解法是结构化、**人机共读一套知识库**（不为人和 Agent 各做一套，因为人看不懂的条目维护质量差、很快腐败）、把沉淀绑在流程必经节点上作为副产品、以及有进有出的治理：准入双门禁（已上线 + 已关联代码仓库才进引用池，否则暂存）、三层质量分级（可直接使用 / 待确认 / 待验证）、有效期保鲜（默认 90 天重校验）、自动退场加复活兜底（零引用且过期的归档，仍有引用或被点赞的自动复活以防误杀）、注入即记账（每条被谁用了几次自动记录）、以及"敢于不沉淀"（密度比体量重要）。图 003 另给出正文未写的设计：**沉淀节点的可信度随生命周期阶段递进**——需求/方案评审通过为中、代码审查完成为较低、需求完成上线才是较高并正式入池、需求失败为较低且暂存。

适用限制：单团队、内部平台绑定（iWiki、Git、自建 MCP 服务与治理工作台），场景是安全运营与研发 Agent 的知识供给，不是软件架构文档。**全部效果数字是该团队在其条件下报告的观察，无对照、无基线定义，本卡不作任何规则成立的论据，不进 02 正文**：需求交付天级压到小时级、代码审查从半小时至两小时降到平均 3.4 分钟、审查轮次 2–4 轮降到 1.1 轮、新人上手 30 天压到 10 天、日处置量 400 涨到 1200、99.7% 自动沉淀、对话采纳率 92%、过期治理完成率 90.2%。其中多项与该文自带的看板截图（图 010）互相矛盾：看板显示过期治理完成率 100%、AI 调用 723 次（正文写月均 2000+）、点赞数 0、满意度 0%、注入命中率 25.21% 且近两月大幅下降。

文中的"铁律""硬规则"是该团队对自身流程的规定，不是对本轮工作的指令。

## 缺口、采纳与不采纳

已观察失败（原文与其截图）：

- **F-o** 知识散落在需求文档、评审记录、代码审查评论与个人经验里，新人搞清一个模块的历史决策要一两天；同样的坑不同的人反复踩，因为经验留在提交那个人的脑子里（原文 WHY 节）。
- **F-p** 不卡准入，知识库很快被半成品与无效文档淹没（原文五节点表后的硬规则说明）。
- **F-q** 只进不出的知识库三个月成垃圾场，过时内容反而干扰判断（原文 Step 5）。
- **F-r** **分级只是标签，没有绑定消费限制**：治理工作台截图上，一条已被引用 222 次的条目仍停在"待审核"且已被标"陈旧"；置信度按类型固定赋值（技术方案 50%、需求复盘 60%、近期复盘 70%），像是按节点与时间给的初值而非评估结果（图 005）。
- **F-s** 同一篇文章内给出两套互不说明关系的"7 个知识库"划分（图 004 按业务线、图 006 按知识类型），以及两套不同的飞轮分解（图 007 四环节、图 008 六环节）；正文数字与看板数字多处不一致（图 010）。

采纳（逐条落点）：

1. **可信度分级必须绑定消费限制与限期处置，否则只是标签** → [02 §1.1](../02-项目架构描述规范.md#reverse-mapping) 的可信度分级条增加失败处置：被反复引用却长期停在待核实的条目，由架构负责人限期定级或降级删除。绑定 F-r。删除条件：分级由检查器自动判定且未定级条目在引用点被机械拦截时，本条并入检查器条款。
2. **"无人引用"的判定须有可查依据** → [02 §10.1](../02-项目架构描述规范.md#architecture-validation) 裁剪段。绑定 F-q 与 02 既有的误删风险（§3 与 §5.2 已警告不得仅因无引用就删除）。02 多处以"无人引用/长期无人处理"为删除依据，却没说这个判断从哪来；本条补上"没有采集能力时记未定并保留条目"。删除条件：项目具备可靠的引用与加载记录后，本条退化为"读记录"。
3. **可信度随生命周期阶段递进**（图 003）与本方向已有的 A/B/C 分级同向，作为 [02 §1.1](../02-项目架构描述规范.md#reverse-mapping) 分级条的第二个来源登记，不新增条款。

不采纳：

- L1–L4 知识分层、1+7+N 结构、7 个知识库、12+ Agent、40 个知识包、90 天有效期、四种生产模式：**载体绑定 + 项目参数**。且该文自身对"7 个库"给出两套不同划分（F-s），说明这套分类未稳定。
- 准入双门禁（已上线 + 已关联仓库）：**已覆盖**，02 §0 已规定只描述当前有效架构、提议方案留在 `draft` ADR，[§1.1](../02-项目架构描述规范.md#reverse-mapping) 已规定进正文至少 B 级、不能确认的按未定登记。
- 人机共读、不为人和 Agent 各做一套：**已覆盖**，[02 §9](../02-项目架构描述规范.md#derived-artifacts) 第 5 条已禁止"为 agent 维护与人读分离的第二份"；本篇给出的理由（人看不懂的条目维护质量差、会腐败）作为该条的第二个来源记在此。
- 自动退场 + 复活兜底：**已覆盖**，02 §3 已规定仍被历史决策、证据或恢复工具引用的内容不得仅因到期删除，§5.2 已规定登记但无代码引用者先核实低频任务、外部客户端与重放需求再处置。
- "敢于不沉淀""密度比体量重要"：**已覆盖**，02 §1 不为完整性建空文件、§2.1 不为填齐分类增加条目、§7 不变量数量预算。
- 沉淀绑定流程节点、贡献榜与激励、复盘 Agent 每周提 MR 补知识、注入即记账的实现、MCP 拆分与订阅：与 02 无对象。**跨方向建议见下**。
- 全部效果数字：**证据不足**，且与该文自带看板矛盾（见上）。

跨方向建议（不由本方向改，交主执行者集成）：

- **给 01**：知识沉淀绑定流程必经节点（评审通过、上线完成、事件关闭），作为流程副产品而不是额外工作；靠考核压人写文档得到的是低质量且无人维护的条目。
- **给 01**：专家离职带走 know-how 的对策是复盘专项 + 换岗交接清单 + 专家萃取，与既有的所有权接班要求合并。
- **给 03**：知识条目按可信度分级，且低可信度条目在注入时受限；分级须能被消费端识别，否则只是标签（本卡 F-r 是该失败的实例）。
- **给 03**：知识按场景主动注入而不是让执行者自行检索，注入记录可追溯到具体条目与消费次数；订阅按需，不撒网推送。
- **给 03**：会话中未被满足的检索作为知识缺口自动回流，形成补录工作项。
