## 原文结论与限制

主张：Agent 的"理解业务"应先回答四个业务问题（意图数量、标签是否常变、标注数据是否充足、需要几轮上下文），再决定技术路线；随复杂度递进的分工是规则 → 轻量分类器 → Embedding 召回 → LLM → 意图 RAG → 多轮状态跟踪 → 规划器，生产上用级联串起来。识别之外单设权限层与执行层——意图层回答"用户想做什么"，权限层判断"用户能否这样做"，执行层确认"动作是否应该立即发生"；每次判断保留执行、追问、拒识、确认四个出口。

适用限制：场景是**对话式业务 Agent**（客服、订单、机票、转账）的自然语言意图识别，不是软件项目的架构描述，也不是 AI 辅助编码。全文无量化结果、无失败记录、无可追读来源；"生产环境通常会采用级联架构"是通识式陈述，无出处。文中的技术名与指标名均为公开语料的通用概念，不构成一手证据。

## 缺口、采纳与不采纳

预期缺口是 02 的业务语义层——业务规则与术语的权威位置及其与代码的对账。**本篇不填这个缺口**：它讲的是运行时如何把一句自然语言判成某个业务意图，不讲业务规则以什么工件形态被写下来、由谁维护、怎么与代码对账。二者共享的只有"领域知识以什么结构存放"这一层措辞，实质对象不同。

**结论：对 02 整篇不采纳。** 逐条理由：

- 意图/权限/执行三层分离、执行 / 追问 / 拒识 / 确认四出口、级联短链路与长链路、参数校验与风险分级的位置：**场景不适用**。这些是某一类系统的内部设计取舍，02 规定的是"架构怎么被描述下来"，不规定被描述的系统该长什么样。若某采用项目确有此类系统，这些属于它自己的模块文档与不变量内容。**跨方向建议见下**。
- 选型前先回答四个业务问题：**证据不足**且属技术选型方法，02 已由 §8 ADR 的"备选方案（至少两个，写明为什么不选）"覆盖判断形式。
- 召回层与判断层分开评估、"正确意图未进入候选集则后续无法补救"、召回失败回流修库：**已覆盖**，[02 §10.1](../02-项目架构描述规范.md#architecture-validation) 已规定"功能测试、静态结构检查和运行演练各有覆盖范围，不能互相冒充"与"核对被测对象是否实际进入检查"，语义相同且已绑定失败。
- 意图库应收录口语表达、相邻意图、混淆反例、业务前置条件与历史误判：与 [02 §2.3 术语表](../02-项目架构描述规范.md#business-semantics)形似而实不同——术语表登记的是业务名词的权威名与归属，不是模型判别用的正负样本集。**场景不适用**，不合并。
- Macro-F1、Recall@K、字段级 F1、拒识率、追问率等评估口径：**场景不适用**，02 的质量场景要求由采用项目按其自身对象定义度量，不引入某一类模型任务的指标名。
- 全篇的"演进八阶段"与"意图识别做得好靠分工随复杂度升级"：**证据不足**，作者叙事与观点，无可核实依据。

本篇未产生任何 02 正文改动，未新增规则。按本方向纪律，整篇不采纳是允许的结果，记录在此以免下一轮重复评估。

跨方向建议（不由本方向改，交主执行者集成）：

- **给 03**：把"理解成功"与"授权完成"分开——判断出用户/上游要做什么，与判断该主体是否有权做、该动作是否应当立即发生，是三件事，不能由同一次判断一并给出。
- **给 03**：每次判断保留四个出口——直接执行、向人追问、拒识、进确认流程；缺信息时追问，置信不足时拒识，高影响动作进确认，而不是在不确定时默认执行。
- **给 04**：高影响动作（删除数据、资金转移、对外发送）需要身份校验或二次确认，低影响动作可直接执行；分级判断发生在权限校验之后。
