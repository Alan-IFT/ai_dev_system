## 原文结论与适用限制

- **Running Codex safely**：把编码 agent 的治理拆成"边界+遥测"。边界侧是沙箱执行边界、审批策略、托管网络策略（放行/拒绝/未知域需批准）、OS keyring 存凭据、强制经企业工作区登录、规则（每条 shell 规则带 `justification`）、**管理员强制的 requirements（用户不可覆盖）**。遥测侧的核心判断：**传统安全日志答"发生了什么"（进程起了、文件变了、试图连接），agent 原生遥测答"为什么、用户意图是什么"**——Codex 支持把用户提示、工具审批判定、工具执行结果、MCP 使用、网络代理放行/拒绝事件按 OpenTelemetry 导出，可进 SIEM 与合规日志，供 AI 安全分诊 agent 还原原始请求与意图。
- **内部监测**：用最强模型（GPT‑5.4 Thinking 满推理）做低时延异步监测，在完成后约定时限内复核全量内部编码 agent 轨迹（含思维链、各类消息、工具调用与返回），分级、只把标记项送人复核；**该系统标出了每一条员工独立上报的交互**（即以员工上报作召回率下界），并发现了许多本会被忽略的行为；自陈局限：依赖可监测性、无法在开放真实流量上自信量化漏检率、**极小部分本地自建/定制部署不在覆盖内**（登记为待补的盲区）。内部编码 agent 的独特风险：可读甚至试图改自己的安全防护、可能影响自己的未来版本。路线图：控制评估估计召回、把异步改为同步阻断。

适用限制：面向前沿实验室的内部编码 agent 大规模部署，具体工具（Codex、OTel 导出、企业合规平台）属载体；本标准取"agent 原生遥测要素""异步复核要登记覆盖率与校准""两层授权"这几条结构要求。

## 缺口

- [04 §6.1](../04-可靠性安全与运行维护.md#agent-run-observability) 的"最少留存"表偏重运行身份/执行结构/用量/结果状态/副作用回执/会话事件，**没有专列 agent 原生遥测的意图与审批要素**（用户提示、审批判定、工具执行结果、网络代理放行/拒绝），也没写这些"答为什么/意图"的价值。
- §6.1 有盲区登记，但**没写异步复核本身要登记覆盖率与校准**（按时限复核、只送标记项、以人工上报作召回率下界、明确不覆盖部分）。
- [01 §5.5](../01-项目管理标准.md#controlled-actions) 有受控动作与执行点，但没写**管理员强制层（用户不可覆盖的托管配置）+ 每条放行规则带 justification**这一"两层授权"结构（属跨方向）。

## 采纳

均并入 §6.1 既有段落。

- **§6.1 意图与审批要素**（§6.1"最少留存"表新增一行）：用户提示、工具审批判定、工具执行结果、网络代理的放行/拒绝事件分别可追溯，可汇入 SIEM 或合规日志；传统日志答"发生了什么"，这些要素答"为什么、用户意图是什么"。**触发**：Agent 承担会改动仓库、发布或生产的动作。**责任**：工具维护者定义并保留。**工件**：四类要素的可追溯记录及其进 SIEM/合规日志的通道。**验收**：取一次运行，能否分别取回用户提示、该步审批判定、工具执行结果与网络放行/拒绝事件。**失败依据**：只有传统日志时，安全分诊只知发生了什么、答不出为什么与用户意图。**复查/删除条件**：项目只有人工开发时随 §6 记不适用。
- **§6.1 异步复核覆盖率与校准**（并入 §6.1 采集段后）：运行记录若接上异步复核，复核本身要登记覆盖率与校准——按约定时限复核轨迹、分级、只把标记项送人；用独立的人工上报作召回率下界；明确不在覆盖内的部分（本地自建、随会话销毁的部署）登记为盲区；厂商报告的复核时限、漏检率与轨迹量只作观察。**触发**：把运行记录接上任何自动/半自动的异步复核。**责任**：运行负责人（覆盖率与校准）、工具维护者（采集）。**工件**：复核覆盖率清单、校准依据（人工上报对照）、盲区登记。**验收**：能否说出复核覆盖了哪些、不覆盖哪些；人工独立上报的事件是否都被复核标出过。**失败依据**：某监测系统自陈极小部分本地/定制部署不在覆盖内、无法在开放流量上自信量化漏检——覆盖与校准不登记则漏检被当成没问题。**复查/删除条件**：不使用异步复核的项目记不适用。

## 跨方向建议（不由本方向修改）

- 给 **01 §5.5**：**管理员强制层（用户不可覆盖的托管配置）＋每条放行规则带 justification**，即"两层授权"——平台强制的硬边界 + 会话内的用户授权，模型都不能改前者。失败依据：Codex 的 requirements 是 admin 强制、用户不可覆盖，规则文件每条 `prefix_rule` 带 `justification`。这与 01 §5.5 的执行点在被约束者之外同向，建议明确"硬边界由平台强制、会话内授权是第二层、二者模型都不可改"。

## 验证办法

① 取一次运行，分别取回用户提示、该步审批判定、工具执行结果、网络放行/拒绝事件；缺任一记缺口。② 说出异步复核覆盖了哪些轨迹、不覆盖哪些；取一条人工独立上报的问题，确认复核也曾标出它。③ 检查放行规则是否每条带可读的 justification、托管配置是否用户不可覆盖。本仓库无 agent 遥测与监测数据，上述验证未定（生成者与验证者同一）。
