# M-26 · 多仓系统的工件分布：一次真实项目的只读测绘

## 来源与阅读边界

- 对象：`NFBY_CMS_FullStack`，一个由人与 AI 编程工具共同开发、当前暂停开发等待管理标准落地的**私有生产项目**。本卡不转载其代码或业务内容，只记与工件分布有关的结构事实。
- 类型：**真实项目的直接观察**。它比公开快照（真0）更接近现场——读到的是工作区当下的状态而非经筛选脱敏的发布集；但同时更弱——**不可被第三方复核**，且本次只做只读测绘，**未运行其任何检查或脚本**，故其规则是否真被执行一律未测。
- 访问日：2026-09-10。方法：`git ls-files` / `git log` / `git remote -v` 与文件比对，全程未写入被测项目。
- 未做：未与项目负责人核对老仓的去留意图；未读两个应用仓的代码结构（该部分测绘中途按用户要求停止）；未验证任何闸门的实际执行。

## 观察到的事实

四个 git 仓库并列检出在同一目录下，各自独立远端，不是 submodule：

| 仓 | 角色 | 跟踪文件 | 最近提交 |
|---|---|---|---|
| `NFBY_CMS_FullStack` | 控制平面（部署链、运维脚本、跨仓集成闸门、三仓共同的决策历史） | 1786 | 2026-09-07 |
| `NFBY_CMS_Backend` | 应用 | 676 | 2026-09-07 |
| `NFBY_CMS_Frontend` | 应用 | 369 | 2026-09-05 |
| `NFBY_CMS` | 拆分前的老单仓 | 2826 | 2026-08-18 |

复算：`git -C <仓> ls-files | wc -l`、`git -C <仓> log -1 --format=%ad --date=short`。

**一、同一份文档在两个仓各有一份。** 控制平面仓的 `docs/` 与老仓的 `docs/` 有 **1614 个同名文件**，覆盖 `features/`、`batches/`、`tasks.md`、`ops/`。复算：`comm -12 <(git -C <控制仓> ls-files docs | sed 's|^docs/||' | sort) <(git -C <老仓> ls-files docs | sed 's|^docs/||' | sort) | wc -l`。两边内容的一致性本卡未逐份比对，记未测。

**二、退役仓保留着完整且已过期的规则集。** 老仓仍带 `.harness/rules/`（10 份）、`.claude/settings.json`、agents 与 skills；其入口文件描述的是一套"7 阶段流水线、子 agent 不自路由、由 PM Orchestrator 调度"的工作方式，而控制平面仓的入口写明**该流水线已于 2026-08-17 由用户决定移除**（"记录留下，机器走了"）。两份文本直接冲突，且都仍在各自仓的会话入口位置。

**三、系统级入口没有列出该仓。** 控制平面仓的入口只列了它自己与两个应用仓，未提及老仓。**结果是：从系统级入口出发无法发现老仓存在，而在老仓目录里起一次会话则会把过期规则当作现行规则读入。** 这两个方向都不经过任何检查。

**四、跨仓引用被当作契约处理，这一条是正面的。** 控制平面仓入口写明"两个应用仓的 `docs/decisions/README.md` 指着这里，所以**这些路径是契约**：搬动它们要同步改那两份文件"。该项目自己已经把跨仓路径的稳定性识别为契约问题。

## 缺口、采纳与不采纳

01 §3 的文档树是**单仓形态**：一棵 `project/` 树、一份入口、一处状态。它没有回答系统跨越多个代码仓时工件归谁。缺了这一条的后果不是"文档写得不好"，而是**"每个仓各有一份入口和一套文档"成为默认结果，而不是一次被记录下来的设计决定**——上面四项观察全部是这个默认的产物。

- [01 §3.8](../01-项目管理标准.md#multi-repo-artifacts)（新增）：系统级工件的单一权威与归属判据、各仓入口是投影不是副本、退役仓必须登记状态并使其规则失效、跨仓引用按契约处理。失败依据取自观察一至三；观察四作为"跨仓引用是契约"这一条的正面佐证。
- **不采纳**：该项目具体的目录名、脚本名、闸门编号与版本钉子机制（载体，且属该项目的技术选择）；其"控制平面仓"这一称呼不写进标准，标准只要求**指定一个仓承载系统级工件**，不规定它叫什么、也不要求它必须无应用代码。
- **不重复**：跨仓改动的顺序与回退边界、代码位置作为第四种边界、共享命名空间分配、公共能力清单的跨仓入口，已由 [02 §2.2](../02-项目架构描述规范.md#runtime-deployment)、[§4](../02-项目架构描述规范.md#dependency-rules) 覆盖（来源 A-06）；本节只管**文档与管理工件**放哪，不重述架构侧的规则。评审输入须覆盖跨仓已在 [01 §4.4](../01-项目管理标准.md#review-flow)（来源 M-24）。

## 验证办法

在一个多仓系统里取三条系统级事实（一条验收条目、一条跨仓契约、一条当前状态），各问一次"它的唯一维护位置在哪"，再在每个仓里 grep 是否存在第二份文本。再从每个仓的入口出发，看能否在两跳内到达系统级权威、能否读出系统由哪几个仓组成及各自状态。退役仓一项的验收是：在退役仓目录里起一次全新会话，看它读到的规则是否被明确标记为失效。

本卡的观察本身**未经这套验收**——它是发现问题的过程，不是已通过的证据。该项目按新增条款的改造尚未进行，收益与代价未定。

## 逐篇闭环

本卡是本轮唯一一张来自私有生产项目直接观察的卡。写卡后即新增 01 §3.8 并回指本卡，未改动被观察项目的任何文件。同批停止的两份代码结构测绘（后端、前端模块清单）不属于本卡范围，其未完成状态记断点。

按 [01 §3.8](../01-项目管理标准.md#multi-repo-artifacts) 的退役条款处置老仓：给其规则文件逐份加上失效头后，跨仓检查器的退役判据由 FAIL 翻成 PASS。同一时刻复看该仓的可执行面，`.claude/settings.json` 里的会话启动钩子与 pre-tool-use 钩子仍然装着，`.harness/scripts/` 下的校验、升级、装钩子脚本全部在位。本次仍未运行被观察项目的任何脚本，钩子“已装且会随会话启动”取自其配置文本，未实地触发验证。

**这不推翻本卡原有结论，是补它没覆盖的一个面**：原条款的对象是入口与规则文件，即会被读的东西；会自动执行的东西不在其内，而检查器只读文档里的失效标记，于是“贴了提醒”被判成“已退役”。01 §3.8 据此增补了针对可执行面的处置、验收与执行点。
