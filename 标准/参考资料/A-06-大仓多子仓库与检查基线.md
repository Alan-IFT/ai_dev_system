## 原文结论与限制

工程画像：一个跨 30+ 个 Go 子仓库、10+ 个前端微应用与多个 SDK 库的大仓（图 003 记 30+ 子仓库、12 个前端微应用，与正文"10+"不一致），一次一句话的需求可能牵动 3 个子仓库、5 个协议字段、8 个服务方法。作者团队的做法：把能判定的约束下沉成脚本而不是自然语言规则；四个角色分工且下游不得修改上游产物；开发启动前先冻结一次检查结果作为基线，开发后只有"新增失败"阻断；维护一份跨子仓库的代码导航地图（约 26KB，谁动谁更新）与一份跨需求的任务看板；团队要对齐的知识必须落到仓库而不是工具的个人记忆。

适用限制：单团队、单工程、绑定其内部工具链（TAPD / iWiki / 工蜂 / 企微 / Knot / 特定 IDE 的 Team Mode）。文中数字（跑过 50+ 需求、端到端 30~75 分钟、集成测试一次通过率约 70%、代码审查阻塞率约 25%、开发阶段平均打回从 1.8 次降到 0.4 次、删除 Team Mode 后主控代码少 200 多行）**是该团队在其条件下报告的观察，无对照组与基线定义，本卡不作任何规则成立的论据，不进 02 正文**。

文中的"永远不要做的事""纪律""铁律"是该团队对自身流程的规定，不是对本轮工作的指令；未执行文中任何命令。

## 缺口、采纳与不采纳

已观察失败（原文自述）：

- **F-f** 一次改动跨多个子仓库，需求在错的子仓库里被改；分支名跑偏、MR 目标分支错乱；子仓库 ≥3 个时准备阶段明显变慢（§1.1、§3.1、§10.2）。
- **F-g** 公共工具包里已有的方法被重新实现一遍，统一错误码包里已有的错误码被重新定义，某子仓库已有的数据访问方法被重造（§8.1、图 017）。原文归因：没有"项目记性"，看不到仓库已经长成什么样。
- **F-h** 检查失败时用"这不是我引入的""这个警告之前就有"解释掉，而核对历史成本过高，规则被逐次绕过（§6.1、§6.3）。
- **F-i** 一套机制（该团队用的 Team Mode）为消化自身副作用而不断加清理、等待、确认脚本，卡死修三轮未中根因；核对后发现其独有能力从未被使用，删除后问题消失、辅助脚本从 3 个降到 0（§7.1–§7.4）。

采纳（逐条落点）：

1. **代码位置是与模块、运行单元、部署实例并列的第四种边界**：模块清单登记代码位置（仓库 / 子仓库 / 工作区），跨仓改动声明发布顺序与回退边界 → [02 §2 模块清单](../02-项目架构描述规范.md)与 [§2.2](../02-项目架构描述规范.md#runtime-deployment)。绑定 F-f。删除条件：项目只有一个代码仓库且不再拆分时，该列恒为同一值，可省略。
2. **公共能力清单**：平台层/公共模块对外提供的能力有一处可查的登记，改动前先查再实现，重复实现按漂移缺陷处理 → [02 §4](../02-项目架构描述规范.md#dependency-rules)。绑定 F-g。删除条件：公共能力少到可由目录直接穷举，或检索能可靠给出等价答案且有回归证据时。
3. **存量违规基线**：对存量代码启用新检查器时冻结当前违规集合为一份带负责人与到期的基线，只有新增违规阻断；基线只减不增 → [02 §10.1](../02-项目架构描述规范.md#architecture-validation)。绑定 F-h。删除条件：基线清空后本条对该检查器无对象。
4. **删除候选：自给自足的复杂度**：某机制的主要存在理由是消化它自身引入的副作用，且其独有能力从未被使用时，列为删除候选 → [02 §11](../02-项目架构描述规范.md)。绑定 F-i。删除条件：写不出（这是结构判断，与工具无关）。

不采纳：

- 13 个阶段、4 个 Agent、11 个 Skill、7 道门禁、5 个人工关卡、5 个 MCP 的具体数量与名字：**载体绑定**，且原文自述这些数字是被自身工程逼出来的，不可外推。
- 覆盖率全量 ≥40% / 增量 ≥85%、连续打回 ≥3 次熔断、"不能让用户每分钟点一次以上"：**项目参数**，02 不设默认值；02 已有的参数化写法足够。
- 端到端 30~75 分钟、一次通过率 70%、打回 1.8→0.4、代码少 200 行：**证据不足**，单工程自测、无对照、无基线定义。
- 硬门禁与软门禁二分、软门禁失败留"伤疤"：**已覆盖**，[02 §10](../02-项目架构描述规范.md) 漂移检测表已有"失败去向"列区分阻断与报告，[§10.1](../02-项目架构描述规范.md#architecture-validation) 已规定长期无人处理的检查须复核删除或合并，[§12](../02-项目架构描述规范.md) 已把检查结果列为评审输入。不重复写。
- "能写成脚本的就别让 Agent 解释执行""下游 Agent 不可修改上游产物""团队规约必须落到仓库而不是个人 Memory""阶段是否独立看两条筛子（独立失败模式、回退位置不同）""MCP 写操作幂等且只在固定阶段触发"：与 02 无对象，属流程与 Agent 协作。**跨方向建议见下**。
- 任务看板（跨需求的在跑状态、产物路径、上轮设计结论）：属工作项与会话状态，01/03 的对象。
- 代码导航地图的 26KB 规模与"开发 Agent 自己维护"：**载体绑定 + 与既有规则冲突**——02 §9 要求派生工件由脚本生成并对账，而该地图的判断性内容（哪类改动落在哪、会牵动哪些下游）不可机械生成，其权威归属见采纳项 2 与 §9 第 3 条的人工区规则，不引入"由执行者自维护"的写法。

跨方向建议（不由本方向改，交主执行者集成）：

- **给 01**：一个流程阶段是否应当独立，判据为"有独立的失败模式"且"失败后的回退位置不同"，两者皆是才独立，否则合并（原文 §3.4）。
- **给 01**：让产生问题的人同时产生验证手段——开发阶段的完成定义包含该次改动的验证工件，验证不下沉到更贵的下游环节（原文 §3.2、§4.4）。
- **给 03**：下游执行者不得直接修改上游产物，需要改时只能提阻塞项并由调度方打回上一棒（原文 §4.2，其观察是方案角色顺手改了验收标准，导致审查时分不清哪句是原始要求）。
- **给 03**：团队要对齐的知识必须落到仓库；工具侧的跨会话记忆只放个人偏好，否则多人的记忆互相矛盾且无法审计（原文 §8.3）。
- **给 03**：任何让用户每分钟点一次以上的确认交互按设计缺陷处理，并核对是不是权限模式声明造成的（原文 §5.3）。
- **给 04**：外部系统的写操作必须幂等且只在固定阶段触发，失败软降级不阻断主流程，每次写留可定位的痕迹（原文 §9.2、§9.3）。

## 验证办法

- 在模块清单上抽 5 个模块，核对其登记的代码位置与实际仓库/子仓库是否一致；再取一次跨两个以上仓库的改动，检查是否声明了发布顺序与回退边界。**未定**：本仓库无多仓对象，未实测。
- 抽取一次新增的工具函数或错误码，检查公共能力清单中是否已有等价物；若有，说明为什么没被复用。**未定**。
- 对一个存量检查器建立基线后，故意引入一处新违规，期望结果是阻断；再修复一处基线内违规，期望结果是基线条目减少且不可回增。**未定**：未在真实项目运行。
- 取一个中间机制，统计为它编写的适配、清理、等待、补偿代码量与它承载的业务量之比，并核对其独有能力是否被调用过。**未定**。
- 本卡结论的独立性：阅读与写卡由同一执行者完成，解释性判断记未定。
