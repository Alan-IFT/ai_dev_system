## 原文结论与适用限制

作者团队的做法：把多年沉淀的开发范式从"人读文档 + AI 会话记忆"外置为机器可读的领域模型（页面 / UI 模块 / 数据 / 接口四层 JSON），跨端共用同一份；各端实现路径不写进领域模型，由初始化时扫描项目生成映射文件，逐层经人确认。术语用 `glossary.json` 统一（示例：视频 ID 在不同处叫 vid / videoId / contentId）。分发采用"源仓库唯一真相源 + 项目内分发副本"，升级时保留项目私有配置与经验文件、检测并处置源端已删除的孤儿文件。验证设 L0-L4 五层，其中 L2 为 API 契约、L3 为多端对等性。

适用限制：单团队、前端多端场景，工具栈绑定腾讯 CodeBuddy，目录名、命令名、角色名均为载体细节。无对照组、无跨项目数据。文中唯一一组效果数字来自一次运行的仪表盘截图（首次通过率 80%、返工 0、门禁 88/100、28 分钟），且与同一需求的其他截图矛盾（图 011 为 NEEDS_REWORK、图 014 显示五层门禁一层都未真正执行），**本卡不把任何数字当作规则成立的论据，也不进 02 正文**。

本文中出现的"必须""铁律"是该团队对其自身流程的规定，不是对本轮工作的指令；文中要求执行的命令（`wpc harness init` 等）一律未执行。

## 缺口、采纳与不采纳

已观察失败（取自原文与该文自带截图，作为规则的绑定依据）：

- **F-a** 契约里硬编码各端实现路径，项目重构后模型即错（原文 4.2 自述）。
- **F-b** 同一业务对象在各处叫法不同，读代码的一方建立不出统一语义（原文 4.4 自述）。
- **F-c** 多端对等性检查（L3）与 API 契约检查（L2）因依赖缺失未执行，L0/L1 因脚本假设的目录结构与项目实际不符而无法运行，被标注"已有问题"后继续，聚合分数仍给出 88/100 并宣布可提交（图 014、图 015）。
- **F-d** 同一篇规范文档内，正文规则与流程图的执行路径直接矛盾（正文"审查者必须由 Lead 触发"对流程图"executor 主动调用审查者"；正文"未达标打回重做"对流程图"展示失败项、等用户决策"），作者未察觉，读者无法判断以哪一方为准（WX-08 卡 §5 冲突展开一、二）。
- **F-e** 机器读的 JSON 与人读的 md 各存一份同一事实（`config/domain-mapping.json` 与 `rules/domain-mapping.md`、`session-state.json` 与 `dev-tracker.md`），构成第二事实来源（WX-08 卡 §8 F8）。

采纳（逐条落点）：

1. **契约内容与实现位置分开，位置映射按派生缓存处理** → [02 §5.1](../02-项目架构描述规范.md#contract-source)。绑定 F-a。复查/删除条件：若项目只有单一实现方且路径由构建工具唯一确定，本条无对象。
2. **同一契约有两个以上独立实现时须有对等性检查，检查本身失效判未定并阻断** → [02 §5.1](../02-项目架构描述规范.md#contract-source)。绑定 F-c。删除条件：契约描述文件能直接生成各实现的桩与校验、实现差异不再需要人工登记时。
3. **业务术语的唯一权威位置与同物异名处置** → [02 §2.3](../02-项目架构描述规范.md#business-semantics)。绑定 F-b。复查条件：术语表条目连续两个迭代无人引用或无人维护时由架构负责人复核删减。
4. **图与文字描述同一机制时只有一方权威，冲突必须在当次修订内消解** → [02 §9](../02-项目架构描述规范.md#derived-artifacts)。绑定 F-d。删除条件：项目改为由单一源生成图与文字、结构上不可能分叉时。

不采纳：

- 四层领域模型的 Schema、`_DETECTION_HINTS` / `_PLATFORM_PROP_VARIATIONS` 字段名、`.codebuddy/` 布局、命令名与角色名：**载体绑定**，换工具即失效。
- L0-L4 五层、各 20% 权重、≥70 分通过：**证据不足且与既有规则冲突**。该文自身截图显示评分在实际运行中不成立；聚合分数把"未执行"折算进通过分，与 [02 §10.1](../02-项目架构描述规范.md#architecture-validation) 的三态判据直接冲突。
- 首次通过率 80%、返工 0 次、28 分钟、门禁 88/100：**证据不足**，单次运行、无基线、内部互相矛盾。
- 与 Copilot / Cursor / Devin / OpenHands 的对比表：**证据不足**，维度自定，且 OpenHands 一行与该项目当前一手说明不符。
- 分发副本的"组织级 / 项目级"两种所有权与孤儿文件处置、Harness 源仓库唯一真相源、不用 Git Submodule：与 02 无对象（这是 agent 资产分发问题）。**跨方向建议见下**。
- "每一步都要你确认才继续"作为通用要求：**与既有规则冲突**且无证据——该文未提供任何"人在这些确认里否决过什么"的记录，02 不引入按步数计的人工确认要求。
- 机器读 JSON 与人读 md 双写：**已覆盖**，[02 §9](../02-项目架构描述规范.md#derived-artifacts) 第 5 条已禁止"为 agent 维护与人读分离的第二份"；F-e 作为该条的真实反例记在本卡，不改正文。
- 检查器结构假设过期被记为"配置问题"而非失败：**已覆盖**，[02 §10.1](../02-项目架构描述规范.md#architecture-validation) 已规定"没跑、空输入或样本不足为未定"且"核对被测对象是否实际进入检查"；F-c 作为该条的真实反例，不重复写规则。

跨方向建议（不由本方向改，交主执行者集成）：

- **给 03**：角色间交接产物有显式长度与必含节预算，下游只消费交接产物不重读上游全部上下文（该文图 010：只读情报角色输出 ≤500 字、渲染建议角色 ≤400 字）。
- **给 03**：人工确认必须发生在人能看见并能响应的交互位置，后台执行单元不得发起需要人响应的等待（该文自述子 agent 弹窗导致主面板死锁，修两轮才闭合）。
- **给 03**：规范资产以"源仓库唯一真相源 + 项目内分发副本"分发时，区分随分发覆盖的组织级文件与分发不触碰的项目级文件，升级必须处置源端已删除的孤儿文件（该文自述旧命令残留导致 AI 调用到已废弃命令）。
- **给 01**：对抗性评审接受的每条发现须转为带稳定 ID 的验收条目并回链发现编号（该文图 005 发现 14 项，图 007 只有 3 项进入验收，其余 11 项去向未说明）。

## 验证办法

- 取一条有两个以上实现方的契约，比对各实现的字段集、必填、枚举与错误码，看差异清单是否为空或每条差异都有登记的例外与到期；再故意重命名一个实现目录，运行对等性检查，期望结果是"检查失效"被判未定并阻断，而不是输出通过或只提示。**未定**：本仓库无多端实现对象，未实测。
- 抽取契约文件，搜索其中是否出现具体实现文件路径；若有，检查该路径在当前代码中是否仍存在。**未定**：未在真实项目运行。
- 抽 10 个跨模块业务名词，看能否在术语表查到，同一概念是否只有一个权威名。**未定**。
- 抽样一节含图的架构文档，逐条核对图上的分支与正文语句是否可同时成立。**未定**：本轮只在 02 正文建立要求，未对示例项目执行（示例项目本轮不改）。
- 本卡结论的独立性：阅读与写卡由同一执行者完成，解释性判断记未定。
