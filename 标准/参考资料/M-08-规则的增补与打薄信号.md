## 原文结论与适用限制

标题的"删掉 80% 的 Prompt 规则"在正文中没有对应的量化记录；正文的主张是三件事——可信上下文、可执行约束、可恢复流程——以及一条增删判据。与 01 有关的：

- **约束力由违反后果决定，不由措辞决定**："如果条件不满足，任务仍然可以继续，它就只是一句提醒；只有条件不满足时，下一步真的无法进行，它才是可执行的约束。"分界点不在有没有脚本，而在**脚本是否自动进入任务的必经路径、失败是否改变后续状态**。
- **两类检查分工**：阶段之间的门禁回答"上一步是否真的完成"（例：进入评审前检查测试报告是否存在、是否本次任务生成、是否在本次修改的代码目录运行、是否调用了项目规定的测试入口、需求写明的必测场景是否真的执行）；动作之前的检查回答"这个动作能不能执行"（推保护分支、强推、跳过项目检查、破坏当前代码现场、未经允许改高风险字段）。作者说明其中一部分检查"不代表每一种风险都曾经造成过真实事故"，是按已知风险提前补的。
- **沉淀的阶梯**："一次问题先修复；重复出现的路径再沉淀；能够机械判断的部分，最后才变成约束。"载体依次是文档 / Runbook → Skill / Script → Gate。
- **候选的发现机制**：其 `AGENTS.md` 里有一段任务后的能力观察规则——只在出现明确信号（重复劳动、反复纠正、反复找同一上下文、可复用命令、反复打外部系统、现有 Rule/Skill/MCP/文档缺口）时输出**一项**证据最充分的候选，无信号则不输出、不扩建，只建议不自动改，写入前必须用户确认。
- **Add / Thin 的信号**（结语）：重复失败、缺少证据、无法恢复 → Add；长期无人消费、重复实现、频繁误伤、明显负收益 → Thin。作者明确"不意味着要定期专门证明某条控制是否还在发挥作用"，判断来自日常任务的观测。
- **不照搬**：同一种工程目标在不同项目落点完全不同；可复用的是发现问题和修复问题的方法，不能照搬已绑定旧项目结构的实现。
- **一条结论要带它依赖的现场**：作者给的最小记录是 claim / source / revision / scope / observed_at / verification，并强调字段按真实问题逐步增加，不一次加满。

**适用限制**：两个项目的单人自述，无对照、无前后数据；文中所有检查项、目录结构与脚本名绑定其项目实现。"删掉 80%"没有可核对的口径，本卡不引用为论据。作者自陈部分门禁是按已知风险预设、未经真实事故，采用方需按 01 §2 N3 自行绑定依据。

## 缺口、采纳与不采纳

01 §4.7 的季度减法只写了"零消费只触发调查"，没有其他删除信号；§4.2 的候选沉淀没有触发门槛，容易每次任务硬凑一条，正是 G9 所防的只增不减；§7 表里出现过"四级约束力（提醒/工具/警告/约束）"，但正文没有任何一处定义什么才算约束；§5.5 与 §5.6 分别写了动作前授权与阶段闸门，从未说明二者分工。

**采纳**

- [01 §4.2](../01-项目管理标准.md#session-protocol) 收工前第 4 条：候选须有明确重复信号才产出，一次任务至多一项；并给出沉淀阶梯——先只记录，同一路径重复出现再写成做法，步骤稳定且高频再做成技能或脚本，能机械判定且失败后不应继续的最后下沉为闸门，不跳级。触发条件为每次收工；责任角色为执行方提候选、具名负责人决定升级；工件是工作项候选区与升级记录；失败处置是无信号不产出。风险依据：G9 的规则膨胀失效路径与原文的能力观察规则。复查条件：候选区连续两个季度无升级项时，按 §4.7 减法复核本机制本身。
- [01 §4.7](../01-项目管理标准.md#maintenance-budget) 每季度一行：删除信号补齐为长期零消费、同一约束在多处重复实现、频繁误伤、明显负收益（原单元格内改写，不新增行）。
- [01 §5.6](../01-项目管理标准.md#gates)：定义约束力——一条要求只有在不满足时下一步真的无法进行时才是约束，否则是提醒；检查须自动进入必经路径且失败改变后续状态，靠执行者记得去跑的不计为闸门。同处点明两类检查的分工：阶段闸门验"上一步是否真的完成"，受控动作核对（§5.5）验"这个动作能不能执行"。
- [01 §8](../01-项目管理标准.md#adoption)：采用时不照搬其他项目已长成的规则集与检查实现，只迁移判据与方法；实现按本项目的真实任务重新长出。

**不采纳**

- 可信上下文供应链、知识库三跳路由（`AGENTS.md` → `context.md` → 专题文档/源码）、`knowledge-index.jsonl` 按场景标签路由、Context 是沿任务路径逐步组装的工作集：对象是 agent 的信息获取，属 **03**，01 不写。
- claim/source/revision/scope/observed_at/verification 最小记录：与 01 §4.2 的证据六字段（断言、原始证据、版本与工作区身份、适用范围、观察时间、确认方法）逐项同构，**已覆盖**；本卡记录它是一条独立同构证据，不改字段名。
- "某处已经存在 ≠ 当前已经生效"（本地已修复但该次 Nightly 消费的仍是旧 revision）：01 §4.1"`done` 不代表已合并、已部署、已发布"、§4.5 分别记录已部署与已开放、§5.9 环境身份可回读，三处**已覆盖**。
- 可恢复流程的 `state.json`（书签）/ 交付日志（正文）分工、"每阶段结束立即换新 Agent 还能否继续"的自测：与 01 G7 的接手演练、§4.2 交接、§3.1 的状态工件**已覆盖**；机器可读状态文件的具体形态属 03。
- 阶段门禁的具体检查项（报告是否本次生成、测试目录与代码目录是否一致等）：绑定其项目实现，采用项目须自行绑定失败依据，01 只保留判据不列清单，**场景不适用**。
- "删掉 80% 的 Prompt 规则"这一标题结论：正文无口径、无数据，**证据不足**，不作为论据也不转述。

## 验证办法

在采用项目取 `GATES.md` 与 `PLAYBOOK` 全部条目，逐条回答两个问题：不满足时下一步是否真的无法进行；检查是否在必经路径上自动执行。再取近两个季度的候选区，统计有多少候选带明确重复信号、有多少最终升级，核对是否存在"每次任务凑一条"的模式。删除信号那条，用一条已知误伤频繁的规则走一遍减法流程，看是否能在不等零消费的情况下被删掉。本仓库无候选区与闸门运行数据，上述验证**未定**（生成者与验证者同一）。
