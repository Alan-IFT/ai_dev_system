## 原文结论与适用限制

这是一份面向某公司内部工具链（CodeBuddy / Knot / 工蜂 / iWiki / TAPD）的团队落地规范。与 01 相关且不依赖具体产品的主张：

- **约束分层**：Rules 分 User（个人、工具设置页）/ Team（平台统一下发、需审批）/ Project（仓库 `.codebuddy/rules/`）三层；团队规范的唯一真实来源是一个独立的 `team-harness` 仓库，业务项目通过同步脚本拉取，可选接入 CI 自动同步。
- **团队协作红线**（原文列为不可违反）：先 Spec 后 Code；**项目级 Rules 必须同步至 Git 仓库，不允许本地私有**；通用逻辑抽象为 Skill 供全队复用；关键元数据优先通过 MCP 实时同步而不是手动维护副本；变更可追溯。
- **入口文档**：`AGENTS.md` 控制在约 100 行，当目录索引用，指向细分文档；原文提到 OpenAI 早期"一个巨大的 AGENTS.md"的做法失败，正确做法是拆成多个专注文档用索引串起来。
- **反模式清单** 8 条，与本卡有关的：Rules 写完不维护、半年后与实际规范脱节；MCP 接入过多导致 Token 消耗暴增；一个 Skill 塞太多功能；聊天记录当文档；盲目信任 AI 输出不审查。
- **合规自检**：把规范的检查项固化成一个可执行的 `harness-audit` Skill，按 7 维度打分并给改进建议；原文明确"审计报告是体检结果，不是 KPI，不要把分数当指标考核"。

**适用限制**：全文围绕一套特定内部产品的配置步骤，大部分内容（安装、平台页面路径、mcp.json 字段）不可移植。文中未给任何前后对比数据，本卡也不引用其"效率提升 10 倍"等转述自 OpenAI 的说法。分层三级、红线与反模式均以规范条文形式给出，未附各自的失败记录，属该团队的主张而非可核验的观察。

## 缺口、采纳与不采纳

01 假定项目的一切约束都在仓库里，没有处理两件真实情况：① 工具账号级配置（个人 Rules、跨会话记忆）与平台下发的团队规则**不随仓库走**，接手者和另一个工具读不到；② 多项目团队的规则有一个仓库外的上游，项目内的是副本。01 §2 N2 只说"同一事实一处权威"，未说跨仓库时权威在哪、副本怎么对账。

**采纳**

- [01 §3.2](../01-项目管理标准.md#doc-responsibility)：新增"仓库外的约束"一段。触发条件为约束被写在工具账号级或平台侧；责任角色为项目所有者；工件是仓库内该约束的权威位置与工具侧的来源标注；失败处置是把影响产出的约束移回仓库、工具侧只留投影或个人偏好。风险依据：G1（知识随仓库）的失效路径——接手者只读仓库时读不到该约束，加上原文"项目级 Rules 不允许本地私有"红线与"Rules 半年后脱节"反模式。复查/删除条件：项目只有一个仓库、无仓库外规则源时本条不适用；团队级规则源退役后按 §4.7 减法删除。
- 同段并入团队级规则的同步：多项目共用的规则权威在一处，项目内副本按 §3.4 的派生关系带来源版本并机械对账，不在项目内单方面改；项目特有的规则写在项目内并注明为什么不上收。

**不采纳**

- 三阶段实施路线图（1-2 周 / 2-4 周 / 持续）与工具安装、平台配置步骤：绑定特定产品，**场景不适用**。
- "半天以上工作量的需求必须走 Plan 模式"：以工作量估算作为流程分档的触发条件，与 01 §4.3"不以修改行数判断风险"同类问题——**与既有规则冲突**，01 按风险分级不改。
- 多 Agent 角色划分（Planner / Generator / Evaluator / Archiver）：其可检查的内核即"生成者 ≠ 验证者"，01 §4.4 与 §6.1 **已覆盖**；再加一层角色名不增加判据。
- "先 Spec 后 Code""变更可追溯""一个 PR 一件事""修 Bug 先写复现测试"：01 §4.1、§5.1、§5.2 **已覆盖**。
- `harness-audit` 式的采用度打分：01 的对应位置是《覆盖与采用检查》，该文已声明它不是认证表；再在 01 里写一条评分机制会造成第二处权威，**已覆盖**且违反 N2。原文"分数不当 KPI"的告诫与 01 §4.8 反游戏条款同源，不重复。
- MCP 接入数量与 Token 消耗、Skill 原子化、知识库挂载与自动引用：属 03 的对象，见下节，01 不写。
- 效果性表述（"效率提升 10 倍""SQL 准确率提升 30%+""Commit 规范率 70%→95%"）一律不采纳为论据。

## 验证办法

在采用项目做一次盘点：列出当前生效的全部约束，逐条标注它写在哪里（仓库 / 工具账号 / 平台），凡不在仓库的，检查新会话只读仓库能否得知该约束存在；再对项目内的团队规则副本核对来源版本是否与上游一致。本仓库无团队级规则上游，也无多项目样本，上述验证**未定**（生成者与验证者同一）。
