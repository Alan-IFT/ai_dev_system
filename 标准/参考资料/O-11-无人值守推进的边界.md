## 原文结论与适用限制

作者的问题陈述是：每个岗位配上 AI 之后单点变快，但一件事仍要靠人"看、转、推"——需求等人评审、评审完等人转述、做完等人验收，因此人下班 Agent 也下班。解法不是造更强的单体 Agent（作者判断其可控性、可观测性、责任边界都不好处理，中途出错几乎没有干预点），而是让外部事件触发系统接手，由工作流组织多个 Agent 接力。第一阶段补出三根骨架（Agent 能力池与路由、可运行的工作流对象、与外部系统的 Hook/Callback 交接），再从真实运行中补出六类能力：结构化准出字段与 pass/fail/blocked 三态裁定、Fan-out 并行与 AND 收敛、End Node 与验收/定向返工、blocked/timeout/Sweeper 自愈、失败诊断字段、事件驱动的四层指标。作者反复强调的两条判断是：**正向链路跑通只证明能跑，失败路径能处理才证明可用**；**Agent completed 不等于 business completed**。第 4.4 节自述"最怕的不是失败，而是静默卡住"。

适用限制：**这是第一阶段的建设自述，不是效果验证**。作者自认"第一阶段的数据还不是长期运营口径下的正式指标"，全文无前后对照、无对照组、无任一场景的样本数与一次通过率。唯一的正文量化陈述是"平台已集中管理 30+ 个来源各异的 Agent"，其余数字全部来自截图，且截图中多条工作项带"[演示]"标签，指标页同一处两个互相矛盾的"首次通过率"（100% 与 50%），"过去 7 天完成 0"与"某 Agent 386 任务成功率 98.4%"并存（WX-11 §3 图 016）——**这些数字不作为本卡任何结论的论据**。场景限于该团队的内部研发流转（标准需求、Bug Fix、平台自迭代、历史问题池），未涉及生产系统的运行操作；文章亦未说明任何 Agent 节点的权限范围与谁承担配置变更风险。Temporal 引入为"测试验证阶段"的规划陈述。第 4.5 节的失败诊断字段清单是"后续要继续增强"的待建项，不是已实现能力。

本卡把该文当作**一份按真实失败逐项补出来的缺陷清单**来用，而不是当作方案推荐：作者自己的截图里，平台自身的 P0 缺陷（返工时未取消下游活跃任务、返工无轮次上限、Agent 退出未提交结果）正是本卡采纳条目的失败依据。

## 缺口

04 §1–§5 全部是生产服务视角，§6 管的是 AI 运行的记录、可重复性、开销与归口判定，**没有一处回答"人不在场时，这条生产线可以自己推进到哪一步、在哪里必须停下"**。[01 §5.5](../01-项目管理标准.md#controlled-actions) 定义了受控动作与授权、执行点在被约束者之外，但它管的是"这个动作能不能执行"，不管"一段可以连续自动推进的工作，其准入条件、停止形态与恢复在场后的复核证据"；[03 §9.5](../03-Agent信息获取与上下文管理.md#delegation-recovery) 管委托的超时、隔离与重放副作用，作用域是一次委托内部，不管无人值守段落整体的准入与出口。

## 采纳

落点统一为新增 [04 §6.5 无人值守推进的准入、停止与复核](../04-可靠性安全与运行维护.md#unattended-operation)。

- **准入按能力次序**：某类工作能否无人值守推进，取决于它已具备可自动判定的完成条件、可自动执行的验证、失败可被发现的观测；三者缺一不得进入，先补齐再放开范围。**触发**：项目允许 Agent 在无人实时在场时继续推进工作项、修改仓库或调用外部系统。**责任**：运行负责人持准入与暂停决定。**失败依据**：该团队第 4.5 节自述外部 Agent 失败只给一个笼统的 `task failed`，无法区分能力、工具、权限、网络还是输入不完整，"最终还是会回到人凭经验猜"——观测未就位就放开自动推进，失败在事后不可归因。
- **无人值守动作范围只能是授权范围的子集**：受控动作、不可逆动作、超出预授权范围的动作一律停下等人，不因流程需要继续而自行放行；判定执行点按 [01 §5.5](../01-项目管理标准.md#controlled-actions) 设在被约束者之外。**失败依据**：该文四类场景含"配置变更"节点，但全文未说明任一 Agent 节点的权限范围，也未说明配置变更风险由谁承担（WX-11 §9 待核项）——这正是无人值守下最容易出现的授权真空。**复查条件**：范围扩大或新增可自动推进的工作类型时重判。
- **停止形态成表**（进程退出/超时/掉线导致步骤停留运行中、状态记录与实际执行不一致、返工重试循环无上限、定向返工时旧一轮下游动作仍在跑、执行者自述阻塞未落成状态）。**失败依据**：全部取自该团队自己暴露的缺陷与巡检场景——"Rework 时未取消下游 active task（P0）"、"max_rework_rounds 上限保护缺失（P0，13 天未解）"、"完善 Agent 退出时的 workflow submit 强制机制"、"活跃 Step 没有对应 Agent Task"、"Runtime 掉线／长时间 running／孤立任务"（正文 4.4 表 + WX-11 §3 图 013/017、§8 F1–F5）。**验收**：每类失败能构造一次并断言被检出。
- **巡检器自身要有超龄检测**。**失败依据**：该团队的每日"系统健康扫描"任务在看板上停留"进行中"5–6 天未更新，而 Sweeper 未把它们判为超时（WX-11 §3 图 017、§8 F10）——巡检器卡住时，"没有告警"与"一切正常"看起来完全一样。
- **执行完成不等于业务完成**：无人值守段落的出口是待复核而非已交付；复核项要能回答做了什么、依据哪些输入、验证跑了没有、剩余风险是什么，只给一句"已完成"的产出退回。原文的对应表述是 "Agent completed 不等于 business completed"（近原文，第 4.3 节）。**失败依据**：作者把这条列为第一阶段的两个关键判断之一，理由是"如果把 Agent 完成直接当业务完成，风险很大"。
- **待复核队列的积压量与停留时长本身要有人看**，长期堆积按 [01 §5.6](../01-项目管理标准.md#gates) 判闸门失效，不记通过。**失败依据**：该平台指标页显示"49 个项目等待审核、平均响应时间 0s、建议处理积压"，看板"审核中 19"（WX-11 §3 图 016/017、§8 F8）——把每条链路的终点都挂到人工验收上，验收会退化为积压，此时"通过率"统计的是没人看过的东西。
- **失败要能归类而不是只留一句失败**：无人值守失败的记录按 [§6.1](../04-可靠性安全与运行维护.md#agent-run-observability) 已有的三类归因处理，不另立字段表。原文 4.5 节的字段清单（失败发生在哪个 step、调用了哪个 Agent 或外部工具、失败类型、failure reason、stderr/stdout 摘要、是否重试、最终状态是 fail/blocked 还是等待人工）与 §6.1 已有的"执行结构／结果状态／副作用回执"重合，**不重复写**，只在 §6.5 引用。

## 不采纳

- 三根骨架、六类能力的具体对象模型（Workflow Template / Node / Edge / Step Instance / Issue / Agent Task / End Node / Acceptance）与事件名：绑定 Multica 二次开发的实现，不同底座对象不同；04 只要求"停止形态可被检出并有具名接收人"。
- 四种 Agent 路由策略（指定／上一步指定／能力匹配／兜底解析）、准出字段名、`prev.xxx` 与 `steps.step_n.<字段>` 引用语法、Issue 标题模板：载体绑定。且"兜底解析"的含义与权限边界文中未说明，谁能被兜底派到高风险节点是未决问题，不宜转成规则。
- Fan-out 并行与 AND 收敛、兄弟任务的 fail/blocked/rework 策略：属委托与并行纪律，[03 §9.4](../03-Agent信息获取与上下文管理.md#delegation) 已管写集重叠与汇合报告，不在 04 复写一套。
- 四层指标体系（Agent 层／工作流层／节点层／场景层）与具体指标名（成功率、blocked 率、一次通过率、返工率、人工介入率）：04 §1 已管 SLI/SLO 的定义责任与盲区标注，§6.1 已管运行记录；再列一套指标名会造成同一事实两处定义。且该文自己的指标页口径矛盾（同页两个首次通过率），不足以支持推荐具体指标组合。
- Multica、Temporal、Dynamic Config、KNot、CodeBuddy 作为选型或参考实现：具名产品，且 Temporal 仅在测试规划中。
- "只要一件事边界清楚、目标明确、结果可验收，就能进入这套机制"作为通用结论：四类场景均无样本数，同期截图显示平台自身缺陷频出，只适用于该团队当前阶段。
- "组织级 Loop Engineering"、Prompt / Personal Loop / Work Loop 三层分期：术语与路线命名，不是可检查的要求。
- "AI 原生工作流"的七步结构（目标理解 → 约束抽取 → 计划生成 → 工具执行 → 自动验证 → 风险判断 → 人类验收）：作者自认无数据支撑，属下一阶段设想。
- 平台"自我迭代"作为持续进化的证据：截图多为"[演示]"，且实施与端到端验证由同一 Agent 承担、人工验收积压，缺独立验证锚点（WX-11 §8 F11）。
- 全部截图数字（30+ Agent、523 已完成、98.4%、健康分 87、首次通过率 100%/50%、封面海报的运行中 28／一次通过率 72%／平均验收 2.1h）：无口径、无对照、含演示数据与 AI 生成装饰图，不进 04 正文，也不作为任何规则的论据。

## 跨方向建议（不由本方向修改）

- 给 01：§5.5 的受控动作清单按"动作类型"组织，缺一个"在无人在场的连续推进中，预授权范围如何声明与到期"的表达；本方向已在 04 §6.5 写"只能是 §5.5 授权范围的子集"，若 01 认为该声明应归 01，请收回。是否合并由主执行者裁决。
- 给 01：该文的"验收积压"（49 项待审核、平均响应 0s）是 §5.6 闸门失效的一个新形态——闸门配置正确、每次都执行，但接收方不处理。§5.6 目前有"误阻断"与"静默失效"两类失效，无"排队即通过"这一类。
- 给 03：§9.5 的超时与撤销面向一次委托；无人值守下的多步链路里"定向返工时旧一轮下游任务未撤销"是同一机制在链路级的表现，可考虑在 §9.4/§9.5 增一句作用域说明，避免读者以为撤销只需覆盖直接子执行者。
- 给 02：Agent 能力池"谁能做什么、现在能不能用、该派谁"本质是一份能力登记与路由约束，与契约登记表同类；是否在 02 立位由 02 方向判断，本方向不写。

## 验证办法

走查一次真实发生过的无人值守运行：① 它在哪一步该停而停了，动作是否全在预授权子集内；② 构造五类停止形态（执行者进程被杀、步骤超龄、状态与实际不一致、连续驳回超过轮次上限、执行者自述阻塞）各一次，断言都被检出并有具名接收人收到；③ 把巡检任务本身挂住，断言超龄被检出；④ 取一条待复核项，看它能否支撑"做了什么、依据什么、验证跑了没有、剩余风险"四问；⑤ 查待复核队列的积压量与最长停留时长有没有人看。任一做不到记缺口工作项，不以"平台已上线自愈能力"代替。
