## 原文结论与适用限制

作者的目标是"守住日常需求的质量下限、提高 token 效率"，做法是先由专业开发搭企业级底座，再让非开发角色借 AI 在底座上提需求、开发、验收。与 01 有关且不在已采纳范围内的：

- **两个独立执行点互为双保险**。数据库变更工具对高危关键字（DROP/DELETE/TRUNCATE）做硬拦截，作者写明这与数据库账号本身的权限"互为双保险"——同一约束在工具层和凭据层各实现一次，不视为重复。
- **变更级别不由执行者自评**。作者写进容器规则的铁律之一是：任何需求哪怕改一个文案都必须走"需求讨论 → 开发实现 → 确认提交"三阶段，每阶段之间需用户明确确认，**禁止 AI 自行判断"小改动可以跳过讨论"**。他给的场景前提是使用者为非专业开发。
- **发现与处置分离**。代码腐化处理拆成两个职责分离的技能：一个扫描问题并建 issue，另一个认领 issue 并修复，作者给的理由是"避免既当裁判又当运动员"。
- **人的反馈质量决定产出质量**。作者称"廉价习得感"是危险的：人不理解 AI 写出的代码就无法审查；他要求非开发同事学基本概念，使反馈能落到"这个逻辑应该放 service 层不是 controller"这种具体位置，而不是"感觉不对，你再看看"。
- 其余做法：monorepo 严格分层且调用方向只能向下；三层规则（仓库根规则文件、研发容器规则文件、工具账号侧的记忆系统）按场景加载、集中不重复；文件命名约定即工作流（`draft_` → `ready_` → `done/`）；封装 CLI 替代临时脚本并强制留痕；组件化配 Storybook 使审查可行；容器启动脚本每步独立、失败即停并列出缺失变量名、幂等可重跑；给非开发者一份"能力地图"列出系统已有的页面、Agent、定时任务与开放 API。
- 一个负结果值得记：作者试用了某上下文压缩工具，结论是压缩偶尔出 bug、部分策略导致语义混淆，收益不足以抵消多依赖一个不稳定组件，因此放弃。

**适用限制**：单团队自述，**无对照组、无消融、无前后周期对比**。全部数字均无测量条件：3 分钟环境就绪是自述耗时无样本数；70% 覆盖率是目标值非实测；"同一功能 token 消耗差 3～5 倍"只出现在图中、正文未提、无测量方法；提交分布截图只证明非开发者有提交，不证明分工均等。大量机制绑定其内部系统（研发容器、代码平台、配置中心、网关、内网 IDE 插件），不可移植。"正在引入 AI 审批 MR"是规划陈述，不是已发生的实践。

## 缺口、采纳与不采纳

01 §4.7 的季度减法列了四类删除信号，其中第二类是"同一约束在多处重复实现"，§3.7 也要求同一约束出现在两处以上按 N2 判缺陷、处置是合并。**按现有文字，工具侧拦截与凭据侧最小权限这样的两层防护会被判为重复实现并合并掉一层**，而这两层的失效是独立的——[M-10](M-10-守卫的执行点.md) 已经指出拦截层可能静默失效。标准需要区分"规则文本的重复"与"执行点的冗余"。这是本篇能补的第一处。第二处：01 §4.3 变更分级表的"谁可以放行"列里，轻量级写的是"执行者本人"；执行者是 agent 时，这一格等于自评自放，与 §4.4"生产者 ≠ 验证者是结构要求"矛盾。

**采纳**

- [01 §4.7](../01-项目管理标准.md#maintenance-budget)：季度减法的第二类删除信号补限定——同一**规则文本**在多处重复是缺陷，处置是合并；同一约束在**失效相互独立的执行点**上各实现一次（如工具侧拦截与凭据侧最小权限）不算重复，删任一层前须确认另一层单独成立（表格单元内改写，不新增行）。触发条件为季度减法命中该信号；责任角色为该约束的负责人；工件是减法记录里的执行点核对；失败处置是确认不了另一层单独成立即不删。风险依据与失效路径：拦截层可静默失效（M-10），此时凭据层是唯一剩余防线，按"重复实现"删掉它即失去全部防护。
- [01 §4.3](../01-项目管理标准.md#change-level)：变更级别由执行者提出、由能对该工件负责的人确认；**执行者为 agent 时不得自评为轻量并自行放行**。触发条件为每次定级；责任角色为该工件的负责人；工件是工作项或简记里的级别与确认人；失败处置是无确认人的轻量级定级不成立，按常规处理。风险依据与失效路径：轻量级的放行人是执行者本人，执行者为 agent 时该格等于自评自放，全部验证与证据要求被一次自评绕过。复查条件：该项目不再存在 agent 直接放行的路径时删除本句。

**不采纳**

- 三层规则（仓库根规则文件、研发容器规则文件、工具账号侧记忆系统）按场景加载、"规则集中、分场景加载、不重复"：其中"工具账号级配置与平台侧下发的规则不随仓库走，必须在仓库有权威位置"由 01 §3.2"仓库外的约束"（[M-06](M-06-团队级规范的权威与同步.md)）**已覆盖**，不重复采纳；分场景加载属 **03**，落点不在 01。
- "任何需求哪怕改一个文案都必须走三阶段"：分级依据是使用者身份而非变更风险，与 01 §1 G8"流程按风险增减"及 §4.3 的分级表**冲突**，不采纳。本篇只取其中"级别不由执行者自评"这一条可独立成立的判据。
- 扫描建 issue 与认领修复两个技能职责分离、"避免既当裁判又当运动员"：01 §4.4"生产者 ≠ 验证者是结构要求"与 §6.1"巡检与异常清单……曝光不等于处置；原因判定、资源调配与关闭须具名"**已覆盖**。
- "廉价习得感"与反馈质量：与 [M-11](M-11-脚手架的到期与保值.md) 本轮采纳的 §4.4 判断带宽条款同向——判不动的检查点只产生"已审过"的记录；本篇不重复采纳，也不新增对评审者知识水平的要求（无可检查判据）。
- 覆盖率 70% 作参考不阻断、AI 写的测试易只覆盖 happy path 或断言太弱：01 §5.2"覆盖率不作闸门（可被无断言刷满），只作提醒"与"测试改动是否有独立依据且未掩盖缺陷"**已覆盖**。
- 前端端到端与后端单元测试互补而非替代（端到端失败时无法定位在哪一层）：01 §5.2"端到端只覆盖关键路径"**已覆盖**其取舍。
- 数据库变更唯一入口、强制先写 changelog 再执行、按风险分级的操作表：01 §5.5 已把 schema 变更与"无精确 WHERE 或影响多行的批量写"列入受控动作并规定执行点在被约束者之外（[M-10](M-10-守卫的执行点.md)），§4.3 已按风险分级，**已覆盖**；具体关键字清单与工具形态是项目实现。
- 文件命名约定即工作流（`draft_` → `ready_` → `done/`）：01 §4.1 的状态机与轻量简记裁剪**已覆盖**状态承载的自由度；该做法无失败依据，只是一种载体选择，不写进标准。
- 环境初始化脚本每步独立、失败即停并列出缺失变量名、幂等可重跑：其实质"每个可能失败的环节有对应的失败状态与去向，不生成半残产物让后续报含糊的错"由 01 §5.8**已覆盖**。
- 能力地图（列出系统已有页面、Agent、定时任务、开放 API 供需求方查阅）：对象是系统能力清单，属 **02** 的模块清单与契约登记表的派生视图；01 §5.10 已规定派生视图须标明来源与对账边界，**落点不在 01**。
- monorepo 分层与调用方向只能向下、组件行数上限、组件配 Storybook：属 **02** 的依赖规则与模块边界，**落点不在 01**。
- 基础设施底座（日志、RBAC、审计、开放 API、MCP、定时任务、持久工作流）、Agent"代码即配置"、工具返回 markdown 而非原始 JSON：分别属采用项目自己的技术决策与 **03** 的上下文成本，**场景不适用**或落点不在 01。
- 上下文压缩工具的负结果：材料有价值，但对象是 token 与上下文，属 **03**。
- 全部效果与规模数字。

## 跨方向建议（不由本执行者落地）

- 给 **02**：① "能力地图"——按业务域罗列系统已有的页面、智能体、定时任务与开放 API，每项一句说明，供需求提出方判断"这是已有能力的微调还是真正的新功能"——是模块清单与契约登记表的一种面向需求方的派生视图，02 可考虑给出它与权威清单的对账关系；② monorepo 下"调用方向只能向下、禁止反向依赖或同层互调"是 02 依赖规则的一手实践表述。本卡不改 02。
- 给 **03**：① 三层规则按场景加载、"规则集中、分场景加载、不重复"与 03 的默认加载合同同构；② 工具返回值用格式化摘要而非原始结构化数据以降低消耗，与 03 的工具返回外部化相邻；③ 该团队试用上下文压缩工具后因"压缩偶尔出 bug、部分策略导致语义混淆"而放弃，是 03 压缩一节少见的负结果材料。本卡不改 03。
- 给 **04**：无建议。

## 验证办法

在采用项目取全部现行约束，逐条列出它的执行点，标注哪些约束有两个以上失效相互独立的执行点；再取近四个季度的减法记录，核对被以"重复实现"为由删除的条目里，有多少实际删的是一层独立执行点而非重复文本。§4.3 那条取近三个月判为轻量的变更，核对定级人与确认人是否为同一主体，以及其中由 agent 定级的比例与事后返工率。本仓库无约束执行点清单、无减法记录、无变更定级样本，上述验证**未定**（生成者与验证者同一）。
