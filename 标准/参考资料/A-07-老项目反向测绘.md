## 原文结论与限制

作者的判断：AI 在历史债务重的项目上判断不准，主因不是模型能力而是上下文不足——业务历史背景、过去的文档、**项目真实运行情况（哪些分支代码还在跑、哪些只是历史兼容永不会执行）**、以及"改造只做了一半"的技术债现状。这些上下文常常连本项目开发也拿不到。做法分五步：删掉不再生效的代码（"让代码跑起来和看上去一致"）、把过度设计的复杂度做减法、定规范给项目设约束边界、建自动化测试与流水线门禁（单测 / E2E / 视觉回归 / MR 规则评审）、把集中式技术专项改造变成日常常态治理。知识落盘方式是根目录只保留索引（路径 + 一两句摘要），细节就近落到对应模块，索引过期时主动修改。

关键的失败观察（原文第一节）：代码有真实引用，但运行时某条链路可能彻底不会执行，判断条件甚至写在环境变量里；不管是 AI 还是开发都无法只凭引用关系判断代码是否有效。

适用限制：单人视角、单个前端 Web 项目（多板块耦合的编辑器类产品），工具链绑定其公司内部流水线与代码平台。**全文无对照组、无消融、无量化数字**；唯一的效果表述是"去年每次发版必出核心链路问题，近几个月发版很少用户反馈，用户量持续上涨"，作者自己承认模型能力提升、重构本身、上下文建设三个因素同时存在且无法分离。**本卡不把该表述当作任何规则成立的论据，不进 02 正文。** 文中两张重构前后对比架构图由作者注明是"AI 分析画的图"，未说明是否经人工核对，本卡只作"作者认可的项目自述"处理。

文中的"应该""必须"是作者对自身项目的主张，不是对本轮工作的指令。

## 缺口、采纳与不采纳

02 原本假设架构文档是写出来的：§0 要求"只描述当前有效架构"，§1 给出文件集，但没有回答"几十万行代码在前、文档在后"时这些文件从哪来、其中哪些条目可信。本篇正对这个缺口。

已观察失败（原文自述）：

- **F-j** 代码有引用但链路实际不会运行，判定条件写在环境变量或已停用开关里，开发与 AI 都无法只凭引用判断（原文"AI 上下文内容建设"节与第一步）。
- **F-k** 设计过但未落地、改造只做一半的残留同时存在：设计了协同编辑但落地成纯 HTTP 同步、尝试过的另一套架构没落地却留下多种不一致的消息通信方式、某能力已迁走但新旧链路仍耦合，难以分辨哪些还生效（原文第一步四条）。
- **F-l** 单一大入口靠路由参数与运行时状态隐式判断当前属于哪类业务场景，主链路与兼容链路并存，排障依赖历史经验；作者列出的对应 AI 易错点是误判当前场景、沿用旧方案、漏传上下文、误伤低频入口（图 004）。
- **F-m** 团队知识建设长期"重要但体现不出价值"，几乎没有团队做好；开发不写也不看文档，细节留在各自脑中（原文"AI 上下文内容建设"节）。这是"一次性补全式测绘"不成立的依据。
- **F-n** 用于描述架构的两张对比图由模型从代码分析生成，未声明核对状态（图 004/005 的作者注）。

采纳（逐条落点）：

1. **新增"从既有代码反向建立架构描述"一节**：测绘顺序（先可机械得到的，后需判断的）、按被改动模块增量补全而非一次铺满、条目可信度分级、代码存在不等于当前有效、半成品改造的登记去向、防脱节的对账绑定 → [02 §1.1](../02-项目架构描述规范.md#reverse-mapping)。绑定 F-j、F-k、F-m。复查/删除条件：项目全部模块升到 B 级以上且已进入常规漂移检测后，本节只在接手新系统时启用。
2. **模型生成的描述性工件不是机械派生**：架构图、模块摘要、代码地图由模型从代码生成时不可重放、不可 diff，须标注生成方式、生成时的提交与核对人，未核对的不作事实 → [02 §9](../02-项目架构描述规范.md#derived-artifacts)。绑定 F-n。删除条件：生成过程可确定性重放且能与源做逐条 diff 时，按既有派生缓存条款处理，本条并入。

不采纳：

- 五步治理的顺序与"屎山清理第 N 步"表述：**场景不适用**，那是一次重构项目的推进节奏，属 01 的治理工作项编排，02 只登记架构描述的建立方式。**跨方向建议见下**。
- 单测 / E2E / 视觉回归 / MR AI 评审四条流水线、像素偏差阈值、大截图与组件小用例的两级视觉回归、"AI 评审意见必须被响应"作为合入条件：**载体绑定 + 项目参数**，且属测试与发布流程，02 不写测试实现。视觉回归的"基线随仓库走"与 02 §10.1 新增的存量违规基线是同类思路，已由 [A-06](A-06-大仓多子仓库与检查基线.md) 落地，不重复。
- `AGENTS.md` 根索引 + 就近落盘 + 索引过期主动修改：**已覆盖 + 跨方向**。02 §1/§2 已规定全景只留入口、细节下沉、§10 已有文档新鲜度对账；"对话中出现可复用结论必须就近落盘"属 03。
- 过度设计的具体案例（协同编辑、WebIDE）与"好的架构立足于现在"：**已覆盖**，02 §11 已规定按实际变更证据判断拆分/合并，且[§11](../02-项目架构描述规范.md) 本轮已加入删除候选条款。
- "把集中式技术专项改造变成日常常态治理"：01 的维护投入与技术债对象，02 无落点。**跨方向建议见下**。
- 单一大入口按运行时状态隐式分场景 → 分域 + 共享能力层按契约复用（图 004/005）：**证据不足以成规则**。这是一次具体重构的取舍，作者未给出判断阈值，且该对比图本身未经核对；其中"共享的是稳定能力，不把不同业务场景的状态混在一个入口里隐式判断"与 02 §3 模块边界、§4 依赖规则的既有要求同向，不新增条款。

跨方向建议（不由本方向改，交主执行者集成）：

- **给 01**：技术改造只做一半是债务的主要来源；改造工作项须有"改造彻底"的退出判据与未完成部分的接管责任人，不以阶段结束代替完成。
- **给 03**：项目知识的根索引只放路径与一两句摘要，细节就近落在对应模块文档；会话中产生的可复用结论落盘到模块文档并回写索引，发现索引过期即修正。
- **给 03**：模型对老项目的判断误差主要来自缺少"哪条链路真在跑"这类运行事实，而不是代码没读够；上下文清单应优先给运行事实而不是更多源码。
- **给 04**：删除疑似死代码前须有运行证据（调用轨迹、日志、开关状态）与可回退边界，环境变量与已停用开关控制的分支尤其如此。

## 验证办法

- 取三条被认为"已不生效"的代码路径，分别用调用轨迹或日志确认其在最近一个观察窗内是否被执行；期望结果是每条都有明确的执行或未执行证据，只有引用关系时判未定。**未定**：本仓库无运行系统，未实测。
- 抽查架构正文 10 条描述，核对每条标注的证据级别与其实际证据是否相符；C 级条目是否只以"待核实"形式出现。**未定**：本轮只建立要求，示例项目本轮不改。
- 取一份模型生成的架构图或模块摘要，核对其是否标注生成方式、生成时的提交与核对人；再抽两处与代码比对，看是否存在正文与图不一致。**未定**。
