# M-23 · 问题跟踪器作控制面与状态写入权：编排只读，状态由执行者在流程内写

- 原题：《An open-source spec for Codex orchestration: Symphony》（OpenAI Engineering），作者 Alex Kotliarskyi、Victor Zhu、Zach Brock。
- 类型：**两档分开记**。①博客正文：**V1 厂商一手**（一个团队讲自家内部工具的动机、做法与观察），转述层数 0。②文中全文嵌入的 `SPEC.md`（"Symphony Service Specification"，"Status: Draft v1 (language-agnostic)"）：该团队公开的**规范原文**，转述层数 0；形态接近 README 所说的"真0"，但它是**规范文本，不是该规范被执行的证据**，且作者明说不打算作为独立产品维护。两档不混用：正文里的效果与观察按 V1 记，SPEC 里的条款按"该团队写下的设计约束"记。
- URL：`https://openai.com/index/open-source-codex-orchestration-symphony`。发布日期：页面所示 April 27, 2026。访问日：2026-09-09（读本地落盘全文，抓取头行声明 DECLARED_LEN 与 CAPTURED_LEN 相等）。
- 实际阅读范围：博客正文全文；SPEC.md 全部 13 节（§1 问题陈述与边界、§2 目标与非目标、§3 系统概览、§4 域模型、§5 工作流文件、§6 配置、§7 编排状态机、§8 轮询与对账、§9 工作区与安全不变量、§10 agent 运行协议、§11 跟踪器集成、§12 提示构造、§13 日志与观测）。**未读**：仓库本身（参考实现、`WORKFLOW.md` 样例、后续提交）、前一篇"harness engineering"博客、agent 运行协议的文档；正文提到的截图与视频。原文去标签后 SPEC 的行号与正文黏连，本卡按语义切分。

## 原文结论与适用限制

正文的动机：交互式编码 agent 的瓶颈是人的注意力（作者称每人同时管三到五个会话即到上限）；于是把问题跟踪器变成控制面——"any open task should get picked up and completed by an agent"（中译：任何打开的任务都应被某个 agent 接起并做完），最终提炼为一句："For every open task, guarantee that an agent is running in its own workspace."（中译：对每个打开的任务，保证有一个 agent 在它自己的工作区里运行。）

SPEC 里与本标准有关的设计约束：

1. **编排器只读跟踪器，状态写入由执行者做。** §1"Important boundary"："Symphony is a scheduler/runner and tracker reader."（中译：Symphony 是调度器/运行器与跟踪器读者。）"Ticket writes (state transitions, comments, PR links) are typically performed by the coding agent using tools available in the workflow/runtime environment."（中译：工单写入——状态转换、评论、PR 关联——通常由编码 agent 用工作流/运行环境里的工具完成。）§2.2 把"怎么改工单、PR、评论的业务逻辑"列为非目标："That logic lives in the workflow prompt and agent tooling."§11.5 再述："The service remains a scheduler/runner and tracker reader."
2. **编排器的认领状态与跟踪器状态是两套。** §7.1："This is not the same as tracker states (`Todo`, `In Progress`, etc.). This is the service's internal claim state."（中译：这不同于跟踪器状态；这是服务内部的认领状态。）§2.1"Maintain a single authoritative orchestrator state for dispatch, retries, and reconciliation"；§7.4"Restart recovery is tracker-driven and filesystem-driven (no durable orchestrator DB required)."（中译：重启恢复由跟踪器与文件系统驱动，不需要持久的编排器数据库。）——编排器重启后从跟踪器重建，不靠自己的持久库。
3. **状态变化即停止运行；每个活跃项保证有执行者。** §2.1"Stop active runs when issue state changes make them ineligible."（中译：当工单状态变化使其不再合格时，停止活跃运行。）§8.5 对账每个 tick 做两件事——停滞检测（超过项目参数无事件即终止并重试）与跟踪器状态刷新（终结态→终止并清工作区；不活跃→终止不清；"If state refresh fails, keep workers running and try again on the next tick."——刷新失败不杀，下个 tick 再试）。
4. **出口是交接态不是 Done。** §1："A successful run may end at a workflow-defined handoff state (for example `Human Review`), not necessarily `Done`."（中译：一次成功的运行可以结束在工作流定义的交接态，如"人工评审"，不一定是"完成"。）§11.5"Workflow-specific success often means 'reached the next handoff state'"。
5. **审批与需人输入不得让运行无限挂起。** §10.5："Approval requests and user-input-required events must not leave a run stalled indefinitely."（中译：审批请求与需要用户输入的事件不得让运行无限期停滞。）要么满足、要么呈给操作员、要么自动解决、要么按文档化策略判失败；高信任示例是"Treat user-input-required turns as hard failure"。
6. **终结原因要可区分。** §7.2 列出 11 个阶段，含 Succeeded / Failed / TimedOut / Stalled / CanceledByReconciliation，"Distinct terminal reasons are important because retry logic and logs differ."（中译：区分终结原因很重要，因为重试逻辑与日志各不相同。）
7. **工作流策略随仓库版本化并热重载。** §1"It keeps the workflow policy in-repo (`WORKFLOW.md`) so teams version the agent prompt and runtime settings with their code."；§6.2 要求监视文件变化、不重启即重载，失效的重载不崩溃、保留最后一份有效配置并给操作员可见的错误；§5.5 工作流文件读取/解析错误阻断新派发、模板错误只失败该次尝试；§5.4 未知变量必须让渲染失败。正文："All of this is a process that humans followed, but it was never documented."（中译：这全是人以前在走的流程，只是从没被写下来。）
8. **Token 计数。** §13.5：优先用绝对累计值，"Ignore delta-style payloads such as `last_token_usage` for dashboard/API totals."；"For absolute totals, track deltas relative to last reported totals to avoid double-counting."（中译：对绝对累计值，按上次报告值取差再累加，避免重复计数。）
9. **阻塞规则与范围外发现。** §8.2 Todo 态下任一阻塞项非终结即不派发。正文：agent 在实施或评审中发现范围外的改进时"simply file a new issue"，由人评估排期。

正文的观察（不进正文）："We also learned that treating agents as rigid nodes in a state machine doesn't work well."（中译：我们还学到，把 agent 当作状态机里的刚性节点并不好用。）——改为给目标而不是给严格的状态转换；"we saw the number of landed PRs increase by 500% in the first three weeks"（按 01 §4.8 不登记为效果）；评审包附"a video walkthrough of the feature working inside the real product"。

适用限制：

- SPEC 是 Draft v1，作者明说"we don't plan to maintain Symphony as a standalone product"，是参考实现。
- 它管的是编排层，**不管执行者内部怎么做**：审批、沙箱、操作员确认姿态都是"implementation-defined"，规范只要求各实现"document its chosen ... posture"。所以它对 01 §5.5 的授权问题不提供任何判据。
- **`WORKFLOW.md` 的策略部分是提示词正文**：按 01 §5.6 的约束/提醒二分，写在里面的工单处理规则是提醒，不是约束；SPEC 里真正的执行点只有工作区不变量（§9.5）、hook 失败即中止（§9.4）、配置错误阻断派发（§5.5）。正文的"Symphony ensures agents follow it"是作者表述，按本标准只能记为"每次运行都被喂了同一份流程"。
- SPEC 没有失败重试的**次数上限**——§8.4 只限退避时长的上限，§7.1 的 `max_turns` 限的是一次 worker 内的轮数；按 [04 §6.5](../04-可靠性安全与运行维护.md#unattended-operation)"返工或重试成环，预设轮次上限"，这是该规范的一个缺口，本卡记录但不替它补。
- 500% 是"some teams"三周的自述，无对照、无口径；正文自己写"the perceived cost of each change drops"，量增的对象是投机性任务。

## 缺口

[01 §4.1](../01-项目管理标准.md#work-item-lifecycle) 已要求每次转换留一行并尽量取自可回读事件，§3.2 把工作项写入方定为"执行方写，负责人核"，§4.1 活性段说巡检"通知负责人核实"——都隐含了巡检不代写状态，但没有明说**自动编排层**能不能写工作项状态，也没有把编排层自己的调度记录与工作项状态分开。当项目引入自动派发/重试/对账的编排层时，它很容易顺手成为第二个写状态的主体：编排器把项标成 in_progress，执行者也标，重启后编排器的内存记录消失，两边对不上。§4.1 活性巡检对象列的是"超龄"，没有"活跃却无执行者"与"已终结而执行者仍在跑"这两个形态；04 §6.5 已有前者的停止处置，01 只缺巡检对象。

## 采纳（落 01）

- **状态的读写权分离**（[01 §4.1](../01-项目管理标准.md#work-item-lifecycle) 转换记录段后补一段）：活性巡检与自动编排只读工作项状态，只做调度、重试与对账；状态转换由执行者在流程内写并留那一行转换记录。编排层自己的认领、运行、重试记录是调度状态，不是工作项状态，两者不互相代写；编排层重启后以工作项状态重建调度状态，反向用调度状态改写工作项状态按 N2 判缺陷。**触发**：项目引入自动派发、重试或对账的编排层。**责任**：编排层的维护者保证它对工作项状态只读；工作项负责人核转换记录的执行者字段。**工件**：工作项的转换记录（执行者字段不得是编排器）；编排层的调度状态（内存或临时文件，可丢）。**验收/失败处置**：抽查转换记录，执行者为编排器的按 N2 记缺陷；重启编排层，看它能否只从工作项状态重建调度而不丢派发、不重复派发——重复派发或丢派发记失败。**失败依据**：SPEC §1/§2.2/§11.5 的边界声明与 §7.1/§7.4 的两套状态设计，加上 N2 的推导——两个写者对同一状态各写一份必然漂移；这是该团队写下的设计约束与本标准的推导，不是已观察事故，按 N3 记风险预防并写明待验证假设："编排层写状态会导致漂移"在本仓库未观察。**复查/删除条件**：项目无编排层时不适用；若跟踪器本身提供事务性的状态转换接口且编排层只是该接口的调用者（执行者字段仍指向真实执行者），本条视为满足。
- **活性巡检对象补两个形态**（§4.1 活性段句内补）：处于活跃状态却没有任何执行者在运行；工作项已终结或转为不活跃而执行者仍在运行。停止与重建按 [04 §6.5](../04-可靠性安全与运行维护.md#unattended-operation)，01 只定巡检对象。**触发**：活性巡检。**责任**：巡检的具名负责人。**工件**：巡检清单。**验收**：构造一个 in_progress 而无执行者的项、一个已 cancelled 而执行者仍在跑的项，巡检各报一次。**失败依据**：SPEC §2.1/§8.5 的对账规则与正文的一句话目标（每个活跃项保证有执行者、状态变化即停止运行）；同为该团队的设计约束，风险是孤儿运行（在已取消的项上继续写）与孤儿项（活跃却无人推进）。**复查条件**：随 04 §6.5。

## 不采纳

- 轮询周期、并发上限、退避公式、工作区路径、hook 名称、协议握手、查询语言细节、模板引擎语义：实现载体。
- "把 agent 当状态机的刚性节点不好用，改为给目标"：该团队的观察，属委托合同的粒度选择（[03 §9.2](../03-Agent信息获取与上下文管理.md#delegation)"目标与完成条件"），不进 01。
- "500% PR 增长"：按 01 §4.8 不设 PR 数一类的产出计数为效果；且无口径。
- 每个活跃项配一个隔离工作区、agent 只能在自己的工作区内运行（§9.5 三条不变量）：属 03 §9.3/§9.4 隔离与 [04 §4](../04-可靠性安全与运行维护.md#security-supply-chain) 执行隔离，01 不立位。
- 出口是 Human Review 而非 Done（§1/§11.5）：04 §6.5"执行完成不等于业务完成，出口是待复核"已覆盖；01 §4.1"done 不代表已合并、已部署、已发布"是同一分层。记佐证。
- 审批与需人输入不得无限挂起（§10.5）：04 §6.5"执行者自述阻塞…阻塞须落成状态"与 01 §4.1 blocked 态已覆盖；记佐证。
- 终结原因可区分（§7.2）：[01 §5.8](../01-项目管理标准.md#error-observability)"失败要可命名、可定位"已覆盖；记佐证。
- `WORKFLOW.md` 随仓库版本化（§1/§5.1/§6.2）：01 G1、§3.2"仓库外的约束"已覆盖，正文那句"从未被文档化的人工流程"是 G1 的一手佐证；热重载与最后一份有效配置是运行实现。
- 配置错误阻断派发、模板未知变量即失败（§5.4/§5.5）：与 01 §5.6"检查器自身故障判故障，暂停依赖其放行的动作"同向，记佐证。
- 范围外发现另开工单（正文）：01 §4.2"新发现但不属于本次目标的问题登记为新工作项"已覆盖；记 V1 佐证。
- 阻塞项非终结即不派发（§8.2）：01 §4.1 blocked 已覆盖。

## 跨方向建议（不由本方向修改）

- 给 **04 §6.3**：SPEC §13.5 的计数规则——绝对累计值与增量值不得混算，绝对值要对上次报告值取差再累加，否则重复计数——是 §6.3"口径"一条的一手佐证，可作为例子写进卡。
- 给 **04 §6.5**：① SPEC 的对账把"状态刷新失败"与"状态变为不活跃"分开处理（前者不杀执行者、下个 tick 再试），是"采集失败与无数据不得同一表示"（01 §5.8）在停止决策上的落点；② 该 SPEC 没有失败重试的次数上限，只限退避时长——可作 §6.5"重试成环须预设轮次上限"的一个反例：一份公开规范也会漏掉它。
- 给 **03 §9.2 / §9.4**：SPEC §10.5 把"需人输入"在高信任模式下直接判失败而不挂起，与委托合同"预算与停机"字段的收口方式一致；"编排者只在需要判断时加载"（03 §9.4）在 SPEC 里的对应是编排器根本不读产物，只读跟踪器状态。

## 验证办法

① 取采用项目的编排层（若有），列出它对工作项状态的写操作；非空即失败。② 重启编排层，比对重启前后的派发集合；丢派发或重复派发记失败。③ 构造"活跃无执行者"与"已终结仍在跑"各一例，看巡检是否报出。本仓库无编排层与自动巡检，三项均**不适用/未定**。
