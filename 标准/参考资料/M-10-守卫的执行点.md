## 原文结论与适用限制

作者把 prompt 管不住的三类问题——长文本偷懒、越权操作、上下文失忆——放到 Agent 框架的 Hook 切面上做确定性兜底。与 01 有关的：

- **越权那一类的处置**：发布、回刷、冻结/解冻、终止这类写生产或不可逆的动作，"prompt 是软约束，不是安全边界"；守卫挂在工具真正执行前的切面上（`beforeTool`），判断是不是危险动作、用户授权了没，没授权就阻断。作者的原话是：无论 Agent 是自作主张还是被诱导，只要没有人工确认这一步，那两个发布工具在框架层就物理走不通。
- **授权标记**：每个危险工具配一个授权标记（`requiredState` key）与确认对话框；用户在前端点选后由 REST 接口把选择写进会话状态，再发起一次续跑，这一轮守卫才放行。"确认动作只能由真实用户在前端触发。"
- **清单是配置不是代码**：危险工具清单写在配置文件里，工具本身无需改代码；作者给的理由是不同租户/环境的危险工具不同，不能写死在工具实现里。
- **静默失效的探测**：回写工具的下游实现对 `scriptFilePath` 留一条告警日志——按协议该字段在到达工具前已被框架剥离，"还在就是 Hook 失效信号"。这是在护栏本应生效之后的位置放一条断言。
- **失败语义按代价差异化**：读侧（把长文落盘换引用句柄）失败则降级透传、不阻断主流程；写侧（把全文加载回入参）失败则抛异常阻断工具调用。作者说明框架原生的 offload 失败统一降级，不会按操作类型做差异化。
- **该做没做的那一类**：模型追求以最少 token 完成任务，不会主动给自己加检查步骤（改完表不查下游影响、跑完脚本不报告产出物）；且存在信息不对称——工具返回里没提生成了什么文件，模型"根本不知道有东西该查"。确定性解法是框架在动作执行后强制采集、结果自动注入下一轮，不让模型决定要不要查。

**适用限制**：单个生产系统的实践自述，无对照。全部机制绑定其 Agent 框架的 Hook API 与沙箱、对象存储实现；文中的效果表述（输出 token 降约 90%、"view→重写"路径下自截断概率近 100%）是该团队在其条件下报告的观察，无公开口径，本卡不作为论据。框架横向对比表基于其调研时的版本，不作为这些产品当前能力的依据。

## 缺口、采纳与不采纳

01 §5.5 写了哪些动作需要核对授权、缺授权时怎么办，§5.7 写了危险动作清单与工具实现分离、模型在会话内不可修改，§6.1 写了授权标记只有人侧通道——**但没有一处说这套核对在哪里执行**。按现有文字，"执行前核对用户已有明确授权"可以被读成对执行者的一条要求，而执行者正是被约束的那一方。这是本篇能补的第一处。第二处是 §5.6 的闸门合同要求写"怎么发现静默失效"，却没给任何方法。

**采纳**

- [01 §5.5](../01-项目管理标准.md#controlled-actions)：核对的执行点在模型控制流之外——受控动作的判定与放行由动作执行前的拦截层或人侧通道完成，每次调用都过，不依赖执行者记得核对；写在提示词或流程说明里的同一句话只是提醒。没有这样的执行点时，该动作的受控状态记未定，不记为已受控。拦截层为每次放行与阻断留回执，与受控动作清单按 §7 对账。触发条件为每个受控动作；责任角色为拦截层维护者与授权人；工件是拦截层配置与回执；失败处置是缺执行点即记未定并补建。失败依据：原文案例二——Agent 在方案讨论阶段径直调发布工具把表结构推上生产。复查条件：该动作退役或不再可达时按 §4.7 删除。
- [01 §5.6](../01-项目管理标准.md#gates)：静默失效的探测方法——在护栏本应生效之后的位置放一条断言，它命中即说明护栏没执行。失败依据：原文的 `scriptFilePath` 防御性日志。

**不采纳**

- 读侧降级 / 写侧阻断的差异化失败语义：01 §5.6 现规定"适用却没配置或未执行的门记未定，不记通过""检查器故障时暂停依赖其放行的动作"，比差异化方案更严；引入"只读路径可降级"会削弱既有条款，**与既有规则冲突**。采用项目若需要该取舍，走 §8 的具名限时例外。
- 长文本读写两侧 offload、引用句柄、强制 `str_replace` 小步改、工具返回裁剪与 Rerank：对象是上下文与 token 管理，属 **03**，01 不写。
- Hook → state → Attachment 的注入闭环、风险分析与产出物自动呈现两个案例：同上，属 03；其中"不让模型决定要不要查，把检查绑到动作的执行点上"这一判据，已由本轮 §5.6 的约束力条款（[M-08](M-08-规则的增补与打薄信号.md)）覆盖，不重复写。
- 危险工具清单配置驱动、按租户/环境不同：01 §5.7"危险动作清单与工具实现分离、按环境配置、版本化慢变，模型在会话内不可修改"**已覆盖**。
- 授权标记由会话状态承载、用户前端点选后续跑：01 §5.5 与 §6.1"授权标记只有人侧通道，模型不能代写"**已覆盖**，具体承载形式属工具实现。
- "prompt 定意图，Skill 定规矩，框架 Hook 定边界"的三层分工：与 01 §7 的四级约束力同向，但原文未给可检查的分界；本轮 §5.6 已用"不满足时下一步是否真的无法进行"给出二分判据，再加一套并列分层会造成第二处权威，**已覆盖**。
- 全部效果数字。

## 验证办法

在采用项目取受控动作清单，逐条回答：它的核对发生在哪个执行点，该执行点是否在被约束的执行者之外，是否每次调用都过，是否留回执。再造一次"应被拦截"的调用，确认它被阻断且回执可回读——这构成 §7"应被拦截回归集"的一条。静默失效那条，检查每道护栏之后是否存在一条会在护栏失效时命中的断言。本仓库无拦截层与回执数据，上述验证**未定**（生成者与验证者同一）。
