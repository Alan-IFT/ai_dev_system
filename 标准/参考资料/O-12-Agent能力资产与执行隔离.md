## 原文结论与适用限制

作者的判断是：企业 Agent 从演示走向生产，分水岭不是模型而是运行时。要回答三个基础问题——一次任务可以访问什么、分散在各团队的业务经验如何进入 Agent、跨越几十上百步的工作状态保存在哪里。给出的架构是三件套：统一 harness 承载执行与安全（会话与 checkpoint、上下文管理、工具编排、权限与人工审批、skill 装载、文件与执行环境、trace）；skill 作为带 owner、版本、风险等级、依赖声明与评测集的可治理资产，用"预筛 + 模型精选 + 动态注册工具"两阶段路由；虚拟文件系统按生命周期分区保存证据、中间态、产物与 checkpoint，并用 manifest 记录产物来源与交付状态。

与本方向直接相关的三条：**有效能力 = 用户授权 ∩ Agent 配置 ∩ 所选 skill 策略 ∩ 会话/任务范围 ∩ 工具侧执行**——用户拥有的全部权限不应自动成为这次任务的全部权限；**prompt 不是安全边界**，四道门是工具可见性、参数策略、执行隔离、人工审批，会话范围在网关冻结、模型不可改；**沙箱保护的是宿主环境，不代表沙箱内的数据天然安全**，输入文件、网络、凭据、运行时长、CPU/内存、输出大小以及回传路径都必须单独约束。作者同时指出框架自带的声明式 filesystem permission 只约束内建文件工具，不自动覆盖自定义工具与 MCP。第 09 节列的五个坑中有一条是"只验证成功路径"：企业 Agent 的关键测试包括权限拒绝、工具超时、发布中断、沙箱资源耗尽、skill 冲突和证据过期。

适用限制：**这是一篇设计提案 + 案例转述，不是实践报告**。全文没有一个来自作者团队的实测数字，没有对照组、消融或 trace 样本；文中的 registry YAML、manifest.json、三类 TypedDict 与目录布局是作者的设计草案，文章未声称已上线。全部"案例"来自 Stripe Kai 与 Deep Agents 的公开材料，属二手转述，其中 Stripe 官方博客本卡与 WX-30 均未取到正文。文中三个数字（NoCode Agent Builder 的工作流 Agent 数量、约 150 个技能时选择质量下降、Kai 的构建周期）全部转述且省略测量条件，作者本人也把最后一个标为宣传数字——**本卡不把其中任何一个当作论据**。整套架构面向"知识工作者用 Agent 处理业务对象"的企业平台形态，与本标准面向的"大型软件项目长期维护"约束不同：它的多租户数据隔离、领域 skill 联邦治理、会话产物交付这些主线在本标准里没有对应对象。

## 缺口

04 §4 的组件登记只覆盖**部署制品 → 代码修订 → 构建运行 → 依赖版本与来源**这条链，登记对象是构建出来的软件。项目自己分发给 Agent 的可执行能力资产——内部技能/提示资产、内部工具与 MCP 服务、Agent 配置——同样决定"模型这次能碰什么"，却既不在锁文件里、也不在 SBOM 里，目前无处登记。04 §4 的环境权限边界写到"开发、构建、测试、发布与生产环境"，没有覆盖**模型生成代码的执行环境**这一类临时隔离环境的出口约束（网络、凭据、可回传路径）。[01 §5.5](../01-项目管理标准.md#controlled-actions) 已定"判定执行点在被约束者之外"，[03 §12](../03-Agent信息获取与上下文管理.md#capability-acceptance) 已定"权限与隔离"的能力验收，两者都不管这批资产作为供应链对象的登记与保护。

## 采纳

只采两条，落点均在 [04 §4 安全设计、开发环境与供应链](../04-可靠性安全与运行维护.md#security-supply-chain)。

- **内部能力资产纳入登记**：项目自己分发给 Agent 的技能与提示资产、内部工具与 MCP 服务、Agent 配置，按 §4 已有的组件登记同等对待，至少记提供方、版本、维护责任、可访问的数据范围与可执行的写动作。**触发**：新增或变更此类资产。**责任**：模块负责人登记，安全责任人核可写动作范围。**工件**：§4 的组件登记（不新建系统）。**验收/失败处置**：能从一次运行反查它当时装载了哪些资产的哪个版本；有写动作而无授权依据、或无维护责任人的资产不得发布。**失败依据**：该文所述的两种形态——同类能力被复制成多份后各自分叉出不同的重试、权限与输出约定，以及"具有写风险但没有审批策略"、"无 owner 的已发布 skill"这类结构性缺陷需要靠 CI 才能查出来；这批资产不进登记时，[§4](../04-可靠性安全与运行维护.md#security-supply-chain) 现有的"从部署制品追到依赖来源"这条链对它们完全不生效。**复查条件**：资产退役或长期无人维护时删除登记项，登记表本身按 §4 的复发/工具漏检行合并冗余。
- **模型生成代码的执行环境按出口约束**：隔离环境保护的是宿主，不等于其中的数据与凭据安全；输入、网络出口、凭据、运行时长、资源与可回传路径分别约束并各自留证。声明式的工具可见性配置只描述模型看得见什么，不构成授权——授权由工具服务端与目标系统按 [01 §5.5](../01-项目管理标准.md#controlled-actions) 的执行点校验。**触发**：项目允许 Agent 在隔离环境执行模型生成的代码。**责任**：安全责任人定边界，工具维护者实现并留回执。**验收**：构造一次越界（读范围外数据、访问范围外网络、回传范围外路径）并断言被拒。**失败依据**：该文对 Deep Agents 文档的转述——框架的声明式文件权限只约束内建文件工具，不自动覆盖自定义工具与 MCP；具备任意命令执行能力的沙箱需要独立策略。写在提示词里的范围限制对沙箱内脚本无效。
- **原始证据只读**（合并进上述第二条的同一句）：运行中取得、结论所依据的原始证据按只读保存，模型可读不可改。**失败依据**：该文 4.1 节的理由是避免模型"修正"原始证据；这与 [§2](../04-可靠性安全与运行维护.md#incident-response) 的"事故记录区分事实、假设与决定"是同一条原则在 AI 运行侧的表现。

## 不采纳

本篇大面积不采纳，属正常结论——它的主线（企业知识工作平台的运行时架构）与本标准的对象不同，且大部分内容已在 02/03 有主。

- 四层架构、harness 最小职责表、七参与者执行链、三类状态（SessionContext / AgentState / ArtifactState）：产品架构设计，属工具选型与实现，不是项目管理标准内容。
- 虚拟文件系统的目录布局（`/sessions/<id>/evidence|working|artifacts|checkpoints`、`/skills/`、`/memories/`、`/shared/`）与 manifest.json 字段：具体载体。产物的来源、验证状态与交付状态在 [04 §8](../04-可靠性安全与运行维护.md#operational-acceptance) 的验收记录里已有 `baseline`/`result`/`evidence`/`limitation`，再写一份 manifest 会造成同一事实两处定义。
- Progressive disclosure 三层加载、两阶段 skill 路由（预筛 + 模型精选）、目录规模导致的选择质量下降：属 [03](../03-Agent信息获取与上下文管理.md) 的按需加载与工具清单治理，03 §13 已有"工具与技能清单只增不减"的反模式条目。**跨方向建议见下**，本方向不写。
- Skill 联邦所有权与 base → team → project → user 覆盖优先级：属 [01](../01-项目管理标准.md) 的文档责任与权威位置、[03](../03-Agent信息获取与上下文管理.md) 的唯一合同，不在 04 立位。
- Skill 路由评测（top-1/top-k、误触发率、漏触发率、近邻负例、混淆对）：属 [03 §11.1](../03-Agent信息获取与上下文管理.md#context-evals) 的离线评估记录字段范畴，且该文未给出任何实测。
- 四组指标（任务结果／路由质量／运行质量／风险治理）与具体指标名：04 §1 管 SLI/SLO 的定义责任，§6.1 管运行记录；再列一套指标名会与两处冲突。其中"无来源产物比例""恢复成功率"是有价值的候选指标，但该文无实测支撑，不进正文。
- summarization / 文件 / checkpoint 三者不可互相替代：正确，但 [03 §8](../03-Agent信息获取与上下文管理.md#externalization) 与 [04 §6.1](../04-可靠性安全与运行维护.md#agent-run-observability) 的会话事件行已分别覆盖压缩有损与检查点，不重复。
- VFS 无 TTL 会变成数据沼泽、会话私有到组织共享要有显式发布点：前半句已由 [04 §3](../04-可靠性安全与运行维护.md#recovery-data) 的数据目录 + [§6.1](../04-可靠性安全与运行维护.md#agent-run-observability) 的留存登记覆盖；后半句属 [03 §10](../03-Agent信息获取与上下文管理.md#memory-governance) 的"人批准晋升"。
- "过早引入多 Agent"：与 [03 §9.1](../03-Agent信息获取与上下文管理.md#delegation) 的委托举证条件重合，不采纳为 04 条目。
- 五个坑中的"只验证成功路径"作为新增条目：04 §8 的走查清单与 §6.5 的停止形态已承担这一职责；其列举的失败项（权限拒绝、工具超时、发布中断、沙箱资源耗尽、技能冲突、证据过期）中，与本方向相关的"权限拒绝"与"隔离环境资源耗尽"已被本卡采纳的第二条验收覆盖，不再单列。
- Stripe Kai、Deep Agents、LangGraph、S3、MCP 作为选型或参考实现：具名产品；且 Stripe 一手材料本轮未取到。
- 全部转述数字（工作流 Agent 数量、约 150 个技能的拐点、构建周期）：无测量条件、无对照，作者本人亦标注其中之一为宣传数字，不作为任何规则的论据。

## 跨方向建议（不由本方向修改）

- 给 03：§13 已有"工具与技能清单只增不减"的反模式，但没有"目录规模到一定量后，模型的选择质量本身会下降"这条**规模阈值**的表达，也没有"工具集应是技能选择的输出而不是常驻全集"（WX-30 §3 图 006）这条装配顺序。该文给的具体拐点数字不可用（转述且省略测量条件），但"按项目自己的目录规模实测选择质量、超过实测拐点即加预筛"是可检查的写法。是否采纳由 03 方向判断。
- 给 03：§12 的"权限与隔离"验收行可考虑增一句——**框架声明式权限的覆盖面必须实测**，自定义工具与 MCP 通常不在其内；本方向已在 04 §4 写了"声明式可见性不构成授权"，若 03 认为覆盖面实测归 03，请收回，避免两处各写一半。
- 给 01：§5.5 目前把"受控动作"按动作类型列举；该文的"有效能力 = 用户授权 ∩ Agent 配置 ∩ 技能策略 ∩ 会话范围 ∩ 工具侧执行"是同一件事的交集式表达，其中"会话/任务范围"这一维在 01 尚无对应词。是否引入由 01 方向判断。
- 给 02：能力资产（技能、内部工具、MCP 服务）的依赖声明与作用范围本质是一种契约；02 的契约登记表是否收编这一类，由 02 方向判断，本方向只在 04 §4 做供应链登记，不定义其契约形态。

## 验证办法

① 取一次真实运行，反查它当时装载了哪些内部能力资产、各自什么版本、由谁维护、能访问什么数据、能执行什么写动作；查不全即记缺口。② 在登记表里找一条有写动作的资产，确认它有授权依据与具名维护责任人；两者缺一即判不得发布。③ 在隔离执行环境里构造三次越界——读范围外数据、访问范围外网络、把文件回传到范围外路径——断言均被拒且各留回执；只在提示词里写"不要访问其他范围"不算。④ 尝试让模型改写一份它自己结论所依据的原始证据文件，断言被拒。
