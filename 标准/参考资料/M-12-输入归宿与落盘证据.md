## 原文结论与适用限制

作者把"AI 会写代码但不会按工程规范开发需求"归到流程与工件缺失上，做法是把需求开发拆成八个固定顺序的阶段，每阶段的输入、产出与退出标准可机器校验。与 01 有关且带具体失败记录的几条：

- **输入必须有归宿**。候选设计稿清单里每一张都必须归到某个需求点或被显式排除，不允许用"参考图"当万能类别。作者给的失败：9 张移动端候选稿里 AI 只挑 2 张做需求点，其余笼统当参考图，漏掉 7 个独立页面。他的处置是双向的——归不上的图，要么是收料时误纳（从清单去掉），要么是需求点遗漏（新增一项）。
- **实施项必须有出处**。"点击 X 触发 Y"这类交互条目的 X 必须有具体引用依据，只接受三种：设计稿上的标注（带 nodeId）、文档原句的直接引用、用户原话；以"看起来也属于这类功能""为了一致性也应该拦一下"为由的条目直接删除不实施。作者给的失败：用户说"点 A 拦截"，AI 联想"按一致性 B 也该拦"，改了不该改的逻辑。
- **联想用于搜索，引用用于决策**。作者明确区分两件事：在"找代码该改哪里"上必须用领域知识扩展候选搜索词（只缩小搜索范围，不进交付物）；在"这条交互要不要实现"上必须有具体引用（直接决定交付物）。
- **落盘判定成功**。长跑命令的成功证据不取自 stdout——它会被终端截断、被当作后台任务、被管道异步化；成功判据改为落盘的 sentinel 文件，或可重读的状态变化（`git log -1` 的 hash 是否更新）。作者给的失败：长 commit 消息被终端置后台，执行者据 stdout 判定失败并重复提交。
- **判断交给模型，精确数值与幂等执行下沉脚本**。设计稿分桶必须先跑脚本出直方图，模型只能在已分桶基础上补判标为 UNCERTAIN 的项，不能凭印象决定。
- 其余：三级知识库（总览 / 模块文件登记表 / 设计 Token→代码 API 映射）配 SHA 基线漂移检测与 pre-commit 阻断；编译退出码 0 是唯一判据、自修复硬上限 3 轮、错误分"可自修复"与"需人介入"两类；运行时验证从改动集反推验证路径并逐步留截图与日志；跨会话用永久规格文档 + 子任务台账 + 会话内时间线三件套接力；四个人机硬关卡守不可逆动作。

**适用限制**：单团队自述，无原始数据、无对照组、无消融。§11 的效果表作者自己标注为"体感（非严格 benchmark）"。**标题的 94% 在全文中没有任何定义**——正文只出现两次，唯一线索是提交阶段由脚本写进 commit message 的一个自报比例，分母、时间窗、是否含人工修正后的行均未说明，本卡只记作"该团队在 commit 元数据里自报的一个比例"，不作为任何论据。"300× 压缩比""命中率 > 80%""半年没有出现地图脱节""范围错判压成 0"同为自述或修辞。大量机制绑定其技术栈（Objective-C/C++、bazel、Figma、iOS 模拟器、facebook/idb）与内部平台，不可移植。

## 缺口、采纳与不采纳

01 §3.4 的"绑定"关系与 §4.4 的"验收映射是否完整"只做了**单向**核对——工作项引用的验收 ID 存在即算通过；**反向没有约束**：本次收到的输入物料是否每一份都归到了某个范围内条目或被显式排除，标准里没有一处要求。这是本篇能补的第一处。第二处：§4.2 的执行中规则有"新发现但不属于本次目标的问题登记为新工作项，不就地扩大范围"，管住了"发现新问题"，但没管住"由一致性推断出一条需求并直接实施"——后者不表现为新问题，表现为范围内多出一条没有出处的条目。第三处：§4.2 证据六字段的②要求"命令 + 完整输出"，没有说这个输出的**载体**可能本身就不可靠。

**采纳**

- [01 §4.1](../01-项目管理标准.md#work-item-lifecycle)：`planned` 的必需工件补"本次输入清单"，每项归到范围内条目或显式记为范围外。触发条件为工作项进入 `planned`；责任角色为该工作项的执行方，负责人核；工件是输入清单；失败处置是归不上的输入按两种可能处理——收料误纳则从清单去掉，条目遗漏则新增，不允许留"参考"类未归项。失败依据：原文 9 张候选稿只归 2 张、漏 7 个页面。复查条件：该项目的输入来源单一且不再出现漏项时可并入范围描述。
- [01 §4.2](../01-项目管理标准.md#session-protocol)：执行中补一条——范围内每条实施项须能指到具体出处（文档原句、图上标注、用户原话之一）；以"一致性""同类功能应该也……"推出的条目不实施，登记为待确认。失败依据：原文因语义联想扩大拦截范围、改了不该改的逻辑。同时写明分界：用领域知识扩展搜索候选不受此限，它只缩小查找范围，不进交付物。
- [01 §4.2](../01-项目管理标准.md#session-protocol)：证据六字段②补"原始证据取自落盘工件或可重读的状态变化；可能被截断、置后台或异步化的输出通道不单独作为成功或失败判据"。失败依据：原文长 commit 消息被置后台、据 stdout 误判失败并重复提交。这与 §2 N1"空输出需结合命令约定、退出码和执行回执判断"是同一判据的上游——N1 说的是空输出怎么判，本条说的是证据该从哪里取。

**不采纳**

- 固定顺序的阶段流水线、"后一阶段输入 = 前一阶段产出"、跳阶段是越界主因：01 §4.1 的状态机与"每个状态写清进入依据与必需工件——工件缺失即不得进入"**已覆盖**同一约束的通用形态；八阶段的具体切分绑定其需求类型，**场景不适用**。
- 编译退出码 0 唯一判据、自修复硬上限 3 轮、错误分可自修复与需人介入两类：01 §4.2 停机条件（同一故障连续两次修复无效且无新证据、重试前必须改变一个输入变量、连续三次工具调用失败）与 §4.1 的 `blocked`/`in_validation` 去向**已覆盖**；轮次的具体数值是项目参数，不写进标准。
- 从改动集反推验证路径、按改动类型给可观察终点（UI 改动看截图、数据改动看页面加日志、纯逻辑改动看日志断言）：01 §4.1 `in_validation` 的"验证计划（从改动集派生的可观察终点）"**已覆盖**；再写一遍按 §3.7 属同义条款，处置是合并不是新增。
- "全部由文件证明，不靠 AI 自报"：01 §1 G4、§4.2 证据六字段、§5.2"执行事实由被验对象之外的采集给出，不采信执行者的自述"（[M-07](M-07-人退到判据上.md)）**已覆盖**。
- 知识库三级金字塔、总览控制在 5KB 以内、模块级文件登记表：01 §3.3 的三层结构与阅读路径、§3.7 的篇幅预算**已覆盖**；具体层级与体积是项目参数。
- SHA 基线缓存 + 三色分诊 + pre-commit 阻断的漂移检测：01 §3.5 的 `source_rev`、§7"文档过期"行的 `check_docs_fresh` **已覆盖**；SHA 缓存是实现细节。
- 红线 YAML 单一真源、分 Critical/Standard 两级、启动即加载与按阶段加载、触发即停并按模板汇报：分层加载属 **03**，**落点不在 01**；"触发即停并报告已知事实、未知与下一步"由 01 §4.2 停机条件**已覆盖**；两级分级与 01 §5.6 现行的约束/提醒二分判据并列会造成第二处权威（[M-10](M-10-守卫的执行点.md) 已指出）。
- 不可逆动作前的人机硬关卡：01 §5.5 **已覆盖**。
- "判断交给模型、精确数值与幂等执行下沉脚本""模型只能补判脚本标为 UNCERTAIN 的项"：前半属 **03** 的工具与执行分工；后半的实质——机械可判定的部分不交给解释——由 01 §5.6"判据是确定事实才做硬拦截"（[M-07](M-07-人退到判据上.md)）**已覆盖**。
- 五步定位法、5 维搜索矩阵、硬关键词表、Figma Token→代码 API 的语义桥、模拟器死角清单：全部绑定其技术栈与物料形态，**场景不适用**；语义桥与术语表的关系属 02 与 03。
- 把代码生成率写进 commit message：01 §4.8"不设个人代码量/PR 数/部署次数排名"与该做法方向相反，**与既有规则冲突**，不采纳。
- 全部效果与规模数字，包括标题的 94%（无定义）。

## 跨方向建议（不由本执行者落地）

- 给 **03**：① 三级知识库 + "前两步只读地图、第三步才脚本检索、第四步才读源码"的漏斗，是 03 分层加载与按需展开的一手实践材料；② 红线按阶段分层加载、元数据常驻正文命中才读，与 03 的默认加载合同同构；③ "长跑命令的成功证据不取自 stdout"对 03 的工具返回外部化与回执回读有直接含义——回执通道本身要选可重读的；④ 跨会话三件套（永久规格 / 子任务台账 / 会话内时间线）按时间尺度分工，可与 03 的交接与记忆分层对照。本卡不改 03。

## 验证办法

在采用项目取近三个月的工作项，逐个核对是否存在输入清单，统计其中"归不上任何条目"的输入数量及其处置（去掉还是新增条目）；再抽查范围内条目，看有多少能指到具体出处，有多少只写了"按一致性"或"同类功能"。证据那条：取一批完成声明，核对其原始证据的载体是落盘工件、可重读状态，还是一次性输出流；对后者造一次输出被截断的情形，确认现有流程判未定而非失败或通过。本仓库无工作项运行数据与完成声明样本，上述验证**未定**（生成者与验证者同一）。
