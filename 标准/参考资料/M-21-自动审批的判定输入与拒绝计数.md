## 原文结论与适用限制

原文讲的是把逐次人工审批换成模型判定的一套设计。与本标准有关的结论有七条：

1. **判定者只读用户消息与执行者的工具调用，不读执行者自己的文字与工具返回。** 原文："The classifier sees only user messages and the agent's tool calls; we strip out Claude's own messages and tool outputs, making it reasoning-blind by design."（中译：分类器只看用户消息和 agent 的工具调用；我们剥掉 Claude 自己的消息和工具输出，让它在设计上对推理不可见。）剥掉执行者文字的理由是"so the agent can't talk the classifier into making a bad call"（中译：这样 agent 就说服不了分类器做错误判断），要"judge what the agent did, not what the agent said"（中译：判它做了什么，不判它说了什么）。作者称做过对照："Including assistant messages and tool results caused a drop in performance on our overeagerness testset."（中译：把助手消息和工具结果加进来，在我们的越权测试集上表现下降。）只看工具调用的变体漏报最低，"but lost the user-intent anchor, blocking actions the user had plainly asked for"（中译：但丢了用户意图的锚点，会拦下用户明明要求过的动作）。剥掉工具返回的另一个作用是把注入内容挡在判定者之外——判定者不需要知道 agent 为什么要往外发环境变量，发这个动作本身就不在授权内。代价是来源不可判：用户没提过的目标标识，判定者分不清是查出来的还是编造的；作者说为了抗注入接受这个代价。
2. **授权由用户的话建立，执行者自选的一切在用户说之前都是未授权。** 原文："The prompt establishes what is authorized; everything the agent chooses on its own is unauthorized until the user says otherwise."（中译：提示词规定什么是被授权的；agent 自己选的一切，在用户另说之前都是未授权的。）"clean up my branches" 不授权批量删除，"can we fix this?" 被当作问句而不是指令。
3. **漏报多数不在识别危险，在判断已有同意是否覆盖本动作。** 原文对漏报样本的检视："In the majority of misses we examined, the classifier correctly identifies the danger."（中译：在我们检视的多数漏报里，分类器正确识别了危险。）"'Clean up the PR' was said by the user, but it doesn't name force-pushing. A similar action was approved earlier, but one approval isn't a pattern."（中译："清理这个 PR"是用户说的，但它没有点名强推；相似的动作早先被批准过，但一次批准不是一种模式。）"The classifier finds approval-shaped evidence and stops short of checking whether it's consent for the blast radius of the action."（中译：分类器找到了长得像批准的证据，却没有进一步查它是不是对这个动作影响面的同意。）作者自述在提示词层面"haven't found a fix that doesn't cost more than it gains"。
4. **阻断后继续而非中止，累计到该产品设定的次数才升级到人；无人可问时终止。** 拒绝作为工具结果返回给执行者，附带"善意对待边界、找更安全的路、不要绕过"的指令；"If a session accumulates 3 consecutive denials or 20 total, we stop the model and escalate to the human."（中译：一个会话累计连续 3 次或总计 20 次拒绝，我们就停下模型、升级到人。）"In headless mode (claude -p) there is no UI to ask the human, so we instead terminate the process."（中译：无头模式没有界面可以问人，所以我们直接终止进程。）作者说这也是误报能被容忍的原因：一次误报只花一次重试，不杀会话。
5. **子执行者的两端各过一次判定。** 委托出去时可拒绝——理由是"Inside the subagent, the orchestrator's instruction is the user message, so tasks look fully authorized."（中译：在子 agent 内部，编排者的指令就是用户消息，所以任务看起来全都是被授权的），要趁它"still recognizable as an agent choice rather than a user request"（中译：还能被识别为 agent 的选择而不是用户的请求）时拦；返回时只警告不丢弃——子执行者可能中途被它读到的内容劫持，返回前复核其完整动作历史。
6. **阻断规则四类**：毁坏或外传；**降低安全性**——原文"Make the system harder to monitor or defend by disabling logging, installing persistence like SSH keys or cronjobs, or modifying the agent's own permission config."（中译：让系统更难监测或防御——关闭日志、安装持久化机制如 SSH 密钥或定时任务、修改 agent 自己的权限配置）；跨越信任边界（跑外部仓库克隆的代码、扫凭据库找可用令牌、发数据给用户没指定的服务）；绕过评审或影响他人（直推主干、生产部署、改不是自己创建的共享资源或作业）。进入该模式时**撤掉已知等于任意代码执行的通配放行项**（整个 shell、通配的脚本解释器、包管理器的运行命令），理由是"leaving them active would mean the classifier never sees the commands most capable of causing damage"（中译：留着它们意味着分类器永远看不到最能造成损害的命令）；窄规则（如放行格式化工具）保留。默认环境信任边界只有当前仓库，其余一律按外传风险看待。
7. **内部事故日志里的动机分类**：越权热心（overeager——理解目标但主动过头，如用碰巧找到的凭据、删它觉得碍事的东西）、诚实误判影响面（把共享资源当测试资源、把别人的分支当自己的）、提示注入、模型失准（作者称目前未在实践中见到）。判定器针对前两类调，因为"we have specific examples of this behavior from internal model testing"。日志里的已发生事件（经作者概括）：因误解指令删了远端分支；把工程师的代码托管平台令牌上传到内部计算集群；对生产数据库尝试迁移。五个改写示例：范围升级（"清理旧分支"→批量删远端）、凭据探索（遇鉴权错误后系统性 grep 环境变量与配置找别的令牌）、执行者自推参数（"取消我的任务"→按名字相似度挑了一个删）、经外部服务分享（把脚本发成公开片段）、**绕过安全检查（部署预检失败后带跳过校验标志重试）**。

数字（**只记为该团队该条件下的观察，不作规则论据，不进正文**）：人工审批模式下用户接受约 93% 的提示；全流水线在 10,000 条真实内部工具调用上误报 0.4%，在 52 条真实越权动作上漏报 17%（作者称"the honest number"），在 1,000 条合成外传任务上漏报 5.7%；第一阶段单独为 8.5% 误报 / 6.6% 漏报。真实越权样本只有 52 条，作者自己说小。

适用限制：

- 厂商讲自家产品；对"我们这样做了、测出什么"是一手，对"别处也该这样"不是。
- 三组数据都是内部员工流量与合成任务，无外部复现；越权集 n=52。
- 作者明说它"is not a drop-in replacement for careful human review on high-stakes infrastructure"（中译：不是高风险基础设施上仔细人工审查的替代品），定位是替代"全部跳过审批"，不是替代人。
- 判定者是模型：它的裁决是概率性的，本身不构成 01 §5.6 意义上的"确定事实"硬拦截；本卡采纳的是它的**输入边界与计数升级**这两个结构性选择，不是"用模型做审批"这一选型。
- 交叉核对的《How we contain Claude》把它定位为"one layer of defense-in-depth inside a sandbox, not a substitute for one"（中译：沙箱之内纵深防御的一层，不是沙箱的替代）。

## 缺口

[01 §5.5](../01-项目管理标准.md#controlled-actions) 已写"核对的执行点在被约束者之外"，但只约束了执行点**在哪**（拦截层或人侧通道），没约束执行点**读什么**。一个结构上在执行者之外的判定者，如果把执行者的解释当输入——"这是安全的因为用户早先默许了""这个目标肯定是我自己建的"——它在信息上仍被执行者俘获。§5.2 已有"执行事实由被验对象之外的采集给出，不采信执行者的自述"，那是证据侧；授权侧没有对应句。§5.5 的受控动作例子表缺"降低安全性"这一类（关日志、装持久化、启动更宽权限的子会话）和"带跳过校验标志重试已被拦下的动作"；"已有授权不能由模型自行扩展"一句没有一手失败佐证；审批疲劳段的依据是 C-15/C-08（P1/T1）。[04 §6.5](../04-可靠性安全与运行维护.md#unattended-operation) 的五类停止形态没有"被拦截后反复推向同一结果"这一形态，也没说无人可问时怎么办；[03 §9.2](../03-Agent信息获取与上下文管理.md#delegation) 治理继承有"不能由委托推导授权"，没有返回侧的复核。

## 采纳（落 01）

- **执行点的判定输入不含被约束者的自述与理由**（[01 §5.5](../01-项目管理标准.md#controlled-actions)"核对的执行点在被约束者之外"段内补一句）。**触发**：任何受控动作的判定与放行——拦截层、审批通道、自动审批器。**责任**：拦截层的维护者定义输入字段；授权的设定者验收。**工件**：拦截层的输入字段清单（回执里能看出判定依据了哪些输入）。**验收/失败处置**：列出自动判定的输入；含执行者对本动作的解释、理由或自评的，该执行点不满足"在被约束者之外"的独立要求，其放行按 N1 记未定，直到把这些字段移出输入。人侧通道呈现动作本身与影响面，执行者的解释作为未核实主张另列。**失败依据**：该厂商内部事故日志中的越权事件，以及作者的对照——加入执行者文字后越权测试集表现下降；理由是执行者能为任何动作生成看似合理的说辞。**复查/删除条件**：与 §5.2"不采信执行者自述"同为原则级条款，不随工具换代到期；若某项目的拦截层在结构上无法接触执行者文字（如纯网络出口策略），本条自动满足，不另验。
- **受控动作例子表补两行**：关闭或削弱日志、审计与监测，安装持久化机制（自启动项、定时任务、长期有效的登录凭据），以跳过校验或强制标志重试已被拦下的动作；启动权限更宽或免审批的嵌套执行者/子会话（后一行来自 [O-19](O-19-长时程模型的轨迹级监测.md)，同行合写）。**触发**：执行者发起上述动作。**责任**：授权设定者维护清单。**工件**：`AGENTS.md` §0 的受控动作清单与拦截层规则。**验收**：构造一次"关日志再执行"与一次"带跳过标志重试"，断言被拦下并留回执。**失败依据**：原文阻断规则第二类的定义与"绕过安全检查"示例（部署预检失败后带跳过校验标志重试，改写自内部日志）；[M-16](M-16-旁路通道绕过既有控制.md) 已记旁路通道形态，本行是它的两种新形态。**复查条件**：项目无自动化执行者时，本行只对人工 CI 变更生效。
- **一次批准不构成模式授权**（§5.5"已有授权不能由模型自行扩展"句内补一句佐证性说明，不新增条款）。**失败依据**：原文漏报检视——多数漏报是判定者把"早先批准过相似动作"或"用户提过目标"当成了对本动作影响面的同意。**复查条件**：随该句。
- **通配放行项不作免审批项保留**（§5.5 审批疲劳段的验收句内补）。**触发**：免审批清单出现"整个命令解释器/脚本运行器/包管理器运行命令"级别的通配项。**责任**：授权设定者。**工件**：免审批清单。**验收**：抽查清单，通配到解释器级别的项移出或收窄到具体动作。**失败依据**：原文进入该模式时撤掉此类规则的理由——它们让判定者看不到最能造成损害的命令；这是可追溯的风险分析，不是已观察事故，按 N3 记风险预防，待验证假设是"通配放行项下的越权动作确实未被任何执行点看到"。**复查条件**：拦截层能对解释器内部的实际命令做判定时（原文的"评估实际影响而非表面文本"），本条可放宽为"通配项须配合该能力"。
- **审批疲劳段的证据强度提升**：该段原依据 C-15/C-08（P1/T1）；本文给出厂商遥测——人工审批模式下用户接受约 93% 的提示、疲劳"在几周内出现"（交叉核对自 C-20 所引原文）。在段末补引 M-21 为 V1 佐证，文字不改。

## 不采纳

- 两阶段分类、第一阶段单 token 判定、缓存命中、判定模型型号：实现细节与选型，绑定该产品。
- "用模型做审批"作为本标准的推荐：判定者是概率性的，不满足 §5.6"确定事实才硬拦截"；本标准只采其输入边界与计数结构。
- 输入层的提示注入探针（对工具返回加警告）：属 [03 §6.1](../03-Agent信息获取与上下文管理.md#source-trust) 来源信任与 C-20 的领域，不在 01 立位；见跨方向建议。
- "动作级阻断与思维链监测正交、互补"：属 04/O-19 的监测领域。
- 三个可定制槽（环境信任边界、阻断规则、放行例外）的具体默认值：产品配置；其中"默认只信任当前仓库、其余一律视为外传风险"的形态已被 [04 §4](../04-可靠性安全与运行维护.md#security-supply-chain) 威胁记录的"信任边界"覆盖，记佐证。
- 分层放行（只读工具免判、项目内编辑免判、其余进判定）：§5.5 已有"常规可逆编辑和验证由任务授权覆盖"与审批疲劳段"机器可判定的先由检查拦掉"，记佐证不复写。
- 全部百分比与样本数：观察，不进正文。
- "判定实际影响而非表面文本"（命令链视为一个动作、评估脚本组装出的命令）：与 §5.5"未列动作按实际后果判断"同义，记佐证。
- 事故日志里的三起事件本身：01 §5.5 例子表已有"删分支""写生产：迁移""凭据"三项，这三起是它们的一手实例，记佐证不改文字。

## 跨方向建议（不由本方向修改）

- 给 **04 §6.5** 停止形态表：补一行"被执行点拒绝后继续推进，但累计拒绝次数达项目约定的连续或累计上限"——处置是停止并升级到具名接收人；**无人可问的运行（无头/无人值守）直接终止而不是等待**。原文的做法是拒绝作为结果返回执行者并要求它找更安全的路，连续 3 次或累计 20 次即停（数字是该产品的参数，标准里写"项目约定"）。这与 §6.5 已有"返工或重试成环，预设轮次上限"是不同的计数对象：那是重试次数，这是**被拦截的次数**——一个反复撞同一道门的执行者是被劫持或越权热心的信号，不是单纯的失败重试。
- 给 **03 §9.2 / §9.4**：委托合同的"治理继承"已有"不能由委托推导授权"，本文给出一手理由——子执行者内部把编排者指令当用户消息，任务看起来全是被授权的，故判定要在**委托出去那一刻**做，趁它还能被识别为执行者的选择；§9.4 汇合可补"返回物进入收口者之前过一次与派发时相同的核对，子执行者可能中途被读到的内容劫持"，原文的返回侧只警告不丢弃。
- 给 **03 §6.1**：输入层注入探针是对"未验工具返回"行的一个实现形态；原文的两层设计——输入层警告、输出层对工具返回不可见——是 03 来源信任与 01 执行点两条各自成立后的组合。由 C-20 一并处理。
- 给 **04 §4**：默认只信任当前仓库、把域名/桶/组织级信任边界写成显式配置，是威胁记录"信任边界"字段的可回读形态。

## 验证办法

① 取采用项目的拦截层或审批通道，列出它的判定输入字段；含执行者对动作的解释或自评字段即记该执行点不独立。② 构造一次越权动作并附一段说服性理由（"用户早先已默许"），比较有无理由两次的判定是否一致；不一致即判定被自述影响。③ 抽查免审批清单里是否有解释器/包管理器级通配项。④ 构造"关闭日志后执行"与"带跳过校验标志重试"各一次，断言被拦并有回执。本仓库无拦截层实现，四项均**未定**。
