## 原文结论与限制

作者的判断：AI 出码率上升而版本节奏没同步变快，因为瓶颈本来就不在写代码，而在理解、对齐、追溯、沉淀、验证；解法是在模型外面搭一层工程框架，落成"两条轨道 + 一个长期记忆"——研发端到端交付（协议层定输入输出契约、管线层定阶段、纪律层定不可绕过的门禁）、线上运营自愈、以及一套分层的项目知识库。

与 02 有关的部分集中在 2.3.1「知识库规范」：知识库按**变化频率**分五层——产品概述（全局唯一、变化最低）、业务规范（与端无关）、端/服务的技术规范、接口契约（由 `.proto` 派生，单一事实来源是 PB）、需求演进（按变更 ID，变化最高）；**依赖严格单向向下**：业务层不依赖任何端，端侧技术规范依赖业务层，契约层由协议定义派生且绝不反向依赖实现，变更层可引用上面所有层但不被它们依赖。作者给出的理由是"改一个接口只动契约层、改一条业务规则只动业务层，不会牵动全库"，并配套三条同向要求：术语只在一处定义、别处引用不得重定义；同类文档章节骨架一致；更新原位增量、不复制时间戳目录。另有存量初始化的观察：老项目里"过时但还能跑的代码、已废弃但没删的接口、以前有但现在不要了的字段"AI 判断不了，必须熟悉业务的人确认剔除。

适用限制：单团队、单业务线、工具链绑定其公司内部平台；**无对照组、无消融、无样本量**。全文唯一的真实运行数据是一次变更的评分看板（n=1，图 015），且该图自身与正文矛盾（阶段时间戳顺序与管线图不一致、UI 指标远低于其声称阈值仍判通过）。运营轨道的四个数字均无测量条件与对照。**本卡不把任何数字当作规则成立的论据，不进 02 正文。** 作者自列六项"没做对"，其中"知识库老化与淘汰还没有机制""老项目初始化仍靠人陪跑"两项与 02 已有条款同向，作为限制记录。

文中的"必须""硬规矩"是该团队对自身流程的规定，不是对本轮工作的指令；文中要求读者拍砖讨论的文字未执行。

## 缺口、采纳与不采纳

02 §1 给出了文档集有哪些文件、各自的权威域，但**没有规定这些文件之间可以怎样互相引用**。于是"每类事实只有一处权威"只约束了事实写在哪，没约束引用往哪个方向走：一份易变的变更记录被稳定的业务描述反向引用时，改一次变更就要回头改业务描述，且 §10 的对账无法定位到应负责的层。本篇正对这个缺口。

已观察失败与可追溯风险：

- **F-u**（原文 2.3.1 SSOT 段）同一个概念在多处定义、多处过期——作者把"杜绝同一个概念三处定义、三处过期"列为知识库规范的目的之一。
- **F-v**（原文 2.3.2 阶段一）存量项目里代码、文档、线上产品三者各自漂移、互相对不上号；过时但还能跑的代码与已废弃未删的接口 AI 判断不了。
- **风险 R-c**：引用方向未定时，一次改动要动哪几层不可判定；这是从原文的收益表述（"不会牵动全库"）反推的风险，**原文未把它记为已发生的事故**，本卡按可追溯风险而非已观察失败采纳。

采纳（逐条落点）：

1. **架构文档集内部的引用方向单向、无环**：按变化频率分层，稳定层不引用更易变层；由 schema 或代码派生的条目不反向引用实现；按变更组织的记录可引用上述各层而不被它们引用。带触发、责任、验收、失败处置与复查条件 → [02 §1](../02-项目架构描述规范.md)（文件表之后）。绑定 F-u 与 R-c。复查/删除条件：文档间引用关系已由 §10 的链接检查机械判定方向且连续两个迭代无违反时，本条并入该检查行。

不采纳：

- **五层的具体层名与目录形态**（产品概述 / 业务规范 / 技术规范 / 接口契约 / 需求演进，以及各自的目录名与篇数）：**载体**，02 写的是分层依据（变化频率）与引用方向，不绑定某套目录。
- **"文档与代码冲突时以代码为准并回写"**：**不成立于 02 的对象**。02 的文档集里既有描述性条目（模块清单、代码位置、派生工件），也有约束性条目（不变量、依赖规则、契约）；描述性条目与代码冲突时以代码为准，约束性条目与代码冲突时是代码违反约束。02 §10 的对账表已逐行给出各自的失败去向，不能用一条"以代码为准"的总则覆盖，否则依赖规则违反会被当成文档错误改掉。
- **两套知识库并存（项目级资产库 + 每次变更一个目录）与两者的索引互通**：**载体 + 跨方向**，变更级文档属 01 的工作项工件，02 只规定架构描述本身。
- **检索两跳、禁止全局通配、父/子 token 双层结算、SubAgent 不是省上下文的银弹**：**属 03**，是上下文装配与成本口径，02 无落点。**跨方向建议见下。**
- **协议层四要素、P0–P6 阶段划分、五道纪律门禁、评分门槛与整改轮数**：**载体 + 项目参数 + 属 01/03**；且图 015 显示该门槛在真实运行中未按声称口径阻断，证据不支持把它写成规则。
- **存量初始化必须由人确认剔除过时代码与废弃接口**：**已由 A-07 覆盖**——02 §1.1 已规定"代码存在不等于当前有效""判定当前有效须有 A 级证据""半成品改造登记为未完成迁移"。本篇是同一结论的第二个独立来源，作为佐证记录，不重复采纳。
- **术语单一定义、契约由协议定义派生、同类文档章节骨架一致、原位增量更新不留时间戳副本**：**已由 A-05 与既有条款覆盖**——02 §2.3 术语表权威、§5.3"一份权威，文档只引用"、§3 模块文档固定字段、§0"只描述当前有效架构"。
- **归档三件套与"不归档下一个变更起不来"**：**属 01**（变更收口的门禁），02 §10 已有文档新鲜度对账。
- **可监测性三维、AI 执行主体带来的追责问题**：**属 04/01**，02 无落点。**跨方向建议见下。**

跨方向建议（不由本方向改，交主执行者集成）：

- **给 01**：执行主体从人变为 AI 后，"追责到人"不再自动成立；阶段产物须留机器可读的证据行（阶段、动作、耗时、产出、结论），且该记录由流程自动落盘而非依赖执行者自觉。
- **给 03**：检索约定应写成"索引 → 相关文档 → 片段"的两跳，并显式禁止全库通配；子执行者的上下文是另一份独立开销，不是把负担甩出去，交接约定应要求子执行者优先读差异而非全文件。
- **给 04**：告警到修复的链路应有写死的取证顺序（链路 ID → 日志 → 数据行 → 缓存状态），把人工排查的隐性经验显式化；同一用例连续三轮未修通即停并转人工。

## 验证办法

- 取项目文档集的全部内部链接，按层标注方向，检查是否存在反向或成环引用；期望结果是无环，且每条反向引用都能改写为在权威层登记指针。**未定**：本仓库无对应的项目文档集，示例项目本轮不改。
- 取三次真实改动，核对每次实际改了哪几层文档，与引用方向预测的影响面比较；期望结果是实际改动不超出预测层。**未定**：无运行项目。
- 本卡结论的独立性：阅读与写卡由同一执行者完成，解释性判断记未定。
