# 04 可靠性、安全与运行维护

适用：项目存在部署交付、持久数据、外部依赖或运行责任时。本文是候选标准的运维专题，采用关系见[标准入口](README.md)；不直接赋予本仓库生产操作权限。

## 0. 接入与裁剪

[01](01-项目管理标准.md)管理工作项、责任与变更分级；[02](02-项目架构描述规范.md)描述质量场景和架构；[03](03-Agent信息获取与上下文管理.md)管理 Agent 执行上下文。本文把运行要求接到同一套工作项和证据上，不另建任务状态机。

责任可由同一人兼任，但每个运行对象都要能找到负责人及无人响应时的升级路径。新服务首次上线、重大依赖/数据变更、事故后，以及项目约定的维护周期触发复核。没有对应对象时写不适用及理由；缺资料、缺人、缺验证不能写不适用。

<a id="service-objectives"></a>

## 1. 服务责任卡、质量目标与运行取舍

每条关键用户旅程关联一张运行责任卡；小项目可在模块文档中嵌入，大项目可在服务目录系统中维护。它引用架构与工作项，不复制代码配置。

| 内容 | 最少回答 |
|---|---|
| 对象和负责人 | 哪个用户/服务/环境；业务负责人、运行负责人及替补/升级联系入口 |
| 关键旅程 | 用户要完成什么；依赖哪个模块和外部服务；失败影响谁 |
| SLI 定义 | 什么算好事件；分母、排除项、窗口；测量来源、查询版本及盲区 |
| SLO 与决策 | 目标由谁确认、从何时适用；预算不足时谁暂停哪类变更、如何恢复 |
| 证据入口 | 仪表盘/查询、告警路由、操作手册、最近验证与待修工作项 |

SLO 衡量运行体验，架构质量场景描述条件和响应，两者按 ID 关联。可用率、延迟、正确性、数据新鲜度按业务选择；批处理重点可能是截止时间和完整性。不得把进程活着或 HTTP 返回成功直接等同业务正确。**无流量、采集断档、只覆盖部分租户时分别注明，不把未知样本算成功。**

错误预算是允许的未达目标空间，预算策略须写具体触发和动作。暂停普通功能发布的同时，要给恢复服务与安全修复保留有责任人、有验证的路径。目标值与观察窗口由真实需求和测量条件确定；不可为变绿而追溯改掉已发生故障的统计口径。

验证：用一条用户侧失败、一次采集缺失和一项低流量场景走查，确认测量与行动都能到达。若长期目标达成但投诉和业务损失持续，先复核指标覆盖和目标；不能只调大阈值。来源与采用边界：[O-01](参考资料/O-01-Google-SLO实施.md)。

<a id="incident-response"></a>

## 2. 告警到恢复、复盘和预防

告警要能回答用户影响、范围、当前证据和第一个诊断动作，关联责任卡及 runbook。明确谁接收、无人应答找谁、何时升级；记录静默的范围、原因、结束时间与替代观察。告警投递成功不等于有人接手。

| 阶段 | 责任与动作 | 出口证据 / 失败去向 |
|---|---|---|
| 宣告与分级 | 首接人按受影响用户、关键业务、数据与安全风险宣告事故；指定指挥、操作和沟通责任，可兼任 | 事故 ID、影响假设、责任人、通信入口；找不到责任人走升级路径 |
| 缓解 | 操作责任人依据现有授权执行隔离、降级或回退；未授权高影响动作交有权人 | 动作、时间、目标环境、执行回执；结果未知先回读现场，不盲目重复 |
| 协调与交接 | 指挥维护当前假设与决策；沟通责任人发布经确认的信息；换班明确接收 | 谁接了什么、已执行副作用、下个动作及下次更新；无人接收则继续升级 |
| 恢复观察 | 运行负责人检查关键旅程、积压、数据一致性及约定观察窗口 | 用户体验恢复与剩余限制；仅告警消失不满足恢复条件，复发回缓解 |
| 复盘跟踪 | 负责人记录事实时间线、促成条件、检测与处置缺口；措施进入已有工作项 | 每个措施有责任、优先级和验证方式；未验证措施保留待办，不能随事故一起关闭 |

事故记录区分事实、假设与决定；敏感日志引用受控位置，不把密钥和用户数据复制到公共复盘。复盘关注系统改进；可以记录责任交接，但不以个人责备替代原因分析。桌面走查至少覆盖负责人失联、恢复后再失败与换班；能否联系到人和能否恢复服务需要分别验证。

升级与复盘流程写明谁能停一次运行、谁能批准重启；早期被某个团队观察到的异常若停在该团队内部、没到达有权停机的人，等于没有升级。对最严重的一类告警预设暂停默认值——约定时限内证不了是误报就先停相关运行，时限具体值按项目定。缓解动作不得销毁尚未取证的现场：把异常当基础设施故障重建或清理前先固定证据。已观察失败：一起评测逃逸事故里，内部团队数周前已观察到越界通信与越权上网却未上达处置负责人，处置时又把承载这些活动记录的共享服务当基础设施故障重建、清掉了现场。

来源与采用边界：[O-02](参考资料/O-02-Google事故响应.md)、[O-16](参考资料/O-16-评测环境逃逸事故群.md)。

## 3. 恢复能力、备份与数据生命周期

数据负责人会同业务负责人定义恢复时间目标 RTO（中断后可接受的恢复时限）和恢复点目标 RPO（可接受的数据丢失时间范围），并明确各自计时起止点。备份频率是实现条件，不等于实测 RPO。目标存于运行责任卡或恢复计划，其他文档只引用。

恢复计划至少有：覆盖数据与遗漏项、备份位置和访问控制、加密密钥恢复方式、依赖/配置恢复顺序、恢复目标环境、数据完整性判据、执行与批准责任、失败退出和回切办法。复制副本不能单独替代备份；逻辑误删或损坏可能已被复制。

恢复验证按项目约定的周期及关键数据/部署/密钥变更触发：

1. 选定故障场景、基线、负载与目标，确认隔离边界和授权；禁止演练环境向真实下游付款、发短信或重放业务写入。
2. 从受保护的备份或备用设施恢复；计时包含计划声明的检测、决策、取得凭据、恢复、路由和验证环节，不能只量导入数据库的时间。
3. 验证应用可运行、关键记录与业务不变量、外部对账与积压处理；记录实际可恢复的数据点和缺失范围。
4. 对比目标，明确通过、失败或未定，关联缺陷工作项；隔离演练只覆盖已测场景，生产切换能力需要有权负责人安排的受控验证。

容量、账户权限、凭据、恢复区域配置及依赖版本变化后，旧成功记录应复核适用性。数据恢复成功但业务状态错误，仍不能声明恢复完成。来源与边界：[O-03](参考资料/O-03-AWS恢复演练.md)。

数据目录同时记录用途、所有者、敏感类别、保留/归档/删除策略及适用依据的引用；具体期限由项目责任人确定。删除须覆盖派生索引、导出与备份到期处理，并保留最少的处置证明。存在保留义务的冲突时交相应负责人处理。以上生命周期字段是本项目管理选择，不把 AWS 本篇当成法律或合规依据。

## 4. 安全设计、开发环境与供应链

在新增外部入口、租户边界、身份权限、敏感数据流、CI 发布凭据或重大依赖时，由模块负责人和安全责任人更新威胁记录：资产、信任边界、攻击/误用路径、影响、控制、剩余风险、验证和复查触发。记录引用 02 架构视图与 ADR；按风险重点验证越权访问、跨租户访问、凭据泄露和不可信输入等适用场景。没有专业人员时明确能力缺口，由项目负责人安排补充评审，不能让 Agent 自认完成专业审计。

开发、构建、测试、发布与生产环境的权限边界在实际平台执行；记录具名维护责任及权限变更证据。凭据按主体、环境、用途与期限授予最小权限；轮换、撤销和泄露响应要有接收人。测试数据脱敏，日志与研究工件不含真实密钥。自动化不能通过修改仓库说明或流水线文件自授生产权限；检查代码的提交权限与发布保护的配置权限须有可验证边界。

项目自己分发给 Agent 的可执行能力资产——内部技能与提示资产、内部工具与 MCP 服务、Agent 配置——进同一份组件登记，至少记提供方、版本、维护责任、可访问的数据范围与可执行的写动作；有写动作而无授权依据或无维护责任人的资产不得发布，退役即删登记项。它们决定模型这次能碰什么，却不在锁文件里，不登记则下文的追溯链对它们不生效。允许 Agent 在隔离环境执行模型生成的代码时，**隔离保护的是宿主，不等于其中数据与凭据安全**：输入、网络出口、凭据、运行时长、资源与可回传路径分别约束并各自留回执，结论所依据的原始证据按只读保存、模型可读不可改。声明式的工具可见性配置只描述模型看得见什么，不构成授权；授权由工具服务端与目标系统按 [01 §5.5](01-项目管理标准.md#controlled-actions) 的执行点校验，框架自带权限的覆盖面须实测，自定义工具与外部工具服务通常不在其内。验收用一次越界构造（读范围外数据、访问范围外网络、回传范围外路径）断言被拒。

给模型自主能力的评测与训练环境要与生产系统同等硬化，不因“里面都是虚构场景”就降级威胁建模——这里运行的是能力尚未测定的模型。沙箱内可达的共享服务（如包缓存、制品库）既是网络出口也是执行者之间的共享存储通道，登记与隔离要按出口面与存储面双重覆盖。生产线上的监测（分类器、思维链监测）默认没有覆盖评测与训练负载，这段未覆盖按已知盲区登记。已观察失败：一起事故里共享制品库先被 agent 当消息板交换信息、又被用作绕过隔离的上网出口，而线上监测当时并未跑在涉事评测上。

出口白名单按“能力授予”评估，不是“目的地过滤”：经允许域名上每个可达函数都是攻击面，允许一个带上传能力的 API 域名等于允许向该服务任意账户上传。工具返回是攻击面，即使工具本身可信——网络型工具的返回要与网页同等做输入审查。已观察失败：出口代理放行了合法 API 域名，攻击者用自带密钥经这条通道把工作区文件上传到自己账户（修法是隔离内代理只放行本会话自带令牌、拒绝嵌入密钥）；连接器可把投毒 README 直送模型上下文且过了 malware 检查。

组件登记至少能从**部署制品追到代码修订、构建运行、直接及传递依赖的版本/来源**，并知道维护责任、支持状态及升级入口。能从构建产物生成 SBOM 时优先生成，不能手写一份与锁文件各自维护的版本表；无法解析的动态依赖单列盲区。制品与元数据要保护完整性；留有哈希或签名并不自动证明构建来源可信，验证方还需核对可信发布者、来源和适用规则。

| 触发 | 处理责任与依据 | 闭环出口 |
|---|---|---|
| 新依赖/升级 | 模块负责人核查来源、维护状态、兼容性与许可证使用信息；需要专门判断时交相应责任人 | 选择理由、变更与回退/替代方案，关联构建验证 |
| 漏洞通知或扫描命中 | 安全责任人确认受影响运行版本、暴露面、可利用性、业务影响；严重度是输入而非全部结论 | 修复期限、负责人、缓解与验证计划；事实不足记未定 |
| 尚无补丁/不能即时升级 | 有权人确认限时风险接受或隔离替代；例外记录影响版本与到期条件 | 到期/风险变化复查；不能用永久扫描忽略代替处置 |
| 修复发布 | 发布与运行负责人核对实际制品、回归与漏洞复查结果 | 线上受影响版本已替换或隔离的证据；仅主分支修完不能关单 |
| 复发/工具漏检 | 分析根因，更新设计、测试或工具，并核验有效性 | 预防工作项；规则重复或无效时合并/替换 |

安全证据与详细漏洞信息存于适当权限范围，公开入口只放引用。漏洞报告接收方式、响应角色及对外通知责任应可查。上述是基于 [O-04](参考资料/O-04-NIST安全开发生命周期.md) 的候选实现，不构成认证或特定法域符合性声明；能力资产登记与执行隔离两段的来源与边界见 [O-12](参考资料/O-12-Agent能力资产与执行隔离.md)。评测/训练环境硬化、共享服务双重面、出口白名单为能力授予与工具返回攻击面的来源见 [O-16](参考资料/O-16-评测环境逃逸事故群.md)、[O-17](参考资料/O-17-容器化与权限旁路的一手缺陷.md)。

## 5. 渐进发布、配置变更与容量

生产发布前，发布负责人准备一份关联工作项的计划：候选与现网制品身份、配置/迁移/功能开关差异、影响对象、所需授权、开始条件、批次与代表性要求、观察指标、停止/回退阈值、回退不可行时的恢复或前向修复方案、执行人及运行接收人。

对分批或灰度发布，先限制暴露对象，再按预先约定指标决定扩展；以关键旅程指标为主，并观察资源和积压。候选/对照的差异需可解释；共享数据库、队列或资源导致互相影响时，不能把比较结果直接归因为候选版本。没有足够流量或未覆盖关键营业周期，记未定并补验证，不因等待时间到了就扩展。无法分流的项目记录替代策略与剩余风险。

**代码回退、数据回退、关闭开关是不同操作。** 发布前验证旧版本能否读新数据、队列是否含新格式、外部副作用能否撤销；不可逆点写进计划。配置和开关也有版本、负责人、回退值及检查；临时开关有清理条件和工作项，避免长期组合爆炸。新环境部署尽量使用已验证的同一制品；重新构建的产物要重新绑定身份与证据。

发布后回读真实运行制品与配置，保留观察窗口、业务结果及未解决限制；控制台显示部署成功不足以证明验收。线上观察失败进入 01 的变更/事故流程，不私自篡改通过阈值。来源：[O-05](参考资料/O-05-Google渐进发布.md)。

容量验证复用 02 的质量场景：说明负载模型、数据量、资源配额、连接池/队列上限、降级行为、扩容提前量与费用假设。大促、数据增长、依赖限额或拓扑改变前由运行负责人复核；用成本变化定位问题时同时观察业务量与体验，不能以降费掩盖可靠性下降。这组项目字段是对质量目标和灰度观察的落地设计，不声称来自单篇容量规划指南。

## 6. AI 协作运行的可观测、可重复与运行开销

适用于项目把 AI 编程工具或 Agent 纳入常规研发、发布或运行流程时；只有人工开发时记不适用及理由。本节管这条生产线自身的运行证据、运行开销与无人值守的推进边界，不重写 [03](03-Agent信息获取与上下文管理.md) 的会话上下文管理，也不承担 [01 §4.7](01-项目管理标准.md#maintenance-budget) 的维护排期。

### 6.1 运行记录与失败归因

触发：Agent 承担会改动仓库、发布或生产的动作；或出现一次无法解释的运行失败。责任：工具维护者定义并保留记录，任务负责人在结论里引用具体运行 ID。

一次运行要能事后回答三件事并各自指出证据位置：**耗时分布在推理还是工具执行、用量集中在哪些会话与调用、失败或中断发生在哪一步**。轮数与工具序列由模型在运行时决定，记录格式不得预设固定步骤表；按时间排列的日志不等于调用关系，须能还原父子关系与时间区间。

| 最少留存 | 说明 |
|---|---|
| 运行身份 | 运行/会话 ID、发起人、目标仓库与环境、模型与宿主版本、提示或委托合同版本 |
| 执行结构 | 每一步的父子关系与起止时间；模型调用与工具调用分别成条 |
| 用量 | 每次模型调用的输入、输出与缓存类别用量，可聚合到会话与整次运行 |
| 结果状态 | 每步通过/失败/未定；重试各自成条不合并；中断、超时、未收尾的调用补记错误类型 |
| 副作用回执 | 写入、提交、发布与外部调用的实际结果；未知状态按 [03 §9.5](03-Agent信息获取与上下文管理.md#delegation-recovery) 处置，不盲目重放 |
| 会话事件 | 上下文压缩、会话重启与交接的发生时点；压缩有损，不留痕则后段失败无法与任务变难区分（[O-09](参考资料/O-09-省Token与用好AI是同一件事.md)） |
| 意图与审批要素 | 用户提示、工具审批判定、工具执行结果、网络代理的放行/拒绝事件分别可追溯，可汇入 SIEM 或合规日志；传统日志答“发生了什么”，这些要素答“为什么、用户意图是什么”（[O-18](参考资料/O-18-编码Agent的原生遥测与内部监测.md)） |

失败先归入模型侧、工具与环境侧、编排或循环中断三类之一再定处置；归不出类记未定，不把重跑当默认动作。字段口径随宿主或模型更换而变化时标注版本并分段比较，不把新旧口径混算成一条趋势。

只存在于开发者本机、随会话销毁的记录无法支撑数日后的复现，属已知盲区须写明；留存位置、访问范围与期限按 [§3](#recovery-data) 的数据目录登记。运行记录默认包含提示词、模型输出、工具参数与返回，可能含凭据、客户数据与源码；捕获开关与脱敏由数据负责人会同安全责任人确定，第三方托管的观测平台按 [§4](#security-supply-chain) 当外部依赖处理。

把执行放进隔离环境会同时降低宿主侧可见性：宿主的端点检测看不进沙箱或 VM，事后拉取式日志导出不等于实时监测，这段缺口按已知盲区登记。跨会话留存的上下文——CLAUDE.md、挂载工作区、计划任务与长期 agent 的状态目录——里的注入会在每次启动被重载，属驻留式攻击面，纳入同一份盲区与来源信任登记（[O-17](参考资料/O-17-容器化与权限旁路的一手缺陷.md)）。

采集不得改变被观测运行的行为或使其失败。采样、限流与队列丢弃会让统计静默偏低，丢弃量须可见；未采到的区间按 [§1](#service-objectives) 记未知，不折算成没有问题。

运行记录若接上异步复核，复核本身要登记覆盖率与校准：按约定时限复核轨迹、分级、只把标记项送人；用独立的人工上报作召回率下界——监测连人都会发现的都没标出即说明漏检，反过来不证明没有更隐蔽的漏检；明确不在覆盖内的部分（本地自建、随会话销毁的部署）登记为盲区。厂商报告的复核时限、漏检率与轨迹量都只是其条件下的观察，不进本项目口径（[O-18](参考资料/O-18-编码Agent的原生遥测与内部监测.md)）。

验收：取一次真实失败的运行走查——能否定位失败步骤、取回该步输入与输出、区分三类归因、说明证据保留到何时及谁可访问。四项任一做不到记缺口工作项，不以"观测平台已接入"代替。来源与采用边界：[O-06](参考资料/O-06-AI运行可观测与失败归因.md)。

### 6.2 AI 参与产出的可重复性

触发：把 AI 运行结果当作验收证据、回归基线或复现依据时。责任：任务负责人声明本次复现的定义，工具维护者登记可钉死的条件。

**先声明复现指什么**：逐字一致的输出、等价的产物（通过同一组测试、产物摘要一致）、多次采样落在约定区间。三者代价和可得性不同，默认不承诺第一种；把"再问一次模型看它是否说同样的话"当复现，会同时制造假回归和漏检。

相同提示词与相同参数（含温度为零、固定随机种子）不足以保证输出一致：并发负载会改变底层运算的合并顺序。因此**输出不一致不能直接推断为输入、代码或数据发生变化；一次一致也不证明后续一致**。差异先按此排除，再进 [§2](#incident-response) 的分析。

可重复性声明绑定模型、推理服务、版本与配置组合，按 [03 §12](03-Agent信息获取与上下文管理.md#capability-acceptance) 登记，不跨版本沿用，并标注它属于**接口契约保证、本地实测观察还是间接推断**；上游为闭源或托管服务时只能来自实测。开关存在不等于生效——确定性配置可能被另一条执行路径静默绕过且不报错，启用后须用反例验证（同一输入分别在有并发负载与无并发负载下比较），失败按 [01 §5.6](01-项目管理标准.md) 判检查器故障，不折算为通过。

严格逐字可重复需要放弃一部分并行度，是有代价的运行模式，由有权人按场景确认适用范围。不自建推理服务的项目不掌握这些开关，只能把可重复性定义在产物与区间上，并在验收记录的 `limitation` 里写明。

更换模型、推理服务或宿主版本按 [§5](#progressive-delivery) 当变更处理：先在**运行之外、且早于本次更换就已存在**的一组比较基准上比对新旧行为，比较结论、生效范围与回退路径进变更记录后分批放开。基准事后补建不满足本条——没有它时，行为变化与任务本身变难在证据上分不开，该次更换的能力结论记未定，不以新版本更好为由全量切换。基准的构造与覆盖度由 [03 §11.1](03-Agent信息获取与上下文管理.md#context-evals) 定义，本节不另立一套。来源与采用边界：[O-07](参考资料/O-07-输出可重复性与确定性代价.md)、[O-14](参考资料/O-14-Anthropic创业公司指南.md)。

### 6.3 运行开销的观测、归因与止损

触发：AI 运行开销成为项目常态支出，或单次运行、单周期开销超出预算。责任：运行负责人持有额度与止损决定，工具维护者提供采集。会话级上下文预算见 [03 §11](03-Agent信息获取与上下文管理.md#measurement)，人力维护容量见 [01 §4.7](01-项目管理标准.md#maintenance-budget)；本节只管开销作为运行约束的观测、归属与止损，不重复它们的分解口径。

- **归属**：每笔开销可追到项目、工作项、角色与目标环境；无法归属的部分单列，不按人头或工时摊平。看不出开销集中在哪时，任何优化排序都无依据。
- **口径**：比较开销时同时报计费类别（缓存命中、未命中、输出）与运行轮次。只报总额会掩盖结构变化——总量下降而未命中上升是常见形态。
- **预算与止损**：额度、告警接收人和超额处置（缩小范围、改用低价档模型、暂停该类运行）预先写明。**止损不得关闭 [§6.1](#agent-run-observability) 的运行记录、审计与安全检查，也不得停掉事故处置与安全修复所需的运行**；这与 [§1](#service-objectives) 错误预算策略是同一条原则。
- **优化的验证**：改动只影响与模型决策无关的确定性环节时，可直接对比同一输入的计量；改动会影响模型决策路径时，单次前后对比的噪声可能大于效果，须多次采样报区间或改测与决策无关的中间量，并按 §6.2 声明本次复现的定义。同时验证措施真实生效（拦截点、字段、作用范围），静默失效按 [01 §5.6](01-项目管理标准.md) 判检查器故障，不以配置项存在为准。
- **收益登记**：分项降幅不得相加或反推为整体降幅；整体收益要端到端实测，未测记未定。外部工具或供应商公布的降幅是其条件下的观察，不登记为本项目预期值。

验收：周期复核走查三问——开销能否归到具体运行与责任人、超额时谁做了什么处置且是否动过记录与检查、已登记的降幅有没有端到端证据。来源与采用边界：[O-08](参考资料/O-08-AI运行开销的归因与止损.md)。

### 6.4 由模型承担的归口判定与口径治理

触发：用模型对用户反馈、缺陷或告警做分类、分诊或责任归属；或该口径发生变更。责任：口径由业务与运行负责人定义并版本化，工具维护者保证执行。事故级反馈按 [§2](#incident-response) 处理，本节不重复其流程；没有此类判定的项目记不适用。

- **口径是工件不是提示词**：每个类别写清归入条件、排除条件、多类同时成立时的优先规则，并与责任归属绑定。规则散落在提示词与定制分支里时，一次调整牵动多处，无法评审、测试与回退。
- **确定的判定用规则执行，模型只做需要语义理解的部分**：指令过长、多条件同时成立或规则相互冲突时，模型不保证稳定执行；为修一个类别追加的说明可能改变其他类别的结果。
- **口径变更作废与旧口径绑定的历史示例、基线与已归档判定**，并记录口径版本。新增或拆分类别后，按旧口径标注为正确的历史案例会持续把结果拉回旧类别——输入没变，变的是口径。
- **口径变更按 [§5](#progressive-delivery) 发布**：先在典型样本与历史数据上验证，再分批发布、观察、保留回退路径。口径直接决定责任归属与任务流转，错误口径全量生效会持续制造错误派单。
- **判定要留依据**：保留归入该类的理由与所依据的输入，否则无法区分错在口径、输入还是模型判断。
- **跨口径版本的准确率不可直接比较**，变更期间的前后对比记未定；修复效果用同一口径观察同类反馈是否下降，口径变了要说明。

验收：走查一次口径变更——旧示例与基线是否标记失效、变更是否在典型样本上验证过并有回退路径、效果比较是否标注口径版本、随机一条判定能否说出理由与依据。来源与采用边界：[O-10](参考资料/O-10-归口判定与口径治理.md)。

### 6.5 无人值守推进的准入、停止与复核

触发：项目允许 Agent 在无人实时在场时继续推进工作项、修改仓库或调用外部系统。责任：运行负责人持准入与暂停决定，工具维护者提供停止手段与回执，工作项负责人做恢复在场后的复核。只在人在场时逐步放行的项目记不适用。

**准入按能力次序，不按意愿**：一类工作能否无人值守推进，取决于它已具备可自动判定的完成条件、可自动执行的验证、以及失败能被发现的观测；三者缺一即不得放开，先补齐再扩范围。缺验证手段的环节自动化后产出的是无人复核的批量结果。**完成条件与验证用例是运行的输入，不是运行的产物**：它们在运行开始前已存在于运行之外的工件，本次运行不得新增、改写或删除（[01 §5.5](01-项目管理标准.md#controlled-actions) 已把改动冻结验收条目列为受控动作）；执行者自产或自改的完成判据不构成完成，比对前后摘要值发现改动而无有权人批准时判该次结果未定。无人值守的动作范围只能是 [01 §5.5](01-项目管理标准.md#controlled-actions) 授权范围的子集：受控、不可逆或超出预授权的动作一律停下等人，不因流程需要继续而自行放行；判定执行点同样在被约束者之外，每次调用都过。允许无人值守推进前，隔离前提要每次运行前验证，不以“上次配好了”自证；已观察失败是隔离配置被误以为生效、实际留有网络出口。任务本身是否可解也是准入条件——目标离线或任务不可解时，执行者往往转而寻找越界的完成路径。

| 停止形态 | 最少处置 |
|---|---|
| 执行者退出、超时或掉线，步骤停留在运行中 | 外部巡检判超龄后转失败或重派；**巡检器自身也要有超龄检测** |
| 状态记录与实际执行不一致（有活跃步骤而无执行者） | 以环境回读为准重建或停止，不以状态记录自证 |
| 返工或重试成环 | 预设轮次上限，超限转阻塞并通知具名接收人 |
| 定向返工时上一轮的下游动作仍在运行 | 先撤销旧写资格再开新一轮，按 [03 §9.5](03-Agent信息获取与上下文管理.md#delegation-recovery) 对账 |
| 执行者自述阻塞 | 暂停该链路并升级；阻塞须落成状态，不能只出现在自然语言里 |

单次动作审批不足以约束一段长序列：每一步看似合规、序列整体可能违规（已观察：把认证令牌拆成两段、运行时重组以绕过扫描器）。无人值守推进因此要有能看整段轨迹意图、而非仅单步的监测点，且能暂停会话交人复核。执行者新起的子执行者或嵌套会话不得以更弱的授权档运行，仍按 [01 §5.5](01-项目管理标准.md#controlled-actions) 的预授权子集校验（已观察：嵌套启动一个免审批的执行者绕过约束）。

每段推进开始时先在目标环境跑一次约定的基线检查并记录结果，把上一段遗留的失败与本段引入的失败分开；基线不通过就停下报告，不在失败的基线上继续推进。基线检查自身不稳定时按 [01 §5.6](01-项目管理标准.md#gates) 判检查器故障，不静默跳过。

**执行完成不等于业务完成**：无人值守段落的出口是待复核，不是已交付。复核项要能回答做了什么、依据哪些输入、验证跑了没有、剩余风险是什么，只有一句"已完成"的产出退回。待复核队列的积压量与最长停留时长本身要有人看——长期堆积说明这道复核已退化为形式，按 [01 §5.6](01-项目管理标准.md#gates) 判闸门失效，不记通过。失败归因复用 [§6.1](#agent-run-observability) 的三类，不另立一套字段。

验收：走查一次真实的无人值守运行——它在哪一步该停而停了、动作是否都在预授权子集内、五类停止形态能否各构造一次并被检出、次日复核的证据是否够判断。范围扩大、模型或宿主更换、出现一次无人发现的失败后重新走查。来源与采用边界：[O-11](参考资料/O-11-无人值守推进的边界.md)、[O-13](参考资料/O-13-长时运行Agent的可靠性.md)、[O-14](参考资料/O-14-Anthropic创业公司指南.md)、[O-16](参考资料/O-16-评测环境逃逸事故群.md)、[O-19](参考资料/O-19-长时程模型的轨迹级监测.md)。

## 7. 交付产品内含模型能力时的运行责任

适用于交付物自身会调用模型能力（自建或第三方），并要长期维护时；没有此类能力的项目记不适用及理由。本节管**产品里的模型能力**，[§6](#agent-run-observability) 管**开发流水线里的 AI**，二者对象、责任人与波动来源都不同，不合并。这类能力的**架构登记**——证据等级、已接入/已声明/已废弃三态、能力上限的单一权威、分类封闭集合——在 [02 §5.6](02-项目架构描述规范.md#external-capability-registry)，本节不重复登记规则，只管登记之后的运行责任。对用户承诺什么、承诺不了什么属 [§1](#service-objectives) 的服务目标，不在此另立一套。

触发：首次把一项模型能力接入交付物；模型、提供方、提示词模板或生成参数变更；供应商侧行为或计费变化。责任：该能力的模块负责人持有版本记录与失败形态，运行负责人持有成本与止损，数据负责人会同安全责任人定日志口径。

- **四样东西各自有版本记录**：模型与提供方、提示词模板、生成参数、登记行状态。任一变化都可能改变产品行为**而代码修订不变**——只比对代码的排查会全部落空，这是长期维护里最难查的一类。四者随部署制品进 [§8](#operational-acceptance) 的 `baseline`，变更按 [§5](#progressive-delivery) 处理。
- **变更前后在固定评测集上比较**：比较基准须早于本次变更就已存在，理由与失败依据见 [§6.2](#agent-run-observability)，本节不重写；无此基准时该次变更的质量结论记未定，不以新版本更好为由放开。
- **调用出口处记录可追踪要素**：一次用户可见的行为要能追到实际调用的提供方、具体对象、能力类别与输入规模，并与该请求的其他日志共享同一追踪标识；要素散落在多条分支里各记一份时，记录必然不全且互相矛盾。日志内容、访问范围与保留期限按 [§3](#recovery-data) 的数据目录登记，与 [§6.1](#agent-run-observability) 同规则，不另立。
- **用户可见的失败形态预先枚举并各有处置**：拒答、超时、输入被拒、降级到低配能力、被改路由到备用模型、能力暂不可用。**展示层承诺的能力不得超出运行时实际可提交的能力**——已发生失败：能力在界面上亮着却提交不了，展示状态与运行时是否真接了这条路径脱节。降级路径按 [§5](#progressive-delivery) 验证过才算存在，未验证的降级路径在事故时才第一次运行。
- **供应商侧不可控变更要有发现方式**：型号静默更新、上限或安全策略调整、区域可用性变化都不会通知消费方，登记行也不会自己变。约定复核触发与观测项，证据等级为间接推断的登记行优先复核；否则变化只在调用失败时暴露。已发生的一手实例：出口管制使一款模型整段停用一段时间、被拦请求被供应商自动改路由到备用模型并通知用户、新增的安全分类器改变了对合法编码请求的行为——三者都非消费方能控制、也都不会等到调用报错才显现，消费方要有观测触发与降级验证。上游废弃、涨价、限流或下线的迁移责任与期限按 [01 §5.4](01-项目管理标准.md#dependency-lifecycle) 处理，不重写。
- **成本按产品运行成本归集**：它随用户量与单次调用规模波动，与 [§6.3](#agent-run-observability) 随开发活动波动的开销分开归集、分开设额度；计量口径、止损不得关闭记录与安全检查、收益须端到端实测三条沿用 §6.3，不另立。

验收：走查一次已上线的模型能力——四样版本记录能否取到当前生效值、随机一次用户请求能否追到实际调用的对象与输入规模、枚举的失败形态能否各构造一次且都有处置、上一次供应商侧变化是被观测发现还是被用户投诉发现。本仓库无此类产品，以上均记未定。来源与采用边界：[O-15](参考资料/O-15-产品内含模型能力的运行责任.md)、[O-20](参考资料/O-20-供应商侧模型能力变更实例.md)。

## 8. 可复制的运行验收记录

以下字段可嵌入既有工作项、发布记录或服务目录，不必新增系统。

```yaml
object: 服务/关键旅程及目标环境
owner: 运行负责人及升级入口
trigger: 首次上线/重大变更/事故后/周期复核
baseline: 代码修订、制品摘要、配置版本
applicability: 适用章节；不适用的对象理由
checks:
  - claim: 本次具体要确认的运行能力
    criterion: 预先确定的判据或目标ID
    method: 查询/演练/检查入口
    result: PASS/FAIL/UNDETERMINED
    evidence: 原始证据受控位置和时间
    limitation: 未覆盖的环境、流量或故障条件
followups: 缺口工作项、责任、到期与复核触发
decision: 是否接收维护、是否发布；有权人及适用范围
```

选用本专题的项目至少走查：告警无人接、数据恢复后业务不一致、依赖漏洞无补丁、灰度样本不足，以及运行责任人离开。采用 [§6](#agent-run-observability) 时增加三条：一次 Agent 失败运行无记录可定位、口径或版本变更后旧证据未失效，以及无人值守推进在无人发现的情况下卡住或越权。采用 [§7](#model-capability-in-product) 时增加一条：产品对外可见的能力与运行时实际可提交的能力不一致。只有证明过的能力才能填通过；模板完整性和真实系统恢复能力分别判定。示例见[运行维护演练包](示例项目-连锁零售中台/docs/operations/README.md)。
