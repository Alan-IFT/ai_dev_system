# ADR-0001：模块化单体而非微服务

状态：active　日期：2025-03-05　决策人：Zhao　批准人：Zhao
取代：无　被取代：无　重评条件：任一模块需要独立伸缩或独立发布节奏（已触发一次 → ADR-0012 拆出 pos-gateway，本决策其余部分不变）

## 背景与约束

一人开发，60 家门店，14 个业务领域。上一套系统（前任外包）是 9 个微服务，两年后没人敢改：跨服务契约无人登记、部署依赖靠口口相传、一次改价要发四个服务。**这个项目立项的直接原因就是上一套无法维护。**

## 备选方案

1. **微服务，按领域一服务**——不选：一人维护 14 个部署单元的运维成本远超收益；跨服务契约在没有登记纪律时必然失控（上一套的死因）。
2. **单体不分模块**——不选：14 个领域不分边界，半年后就是大泥球；agent 每次改动都要读整个代码库。
3. **模块化单体 + 依赖规则机械检查 + 事件总线**——选。

## 决定与适用边界

- 一个代码库、一个主部署单元 `core`；按模块分目录、分 schema、分 API；模块间同步走公开 API、异步走登记的事件。
- 依赖方向由 `dependency-rules.md` 的矩阵规定并由 CI 阻断（INV-02、INV-03）。
- 拆出独立部署单元只在满足"独立伸缩 / 独立发布节奏 / 独立安全边界"之一**且**边界已有契约测试时（见 02 规范 §11）。

## 代价与风险

- 一个部署单元意味着一处故障可能影响全部——用 SLO 与回滚速度补偿，不用拆分补偿。
- 模块边界靠纪律 + 检查器；检查器失效时边界会悄悄腐蚀（F-026 真的发生了）。
- 将来拆分时要重新做一次契约梳理——但登记表从第一天就有，这个成本已经预付。

## 验证方式

- 每季度看：依赖规则例外数（应 ≤ 3）、跨模块直接写（应为 0）、一次常规变更平均触碰模块数（应 ≤ 2）。
- 2026-09 复查：例外 2，直接写 0，平均触碰 1.6。有效。
