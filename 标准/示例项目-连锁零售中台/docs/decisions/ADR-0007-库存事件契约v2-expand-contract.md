# ADR-0007：库存事件契约 v1 → v2 采用 expand/contract 迁移

状态：active　日期：2025-12-08　决策人：Zhao　批准人：Zhao
取代：无　被取代：无　重评条件：出现第三种需要不同分区键的消费者；或事件量级使按门店分区不足以保序

## 背景与约束

- 2025-11-18 事故（F-017）：reporting 消费者重启后重放了 6 小时事件，`inventory.stock-changed` v1 没有幂等键，pos-gateway 的出库回调被重复执行，11 家门店 340 个 SKU 库存双扣，人工修了两天。
- v1 有三个消费者（reporting、pos-gateway、settlement），各自解析代码不同。
- 2025-12-02 一次尝试（F-019）：直接在 v1 上加字段并改 `store_id` 语义，两个消费者的 schema 校验当场崩，回滚。**这次失败是本 ADR 的直接来源。**
- 约束：不能停业务；prod 每周二发布；三个消费者由同一人维护但在不同模块。

## 备选方案

1. **原地改 v1（加字段 + 改语义）**——已实测失败（F-019）：消费者同时崩、无法逐个回滚。
2. **v2 新事件，一次性切换全部消费者**——不选：切换窗口内任一消费者失败就要整体回滚，等于方案 1 换了个名字。
3. **expand → migrate → contract：v1、v2 并行发出，消费者逐个切，最后下线 v1**——选。代价是共存期 outbox 写两条、消息量翻倍，约 8 周。
4. **加一层去重网关，消费者不动**——不选：只解决幂等，不解决分区键与保序；且网关是新的失效面，写不出独立探测。

## 决定与适用边界

- v2 schema：加 `event_id`、`version`、`idempotency_key`（`{source}:{source_ref}`）、`emitted_at`；`store_id` 成为分区键。
- 三阶段，每阶段独立可发布、可回滚：
  - **expand**（WI-0142 阶段 1）：inventory 同时发 v1 与 v2；v2 走新队列；契约测试覆盖 v2 提供方。
  - **migrate**（阶段 2）：reporting → pos-gateway → settlement 依次切到 v2，每个一次发布、各自证据；切换顺序按风险从低到高。
  - **contract**（阶段 3）：登记表 v1 消费者为零，v1 队列 7 天无投递，告警期 7 天，删 v1（INV-015）。
- 幂等去重由 platform 的 `idempotency_receipt` 提供（ADR-0009），消费者不各自造轮子。
- 本模式成为**全部破坏性契约变更的默认流程**（INV-07）。

## 代价与风险

- 共存期消息翻倍：RabbitMQ 负载观察，阈值 70%。
- 三个消费者切换期间语义不一致（一个按 v2 去重、两个还没）——可接受，因为 v1 消费者本来就没去重，没有变得更差。
- 8 周的日历时间；期间 inventory 不能做其他 schema 变更。

## 验证方式

- INV-014：v2 事件字段完整；同一幂等键重复投递每消费者只处理一次（回执数 == 去重后投递数）。
- INV-016：对任一消费者重放 24h 事件，结果与重放前一致。
- INV-015：v1 消费者为零后下线。
- 复查：2026-06-08（半年）——已复查，无回退，见 WI-0142 收口记录。
