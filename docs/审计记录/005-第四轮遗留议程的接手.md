## 1. 为什么跑这一次

三个目的一次办：① `交付型 × 接手`是[合同](../../CONTEXT_MANIFEST.md)两个视图里从未真跑过的组合，而第十二轮的读数是"只有换运行类型才撞得到新形状的缺陷"；② 这 16 项从第四轮挂到现在九轮没动，是仓库里最老的停滞项，工件确实残缺（其中 8 项的前提已被 D-055 改掉）；③ [A0⁶](../历史/待决策清单.md#a0-handover) 第 1 项的假设需要一个真实接手运行来证伪，而"旧议程 vs 新前提"恰好就是它说的那种**两个权威打架**。

## 2. 开工前的八项事实：四项答不上

[22 §2 P3](../22-上下文装配.md) 要求动手前执行者能基于工件说清八项，"答不上来就先补工件，不靠回忆"，删除条件是"写不出（责任结构型）"，**不含接手例外**。实测：

| 22-P3 要求的事实 | 能否由工件回答 |
|---|---|
| 目标与非目标 | 能 |
| **当前工作项与它的状态版本** | **不能**——合同的 `current_work_item` 是 `null`，且 004 §8 无状态版本 |
| 工作副本身份 | 能 |
| **事实源** | **不能**——这 16 项在仓库里有两份记录，没有一处声明哪份权威 |
| 目标环境 | 能 |
| **验收标识** | **不能**——"审议 16 项"没有对应的验收条目 |
| 风险与阻塞 | 能 |
| **未决策项** | **不能**——它正是本工作项本身，而两份记录不一致 |

**结论：22-P3 在 `交付型 × 接手` 下是可执行的，但执行它就等于把这次运行的前半段变成一次事实型运行。** 本轮"补工件"消耗了大部分预算，真正的裁决工作是在补完之后才开始的。规范里没有任何一处说这是合法的，也没有说该怎么记——[00 §3](../00-总览.md#default-scope) 只要求"在起点声明它的类型"，未建模**一次运行前后两段类型不同**。这与 [Case C-014](../失败Case清单.md) 是同一处缺口的另一面：C-014 说的是 22 章的接手路径写在字段之外，本轮说的是那条路径即使找到了也没说清代价由谁付。

## 4. 三处结构缺陷

**（一）同一份议程有两份记录，且已漂移。** [004 §8](../输入材料/004-第四轮公众号文章综合记录.md#open) 16 项、[待决策清单 A0″](../历史/待决策清单.md#a0-round4) 11 项（重新分组）。A0″ 带着后续各轮批注（哪些被 D-055 吸收、哪些已降级），004 §8 一条都没有；而 [PROJECT_STATUS](../../PROJECT_STATUS.md) 的下一步指的是 **004 §8**。**接手者按状态文件的指引走，拿到的必然是旧的那份。**（Case C-019）
处置：004 §8 标注冻结并路由到 A0″；PROJECT_STATUS 改指 A0″。**没有合并两份**——004 是第四轮的输入材料，冻结件不该被改写。

**（二）[12 章](../12-记忆与知识治理.md) §1「未决」与同章 §2 直接矛盾。** §1 把"影子态是否参与默认检索""自动晋升两轴是『且』还是『任一』""个人偏好层是否重分类"列为未决，而 §2 的 P5、P3、P8 已按 004 §8 第 5、4、6 项的默认裁决落地，**三处逐字对得上**。默认裁决执行了，登记处没跟着改，此后九轮无人发现。（Case C-018）
处置：删去三项重复登记，条文未动，理由记入[追溯账本 ch-12](../追溯账本.md#ch-12)。

**（三）合同的 `current_work_item` 自基线以来从未被填写过一次。** 合同明文写着"若进入真实实施，必须在此填写一个精确工作项路径"，而 `git log -S` 显示它自 `78664b0` 起一直是 `null`——期间第九～十三轮全是真实的条文变更。**D-015 已生效，但它的载体上这个字段是死的**，且没有任何检查覆盖它。（Case C-017）

## 5. 一处缺陷，不是待裁项

[33 §2 P9](../33-评估与演进.md) 的删除门槛是"绑定 Case 不再复现**或**持续零消费"。第十一轮实测：当场修掉的失败不留痕，"这条规则拦住过东西吗"无法回答，**第二个析取项不可判定**。这不是"该怎么裁"的问题，是一条已落地条文里有一半执行不了。两个选项与代价见[待决策清单 A0⁷](../历史/待决策清单.md#a0-thin)。本轮不自行裁——它改的是一条原则的可执行性。

## 6. A0⁶ 第 1 项的假设：**未被证伪，但需要改一个词**

[A0⁶](../历史/待决策清单.md#a0-handover) 第 1 项的假设是：降级解决的是**证据不足**，不解决**两个权威打架**；后者不能降级，因为"带成立条件继续"等于让执行者自己挑权威。

本轮撞到的 §4（二）正是一次真实的权威冲突——12 §1 与 12 §2 就同三件事给出相反的状态。**处置结果与假设一致：没有降级，而是停下来查。**但查的过程暴露了假设里一个不准确的地方：

> 这次冲突**能**被消解，靠的不是"证据够不够"，而是存在第三份记录（004 §8 与 A0″）说明哪一侧是当前值。**决定能不能继续的，不是冲突的类型，是有没有一份说明哪个权威当前有效的记录。**

两种情形的去向仍然都不是降级：
- **有这份记录** → 按记录消解冲突，继续；此时根本用不到降级。
- **没有这份记录** → 停止；此时降级恰好等于让执行者自己挑权威。

所以假设的**结论**成立（权威冲突不走降级），**理由**要换一个：不是"证据不足与否"，而是"是否存在一份指明当前权威的记录"。**若按此定稿，00 §3 那一句话要写成"降级适用于证据不足；权威冲突先查有无指明当前权威的记录，有则消解、无则停止"**——仍是一句话，但比原措辞多了一个可执行的动作。

**这一条的证据强度**：一次真实观察，n=1。它没有证伪假设，也**不足以确认**——需要一次"没有第三份记录"的权威冲突才能验后半句。

## 6.5 顺带更新架构图时撞到的两条

架构本身这轮没变，图上加的是它此前完全没有的一条架构级内容——**一次运行的两个属性**。做的过程中撞到两条同形状的缺陷：

- **图例一直是工具的默认 Web 应用分类**（前端 / 后端 / 数据库 / 安全 / 外部系统），与这张图一个词都对不上，自第十轮成图起印在每一张导出的 PNG 上。`archify validate` 是 9/9 通过的——它检查构图，不检查文字说得对不对。发现方式是导出后**真去看了一眼图**（Case C-020）。
- **`archify visual-check` 自成图起一直是 fail，而这条命令从没被跑过一次**（Case C-021）。判为取舍不修：这一页是文档，本来就要滚动。

两条与 §4 的三条是同一形状：**出问题的地方都有人写过、没人再看过。**
