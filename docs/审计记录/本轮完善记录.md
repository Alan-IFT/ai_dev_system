## 本轮问题与预先验收

要回答：现有文档能否支持大型项目跨团队、跨发布周期和故障后的持续维护，而不只支持一次 Agent 编码会话？

成功标准：

- 对发现的管理、架构、上下文及运维安全缺口，逐篇读取一手资料，分别记录原意、适用边界、采纳理由和实际修改落点；完成一篇的落地后才继续该方向下一篇。
- 新增要求有触发、责任、可定位工件与验收/失败处置；可按风险裁剪，不用虚构事故或收益数字证明必要性。
- 共享入口指向更新后的标准；示例补出可走查的长期维护工件，并明确虚构场景不构成真实运行证据。
- 跑仓库效力检查和链接检查；独立执行者复核本轮改动中的来源归因、矛盾与完成声称。

失败标准：只堆资料不改标准；把摘要当成读过原文；新增规则与旧规则互相抵消；把演练模板写成生产验证已通过；检查未跑却写通过。

结论等级：文件与链接可机械确认；资料支持只限实际阅读范围；实际项目的收益与充分性仍待试用验证。

### 过程中查出并修好的 Windows 兼容缺陷（都只改自检夹具或环境假设，**没有放宽任何判据**）

1. `stdlib.GIT_HARDEN_CONFIG` 里四项取值是空串：Windows 上 `os.environ[k] = ""` 不会传给子进程，`GIT_CONFIG_COUNT` 却照旧，git 报 `missing config value` 整条命令失败，使九项检查器自检全记未定。改取 `true`（语义同样是「不执行被扫方指定的程序」）。
2. `linkcheck.py` 的仓根路径是 git 返回的正斜杠形式，与反斜杠路径做 `commonpath` 比较恒不等，把全部 6812 条链接判成「越出仓根」；先 `normpath`。
