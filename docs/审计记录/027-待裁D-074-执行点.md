### 2.2 历史重放：28 次提交逐笔重跑（本文新增的证据）

上一节是"清单怎么说"。本节问的是另一个问题：**如果这个钩子从第一天就装着，本仓库 28 次提交里有几次会被它挡下来？**

方法（可复跑，不碰 `.git/`，用 `git archive` 导出各提交的树到仓库外的临时目录，并用**该提交自己那一版脚本**跑**该提交自己的树**）：

```bash
W=$HOME/hp
for c in $(git log --format=%h --reverse); do
  rm -rf $W; mkdir -p $W; git archive $c | tar -x -C $W >/dev/null 2>&1
  cf=$W/docs/附录-载体实例/check_normative_force.py
  lf=$W/docs/附录-载体实例/linkcheck.py
  r1=none; r2=none
  [ -f "$cf" ] && { (cd $W && python3 "$cf" >/dev/null 2>&1); r1=$?; }
  [ -f "$lf" ] && { (cd $W && python3 "$lf" . >/dev/null 2>&1); r2=$?; }
  echo "$c checker=$r1 linkcheck=$r2"
done
rm -rf $W
```

**读数**：

| 脚本 | 存在于几次提交 | 退出非零（会被钩子挡下）的提交 |
|---|---|---|
| `check_normative_force.py` | 28 / 28（含基线 `78664b0`） | **0 次** |
| `linkcheck.py` | 21 / 28（`3c330e8`「链接自检固化为脚本」起） | **2 次**：`e577caf`、`aab03ab` |

**那 2 次是什么？逐条看，两次全部是误伤，一条真缺陷都没有。**

`e577caf`（14 条）与 `aab03ab`（9 条）报出的断链，**无一例外是指向下一笔提交才加进来的文件**：

### 2.5 一个有具体日期的失效模式（本文新查出，各路材料均未提）

**实测输出**：`exit = 1`，findings 含「D-057（试行）已于 2026-12-03 到期，按 D-014 §6 自动退回「提议」，须从生效登记表移除或重新批准」。

> **推论：若挂上钩子，本仓库从 2026-12-04 零点起无法提交任何东西**，直到有人重新批准 D-057、或把它从登记表移除、或每一笔都 `--no-verify`。

**这不是脚本的 bug，C3 报得对。** 问题在于：把一个**带日历触发的检查**放上必经路径，等于给仓库装了一个**没有人排过期、也没有人被通知**的定时停机。[31 §2 P4](../31-守卫与权限边界.md) 要求 Gate 合同写明「**失败后的去向与屏障范围**」与「**谁能限时豁免、何时自动失效**」——**这一格今天是空的，而它有一个确定的到期日。**

## 3. 「少就是多」这一格：有没有比挂钩子更少的做法

### 3.1 先把判据说清楚——这是本条的核心

[31 §2 P1](../31-守卫与权限边界.md) 逐字：

> **P1 约束力由两个独立维度决定，据此分四级。** 两个维度是：检查是否自动进入必经路径；失败是否改变后续状态。只写在指令里的是提醒；写成程序但要执行者想起来运行的是工具；自动运行而失败仍可继续的是警告；只有自动运行且失败使下一步无法进行的才是约束。更强烈的措辞不构成任何一级。

**注意一处必须写明的引用事实**：「**动作空间被该通道穷尽**」这句话——D-064、C-041 与 [审计 023 §2](023-执行清单-冻结版.md) 都拿它当判据用——**不在 31-P1 的正文里**。现跑 `grep -c "动作空间" docs/31-守卫与权限边界.md` → **0**。它出自 [015 §2.3](015-图工程三原则综合审计.md) 的 **B-1 拟增文本**，逐字是：

> 「'自动进入必经路径'以**动作空间被该通道穷尽**为前提；存在一条绕过该通道的写入路径时，本级不成立」

而 B-1 的状态：[D-065](../决策日志.md#decision-index) 逐字判它「**推后，不是被否**」，并逐字写着「B-1 的措辞依赖试点结果，而试点（D-068）的判据本身未定」；[D-073](../决策日志.md#decision-index) 逐字收尾：「**D-065 的 B-1 也压在这里等**」。

**这产生一个必须写下来的后果：**

> **D-074 的整个收益命题——"能把「警告」级从空集变成非空的唯一动作就是这一行配置"——是用一条尚未裁定的判据算出来的；而按那条判据的拟定原文，pre-commit 钩子恰恰不成立。**

理由是两条独立的绕过写入路径，任一条都足以让"穷尽"不成立：

1. **`git commit --no-verify` 是一条不需要改任何配置的绕过路径。**
2. **更要害的是：本仓库的权威状态是工作副本，不是提交。** 本轮的十五项工作、三路执行前审计、以及被 §2.2 重放挡下的那批产出，**在被提交之前就已经是仓库的事实内容**；[021 §6](021-执行前审计-删减路.md) 第 15 项自己就在处理「**第二十四/二十五轮已完成、仍未跟踪的产出**」。**"改这个仓库"的动作空间远大于"提交"，`pre-commit` 只覆盖它的一个出口。**

**按 31-P1 当前正文（无穷尽前提）**：钩子自动运行，失败使提交无法进行 → 落「**约束**」级，或因 `--no-verify` 可继续而落「**警告**」级。**这两读给出不同的级，而选哪一读正是 B-1 要裁的事——按 [30 §2 P1](../30-验证与测试.md)「缺成立条件即记未定」，本文对"钩子落哪一级"记未定，不折算。**

**按 B-1 拟定原文**：不成立，**警告级仍是空集**。

### 3.2 逐个更少的做法

**做法 A · 在[仓库工作须知](../附录-载体实例/仓库工作须知.md)里写一句"提交前必须跑两个脚本"**

**它和钩子差在哪：差一整级，而且这句话已经写了。**

- **已经写了**：[§2 标题](../附录-载体实例/仓库工作须知.md)逐字「**两项自检（每次改完都要跑，都要 PASS）**」。这不是备选方案，是**现状**。
- **级别差**：按 31-P1，一句话是「提醒」级，脚本是「工具」级。**这两级的共同点是"绕过它不需要任何动作"**——[审计 023 §2](023-执行清单-冻结版.md) 逐字：「按「动作空间被该通道穷尽」的判据，**它们连"警告"级都不成立，因为绕过它们不需要任何动作**」。钩子把"绕过"的代价从 0 个动作抬到 1 个动作（敲 `--no-verify`）。**这就是全部差别，一个动作。**
- **而按 §2.1 的对账，这一个动作换不到任何一条 Case。** 八行「两项自检当轮 PASS」证明：这句话被遵守了，脚本被跑了，失败照样发生。**问题从来不在触发，在覆盖。**

**做法 B · 把两个脚本合并成一个入口**

- **省的是什么**：把"想起来跑两次"降成"想起来跑一次"。
- **级别不变**：仍是「工具」级，一格没动。
- **代价不是零**：[C-023](../失败Case清单.md) 逐字记过——两个脚本对同一件事数出不同结果，其处置里逐字写着「**未做的**：没有让两个脚本互相断言——**那需要一个共享模块**，当前三个脚本各自独立，先记着，等同型 Case 再攒一条再判」。**合并入口要么只是套一层 shell（省不到什么），要么就是那个共享模块（本仓库已判"再攒一条再判"）。**
- **判**：不解决本条要解决的问题（级别），而它自己那件事本仓库已经写明推后。**不推荐，也不反对——它与 D-074 不是同一件事。**

**做法 C · 用 git 的其他机制**

| 机制 | 相对 pre-commit 的差别 | 本文的实测判读 |
|---|---|---|
| `pre-push` | 只在推送时跑一次，看的是最终状态 | **按 §2.2 的重放，`e577caf` 与 `aab03ab` 那两次误伤全部消失**（最终状态 `a282e31` 是 0 断链）。**误报率从 2/21 降到 0/21，真阳性仍是 0/21。** 严格优于 pre-commit |
| `core.hooksPath` 指向一个被版本化的目录 | 钩子进版本控制，可被审阅、其缺失可被发现 | 修好了"钩子本身不可他证"这一半（[31 §2 P9](../31-守卫与权限边界.md)、[落地包 04 §1](../图工程落地包/04-接入与验收清单.md)），但**每份克隆仍要人手跑一次 `git config`，而那一步本身没有任何东西保证**——**递归回「提醒」级** |
| `pre-commit` 框架等第三方工具 | 引入依赖与配置文件 | 净增最多；且它把工具名与格式带进仓库，是纯粹的载体绑定 |

**做法 D · 什么都不做，把"警告级为空集"写进读数**

**它已经做完了。** [C-041](../失败Case清单.md) 与 [D-064](../决策日志.md#decision-index) 已经把这条事实登记完毕，并且 [D-074](../决策日志.md#decision-index) 行自己逐字写下了不做时的纪律：

> **若不开：「拦住 0 条」这一读数的成因保持为「没有任何自动执行点」，不得再归因于条文写得不好**

**代价为零，且它是本轮唯一已经兑现的动作。**

**做法 E · 本文提出的第五条：不动 git，把两个脚本并进那条已经存在、且已被证明有效的必经路径**

[仓库工作须知 §5](../附录-载体实例/仓库工作须知.md) 第 4 条已立为纪律：「**提交前，让一个独立执行者只读 `git diff`，逐条试图证伪其中的事实性断言与"已修 X"这类声称。**」它有两条别的机制都没有的性质：

- **它是全清单唯一一条把非机械失败当场拦住的机制**（[C-038](../失败Case清单.md) 逐字：「**是——这是本清单里第一条被非机械手段当场拦住的**」）；[022 §2.4](022-执行前审计-价值与顺序路.md) 判它对检验① 与检验③ 都是「**有（唯一已兑现的一项）**」。
- **它天然是他证的**——产出方不参与判定，符合 [落地包 04 §2.1](../图工程落地包/04-接入与验收清单.md) 的他证定义逐字：「**产出被验收对象的一方不参与判定，且判定所依据的信号不是由该方生成的文本**」。

**最小写法（+1 分句，落在该条已有的「给对抗者的话要写死两条」旁边）**：要求对抗者**在报告里附上两个脚本的实际输出**。

**它买到什么、买不到什么，必须诚实分开：**

- **买不到**：31-P1 的级。它仍是「提醒」级，警告级仍是空集，**不解决 D-074 字面上问的那件事**。
- **买到的是另一样东西，而且是 31-P9 真正要的那样**：脚本"有没有真的跑过"从**执行者自报**变成**第三方可见**。[31 §2 P9](../31-守卫与权限边界.md) 逐字：「**机制是否生效以运行时观察为准，不以执行者自报为准**」。

**这里有一处本文认为最值得写下来的区分**：

> **钩子提升的是「级」，不提升「他证性」**——`.git/hooks/` 不版本化，谁也验不了它今天还在、还是被谁删了。
> **做法 E 提升的是「他证性」，不提升「级」。**
> 而按 [落地包 04 §1](../图工程落地包/04-接入与验收清单.md) 的接入门槛（他证验收信号 + 空转信号，缺一记未定），**钩子过不了这道门槛，做法 E 过得了。**

## 4. 「好设计 vs 修修补补」这一格：钩子会不断长大吗

### 4.1 直接回答：**钩子本身不会长大，长大的是检查器，而它长不长大与挂不挂钩子无关。**

钩子是两行调用，加一条检查不需要改钩子一个字。**这一格上钩子是清白的。**

### 4.2 但检查器的结构决定了加检查的成本，而这个成本已经不低

现跑度量：

```bash
f=docs/附录-载体实例/check_normative_force.py
wc -l < $f                       # → 312
awk '/^def main/,0' $f | wc -l   # → 224
grep -c "rglob\|ROOT.glob" $f    # → 5
```

**结构读数**：C1～C10 全部内联在同一个 224 行的 `main()` 里，按顺序排下来；没有检查注册表、没有单检查开关、没有随文件走的自测；全仓遍历 5 处（其中 `rglob("*.md")` 两处，C8 与 C10 各走一遍）。**加一条检查 = 在 `main()` 里再内联一段 + 多半再加一次全仓遍历。**

### 4.3 真正的成本不在行数，在本仓库自己测过的那条读数

[失败 Case 清单读数三](../失败Case清单.md)逐字：

> **三、写检查器本身出缺陷的频率高于写规则，而且缺陷形态是"能通过但不检查"。**

已登记的检查器自身缺陷：[C-006](../失败Case清单.md)（C7 正则混进不可见退格符，恒不匹配、永远通过）、[C-011](../失败Case清单.md)（C10 误伤举例）、[C-016](../失败Case清单.md)（linkcheck 现写版忘排除 `.staging/`，40 条假断链）、[C-022](../失败Case清单.md)（C5 只认括号形态，漏了四轮）、[C-023](../失败Case清单.md)（两脚本口径不同）、[C-037](../失败Case清单.md)（C5/C6 扫描面漏掉 8 个文件的 front matter，今天仍 PASS）。

**把它放上必经路径，两种缺陷形态的后果都被放大：**
- 「恒为通过」型（C-006 形状）：**钩子给它盖上一个绿章**——每次提交都 PASS，看起来这条检查在工作。这正是 [31 §2 P9](../31-守卫与权限边界.md) 与 [落地包 05 §4.5](../图工程落地包/05-图形态工作流落地规范.md) 反复要防的「锚点恒为绿，因为它根本不检查（[C-006](../失败Case清单.md) 的形状）」。
- 「误伤」型（C-011、C-016 形状）：**从"重跑一次"升级为"活干不下去"**。§2.2 的 2/21 就是这一形态的实测。

### 4.4 这一格的判定

**钩子不是一个会不断长大的东西**（正分）。**但它是一个会把已有毛病的后果放大的东西**（负分），而本仓库对"已有毛病"有六条书证。

**并且它引入一处真正的"修修补补"结构**：按 §2.4，装上它就欠 31-P4 的十二项合同、31-P9 的失效探测、31-P10 的豁免留痕。**这三样都是要逐轮维护的记账**，而 [022 §3.1](022-执行前审计-价值与顺序路.md) 第 5 条逐字判过本仓库的病灶位置：「[015 §3.2](015-图工程三原则综合审计.md) 已判「**修修补补发生在账本层与记账层，不在条文层**」……**在一个已诊断出"记账层过重"的仓库里，本轮的六项记账工作是在给病灶加料，不是治它。**」**挂钩子会新增第七项记账。**

## 5. D-020 那一问：给本仓库自己挂 git 钩子，算不算违反？逐字答案

### 5.1 答案：**不算。但"不算"的成立条件很窄，而且真正的价签不在 D-020 那一侧。**

### 5.2 逐字依据

**第一步，看 D-020 的 blocks 是怎么写的**（[生效登记表](../决策日志.md#effective-register) D-020 行，逐字）：

> **在本仓库全部规范正文内**：阻止载体绑定内容进入正文；阻止未通过两种机制类型检验的候选进入正文；阻止只举一种形态的探测提示；阻止在规范中维护各工具映射表；阻止把附录载体实例引用为落地要求

**五条 blocks 的对象全部是"正文"或"规范"，一条也不是"维护者的动作"。** 这不是本文的读法，是本仓库已经裁过的：[C-026](../失败Case清单.md) 逐字记着这条区分——

> 现有先例是分开的——D-014、D-015 是元治理与载体类才写 `repo:...`，D-020、D-043、D-047 是内容类、写"本仓库全部规范正文内"（**约束文本能写什么，不约束维护者做什么**）

**第二步，看 [09 §3](../09-跨工具通用性.md#criteria-which)。** 它确实把「**具名机制（钩子事件名、命令名、子代理名、工具名）**」逐字列为载体绑定的常见伪装形态——**但那一节的标题逐字是「判据三：这句话是语义还是载体」，它判的是"这句话"，即候选条文。**

**第三步，看 [09 §8](../09-跨工具通用性.md#carrier-instances) 给载体实例定的位置**，逐字：

> 移出正文的载体绑定内容进入[附录·载体实例]，其效力为**零**：不阻断、不授权、不构成落地要求。
> 载体实例的唯一作用是充当**可行性证据**与**反面参照**……**附录整体删除不影响规范。**

**本仓库已经有一整柜这样的东西，而且就是这两个脚本本身**——[附录 README](../附录-载体实例/README.md) 逐字给 `check_normative_force.py` 填的"绑定的载体假设"是「Markdown 文件 + 文件头 `governed_by:` + Git 仓库 + Python 运行环境」，"换工具后是否失效"填「**是**」。**脚本本身就是一个已登记的载体绑定物，而它的存在从未被判为违反 D-020。** 一个调用它们的钩子，与它们同族。

**第四步，[09 §7](../09-跨工具通用性.md#no-mapping-table) 给了自检信号**，逐字：

> 推论：本规范**不因某个工具的约定变化而需要修订**。若某次工具变化迫使正文修改，说明该处正文本来就是载体绑定，应按判据三移出。**这是本规范通用性的自检信号。**

**这条给出了"不算违反"的可执行判据**：挂钩子若不迫使正文改一个字，就没有触碰 D-020 的任何一条 block。

### 5.3 逐字答案（可直接引用）

> **给本仓库自己挂一个 git 钩子，不违反 D-020——只要同时满足三条，任一条不满足即违反：**
>
> **①（对 blocks 第 1 条）正文十四章与元治理两章零改动。** D-020 的五条 blocks 全部以「在本仓库全部规范正文内」为作用域，而钩子不是正文。可复跑的证伪命令照抄 [D-070](../决策日志.md#decision-index) 的形态：`grep -rn 'pre-commit\|hooks' docs/[1234][0-9]-*.md docs/0[89]-*.md` **返回非空即违反**。
>
> **②（对 blocks 第 5 条）钩子登记为载体实例、效力为零，不得被任何一处引用为落地要求。** 按 [09 §8](../09-跨工具通用性.md#carrier-instances)「附录整体删除不影响规范」——**删掉这个钩子，规范必须一个字都不用改。**
>
> **③（对 [09 §7](../09-跨工具通用性.md#no-mapping-table) 的自检信号）它不得迫使正文修订。** 若哪天"因为我们挂了钩子，所以正文这句要改"，按 §7 那一处正文本来就是载体绑定，该移出——**不是钩子该留。**

### 5.4 但真正的价签不在 D-020 那一侧，必须一并写明

**D-020 管"能不能写成这样"，D-057 管"写了之后谁被约束"**（[09 §9](../09-跨工具通用性.md#relation-d014) 对 D-014 的分工逐字：「D-014 规定一条规则**是否生效**，D-020 规定一条规则**能否写成这样**」）。

**挂钩子在 D-020 这一侧是自由的，在 D-057 这一侧是要付钱的**——它给本仓库造出第一个 Gate 实例，31 章十条原则随即生效并约束本仓库自己（§2.4 已列价签）。**若有人只查 D-020 就放行，会漏掉全部成本。**

## 6. 人侧排除：那句话的语境现在还成立吗

### 6.1 先按 [D-042](../决策日志.md#decision-index) 标证据等级

**换句话说：当初那句排除的表层理由（"要写代码"）今天不再成立，但它挡住的那个风险（"机制上得早会锁死没想清楚的东西"）今天比 2026-09-02 更清楚、更可量化。**

**这不是替他改主意，也不是替他维持原判**——是把两侧摆平：**若他当初排除 hooks 是因为不想写代码，那个理由没了；若是因为不想过早上机制，那个理由今天有了三条书证。** 哪一个是他的本意，本仓库内**没有书证可判，记未定，不折算**。

## 8. 按最高原则排序的裁定与推荐

**Alan 的排序**：以行业标准规范推荐 > 少就是多 > 优先用好的设计避免不断的修修补补。

**第一格 · 行业标准规范推荐**：pre-commit 钩子跑 lint 是行业通行做法，**这一格支持挂**。但行业做法的前提是"检查能查出真缺陷"，而 §2.2 实测本仓库的真阳性是 0、假阳性是 2。**行业标准推荐的是"把已被证明有效的检查自动化"，不是"把一个从未拦住过东西的检查自动化"。这一格判：中性偏支持，但支持的对象是"有效的检查"，本仓库的两个脚本在实测上不是。**

**第二格 · 少就是多**：选项四 +1 分句、零新工件、零 `.git/` 改动；选项一零动作。选项二三是"一行配置"这个标价，而 §2.4 实测真实价签是一行配置 + 三样不存在的东西。**这一格明确支持选项一与选项四，反对二三。**

**第三格 · 好设计 vs 修修补补**：选项二三把一个"绕过要一个动作"的通道装在一个"权威状态是工作副本"的仓库上，且引入日历定时停机（§2.5）与第七项记账。选项四用的是已经存在、已被证明有效、且天然他证的通道。**这一格明确支持选项四。**

### 推荐

> **推荐组合：主裁「不挂」（选项一），并配一条选项四的 +1 分句。**

**理由，每一条指向本文一处现跑结果：**

1. **本条价值命题的唯一硬证据是零**（§2.1）。41 条 Case 里没有一条满足"这两个脚本本来就能查出、只是当时没人跑"，八行「两项自检当轮 PASS」是它的反证。按 §0 写下的判据，**这不是"证据不足"，是"判据判成了不成立"，不折算。**
2. **28 次提交的重放里，它的每一次阻断都是误伤**（§2.2）。真阳性 0，假阳性 2，而那 2 次挡的是本仓库自己定的"拆两笔提交"纪律。按 [31 §2 P3](../31-守卫与权限边界.md)（误报率约束数量上限）与 [33 §2 P9](../33-评估与演进.md)（频繁误伤是 Thin 信号），**它在装上之前就已经是 Thin 候选。**
3. **它唯一的正分（造出 31 章实例）自带四样代价，而"一行配置"这个标价把它们全省略了**（§2.4）。脚本作者自己在文件头逐字写过「**这是 checker，不是 Gate。把它接成阻断需要单独的 Gate 决策（D-018）**」，而 D-018 至今是`提议`。
4. **它有一个确定日期的停机**（§2.5）：2026-12-04 起 C3 必报 D-057 过期，退出码 1。**在一个还没写 Gate 合同、没定失败去向、没定豁免制度的仓库里装一个带日历触发的阻断，正是理由 ③ 当初要防的那件事。**
5. **人侧排除仍在，且它挡住的风险今天证据更足**（§6.3）。表层理由（"要写代码"）过期了，实质风险（"过早上机制会锁死没想清楚的东西"）拿到了三条新书证。
6. **而"级"这件事，选项四买不到——本文不掩饰这一点。** 若 Alan 要的就是"让警告级非空"，那么**只有选项二三做得到，且必须连同 §2.4 的四样代价一起批**。本文的判断是：**在真阳性为 0 的前提下先买"级"，是先装门后找锁。**

### 若裁准要挂，本文建议的最小形态与前置

**这一段不是推荐，是"若裁准"的最小写法**（照 [021](021-执行前审计-删减路.md) 的降档形态）：

1. **改 `pre-push`，不用 `pre-commit`**——§2.2 实测误报从 2 降到 0，真阳性不变。
2. **先处理 2026-12-04**：或在钩子里把 C3 的到期发现降级为不阻断，或先裁 D-057 的续期。**不处理即等于给仓库设了一个无人值守的停机日。**
3. **先补 [31 §2 P4](../31-守卫与权限边界.md) 的 Gate 合同**，至少写死其中三项：失败后的去向与屏障范围、谁能限时豁免与何时自动失效、怎样发现误阻断与静默失效。**这三项正是本文查出的三处空缺。**
4. **配一条不由钩子自己产出的失效探测**（[31 §2 P9](../31-守卫与权限边界.md)、[落地包 04 §1](../图工程落地包/04-接入与验收清单.md)）：最省的形态是把"钩子在不在、上次跑于何时"并入选项四那位对抗者的必答项。
5. **同时执行选项四**——它便宜、独立、且是本仓库唯一已兑现的拦截机制。
