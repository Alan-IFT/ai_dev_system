## 3. 最难堪的三条，都是我前一天写的

1. **C-031 的处置栏两句都不成立**：它声称"PROJECT_STATUS 的当前风险整节重写为不含测得数"——而宣布这件事的那句话**自己列了十个测得数**；它声称"断言本身错的重写"——而[仓库工作须知 §4](../附录-载体实例/仓库工作须知.md) 至今写着"永久豁免从 72% 降到 35%"，**两个数都错**（84 是 127 里的 84 = 66%；终值复算为 40 条 = 34%）。
2. **C-032 把空缺划小了**：§3 九条读数在同一次提交里被整体重写，**第一次核查读的是旧文本**；读数十从未进过任何一格；§4、front matter、§2 表头同样无人负责。它说的"抽查两行即得两处错"里**只有一处成立**。
3. **C-034 的等级挂 A，而承重的那句在 git 里零书证**——"按合同加载过的运行只有第十二、十四两轮"只有作者自述，且它在仓库里的三处载体全部出自同一次提交。**已降为 B，字面量已删。**

## 4. 又有一组退化成了对账——上一轮的教训没吃透

明令"不许拿仓库内散文数字当基准"之后，**仍有一组把"两处副本"这个数从被查的 Case 行里搬过来当结论用**，没有自己枚举。实扫是**三处**（合同第 13、15、49 行），front matter 还有第四处 C5 至今认不出的形态。后果是实质的：它据此判 C-032 的第二处指控不成立，**等于替一条另一组已经证伪的断言背了书**。

另有两处较软的同类：两组以作者本人的散文自述作最终判据，而另外两组对结构完全相同的证据判"不可判定"——**同一批证据在四组手里适用了两套标准。**

## 5. 结构性的三条

- **§5「处置只有四种」是枚举，而 34 行里 24 行落在它之外**。这违反本仓库自己的硬规矩"判据优先于枚举"。尤其**"已修…未加检查"这一档实际含义是"未处置，已登记"，而表把它读成"已修"**——已改为按判据写。
- **§5「本清单只增不改」已被推翻**：已登记行被就地改写过六次、涉及四行，本轮又改七行。改为"只增不删"，并要求改写时在行内标出改了什么。
- **等级 B 的四条至今无一条注明"为什么没进提交"**，而 §5 明文要求。
- **C-007 六格无一站得住**，批评者判它最该作废：18 条边与 25 处违规复算不出（入库三份图是 12/15/15），规则点名与失败无因果，B 档没写理由，处置是"无需处置"。**本轮未作废**——需要先给"登记错了"定一档处置。
