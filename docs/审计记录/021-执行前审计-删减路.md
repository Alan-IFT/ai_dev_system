**读数 B · 本仓库的自动化面（命令 9）——这是本文最重要的一条现跑结果**

按 [31 §2 P1](../31-守卫与权限边界.md) 的四级逐字（「只写在指令里的是提醒；写成程序但要执行者想起来运行的是工具；自动运行而失败仍可继续的是警告；只有自动运行且失败使下一步无法进行的才是约束」）：

| 级 | 本仓库的实例 | 数 |
|---|---|---|
| 提醒 | 正文 117 条 + 全部散文纪律 | 117+ |
| 工具 | 三个脚本，全部靠人想起来跑 | 3 |
| 警告 | —— | **0** |
| 约束 | —— | **0** |

**这一格顺带推翻 [015 §2.4](015-图工程三原则综合审计.md) 预写的后半句。** 015 逐字预期：「31-P1 的"约束"级对条文**结构上不可得**，而**对检查器可得**。」前半句成立；**后半句不成立**——本仓库没有任何 hook、没有任何 CI，三个脚本与条文一样需要人主动发起，按 P1 的定义同为**工具级**。要让它们升到约束级，缺的不是脚本而是一个自动入口，而那件事在本仓库内做得到（一个 pre-commit hook）却从没有人做。**这是 C-1 盘点的全部答案，四条 `ls` 就得出，不需要一次事实型运行。**

## 3. 三处必须单独写清的发现（本轮新出，019/015/005 均未登记）

### 3.1 B-2「验证者的默认判决是否定」与 30-P1 的三态纪律相撞

30-P1 现文逐字：「**每层输出三态，未定不得折算。** 三态是通过 / 失败 / 未定（UNDETERMINED）；未定至少含未执行、无法核验、结果未知、生成者与验证者同一四种子原因……**含未定层的完成判定为未定，必须停止并报告**」。

**"默认判决是否定"这句话有两种读法，后果完全不同：**

- 读作**判决态**（起始态 = 失败）：与 30-P1 直接冲突。30-P1 规定的起始态是**未定**，且"未定不得折算"——把没验的东西预置成"失败"，是把未定折算成了一个结论，方向与"折算成通过"相反但错法同型。这一条同时违反 [00 §3](../00-总览.md#default-scope) 的「未执行与无法核验记为**未定**，不折算为通过」。
- 读作**姿态**（验证者的起始假设是"产出物有缺陷"，须由证据翻转）：不冲突，它约束的是验证者怎么读材料，不是三态的取值。原始支撑（Bun 官方博客：审查者「只拿到 diff，被告知假定代码是错的」）说的正是姿态。

**处置**：若落，必须写成姿态而非判决态，措辞近似「验证者的起始假设是产出物未通过，翻转须由证据完成；这不改变三态取值，未验部分仍记未定（[30 §2 P1](../30-验证与测试.md)）」。**按015 §2.3 原样落"默认判决是否定"六个字，会在 30 章内造出一条与 P1 相反的规则**——而 D-057 已让两条同时生效，按 [08 §8](../08-规范效力元治理.md) 是"两条生效规则在同一 scope 内给出相反判定"，须失败关闭。

### 3.2 D-066 第 11 项「控制流不得来自记忆内容」与 12-P5 表面相反，须先登记冲突

12-P5 现文逐字：「条目携带置信态与使用方式……**强可驱动执行**，弱只提示风险，影子只助发现与背景召回、不得单独作为执行依据」。

第 11 项的表述是「记忆只能改变'我知道什么'，**不能改变'我这一轮该做什么'**」。

两句在字面上给同一个对象（记忆条目）相反的授权。我判它们**语义上可以并存**（12-P5 说的是"作为依据的强度"，第 11 项说的是"作为指令的资格"——防的是提示注入经记忆持久化后跨会话生效），**但正文里没有任何一句把这两层分开**。按 [11 §2 P1](../11-项目知识.md)「同一主题的意图、源定义……可以同时正确」的处置形式，**落第 11 项之前须先登记这处冲突并写明分层**，否则落下去就是一条与 12-P5 字面矛盾的新条文。

**019 待裁二推荐 A（两条都接受）时没有对 12-P5 现文做这次比对**，这是本文对 019 的一处补正。

### 3.3 删 99 行强度表会直接打断检查器 C7

命令 6 现跑：
```
awk '强度表区内' | grep -cE '^\|\s*P[0-9]+\s*\|'   →  117
grep -cE '^\|\s*P[0-9]+\s*\|' docs/追溯账本.md      →  117
```
**两个数相等，说明追溯账本全文的 `| Pn |` 行全部落在「各条原则的证据强度」表内，没有第二张同形状的表。**

**而账本自己在 §1 第 24 行逐字声明了这条硬约束**：「本文与正文之间只有一条硬约束：**每条原则在本文中有且只有一条强度记录，编号与正文一致**……改动一条原则的编号或增删原则时，本文同步更新；**对不上即为待修复缺陷**。」——**删掉 99 行不只是打断一个检查器，是直接违反被删对象所在文件自己声明的唯一硬约束。**

而 `check_normative_force.py` 第 210–236 行的 C7 逐字：
```python
in_body   = re.findall(r"^- \*\*(P\d+)", 正文, re.M)
in_ledger = re.findall(r"^\|\s*(P\d+)\s*\|", sec, re.M)
miss = [x for x in in_body if x not in in_ledger]
```
**C7 对账的就是这 117 行。** 按 [015 §2.3](015-图工程三原则综合审计.md) 的处置（"段首写一句'未列出者为一手多来源'，只留 18 行例外"），C7 会对十四章逐章报「正文有账本无」共 99 条。

**所以这处删除不是"−1,200 字符、零风险"，它同时要改一个检查器。** 而 [读数三](../失败Case清单.md)逐字：本仓库自写的检查已出 **3 处缺陷**，「**前两处"跑一遍看到 PASS"完全察觉不到**」。改 C7 必须走 [仓库工作须知 §2](../附录-载体实例/仓库工作须知.md) 的四步验收（验字节 / 注入前断言待替换串存在 / 反例测试 / 全仓看误伤）。

**016 已经点过这个位置的一半**（逐字：「**D-069** 捆了两处删除，检验列只写了 25-P3 那半……**99 行强度表那半没有检验**」），但它给的补法是"删后若 grep 出任何一处引用该尾标的活文档，即回滚"——**那条补法查不出 C7 这个依赖**，因为 C7 引的不是"尾标"这三个字，是 `| Pn |` 这个行形状。
