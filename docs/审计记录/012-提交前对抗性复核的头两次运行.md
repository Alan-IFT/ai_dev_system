# 012 第二十三轮：提交前对抗性复核立为纪律——三次运行，每一次都把前一次的修补拆了

状态：证据材料。效力为零。不在默认上下文内。

> **本记录的成立条件与前十一份不同**：§2、§3 的判定由**独立执行者**产出，且它们查的是我**尚未提交**的 diff。§5 的处置与解释由被查方写，按未定读。

日期：2026-09-04　运行类型：**交付型 × 从头**

## 1. 立了什么

[仓库工作须知 §5](../附录-载体实例/仓库工作须知.md) 第 4 条：**提交前，让一个独立执行者只读 `git diff`，逐条试图证伪其中的事实性断言与"已修 X"这类声称。**

依据是 [30 §2 P5](../30-验证与测试.md)（验证者独立于生产者，随 D-057 生效）。[Case C-025](../失败Case清单.md) 登记了本仓库生产与验证是同一方，但它标"已修"的只是 [30 §2 P1](../30-验证与测试.md) 的未定标注那一侧；P5 要求的结构性分离此前**只逐轮临时做过**（[009](009-默认加载集的体量与片段外延.md)、[010](010-标准结论的独立重算.md)、[011](011-源表的独立核查.md)），从未固化成每次提交都跑。

## 2. 第一次运行：13 行的 diff，报出 14 条，8 条证伪

被查的正是**采纳这条纪律的那次改动**。它拆掉的是这条纪律自己的论据：

| 被证伪的 | 实测 |
|---|---|
| 那条专门防"抄数"的规则**自己写了十余个当前状态的计数字面量** | 同一形状的第三次（前两次：第十一轮、第二十一轮） |
| 「查出 N 条不属实」把 `已过期` 与 `不可判定` 折算进了"不属实" | **违反 [30 §2 P1](../30-验证与测试.md)「未定不得折算」**；写下时就错的是 24/139 与 23/112 |
| 「两次**全量**核查」 | 两次都不是全量——正文一条没碰 |
| 「成本是全量的二十分之一」 | 给出的区间没有一端等于 1/20，且是**零测量的预测** |
| 「三次同形复发…已两次；八次」 | 2+8 怎么读都不是 3 |

它也**如实报了证伪不掉的**：30-P5 那句引文逐字符核对通过，且它自己独立导出章号复核了生效性。

## 3. 第二次运行：改完再跑，又把第一次的修补拆了

这一次的发现比第一次更要害：

1. **「第 4 条现含零个计数字面量」→ 证伪，实为十余个。** 我的自查正则只认阿拉伯数字，**漏掉了中文数词**——用来验证"已修"的方法本身是错的。
2. **「折算口径已在读数十与 PROJECT_STATUS 一并更正」→ 证伪。** PROJECT_STATUS 两处、Case 表 C-035 一处都没改。**这正是 [C-031](../失败Case清单.md) 登记的"声称已修但没修"，隔一轮又犯。**
3. **读数一插入了更正，却留着被更正的那句**（"无一例外是程序"紧接其后，"这一列至今仍全是机械检查器"原封未动，粗体标题也没改）。
4. **「P5 至今没有处置」→ 证伪**：009 自己写着"这是本仓库第一次真正满足 30 §2 P5"。正确说法是"只逐轮临时做过，从未固化"。
5. **标题「第 1～3 条 2026-09-03 立」→ 证伪**：第 3 条是 2026-09-04（`74be133`）。**我把一处模糊表述锐化成了一个可证伪的错。**
6. **「下面三条」**——我加了第 4 条却没改引导句，缺陷完全在 diff 内。
7. **「逐条清单见 010、011」→ 证伪**：两份都没有逐条留档，010 §6 自己写明"未逐条复核"。
8. **「那条就引在同一段下面五行」→ 点名指错**：第一版 diff 里根本没引过 P1。**这是我转述上一个对抗者的结论时改坏的**——[自指风险三](../../PROJECT_STATUS.md)（转述失真）的又一实例。

## 3.5 第三次运行：只问"兑现了没有"，10 条裁定 5 条真兑现

第三次只查一件事：第二次的每条裁定有没有真被兑现。结果**5 条已兑现、3 条部分兑现、1 条有残留、1 条完全没动**。

**而核心缺陷与第二次一模一样，只是换了位置**：我在[仓库工作须知](../附录-载体实例/仓库工作须知.md)与本记录里都改了口，**却把第二次判为假的那两句原样搬进了 [PROJECT_STATUS](../../PROJECT_STATUS.md) 新增的那条记录**——"第 4 条现含零个计数字面量"与"P5 结构性分离此前从没处置过"。**即在宣布修好它的同一次提交里，重新发布了被裁定的错误陈述。这是"声称已修但没修"的第三次复发。**

它还查出三处**改的过程中新造的**缺陷：本记录 §4 由自己那张表导出的"低约一个数量级"算不出来（六个两两比值是 5.1～10.4，009 那档只有 5 倍多）——**与第一次报出的"算不出二十分之一"是同一种缺陷，而本记录正是记录那条裁定的文件**；另有两处加粗不闭合、一处重复链接。全部已修。

## 5. 处置

按两次裁定逐条改写；**不再写"零个""已修"这类无法复跑的断言**——凡声称已修，要么附一条可复跑的命令，要么写明"未验证"。

**没有追求"改到对抗者一条都报不出"**：第二次运行剩下的 `存疑` 项多为口径未定义（"十四个"算不算一个判据、"27 条"的分母），追下去会变成新一轮的数字纠缠。**这些如实留在 [C-038](../失败Case清单.md) 里，不在正文中复述。**

## 6. 这两次运行本身说明了什么

- **纪律有效，而且第一次就自证**：它拆的是采纳它的那次提交。
- **第二次比第一次更重要**：它证明了"我改完自查一遍"不足够——**自查用的方法本身可能是错的**（漏中文数词），而"已修"是本仓库最高危的一类句子。
- **成本可承受**：一次约十万 token，是深度核查的 1/5～1/10（见 §4；不要写成"十分之一"），可以每轮跑。
- **它抓不住存量**：不在 diff 里的旧错（如 C-001，落在上千文件、两百多万行的基线提交里）只能靠深度核查。**分层不变：对抗者管新增，深度核查管存量。**
