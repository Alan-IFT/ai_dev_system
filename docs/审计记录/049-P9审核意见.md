这不是形式问题。删 `check_adoption` 直接推翻的是 **D-088**（`docs/决策日志.md:123`）里那句**已裁决**的话：

## 二、五个问题的明确结论

### Q1 · `check_adoption`：**两条实测都成立，但结论是"改小"，不是"删"。**

我复现了两条：

- 在一个全新空仓（只有 `governance/project.yaml: tier: L0` + `git init`）里放一份格式正确的
  `STANDARD_VERSION`（`1.0` + `adopted_at`），得到 **2 PASS + 1 UNDETERMINED**，没有 FAIL。
  删掉该文件，得到 **1 FAIL + 同一条 UNDETERMINED**。审计的两条断言都对。
- 那条 UNDETERMINED 的内容是 `标准/README.md` 与 `CONTRACT.md §5` 关于"裁剪登记记在哪"的互相矛盾，
  由 `_tailoring_undetermined()` **无条件追加**，被扫项目做任何事都消不掉它。

**"一个工具把自己文档的内部矛盾报成对被扫项目的发现"——算不算缺陷？算，而且是重的一类。**
按契约 §4「`why` 必须能追到标准的具体条款，追不到的检查项不进本工具」，这条的 `why` 追到的不是
被扫项目违反了什么，是**工具自己的上游没调和**。按 §5.6 的违规三层定位，它属于第①层
（没有这条规则——因为两份上游相反，规则还不存在），处置是**补/调和规则**，不是往每份报告里塞一条未定。
它还违反 M-07：已知易误报（这里是"已知恒定命中且被审计方不可能修"）的规则不做输出，
"误阻断的代价不是浪费一次提醒"。

**但删掉整个检查器是过度反应。** 拆开看，`check_adoption` 是两样东西缝在一起：

| 部分 | 行数（实测） | 判定 |
|---|---|---|
| 存在性 + 版本值 + 采用日期三条判定（含"不与工具常量比对"的变异验证） | ~208 行 | **留** |
| `_tailoring_undetermined` + `_TAILORING_KEYS` + 相关 scope 条目 | ~35 行 | **删** |
| 自检段 | 124 行（不是审计说的"另加 63 行"，见第三节） | 随之收缩 |

留的理由，逐条对着 M-08 的四个信号：
- **零消费**：不成立。它是 01 §8 第一条与 §4.7「标准升级」验收行（"`STANDARD_VERSION` 与差异记录一致"）
  在整套工具里的**唯一**机械执行点。全仓 grep 确认：除它之外没有任何代码读这个文件。
- **重复实现**：不成立。没有第二层。审计给的替代"`test -f governance/STANDARD_VERSION` 一行可得"
  **不是执行点**——01 §5.6 与 M-10 都写死了"靠执行者记得去跑的不计为闸门"。用它换掉检查器，
  是把一道闸门降级成一句提醒，正是 M-15 说的"层级判错则修改无效"。
- **频繁误伤**：成立，但只对那一条恒定未定成立，删那 35 行即消。
- **明显负收益**：不成立。它在空仓上给出 FAIL，那是一条真结论。

**"删了之后 `STANDARD_VERSION` 又没人读了，那当初为什么要建？"** —— 反过来问才对：
当初建它是 D-088 的**成立条件**。删它 = 撤销 D-088 的一半，而 D-088 的另一半（删 `project.yaml`
的 `standard_version` 字段）已经落地。只删一半，回到的不是删之前，是**比删之前更差**的状态：
字段没了，读取也没了，`governance/STANDARD_VERSION` 变成一份纯装饰文件。

### Q2 · `check_evidence`：**删早了。真实原因既不是判据错，也不是"还没建工作项目录"。**

我查清了。`NFBY-标准符合性报告.md` §2.5 白纸黑字写着：

> **NFBY 的工作项就在 `docs/features/<slug>/` 下**，而 `docs/features` 已按 §2.4 冻结。
> 如果把 `work_root` 指向 `docs/features`，……会因 frozen 跳过而一条对象都取不到……
> 因此本次**不配 `work_root`**。

也就是说：**NFBY 有工作项，192 个归档任务目录 + 12 个残留目录、`docs/features/**` 下 1529 个文件
（测绘 §1 实测），扫描者出于 frozen 语义冲突而有意没有指向它们。**"覆盖对象为零"是一次配置选择的结果，
不是世界的状态。用这个零去支持"删掉判据"，是把自己的取样决定当成了被测对象的属性。

本仓的情况不同也不更有利于删：`governance/project.yaml` 写了 `work_root: docs/state/work`，
而 `docs/state/` 根本不存在——**本仓自己的配置在说谎**（这条方案没列，见第五节）。

**第三条路已经在代码里了，不用新建。** `check_evidence._run()` 第 336–343 行：工作项目录不存在时
返回**一条显式 UNDETERMINED**，理由写着"项目可能还没建工作项，或 layout.work_root 配错；两者本工具分不出"。
这正是 P9 问的那条路。所以真正的取舍是：**为了保住"01 §4.2 证据六字段"这条 G4 核心规则的唯一机械执行点，
值不值得留 528 行、每次运行 0.156 秒（自检）+ 0.000 秒（run）。**

判定：**留，但必须同时修好触发条件**，否则它永远是那一条未定。要做的是两件小事，不是删 528 行：
1. 解决 frozen 与 work_root 的语义冲突——`frozen` 的语义是"不承担**更新**义务"（01 §3.1），
   而证据六字段查的是"**完成声明**成不成立"，跟更新义务无关。`check_evidence` 现在把 frozen 直接当跳过条件
   （第 352 行 `in_frozen` → `continue`），这是把 §3.1 的一条豁免搬到了一条它不适用的判据上。**这才是判据错的地方。**
   改掉之后 NFBY 就能配 `work_root: docs/features` 并真正取到对象。
2. 本仓要么建 `docs/state/work`，要么把 `work_root` 从 `project.yaml` 里删掉——现在这行是假事实。

删了以后 NFBY 建了再加回来？不会加回来。M-08 的沉淀阶梯是"文档 → Runbook → Skill/Script → Gate，不跳级"，
反向是没有电梯的：删掉的 528 行不会有人重写。P9 自己的开场白说得对——"删掉的判据不会再有人想起来"。

### Q3 · 角色表落地后的开箱体验：**不是"一屏未定"，是"一行未定"——问题恰恰相反。**

`check_layout._TIER_ITEMS` 是 `{role: (中文名, ★, 存在性判据, 候选路径列表)}`，L0 五项、L1 +3、L2 +6、L3 +3。
拿掉候选路径列后，未声明角色 → 按方案是**一条聚合未定**。所以担心的"一屏未定"不会发生。

真正会发生的是三件方案没算到的事：

1. **本仓当前的 3 条 PASS 会消失**（入口 `CONTEXT_MANIFEST.md` 在、状态 `PROJECT_STATUS.md` 在、
   元信息齐）。其中"状态"是靠 `layout.artifacts` 声明的，保住；"入口"靠 `layout.entry`，保住；
   其余靠候选命中的一律变未定。NFBY 的 2 条 PASS 同理。
2. **★ 工件的 FAIL 会退化成 UND。** 本仓现在有一条 `★ 验收 类工件缺失（acceptance）` 的 FAIL，
   `project.yaml` 里那句注释"acceptance 故意不填：本仓库确实没有验收条目工件，留着让它报 FAIL"
   就是冲着它写的。角色表落地后"不填"= 未定，这条**有意留下的真 FAIL 会静音**。
   要保住它，本仓得写 `acceptance: ACCEPTANCE.md`（指向一个不存在的文件）——即
   **"我没有这件工件"与"我没告诉你它在哪"被合并成了同一个输入**。这是 N1 最忌讳的那种合并，方向还反了。
3. **角色词表本身要留。** 契约 §5 明写"role 名见 `check_layout` 的 `_TIER_ITEMS`"。方案让
   `layout.artifacts` 成为唯一入口，同时把 `_TIER_ITEMS` 列进 20 张待删名字表——**这两条互斥**：
   删掉词表，`layout.artifacts` 就没有可校验的键空间，任何角色名都合法，判据也就绑不上任何东西。

**正确的改法是"删一列"，不是"删一张表"**：`_TIER_ITEMS` 里的 `role / 中文名 / ★ / 分档`
是 01 §3.1 的正文内容（哪几档该有哪些工件、哪三件是最小起点），**它不是名字猜测**；
只有第五个元素"候选相对路径"是猜测。删那一列，其余四列留下并在契约 §5 登记为角色词表。

**引导路径：不要加 `--init`。** 按原则一先问能不能不存在——答案是不能存在：
`CONTRACT.md §5` 已经有一段完整的示例 yaml，而且它被 `_contract_examples_selftest` 守着必然可解析；
本仓 `governance/project.yaml` 是第二份带注释的实例。再生成第三份骨架就是 N2 的副本。
要做的只有一件不加组件的事：那条聚合未定的 `reason` 里直接列出**本档缺哪几个角色名**，
并指到 `CONTRACT.md §5`。零新增。

### Q4 · 自检闸门移出普通运行：**否决。这条给硬结论。**

先核数，审计给的 63% 我复算过，**数对，但它是个百分比，掩盖了绝对值**：

| 项 | 实测（三次一致） |
|---|---|
| 普通运行总耗时 | **3.53 秒**（审计说 3.68） |
| 九个检查器的自检闸门合计 | **2.274 秒**（审计说 2.31）= 64% |
| 九个检查器 `run()` 合计 | **1.123 秒** |
| 身份取两次 + discover + load_config | 0.104 秒 |
| `--selftest` 全量 | **11.84 秒**、37 项、rc=0（审计说 12.4/12.5） |

**所以这条交易的真实条款是：用 2.27 秒，换掉一条已经抓住过 13 条假 PASS 的纪律。**
2.27 秒不是"明显负收益"，M-08 那个信号在这里根本不成立。审计报了比例而没报绝对值。

方案自己已经把否决理由写出来了——"身份哈希只能证明跑的是哪一版，不能证明那一版通过了自检"。
这句话是对的，而且比它看起来更严重：

- 契约 §3 的语义是"**没有反例测试的检查器，其结果记 `UNDETERMINED`，不记 `PASS`**"。
  这是一条**关于每次输出的**约束，不是关于代码库状态的约束。闸门只在 `--selftest` 跑，
  普通运行输出的 PASS 就不再有"这一版通过过反例"作为成立条件——**按 N1，它们全部应记未定**。
  把闸门挪走而继续输出 PASS，是把未定静默升格成通过，正是契约 §1 第一条禁止的事。
- 01 §5.6 与 M-10 的落点条款：**"检查是否自动进入必经路径、失败是否改变后续状态——
  靠执行者记得去跑的不计为闸门。"** 移出之后，"这套检查器今天通过过自检吗"取决于有没有人跑过
  `--selftest`。这不是弱化，这是**从约束降级为提醒**，是 M-08/M-10 两卡共同点名的那一类退化。
- `check_all.py` 里 `_gated_by_selftest` 的 docstring 自己写着"**禁止在这里做任何 memo / 缓存**……
  闸门就不再是'这次扫描前刚跑过'，而是'某一次跑过、且不知道是哪一次'"。方案要做的正是这件事，
  只是把缓存换成了人的记性——比缓存还弱。

**如果确实要省这 2.27 秒，有一条不放弃纪律的第三条路，约 30 行：**
把自检结果**绑在身份摘要上**。`--selftest` 通过后，在 `tools/std/` 下写一条
`<digest> ok <utc>` 的记录；普通运行算出当前 digest（现在本来就算两次），在记录里查：
命中 → 各检查器照常给 PASS，并在证据里写明"自检通过记录 digest=…, 时间=…"；
未命中或 digest 不同 → **全部检查器记未定**（就是今天闸门失败时的处置），并提示先跑 `--selftest`。
这样：① 每次运行都过一道机械核对，仍是约束不是提醒；② 改任何一个 `check_*.py` / `stdlib.py` /
`check_all.py` / `CONTRACT.md` 都会让 digest 变、记录立即失效，抓得住"改了没重跑自检"这个真实失效路径；
③ 普通运行降到 ~1.3 秒。记录文件不进 digest，所以不会自指；它与代码同一信任边界，可接受。
**注意这是加组件**，按原则一要先问能不能不存在——能：直接保持现状（3.5 秒）也完全可以接受。
所以我的建议顺位是：**首选什么都不做；次选上面这 30 行；绝不采纳方案原文的写法。**

（附一条：`_entry_smoke_selftest` 嵌套跑整轮 `run_all` 再跑两遍 `main` 导致 `--selftest` 11.84 秒。
这一项是可以单独优化的，且与闸门去留无关——嵌套那几轮里的闸门是"另一次扫描的闸门"，
docstring 已经解释过为什么不能消掉。要削就削嵌套层数，不要削闸门。）

### Q5 · `single-authority` 判据 3：**改小，不删。审计的"0 条被确认"是"0 条被人看过"，不是"0 条为真"。**

逐条对 M-08 的四个信号：

| 信号 | 判据 3 | 说明 |
|---|---|---|
| 长期零消费 | **不成立** | 它是全仓输出量最大的一项（31/43 条未定），不是没人看见，是没人裁 |
| 重复实现 | **不成立** | G2「同一数值出现在两处」在整套工具里只有它一个执行点 |
| 频繁误伤 | **成立，且严重** | 见下 |
| 明显负收益 | **成立** | 31 条里 20+ 条是噪声，把报告的未定区淹掉了 |

我逐条看了本仓那 31 条。**它们不是均质的噪声：**

## 五、别名判据（`repos[].former_names` + 全量 grep）：**可行，但 40 行不够，且按方案写法会变成下一台造未定的机器。**

### 耗时：取决于实现，差 600 倍，方案没写清是哪种

我在本仓（1513 个跟踪文件）实测三种写法：

| 写法 | 耗时 | 说明 |
|---|---|---|
| 方案原文的"全量 grep 全部跟踪文本文件"（逐个读、读完再判是不是二进制） | **31.81 秒** | 读了 547.9 MB。本仓 197 MB 是 `.html`（archify 产物）、178 MB `.png`、155 MB `.gif` |
| 先按扩展名跳二进制 + 单文件 2 MB 上限 | **0.05 秒** | 实读 596 个文件 / 33.9 MB |
| `git grep -l -I -F <name>` | **0.107 秒** | `-I` 自带二进制识别 |

**31.81 秒是当前整轮扫描（3.53 秒）的九倍。** 方案说"约 40 行、不新增机制"——
40 行里如果没有扩展名/大小过滤，这个检查器会成为整套工具里最慢的一项。
NFBY 四仓约 5600 个跟踪文件、体量更大，naive 写法只会更糟。**必须写死用 `git grep -I -F` 或等价过滤。**

### 误报：这才是真问题，量级 **≥88%**

按测绘 §1.6 的实测，NFBY 容器仓里 `NFBY_CMS/` 的命中分布：

| 类别 | 数量 | 是不是真问题 |
|---|---|---|
| 活引用（会改变机器行为）：`scripts/deploy-production.sh:89`、`scripts/systemd/nfby-backup.service:9,10` | **2 处** | **是** |
| 文档/工作区声明：`.gitignore:104-112`（把老仓登记为工作区成员的**唯一**声明）、三份决策文档的"复核命令"（**有意**拿老仓当冻结对照组）、`three-layer-architecture.md:1111` | 5 类 | **否，全是有意为之** |
| `docs/features/**`、`docs/batches/**` 归档文本 | **85 个文件** | 否 |

合计约 92+ 处命中、2 处真问题 → **误报率 ≥ 97%；即使加上 frozen 过滤挡掉 85 个归档，仍是 11 报 2 真、82% 误报。**

还有一个方案完全没提的坑：**`former_names: [NFBY_CMS]` 是三个在役仓名的子串**
（`NFBY_CMS_FullStack`/`_Backend`/`_Frontend`）。裸子串 grep 会命中**每一处**提到在役仓的地方。
测绘里那条命令写的是 `NFBY_CMS/`（带斜杠）正是为了避开这件事。
**别名匹配必须做路径分隔符/词边界锚定，否则第一次跑就是几百条。**

### 判定

这条判据**结构上与判据 3 完全同型**：机械判得出"这个名字出现在这里"，判不出"这处出现是不是缺陷"，
于是只能一律记未定。它就是审计第三章那个根因的第 8 次出现——**"标准的条款说的是角色，工具手上只有名字"**，
这次连"名字"都是旧名字。审计把它列为"唯一值得增加的东西"，但没有对它自己用第三章的判据。

**要做就必须先收窄到"确定事实"那一侧**（01 §5.6：判据是确定事实才做硬拦截，是代理指标最多做提醒）：

1. 匹配锚定到路径分隔符（`<name>/`、`/<name>`、`<name>.git`），不做裸子串。
2. 用 `git grep -I -F`，不做全量读。
3. **只对"会改变机器行为"的面做 FAIL**：`*.sh`、`*.service`、`*.timer`、CI 配置、`Makefile`、
   `*.py`/`*.js` 的**非注释行**。这一层在 NFBY 上正好命中那 2 处真问题，0 误报。
4. 其余全部命中（文档、`.gitignore`、注释、frozen 区）**聚合成一条 UNDETERMINED**，给计数与前 10 个位置。

这样写大约 **80~120 行**，不是 40 行。**在没收窄之前，不要把它加进来。**
另：这条与 `cross_repo` 现有的退役仓判据是互补的两半（那半查"退役仓自己的规则文件有没有标失效"，
这半查"别人还在不在指它"），放进 `check_cross_repo` 是对的，不必新建检查器。
