# 切片演练：维护期的计费规则变更 + 历史数据回填

演练性质：证伪。目标是找出理论接不住的地方，不是让切片走通。
依据版本：`v0.7-architecture` / `v0.7-theory-draft`（四平面 14 部件、六条不变量、D-043、D-047）。

## 1. 切片设定

**场景。** 已上线三年、约 40 万行的多模块业务系统，8 人团队。产品侧要求改某类订单的折扣计算口径，并把历史订单按新口径回填。同类需求每两周一次，是日常而非特例。

**规模与形态。** L2（团队）：验证者与生成者分离、事实门禁在线、成本按单元可观测。

**必须体现的历史包袱。**
- 计费逻辑散在三处（服务端计算、报表口径、对账脚本），三者在某些边界条件上行为已不一致，且无人能说出哪个是对的。
- 存在一份两年前的《计费规则说明》，与代码已对不上，但下游团队仍按它做对接。
- 回填目标约两千万行，回填期间系统持续对外提供服务。

**约束。** 至少跨两次会话；回填不可逆（写进去不能一键撤回）；上线受变更窗口约束。

**外部对象逐个按判据判定**（判据见架构确定 §5.3：满足任一条即为外部——权威记录源不由本项目治理；或其上已发生的事我们不能单方面撤销）：

| 对象 | 判定 | 命中判据 |
|---|---|---|
| 需求 / 工单系统 | 外部 | 判据一（治理权、审批与发布节奏在别的团队） |
| 生产环境的订单数据 | 外部 | 判据二（回填写入不能单方面撤销）；判据一部分成立（数据内容由业务产生，不由本项目治理） |
| 下游团队的对账系统 | 外部 | 判据一（它的记录源与发布节奏不归我们） |
| 团队即时通讯渠道 | 外部 | 判据一（消息发出即在别人的记录里）；判据二（已发出的通知不能单方面撤销） |
| 本项目代码仓库、构建与测试 | 内部 | 两条判据均不满足（记录源归我们、可重置） |
| 变更窗口（发布流程） | 外部 | 判据一（窗口由运维/发布流程治理） |
| 《计费规则说明》文档 | **判不清** | 判据一不满足（文档由我们治理）；判据二字面不满足（改文档可回滚）。但下游据它实现了两年，那部分不可撤销。按 §6.4「判不清时按外部处理」判为外部——详见 §5 与 §4-B5 |
| 三处实现已经产出的历史账单与报表 | 外部 | 判据二（已发给下游、已入账，不可单方面撤销） |

## 3. 发现：无处归属的内容

### A1. 我方工件被外部消费时的变更纪律（反向边界）

**它是什么。** 下游对账系统按旧口径读我们的订单数据。改口径不是我们对它做了什么，而是我们改了自己的东西，后果外溢到边界另一侧。要回答的问题是：改动前要不要预告、要不要留双跑期、过渡期的不一致谁承担、旧口径要兼容多久。步骤 4 与步骤 7 的过渡期退出条件都卡在这里。

**为什么接不住。** 判据能判出下游是外部（判据一），但第六条不变量的四条推论**全部是单向的**，站的都是"我方作为外部对象的消费者或写入者"的位置：读只引用不复制（我方读外部）、写限窗口并幂等留回执（我方写外部）、可用性不保证（我方依赖外部）、唤醒不等于授权（外部触发我方）。本切片里**没有一个我方动作跨过这条边界**——只有后果跨过去了。四条推论一条都不适用。14 个部件同样接不住：11 管我方权威记录源的指派，31 管我方的权限上限与可作用对象，40-P8 的风险接受记录里有"受影响用户或数据"一栏但那是事后登记而非变更准入，21 管我方的阶段与返工。没有任何一处把"我方是别人的上游"写成职责。

**它更像哪一类。** 架构级。架构确定 §6.4 登记的证伪信号第二条原文是"出现一条既不属于四条推论、也无法由'外部'判据推出的跨边界纪律"——这就是一条，而且它不是边角情形：维护期改一个已被消费的口径，是这类系统最常见的变更形态。

**建议。** 不新增部件，但第六条不变量需要补第五条推论或把判据双向化，语义大致是"外部对我方工件的既有依赖同样不可单方面撤销；改变被外部消费的口径或契约前，须登记受影响的外部消费者与兼容窗口"。它同样可以挂回已有规则收紧（11-P1 的主张模型 + 10-P4 的冻结与验收变更），符合 D-047 的做法。**注意这不构成回到选项 B**：它仍然是约束的形状，不是部件的形状。

### A2. 既有实现的行为考古（"现状是什么"的权威重建）

**它是什么。** 新口径只能相对旧口径定义，而旧口径散在三处互相矛盾的实现里，权威文档已失效。要产出"三处各自在哪些边界条件上给出什么结果""下游实际依赖的是哪一处"这份事实，需要一次独立的、消耗可观执行预算的调查（步骤 3）。同源的还有：40 万行系统里这次改动的真实影响面，也是要被发现的，不是已知的。

**为什么接不住。** 交付线从"意图确认与冻结"起步，前提是意图可被确认；14 个部件都建立在这个前提上。10 管条目清单，不管条目从哪来；11-P1 说"权威按主张指定"、§2 说"冲突时列出互相冲突的主张与各自范围、版本、环境，不静默挑一个"——列完之后由谁、按什么程序、消耗多少预算把它裁决成一个权威，没有部件负责；30 的验证计划"从**本次改动集**派生"，而这里要刻画的是改动前的现状，不由改动集派生；30-P7 的验证基线记的是"变更前的失败集合"，不是"三处行为的差异集合"；33 评的是 Harness 本身在变好还是变坏，不是被交付系统的现状；23 只承载"仍需情境判断的重复方法"，不承载一次性的调查结论。11-P8 兜底句允许把运行观察写下来，但那是**结论的落点**，不是**产生结论的职责**。

**它更像哪一类。** 部件级，最像 11 项目知识缺的一项最小职责：**当同类主张有多个互相冲突的既有载体时，重建权威的程序与其产物形态**。也可能是 10 与 11 之间未指派的边界。

**建议。** 在 11 的最小职责里补一项，明确它的产物是一份带范围与观察时间的现行行为主张集合、它的裁决落在责任平面、它的成本进 32 的记账。不新增部件、不新增章节。

### A3. 与不受我方调度的写入者共享目标对象

**它是什么。** 回填期间生产系统持续对外服务，在线交易与回填作业同时写同一批行（步骤 13）。回填可能覆盖在线刚写入的新值，或读到写一半的中间态。

**为什么接不住。** 21-P9（并行单元只写自身局部空间，总状态由收口阶段的单一执行者更新）与 24-P8（隔离工作区是环境能力，动作影响范围由环境限定）都成立，但两者的前提是**写入者集合由我们决定**：P9 说的是我方拆出的并行执行单元，P8 说的是我方动作的影响范围。这里的另一个写入者是被交付系统自身，不接受我们的调度也不在我们的能力目录里。24-P7 的"更新类动作在参数不完整时先回读当前对象状态再提交"最接近，但它防的是"残缺参数覆盖完整对象"，不是"两个独立写入者的时序竞争"。不变量 6 的四条推论里也没有并发语义。

**它更像哪一类。** 部件级，属于 24 工具与执行环境（外部写入的并发前提），或架构级（推论二"写须幂等"的一个前提条件：幂等只在没有竞争写入者时才等价于安全）。

**建议。** 在 24-P7 补一句前提声明：外部写入的幂等性只在目标对象无其他写入者时成立；存在不受本流程调度的写入者时须另行声明冲突处置，否则该写入判未定。

### A4. 已成功但事后判定为错误的不可逆写，其反向方案

**它是什么。** 回填跑到 40% 时发现口径判错了。已写进去的 800 万行怎么办（步骤 14）。

**为什么接不住。** 规范里"待补偿"只有一种语义：**写没成功、结果未知、要补做**（24-P7"未成功的写入进入待补偿记录"、20-P8、20 §2"待补偿的外部写清单"）。本切片需要的是相反的一种：**写成功了、判据错了、要反写**。两者共用一个词，语义相反。不变量 6 判据二把"不可逆"用作**边界判据**（不可单方面撤销即为外部），然后交给不变量 5（人授权）防住，逻辑是"既然撤不回来，就在做之前让人拍板"——但没有任何一条要求"不可逆动作在授权前须有可执行的反向方案，或明确声明没有反向方案并由人接受这一点"。40-P5 的授权参数是方式、范围、批准人、时间窗，不含回退方案；31-P4 的 Gate 合同有"失败后的去向与屏障范围"，那是 Gate 失败，不是动作成功后判错；33-P6 的晋升检查有"回滚可用"一项，但 33 管的是 Harness 自身的变更，不是业务交付动作。40-P8 的风险接受记录里有"补偿控制"与"替代方案"两栏，是全篇唯一沾边的地方，但它是**风险登记的字段**，触发条件是"实现者不能自行接受其产生的重大风险"，性质是事后兜底而不是动作准入。

**它更像哪一类。** 架构级。不变量 5 只说"不可逆动作只能由人授权"，缺的是授权的**前置内容**。

**建议。** 在不变量 5 或 40-P5 的授权参数里补一项：不可逆动作的授权须同时呈现反向方案，或呈现"无反向方案"这一事实本身。这不新增原则，只是把 40-P8 已有的字段前移为准入条件。

## 4. 发现：勉强接住但别扭的地方

### B1. 抽样验证只能被记成"通过 + 盲区"

30-P1 的三态与 30-P2 的盲区声明形式上接住了（步骤 22）：抽样跑完，裁定通过，未抽到的部分写进盲区。别扭在于**盲区不改变裁定**。对两千万行的不可逆写，盲区里藏的是不可发现且不可撤销的错误数据，而它与"端到端测试没覆盖视觉"这种盲区被记成同一种东西。不变量 4 说"执行事实来自环境回读"，这里只回读了万分之一，却产出与全量回读同等效力的"通过"。三态的四个未定子原因（未执行、无法核验、结果未知、生成者与验证者同一）没有一个能表达"以某置信度覆盖了某比例"。→ 缺口，见 §6。

### B2. 不可逆动作的粒度未定义，一次性批作业被塞进为常规动作设计的授权结构

回填是一个动作还是两千万个动作？规范没有判据，而这个粒度直接决定不变量 5 与推论二能不能落地：按一个算，"已执行的不可逆动作清单"与回执无法支持恢复（恢复要知道做到哪一行）；按两千万个算，清单不可维护、逐个人授权荒谬。实际走通的路是 40-P6 的预批准动作集 + 40-P5 的时间窗参数（步骤 18、20），但**性质错配**：术语表把预批准动作集定义为"慢变、可审计的授权变更"，其设计假定是重复出现的常规动作；这里拿它包一个只发生一次、几天后即作废的动作。31-P8"交互式审批不得沉淀为永久授权"防的正是这类扩张，本切片却必须主动制造一次这样的扩张再手工撤掉。

### B3. 状态工件的新鲜度协议对外部状态空转

20-P2 要求每条状态记录绑定可重新验证的工作副本身份与版本，20-P3 要求新鲜度冲突时失败关闭。回填进度的权威在生产库（外部），推论一说读只引用不复制，于是状态工件里只能放指针，每次恢复回读（步骤 16）。这条路是通的，但 P2/P3 的整套协议在这个字段上**空转**：外部状态没有我们能比对的版本号，"版本缺失、倒退、同版本内容不同"这三种触发条件都无从判断，"失败关闭"永不触发。20 章 §2 的身份模型是围绕代码工作副本建的，对"权威在外部的状态"没有形态。

### B4. Gate 合同的触发单位挂不上持续运行的作业；被交付系统的资源成本无记账口径

回填期需要一个按生产延迟与错误率阻断的闸门（步骤 21）。判据是可直接观察的确定事实，符合 31-P2，可以阻断。别扭在 31-P4 的合同字段："生效范围与触发的动作或状态转换"——全部围绕**离散的动作与状态转换**设计，而这里的闸门要挂在一个连续跑几小时的批处理上，触发单位对不上。另一半是成本：22-P9 的三轴与 32-P8 的价表版本口径只覆盖 AI 侧消耗（来源、缓存、执行单元），而本切片最大的成本是回填对生产库的负载与在线业务影响。40-P8 的风险接受记录能登记一次，但它是静态登记，不是持续观测。

### B5. 判为外部却无推论可用

《计费规则说明》的内外判定落空（步骤 2、24）：判据一不满足（文档由我们治理），判据二字面不满足（改文档可回滚，"其上已发生的事"指的是这个对象自身）。按 §6.4 的 fallback"判不清时按外部处理"判为外部——然后四条推论**一条都不适用**：我们不是在读它（我们要改它），不是在写外部系统（它是我们的），可用性不成问题，唤醒不成问题。fallback 的辩护理由是"按外部处理只会更保守"，但这里按外部处理不产生任何约束，只产生一个用不上的标注。**判据的产出（内/外标注）与推论的适用性之间没有保证。**根因与 A1 同一条：规范只建模了我方作为外部对象的消费者。

### B6. 验证基线只有代码侧形态，数据侧无对应物

30-P7 的验证基线是"变更前的失败集合及其版本与工作区身份"，判定对象是"变更后失败集减基线集"。数据回填没有对应物：回填前不存在一个"失败集合"，只存在两千万行现值。32-P4 要求变更验证附"变更前的失败集合"作为字段，本切片这一栏只能填未定或空（步骤 11）。要达到 P7 的等效效果（把新引入的错误与存量错误分开），需要的是回填前的现值快照与逐行差分预演，规范里没有这个形态。

### B7. 幂等是被作用对象的属性，而 24 的设计对象是工具接口

24-P7 说"重试须带幂等标识"，24-P1 说"工具接口是一等设计对象"。回填的幂等性实际由**目标数据表的设计**决定（能否按新口径重算并与旧值比对、能否记录已处理水位、是否有可用的自然幂等键），而不是由调用它的工具接口决定（步骤 12）。24 章把全部设计投入指向工具接口一侧，没有一条要求"被作用的持久对象须具备可幂等重放的结构"。老系统的历史表往往不具备，而这决定了推论二能不能落地。

### B8. 结构性删减不作用于被交付的代码

三处实现各自改到新口径，不一致的结构完整保留，下次变更还要改三处。21-P1"只修改切片所需范围，无关阻力记为改进候选"合法化了这个做法，33-P9 收下这条 Add 候选（步骤 27）。别扭在于：33-P9 的 Add/Thin 明确声明"作用域是共享组件"，12-P8 与 23-P8 的结构性删减作用于知识、记忆、规则与方法条目——**没有任何一处的删减机制作用于被交付系统本身的重复实现**。规范对"规则只增不减"有一整套结构性刹车，对"同一事实有三份实现"只有一条改进候选，而后者正是本切片全部风险的来源。33-P9 的 Add 信号清单里也没有"同一主张有多个实现载体"这一项。

### 期待有、但翻遍 14 章找不到的（缺口）

1. **不可逆动作的粒度判据**：一次动作是什么。这个粒度直接决定不变量 5 与推论二能否落地，规范全篇未定义（B2）。
2. **不可逆动作的反向方案作为授权准入条件**：40-P8 有"补偿控制"字段但位置是事后风险登记（A4）。
3. **我方作为被消费方的变更纪律**：A1。
4. **既有实现冲突时的权威重建程序**：11-P1 给了指派规则，没给发现程序（A2）。
5. **统计性 / 抽样验证的裁定语义**：三态与四个未定子原因都表达不了"以某置信度覆盖某比例"（B1）。
6. **数据变更的验证基线形态**：30-P7 的基线只有"失败集合"一种形态（B6）。
7. **被交付系统的运行资源成本口径**：22-P9 与 32-P8 只覆盖 AI 侧消耗（B4）。
8. **被作用持久对象的可幂等结构要求**：24 把设计投入全部指向工具接口一侧（B7）。

### 本切片明显用不上、但章里写得像"必须"的（过度约束候选）

- **12 记忆与知识治理的大部分**（P2 两维准入、P3 自动晋升允许域、P5 置信态三档、P9 个人与团队边界）。8 人团队做一次口径变更，全程没有一条记忆候选值得走这套流程，但 12 §2 把"在交付链既有状态转换处提取候选"写成最小职责，意味着本切片的每次状态转换都要跑一次提取器。P4 允许提取器输出"无可沉淀"，算是留了出口，但这套机制在本切片里的产出接近于零。
- **22-P9 三轴成本与子执行者独立计费**：本切片的成本压倒性地在生产系统与人的带宽上，AI 侧 token 成本可忽略，而章里写成"只报总量、或只报原始计数而不分单元与阶段的优化提案不进评审"。
- **25-P8 模型代际消融候选**：与本切片完全无关，但列在最小职责里。
- **33-P4 的实验 manifest 与 33-P6"晋升链是唯一入口"**：33 §2 的最小职责写的是"让**所有变更**走同一条晋升链"，字面包含业务交付变更。上下文显然指 Harness 自身的变更，但作用域没有写死，读者按字面执行会给每次业务需求套一份十几字段的 manifest。这是措辞歧义而不是真的过度约束，值得收紧一句。

## 7. 一句话结论

这套理论能支撑本切片的主干——意图冻结与派生、验证者与生成者分离、三态不折算、不可逆动作由人授权、跨会话读状态不读对话，这五条在演练里全部真正用上并且都拦住了东西；但它在"不可逆的批量数据变更"和"我方是别人的上游"这两处接不住，其中后者是根本问题：**第六条不变量只建模了我方作为外部对象的消费者与写入者，没有建模我方工件被外部消费，而这恰恰是维护期变更最常见的形态**——本切片十个跨边界对象里有三个落在这个盲区，并且它们已经构成 D-047 自己登记的证伪信号；不过修补它仍然只需要一条推论而不是一个部件，选项 D 的形状本身没有被证伪。
