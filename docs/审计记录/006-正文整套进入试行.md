## 3. 那 42 条提议是什么：35 条的内容早已写成正文

按各章文件头的 `governed_by` 统计（可机械复核）：**41 条`提议`里 35 条被某章明确认领**。剩 6 条中，D-007 自己写着"拟被 D-033 取代"、D-022 的八层结构已被四平面（D-043）取代、D-041 与 D-042 是关于交付形态与研究纪律的元决策、D-004 是否决型（没有可落地的正文）。**真正内容未落地的只有 D-046。**

这与第十四轮在 A0″ 的发现是同一件事，只是范围从 16 项扩到全部：**默认裁决早就执行了、写成了正文；开着的从来不是"该怎么写"，而是"写好的这套算不算生效"。**

## 4. 根因

> **这个仓库在用两态（`提议` / `已接受`）运行一个三态系统，而缺掉的中间态正好是 42 条各自需要的那一个。**

`已接受`要求确定性，Alan 给不出，于是不动；`提议`没有执行点，于是[失败 Case 清单](../失败Case清单.md)读数一成立——117 条原则拦住 0 条。**在有效力之前，这 117 条永远不会产生任何验证数据。**

而卡住的东西必须记在什么地方，于是长出了那份 53 条、10 个组的待决策清单。它的漂移已实测：

| 待决策清单作为登记处的实测偏差 | 条数 |
|---|---|
| `提议`决策**根本没进**清单 | 7（D-002/003/004/008/012/032/046） |
| 清单里已生效或已取代、**不再待裁** | 14（5 已接受 + 9 已取代） |
| 同一决策**被两个及以上组重复列** | 16 |

**它是决策日志状态列的手工副本**，正是 [08 §7](../08-规范效力元治理.md) 禁止的那种。清单不是问题，是症状。

## 6. 顺带修掉的：C5 只认了一种形态
