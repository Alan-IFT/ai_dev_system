## 3. 解释与判断（按未定读，子原因：生成者与验证者同一）

**根因不是那几条不合规，是 D-057 的 scope 在两种读法之间没有选**：

- **(甲)** 117 条约束任何在本仓库内作业的人——我，每一轮；
- **(乙)** 117 条作为一份规范生效，采用它的项目须遵守。

**现有生效规则的先例是分开的**：D-014 与 D-015 是元治理与载体类，scope 写 `repo:...`；D-020、D-043、D-047 是内容类，scope 写"本仓库全部规范正文内"——它们约束**文本能写什么**，不约束维护者要做什么。**D-057 把一批内容类规则挂上了元治理类的作用域，这是我上一轮写下的缺陷**（[Case C-026](../失败Case清单.md)）。

按 (甲) 读下去，本仓库得为了编辑 markdown 而建验收条目、Gate 集合、工作项与交接、预声明阈值；按 (乙) 读，D-057 只剩状态变更，三项检验一项也答不了。

## 8. 当天更正：那份"哪几章有实例"的名单不该存在

**它错了两格，而且是机械可证的。** 把[失败 Case 清单](../失败Case清单.md)"本该防住它的规则"那一列按章聚合，得到已被证明有实例的章是 **11、20、22、23、30、33**。对比 §5 写下的名单：

| | 结果 |
|---|---|
| 判"无实例"但清单里有 Case 绑到它 | **11 章**（11-P2、11-P5）、**23 章**（23-P4、23-P7）。一条 Case 存在即证明那里发生过失败，**实例必然存在** |

而这两章不是边角：**11-P2「每类工件在任一时刻只有一个权威记录系统」是本仓库用得最多的一条**——版本号 26 份副本、HEAD、两份议程全是它；**23 章的实例就是[仓库工作须知](../附录-载体实例/仓库工作须知.md)自己**。

**根因**：[D-057 的登记行](../决策日志.md#effective-register)已经有判据了，我却又在两处手写了一份它的投影。而[仓库工作须知 §4](../附录-载体实例/仓库工作须知.md) 的第三条硬规矩正是"判据优先于枚举"——**枚举写在了那一条的下一节**。

**处置：删名单，不加检查。** 名单一删就没有可检查的对象；给要删的东西加守卫是纯粹的添加。哪些章已被证明有实例是**可导出的**——读 Case 清单那一列。这与前四次（版本号 26 份副本、HEAD、Case 条数、两份议程、正文效力状态）是同一个病的第六次，登记为 [Case C-027](../失败Case清单.md)。
