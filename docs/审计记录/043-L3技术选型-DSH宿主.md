# 043 L3 技术选型（DSH 宿主）

## 0. 本文是什么

- **是**：在 [041](041-技术选型的综合审计与推荐.md) 的逐部件判定之上，按 Alan 改定的口径——**栈直接按 L3 选，宿主定为 DeepSeek Harness（dsh）**——给 14 个部件各一个确定的载体、给 dsh 补上它在 L3 缺的那几块、并写死"在真正开工前必须先验证什么"。两份补充核对是本文的证据底：G 把 dsh 官方仓库整个浅克隆下来逐文件读（HEAD `d347e70`，`0.1.3-alpha.1`，2026-09-04），H 核了 dsh 之外的外围件。**两份都没有运行过任何东西**——本文的每一句"dsh 会怎样"都是"仓库文件这么写"，不是"运行时确实如此"；把它变成"确实如此"的动作在 §7。
- **不是**：不写代码（Alan 2026-09-02 方针未改，本轮只做选型）；不改正文；不改生效登记表。D-087 行加一句「修订」记录口径变化（§10）。本文第一版经提交前对抗性复核（[审计记录 044](044-第二十八轮提交前对抗性复核-043.md)）改过一轮：七条证伪与十条部分成立全部按其给出的写法改正，改动点在该记录 §0 逐条列出。
- **与 041 的关系**：041 §6 以 L1 为起点的分档表**不再作基线**。但 041 逐部件的判定（哪些候选按判据 B/C 不装、哪些要求市面无物只能自建）本文全部沿用，不重复论证；本文只在 dsh 上把"L3 形态"写实。

**对"直接做 L3"的一句话处理。** 00 §7 写着四档不是必经阶段，是同一套部件在不同规模下的形态，升档的唯一条件是验证能力跟得上；21 §2 P3 写着判定器必须先于自动触发器就位。这两条与 Alan 的意图并不冲突，冲突的只是词：**"直接做 L3"指的是栈——所有 L3 才需要的载体现在就选定、就搭好，不留"以后再换"的部件；不指自主度**——每一个"无人在场也放行"的行为都挂在一个判定器上，判定器的已知答案回归集没绿之前，那个开关就是关着的，同一套栈按 L1/L2 的形态跑。这样既不推倒重来，也不违反"判定器先于自动触发器"。§6 把每个开关和它的判定器列成表。

## 1. 三句结论

1. **dsh 值得当 L3 的执行宿主，但只当执行宿主。** 按 041 的五家对照，有两样是 dsh 独有的（指令预算超限时**点名丢了什么**的通告；审批把"未知默认关闭"做成结构性保证而非超时约定），其余几样是 dsh 做得最贴近本理论的：单调守卫（只能拒不能放，按已解析的参数判、可 per-agent）、审批策略 `never` 下每个 ask 确定性 `rejected` 且在瀑布分发前就强制、沙箱不可用时 fail-closed 的 `SANDBOX_UNAVAILABLE`（Claude Code 的默认是降级为不沙箱）、模型请求前与顶层工具体执行前落盘的会话检查点（嵌套调度复用外层那一次）、schema 公开的只追加会话日志、子代理 `outputSchema` 的结构化返回（满足时按 schema 校验，官方明写请求 schema 不保证一定产出）。**但它的编排层官方明写"No journaling or resume"，headless 入口没有 JSON 输出，沙箱官方明写不管网络，出厂配置把遥测指向厂商端点且无脱敏规则（触发条件是有人执行 `/feedback`），版本 alpha、天级发版、自述必然破坏兼容。** 所以：编排与状态放在 dsh 之外，网络边界放在 dsh 之外，遥测先关掉，版本 pin 死。
2. **整套栈只有三个信任域、零个新的常驻第三方服务、零个新数据库。** "服务"在本文里指需要独立运维的第三方常驻件（Temporal / ClickHouse / SigNoz / 记忆库 / 向量库这一类）——一个不装；PostgreSQL 18 与 Docker 两台机器上都已有。新增的常驻件只有两样、都在我们自己的代码里：编排进程（一个 Node 长驻进程，用 DBOS Transact 库把工作流检查点写进 PostgreSQL）与一条巡检 cron，各自在 §9 登记活性探测。三个信任域：仓库（git，知识平面与控制平面的全部文件）、编排进程、执行容器（Docker 里跑 dsh，容器内 iptables 出口白名单）。外部依赖三个且都按第六条不变量标为"边界外"：GitHub（必经路径与人的检查点）、sub2api 网关（模型）、企业微信 webhook（只唤醒不授权）。语言只有一种（TypeScript：dsh 插件与编排器同一运行时），评估侧例外用 Python（Inspect AI）。
3. **L3 与 L1 的区别只在六个开关，不在部件。** 自动合并、自动晋升记忆、自动起工作项、自动重试、自动放行外部写、自动升级停机——每个开关对应一个判定器与一份已知答案回归集（§6）。开关全关时这套栈就是 041 推荐的 L1；开关逐个打开就是 L3。**避免推倒重来的办法不是一开始就全自动，而是一开始就把全自动需要的东西装在正确的位置上。**

## 2. 选 dsh 买到了什么、没买到什么、代价是什么

Alan 的理由是"自由度、可监测、可定制程度最高"。按 G 的一手核对，这三点各自成立到什么程度：

**自由度——成立，且有一个必须知道的形态。** dsh 是 Cordis 插件运行时，能力位可整体替换（压缩、审批应答者、沙箱后端、子代理后端都是"服务定义 + 提供者"）。项目自己的守卫、工具、不变量都可以是**项目目录里的一个本地 `.ts` 插件**，但 dsh 不自动发现项目插件：每次启动要带 `--patch /绝对路径/项目/dsh/cordis.yml`，稳定归宿是 `$DSH_HOME/profiles/<name>/cordis.patch.yml`。**"忘记带 patch 启动"本身是一个失效面**（判据 C）——探测是让守卫插件在会话里留一条自己的事件，编排器开工前查它在不在。

**可监测——成立，且是五家里最强的一块。** 会话日志是每会话一目录的只追加 JSONL（默认 zstd 分帧，可配 `compression: 'none'` 得纯文本行），信封字段 `type` / 单调 `seq` / epoch-ms `time` / `data`，载荷强制 JSON 可序列化，全部事件类型有生成的目录文档（`docs/persistence-catalog.md`）。这几乎就是 32 章"只追加保存原始记录、导出是派生投影"的原样。**代价**：出厂 `dsh-base` 把遥测配成 `FEEDBACK_ONLY` 并指向 `harness-telemetry.deepseeksvc.com`；官方逐字"FEEDBACK_ONLY uploads only when the user records /feedback"——触发条件是有人执行 `/feedback`，不是每次会话——但一旦触发即"no session-telemetry/record redaction rule, so exports are the raw captured copy"。官方逐字"config cannot disable a row"说的是配置层撤不掉这一行插件，但可以改它的 `mode`：profile patch 里设 `mode: DISABLED`（DISABLED 下导出器根本不构造），另有 `DSH_TELEMETRY_MODE=DISABLED` 与 `DSH_TELEMETRY_DISABLED`（任意非空值）两条环境变量路。**L3 三条一起用，并让出口白名单不含该域——按 31 章"未知默认关闭"处置，不论触发条件。**

**可定制——成立，边界要说清。** `ctx.tools.restrict()` / 子代理 `toolFilter` 会让被过滤的工具**从提示里消失并拒绝执行**（G 修正了 V1 那条"只是可见性过滤"的粗表述），但官方自己的小节标题是 **"Visibility is not authority"**：子代理本地新注册的工具、deny 清单之后新增的全局工具都会逃出去。所以：**`toolFilter` 落 24 §2 P3 的可见性层——管"这个执行者该看见什么"（22、25）；`ctx.tools.guard()` 落 31 的权限层——管"绝对不许发生什么"**，两者不互相顶替，也不能把前者算作权限检查（31 §2 P6 与 24 §2 P3 都点名要防"可见性收窄被当成能力面收窄"）。31 §2 P6 要的两个位置由权限面自己给出：创建时冻结在 profile patch（preset 只一个窄条目 + `sandbox-policy.mode` + `approval: never`），执行时复核在 `ctx.tools.guard()`（全局层先、再 scope 链，源码逐字"First monotonic denial from the global then the scope chain's guard layers, farthest first"）。

**没买到的五样，每样一个补法**：编排持久化（用 DBOS，§5 洞 2）、网络边界（用容器 iptables，§5 洞 1）、结构化最终裁定（用工具写文件再回读，§5 洞 3）、记忆与评估（用文件与 Inspect AI，§4 表 12 / 33 行）、成本记账（用网关侧记账，§5 末段）。§5 的六个洞另含三个不属于"没买到"而属于"买来的东西自己会漏"：preset 可放宽、遥测默认指向厂商、版本 alpha。

**代价——一条必须写在最上面的风险。** dsh 首个公开版本距今不到一个月，仓库 master 与 npm latest 隔一天一个 alpha 版，README 全大写"THERE WILL BE COMPATIBILITY-BREAKING CHANGES"，无 CHANGELOG、无迁移指南。官方 `SAFETY.md` 逐字："Do not rely on DeepSeek Harness as the sole security control for untrusted workloads"。**处置**：版本 pin 死（Alan 已用 `minimumReleaseAgeStrict`）；升级只走一条必经路径——先跑 Inspect 的已知答案回归集，绿了才换版本；dsh 绑定层的接触面控制在 §5 那一张表里，换宿主时只重写那一张表。

| 40 人的检查点与授权 | 40 §2 P1 的五处状态转换全部落在 **GitHub**（PR 为主）：确认意图 → `ACCEPTANCE.md` 变更 PR；接受计划 → 切片计划 PR / issue；批准集成 → 切片 PR 合并；授权发布 → 不可逆动作的授权 PR / 标签；抽查自动决策 → 每周对自动合并与自动晋升样本的抽查 issue（40 §3 L3 行：每次自动决策留下可抽查的记录）。记忆与规则的晋升批准、停机后的决定是 40 §1 给 12 / 21 的授权点，不占五处名额，同样走 PR / issue。CODEOWNERS 指到人；auto-merge 只在必需检查与必需评审全满足后；企业微信 webhook 只唤醒 | `dsh-user-approval` 在 headless 下全部 `rejected`——**dsh 不承担检查点**，它只负责拒得干净、拒得留痕 | 每日心跳消息；通知先聚合再发（限频） |

四点说明：

- **为什么编排不放在 dsh 里。** `dsh-workflow` 官方逐字："No journaling or resume — scripts, child progress, and intermediate values are not checkpointed, so a process restart cannot continue a run"，且"The tool blocks the parent turn until the whole workflow settles"。20 §2 P8 要的"从上一检查点之后重放、不重复已发生的不可逆副作用"在 dsh 编排层没有载体；会话层有检查点，编排层没有。DBOS 给的恰是那一层："Steps are tried at least once but are never re-executed after they complete"，"An assigned workflow ID acts as an idempotency key"，单进程重启自动恢复 PENDING 工作流——**但抛异常的工作流进 `ERROR` 态且不恢复**，所以我们的工作流不许抛异常，任何异常都要落成 `未定` 裁定并转阻塞；活性巡检（租约）仍要自己做，DBOS 不管"进程活着但卡死"。041 §5.2 的降级理由仍成立：at-least-once 意味着**中断中的那一步会重跑一次**，所以每个 step 自身必须幂等（外部写带幂等键 + 回执，§6 第五行），DBOS 在 20 §2 P8 上是"部分（最强）"不是"满足"。DBOS 对 PostgreSQL 18 与 Node 24 没有官方支持声明（只有 `engines.node >= 20`），§7 要先测。
- **为什么裁定走文件不走 stdout。** headless 只打印自由文本与 0/1 退出码；SDK 的 `finalResponse` 官方逐字"not a response causally assigned to the prompt"。21 §2 P7 要"上游只消费裁定，不解析自由文本"，所以：我们的插件定义一个 `report_verdict` 工具（输入 schema 就是三态裁定的字段集），工具把裁定写到 `work/verdicts/<run_id>.json`；编排器**回读该文件**，缺文件或缺字段即记 `未定` 并拒收。这与不变量④"事实来自回读"同构。子代理层则直接用 `outputSchema`。
- **为什么容器是唯一边界、沙箱是第二层。** dsh 沙箱官方逐字"network stays unrestricted"；H 核实 Ubuntu 24.04 默认 AppArmor 阻止 bwrap 建用户命名空间、非特权容器内 bwrap 挂不了新 `/proc`。所以网络与文件的硬边界只能是容器（iptables 默认 OUTPUT DROP + ipset 白名单，Anthropic 参考脚本自带两条探针）；容器内 dsh 沙箱走 Landlock 回落，`enforcement` 可能是 `partial`——按官方口径 partial 不能当 full 用，守卫读到 partial 时记一条事件，`SANDBOX_UNAVAILABLE` 时整次运行判 `未定`，**不降级**。这比 Claude Code 默认"警告后不沙箱运行"更贴 31 章"未知默认关闭"。
- **为什么人的检查点不用 dsh 的审批。** `never` 之下 ask 不是"挂起等人"而是"立刻拒绝"——它满足 31 章，满足不了 40 章。检查点要的是"停下来等人裁"，载体是 GitHub：编排器把需要人裁的东西开成 PR（停机后的决定走 issue），webhook 唤醒，人在 GitHub 上裁，auto-merge 只在必需评审与必需检查全满足后发生。这正是 H6 三家官方材料收敛的骨架——权限最小化的执行 + 结构化输出 + 有写权限的旁路 + PR 审查。

**六个洞与堵法**（每个都附"它坏了怎么被发现"）：

1. **网络不受沙箱管** → 容器内 iptables 默认 DROP + ipset 白名单（sub2api、GitHub、包源；**不含** `harness-telemetry.deepseeksvc.com`）。探测：开工前两条探针（未授权域必失败、网关必成功）+ 每轮对白名单域重解析求与 ipset 的差集。
2. **编排不可恢复** → DBOS 工作流承担切片间状态；dsh 只跑一次切片。探测：ERROR 态工作流计数 + 租约过期巡检 + `events.jsonl` 尾行 sha 与 HEAD 比对。
3. **最终结果无 schema** → `report_verdict` 工具写文件、编排器回读。探测：缺文件 / 缺字段即 `未定`，每日统计 `未定` 占比，突增即报警。
4. **preset 可放宽** → 表只留一个窄条目 + 不给 `danger-full-access` + `approval: never` + 守卫。探测：会话日志里出现 `sandbox/mode` 变宽或 `approval/policy` 变 `ask` 即报警——这个探测在 dsh 之外读日志，独立于 dsh 自身。
5. **遥测默认指向厂商端点、无脱敏规则**（触发条件是 `/feedback`）→ profile patch `mode: DISABLED` + `DSH_TELEMETRY_DISABLED` + 白名单不含该域（三保险）。探测：iptables 计数器上对该域的 DROP 次数应恒为 0 且探针访问它必失败。
6. **版本 alpha、必然破坏兼容** → pin 版本 + `minimumReleaseAgeStrict` + 升级前跑 Inspect 回归集。探测：回归集里四条金标样本（两条必通过、两条必失败），裁定与预期不符即 harness 坏了而不是被评者退步。

另有三条不是洞但要写下的限制：`dsh-mcp-client` 只桥 tools 不桥 resources / prompts（任何"用 MCP resources 承载项目知识只引用不复制"的想法在 dsh 上不成立）；dsh 自己不声明支持哪一版 MCP 规范（只依赖 `@modelcontextprotocol/sdk@1.29.0`，协商由 SDK 负责）——**记未定**，按 041 §5.2 的口径，MCP 桥的失效形态是"工具静默消失"，§9 为此加一行探测；`ctx.tokenMeter` 只给 token 估算不给金额、不给价表——32 §2 P8"按计费类别加权记账并声明价表版本"只能在 sub2api 网关侧按 session id 做，价表版本文件放仓库。

## 6. L3 准入开关表

**同一套栈，六个开关；每个开关的打开条件是它的判定条件在 CI 里绿了，且 `policy/judges.md` 有登记（覆盖域与归属人写在登记表里，本表只列指向）。** 六行分两类：前两行的判定器是 12 §2 P3 意义上的判定器（须独立于生成者、带保留样本、声明覆盖域与归属人）；后四行是程序化条件（确定性规则或对账），不受那三项约束，但同样要有一条已知答案样本证明它拦得住。开关关着时的形态就是 L1/L2（人裁）。

| 开关（无人在场也放行的行为） | 类型 | 判定器 / 程序化条件 | 覆盖域 | 归属人 | 回归集在哪 | 关着时的退化形态 |
|---|---|---|---|---|---|---|
| 自动合并切片 PR | 判定器 | GitHub 必需检查全绿 + Inspect 最终验证集 + 无 `未定`。**排除集（12 §2 P3 必经人审）**：触及 `policy/**`、`eval/**`、守卫插件、`GATES.md`、`exemptions.md`、回滚相关路径的 PR 一律不自动合并，由 CODEOWNERS + ruleset 强制 | 代码与文档切片，不含排除集 | Alan | `eval/final/`（守卫禁执行者读） | auto-merge 关，人在 PR 上裁 |

**不是开关而是义务的一行**：40 §2 P1 的第五处"抽查自动决策"与 40 §3 L3 行"每次自动决策留下可抽查的记录"——六个开关每打开一个，编排器就为它的每次自动决策写一条带 run_id 的记录，每周一个抽查 issue 从中抽样，抽查否决率进入 40 章的带宽度量。**没有这一行，六个开关都不许开。**

## 8. 明确不采纳（本文新增的，041 已列的不重复）

- **`dsh-workflow` / `dsh-jobs` 作跨切片编排**：官方明写无 journaling、无 resume、结果阻塞父轮；只在一次运行内用。
- **`dsh-schedule` 作调度器**：它是会话内的持久提醒，"Delivery stays inside the session"，不能唤醒编排器。
- **`dsh-session-log-export` 作程序化导出**：官方明写是浏览器下载；投影直接读 JSONL 目录。
- **`dsh-session-telemetry-otel` 上生产**：只导 logs、无脱敏、无 token 与成本、默认指向厂商端点；信息量不超过 JSONL；关闭。
- **把 `toolFilter` / `restrict` 当权限边界**：官方 "Visibility is not authority"。
- **容器内再套 bwrap**：Ubuntu 24.04 与非特权容器两层限制叠加，官方给的绕法自述"considerably weakens security"；容器为唯一硬边界，dsh 沙箱走 Landlock 作第二层。
- **OTel Collector → PostgreSQL**：contrib 无官方 PG 导出器（捐赠 issue 仍 open，旧 issue closed as not planned）；用会话日志投影脚本。
- **ClickHouse / SigNoz**：第二个数据库 + 一套服务；单机单人下判据 B 可选、判据 C 探测成本不抵收益。
- **企业微信作授权载体**：无回执、无身份绑定、20 条/分钟限频；只唤醒。（H 未查到模板卡片是否支持交互回调，**记未定**，见 §7 0.16；即便支持，授权仍只在 GitHub 上发生。）
- **Docker Sandboxes（microVM）现在就上**：能力更强但整个新产品、治理付费、Linux 可用性未查到；记为出现对抗性外泄需求时的升级路径。
- **在生产机 nfsy 上跑 L3 宿主**：生产与开发分离是 Alan 自己定的纪律；编排进程与执行容器都在开发机。
