## G · DSH 一手核对（输出：`G-DSH一手核对.md`）

逐条回答，编号照抄：
- G1 headless / 非交互入口：dsh 有没有类似 `dsh run`/`--print`/`-p` 的非交互模式？输出能否是 JSON？能否强制输出 schema？若没有，`ctx.agentLoop` / `dsh-workflow` 能否作为"从外部程序驱动一次会话并拿回结构化结果"的替代（进程内 API）？
- G2 `ctx.tools.guard()`：注册位置（是否只能在插件包里）、作用域（全局 / per-agent / per-session）、能否读项目目录里的文件（如项目本地插件或配置）。
- G3 `dsh-invariants`：伴生件的声明方式；能否由项目侧提供而非发布 npm 包；InvariantError 发生时会话是停止还是仅记录。
- G4 `dsh-sandbox` / `dsh-sandbox-policy`：README 对网络与进程可见性的原话；Linux 后端（bwrap / Landlock）细节；`mode` 取值；`full` 与 `partial` 强制的含义；能否在容器内运行 dsh（有没有已知限制，如用户命名空间）。
- G5 permission preset：`dsh-permission-presets` / `dsh-authorization` 的 README 里，会话中 `set()` 是否可放宽；有没有"锁定"或"只允许收窄"的配置/事件；`sandbox/mode`、`approval/asked`、`approval/decided` 之类事件的名称与载荷（用于外部对账）。
- G6 headless 下的审批：`ApprovalPolicy` `'never'` 的确切语义（每个 ask 是否确定性 `rejected`）；answerer 缺失/抛错时的结果值；是否记进会话审计日志。
- G7 会话日志：`dsh-session` 事件日志的持久格式（jsonl.zstd？多帧？）、schema 是否公开、能否被外部程序读取并投影；`dsh-session-log-export` 导出什么；`dsh-session-checkpoint-policy` 的"崩溃不丢模型请求与工具副作用"原句。
- G8 `dsh-workflow` / `dsh-jobs` / `dsh-schedule` / `dsh-goal-round-driver`：各自的职责原句；有没有"从检查点恢复""幂等""重试"语义；工作流是否持久化、崩溃后是否续跑。
- G9 `dsh-subagent`：spawn 与 fork 的差异原句；`toolFilter` 与 `ctx.tools.restrict` 的关系（是同一路径还是不同）；子代理返回给父的是什么（自由文本 / 结构化）；能否为子代理指定不同模型。
- G10 `dsh-session-telemetry-otel`：导出哪些信号（trace / metrics / logs）、属性名、脱敏链、是否含 token 与成本、是否含 per-agent 归因。`ctx.tokenMeter` 的粒度。
- G11 指令加载：`dsh-agent-instructions` 的 README 原句——读哪些文件、顺序、`maxBytes` 默认值、超预算通告的原文形态。（这一条已有一手，只需确认与补齐。）
- G12 版本与变更政策：当前最新版本号与日期、发布节奏、README 关于兼容性的原句、有没有 CHANGELOG / 迁移指南；`dsh-hooks-claude-code` 与 `dsh-hooks-codex` 的 README 原句（桥接了哪些事件）。
- G13 `dsh-mcp-client` 支持的 MCP 版本（有没有标注 2026-07-28 或 2025-11-25）。
- G14 有没有官方的 headless/自动化/CI 用例（如 GitHub Action、Docker 镜像、`dsh` 在 CI 里跑的示例）。

## H · L3 外围件核对（输出：`H-L3外围件核对.md`）

- H1 **DBOS Transact TypeScript**：最新版本与日期、Node 22/24 支持、PostgreSQL 18 支持声明、许可证；`DBOS.workflow`/`step` 的恢复语义原句（已知："Steps are tried at least once but are never re-executed after they complete"）；`setWorkflowID` 幂等原句；队列与并发限制；**单节点无 Conductor 时崩溃恢复怎么做**（原句）；能否作为库嵌进一个 Node 22 的长驻进程里驱动子进程。
- H2 **出口白名单的最少组件**（Ubuntu 24.04）：让一个容器/进程只允许访问指定域名（模型网关 + git 远端 + 包源）的最简做法——Docker + iptables/nftables + 本地 DNS 白名单？Docker Sandboxes（microVM）在 Linux 上是否可用及其网络策略能力？Anthropic 参考 devcontainer 的防火墙脚本做法（官方原句"convention rather than an enforcement boundary"）。给出"最少组件 + 它坏了怎么被发现（探针）"。
- H3 **遥测落库**：OpenTelemetry Collector 有没有直接写 PostgreSQL 的导出器（trace/metrics/logs 任一）？若没有，最少组件的替代：dsh 会话日志 JSONL → 脚本导入 PG；或 ClickHouse/SigNoz（新组件，判据 C 要写探测）。**按"以少就是多"给排序。**
- H4 **Inspect AI** 能否把一个外部 CLI/进程型 agent（如 dsh 的一次运行）作为被评对象（solver/agent 桥接方式）；eval log 格式；已知答案回归集的最小形态；版本与许可证。
- H5 **人裁队列通知**：企业微信群机器人 webhook 的消息类型与限频（官方文档）；GitHub PR review / CODEOWNERS 作为"五处检查点"的载体在无人值守下的形态（required reviewers、auto-merge 条件）。
- H6 **无人值守编码 agent 的 2026 年行业做法**（只要官方材料）：Claude Code 官方对"完全无人值守"的隔离建议（sandbox-environments 页原句）、OpenAI Codex 云端/CI 运行的隔离与审批模型、gh-aw 的 safe-outputs 模型；各自"人在哪里介入"。目的是给 L3 的"五处检查点"找现成形态，不是比较产品。
- H7 **Landlock / bubblewrap 在 Docker 容器内**：容器内启用用户命名空间与 Landlock 的已知限制（Ubuntu 24.04 的 AppArmor 对 unprivileged user namespaces 的限制原句），以及 Claude Code 沙箱文档对此的说法（可作旁证）。
