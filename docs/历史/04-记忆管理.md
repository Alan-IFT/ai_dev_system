<a id="operational-separation"></a>

## 1. 运营分类：知识与记忆严格分开

| 概念 | 本规范中的定义 | 权威性 |
|---|---|---|
| 上下文 | 当前一次推理实际可见的 Token 工作集 | 否 |
| 任务状态 | 带身份和时间的当前阶段、阻塞与下一步 | 只对声明范围内的进度有效 |
| 项目知识 | 经治理的需求、架构、契约、规则和说明，带 owner/source/scope | 由批准状态与 owner 决定 |
| 长期记忆 | 从过去保留、供未来召回的观察、经历、偏好或候选经验 | 永不因“被记住”而自动权威；权威性只来自 owner 批准或已登记判定器的验证证据（个人偏好的例外见 §8） |
| 验收证据 | 绑定 claim、验收 ID、revision、环境、过程与结果的记录 | 只支持声明范围内的 claim |

聊天历史与 compaction 是临时上下文；PROJECT_STATUS/WORK_ITEM 是状态；PRD/架构/ADR 是项目知识。三者都不因被放入向量库而变成“记忆权威”。

<a id="coala-lens"></a>

## 2. CoALA 只是认知视角

CoALA 用工作、语义、情节、程序记忆描述语言 Agent 的认知架构。本规范借它检查“当前注意力、事实性概念、历史经历、操作方法”是否被考虑，但不把论文分类直接映射成项目治理制度。

- 工作记忆在运营上落入当前上下文与任务状态；
- 语义信息可能来自项目知识，也可能只是待核验记忆候选；两者必须按治理身份区分；
- 情节记忆对应任务、事故、试验与失败历史；
- 程序性经验在审核前是记忆候选，晋升后成为 Runbook、Skill、Workflow、脚本或 Gate，而不继续作为第二权威副本。

这是一项适配提议，不是 CoALA 论文证明的最佳实现。

<a id="memory-candidate-schema"></a>

## 3. 长期记忆候选最小身份

候选至少回答：`memory_id`、title、type（fact_candidate/episode/procedure_candidate/preference）、status、source/observation（含来源交付节点或触发事件）、置信态（强 / 弱 / 影子）与使用方式、生成与评估它的模型、scope、owner、created_at、last_verified、retrieval_hint、sensitivity、retention/expiry（有时效者为绝对失效时点；派生知识改记派生来源与源版本）、conflicts、promotion_target、待补齐项。

内容槽位探测提示（形态由项目定，不作必填）：定义之外通常还有真实样例、反例与易混项、适用前置条件、历史误判；经验类条目通常还有决策理由、被排除路径、验证方式；关系/组织类条目应显式列出待补齐项。

字段载体可用文档、数据库或任务系统；固定目录深度、固定召回条数和固定保留期都只是项目参数。

<a id="memory-staging"></a>

## 4. 候选区与写入协议

状态机候选：`candidate → quarantined / 影子（shadow） / review → promoted | rejected | expired | archived`。候选“进入默认可见范围”（入池）与“进入权威载体”（权威）是两个独立维度：前者由交付链的客观信号满足，后者由 owner 批准。

- AI 可在已授权候选区写入带原始位置的候选，不得直接改生效 PRD、架构、安全规则或个人档案；模型自身输出或推断不得成为候选，只分流到任务记录，写入决策应记录被排除项及理由。
- 敏感、来源不清或与现有知识冲突的候选进入 quarantined，不参与默认检索；影子（shadow）态可参与发现与背景召回，不得单独作为执行依据。
- 入池条件是客观交付信号（如关联到已生效的验收或工作区），评审通过但未生效的方案不得进入默认可见范围；审批点在进入权威载体或默认可见范围前，而非写入候选区前；归档与晋升是两个动作。
- 候选的提取绑定交付链既有状态转换（评审通过、审查完成、发布生效、任务失败）作为副产品发生；候选量由去噪策略、风险和评估决定，不设“每任务最多一项”的跨项目固定阈值。
- 保留期、审核时限、删除权限、审计保留期和可见范围必须由项目决定。
- 私人信息默认需本人确认，不能因团队项目需要而自动传播。

<a id="promotion-transaction"></a>

## 5. 晋升是一项治理事务

候选晋升时必须原子完成：

1. 核对来源、冲突、适用范围、敏感性、置信态和验证结果；
2. 由对应 owner 批准目标工件和状态；或——仅当候选影响面为局部、可撤回，且存在独立于生成者、带保留样本、已登记并覆盖该任务域的判定器时——由该判定器通过替代批准，并记录事后否决入口；全局规则、安全与权限边界、评估集、回滚决策、冷启动种子必经人审；
3. 在项目知识或程序资产中创建/更新唯一权威项；
4. 更新检索索引与替代关系；
5. 把候选标记 promoted，并只保留指向新权威项的链接；
6. 记录批准人、时间、版本、复查/失效条件和回退方式。

验证者与生成者信息隔离：验证者只拿任务与产出物，不拿提案说明；权威验证只返回不可逆推的结果；代理验证与权威验证的分歧率应记录，分歧时先强化验证器再改候选。

典型晋升链：一次性工件 → 被重复生成 → 情节观察 → 重复模式 → Runbook/Skill 候选 → 稳定步骤 → 脚本 → 可机械判断且高代价违规 → Gate。每一步都需要新证据和独立决策，不能一次跳级；即席脚本、查询、看板等一次性工件不进常驻记忆，同类工件被重复生成才成候选。

<a id="memory-retrieval"></a>

## 6. 检索与使用

采用“短索引 → 元数据筛选 → 回到原始来源/当前知识 → 组装最小片段”的候选路径。高频、稳定、短小且低敏的信息可以考虑预载；庞大、动态、低频或敏感信息即时检索。

装配时须留下消费记录（条目、任务、时间），输出中引用所用条目的标识，使人能分辨模型判断与团队事实；使用后记录有帮助或误导，作为后续 eval 输入，指标须区分“到达”与“有用”两维，只报到达率视为反馈环缺失。人明确绑定的条目与浮动召回分区呈现，前者不被相似度排序挤出。

召回结果按置信态与使用方式使用：强条目可驱动执行，弱条目只提示风险，影子（shadow）条目只助发现；偏好只影响形式不覆盖事实；有时效条目用前核时效；个案经验只作类比，不得以旧经验替代新问题的排查；召回为空须声明“无历史经验”。使用前核对状态、作用域、版本、环境、最近核验时间与当前 source of record。

<a id="memory-conflict-gc"></a>

## 7. 冲突、过期与垃圾回收

两类过期：派生知识记录派生来源与源版本，源差异超过项目设定即机械判过期，过期后默认不作事实，只可带“待核实”标签引用；经验知识记录作用域、产生事件与产生时版本，作用域内源变化触发复核而非判过期；有时效条目到绝对失效时点退出检索。此外，关联组织/模型变化、超过复查期、长期无人使用、频繁误召回、与当前知识冲突、重复或已被程序/Gate 替代时触发复核；生成或评估它的模型更换时回到候选态重评。

过期或零消费条目默认退出检索但不删，被引用或被标有用时恢复；删除需遵守审计、隐私与保留要求。库的健康度按下游任务结果与召回有用率评估而非条目数；提取器可输出“无可沉淀”；删减须有结构性机制（探测提示：容量置换、相似合并加版本、压缩约束、到期归档，须并列），不依赖策展者自觉；策展（提取/合并/删除）是独立评估组件，应有自己的 Case 与指标。

冲突时使用[主张模型](01-工作原则与事实来源.md#claim-model)，不要让 AI 静默选择记忆覆盖权威知识。

<a id="personal-project-memory"></a>

## 8. 个人记忆与项目资产

个人偏好、原则与身份由本人所有并确认，可跨工具迁移，不要求外部证据；进入项目/团队会话时效力低于项目规则、生效决策与事实性主张，沟通偏好不能覆盖安全、法律、验收和生效决策。描述性经验（发生过、验证过什么）无论归属都需证据。项目知识与程序资产由项目所有并受项目权限控制，项目事实不得复制进个人记忆。访问边界在读取前：团队记忆必须按身份与作用域过滤后再检索；个人单用户可降级为标注，但一旦被非本人发起的流程或含他人可见输出的会话读取，即须升级为加载前过滤。“五层个人记忆”“固定两级目录”等只保留为实践候选。
