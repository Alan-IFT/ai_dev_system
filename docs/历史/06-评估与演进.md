<a id="evaluation-layers"></a>

## 1. 四层评估

| 层 | 关注点 | 候选方法 |
|---|---|---|
| 工件级 | 代码、配置、文档是否满足确定性要求 | 测试、lint、schema、构建、链接检查 |
| 轨迹级 | Agent 是否读对来源、选对工具、遵守权限和正确交接；被注入的知识/记忆是否到达并被使用 | 满足最小结构的轨迹（调用树 + 时间区间 + 节点状态与用量 + 重试/中断作为一等节点 + 注入内容可按来源回看）、结构化 grader、人工轨迹审阅 |
| Harness 机制级 | 每项规则、文档、技能、检查在本次运行中是否被消费、是否拦住真实问题、是否误伤 | 按机制聚合的消费与误伤计数、接入后的生效探针、零消费机制定期复查 |
| 任务级 | 端到端任务能否稳定完成 | 固定 Case、保留集、重复 eval run、回归比较 |
| 项目级 | 是否改善真实交付与维护 | 返工、缺陷、恢复时间、周期、成本、业务结果 |

OpenAI 的 Agent eval 指南直接支持“调试行为时检查 trace；定义好坏后使用数据集与可重复 eval run”。将这个顺序用于 AI 编码 Harness 是本项目的外推假设，必须在真实项目 eval 中验证，不能把官方指南当成已证明的跨场景结论。

Harness 机制级是第四观测面：一项机制若给不出消费与误伤计数，不得被判定为有效，“已配置”不等于“已生效”；但消费计数只能发现摆设与误伤，发现不了仍被消费却已不需要的规则，须与 §6 的代际审计并用。轨迹的导出与聚合视图是派生投影而非权威记录：丢失应显式可见，验收证据须能回读原始记录，观测组件的异常不得影响被观测的执行。

<a id="case-registry"></a>

## 2. Case 注册表

Case 来自已观察的失败（附轨迹）或已构造的失败（附风险来源），两者同等登记并注明来源类型；来源事件优先是真实缺陷、人工纠正、权限边界、正常主路径、过期文档、中断恢复、模型/工具回归，以及代理验证与权威验证的分歧样本。不变量类 Case 应在系统切换策略的边界两侧取点。每个 Case 至少记录：`case_id/revision`、来源事件与来源类型、输入前提、允许和禁止行为、target environment、grader、期望差异、敏感级别与保留策略、标注所依据的权威定义版本、用途。

评估样本按用途分区：诊断类可暴露给修改 Harness 或记忆的执行者（仅统计摘要）；筛选与最终验证类不得被其读取，并定期以真实新失败替换；教学/示例 Case 与评测 Case 分开存放。三分在存在自动改进闭环（Harness 变更由模型生成）时必备，纯人工改进至少保留未用于调优的保留样本并绑定版本；不能只回放已经被 Prompt 记住的 badcase。

评估集自身有饱和与过期条件，样本绑定其标注所依据的权威定义版本，定义变更后旧样本只能判未定（UNDETERMINED）而不能作通过依据。评估集与标准的增删是受门控的人工变更，评估失败不得由自动流程以“样本过时”消解。晋升评估遵守时间顺序，目标任务之后才出现的结论不得作为“历史经验”；有效性由任务的机器验证判定。

<a id="eval-manifest"></a>

## 3. Eval manifest

每次 Harness 实验固定：

- experiment_id、hypothesis、owner；
- case_set_revision、holdout policy 与各分区用途；
- model/provider/version、system/developer prompt revision；
- tool、Skill、memory、workflow、permission 与 Gate revision；
- grader/metric revision 及其校准证据（基准样本结果、与人工一致性、判分器变更后重跑历史）与覆盖域；预先声明的阈值、重复次数与重复策略；
- 环境与基础设施配置、执行隔离条件（独占/并发）、执行模式与噪声基线；预算（候选与基线相等）、延迟与人工成本；
- 成本按计费类别加权并声明价表版本，同时保留原始计数，按执行单元/阶段分解并注明被报告单元占总成本的份额；被测机制是否改变模型所见（是则须报路径层指标）；结论等级（已确认 / 同时观察到 / 尚未确认）；
- baseline、candidate、result artifact、limitations 和 rollback。

先写成功/失败标准再运行，避免看结果后改阈值。效果量小于噪声基线的差异不得作为依据；靠增加采样、重试或推理预算获得的提升不计为 Harness 改进。模板见 [EVAL_MANIFEST](../../templates/EVAL_MANIFEST.md)。

同一实验的前后对比必须引用同一基线工件。“确定 / 可复现”类结论须绑定保证来源类型（接口契约 / 测试观察 / 防御性配置），只观察到的不得写成保证；判分器应有已知答案的回归 Case，可被刷满的代理指标须配直接信号。

<a id="promotion-gate"></a>

## 4. Harness 晋升链

候选变更必须经过：

`观察到失败 → 可复现 Case → 基线 → 候选实验 → 评估通过 → 人类批准 → 决策进入试行/已接受 → 受控发布 → 线上观察 → 保留/修改/回退`

晋升 Gate 至少检查：eval manifest 完整、阈值预先声明、同预算对照、原失败路径与至少一条正常路径 Case 双通过（不只失败路径复现）、成本按加权口径在预算内、批准人与生效范围明确、回滚可用；候选若为规则、技能或记忆条目，须附分类（能力补偿 / 组织信息 / 责任结构）与相应的淘汰或迁移条件，并引用一个已登记 Case 而非口头风险。方向性指标越界时冻结晋升。线上观察不能被离线分数替代。

<a id="failure-taxonomy"></a>

## 5. 先修最早偏离层

失败先按层定位：意图、source of record、检索/上下文、状态/记忆、工具/ACI、工作流/权限、验证/证据、环境、模型。再做子归因：既有规则被违反，先区分是措辞歧义、位置稀释、规则冲突、训练偏差、参考材料互相打架还是上下文丢失；执行者异常，先区分是能力缺失、有能力但无约束，还是约束存在而执行器有缺陷；落到模型层的，再区分部分完成即宣布完成、自我偏好、目标漂移与方案过度复杂。诊断输出区分已确认 / 推断 / 未验证。

定位后再选择文档、索引、状态、工具、Gate、测试或模型修复；不要在下游无限追加 Prompt。修复优先改既有规则，新增规则须附“不存在等价规则”的证据；同一失败模式在仅改指令/配置层的多轮迭代后仍不改善，或同层修复后复发，视为误诊，应停止该层迭代转向工具、环境与数据层（重试纪律见 02 §3）。

<a id="ablation"></a>

## 6. 模型升级与受控消融

到期审计有三种触发并存、分工不同：日常观测（无消费 / 误伤计数）发现摆设与误伤；模型代际更替时的全删对照发现静默过期；周期清扫处理存量。代际审计不可被日常观测替代——没有提示反而更好的信号，被动观测发不出来。

模型代际更替时，对能力补偿类规则做到期审计：保留责任与结构类（安全、权限、不可逆边界、验证者分离），在隔离环境中以全删对照建立最小基线，再不带某规则重跑其绑定 Case，通过则删除并记录到期证据；组织信息类不因模型过期，但可从指令形态迁移到工具或检查器形态。到期规则多数反转为负作用（过度验证、过度触发、过度分析），不只是冗余；删除条件可以是触发条件收窄而非整体移除。删减同样需要 eval 与回退；用来判断过期的评估集自身也会饱和，须同步复查。

<a id="add-thin"></a>

## 7. Add / Thin

Add 信号：重复失败/纠正、来源错读、恢复或验收失败、高风险边界仍依赖模型自觉、稳定步骤反复消耗人工注意力。Add 与 Thin 的作用域是共享组件；一次性工件只有在被重复生成时才成为 Add 候选。

Thin 信号：无法说明解决什么 Case、长期无消费（以机制级观测计数为准）、机制重复、模型已可靠内化（以代际审计为准）、频繁误伤、维护与上下文成本超过收益、已由更确定机制替代。

Thin 是结构性机制——入必有出，不依赖策展者自觉（探测提示，并列：容量置换 / 相似合并加版本 / 压缩比约束 / 周期性自动清扫）；删除门槛低于新增，绑定 Case 不再复现或持续零消费即可由 owner 删除并保留历史。库或规则集的健康度只能是下游结果与召回有用率，不能是条目数。候选发现是改进闭环的独立步骤且自带限流：任务后才触发、有信号才输出、单次输出有上限、只建议不写入，进入待审队列后才走 §4 晋升链。规范自审计只作诊断，维度为规则的来源 Case 绑定率、消费记录、增删比与规模预算；上限是护栏不是削减目标，超限须在变更中辩护，不按存在性或数量打分。

<a id="metrics-candidates"></a>

## 8. 指标候选

从以下选择 3–5 个并先建立基线：新会话恢复时间、首次端到端验收通过率、上下文/状态过期返工、无新证据重复尝试、每切片周期与人工介入、生产逃逸缺陷、证据身份错配、Gate 误阻断、Token/计算/维护成本。

每个指标应声明归属层级（探测提示：任务内的局部输出 / 行动路径 / 整体结果；组织内的个人 / 团队交付链 / 业务结果）与可归因程度，低层收益不得引为高层证据。流动类指标（周期、吞吐、长尾）不得单独报告，须与质量反指标（缺陷密度、返工）和集中度反指标（单点依赖）成对出现并带基线期。除结果指标外监控方向性指标（输出规模、工具调用次数、被删除的测试与被禁用的检查、资产库增长方向等）并设阈值，以捕捉每步过门控但多轮累积偏离的形态。

代码行数、PR 数或 Token 计数不能单独代表价值；原始 Token 计数也不能代表成本，须按计费类别加权并声明价表（观测语义见 03 §9）。还要检查瓶颈是否转移到需求、Review、发布或业务验证。
