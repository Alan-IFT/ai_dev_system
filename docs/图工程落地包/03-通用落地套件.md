## 1. 筛选判据：不给清单，给判据

清单会随载体死亡而失效——卡 05 §8 给的实证是 AutoGen 已进入维护模式（该项目自述"will not receive new features or enhancements and is community managed going forward"），而它在 2026 年的综述里仍被列为 System Intelligence 的标准载体。**一个被 2026 年综述列为标准载体的库，其上游已停止新功能。**

### 判据 A（必需性），逐字取自卡 05 §8

> **没有它，某条规范条文就无法被判定为"已执行"或"已违反"**

**这条判据的严格用法有一个陷阱**，本文明写：如果一条条文的对象**根本不存在**（例如项目里一条方法规则都没有，那么"每条规则须绑定 Case"这条），按 [D-014 空集合条款](../08-规范效力元治理.md#empty-set)判 **UNDETERMINED 而非 PASS**——**判不出 ≠ 已执行**。因此判据 A 要分成两问：

- **A1（无条件必需）**：这条条文的对象在项目开工的第一天就存在。→ 该文件是 L0 无条件必需。
- **A2（条件必需）**：对象出现之后才存在。→ 该文件在对象出现的那一刻起必需，**且它必须与承接该对象判定的文件成对建立**（见 §2.3 的 PLAYBOOK/FAILURES 成对规则）。

### 判据 B（可选性），逐字取自卡 05 §8

> **它是否只是把仓库里已有的信息重新组织了一遍**

是 → 可选，属优化。卡 05 点名落在这里的：图数据库、向量库、记忆服务、可视化画布。理由逐字："依赖关系本来就在代码里，历史决策本来就在 git 里。"

### 判据 C（引入门槛），逐字取自卡 05 §8

> **它是否引入了新的失效面而没有自带独立探测**

引入即须配探测，否则不装。**本文把它写成一条可执行的准入动作**：任何进入套件的新部件，必须在它进入的同一次变更里，写下"它坏了的时候会怎么被发现"，且该发现方式不能是它自己（[31 §2 P9](../31-守卫与权限边界.md)：机制是否生效以运行时观察为准，不以执行者自报为准）。写不出的，不装。

### 一条反判据（卡 05 §8 明写，本文照抄其效力）

> **规范文档本身可以是负收益**

TDAD 的对照组（逐字）："adding TDD procedural instructions without targeted test context increased regressions to 9.94% -- worse than no intervention at all"；作者结论逐字："surfacing contextual information outperforms prescribing procedural workflows."

**推论（卡 05 原文）**：每写一条"应该怎么做"，都必须同时回答"执行它的那一步会被喂进什么具体上下文"。只有前者、没有后者的条文，在这个实验的条件下应被视为**有害而非中性**。
**条件必须一起记**：SWE-bench Verified，两个开源权重模型，125 个实例，样本小。卡 05 明写"不作强论据，作强提醒"。

**本套件对这条反判据的执行方式**：下面每个文件的模板骨架里，凡是"要求做某事"的字段，旁边都有一个 `需要的上下文` 字段。**该字段为空的条目，视为未完成登记。**

## 2. L0 · 一人一工具

### 2.1 按判据 A 筛出来的结果

| 文件 | 承载的最小职责（一句话） | A1/A2 | 加载 | 谁维护 | 什么时候更新 |
|---|---|---|---|---|---|
| `CONTEXT.md` | **这次推理看什么、缺了怎么办**——唯一一份默认加载清单 | **A1** | 默认，整份 | 项目所有者 | 切换工作项、切换运行类型、增删任一必读项时 |
| `ACCEPTANCE.md` | **要做什么、做到什么算完成**——每条带稳定 ID 与可观察结果 | **A1** | 默认，只加载当前相关条目 | 项目所有者（L0 即本人确认并冻结） | 意图变化时，且变化须留痕不覆盖 |
| `WORK.md` | **做到哪了、怎么恢复、凭什么说做完了** | **A1** | 默认，整份 | 每次运行的执行方写，本人核 | 每次状态转换；每次会话结束前 |
| `PLAYBOOK.md` | **只有本项目知道的做法与踩过的坑** | **A2** | 按触发条件，不常驻 | 只有人 | 新增一条规则时；一条规则被判不可执行时 |
| `FAILURES.md` | **出过的错，一份不分区的清单** | **A2**（与 PLAYBOOK 成对） | 只在做删减、到期审计或补绑定时 | 只有人 | 每次观察到一次失败时 |

**代码、测试、构建照项目原样，不动。** 判据 A 的第三件（"一个已知答案的验证参照"）在多数项目里**已经存在**——它是项目原有的测试套件；套件缺失时它落在 `ACCEPTANCE.md` 的「怎么算通过」一节，不新建文件。

### 2.2 无条件必需只有三个：为什么

- **`CONTEXT.md`**：没有它，[22 §2 P1](../22-上下文装配.md#context-levels)"每个项目只有一份默认加载清单"连"有没有清单"都判不出。**判不出即未定，不是通过。**
- **`ACCEPTANCE.md`**：没有它，[30 §2 P1](../30-验证与测试.md) 的三态没有对象，[32 §2 P2](../32-证据与追踪.md) 的完成主张绑不到条目，"完成"不可判。
- **`WORK.md`**：没有它，[20 §2 P2](../20-状态工件.md#state-artifacts)"每条状态记录必须归属到一个具体的、可重新验证的工作副本快照"没有落点；恢复、交接、驳回原因回流全部无处存放。

三者对应 [00 总览 §1](../00-总览.md) 的三个可判定问题：**看什么**（执行）、**算不算完成**（知识+控制）、**在哪里**（执行）。

### 2.3 PLAYBOOK 与 FAILURES 必须成对——这是本文对现有样板的一处细化

[23 §2 P5](../23-方法库.md)"每条规则绑定一个已登记的失败 Case"。**只建 `PLAYBOOK.md` 不建 `FAILURES.md`，这条条文结构性不可满足**——绑定的另一端不存在。

**本仓库自己就是这条的实证**（[失败 Case 清单 §0](../失败Case清单.md) 逐字）：

> **本仓库写下这条规定十轮，从未建过这份清单。**

以及它的后果（逐字）：

> 没有清单，当时已记的决策绝大多数绑不出来……没有清单就没有消费计数，**Thin 判据在本仓库一直不可执行**。

【修订】相对 [templates/文件树与落地路径.md](../../templates/文件树与落地路径.md)：那一份把五个文件并列为 L0，本文按判据 A 把它们分成"无条件三个 + 成对两个"。
｜防的失败：项目先建 PLAYBOOK 攒规则、想着"以后再建失败清单"，于是 23-P5 从第一天起就不可满足，而没有任何东西会发现这件事。
｜删除条件：当规则的绑定关系由载体强制（新增规则时必须选一条已存在的 Case，否则无法保存）时，"成对建立"这条纪律可删——载体已经保证了。
｜可以删掉现有的什么：**可删 [templates/文件树与落地路径.md](../../templates/文件树与落地路径.md) §2 末尾"L0 的真正门槛不是文件数，是两条纪律"里的第二条**（"跑不了的检查写未定"）——那条是 [30 §2 P1](../30-验证与测试.md) 的直接复述，属副本；成对规则是新的、非副本的门槛。

### 2.4 与现有样板的一处差异，明写

[templates/文件树与落地路径.md](../../templates/文件树与落地路径.md) §1 的结论是"一人一工具的项目落地是 **5 个文件**"。本文的结论是"**3 个无条件 + 2 个条件必需且成对**"。

**这不是矛盾，是同一结论的两种表述**：项目一旦写下第一条项目特有做法（几乎总是第一周内），两份结论就完全一致。差别只在**第一天**：本文允许一个项目在还没有任何项目特有做法时，先只建三个文件而不建空的 PLAYBOOK/FAILURES——因为**空文件比没文件更危险**，它让"有没有"这个检查恒为通过（本仓库 [C-006](../失败Case清单.md) 的同型：一条恒为通过的检查看起来是真的 PASS）。

**本文不改那一份**（本轮只新建文件）。差异登记在此，处置留待审议。

## 3. L1 · 一人多会话（+2）

主题是**跨会话的连续性**。判据 A 的形态变化：L1 出现了"上一次会话"这个对象，于是 [20 §2 P9](../20-状态工件.md#state-artifacts)（交接分两层）与 [22 §2 P6](../22-上下文装配.md#context-levels)（工具返回外部化到可回读位置）有了对象。

| 文件 | 职责（一句话） | 加载 | 谁维护 | 何时更新 |
|---|---|---|---|---|
| `work/handoff.md` | **短交接**：只含当前判断所需的结论、身份、状态版本、未完成原因、下一原子动作 | 默认（新会话的第一读） | 上一次运行的执行方 | 每次会话结束、每次压缩之前 |
| `work/artifacts/` | 工具返回的**原文落点**——不随历史逐轮携带，按引用回源 | **不加载**，按引用回源 | 自动落盘 | 每次大体量工具返回 |

**`WORK.md` 在 L1 拆成两半**：`work/current.md`（实时状态源）与 `work/handoff.md`（临时快照）。[20 §2 P1](../20-状态工件.md#state-artifacts) 要求三类状态工件职责不重叠，但载体是否合并是 [20 §4 未决](../20-状态工件.md)——L0 允许合成一份，L1 建议拆开，因为"交接"这个对象在 L1 才第一次出现。

**L1 不新建记忆文件。** 理由是现有正文自己给的：[12 §2 P2](../12-记忆与知识治理.md#memory-retrieval)与[12 §2 P8](../12-记忆与知识治理.md#memory-retrieval)的删除条件都写着"**起始档——本条自 L2 起才有对象（L0/L1 单用户没有'归属人批准'这一侧）**"。L0/L1 的记忆闸门由 `WORK.md` 的候选区一节 + `PLAYBOOK.md` 承载。

## 4. L2 · 团队（+5）

主题是**责任分离与一致性**。

| 文件 | 职责（一句话） | 加载 | 谁维护 | 何时更新 |
|---|---|---|---|---|
| `DECISIONS.md` | **唯一效力源**：决策 + 生效登记表；"某条规则此刻有没有阻断力"只查这里 | 默认（生效登记表片段） | 具名的决策归属人 | 每次效力状态变化 |
| `SOURCES.md` | **权威记录源的指派，具名到人**：哪类主张归谁定义 | 按需（判断冲突归属时） | 项目所有者 | 新增一类主张、或归属人变更 |
| `GATES.md` | **闸门合同**：身份、生效范围、触发的动作或状态转换、判据类型、未知默认值、失效探测 | 按需 | 闸门维护者 | 新增/修改闸门 |
| `memory/` | **候选池 + 事实层**：个人与团队分源挂载，按身份过滤后检索 | 按需（过滤后） | 提取器写候选，归属人批准晋升 | 每次状态转换 |
| `eval/` | **评估集三分区**：诊断 / 筛选 / 最终验证；筛选与最终验证类**不得被会修改 harness 的执行者读取** | 按需 | 评估归属人 | 实验前固定，实验中不改 |

**L2 是记忆治理第一次有对象的档位**（[12 §3](../12-记忆与知识治理.md#coala-lens) 明写）。`memory/` 的内部结构见 §7 的模板骨架。

**为什么 `tools/check_*.py` 不在这张表里**：它不是一个"文件类型"，而是判据 C 的产物——每引入一个新的失效面就要配一个探测。**它按需出现，不按档位出现。**

## 5. L3 · 无人值守（+3）

**L3 的准入条件不是工具，是一句话**（[00 §7](../00-总览.md) 已写）：有一个不需要人在场就能拒绝坏输出的判定器。没有它，前面三档做得再全也上不了 L3。

| 文件 | 职责（一句话） | 何时更新 |
|---|---|---|
| `policy/judges.md` | **判定器登记**：每个判定器的覆盖域、归属人、保留样本、独立于生成者的证明——这是自动晋升的允许域（[12 §2 P3](../12-记忆与知识治理.md#memory-retrieval)） | 新增判定器；覆盖域变化 |
| `policy/budget.md` | **预算与范围在创建时固化，执行中只能收窄**（[31 §2 P6](../31-守卫与权限边界.md)） | 每次运行创建时 |
| `ops/liveness.md` | **活性巡检与合法停止点**；待补偿清单非空即不得宣告完成（[20 §2 P7/P8](../20-状态工件.md#state-artifacts)） | 巡检口径变化 |

**L3 追加一条验收信号**（来自 [02 §1.3](02-记忆管理落地设计.md)）：日志可确定性重放。它需要一份重放契约（禁随机、禁墙钟、禁框架外 I/O、禁可变全局态）。**这不是一个新文件，是 `policy/budget.md` 的一节。**

## 7. 字段级模板骨架（可直接复制）

**每个骨架下面都给两种机制类型不同的落法**（[09 §5](../09-跨工具通用性.md#feasibility-test)）。两种实例不同属一个工具。

### 7.1 `CONTEXT.md`

```markdown
---
contract_id: <项目名>-context-001
contract_revision: 1
updated_at: <ISO-8601>
status: proposal | trial | accepted
run_type_axes:                      # 见 00 总览 §3；四格，不是两列
  output: delivery | fact           # 产出类型：交付型 / 事实型
  origin: fresh | handover          # 起点状态：从头 / 接手
current_run_type: <output>/<origin> # 本次运行在起点声明；判不清 → delivery/handover
current_work_item: <精确路径 或 null>
---

# Default Context Contract

本项目只有这一份默认加载清单。清单只做路由，不复制被路由文档的正文。
视图是同一份清单的投影，不是第二份清单。

## Required context

| # | ref (path#fragment) | why（承载哪条主张 / 原则编号 / 验收 ID） | extent | D/F | D/H | F/F | F/H | on_missing |
|---|---|---|---|:-:|:-:|:-:|:-:|---|
| 1 | CONTEXT.md（整份，含 front matter） | 确认合同版本与加载边界 | whole-file | ● | ● | ● | ● | 停止 |
| 2 | ACCEPTANCE.md#<当前条目 ID> | 本次的完成定义（10 章） | anchor-to-next | ● | ● | ○ | ○ | 停止 |
| 3 | WORK.md#current | 当前状态、工作副本身份、下一原子动作（20-P2） | anchor-to-next | ● | ● | △ | △ | 降级继续并记未定 |
| … | | | | | | | | |

图例：● 必读　○ 不读　△ 条件读（条件写在 why 里）
D/F=交付型×从头　D/H=交付型×接手　F/F=事实型×从头　F/H=事实型×接手

## 接手格追加的核对动作（仅 D/H 与 F/H）

对每个 ● 项回答两个问题；两个都答不上的记未定并升级：
- last_written：这一项上次被写是什么时候？
- last_read：这一项上次被读是什么时候？

## Optional context

| 触发条件 | ref | 不加载条件 |
|---|---|---|

## Excluded by default

## Resolution rules

1. ref 用仓库相对 canonical path；相同 path#fragment 只加载一次。
2. extent 取值：whole-file | anchor-to-next | lines:<a>-<b>。缺省 anchor-to-next。
3. 链接不递归展开；"相关""当前""对应"等动态描述不得由执行者猜测。
4. 每一层允许合法的"什么都不加载"；但空输出必须与"采集未执行"可区分。
5. 合同、工作项或工作副本身份冲突时失败关闭。
6. 切换工作项或运行类型时递增 contract_revision。
```

**两种落法**：
- **机制类型 A（外部状态存储）**：如上，仓库根一份 Markdown。跨工具通用，因为它是纯文本（卡 05 §7 的横向结论）。
- **机制类型 B（条件加载规则）**：任务系统里给每个工作项加一组字段——`run_type`、`required_refs`（多值链接）、`on_missing`（每个链接一个枚举）。合同不是文件而是一次查询。**这一种在没有任务系统的项目上不可用**，因此它是并列形态之一，不是必填形态。

### 7.2 `ACCEPTANCE.md`

```markdown
# 验收条目

冻结日期：<ISO-8601>　冻结人：<姓名>
变更规则：条目 ID 一经分配不复用；修改留痕不覆盖。

## AC-001 <一句话标题>

**事件（L1）**——只追加，无改写接口：

```

 "source_trust":"trusted|untrusted","source":"<来源标识>","payload_ref":"<原文落点>","digest":"<内容指纹>"}

**事实（L2）**——一条一份：

```markdown
---
fact_id: FA-0031
claim_type: intent | source_def | deploy_state | runtime_observation   # 11-P1 的五概念之一
scope: <范围 / 版本 / 环境>

source_trust: trusted | untrusted  # untrusted 时正文必须以"某来源声称"开头
t_created: <ISO-8601>              # 系统何时知道
t_expired: <ISO-8601 | null>       # 系统何时标为作废
t_valid:   <ISO-8601 | 未定>       # 事实何时开始为真
t_invalid: <ISO-8601 | null>       # 事实何时不再为真
superseded_by: <fact_id | null>    # 作废不删除
owner: <归属人 | null>             # null = 尚未晋升为权威
recall_count: 0
last_recalled: null
---

<一句话事实。必须 context-independent：不含代词指代，不引用本条外未定义的缩写。>
```

**两种落法**：
- **A（外部状态存储）**：如上，仓库内纯文本。**这是本文的默认推荐**，理由是卡 05 §7 的横向结论（"仓库内的纯文本"是那份材料范围内唯一在所有部件上都成立的跨工具载体）。
- **E（外部服务 / MCP）**：把 `memory/` 换成一个 MCP server 暴露的 resource，消费端只写一段配置（卡 05 §4.1 逐字："Build MCP servers that expose tools, resources, and prompts to **any MCP host**"；且"接一个已有 server 到宿主只写一段 JSON 配置"）。
  **按判据 C，这条落法引入的新失效面必须一起写**：服务不在线、抽取质量、限流（卡 05 记录 Graphiti 的 `SEMAPHORE_LIMIT` 默认 10）、小模型 JSON 抽取失败。**配不出独立探测就不装。**

## 8. 一张判据表：某个候选部件该不该进套件

| 问题 | 是 | 否 |
|---|---|---|
| 没有它，某条条文无法被判定为已执行/已违反？ | 继续问下一行 | **不进套件**（属优化，判据 B） |
| 该条文的对象在第一天就存在？ | **无条件必需** | **条件必需**，且必须与判定它的对象成对建立 |
| 它引入了新的失效面吗？ | 必须在同一次变更里写出它坏了怎么被发现，且发现方式不是它自己 | 直接装 |
| 它只是把已有信息重新组织了一遍吗？ | **可选**，先用最低成本形态（一个静态文本文件）试，别上服务 | — |
| 它有没有"上游停更"的风险？ | 按卡 05：上游停更本身是一个失效面，**且它不自带探测** | — |

**最后一条的处置**：任何绑定到具体第三方载体的部件，套件里必须同时写下它的**语义**（换载体不变的那部分）与**当前载体**（会死的那部分），并让语义写在正文位置、载体写在附录位置。这就是 [09 §7](../09-跨工具通用性.md#no-mapping-table) 的"规范不因某个工具的约定变化而需要修订"在套件层的落点。
