## 1. 上下文合同规格

### 1.1 为什么合同必须按运行类型出视图，而不是按角色出清单

[00 总览 §3](../00-总览.md#default-scope) 已定义一次运行由两个正交属性描述：**产出类型**（交付型 / 事实型）× **起点状态**（从头 / 接手）。**这是 2×2 四格，不是两列。** 本仓库自己的 [CONTEXT_MANIFEST.md](../../CONTEXT_MANIFEST.md) 目前只做了产出类型一轴的两列视图，起点状态那一轴没有落进合同——本文补上它，并说明补的理由。

补的理由是一条实测观察，来自本仓库的[失败 Case 清单](../失败Case清单.md)读数六（逐字）：

> **换到 `交付型 × 接手` 之后，出现了第三种形状：写着、但从没被执行过，也没有任何东西会发现。**

以及同段末句（逐字）：

> **缺陷的形状由运行类型决定，而本仓库前十一轮只跑过一种类型。**

**推论：起点状态这一轴决定的不是"读多少"，而是"哪些字段可能是死的"。** 从头运行里所有字段都是刚写的，接手运行里任何一个字段都可能已经空转多轮。两者需要的不是同一份清单的宽窄差别，而是**不同的核对动作**。

### 1.2 四格视图：每格的出口、必读集与核对动作

| 格 | 本次运行的出口 | 相对基准列的差 | 该格特有的核对动作 |
|---|---|---|---|
| **交付型 × 从头** | 一次验收 | 基准列（最宽），判不清时按此格处理 | 无（全部字段都是本次写的） |
| **交付型 × 接手** | 一次验收 | 基准列 **+ 空转探测集** | 对每个"必读"项问一句：它上次被写是什么时候、上次被读是什么时候；两个答案都答不上的记未定并升级 |
| **事实型 × 从头** | 一份带成立条件的事实 | 基准列 **− 议程类** −（不改条文则）**账本类** | 在起点声明"问题从哪来"（本仓库 [C-013](../失败Case清单.md) 的处置：**问题来源由请求者在起点给定**） |
| **事实型 × 接手** | 同上 | 同上 **+ 空转探测集** | 上两格的并集 |

**"判不清按更宽的那一列处理"是已有规则**（[CONTEXT_MANIFEST.md](../../CONTEXT_MANIFEST.md) 现文），本文不改。四格化之后这条规则的表达是：**产出类型判不清按交付型；起点状态判不清按接手**——接手是更宽的那一侧，因为它多一组核对动作而不是少一组。

【修订】把合同的视图轴从一轴扩到两轴。
｜防的失败：一次接手运行按"从头"的视图加载，于是没有任何一步会去问"这个字段上次被写是什么时候"，一处长期空转的要求继续空转（本仓库 C-017：`current_work_item` 自基线以来从未被填写过一次；C-021：`archify visual-check` 自成图起一直 fail 而从没被跑过）。
｜删除条件：当载体能对每个必读项自动给出"最后写入时间 / 最后读取时间"两个可机械核对的值时，起点状态这一轴的**核对动作**可删，轴本身仍在（它还决定问题来源从哪来）。
｜可以删掉现有的什么：**可删 [CONTEXT_MANIFEST.md](../../CONTEXT_MANIFEST.md) 现文里"视图边界原有两处空缺……余下一处"整段散文**——那段在讨论"事实型运行的问题从哪来"，四格化后它是"事实型 × 从头"格的一个格内字段，不再需要一段解释性散文承载。

### 1.3 每一行的字段：合同的最小行结构

**这是本文对现有合同形态提出的核心修改：每一行必须写「为什么在这里」。**

现有 [22 §2 P1](../22-上下文装配.md#context-levels) 要求"清单只做路由，不复制正文"，[CONTEXT_MANIFEST.md](../../CONTEXT_MANIFEST.md) 也确实有一列叫「用途」——但「用途」写的是"这份文件是干什么的"，不是"**这一行凭什么占默认加载集的一格**"。二者的差别在删的时候才显出来：本仓库 [C-028](../失败Case清单.md) 里提出删掉合同第 5 项，五个独立执行者五比零驳回，而争议的全部内容是"这一行的职责是否与另一行重复"——**如果每一行当初就写了它对应哪条主张，这场争论在写下的那一刻就已经解决了。**

合同每一行的最小字段集：

| 字段 | 取值形态 | 缺失时 |
|---|---|---|
| `order` | 整数，决定加载顺序 | 可缺（按表格行序） |
| `ref` | canonical `path#fragment`，**精确**，不得写"当前工作项"之类的动态占位 | 该行不成立，删除 |
| `views` | 四格各一个取值：`必读` / `不读` / `条件读（写出条件）` | 判不出记 `未定`，按 `必读` 处理 |
| `why` | **它承载哪条主张、对应哪条原则编号或哪条验收条目 ID**。写不出的行不得存在 | **该行不得进入合同**——这是本字段的全部意义 |
| `extent` | 片段外延：`该锚点起至下一个锚点之前` / `整份文件` / `显式行区间` | 记 `未定`，按"整份文件"计入预算并在评审中报出 |
| `on_missing` | 见 §1.4 的四值域 | 记 `未定`，按 `停止` 处理（失败关闭） |
| `last_written` / `last_read` | 仅接手格需要；取值是可他证的时间或"不可得" | 记 `不可得`，并把该行列入空转探测集 |

【新增】`why` 字段。
｜防的失败：一份加载清单在几轮之后没有任何人能判断某一行该不该删，于是它只增不减；或者反过来，有人凭一个错误的重复性判断把一行删掉（C-028 的形状）。
｜删除条件：当载体能从"这一行被消费之后产出中引用了它"机械回归出该行的贡献时（即 [12 §2 P6](../12-记忆与知识治理.md#memory-retrieval) 的"有用"一维可机械得出），`why` 可由消费记录取代。
｜可以删掉现有的什么：**可删 [CONTEXT_MANIFEST.md](../../CONTEXT_MANIFEST.md) 现文第 7 项与第 5 项行内的两段解释性散文**（"元治理两章的纳入是 D-058 第 ③ 项的裁决结果——第十二轮之所以……"、"当前审议队列——即该表中尚未结案的行……"）。那两段正是在补写各自行的 `why`，只是写在了行内的散文里而不是一个字段里；有了字段，散文可以删。

【已有】`extent` 字段。合同[解析规则 2](../../CONTEXT_MANIFEST.md) 已于 2026-09-04 写入："`#fragment` 的外延是'该锚点起，至下一个锚点之前'"。本文只把它从一条全局规则改为**每行可覆写的字段**，因为"整份文件"这个取值（合同第 1 项就是）在全局规则下表达不了。

### 1.4 `on_missing` 的四值域，与它为什么必须手写

| 取值 | 语义 | 什么时候选它 |
|---|---|---|
| `停止` | 失败关闭，本次运行不继续 | 缺了它就无法确认效力、无法确认边界、或无法确认自己在改什么 |
| `降级继续并记未定` | 继续，但依赖该项的结论一律带成立条件，且依赖它的**不可逆动作与验收判定必须停止** | 该项影响判断质量但不影响判断合法性；形式见 [20 §2 P3](../20-状态工件.md#state-artifacts)（"结论 + 其成立条件"） |
| `继续并登记缺失` | 继续，缺失本身作为一条观察登记 | 该项是可选增益 |
| `换源` | 从声明的替代源取，替代源同样带 `on_missing` | 该项有已声明的次级权威记录源（[11 §2 P2](../11-项目知识.md#claim-model)） |

**为什么这一列不能由图算出来——这是本文最重要的一条判据。** 卡片 04 §7.5 的第 2 条已经把话说死（转述其结论）：合同里真正在做判断的不是"哪些文件相关"，而是"这次运行是交付型还是事实型"以及"缺失时停止还是继续"；前者是对本次运行意图的声明，图上没有这条信息；后者是**责任归属**——谁承担读漏的后果——按 [08 规范效力元治理](../08-规范效力元治理.md) 属责任结构型，**不因为工具变强而消失**。卡片同时记录：**本轮没有任何材料触碰这两件事。**

因此：`views` 与 `on_missing` 两列，无论图化做到什么程度，都留在手写侧。

## 2. 哪部分由图算、哪部分必须手写

### 2.1 材料给出的结论是"分工"，不是"替代"

卡片 04 §7.4 记录的 TDAD 逐字：

> "test_map.txt maps source files to test files (one line per mapping, grep-able). SKILL.md is a 20-line definition: (1) fix the bug, (2) grep test_map.txt for related tests, (3) run them and fix failures. This brevity proved critical: through the auto-improvement loop, we found that simplifying SKILL.md from 107 to 20 lines alone quadrupled resolution from 12% to 50%."

以及：

> "At runtime the agent needs only grep and pytest—no graph database, MCP server, or API calls."

卡片自己的读数（逐字）：

> **图没有消灭那份手写清单，图让那份手写清单可以缩到 20 行。** 收益不是来自"用图替代人写的规则"，而是来自 **"人写的规则从'枚举内容'退化成'怎么去查那张图'"**

**必须与这条数字一起引用的自陈**（卡片 04 §10.2 第 8 条明写"分开引就是误导"），逐字：

> "frontier-scale models with longer context windows may not exhibit the same TDD-prompting paradox, as verbose instructions would consume a smaller fraction of available context."

条件同样必须一起写：SWE-bench Verified、Qwen3-Coder 30B 与 Qwen3.5-35B-A3B、样本 100 与 25 例、原文自陈 "without formal significance tests"。**本文取用的是形态，不是效果。**

### 2.2 三条归属判据

对合同里的**每一行**，按顺序问三个问题。第一个答"是"就定档，不继续问。

**判据 R1（必须手写）：这一行承载的是"本次运行的意图声明"或"缺失时谁承担后果"吗？**

是 → **手写侧，永久**。理由见 §1.4：图上没有意图这条信息，责任归属是责任结构型。
落在这一档的：`views` 全列、`on_missing` 全列、`current_work_item`、运行类型声明本身、合法停止点与出口的声明。

**判据 R2（可图算）：这一行要回答的是"从某个已知入口出发还必须一起看哪些"，且那些边是从工件本身机械可抽取的吗？**

是 → **图算侧**，前提是同时满足三条：

- **边是机械可抽取的**：不需要语义判断就能从工件本身读出。本仓库现成的例子是章与章之间的 markdown 链接、`governed_by` 指向的决策 ID、`#ch-NN` 指向的账本段、章正文与追溯账本的一一对应——卡片 04 §7.5 第 1 条已指出："**这些边今天已经写在文件里了，只是没有人把它们当图用。**"
- **抽取器的错误可被独立检出**：抽取错了必须会报，不能安静地存进一条假边。这一条来自卡片 03 §3.5 的读数（转述）：图记忆的代价是"抽取质量成为新的单点故障，且这个故障是静默的"。
- **产物是可回读的静态工件，不是一个必须在线的服务**：TDAD 的产物是一个 grep 得动的文本文件；卡 05 §7 的横向结论是"仓库内的纯文本"是那份材料范围内唯一一个在所有部件上都成立的跨工具载体。

**判据 R3（其余）：既不是意图/责任，又不满足 R2 的三条前提。**

→ **手写，但登记为待图化候选**，并绑定一条删除条件："当满足 R2 三条前提的抽取器上线且过验收，本行的枚举部分删除，只留一句怎么查那张图。"

### 2.3 判据的产物：合同分成两半

| 半 | 内容 | 谁维护 | 目标形态 |
|---|---|---|---|
| **手写半（合同本体）** | 运行类型声明、四格视图的 `views` 与 `on_missing`、每行的 `why`、片段外延规则、冲突与缺失的处置 | 人；变更走审议 | **路由 + 判据**，不枚举内容。目标是"短到每次都会被读完" |
| **机器半（映射表）** | 从每个入口出发的可达闭包、锚点外延的实际字符数、每行最后写入 / 最后读取时间、悬空引用 | 抽取器；每次变更后重算 | 可 grep 的静态文本，不进默认加载集，只在需要时被查 |

**两半之间的接口只有一句话**：手写半写"从入口 X 出发，按映射表 M 取它的直接依赖，不递归"，映射表由程序产出。**"不递归"是手写半的判断**——[22 §2 P1](../22-上下文装配.md#context-levels) 已有"链接不自动递归展开"，图算侧不得改写它。

【修订】合同分两半。
｜防的失败：手写清单枚举内容 → 每次结构变化都要人工同步 → 同步会忘 → 清单与实际结构漂移（本仓库 [C-003](../失败Case清单.md)：悬空引用存活三轮无人发现）。
｜删除条件：抽取器覆盖不到的边类型（当前已知：散文里的"NN §M"式引用，本仓库 C-003 的检查器 C10 正是为它写的）全部消失时，手写半的"怎么查"一句可与映射表合并。
｜可以删掉现有的什么：**可删本仓库 [templates/文件树与落地路径.md](../../templates/文件树与落地路径.md) §6 那张"默认加载 / 按需 / 不加载"三行表**——那张表是合同的一份投影，且是手写的（本仓库同型病已复发六次以上，见 C-027 逐字："**这是同一个病的第六次**"）。分两半之后它由机器半直接产出。

### 2.4 一条明确的否定：不要把 GraphRAG 那种图化搬过来

卡片 04 §7.3 记录 GraphRAG 的 MECE 性质来自 Leiden 层次划分（逐字）：

> "Each level of this hierarchy provides a community partition that covers the nodes of the graph in a mutually exclusive, collectively exhaustive way, enabling divide-and-conquer global summarization."

卡片同时写清它的适用面与代价：它解的是 "What are the main themes in the dataset?" 这类全局问题，**是粒度轴上的图化，不是任务轴上的图化**；该团队报告 Podcast 数据集在 600 token 窗口下建索引 "took 281 minutes"。卡片的判断（逐字）：

> **图索引是一次性重投入，只有在同一语料被反复查询时才回本。** 一个还在天天改的规范仓库，语料每天变，这个前提不成立。

**本文照此判定：任何需要"全量重建索引"的图化方案，在语料日改的项目上不进 L0–L2 档。** 判不出语料变更频率的记未定。

## 3. 上下文膨胀的失败模式：处置与他证探测

### 3.1 探测的门槛：什么叫"他证"

[31 §2 P9](../31-守卫与权限边界.md) 与 [33 §2 P10](../33-评估与演进.md) 已有的口径是：**机制是否生效以运行时观察为准，不以执行者自报为准**；评估器自身是被评估对象。本文把它收成一句可套用的判据：

> **一条探测是他证的，当且仅当：产出该内容的一方不参与判定，且判定所依据的信号不是由该方生成的文本。**

据此，以下都**不算**探测：模型说"我已经压缩了关键状态"；模型给自己的记忆条目打重要性分（卡片 03 §5.2 第 4 条已单独拒绝 Generative Agents 的 1–10 poignancy 自评，理由逐字："让模型给自己的记忆打重要性分，是自证"）；一次"跑一遍看到 PASS"（本仓库 [C-006](../失败Case清单.md)：检查器正则里混进一个不可见退格符，该检查恒不匹配、永远通过，而 PASS 看起来是真的）。

### 3.2 失败模式表

### 3.3 一条必须并列保留的冲突：沉淀从宽，装配从严

卡片 04 §4 把两条判据的冲突写在明处，并明确"不能靠'看情况'和稀泥"：

- 判据 A（Anthropic，V1，本仓库已采纳）逐字："Finding the *smallest* *possible* set of high-signal tokens that maximize the likelihood of some desired outcome."
- 判据 B（ACE，预印本）逐字："Unlike humans, who often benefit from concise generalization, LLMs are more effective when provided with long, detailed contexts and can distill relevance autonomously."

卡片给出的化解（逐字）：

> 它们的适用对象不同：A 说的是**单次推理可见的工作集**（每个 token 都在花注意力预算），B 说的是**跨会话积累的知识库/playbook**（漏掉一条领域启发式的代价是重复踩坑）。合起来的可操作判据是：**沉淀侧从宽，装配侧从严**；两者之间必须有一道按需拉取的闸。

**注意卡片 §10.2 第 2 条的限制：判据 B 不可取用为装配侧原则**，只能作为"沉淀侧从宽"的依据登记。本文遵守。

【已有】这条结构本仓库已有：[11 §2 P3](../11-项目知识.md#claim-model)（入口只做地图、细节就近）+ [22 §2 P2](../22-上下文装配.md#context-levels)（分层加载、"可能有用"不是加载理由）。**卡片没有推翻它，只是补了一个此前缺的理由：不推送不等于不积累。**

### 3.4 一个可补的缺口：允许某一层什么都不加载

卡片 04 判据 F 引 RECOMP（**A1**）逐字：

> "If the retrieved documents are irrelevant to the input or offer no additional information to LM, our compressor can return an empty string, implementing selective augmentation."

以及判据 G 引 Self-RAG（**A1**）逐字：

> "indiscriminately retrieving and incorporating a fixed number of retrieved passages, regardless of whether retrieval is necessary, or passages are relevant, diminishes LM versatility or can lead to unhelpful response generation."

卡片的判断（逐字）：**"本条是本轮唯一有 A1 支撑的可取用点。"** 且指出现有 P2 只说"'可能有用'不是加载理由"，**没有一条说"允许某一层什么都不加载"**。

【新增】装配的每一层都必须有一个合法的"什么都不加"的输出，且该输出不得被下游读成"采集失败"。
｜防的失败：固定 Top-K 或固定条数的配额把噪声强行塞进窗口；反向地，一个合法的空输出被下游当成"检索器坏了"而触发重试或降级。
｜删除条件：当装配侧不再有任何固定配额参数时（即每一层的条数完全由判据决定），本条的前半句可删；后半句"空不等于失败"与 [D-014 空集合条款](../08-规范效力元治理.md#empty-set)同源，取"写不出（责任结构型：空输出的两种成因——真的没有 vs 采集没跑起来——后果由消费方承担，二者必须可区分）"。
｜可以删掉现有的什么：**可删 [22 §2 P2](../22-上下文装配.md#context-levels) 末句"固定比例与固定条数只是项目参数"**——本条成立后，那句从"是参数"升级为"是可以为零的参数"，末句被吸收。

**与本仓库最痛教训的连接**：[D-014 空集合条款](../08-规范效力元治理.md#empty-set)逐字——"形如『全部 X 通过』的条件在 X 为空时判 UNDETERMINED 而非 PASS"。本仓库 [C-012](../失败Case清单.md) 是它的精确实例（逐字）："**两次我都差点把'没有输出'读成结论**"，而两次空输出的真实原因都是**采集根本没跑起来**。**因此本条新增的后半句不是可选的**：允许空输出的同时，必须能区分"合法的空"与"没跑起来的空"，否则这条新增本身会制造一类新的静默失败。

|---|---|---|---|
| 合同本体 | 仓库根一份 `CONTEXT.md`，front matter 放 `contract_id` / `contract_revision` / `run_type` / `current_work_item`，正文一张表（2026-09-24 追加：front matter 会被宿主剥掉，这几项应改写成标题下的一行正文，见[决策日志](../决策日志.md#decision-index) D-121） | 不适用（合同是被检查的对象，不是检查器） | 任务系统里的一个"运行类型"字段 + 每类型一组必读工件链接；合同不是文件而是查询 |
