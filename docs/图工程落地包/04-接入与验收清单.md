## 1. 先讲这份清单为什么长这样：本仓库最痛的一课

[失败 Case 清单](../失败Case清单.md)的读数六（逐字）：

> **换到 `交付型 × 接手` 之后，出现了第三种形状：写着、但从没被执行过，也没有任何东西会发现。** C-017（合同的 `current_work_item` 自基线起从未填过一次）、C-018（12 章 §1 把三件同章 §2 已裁定的事继续列为未决）、C-019（同一份议程两份记录，而状态文件指向旧的那份）——三条都不是"规则失守"，也不是"规则之间对不上"，而是**一处要求或一份登记长期空转，且它的空转不产生任何信号**。

同段还有两条同形的（逐字）：C-021 是 `archify visual-check` 自成图起一直 fail 而从没被跑过，C-020 是图例一直印着工具的默认 Web 应用分类而没人看过一眼。结论逐字：

> **五条的共同点是：出问题的地方都有人写过、没人再看过。**

**推论，也是本文全部内容的组织原则：**

> **一个落地项不算"已接入"，除非它同时具备两样东西：一个他证的验收信号，和一个"它空转时会发出的信号"。**
> 后者说不出的项，一律记**未定**，不计入接入进度。

这两样东西是不同的：验收信号回答"装的那一刻它对不对"，空转信号回答"三个月后它还活着吗"。**本仓库的五条 Case 全部是第二种缺失**——它们装的那一刻都是对的。

## 2. 验收信号的门槛

### 2.1 他证的定义

> 一条验收信号是他证的，当且仅当：**产出被验收对象的一方不参与判定，且判定所依据的信号不是由该方生成的文本。**

依据是 [30 §2 P5](../30-验证与测试.md)（验证者独立于生产者是结构要求，不随模型能力消解）与 [31 §2 P9](../31-守卫与权限边界.md)（机制是否生效以运行时观察为准，不以执行者自报为准）。

**不算他证的**：模型说"我已经按合同加载了"；一次"跑一遍看到 PASS"；一份由同一方写的自评报告。

### 2.2 新增一条检查时的四步验收（本仓库的处置，逐字照抄）

> ① 验字节（控制字符在 grep 里隐身）② 注入前先断言待替换串存在 ③ 反例测试确认它真报 ④ 跑全仓看误伤。**任一步拿到空输出一律记未定**——空输出最常见的原因是采集根本没跑起来。

来源与后果一起记（逐字）：本仓库写过的检查里，**有两条曾"恒为通过、其实不检查"，而"跑一遍看到 PASS"完全察觉不到**（[C-006](../失败Case清单.md)：检查器 C7 的正则里混进一个不可见退格符）。

**空输出的处置有独立依据**：[D-014 空集合条款](../08-规范效力元治理.md#empty-set)逐字——"形如『全部 X 通过』的条件在 X 为空时判 UNDETERMINED 而非 PASS"。

### 2.3 三种"看起来通过其实没有"的形状，各配一条探测

| 形状 | 本仓库的样本 | 探测 |
|---|---|---|
| **恒为通过** | C-006：正则里的不可见控制字符 | 反例测试：故意注入一个应当被报的实例，检查它真报 |
| **恒不覆盖** | C-022：检查器只认括号形态，系动词形态挂了四轮没报；合同**从来不在扫描面里** | 覆盖面审计：列出该检查的扫描面，与"它本该覆盖的对象全集"对账；差集 > 0 即报 |
| **从没被跑过** | C-021：`archify visual-check` 自成图起一直 fail，从没被跑过一次 | 执行计数：每条检查记录"最后一次执行时间"；超过项目声明的窗口未执行 → 该检查的结论一律记未定，**不得沿用上次结果** |

**第三种是最难探测的一种**，因为它不产生任何输出。**本文给出的唯一可靠办法是：把"最后一次执行时间"当成一个必须被写入的状态字段，而不是一个可以推断的属性。** 没有这个字段，"从没被跑过"与"跑了且通过"在事后无法区分。

## 3. 从零接入：顺序与逐步验收

**顺序原则**：先建"能判定别的东西"的，再建"被判定的东西"。理由是判据 A——一个文件的必需性是"没有它某条条文无法被判定"，所以判定能力必须先到位。

### S0 · 声明本次接入是哪种运行（5 分钟）

- **做什么**：在 `WORK.md` 顶部写一行：本次接入是 `交付型 × 从头`。写下本次接入的合法停止点与出口。
- **他证验收信号**：该行存在，且写了具体的停止点（不是"做完为止"）。**由另一个人或一个检查器读，不由写的人自己确认。**
- **空转信号**：无（这是一次性动作）。
- **判不出时**：按 `交付型 × 接手` 处理（更宽的那一侧）。

### S1 · 建 `ACCEPTANCE.md`，并冻结第一批条目

- **做什么**：按 [03 §7.2](03-通用落地套件.md) 的骨架写至少一条 `AC-001`，含可观察结果、观察方法、三态口径、**需要的上下文**。冻结并署名。
- **他证验收信号**：**拿 `AC-001` 的「观察方法」去实际跑一次，得到三态之一。** 跑不出来的（命令不存在、查询无权限、人工步骤说不清）→ 该条目不合格，重写。**这是全流程第一个也是最重要的他证信号：它证明"完成"这个词在这个项目里有对象。**
- **空转信号**：条目 ID 从未被任何一次状态转换记录引用过 → 该条目从未被用来判定任何事。
- **判不出时**：记未定，不进入 S2。**不要用一条判不出的验收条目开始建别的东西。**

### S2 · 建 `WORK.md`

- **做什么**：按 [03 §7.3](03-通用落地套件.md) 的骨架建；关键是**工作副本身份**与**状态版本**两个字段有真值。
- **他证验收信号**：**拿 `WORK.md` 里的工作副本身份，去实际工件上交叉核对一次**（[20 §2 P2](../20-状态工件.md#state-artifacts)："仅凭记录自称不算"）。对不上 → 不合格。
- **空转信号**：`状态版本` 连续 N 次运行没有递增，而期间确实发生了状态转换。
- **判不出时**：工作副本身份的形态是并列的多种可能（[09 §6](../09-跨工具通用性.md#detection-hints)），项目选一种并在项目内保持一致；选不出记未定。

### S3 · 建 `CONTEXT.md`，四格视图，每行写 `why`

- **做什么**：按 [03 §7.1](03-通用落地套件.md) 的骨架建。此时只有三个文件，清单会很短——**这是对的**。
- **他证验收信号**（三条，全部要过）：
  1. **一次"照单加载"演练**：由**没有参与写合同的一方**，只按合同加载，然后回答 [22 §2 P3](../22-上下文装配.md#context-levels) 的开工前八项事实（目标与非目标、当前工作项与状态版本、工作副本身份、事实源、目标环境、验收标识、风险与阻塞、未决策项）。**答不上来的项数 > 0 → 合同不合格，补的是合同不是记忆。**
  2. **`why` 列无空**：检查器扫，空行数 > 0 即 FAIL。
  3. **片段外延实测**：按每行的 `extent` 实算字符数，与合同声明的预算对账。**本仓库 [C-028](../失败Case清单.md) 的教训是这一步做不做差 35%**（同一项被读成 14,855 或 23,011 两个数，多算的 8,156 属于六个无关小节）。
- **空转信号**：`contract_revision` 长期不变而工作项在变；`current_work_item` 一直是 `null`（**这正是本仓库 C-017 的形状：该字段自基线以来从未被填写过一次**）。
- **判不出时**：某一行的 `why` 写不出 → **删掉那一行**。这是 `why` 字段存在的全部意义。

### S4 · 跑一次真实运行，只用这三个文件

- **做什么**：完整跑一次 `交付型 × 从头`：读合同 → 读状态 → 干活 → 三态裁定 → 证据写回 → 状态转换。
- **他证验收信号**：这次运行结束时，`WORK.md` 的状态转换记录里有一行，它的「三态裁定」是**实际跑出来的**，且它的「证据位置」指向的东西真的存在（由检查器验证链接可达）。
- **空转信号**：运行结束了但没有新增状态转换记录行。
- **判不出时**：裁定记未定，**不折算为通过**（[30 §2 P1](../30-验证与测试.md)）。

### S5 · 第一次踩坑之后，成对建 `PLAYBOOK.md` + `FAILURES.md`

- **做什么**：先写 `FAILURES.md` 的 `F-001`（观察到的失败、等级、本该防住它的规则 = "无"、当时被拦住了吗 = "否"、处置），**再**写 `PLAYBOOK.md` 的 `R-001` 并把 `绑定 Case` 指向 `F-001`。**顺序不能反**——先有失败才有规则，这是 [23 §2 P5](../23-方法库.md)。
- **他证验收信号**：检查器扫 `PLAYBOOK.md`，每条 `绑定 Case` 的值都能在 `FAILURES.md` 里找到；找不到的条数 > 0 即 FAIL。
- **空转信号**：`triggered` 计数长期为 0（规则从未被加载）；或 `triggered > 0` 而 `complied = 0`（**Thin 第三信号**，见 [02 §5.3](02-记忆管理落地设计.md)）。
- **判不出时**：一条规则说不清它防什么 → 不予登记（[23 §2 P5](../23-方法库.md)）。

### S6 · 装第一个检查器

- **做什么**：把 S3/S5 里最容易漂的一条判定下沉为程序。**选哪一条的判据**：它是否是确定性判断（[00 §4](../00-总览.md)"确定性判断先由程序做，模型只判残余"）。
- **他证验收信号**：**§2.2 的四步全过**。任一步空输出记未定。
- **空转信号**：该检查的「最后一次执行时间」超窗口。
- **判不出时**：不装。**一个装了但不确定它在检查什么的检查器，比没有更坏**——它制造"我们有检查"的假象（C-006 的形状）。

### S7 · L1 起：`work/handoff.md` 与 `work/artifacts/`

- **做什么**：会话结束与压缩之前生成短交接（两半：叙事摘要 + 活动工作集引用）。
- **他证验收信号**：**下一次会话由另一方只读短交接开工**，能答出"下一原子动作是什么、上一次为什么停"。答不出 → 交接不合格。
- **空转信号**：`handoff.md` 的捕获时间长期不变而会话在继续。

### S8 · L2 起：`DECISIONS.md` 与生效登记表

- **做什么**：建唯一效力源。
- **他证验收信号**：全仓扫描状态值副本，第三处副本数 = 0。**注意扫描要认多种形态**（本仓库 [C-022](../失败Case清单.md)：只认括号形态，系动词形态漏了四轮）。
- **空转信号**：登记表的行数与实际决策数长期不一致。

**S8 之后的档位（L2 其余、L3）按 [03 §4/§5](03-通用落地套件.md) 建，每一项照本节的四栏格式（做什么 / 他证验收 / 空转信号 / 判不出时）自行补齐。写不出后两栏的项不算接入。**

## 4. 从半路接手：顺序不同，且第一步不是建东西

**接手与从头的根本差别**（本仓库读数六）：接手运行里任何一个字段都可能已经空转多轮，而从头运行里所有字段都是刚写的。因此**接手的第一步是测绘，不是建设**。

### H0 · 声明运行类型，并把出口写成"一份带成立条件的事实"

接入一个已有项目的第一次运行应当是 `事实型 × 接手`，出口是一份**现状测绘**，**不是变更**。理由是 [00 §3](../00-总览.md#default-scope)：事实型运行的出口是"一份带成立条件的事实、一个假设与一组待人裁决项"。

**他证验收信号**：这次运行结束时**没有产生任何条文变更**。产生了 → 说明它其实是交付型，运行类型声明错了。

### H1 · 测绘：这个项目现在有什么、哪些是活的

对项目里每一份"看起来像规范/清单/规则"的工件，填一行：

| 工件 | 它自称承载什么 | 最后一次被写 | 最后一次被读/被执行 | 判定 |
|---|---|---|---|---|
| … | … | <可他证的时间> | <可他证的时间或"不可得"> | 活 / **空转** / 未定 |

- **"最后一次被写"**通常可他证（版本控制历史、文件 mtime、任务系统的修改记录）。
- **"最后一次被读/被执行"**通常**不可得**——这正是问题所在。**不可得时记"不可得"，不要推断，也不要因为"它看起来很重要"就判它是活的。**
- **判定规则**：两栏都不可得 → 记 **未定**，进 H2 的抽查；"最后一次被写"很久以前且"被读"不可得 → 记 **疑似空转**。

**他证验收信号**：测绘表的每一行的时间值都能被第二个人独立复算。复算不出的行改记"不可得"。

**这一步的产出就是"哪些东西写着但从没被执行过"的清单。** 它是接手场景全部价值所在。

### H2 · 抽查：对疑似空转项做一次反例注入

对 H1 判为"疑似空转"的每一项，做一次**能观测到的破坏**：故意违反它一次，看有没有任何东西报出来。

- 报出来了 → 它是活的，改判"活"。
- 没报 → **确认空转**。此时有三个出口，选一个并记录理由：
  1. **删掉它**（它没有防住任何东西，且删掉后没人会发现）；
  2. **给它配一个探测**（它防的东西仍然重要，缺的是发现机制）；
  3. **判为取舍，不修**（代价大于收益）——**但必须写下判据**，本仓库 [C-021](../失败Case清单.md) 就是这样处置的：改动前后诊断条数一致即视为未引入新问题。

**他证验收信号**：每一项都有一个记录在案的出口选择 + 理由。**"以后再说"不是出口。**

**风险提示**：反例注入本身会改文件。本仓库 [C-012](../失败Case清单.md) 的教训（逐字）：注入脚本写成 `open(f,"w").write(open(f).read()...)`，先截断再读，于是读到空、写回空——**三个文件被清空**（靠备份逐字节复原）。**注入前先备份，注入后先断言待替换串确实变了。**

### H3 · 建缺的那几个：按 §3 的 S1→S3 顺序，但只补 H1 判为"缺失"的

**不要重建已有的。** 已有的重建就是造第二份——本仓库同一个病复发六次以上（[C-027](../失败Case清单.md) 逐字："每次都删掉副本、然后下一轮新造一份"）。

**他证验收信号**：补完之后，同一类工件在全项目里只有一份。由检查器扫描"同类工件的份数"，> 1 即 FAIL。

### H4 · 一次"照单加载"演练，由没参与测绘的一方做

同 S3 的第一条验收信号。**接手场景下这一步的价值最高**，因为它是唯一会去问"当前工作项是什么、事实源是哪份"的动作——本仓库读数六逐字：**"接手是唯一会去问这些问题的运行类型，从头做的运行不问，改条文的运行也不问。"**

### H5 · 转入 `交付型 × 接手`，跑第一次真实运行

同 S4，但加一个动作：对每个 ● 项回答 `last_written` / `last_read`（见 [03 §7.1](03-通用落地套件.md) 的接手格核对动作）。

| H2 | 反例注入（接手） | 每项一个出口选择 | **故意违反一次，看有没有东西报** | — | 三个出口选一个并写理由 |

## 6. 三个最可能出错的地方

### 6.1 把"建好了"当成"生效了"

这是本仓库五条 Case 的共同形状。**处置**：接入进度的计量单位不是"建了几个文件"，而是"**有几条条文从判不出变成了判得出**"。后者才是判据 A 的直接度量。

**一个可直接用的进度指标**：列出项目声称采纳的条文，逐条标 `可判定 / 判不出`。接入前后的 `判不出` 条数之差，就是这次接入的真实产出。**这个指标的好处是它天然是他证的**——"这条现在判得出吗"由一次实际执行回答，不由任何人的意见回答。

### 6.2 把探测建在被探测者身上

例：让执行者自己报告"我按合同加载了"；让写规则的人自己判断规则有没有被遵守；让检查器自己声明它覆盖了什么。

**处置**：每条探测写下来时，同时写"**产出这个信号的是谁**"。是被探测方 → 换一条。

### 6.3 只给流程不给上下文

卡 05 §8 的反判据（TDAD 的对照组，逐字）："adding TDD procedural instructions without targeted test context increased regressions to 9.94% -- worse than no intervention at all."

**处置**：`PLAYBOOK.md` 与 `ACCEPTANCE.md` 的骨架里都有 `需要的上下文` 字段（[03 §7](03-通用落地套件.md)）。**空 = 未完成登记**，检查器可扫。

**这个字段的空缺率是本文推荐的第一个健康度指标**，因为它是这套方案里唯一有实验对照支撑（虽然是小样本预印本）指向"负收益"的一条。

## 7. 两种机制类型的落法（D-020 §5 检验）

| 落地项 | 机制类型 A：**检查器** | 机制类型 B：**人工检查点** | 机制类型 C（备选）：**外部状态存储** |
|---|---|---|---|
| "照单加载"演练（S3/H4） | 不适用（这一步要的是人答不出来） | **一次具名的人工检查点**：由未参与方回答八项事实，答不上的项数入记录 | 把八项事实写成一份表单工件，每次运行填一次，历史可对比 |
| `why` 列无空 | 扫描，空行数 > 0 即 FAIL | 评审时逐行看 | 载体强制必填（任务系统字段不允许为空则无法保存） |
| 绑定 Case 可达 | 扫描，找不到即 FAIL | 评审时人工核 | 外键约束 |
| 检查器"最后执行时间" | 检查的检查（[30 §2 P7](../30-验证与测试.md)：检查器自身是被验证对象） | 定期人工巡检 | 每次执行写一条事件到只追加日志，超窗口即由查询发现 |
| 空转探测（H2 反例注入） | 自动注入 + 自动回滚 | 人工在隔离工作副本上做一次 | 保留一份"已知应被报出的实例集"，每次检查器变更后重跑 |
| 状态值副本 = 0（S8） | 全仓扫描，认多种形态 | 评审 | 载体只存一处，别处只能引用不能存值 |

**同属一个工具的组合不算数。** A 列与 B 列在任何 harness 上都可实现；C 列依赖载体能力，按 [09 §6](../09-跨工具通用性.md#detection-hints) 只作并列探测提示。

## 8. 本文未做的事，与最可能落不了地的一步

- **本清单没有在任何真实项目上跑过一遍。** 所有验收信号都是设计出来的，不是实测出来的。
- **H2 的反例注入没有给通用的注入方法**——它必然是项目特定的，本文只给了它的判据与一条安全提示。
- **"最后一次被读/被执行"在多数项目里不可得**，而本文的空转探测有一半依赖它。这是本方案最薄的一环，见下。
- **没有给任何窗口长度**（"超过多久未执行算空转"）——项目参数。
- 所有引自卡片的逐字内容继承卡片自身的验证边界（WebFetch 抽取，未字符级回原文比对）。

### 最可能落不了地的一步

**是 H1/S6 依赖的"最后一次被读 / 被执行"这个值。**

理由：它在多数 harness 上**根本不产生**。"这份文件被加载进了上下文"这件事，绝大多数工具不写日志、不写事件、也不暴露给工作流。于是本文所有空转探测里最重要的那一半，在真实项目上大概率取不到值——**而取不到值的处置是记"不可得"，"不可得"堆多了就等于没有探测。**

它有两条已知的降级路径，两条都不完整：

1. **用"最后一次被写"代替**——但本仓库的五条 Case 恰恰全是"写过、没人再看"，这条代替正好绕开了要探测的东西。
2. **每次运行由执行方主动记录"我读了哪些"**——这是**自证**，按 [31 §2 P9](../31-守卫与权限边界.md)与 [33 §2 P10](../33-评估与演进.md)不构成探测。

**因此本文对这一步的判定是「未定」**：在能拿到加载事件的执行环境上，本方案的空转探测成立；拿不到的环境上，**空转探测退化为 H2 的定期反例注入**——它有效，但成本高、频率低、只覆盖能被机械违反的项。**说不清怎么违反的项（例如一份"应该被读一读"的说明文档），本方案探测不了，应当记未定并在接入报告里列出。**
