## 0. 这是什么，为什么第十一轮才有

[33 评估与演进](33-评估与演进.md) §2 P1 规定："Case 注册表接受两种来源……已观察的失败附轨迹，已构造的失败附风险来源，两者同等登记并注明来源类型"，其 L0 形态是"一份不分区的失败 Case 清单"。**本仓库写下这条规定十轮，从未建过这份清单。** 本文是它的第一次落地，不是新机制。

这件事有后果，而且是硬的：

- [D-021](决策日志.md#decision-index) 要求每条规则绑定它防御的**可复现失败**。没有清单，56 条决策里的绝大多数至今绑不出来——这就是[自指风险一](../PROJECT_STATUS.md)。
- [33 §2 P9](33-评估与演进.md) 的 Thin 信号里，"长期无消费"是删除的主要正当依据。没有清单就没有消费计数，**Thin 判据在本仓库一直不可执行**——这就是自指风险二"只能删却不知道删什么"的直接原因。

## 1. 来源与证据等级

本清单前 12 条来自第九～十一轮在本仓库上的真实运行（提交 `9acf832`、`c1793e7`、`fdcd177`、`ff75b26`、`5ab136d`），C-013 起来自第十二轮的[事实型运行](审计记录/004-接手场景事实型运行.md)。全部非构造。但它们的可核性分两档，必须分开写——[自指风险三](../PROJECT_STATUS.md)登记过本规范前三轮有约 20 处转述失真，这里不能再犯：

| 等级 | 含义 | 条数 |
|---|---|---|
| **A｜仓库可复核** | 从 git 历史或当前文件即可独立复算，不依赖任何人的叙述 | 10 |
| **B｜仅会话记录** | 失败在同一轮内被当场修掉，未进入任何提交，只有会话过程为证 | 4 |

**B 档的存在本身是一条发现**，见 §3 第 2 条。

## 3. 从这批 Case 读出什么

**一、拦住东西的全部是机械检查器，正文的 117 条原则拦住 0 条。** 被当场拦住的只有 3 条（C-007 archify 校验器、C-008 检查器 C4、C-010 检查器 C10），无一例外是程序。这不是因为原则写得不好——是因为它们全部是`提议`，没有任何执行点，按 [D-014](08-规范效力元治理.md) 的效力语义本就不阻断。**这是 [D-008](决策日志.md#decision-index)「可确定的规则下沉到程序、测试、权限或 Gate」的第一份非构造证据**，也是 [23 §2 P1](23-方法库.md)「高风险动作靠自觉、'强制走链'只在文字里」的第一份。

**二、当场修掉的失败不留痕，于是"这条规则拦住过东西吗"永远无法回答。** B 档 4 条都是在同一轮内被修掉、从未进入提交的，仓库里查不到它们存在过（C-012 甚至一度清空了三个文件，复原后 git 里同样毫无痕迹）。[33 §2 P2](33-评估与演进.md) 要求"已观察的失败附轨迹"、[32 §2 P6](32-证据与追踪.md) 要求轨迹能还原调用与重试——两条在本仓库都从未落地。后果是 [33 §2 P9](33-评估与演进.md) 的 Thin 信号"长期无消费"**在本仓库不可执行**：不是没有消费，是从来没测过。本清单是这条链路的起点。

**三、写检查器本身出缺陷的频率高于写规则，而且缺陷形态是"能通过但不检查"。** 迄今写过 4 条检查（C7、C8、C9、C10），出了 **3 处缺陷**：C7 的正则混进不可见退格符导致恒不匹配（C-006）、C10 只认裸写形态认不出链接形态（发现于反例测试）、C10 对举例误伤（C-011，发现于实际运行）。**前两处"跑一遍看到 PASS"完全察觉不到**——这直接支持 [30 §2 P1](30-验证与测试.md)：未执行不得折算为通过，而"看起来通过"和"确实执行了"是两回事。第三处是相反方向的教训：检查一旦上线就会误伤合法写法，[33 §2 P9](33-评估与演进.md) 把误伤列为 Thin 信号是对的。

**四、第一次有了非"改条文"类运行的 Case，而它们的形状不同。** C-013 与 C-014 来自一次[事实型运行](审计记录/004-接手场景事实型运行.md)，两条都不是"某条规则失守"，而是**规则之间对不上**：一条是合同的视图边界没覆盖到真实用法，一条是正文把作用域写在了 09 §4 指定的字段之外。前 12 条几乎全是"该拦没拦住"，这两条是"规则本身互相不一致"。**这类缺陷机械检查抓不到**，只有真跑一次不同类型的运行才会撞上——这是继续攒 Case 时应当刻意换运行类型的理由。

**五、本仓库最看重的那条原则，第一次有了自己的真实样本。** [D-014 的空集合条款](08-规范效力元治理.md#empty-set)说"全部 X 通过"在 X 为空时应判 UNDETERMINED——C-012 是它的精确实例：我两次拿到空输出，两次都差点读成结论，而两次空输出的真实原因都是**采集根本没跑起来**（grep 语法错、注入脚本截断文件），与"检查失效"或"检查通过"都无关。**这条原则此前只有推理支撑，现在有观测了。**

**推论（本轮唯一的新做法，不是新规则）**：新增检查的验收不是"跑一遍 PASS"，而是四步——① 验字节（控制字符会隐身）；② 注入前断言待替换串存在；③ 反例测试确认它真报；④ 跑全仓看误伤。**任一步得到空输出即记未定，不得读作通过。** 四步写在[仓库工作须知 §2](附录-载体实例/仓库工作须知.md)。

## 4. 本轮刻意没有做的

**没有产生任何 Thin。** 按 [33 §2 P9](33-评估与演进.md)，Thin 的主要信号是"长期无消费"。本仓库的消费计数从今天才开始，**十轮没测量不等于十轮无消费**；用"没有数据"反推"可以删"，恰好是该条禁止的方向（"删除门槛低于新增"是给有数据的情形定的，不是给没数据的）。

因此第十一轮只做两件事：建立清单、把已发生的失败绑上去。删减要等这份清单有足够条数、且能看出哪些规则从没出现在任何一条 Case 的"本该防住它的规则"列里。

## 5. 登记规则

- 每条 Case 至少写：观察到的失败、证据等级（A/B）、本该防住它的规则、当时是否被拦住、处置。
- **等级 B 的条目要注明它为什么没进提交**；如果一类失败反复以 B 档出现，说明轨迹留存本身该被处置。
- 处置只有四种：**Add**（下沉为机械检查或补规则）、**Thin**（删规则）、**无需处置**（机制已生效）、**不可机械验**（记录原因，靠人复核）。
- 本清单只增不改：已登记的 Case 不因后来修好而删除——它是"这条规则拦住过东西吗"的唯一数据来源。
