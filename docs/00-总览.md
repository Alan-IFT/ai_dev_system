# 00 总览：一套 AI 辅助大型项目的开发系统

状态：`v0.7-theory-draft`
governed_by：D-014、D-020、D-043
用途：本文是全部正文的入口。读完应该能回答三件事——系统由哪些部件组成、部件之间怎么连、从项目第一天到维护第 N 个月它们怎样配合。各部件的细节在各自的章里。

架构的归纳过程与证据（52 个独立来源的部件频次、不可省略投票、失败归因）见[架构确定](架构确定.md)；本文只讲结论。

## 1. 一句话

> **AI 辅助开发系统 = 四个平面 + 一条交付线。**

四个平面按职责划分：**知识平面**说什么是真的、要做什么；**执行平面**把事做出来、并能接着做；**控制平面**判断做对了没有、有没有失控、怎么自我修正；**责任平面**是只有人能承担的那部分判断。交付线从意图穿到验收，贯穿四个平面。

这个划分的实际含义是：

- 知识平面是**资产**，随项目积累，换工具不丢。
- 执行平面是**工具**，随时可换——换 AI 编程工具，换的是这一层。
- 控制平面是**纪律**，可以只用文档和人工流程实现，不必先有工具。
- 责任平面是**人**，不可转移，不随模型能力消解。

## 3. 一条交付线

意图确认与冻结 → 从验收条目派生工作项与验证用例 → 每轮先读状态工件 → 派发一个可独立验收的切片 → 装配上下文 → 执行 → 从环境回读事实 → 三态裁定（通过 / 失败 / 未定）→ 证据写回状态 → 状态转换 → 验收。

三条规则贯穿全线：每一步的出口是可版本化、下一步能机器读取的工件；未执行与无法核验记为**未定**，不折算为通过；人只在五处状态转换上出现。

四个闭环是这条线上的回流：**交付闭环**即本线；**上下文闭环**在执行平面内（装配 → 使用 → 外部化）；**记忆闭环**是执行 → 控制 → 知识（经验候选 → 验证与治理 → 晋升为知识或方法）；**改进闭环**在控制平面内（观察 → 归因到层 → 可复现 Case → 修复 → 双路径验证 → 接受或回退 → 删减）。

## 4. 平面之间的接口

括号内是明确画出这条关系的独立来源数。

- 知识 → 执行：短入口按需拉取，不全量推送（24）；验收条目派生工作项与用例（12）；状态工件是每轮起点，不回放对话（20）。
- 执行 → 控制：执行事实由环境回读，不信模型自述（21）；子执行者只回结构化结果（18）；确定性判断先由程序做，模型只判残余（18）。
- 控制 → 执行：动作或阶段转换前阻断并回显原因（29）；独立验证者给出裁定与定位（22）；范围与预算在创建时固化、执行中只能收窄（15）。
- 控制 → 知识：证据与轨迹是评估、删减、到期审计的输入（28）；失败驱动规则与方法的增删（22）；状态转换处提取记忆候选并经治理写回（15）。
- 控制 → 责任：超限、门禁失败、告警升级到人（21）。
- 责任 → 知识：人确认并冻结意图（19）。
- 责任 → 控制：不可逆动作只能由人授权（17）。

## 5. 六条不变量

换任何工具都不变的六条。它们是各章原则的公共前提，与十四个部件并列，本身不隶属于任何一个部件。

1. **控制平面独立于执行平面**：验证者不是生成者，守卫在模型控制流之外。
2. **状态外置且朴素**：一份进度、一份清单、一份交接；编排靠读状态，不靠读对话。
3. **知识单一权威**：项目知识是唯一记录源，入口短、细节就近；代码图谱与记忆都是它的派生或候选，不是第二权威。
4. **事实来自回读**：执行事实来自环境观察与只追加记录，模型可见的都被记录；证据喂给演进。
5. **责任不可转移**：人是稀缺资源，检查点集中在少数状态转换，不可逆动作只能由人授权。
6. **边界外不由我们控制**：权威记录源不由本项目治理、或其上已发生的事不能单方面撤销的，即为外部。对外部：读只引用不复制；写只在声明的阶段窗口内、须幂等、须留回执，结果未知即记未定；可用性不保证，依赖分必需与推荐两档；唤醒不等于授权。默认跨边界多读少写。

## 6. 后期为什么会变慢：按部件的诊断表

大型项目到后期变慢，通常不是生成速度不够，而是某个部件失守。下表按"被多少来源归因"排序，可当作排查顺序。

| 症状 | 最可能失守的部件 |
|---|---|
| 做完了但说不清对不对；测试全绿仍出事 | [30 验证与测试](30-验证与测试.md)（32 个来源归因） |
| 新会话一开始就臃肿；规则越写越多却越不被遵守 | [22 上下文装配](22-上下文装配.md)（29） |
| 规则只写在文档里、从没拦住过任何事 | [31 守卫与权限边界](31-守卫与权限边界.md)（28） |
| 换个会话就失忆；中断后不知从哪继续；重复已失败的尝试 | [20 状态工件](20-状态工件.md)（27） |
| 规则与资产只增不减；改了很多但说不清有没有变好 | [33 评估与演进](33-评估与演进.md)（25） |
| 越权改动、并行互相覆盖、审批被绕过 | [31 守卫与权限边界](31-守卫与权限边界.md)（23） |
| 完成声明查无实据；成本不知去向 | [32 证据与追踪](32-证据与追踪.md)（22） |
| 按过期文档行事；文档与代码对不上 | [11 项目知识](11-项目知识.md)（21） |
| 人被打断到麻木；验收积压无人真判 | [40 人的检查点与授权](40-人的检查点与授权.md)（19） |

## 7. 从 L0 到 L3

四档不是必经阶段，是**同一套部件在不同规模下的形态**。升级到下一档的唯一条件是：上一档的验证能力跟得上。自主度的上限永远是"能廉价可靠验证的量"。

| 档 | 场景 | 这一档的重点 |
|---|---|---|
| L0 | 一人一工具 | 四个平面都存在，但全部是文档与人工流程：一份验收条目清单、一张模块地图、一份工作项与交接、几条踩坑规则、人自己确认五处。 |
| L1 | 一人多会话 | 跨会话的连续性成为主要问题：状态外置、交接两层、压缩当作事件处理、条目 ID 作为跨会话锚点。 |
| L2 | 团队 | 责任分离与一致性成为主要问题：验证者与生成者分开、写入权与生成权分开、事实门禁上线、记忆与方法进入治理、成本按单元可观测。**第六条不变量通常在这一档第一次真正生效**——组织已有系统进入回路，内部 / 外部标注与跨边界写纪律开始有对象。 |
| L3 | 无人值守 | 前置条件是"有一个不需要人在场就能拒绝坏输出的判定器"；预算与范围创建时固化、活性巡检、机制自身的消费与误伤计数。 |

各章 §4 给出本部件在四档的具体形态。
