## 2. 裁决：**不换骨架**

按 Alan 给的原则优先级逐条裁定，形式为「结论 + 其成立条件」（D-055 改动 3）。

### ① 行业标准规范推荐（最高优先级）→ **反对换骨架**

015 的独立取证（2026-09-04，逐条命令在该记录 §1）：该资源库当日约 32 星 0 fork；检索到的用词者是 2026 年 7–8 月的**博客与自媒体**（中英文都有），**无标准文件、无厂商官方文档**；两份中立评述明确否认其标准地位——TrueFoundry 称之为 "a naming event"，Turing Post 写 "None of this is new to software engineering. State machines, DAGs, workflow engines, and orchestration systems have been doing versions of it for decades."（**两处均为 015 自网页抽取，该记录自标未字符级回原比对**）。综述自称 "an emerging paradigm"，并把 Ontology Engineering 放进 **Future Direction**——即它不属图工程本体（卡片 01 已核实）。

**一份要管长期的开发规范，骨架不宜建立在一个刚出现不久、采用度极低的学术分类法上。** 015 给出该对齐的三份真标准：ISO/IEC/IEEE 12207:2026（生命周期骨架）、SLSA v1.2（provenance / attestation / levels，正对 32 章「完成声明查无实据」）、ISO/IEC 42001:2023（条件性——仅当最终形态是组织治理文件时）。**这三份的对齐工作 A/B/C 三个方案一条也没做**，是本轮真正暴露出的空缺。

> **成立条件**：若出现厂商官方文档、标准组织文件或多家独立厂商采用该术语与三层分类法，本条重判。检验点建议绑 D-057 复审日（2026-11-19）。

### ② 少就是多 → **反对换骨架（这一格不依赖计数）**

**正方自己交了械。** 013 §6.1 的自评（转述，非逐字）：它给不出换骨架删掉了什么；换骨架必然让总量上升；必然产生"新骨架 ↔ 旧 14 部件"对照表——而"删掉副本、然后新造一份副本"在[失败 Case 清单](../../失败Case清单.md)里已反复出现（**具体是第几次，清单内自身有 6/7/8 三种说法，本记录记未定，不取序数**）。第十轮实测：**移位改善单次阅读量，但总量反而上升；要降总量只能删除。** 换骨架是纯移位。

三方各自算的迁移成本口径互不相同（06 用 `G=(V,E,S,P)` 四槽、014 用三层+16 子类、013 用自建的关系容器），得数相差一个数量级；**013 另用 06 自己的容器逐条重判得 36 条，而 06 自报 57 条**。**013 自己给出了最有价值也最不利于它的读数**：这些数"是容器宽严的函数，不是理论的函数"，该口径应退场，**包括 013 自己那一个**。故**本格的裁决不使用任何迁移成本数字**——它只用"指认不出删除项"这一条。

**另一侧指认得出的删除项，本记录如实登记两条**：014 指认 **25-P3**（其规范内容被 31-P7 包含，`grep` 证实零入向引用，117→116）；015 指认**追溯账本 99 行取值相同的强度表**（审计 003 实测该尾标在三份演练中被引用 0 次，净减约 −1,200 字符）。**两条都不需要换骨架就能做。**

> **成立条件**：若能指出至少一条**只有换骨架才能删掉**的东西，本格重开。

### ③ 优先用好的设计避免修修补补 → **换骨架治错了层**

015 用 `git log` 查实：**正文 14 章连续 10 次提交 0 行改动**，churn 前六名"全是账本、状态、Case 清单与操作说明"。**注意这不等于"全是账本"**：015 §3.2 专门写过第一名 PROJECT_STATUS"是记账，不是结构"，现跑前六里只有决策日志一项是账本。审计 003 的结构判断在方向上被再次证实——"这套理论的结构没有过重，它的账本过重"——**但"账本"这个词在此处是简称，实际分布跨四类记账型文件。**

> **一处必须写下的限制**（[审计 016](../../审计记录/016-第二十四轮提交前对抗性复核.md) §4 Q-06）：churn 分布是**尺寸证据**，而"容器类型与内容类型是否匹配"是**类型问题**，尺寸不能直接回答类型。故本格的结论只到"换骨架治不了账本层的膨胀"，**不足以单独否定 §4 的类型失配**。
>
> **一个曾被考虑、已被证伪的反解释，记录在此以免下次重犯**：本记录第二版曾写"D-057 冻结了正文，故'不动'未必等于'稳定'"。**这是错的**——014 §7.8(d) 逐字判「生效规则受影响 **0**（修订正文在 D-057 授权范围内）」，且 `git show --numstat 32389c6` 证明 D-057 之后正文被改过。**但删这条时不要把仍成立的那一半带走**：015 §3.3 与[审计 007](../../审计记录/007-D-057作用域与本仓库自身合规.md) 的限定式命题——「**没有部件实例的原则**在此不被触发」（D-057 登记行作「没有实例的部件其原则在此不被触发」）——仍然成立，它同样能解释一部分"正文不动"。**注意这是限定式不是全称式**：跑 `repo_counts.py`，14 章里已被证明有实例的是 11、20、22、23、30、33 共 6 章（C-027 登记过这件事），**说"本仓库没有部件实例"是假的**。

> **成立条件**：若出现"新增内容无法归属于 14 部件之一"的实例（D-043 的证伪信号），架构问题重开。**本轮六份卡片未产生任何这样的实例**（此处的证伪信号计量单位是"主张条数"，不是字符数）。

## 4. 一个类型失配：正方守住的最小阵地

013 唯一守住、且不依赖图工程材料的论证。**013 §0 声明本节按未定读**（生成者与验证者同一），本记录沿用该标注。

审计 003 的根因 R1 是"边界被建模成对象的一元属性"，处置是把第六条不变量改写为关系模型，D-047 登记行自称"关系模型"。而审计 003 §4 判"只有 1 与 6 在任何单个部件里写不下"——这两条恰好都是**二元关系**（验证者 ≠ 生成者；权威侧 / 消费侧），只能挂在"架构级内容"这个例外层上，**而这个例外与 D-043 的 blocks 是同一天写下的**。即：**四平面是对象分类法，没有边；容器类型与内容类型不匹配。**

**013 与本记录在处置上不一致，如实记录**：013 §2.3 认为换一个容器之后这两条不再需要例外，"**这是收益不是损失**"；本记录不采纳换容器，理由在 §2② 与 §2③——但**这是取舍不是反驳**，013 那一点未被驳倒。
