<a id="canonical-states"></a>

## 1. 唯一状态机

工作项只能使用下表状态。`ACCEPTED` 是交付完成；`IMPLEMENTED` 只说明实现候选已形成。

增删一个状态应同时说明：它有与相邻状态不同的失败模式、失败后的回退目标不同、有单一责任主体、退出条件可观察；并标注它为验证、责任还是人类交接而存在，为交接而存在的状态按运行数据定期复审。状态机不向上游需求规划延伸。表中“失败/变化回边”一律定向到出错状态并携带驳回原因。

| 状态 | 进入输入 | 主要输出与责任 | 退出 Gate | 失败/变化回边 |
|---|---|---|---|---|
| DEFINED | 业务问题与负责人 | 已批准目标、非目标、稳定验收 ID；产品负责人负责 | 验收可观察、开放问题有归属 | 目标变化留在 DEFINED |
| DESIGNED | DEFINED | 边界、关键流程、风险、技术方案、验证与回滚思路；产品/技术负责人批准重大取舍 | 关键约束和影响面可执行 | 发现需求空洞回 DEFINED |
| READY | DESIGNED | WORK_ITEM、范围、工作区、target environment、Gate 清单；执行负责人负责 | 事实入口可读、权限和验证计划明确、隔离工作副本上的验证基线已记录并绑定工作区身份（字段见 [05 §4](05-质量闸门与交付证据.md#evidence-package)）、关联切片共享版本一致 | 身份/依赖缺失回 DESIGNED 或 BLOCKED |
| IMPLEMENTING | READY | 最小实现、测试和持续观察；实现者负责 | 尚无阶段完成声明 | 新事实推翻方案回 DESIGNED；故障可进入 BLOCKED |
| IMPLEMENTED | IMPLEMENTING | 与当前 revision 绑定的局部实现与验证结果 | 实现范围满足、局部检查通过 | 失败回 IMPLEMENTING |
| INTEGRATION_READY | IMPLEMENTED | Review 结论、项目级 CI、迁移/配置/回滚准备 | 生效 Gate 全部通过或存在有效豁免 | finding 或 CI 失败回 IMPLEMENTING |
| RELEASED | INTEGRATION_READY | 目标环境发布记录与 readback；发布负责人负责 | 目标环境身份和关键观察匹配，且无未补偿的外部写入（结果未知者为未定，解除只能靠回读） | 发布失败回 INTEGRATION_READY 或执行回滚 |
| RELEASE_NA | INTEGRATION_READY | `N/A` 理由、适用边界、批准人和批准时间 | 明确无需发布且不隐藏环境验证 | 理由不成立回 INTEGRATION_READY |
| ACCEPTED | RELEASED 或 RELEASE_NA | 每个验收 ID 的 acceptance evidence、遗留与风险接受；产品/指定验收人负责 | 验收逐项通过，限制已公开 | 验收失败回 IMPLEMENTING、INTEGRATION_READY 或 RELEASED |
| OPERATING | ACCEPTED | 指标、事故、维护和反馈；运行所有者负责 | 新需求/缺陷建立新工作项 | 事故进入响应流程，不能改写历史验收 |

`BLOCKED` 是附加标记，不是乐观完成状态。必须记录阻塞原因、所需新证据或决策、owner 和复查条件。进行中的工作项必须绑定可探活的执行者与最后活动时间（活性不变量）；失去绑定或超期即转 BLOCKED 并通知，而不是保持进行中；未到合法停止点不得静默停止。恢复语义见[会话结束与恢复](03-上下文与会话协议.md#session-end)。

<a id="phase-guidance"></a>

## 2. 各阶段候选实践

### 定义与设计

- 说明用户、问题、目标、非目标、页面/入口和关键状态。
- 验收条目使用稳定 ID，描述可观察结果、目标环境和风险；对抗性分析中被接受的发现转为新条目。条目确认后冻结语义，实施期修改须记为验收变更并回原批准人。
- 明确安全、隐私、可靠性、性能、成本与可观测性边界。
- 技术栈优先选择可测试、可进入 CI、团队可维护且资料充分的方案。

### Ready 与实施

- 工作项与验证用例都从同一份已批准验收条目列表派生，下游不得重新解释意图，不从聊天灵感直接开工。
- 先读取相关源定义与测试，记录观察，不根据文件名猜行为。
- 计划包含验证、发布/N/A 条件和回滚思路。
- 只修改切片所需范围；执行中遇到的无关阻力记录为改进候选，现场解决需范围变更批准。“实现完成”包含该实现的验证手段，由独立角色对照验收条目审查；证明修复的测试不得由修复者修改。

### 集成、发布与验收

- Review 检查正确性、回归、安全、可维护性和文档一致性。
- 发布前核对制品、配置、迁移、监控和回滚；高风险功能采用受控发布。
- 发布后从目标环境回读版本和关键旅程；本地通过不等于已发布。
- 验收逐项绑定 evidence package；没有目标环境的工作必须明确 `RELEASE_NA`，不能省略发布状态。

### 长期维护

- 依赖升级小批次处理；重构绑定具体痛点和成功指标。
- 事故记录时间线、最早偏离点、恢复证据和回归 Case。
- 规则与 Harness 根据真实失败 Add，根据无收益、重复或误伤 Thin。

<a id="fault-stop"></a>

## 3. 故障止损候选

停机条件三类并存，任一触发即转 BLOCKED 并升级，附已尝试记录；它们不限制有信息增益的系统排查：

- 证据型：同一报错、同一假设和同一类修复重复出现，且没有产生新日志、最小复现、范围缩小或排除项；
- 停滞型：连续多轮无新发现或指标无提升（轮数为项目参数），“新”相对全部已见项（含被否决项）判定；
- 上限型：轮次或预算耗尽。

重试前须改变至少一个输入变量并记录；改变变量不自动构成新证据，换模型、改 Prompt 或补上下文本身不自动算新路径。重试预算按失败所在层分配：被验对象错回实施、验证设计错回设计，只有验证执行错允许原地重试。

触发后：保留原始错误与复现步骤，列出已确认/排除/未知，写可证伪假设清单，用可识别、可机械清除的临时观测取运行时证据，复现由人或可信环境执行，定位执行链最早偏离层，获取新观察或升级所需权限/架构决定。同层修复后复发即视为误诊，下一轮换层。有新假设或新证据后才进入下一轮。

<a id="state-transition-record"></a>

## 4. 状态转换记录

每次转换至少记录：`from/to`、work_item_id、state_revision、actor/owner、occurred_at、[工作区身份](03-上下文与会话协议.md#workspace-identity)、target environment、gate_id、三态裁定（通过 / 失败 / 未定（UNDETERMINED）及其子原因）与定位信息、evidence links、触发来源（工件事件或人工改写，人工改写标低可信）、有效豁免和限制。延期或取消时附下游影响链。裁定是与执行者无关的结构化结果：验证层未执行、外部写入结果未知、审批应答缺席、生成者与验证者同一，均记为未定，不得折算为通过。

过程度量（耗时、消耗含子执行者、重试、改动量）由事件采集，不由执行者自报。

具体 Gate 的合同语义见[质量闸门与交付证据](05-质量闸门与交付证据.md#gate-contract)。若最低 Gate 尚未被接受，不得用“适用 Gate”把空集合解释为已通过。
