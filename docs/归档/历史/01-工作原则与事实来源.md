<a id="responsibilities"></a>

## 1. 候选责任边界

- 人类负责产品目标、非目标、优先级、重大取舍、风险接受和最终产品验收。
- AI 负责调查、方案比较、实现候选、机械检查、证据收集和状态归纳。
- 可机械验证的判断优先交给程序；不可机械化的价值与风险判断必须有明确责任人。
- AI 可以提出改变边界的候选，但建议、记忆和聊天均不构成授权。

<a id="claim-model"></a>

## 2. 主张模型

先明确要证明的主张，再讨论哪个来源有权定义、哪些观察能够支持。五个概念不可互换：

| 概念 | 定义 | 例子 | 不能单独证明 |
|---|---|---|---|
| Claim / 主张 | 带范围、时间、版本和环境的待判断陈述 | “revision X 在 staging 满足 AC-12” | 自身真假 |
| Source of record / 权威记录源 | 对某类意图、定义或状态具有治理权限的载体 | 已批准 PRD 定义产品意图；对应 revision 的源码定义实现 | 目标环境已实际生效 |
| Observation / 观察 | 在明确时间、环境和方法下直接读取到的结果 | 当前工作副本版本、部署版本、readback、日志值 | 超出观察范围的结论 |
| Validation result / 验证结果 | 对工件执行指定过程后的结果 | 某 revision 的测试运行、构建、人工 Review 结论 | 未执行环境或未覆盖行为 |
| Acceptance evidence / 验收证据 | 将验收 ID、版本、环境、过程、结果、工件和限制绑定的证据包 | AC-12 对应的 CI 报告与 staging readback | 未列出的验收或环境 |

代码和配置是某 revision 的源定义；测试文件描述预期或检查器；只有测试实际运行记录才是验证结果。部署记录说明发生过部署动作，目标系统 readback 才能观察实际状态。同理，长时或异步执行的即时输出只说明动作曾被发起，带任务标识的持久完成标记或目标状态的预期变化才是观察；外部写入的结果在回读前是未定（UNDETERMINED，结果未知），不得记为成功。自动化运行应记录它实际消费的输入版本，"已生效"只对照该记录判定。工具副作用由系统直接观察或由工具声明，不由模型转述。

<a id="authority-by-question"></a>

## 3. 按问题指定权威记录源

不存在对所有问题都最高优先的单一文档。每个 claim 应记录 `claim_id`、claim 类型、owner、source of record、supporting observations/results、scope、revision、environment、observed_at 和 limitations。

| 要回答的问题 | 首选 source of record | 常见支撑观察/结果 |
|---|---|---|
| 产品应该怎样工作 | 已批准 PRD、验收标准、产品所有者决定 | 原型评审、用户研究、验收记录 |
| 系统边界和关键取舍 | 生效架构说明与 ADR | 架构测试、依赖分析、评审结果 |
| 某 revision 定义了什么实现 | 对应源码、配置、生成契约 | 静态分析、构建、测试运行 |
| 某环境实际部署了什么 | 发布系统记录 | 制品摘要、目标系统版本 readback |
| 某次运行实际发生了什么 | 该次运行的直接观察 | 日志、指标、trace、业务结果 |
| 当前任务在哪里 | WORK_ITEM | 工作区身份与工件核对、SESSION_HANDOFF 差异 |
| 当前项目里程碑 | PROJECT_STATUS | 活动工作项索引与负责人确认 |

每类工件在任一时刻只有一个权威记录系统；存在副本时应声明主从或至少互链。由代码派生的导航索引可以存在，但只能作为声明的缓存（存在条件见 §4），不得成为第二事实来源。工件归属优先由其可推导属性（所在工作区、绑定 revision、生成事件）确定，与生成者的自我声明冲突时以推导为准。

<a id="claim-conflicts"></a>

## 4. 冲突处理候选协议

发生冲突时不静默挑选一个来源：

1. 写出互相冲突的 claim；
2. 分别记录 source、owner、scope、revision、environment 和时间；
3. 区分意图冲突、源定义冲突、状态过期、观察差异或验证盲区；
4. 标记当前可确认、已排除和未知项；
5. 由有权责任人决定改变意图、实现、部署还是状态记录；
6. 形成新的验证结果后再推进。

新摘要不能覆盖原始来源，也不能用复制旧内容的方式制造“新权威”。由代码派生的导航、摘要或地图只能作为声明的缓存存在，须同时满足：记录派生来源与源版本；在变更进入主线前由检查器与源机械对账，差异由人分诊；人工写入区受保护并对自动区有覆盖权；再生成只追加不可覆盖的变更记录。缓存供人与 Agent 共读，不为 Agent 维护与人读版本分离的第二副本。

<a id="document-budget"></a>

## 5. 文档预算候选

- 状态和入口保持短小；超出预算时归档历史，不压掉风险、身份与下一步。
- 工作项只覆盖一个可独立验收切片；PRD 不记录实现过程。
- 架构正文只保留当前生效设计，历史取舍进入 ADR。
- 派生知识（由代码或文档生成的索引、摘要、地图）记录源版本，差异超出项目声明的阈值即机械判过期；过期者默认不作事实，只可带“待核实”标签引用。
- 经验知识（排障结论、兼容性、口述背景）带 scope、产生事件与产生时版本；scope 内源变化触发复核，而非静默沿用或机械判过期。
- 固定行数、Token 百分比或目录深度不作为跨项目硬规则，只能成为可评估的项目参数。

<a id="development-principles"></a>

## 6. 开发原则候选

- 采用端到端小切片，避免前后端或模块长期各自堆积后才集成。
- 修改前搜索既有抽象、契约和测试；不顺手扩大范围。
- 密钥与高权限凭证不进入前端或仓库；高风险动作由实际权限和动作前 Gate 控制。
- 新依赖、外部服务、破坏性数据变更和安全边界变化需要显式决策。
- 同输入同输出且规则可完整表达的问题优先使用普通程序，不每次调用模型重新判断。
