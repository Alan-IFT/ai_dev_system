## 1. 研究对象

我们研究的不是“怎样写出一个万能 Prompt”，而是怎样建立一套可以长期交付和维护软件的 **AI 辅助开发系统**：

> AI 辅助开发系统 = 人类治理 + 模型 + 项目知识 + 任务状态 + 工具与环境 + 工作流与权限 + 验证与反馈

模型只是其中一个可替换组件。一个模型能生成正确代码，不代表系统已经能安全、连续、可验证地交付。

## 2. 四类工程范式的关系

| 范式 | 主要问题 | 不能单独解决的问题 |
|---|---|---|
| Prompt Engineering | 单次调用如何表达任务、约束和输出 | 动态检索、跨会话状态、外部执行与长期治理 |
| Agent/行动循环 | 模型如何观察环境、选择工具并迭代行动 | 信息持续膨胀、事实可信度、记忆写入与交付证明 |
| Context Engineering | 每次推理应让模型看到哪些高价值信息 | 权限是否可执行、真实系统是否改变、结果是否通过验收 |
| Harness Engineering | 怎样把知识、工具、权限、状态、门禁和反馈组织成可运行环境 | 产品方向、风险接受和价值判断仍需人类负责 |

它们是互补关系，不宜简单理解为后一种完全替代前一种。

## 3. 八个系统层

| 层 | 回答的问题 | 主要产物 |
|---|---|---|
| 1. 意图与权威 | 做什么、为何做、谁能决定 | PRD、非目标、验收标准、风险所有者 |
| 2. 事实与知识 | 哪个 claim 的 source of record 是什么 | PRD、契约、架构、ADR、源码/配置、来源元数据 |
| 3. 上下文 | 本次推理应加载什么 | 短入口、当前任务包、按需检索结果、压缩摘要 |
| 4. 长期记忆 | 哪些非权威经验应跨会话保留 | 情节、偏好、事实/程序候选及索引 |
| 5. 状态与工作流 | 现在做到哪里，怎样交接 | 工作项、状态机、检查点、交接合同 |
| 6. 工具与执行 | Agent 能做什么，怎样安全地做 | 工具接口、沙箱、权限、幂等与回滚能力 |
| 7. 验证与证据 | 怎样证明特定 claim 已满足 | 验证结果、验收证据包、发布回执、运行回读 |
| 8. 评估与演进 | 怎样发现系统退化并持续改进 | 轨迹、失败分类、评估集、指标、Add/Thin 记录 |

安全、隐私、成本、可观测性和人工责任贯穿全部层，而不是单独放在最后补做。

## 4. 四个闭环

### 4.1 交付闭环

意图澄清 → 带稳定验收 ID 的条目列表（对抗性发现并入其中，确认后冻结）→ 从同一列表派生工作项与验证用例 → 记录验证基线 → 实施 → 状态转换 Gate（三态裁定：通过 / 失败 / 未定）→ 环境验证 → 现实回读 → acceptance evidence → 验收。

每一步的出口是可版本化、可被下一步机器读取的工件；未执行、无法核验的环节记为未定，不得折算为通过。

代码是中间产物。`IMPLEMENTED` 与 `ACCEPTED` 不同；完成必须绑定验收 ID、版本、环境、过程、结果和限制。验收条目列表是唯一来源，下游不得重新解释意图；生成权与写入权应结构分离，证明修复的验证用例不应由修复者修改。

### 4.2 上下文闭环

任务识别 → 入口路由 → 按需检索 → 来源/版本/范围校验 → 组装工作集 → 使用 → 清理或外部化。

上下文不是知识库的副本，而是当前一步需要的临时工作集。

### 4.3 记忆闭环

任务产生经验（含消费记录与多次尝试对比）→ 在交付链状态转换处提取候选 → 核对来源、范围与置信态 → 按影响面与判定器可得性决定审批方式 → 晋升项目知识/程序资产或归档 → 建立索引 → 按使用方式召回 → 使用后记账与验证。

晋升按入池条件（客观交付信号）、权威性（owner）与影响面三维分级：模型自身推断与输出不得成为候选；带独立判定器证据、影响面局部的经验可按[记忆管理](04-记忆管理.md)§5 自动晋升并可事后否决；全局规则、安全边界、评估集、回滚与冷启动种子必经人审；审批点位于进入权威载体或默认可见范围之前。知识与长期记忆的运营边界见[记忆管理](04-记忆管理.md#operational-separation)。

### 4.4 改进闭环

观察真实任务（含 Harness 机制自身是否被消费、是否误伤）→ 找到最早偏离点并归因到层 → 形成可复现 Case（已观察或已构造，均入注册表）→ 限流地提出候选 → 修复根因 → 用原失败路径与一条正常路径验证 → 接受或回退 → 按三种触发删减失效控制（日常观测 / 模型代际全删对照 / 周期清扫）。

新增 Harness 组件与删除 Harness 组件都应有证据；删除的证据是绑定 Case 不再复现或长期无消费，删除门槛应低于新增。

## 5. 稳定原则与可变实现

<a id="candidate-stable-principles"></a>

### 候选稳定原则（效力见生效登记表）

- 用项目内、可版本化、可追溯的事实替代聊天记忆。
- 给 Agent 地图和检索能力，而不是默认加载百科全书。
- 确定性要求进入程序、测试、权限或 Gate，不只写成提醒。
- 长任务靠持久工件恢复任务，不依赖恢复某次会话。
- 每次只推进可独立验收的端到端切片。
- 证据必须绑定版本、环境、时间和适用范围。
- 模型和 Harness 的变化必须通过代表性任务评估；评估器与评估集本身也是会退化、会过期的组件，须被校准并绑定版本。
- 人类保留产品方向、高风险权限、知识晋升和最终风险接受权。

### 明确属于载体绑定

以下均为**载体绑定**，不进入规范正文。判定与处置见[跨工具通用性](../../09-跨工具通用性.md)（D-020，已接受）：

- 入口文件的名称与位置；
- 状态、知识与证据的存储形态（文档、结构化数据、任务系统或数据库）；
- 目录深度、文件行数、上下文预算比例或检索条数；
- 单 Agent、多 Agent、固定 Workflow 还是自治 Agent；
- 具体模型、工具、框架和产品；
- 钩子事件、命令名、角色名与权限配置的具体形式。

这些只能在项目和模型的真实评估中确定，不应先写成跨项目真理。本清单原为凭直觉划分；D-020 接受后改由三条判据判定——信息源头在哪、责任能否转移、换工具要不要改。

## 6. 人类与 AI 的责任边界

| 事项 | 人类 | AI/自动化 |
|---|---|---|
| 产品目标、非目标、优先级 | 决策并负责 | 澄清、比较、记录 |
| 架构和风险取舍 | 对重大取舍批准 | 调查、提出方案、实现已批准方案 |
| 项目事实维护 | 指定所有者并审核权威变更 | 检测冲突、提出更新候选 |
| 代码和测试 | 按风险决定审查深度 | 实现、运行、收集证据 |
| 安全和不可逆操作 | 授权并接受剩余风险 | 在权限边界内执行，遇边界升级 |
| 完成判定 | 接受产品结果 | 提供机器结果和可复查证据，不自封完成 |
| 需要人决定的问题 | 价值排序、范围边界、权限授予、不可逆选择 | 先穷尽可读事实，只上交这四类问题 |
| 授权移交（自批、预批准动作集） | 慢变、可审计地批准并抽样复核 | 记录判断信号与理由，不自行扩大授权 |

“人类负责判断、AI 负责体力活”是起点，但不够精确。可机械验证的判断应自动化；不可机械化的价值与风险判断必须有明确责任人，且人应声明自己实际审查了什么。

人类保留的检查点应集中在五处状态转换——确认意图、接受计划、批准集成、授权发布、抽查自动决策——而不散布在动作流中；并行自主流的数量以人能认真审查的数量为上限。外行加 AI 可以提出挑战，不能替代有验证能力者的最终判断。

## 7. 最小落地顺序

1. 先跑一个真实、低风险、可验收任务，建立基线；存量项目的第一个真实任务可以是资产盘点。
2. 补齐任务实际缺失的事实入口、启动方式和验收证据。
3. 对重复出现的人工纠正或被重复生成的一次性工件，依次考虑文档、Runbook、预批准动作集、Skill、脚本或 Gate；一次性工件本身不进入常驻 Harness。
4. 阶梯双向：路径未知时可先用自治执行跑通，同一输入多次运行结果一致的步骤即降级为确定性程序；只有固定路径无法处理、且任务重复到足以摊销结构成本时，才升级到多单元编排。验证器必须先于自动触发器就位。
5. 用真实失败和成功 Case 评估改动；长期无价值或频繁误伤的控制应删减。

这意味着 Harness 应从任务中生长，而不是先建一个抽象平台再寻找使用场景。
