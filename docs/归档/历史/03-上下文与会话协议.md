# 上下文与会话协议

状态：`v0.6-theory-draft`  
governed_by：D-001、D-006、D-015、D-016、D-020、D-030、D-031、D-032、D-036
效力查询：[决策日志 · 生效登记表](../../决策日志.md#effective-register)

> 决策效力：本文规则的效力由上方 `governed_by` 所列决策在[生效登记表](../../决策日志.md#effective-register)中的状态决定，本文不复制状态值。未登记的决策为`提议`：不阻断、不授权。未标注规则按[分向降级](../../08-规范效力元治理.md#unmarked-default)处理——可作为拒绝理由，不可作为授权理由。

目标：让新会话恢复到正确任务状态，同时不把项目历史取并集塞入上下文。

<a id="one-contract"></a>

## 1. 唯一上下文合同

每个项目只设一个 Default Context Contract。它列出精确路径、可选片段、当前工作项、相关决策、合同版本和缺失处理。README、项目状态和工作项只能链接合同，不复制第二份默认加载列表。

合同只负责路由，不复制 PRD、架构、工作项或证据正文。链接不自动递归展开，加载集合按 canonical `path#fragment` 去重。

合同可采用 Markdown、JSON 或任务系统字段；载体可变，但以下语义不可缺失：`contract_id`、`revision`、`updated_at`、`current_work_item`、`required_context`、`optional_context`、`excluded_context`、`missing/conflict behavior`。

<a id="state-artifacts"></a>

## 2. 三类状态工件

| 工件 | 唯一职责 | 必要身份 | 是否直接覆盖其他工件 |
|---|---|---|---|
| WORK_ITEM | 当前任务的实时状态源：范围、验收、阶段、阻塞、下一原子动作 | work_item_id、state_revision、updated_at、owner、**工作区身份**、target environment | 否；只更新本任务 |
| SESSION_HANDOFF | 某一时刻的临时恢复快照 | handoff_id、work_item_id、captured_at、source_state_revision、**工作区身份**、未提交/未保存变更、证据链接 | 否；恢复核对后合并回工作项并归档 |
| PROJECT_STATUS | 跨工作项的里程碑摘要、项目级风险与优先级 | status_revision、updated_at、owner、项目范围、last_verified_at | 否；不承载实时步骤 |

<a id="workspace-identity"></a>

**工作区身份**是本规范的语义要求，不绑定任何版本控制系统：一条状态记录或一份证据，必须能被归属到一个**具体的、可重新验证的工作副本快照**。它至少要能回答"是哪一份工作副本"和"是它的哪一个版本"，且该标识可与实际工件交叉核对——仅凭记录自称不算。

探测提示（并列形态，不是必填字段）：版本控制项目中通常是仓库、工作树、分支与提交标识；容器化或制品化流程中可能是镜像或制品摘要；任务系统或云端工作区驱动的流程中可能是快照 ID 或工作区 ID。项目选定其中一种后在本项目内保持一致即可；本规范不规定选哪一种，也不维护各工具的对照表（见 [D-020 §6–§7](../../09-跨工具通用性.md#detection-hints)）。

项目知识描述系统和需求；状态描述“现在在哪里”。状态可以快速变化，所以必须带时间与工作区身份，不能因写入持久文件就被称为稳定事实。

<a id="state-conflicts"></a>

## 3. 新鲜度与冲突协议

1. 先确认 `work_item_id`、[工作区身份](#workspace-identity)和目标环境是否相同；身份不同的记录不可直接比较。
2. 对同一身份，WORK_ITEM 是实时任务源；`state_revision` 较高者优先，但仍需与 Git/工件交叉核对。
3. SESSION_HANDOFF 只是快照。若它比 WORK_ITEM 更新，不直接覆盖；先重放差异、核对工作区，再由恢复者递增 WORK_ITEM 的状态版本。
4. PROJECT_STATUS 只决定里程碑和项目级优先级，不覆盖任务内下一步。
5. 时间或 revision 缺失、倒退、相同版本内容不同、工作区不匹配时失败关闭：标记冲突，不继续沿用旧验证结果。
6. 状态字段有失效责任：阶段切换时写入方应更新或移除过时字段（如上一阶段的"当前文件""当前错误"）；读取方不应把"记录里还在"当作仍然有效。

<a id="context-levels"></a>

## 4. 分层加载

- L0：合同明确列出的入口与当前工作项；
- L1：当前任务明确引用的代码、测试、PRD/架构片段、生效 ADR 与契约；
- L2：仅调查时读取的历史工作项、旧方案、完整故障史、来源材料和无关模块。

“可能有用”不是加载理由，但给少了也有补偿成本（更多搜索、测试与修复），加载以当前步骤所需为准。先索引、后正文；先片段、后扩展；索引与项目级入口只做路由（去哪找 + 一句摘要），不具权威，与就近细节冲突时以细节为准，索引失配应可检测。会话启动的固定开销（系统级指令、能力描述、输出格式约束、路由类元机制）计入上下文预算：能力描述按需注入，角色可见的能力集作为慢变配置而非逐轮增删。固定 Token 百分比和固定 Top-K 只是项目参数。

<a id="session-start"></a>

## 5. 会话开始候选协议

在改动前，执行者应能基于工件而非聊天回答：目标与非目标、当前工作项和状态版本、工作区身份、事实源、目标环境、验收 ID、风险/阻塞、未决策项。

若项目意图、源码定义、测试运行或目标环境观察冲突，使用[主张模型](01-工作原则与事实来源.md#claim-model)分类，不把代码或摘要自动当成产品意图或运行事实。

<a id="session-run"></a>

## 6. 会话执行候选协议

1. 先调查和记录观察，再形成计划；计划以工作项范围为边界。
2. 关键判断写明 claim、来源/观察、适用范围和未知项。
3. 进展以可独立验证的步骤或 Gate 为周期外部化（当前理解、已完成、待办），不只在结束时；进度状态存于会话外，会话内只输出最小变更行，不复制完整背景或工具输出；组装输入时稳定内容在前、易变内容在后；恢复靠读记录，不靠回放历史。
4. 权限与 Gate 只以已生效决策和实际执行机制为准；草案文字不能扩大授权。
5. 向人提问前应穷尽环境中可直接读取的事实；上交的问题应限于价值排序、范围边界、权限授予、不可逆选择四类，并附已查证事实与待决选项；面向人的输出先给少量决策点，确认后再展开；记录选项、取舍、建议、默认影响和决定人。
6. 任务所需的固定观察集可由确定性程序在推理前采集，或在执行时由程序过滤后再交模型；已知且可程序化判定的盲区检查（改动后影响分析、执行后产物盘点）由系统在动作后确定性触发，结果作为带产生时间与触发事件身份的观察推送到下一步推理，消费后即清理、不累积。

<a id="session-end"></a>

## 7. 会话结束与恢复

未完成任务在会话结束前生成 SESSION_HANDOFF，压缩前同样生成。交接分两层：窗口内短交接只含当前判断所需的结论、关键决策、已完成项与证据位置、未完成原因、[工作区身份](#workspace-identity)与未提交/未保存变更、状态版本、捕获时间、目标环境、最后验证时间、已执行的不可逆动作清单、风险和下一原子动作；窗口外完整产物（方案、源码证据、diff、测试结果）原样保留、不改写、不预先塞入，接收方按位置回源。

恢复者先核对 handoff 与工作区身份及 WORK_ITEM 状态版本，再核对已执行的不可逆动作清单与外部回执：恢复即从上一检查点之后重放，已发生的不可逆副作用必须跳过或补偿，已确认结果不得丢失；不可逆动作前状态必须已同步持久化，对外部系统的写只在声明的阶段窗口内进行，写失败须入待补偿记录，依赖该写入的状态在补偿完成前记为未定（UNDETERMINED，结果未知），不得宣告。核对成功后把有效变化合并回 WORK_ITEM 并归档 handoff；里程碑变化才更新 PROJECT_STATUS。恢复入口由持久工件的存在性决定，会话开始与压缩后都重新提供；未达合法停止点的停止视为需拦截的动作，生成交接是合法停止点之一。

<a id="compaction"></a><a id="compaction-protocol"></a>

## 8. 压缩与外部化协议
压缩与会话结束是同等的、可在其前被拦截的生命周期事件：压缩前先把关键状态、失败尝试转成的教训条目（假设、证据、为何失败）与活动工作集引用外部化，原始错误轨迹随后丢弃、不进长期记忆。触发条件除窗口余量外应含行为信号（重复询问已确认事项、重复同类错误、任务阶段切换）与单会话历史增长曲线，具体阈值为项目参数。压缩策略（清空 / 确定性截断 / 摘要 / 外部化为交接件 / 主动结构化笔记）是显式选择，每种应声明丢失什么、保留什么。压缩产物分两半且不互相替代：叙事摘要（目标/范围、已生效决策、状态身份、未解决错误、验证结果、风险、下一步、原始位置）+ 活动工作集原文（正在编辑/验证的少量工件按引用原样重载）。窗口重建后必须重新核对合同、WORK_ITEM、工件与关键验收记录，并把任务不变量（目标/范围、已生效决策、安全边界、工作区身份）重新锚定到高注意力位置，规则优先级显式声明而非靠出现次数或措辞强度暗示；具体位置方向只是并列探测提示。Compaction 不是项目知识或长期记忆，也不能自证正确。

### 8.1 工具返回与工件的进出
工具返回默认只服务当前决策：决策后窗口只留结论与回源位置，原文外部化到可回读位置，不随历史逐轮携带；大体量外部数据由短生命周期执行单元消化，进入长生命周期单元的只能是结构化摘要与引用。超出单次输出可靠承载的工件不应以"模型完整输出"往返：读入只得引用与局部窗口，修改只做局部替换，写回外部系统时内容取自持久工件而非模型输出。拦截的失败语义按后果非对称：读路径失败可降级放行并留痕，写路径失败应关闭并转人工。

### 8.2 有损观察压缩
对执行者观察结果（命令输出、检索结果、日志）做有损压缩时必须：有可机械检测的损失信号；命中信号后自动回退无损；验证、审查与验收环节不使用有损输出（删除条件：模型能从压缩摘要识别线索缺失并主动回源）；采用/跳过/回退可记录，并按整任务而非单条输出评估。程序侧注入与过滤须有大小上限与截断规则。评价此类机制时，组件级对照只能对局部输出层下结论；凡改变模型所见信息的机制须另报路径层指标（口径见 [06 §8](06-评估与演进.md#metrics-candidates)）。

### 8.3 隔离原语
上下文隔离至少区分三类原语：委托（不继承历史、只回结论）、分叉试探（继承全部历史、产物不回流主线、用完即弃）、压缩外部化（主线自身瘦身），按"任务是否依赖已有上下文"与"产物是否需回流"选择；试探性方案与一次性产出默认走分叉试探，独立的高输出操作默认走委托。隔离委托必须声明是否继承治理规则（项目入口指令、权限边界、安全规则），未声明视为不继承；不继承者只授予只读或纯输出型任务。交给低能力或低成本执行者的子任务应原子（完全独立、不需跨轮累积、输入输出与验收在派发时写清），否则不得降级执行者；子执行者的上下文独立计费（见 §9）。委托合同字段见 [07 §4](07-Agent与工作流选择.md#worker-contract)。

<a id="context-cost"></a>

## 9. 上下文成本可观测

上下文成本按三个正交轴可观测：来源（系统级指令、能力描述、输出约束、历史、工具返回、用户输入、模型输出）、是否重复携带（缓存命中 / 新输入 / 输出）、执行单元与阶段。子执行者的上下文独立计费：拆分本身不省成本（各单元固定开销并行叠加），其收益是生命周期可切段、上下文有重置时机；编排者每站重新理解状态的成本单独计量，可确定的迁移、路由与去重交给程序。成本报告须按计费类别加权并声明价表版本；只报总量或只报原始计数、不分单元与阶段的优化提案不进评审。报告口径见 [06 §8](06-评估与演进.md#metrics-candidates)。
