# 输入材料 001：用户提供的初始资料

日期：2026-09-01  
性质：外部资料汇总，**不代表已经接受的决策**。

## 原始要点

### 开发前准备

1. 定图纸，避免 AI 边写功能边倒推 UI。
   - 先说明需求。
   - 让 AI 整理 PRD，确定验收标准。
   - PRD 包含功能列表、用户流程、页面清单。
   - 明确每个功能做到什么样才算完成。
   - 提前确定视觉和页面框架，可借助 Figma、墨刀等工具。
2. 打地基。
   - 确定项目边界和非功能需求：安全、性能、可用性、成本。
   - 锁定技术栈，越可验证越好，不必非常前沿。
   - 技术栈需要能运行测试、进入 CI、保持可控，并具有充足资料和活跃社区。
   - 让 AI 输出轻量架构草案，持续迭代，每次记录更新原因。
   - 保持 PRD、架构、项目状态三份文档，在会话开始时帮助 AI 熟悉项目。
3. 立规矩。
   - 制定开发规范并建立参考资料目录。
   - 明确语言要求、命名规则、文件大小上限。
   - 写代码前建立 Git 和质量闸门。

### 开发中核心关键点

- 人类负责边界和验收，AI 负责体力工作。
- 小步迭代并采用端到端切片。
- 主动拆分模块，禁止代码聚成一坨。
- 限制 AI 擅自做主，使用状态摘要管理。
- 坚守安全底线，密钥不进入前端。
- 科学应对错误：两次没有新证据就停止重复尝试。

## 在 v0.1 草案中的处理

- “三份文档每次全部提供”被改写为分层加载提议：项目状态默认加载，PRD 和架构按任务相关性加载。
- “文件大小上限”保留为开放问题；当前提议是不设跨语言统一硬阈值。
- “两次无新证据就停”已补充可操作定义，避免误解成只允许排查两次。
- 其余要点已进入候选工作原则和生命周期工作流，但均未被接受为生效规则。
