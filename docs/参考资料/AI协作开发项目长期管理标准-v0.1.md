# AI 协作开发项目长期管理标准

版本：v0.1（评审草案）  
整理日期：2026-09-07  
适用对象：使用 Codex、Claude Code、Cursor 等工具持续开发和维护软件项目的个人及团队  
文档定位：工具无关的项目治理协议及基础模板，不是外部认证标准

## 1. 目的与适用范围

建立一套随项目仓库保存、可以跨工具和跨会话复用的管理协议，使任何接手者都能找到可信的项目现状、理解已有约束、继续推进工作，并留下可检查的完成证据。

本标准管理的是“AI 参与软件开发的过程”。普通网站、桌面程序、服务端系统和产品内包含 AI 能力的项目均可采用。模型评测、提示词版本和推理成本等要求属于可选扩展，不作为所有项目的基础负担。

本标准解决五个问题：

1. 项目要达成什么目标，本期不做什么。
2. 当前已经实现什么，还有哪些工作和阻塞。
3. 现有架构为什么如此设计，哪些契约需要保持。
4. 下一位接手者应如何继续执行任务。
5. 通过什么证据判断任务已完成、版本可交付。

采用标准不意味着每次任务都读取全部文档，也不意味着每项小修改都需要独立计划或人工批准。

## 2. 核心原则

| 编号 | 原则 | 执行要求 |
|---|---|---|
| GOV-01 | 项目知识随仓库保存 | 影响后续维护的目标、约束、决策和进度不得仅存在于某个工具的聊天记录中。 |
| GOV-02 | 权威信息各有归属 | 同一事实只有一个主要维护位置，其他文档通过引用使用。 |
| GOV-03 | 目标与现状分开 | “规范已批准”“代码已修改”“行为已验证”必须分别表达。 |
| GOV-04 | 完成需要证据 | 验收记录说明实际检查了什么、结果如何、对应哪个代码版本。 |
| GOV-05 | 约束能够检查 | 高价值规则尽量对应脚本、测试或明确的人工验收步骤。 |
| GOV-06 | 变更可追踪 | 重大契约与架构变更记录原因、影响范围、替代方案及实施状态。 |
| GOV-07 | 工作可以接续 | 中断或交接时保存剩余步骤、阻塞、验证状态和工作区信息。 |
| GOV-08 | 流程按风险增减 | 小修改保持轻量；涉及数据、跨模块契约和发布时增加必要验证。 |
| GOV-09 | 规则允许受控演进 | 规则具备版本、适用范围和修订方式；项目例外明确记录。 |
| GOV-10 | 工具入口保持简短 | 入口提供关键约束与阅读路径，详细业务规则由公共文档维护。 |

本标准中的“必须”表示采用本标准后的最低要求；“建议”表示可按项目情况选择；“可选”表示仅在相应需求存在时启用。

## 3. 三层结构与复用方式

| 层级 | 内容 | 维护方式 |
|---|---|---|
| 通用标准层 | 工作协议、任务状态、验收规则、交接格式、模板 | 在公共模板仓库统一维护和发布版本。 |
| 项目层 | 技术栈、检查命令、产品目标、架构、任务、决策、发布记录 | 随项目代码提交，反映该项目的实际情况。 |
| 工具适配层 | 当前工具的阅读入口、命令调用差异、环境限制 | 使用工具支持的项目指令机制，引用公共协议。 |

项目必须记录采用的标准版本。公共标准升级后，项目显式评估并升级，不应在任务执行过程中自动跟随未经评估的最新规则。

工具适配层只保留必要差异。不要分别在多个工具入口维护产品架构、任务状态或完整开发规范。

本草案不固定各工具的专用配置文件名和加载机制。实际适配时，应核对工具版本及其官方支持方式。工具自身的权限和执行机制仍然有效，项目文档不能替代它们。

## 4. 最小项目结构与信息归属

以下为建议结构。已有项目可以映射现有路径，不要求为了采用标准而整体搬迁文件。

```text
project/
├── governance/
│   ├── standard.md          # 采用的通用协议，标明版本
│   ├── project.yaml         # 项目配置与检查命令
│   └── exceptions.md        # 可选：项目例外及复查条件
├── docs/
│   ├── index.md             # 阅读入口、文档索引和权威位置
│   ├── product.md           # 产品目标、范围、非目标
│   ├── architecture.md      # 当前架构、模块职责和契约索引
│   ├── state.md             # 当前基线、重点任务、阻塞索引
│   ├── decisions/           # 可选：重要决策记录
│   ├── tasks/               # 任务及其执行、验收、交接记录
│   ├── runbooks/            # 可选：故障排查和维护操作指南
│   └── releases/            # 可选：版本交付与恢复记录
└── scripts/
    └── ...                  # 项目检查与维护脚本
```

| 信息 | 权威位置 | 其他文档如何使用 |
|---|---|---|
| 产品目标与非目标 | `product.md` | 任务引用对应目标，并记录本任务范围。 |
| 构建、测试、启动命令 | `project.yaml` | 工具入口和任务引用配置，不各自维护一份命令。 |
| 当前有效架构与契约 | `architecture.md` 或其链接的专题规范 | 决策记录解释形成原因，任务记录实施情况。 |
| 任务详细状态 | 对应任务记录 | `state.md` 仅列当前重点并链接任务，不复制完整进度。 |
| 重要取舍及其前提 | 对应决策记录 | 当前架构引用仍有效的决定。 |
| 实际运行行为 | 对应代码与可复现验证证据 | 发现与规范不同，登记差异并决定修正实现或修订规范。 |

聊天内容可以作为讨论材料；被采纳且影响未来工作的结论，应写入相应的权威位置。无需复制完整对话。

当项目文档发生冲突时，先检查适用范围、状态及明确的替代关系。日期较新或标题写着“终稿”，不自动意味着已取代其他规范。缺少明确裁定时，应记录冲突；需要负责人决定的部分等待决定，其他独立工作可以继续。

## 5. 文档生命周期与标准条目

重要规范与决策至少记录以下元信息：

```yaml
id: SPEC-EXAMPLE-001
version: 1
status: draft
scope: 适用模块或场景
owner: 维护人或维护角色
updated_at: YYYY-MM-DD
supersedes: []
```

文档状态建议使用：`draft`（草案）、`active`（当前有效）、`superseded`（已被替代）、`retired`（已退出使用）。

涉及实施的规范另行关联任务及验证记录，不使用文档状态代替实施状态。历史文档应保留必要追溯信息，并指向替代文档，避免 AI 将过时方案当成当前要求。

每条重要规则建议包含：

| 字段 | 内容 |
|---|---|
| 规则编号 | 稳定、可以在任务和检查结果中引用的 ID。 |
| 适用范围 | 在什么模块、阶段或触发条件下生效。 |
| 要求 | 必须保持的行为、边界或不变式。 |
| 检查方式 | 脚本、测试或人工操作步骤。 |
| 验收证据 | 检查结果及对应版本的保存位置。 |
| 维护责任 | 谁维护规则，谁处理无法自动判断的冲突。 |
| 例外与失效条件 | 何时允许偏离，何时需要重新评估。 |

示例：声明某项设置能够跨重启保存时，必须通过“修改设置—退出进程—重新启动—核对恢复结果”的验收。内存更新日志不能单独证明跨重启持久化已经完成。

## 6. 统一任务流程

### 6.1 开始前：恢复上下文

接手者应按需完成以下步骤：

1. 读取入口、项目配置和项目现状。
2. 确认当前分支、代码基线、未提交修改和正在进行的任务。
3. 读取本任务直接相关的架构、契约、决策和故障经验。
4. 核对实际代码与任务描述；记录发现的差异。
5. 确认目标、范围、验收要求及需要处理的前置依赖。

不得未经判断覆盖其他工作留下的修改。已有明确授权的常规实施，不因采用本标准而重复增加确认步骤。

### 6.2 执行中：控制变更

- 简单修改可以直接实施，在已有任务或变更记录中留下简短说明。
- 跨模块、接口或数据变更必须记录影响清单、实施顺序和相应验证。
- 重大架构或产品取舍应形成决策记录，并关联执行任务。
- 遇到阻塞时记录缺少的条件；不能把“等待某个条件”写成“已完成”。
- 新发现但不属于当前目标的问题登记后续任务，避免无边界扩大当前任务。

### 6.3 结束前：验证与交接

执行相关检查，记录结果，更新任务状态；影响项目整体认知时同步更新项目现状、架构或决策记录。

任务完成至少满足：

1. 目标范围内的验收条件已满足。
2. 必要检查已执行并通过，或存在明确接受且可追踪的例外。
3. 相关契约和文档已同步。
4. 已知限制与剩余风险已说明。
5. 验证结果能够关联到代码版本；验证后若代码继续变化，应说明证据是否仍有效。

任务完成不自动代表已合并、已部署或已发布。这些状态按项目需要单独记录。

### 6.4 任务状态

| 状态 | 含义 | 进入或退出依据 |
|---|---|---|
| `planned` | 已记录目标，尚未开始 | 目标与范围足以开展工作。 |
| `in_progress` | 正在实施 | 已开始修改或开展具体调查。 |
| `blocked` | 依赖条件不足，无法推进必要步骤 | 记录缺失条件、影响和解除方式。 |
| `in_validation` | 实施结果正在验证 | 已具备可检查结果，验收尚未全部结束。 |
| `done` | 满足本任务完成条件 | 有验收证据和必要的文档更新。 |
| `cancelled` | 明确不再执行 | 记录取消原因及已有工作的处理结果。 |

`blocked` 解除后回到适当的执行状态；验证失败回到 `in_progress`。`done` 后若发现验收不成立，可以重新打开，并记录原因。

## 7. 按变更风险选择流程

| 类型 | 常见例子 | 最低记录与验证 |
|---|---|---|
| 轻量变更 | 文案、样式、小范围且行为明确的修复 | 简短变更记录、适用的构建或行为检查。 |
| 常规变更 | 新功能、模块内重构、一般缺陷修复 | 任务卡、相关测试、文档同步和验收结果。 |
| 高影响变更 | 数据迁移、公共接口变化、核心架构调整、生产发布 | 影响与依赖清单、分阶段计划、兼容及恢复策略、针对关键风险的验证。 |

不以修改行数单独判断风险，也不要求所有任务追求相同测试数量或覆盖率。

已有用户和数据的项目，必须明确数据与接口的兼容策略。未上线项目可以选择破坏性重构，但应记录适用前提；不能将“零兼容”推广为所有项目的默认规则。

错误处理应避免未经声明地掩盖失败或改变用户意图。重试、缓存和降级是否可用，由项目策略规定，并保留可以识别的执行记录。

## 8. 基础模板

### 8.1 项目配置

以下是示例字段设计，不代表已经提供了配置解析器或自动执行工具。实际采用时填写真实命令，并检查它们是否可运行。

```yaml

project_name: "待填写"
project_stage: "pre_release"  # 可用 pre_release / production
maintainer: "待填写"
default_branch: "待填写"
stack: []
paths:
  entry: "docs/index.md"
  state: "docs/state.md"
  architecture: "docs/architecture.md"
  tasks: "docs/tasks"
commands:
  # 填写从指定目录执行的真实命令，不适用的检查应注明原因。
  build:
    cwd: "."
    run: "待填写"
  test:
    cwd: "."
    run: "待填写"
  lint:
    cwd: "."
    run: "待填写"
compatibility:
  policy: "待填写：数据、接口和旧版本支持范围"
```

### 8.2 项目现状

```markdown
# 项目现状
更新时间：
当前基线：分支 / 提交 / 已发布版本
当前阶段与本期目标：

## 当前重点
- 任务 ID、简述、链接

## 影响后续工作的阻塞与限制

- 建议优先继续的任务及原因
```

项目现状应保持简短。完成任务移出“当前重点”，历史细节保留在任务记录和版本记录中。

### 8.5 工具适配入口

以下文字可按工具支持的项目指令机制进行适配：

> 本项目采用 `governance/standard.md` 中的工作协议。开始任务时读取 `docs/index.md`、`governance/project.yaml` 和 `docs/state.md`，再按任务需要读取相关文档。先核对工作区和实际实现，保留已有修改。检查命令以项目配置为准。结束或中断工作时更新对应任务的实施结果、验证证据和下一步；必要时更新项目现状。不要将草案、历史方案或尚未验证的实现当成当前已完成能力。

工具专用部分只补充环境、命令调用方式和必要限制；公共规则不重复展开。

## 9. 并行协作与长期维护

多个工具或人员同时工作时，必须明确任务分工与修改范围。共享工作区中不得各自覆盖同一文件的未知修改；可使用隔离分支或工作目录，并在集成时统一检查。

公共架构和数据契约的变更应由明确的协调者维护，其他任务引用相应决定。单人项目的维护人可以承担全部角色，不要求额外组织层级。

建议的维护触发点：

| 触发点 | 维护动作 |
|---|---|
| 每次任务结束或中断 | 更新任务结果、验证和交接信息。 |
| 当前阶段或重点变化 | 更新项目现状与产品范围。 |
| 接口、数据或架构变更 | 更新有效规范，关联决策与迁移任务。 |
| 故障修复完成 | 保留根因和回归验证；重复发生的问题沉淀为检查或排障指南。 |
| 每个迭代结束 | 检查未闭环缺陷、技术债、过时文档和未处理例外。 |
| 发布前后 | 按项目风险记录版本、检查结果、已知限制及恢复方案。 |
| 标准升级时 | 阅读升级差异，更新项目配置与适配入口，记录采用版本。 |

例外记录至少包含规则编号、偏离原因、影响范围、决定人、替代检查和复查条件。例外不能只是让检查永久跳过的无说明名单。

## 10. 可选扩展

当项目本身包含模型调用或生成能力时，可增加：

- 模型、提供方、提示词模板与能力配置的版本记录。
- 固定评测集及质量、失败率、延迟、成本的变更前后比较。
- 任务作用域、并发、取消、失败恢复和重复提交策略。
- 外部 API 能力的证据来源、核验日期和变更记录。
- 请求与结果的必要追踪；根据数据性质控制日志内容、访问和保留期限。

评测用来比较行为与质量，不承诺非确定性模型每次返回相同内容。

这些扩展可以形成单独规范，通过公共入口索引，不应增加到所有普通项目的默认必读内容中。

## 11. 落地步骤与试点验收

### 11.1 落地顺序

1. 选择一个持续维护的项目，梳理已有文档并映射权威位置。
2. 建立入口、项目配置、项目现状与任务模板；保留仍然适用的现有结构。
3. 补全真实检查命令，验证这些命令能够运行。
4. 为正在进行的工作建立任务记录；优先整理当前有效约束，无需一次性补写所有历史。
5. 添加两个工具的薄入口，开展顺序接手试验。
6. 将调整后的公共部分用于第二个项目，检查是否只需修改项目配置。
7. 根据试点发现修订标准，再形成初始化脚本、检查工具和升级机制。

### 11.2 试点通过条件

- 新接手者只依赖仓库和可用运行环境，能够找到目标、现状和下一步。
- 两个工具先后接手同一项任务，保留已有修改和有效决策。
- 两个工具使用相同的权威规则及项目检查命令。
- 完成记录含可核对的版本、验收结果和未解决限制。
- 第二个项目能够复用协议和模板，通过项目配置表达技术差异。
- 草案、已废止规范与当前有效要求可以清楚区分。

可持续观察的指标包括接手耗时、任务验收证据完整性、重复缺陷、文档与实现冲突，以及维护协议本身的时间成本。第一版先建立基线，不预设缺少依据的统一分数或达标阈值。
