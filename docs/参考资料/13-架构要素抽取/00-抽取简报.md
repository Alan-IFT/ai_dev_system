# 架构要素抽取简报

目的：我们要**从参考资料中归纳**一套 AI 辅助大型项目开发系统的架构（由哪些部件组成、部件之间怎么连、哪些不可省略），而不是先拍脑袋定五个部件再找证据。你负责一批来源的**架构要素抽取**，输出一张结构化表，供主 Agent 跨来源统计与裁决。

不要写理论、不要评价好坏、不要提建议——只抽取"该来源的系统（或它描述的系统）长什么样"。

## 读什么

指派给你的每张卡片（`（工作区）cards/WX-NN.md`）全文，重点 §1 文章在讲什么、§2 核心主张、§3 图片信息（架构图/流程图的描述最重要）、§5 对照、§6 建议采纳。需要时回看原文 `（工作区）docs/归档/参考资料-公众号文章/<目录>/article.md` 与图片（png/jpg 直接 Read，webp/gif 看同名 `_view.png`）。

## 对每个来源抽取（写入你的输出文件，每来源一节）

```markdown
### WX-NN <标题>（类型：V1/P1/S1/T1/O1；场景：<编码 Agent / 企业 Agent 平台 / 个人 / 对话 Agent / 基础设施…>）
- **部件清单**：来源自己的名字 → 归一化名。逐条列出该来源系统里明确存在的部件（工具、库、流程角色、工件类型都算）。归一化名从下面词表选，选不到就新造并标 ★。
- **部件关系**：谁向谁提供什么（数据 / 控制 / 触发），只写来源明确画出或写出的，不推断。
- **不可省略**：来源明确说"没有它就不行 / 最重要 / 最先建"的部件（引用原句或图注）。
- **分层 / 演进**：来源自己的分层模型或成长阶段（如有）。
- **失败归因**：来源把"变慢 / 失败 / 失控"归因到哪个部件缺失或失守。
- **证据形态**：架构图 / 运行截图 / 文字描述 / 一手文档；有无实测。
```

归一化词表（可扩展，新词标 ★）：
`意图与验收（需求/PRD/验收条目）`、`任务拆分与调度（编排/流水线/agent team）`、`执行者（Agent/子代理）`、`代码地图（codegraph/索引/仓库地图）`、`项目知识（文档/契约/ADR/入口文件）`、`长期记忆（经验库/memory 工具）`、`上下文装配（加载清单/检索/压缩/外部化）`、`Skill/方法库（SOP/Runbook/规则）`、`工具与执行环境（MCP/沙箱/命令）`、`权限与边界（审批/allowlist/隔离）`、`拦截与守卫（hook/检查器/lint/Gate）`、`验证与测试（测试/评审/回读）`、`状态工件（工作项/交接/进度/任务系统）`、`证据与追踪（trace/日志/回执）`、`评估与演进（eval/badcase/消融/Thin）`、`人（审批/验收/责任人）`、`模型（LLM 本身）`。

## 批次汇总（输出文件末尾）

1. **部件频次表**：归一化名 → 出现的来源数 / 本批来源总数，并列出各来源用的原名。
2. **共现关系表**：本批出现 ≥2 次的"A → B 提供 X"关系。
3. **不可省略投票**：被 ≥1 个来源明确标为不可省略的部件及来源。
4. **分层模型清单**：本批出现的所有分层/演进模型（原名 + 层名）。
5. **失败归因频次**：部件 → 被归因次数。

输出文件：`（工作区）arch/<批次名>.md`，中文，200～350 行。最终回复只报：抽取来源数、频次表前 8 名、新造 ★ 词、输出路径（≤12 行）。禁止修改其它文件。
