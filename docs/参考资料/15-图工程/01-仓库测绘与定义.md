## 2. 一个必须先说清的结构事实：README 的树 ≠ 论文的树

任务书里给我的那份 17 项清单接近但不等于事实。**实际是 16 个子类**，而且两个来源的挂法不同：

| README 的挂法 | 论文的挂法 |
|---|---|
| Model Intelligence 下 4 子类平铺 | §3.1 Foundation Models（含 3.1.1 Pre-training / 3.1.2 Post-training）+ §3.2 Prompt and Context Engineering（含 3.2.1 / 3.2.2） |
| Individual Intelligence 下 **7 子类平铺** | **分属两个具名范式**：§3.3 **Harness Engineering**（3.3.1 Tool Integration / 3.3.2 Memory Management / 3.3.3 Skill Composition / 3.3.4 Runtime Orchestration）+ §3.4 **Loop Engineering**（3.4.1 Loop Architecture / 3.4.2 Interaction Paradigm / 3.4.3 Environment Feedback） |
| System Intelligence 下 5 子类平铺，**含 Ontology Engineering** | §4 Graph Engineering 只有 4 个维度（4.2 Task Organization / 4.3 Agent Coordination / 4.4 Runtime State Management / 4.5 System Evolution）；**Ontology Engineering 是 §6"Future Direction"，不是 Graph Engineering 的组成部分** |

**这两条差异是本卡最有价值的读数之一：**

1. **Harness Engineering 与 Loop Engineering 不是图工程的竞争者，是它下面的一层。** 论文把这两个词当作 Individual Intelligence 内部的两个子范式收编了。所以"图工程 vs. Loop Engineering"这个问法在原文框架里不成立——它们不在同一层。
2. **Ontology Engineering 在论文里被明确定为"未来方向"，即作者认为图工程本身还不够。** README 把它平铺进 System Intelligence 会让人误以为它是现成的一类。**以论文为准：它是待办，不是已有。**

## 3. 定义与分类法（逐字引用 + 直译）

### 3.1 图工程的定义

**定义句 A —— README 首段（A 级，字节级准确）**

> "Graph Engineering studies how explicit, dynamic, and evolving graph structures can organize tasks, coordinate heterogeneous agents, maintain runtime state, and support system evolution."

直译：图工程研究**显式的、动态的、演化中的图结构**如何能够组织任务、协调异构 agent、维持运行时状态、并支撑系统演化。

**定义句 B —— 摘要（B 级）**

> "We introduce Graph Engineering, an emerging paradigm for next-generation agent systems. Unlike prior paradigms that mainly optimize individual interactions or agent-level behavior, Graph Engineering constructs explicit, dynamic, evolving graph structures representing tasks, agents, and system states."

直译：我们提出图工程，一种面向下一代 agent 系统的新兴范式。与主要优化单次交互或 agent 层行为的既往范式不同，**图工程构造出显式的、动态的、演化中的图结构，用以表示任务、agent 与系统状态**。

**定义句 C —— 正文 §4.1（C 级，两次抓取一致）**

> "To this end, we introduce Graph Engineering as a structure-centered engineering foundation for system intelligence: it uses graph structures as the core substrate for externalizing relationships among tasks, components, and runtime states, thereby supporting system-level organization, coordination, monitoring, recovery, and optimization."

直译：为此我们提出图工程，作为**系统智能的、以结构为中心的工程基础**：它以图结构作为**外化**任务、组件与运行时状态之间关系的**核心基底（substrate）**，从而支撑系统级的组织、协调、监控、恢复与优化。

**三句合看，定义的四个硬要件是：**①显式（explicit）②动态（dynamic）③演化（evolving）④图结构本身是**基底（substrate）**、承担**外化（externalizing）**职能。

### 3.2 三层各自的定义（正文，C 级）

- **Model Intelligence**：> "the ability of an individual model to leverage its knowledge and reasoning capabilities to solve tasks within a given context"
  直译：单个模型在**给定上下文之内**、利用其知识与推理能力解决任务的能力。
- **Individual Intelligence**：> "the ability of an individual agent to extend model-level reasoning into persistent, goal-directed execution through resource orchestration and iterative interaction with the environment"
  直译：单个 agent 通过**资源编排**与**与环境的迭代交互**，把模型层推理**延展为持久的、目标导向的执行**的能力。
- **System Intelligence**（摘要版，B 级）：> "an agent system's ability to organize and coordinate multiple intelligent components into a coherent, adaptive whole pursuing a shared objective"
  直译：一个 agent 系统把**多个智能组件组织协调成一个连贯的、自适应的、追求共同目标的整体**的能力。
- **System Intelligence**（正文版，C 级）：> "the ability of an intelligent system to decompose and organize complex objectives, allocate responsibilities across heterogeneous computational agents, coordinate their interdependent execution, and maintain system-level state throughout the task lifecycle."
  直译：智能系统**分解并组织复杂目标、在异构计算 agent 之间分派职责、协调其相互依赖的执行、并在整个任务生命周期内维持系统级状态**的能力。

### 3.3 三层的划分判据

**原文没有一句"我们按 X 判据分三层"的元陈述。** 我做了针对性检索，抓取返回 `NOT FOUND`（原话：*"The text motivates the progression through limitations but does not explicitly state the logical criterion for this ordering sequence"*）。**判据是靠"上一层的失效"逐层推出来的，不是先验声明的。**

可核对的推进链条如下（每一层的边界 = 下一层被迫出现的理由）：

**M → I 的分界（摘要，B 级）**

> "LLMs have evolved from language generators to autonomous agents capable of complex, long-horizon tasks."

分界点是**从"生成语言"到"持久执行"**。对应到定义句：Model Intelligence 被限定在 `"within a given context"`（上下文之内），Individual Intelligence 是 `"extend model-level reasoning into persistent, goal-directed execution"`（延展为持久执行）。**判据 = 是否跨越单次上下文而持续。**

**I → S 的分界（摘要，B 级 —— 这是全篇最硬的一段）**

> "Yet as tasks grow more complex, individual intelligence faces a fundamental limit: many tasks require heterogeneous expertise, interdependent subtasks, parallel execution, independent verification, and persistent state, exceeding any single agent's organizational capacity. Augmenting one agent's capabilities or context cannot resolve this architectural mismatch; intelligence must instead be distributed across specialized agents and organized at the system level."

直译：然而随任务变复杂，个体智能面临一个**根本性极限**：许多任务需要**异构专长、相互依赖的子任务、并行执行、独立验证、以及持久状态**，这些要求**超出任何单个 agent 的组织能力**。**增强单个 agent 的能力或上下文无法解决这一架构性错配**；智能必须转而**分布到专门化的 agent 上并在系统层被组织**。

**这段的判据是可操作的五项**：异构专长 / 相互依赖子任务 / 并行执行 / 独立验证 / 持久状态。**任务只要同时压上这五项，就越过了 I 层的天花板。**

**为什么是三层不是两层或四层——原文未直接回答，我只能给可核对的间接证据：**
- 不是两层：因为 §3.5 单列一节 "Limitations of Individual Intelligence"，即 I 层被明确当作一个**独立的、有自身失效模式的**层，而不是 M 层的延伸。
- 不是四层：因为第四层候选（Ontology Engineering）被作者自己放在 §6 "Future Direction"，即**明说它还不成层**。
- **这两条是我从章节编排推出的，不是原文断言。标为归纳。**

## 6. "图"到底是什么图？比喻还是真结构？

**这是本卡最关键的一节，也是我核对得最不彻底的一节——最直接的那节（§11.2）我没读到。**

### 6.1 可核对的定性证据（按强度排序）

**证据一（最强，A+B 级）：定义句里"explicit"是**修饰"graph structures"**的第一个形容词，且三处定义句全部出现。**

> "**explicit**, dynamic, and evolving graph structures" `[README原文]`
> "constructs **explicit**, dynamic, evolving graph structures representing tasks, agents, and system states" `[摘要]`

作者反复用 explicit，且在摘要里与"prior paradigms that mainly optimize individual interactions or agent-level behavior"对举——**explicit 是它自我区分的核心词**。

**证据二（C 级，两次一致）：图被称为 substrate（基底），职能是 externalizing（外化）。**

> "it uses graph structures as the core **substrate** for **externalizing** relationships among tasks, components, and runtime states"

"externalizing" 的反义是留在模型内部的隐式推理。**这句最能定性：图的作用就是把原本隐含在 agent 推理里的关系搬到模型外面去。**

**证据三（C 级）：明写"从隐式推理转为系统结构"。**

> "externalizes task decomposition and executable operations as graph structures, transforming task organization from **implicit reasoning** into a **schedulable, optimizable, and revisable system structure**"

直译：把任务分解与可执行操作外化为图结构，将任务组织**从隐式推理转变为可调度、可优化、可修订的系统结构**。
**"schedulable / optimizable / revisable" 这三个词是决定性的**——可调度意味着有调度器读它，可修订意味着有写操作作用于它。**比喻不可调度。**

**证据四（C 级）：节点与边被具体类型化。**

> §4.3.1：`"nodes represent agents, skills, tools, models, and other resources, while typed edges encode capability ownership, resource access, permissions, and reliability."`
> §4.2.1：`"representing an objective as a graph of subgoals and dependencies, where nodes denote subtasks or intermediate goals and edges encode precedence, data, or logical relations"`
> §4.2.1：`"LLMCompiler compiles function-calling plans into a dataflow DAG, so that ready nodes can be dispatched in parallel."`

**"typed edges"（带类型的边）承载 permissions（权限）和 reliability（可靠性）；"dataflow DAG" 被 dispatch。这不是比喻的用法。**

### 6.2 具体是哪些图

原文**没有一句把所有图类型列全的句子**（我专门检索过，返回 NOT FOUND）。按 §4 的四个维度，可核对到的是四类互不相同的图：

| 维度 | 图是什么 | 节点 | 边 |
|---|---|---|---|
| §4.2 Task Organization | **任务/依赖图（dataflow DAG）** | 子目标、子任务、具体算子 | 先后次序、数据流、逻辑关系 |
| §4.3 Agent Coordination | **能力图 / 协作拓扑图（DAG）** | agents, skills, tools, models, and other resources | typed edges：capability ownership, resource access, permissions, reliability |
| §4.4 Runtime State Management | **状态/溯源图** | 执行状态 | 未核对到边的定义；职能含 preserve provenance |
| §4.5 System Evolution | 上述图**自身的变更** | — | — |
| §6 Ontology（未来方向） | 本体/语义图 | **整节未核对** | — |

**知识图谱（KG）不在 §4 的四维度里。** README 把 GraphRAG-Bench 放在**基准的 Model Intelligence 档**，把 Palantir Ontology System 放在 Ontology Engineering 档——即作者把"图作为知识/检索载体"和"图作为系统控制结构"**分开摆放**。

### 6.3 结论（带置信度）

**判定：是真实结构，不是比喻——但"可查询（queryable）"这一条我没核对到原文支持。**

- **有原文支持的**：显式（explicit）、外化（externalizing）、基底（substrate）、可调度（schedulable）、可优化（optimizable）、可修订（revisable）、边带类型且承载权限。
- **没有原文支持、我专门找过且返回 NOT FOUND 的**："materialized"、"queryable"、"first-class"、"persisted"、"versioned" 这些词，以及"必须存在一个可查询的图数据库"这类要求。抓取原话：*"The paper emphasizes graphs as organizational structures but does not explicitly state they are 'persistent/materialized artifacts that can be inspected, queried, stored, versioned, or executed on' in those terms."*
- **所以准确的说法是**：它要求图是**运行时真实存在、可被调度器读取、可被修订的控制结构**；它**没有**要求这个图存在于一个图数据库里、也没有要求它对外提供查询接口。**"必须上 Neo4j"是过度解读。**
- **本节结论的最大风险**：§11.2 未核对。若那一节有更强或相反的定性句，本节可能需要修订。

## 7. 它明确反对什么

**反对①：反对"单个 agent 的线性循环"作为复杂任务的组织形态。**（三次抓取一致的部分）

> "A single-agent loop, however, tends to compress them into a serial execution trace"

直译：然而单 agent 循环倾向于把它们**压扁成一条串行执行轨迹**。
（紧接的后果句在两次抓取中为：> "This makes scheduling implicit, wastes the efficiency of parallelism, and makes failure location difficult." —— **使调度变得隐式、浪费并行性、并使失败定位变得困难**。第三次抓取给出不同收尾，见 §1，故本句标为"高度可能但形态未定"。）

**注意它反对的确切对象**：不是"循环"本身（Loop Engineering 是它收编的一层，且被正面定义），而是**把本可并行、有依赖的工作压成一条串行轨迹**。**"隐式调度"才是被针对的靶子。**

**反对②：反对"给单个 agent 加能力/加上下文"这条解法。**（摘要，B 级，最硬的一句）

> "Augmenting one agent's capabilities or context cannot resolve this architectural mismatch"

直译：**增强单个 agent 的能力或上下文，无法解决这一架构性错配。**
这句直接否定了"更长上下文 / 更多工具 / 更好 prompt"作为复杂系统问题的解法路径，把问题定性为 **architectural mismatch（架构性错配）**。

**反对③：反对把角色能力留在同一个控制回路里。**（C 级）

> "Although a single agent can use tools or call specialist models, these capabilities remain coordinated within the same control loop rather than organized into stable and independent roles."

直译：尽管单个 agent 可以使用工具或调用专家模型，这些能力**仍然是在同一个控制回路内被协调的，而没有被组织成稳定且独立的角色**。

**反对④：反对错误在回路里被顺延。**（C 级）

> "Once an error enters the execution loop, it can be carried through later steps, making it difficult to repair only the affected parts or to recover in a way that can be traced and checked."

直译：一旦错误进入执行回路，它会被**带到后续步骤**，使得**只修复受影响部分**、或以**可追踪可检查的方式恢复**变得困难。

**它没有反对什么（重要）**：没有反对 Prompt Engineering、Context Engineering、Harness Engineering、Loop Engineering 中的任何一个。这四者在论文里都被**正面定义并收编为下层**。图工程的主张是"再加一层"，不是"换掉下面几层"。

## 9. 一条要记住的读数

**这份材料对本规范最大的价值，不是它的分类树，而是那句"architectural mismatch"。**

它把"复杂任务做不好"从**能力问题**重新定性为**架构问题**，并给出了一条可判定的分界线（五项并发要求）。这条线是外部的、独立于本规范的，因此可以用来**反过来检查本规范自己的分层是不是切在同一个地方**。

同时必须记住：**它自己承认结构还不够。** §6 把 Ontology Engineering 列为未来方向，理由所在的 §6.1 标题就叫 "Limitation of Graph Engineering-based System Intelligence"——**作者认为图工程本身有极限**。那一节我没读到，这是本卡最大的空洞，也是下一轮最该补的一格。
