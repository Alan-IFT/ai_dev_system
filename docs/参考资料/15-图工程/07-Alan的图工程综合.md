## 2. 原文（逐字保留）

### 2.1 Graph 可执行系统的核心范式与拓扑

- 工程重心从编排单个智能体的行为上移至编排智能体集群的组织协作；
- Graph建立在前四层稳固的基础上，解决单体循环无法触达的系统性问题；
- Graph的本质为可执行分布式系统；核心使命：解决如何将多个智能体、工具与人，组织成一个可观测、可恢复、可拓展的分布式系统；
- 工程隐喻：从单人的while循环，升级为现代企业的组织架构与流水线（工位、交接、看板、制度）
- 系统架构的四大核心元语：G=（V,E,S,P）
  - V(Nodes)节点：单一职责的执行单元（单进单出）。可以是专用智能体，也可以是确定性函数代码
  - E(Edges）边：定义控制流与路由调度。支持直通、条件分支、扇出扇入及回环纠错
  - S(State)状态：系统的粘合剂。沿着边流动的读写对象，记录进度、预算、产物与检查点
  - P（Policy）策略：定义权限与边界。控制节点创建、工具调用外部副作用及人工审批流
- Graph三大经典拓扑模式
  - 扇出与扇入： 拆分任务 → 各任务同步执行 → 任务结果去重合并，交给拟稿人
    - 打破线性时序，多信源汇聚并行处理
  - 主管模式：主管agent管理多个Work Agent灵活分配工作
    - 高度动态，适用于运行时无法预先确定任务路径的复杂调度
  - 流水线：对那个步骤的一步步执行下去
    - 复杂任务降级为固定步骤，以执行延迟换取极致的准确率
- Anthropic官方工作流模式匹配
  - 核心原则：先找最简单的方案，只在真正需要时才增加复杂度。拒绝过度设计

| 模式名称 | 工程行为/核心机制 | 使用场景 |
| --- | --- | --- |
| 提示链（Prompt Chaining） | 分解为固定步骤链 | 任务边界清晰，用延迟换准确率 |
| 路由（Routing） | 输入分类与分发 | 关注点分离，避免复杂Prompt拖累推理 |
| 并行（Parallelization） | 独立分支同步执行 | 任务可解耦，需多视角交叉验证 |
| 主管-工作者（Orchestrator） | 动态拆解与汇总 | 任务拆解不可预测，需运行时调度 |
| 评估-优化（Evaluator-Optimizer） | 生成与打分循环迭代 | 具备明确客观评价标准，且迭代收益显著 |

### 2.2 Graph 的关键工程设计与安全治理

- 反模式：自动验证的失败，让一个agent负责 规划+执行+审查，在同一个被污染的上下文中进行自我盖章通过
  - 工程警示：永远不要让写代码的智能体，在充满过往试错噪音的上下文中，去审查自己的代码。顺从性导致系统必然静默放行错误，引发级联崩溃
- 重构验证：引入独立Verifier（验证器）节点
  - 将生产与验证物理隔离。验证器不关心生成过程，只凭借全新上下文检验最终产物
    - 生产者给结论→ 验证器（独立、干净、专职挑错）
      - 通过验证 → 放行，为最终答案
      - 未通过验证 → 打回重做（全新上下文）
  - 对抗式：多路并行驳斥，少数服从多数
  - 多视角：正确性、安全性、复现性分离独立审查
  - 评委制：多方案并行，计分择优并吸收次优项
- 系统确定性：边界划分与现实锚点
  - 模型计算域/LLM节点：负责意图理解与模糊判断
  - 确定性执行域/传统代码边：负责格式校验（如JSON）、数学计算、权限收口、去重与兜底路由
  - 警告：缺乏现实锚点（如自动化测试通过、数据库事务提交、真实业务指标回传）的全闭环模型图，只是做一个项目管理做得更好的幻觉工厂，让模型的判断落在节点上，让代码的可靠性落在边上
- 安全红线：工作图与角色图隔离
  - 权限治理是多智能体上生产环境的不可妥协底线
  - 工作图（Work Graph）：允许快变。任务如何拆解、合并，可以交由大模型在沙盒内现场灵活调度。允许大模型发挥规划能力
  - 角色图（Role Graph）：必须变慢（严禁越线）。基础架构权限（如谁有权修改数据库、谁能绕过审批执行脚本），绝对禁止模型现场发挥
    - 安全定性：权限必须预定义、强约束、可审计。否则搭建的不是智能系统，而是随时引爆的生产事故
- 企业级框架：从对话驱动到持久化状态（LangGraph）
  - 常规消息驱动框架：智能体间通过长篇对话传递背景，产生大量解释性废话。消耗约8000token
  - 状态驱动（Graph）：智能体交互直接转变为精准的状态Payload读写，消除冗余。消耗约2000token
  - Graph带来的工程保障能力：
    1. 人在回路：断点挂起，人工修改后恢复
    2. 长效记忆：跨越会话周期的上下文留存
    3. 时间旅行：回滚至历史节点重放或分叉
    4. 精准容错：仅重试异常节点，保留已成功节点的产出
- 案例推演：单体Loop vs 微型Graph
  - 业务目标：多渠道搜索 → 写摘要 → 准确性核对 → 发送邮件
    - 方案A（Loop）：搜信源+起草+审查自身操作
      - 灾难点：串行阻塞、上下文越滚越脏、自己给自己判卷
    - 方案B（Graph）：节点1（研究员）扇出检索，仅传递结构化笔记 → 节点2（写手）注入全新干净上下文写草稿 → 节点3（审稿人）对照标准挑错，不合格打回写手
      - 核心优势：物理隔离带来的纯净推理环境与并行效率

| 对比维度 | Loop | Graph |
| --- | --- | --- |
| 上下文隔离 | 全糊在一起，越滚越脏 | 节点各自物理隔离，保持干净 |
| 审查有效性 | 作者审查自身，形同虚设 | 全新独立上下文，真实挑错 |
| 搜集效率 | 单信源串行阻塞，极慢 | 多信源并行扇出，极快 |
| 开发维护成本 | 1个提示词，启动成本极低 | 3个提示词+状态结构定义，启动成本较高 |
| 适用边界 | 一次性尝鲜任务、简单单线任务 | 每天稳定运行、对质量零容忍的生产级管线 |

- 工程权衡：性能提升与资源开销
  - 多智能体性能最强，但token消耗较高
- 决策树
  - 任务若只有一个目标、一个停止条件，强行拆解多智能体只会徒增延迟与成本，此时采用loop来完成任务
  - 任务存在分支、并行需求，需要跨天状态留存与人工审批，此时采用Graph来完成任务
    - 上下文保护：子任务产生超1000token无关信息
    - 并发探索：任务可切割为独立分支，需扩展搜索空间
    - 异构专业化：不同步骤强依赖异构工具组或护栏
- 演进终局：工作流、ReAct与Graph的融合
  - 工作流Workflow：节点与边均写死：极度稳定，但毫无灵活性，遇到变化不会拐弯
  - ReAct模式：全场临场发挥，控制流全包在模型对话中。极度灵活，但难复现、难审计、易失控
  - Graph模式：结构预定、节点自主
- Graph工程的三条核心箴言
  - 极简至上：别为了图而图。能用一张餐巾纸画清的单体循环，就绝对不要引入多节点复杂度
  - 向外求稳：图的价值来自确定性，而非智能体堆砌。模型做模糊判断，代码做规则兜底，并配置独立挑刺的眼睛
  - 现实锚点：必须接入无可辩驳的业务事实（如：测试通过、数据落库）。无现实检验的系统，只是更有组织的幻觉工厂
- 从 单体莽干 到 组织化群体协作 的工程主轴，是必然趋势
