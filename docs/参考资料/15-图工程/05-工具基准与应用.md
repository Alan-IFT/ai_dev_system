## 2. 材料的自我定位（决定后面怎么读）

README 的 Overview 逐字：

> **Graph Engineering studies how explicit, dynamic, and evolving graph structures can organize tasks, coordinate heterogeneous agents, maintain runtime state, and support system evolution.**

三段递进（逐字）：

## 4. 十个库的逐个精读：它承载哪一层、要写多少代码、绑不绑宿主

按"编排框架 / 记忆层 / 代码图谱 / 上下文层 / 评测"五分法归位。**归位结论是我做的判断，不是原文说法。**

### 4.1 MCP Python SDK —— 上下文层与工具层，**唯一真正跨宿主的载体**

逐字：

> "The Model Context Protocol lets you build servers that expose data and functionality to LLM applications in a secure, standardized way."

> "With this SDK you can: Build MCP servers that expose tools, resources, and prompts to **any MCP host**" / "Build MCP clients that connect to **any MCP server**."

> "Speak every standard transport: stdio, Streamable HTTP, and SSE"

**归位**：上下文层 + 工具接入层。三种暴露物：tools / resources / prompts。
**写多少代码**：写一个 server 要写 Python（装饰器 `@mcp.tool()` / `@mcp.resource()`）；**接一个已有 server 到宿主只写一段 JSON 配置**。这条区分很关键——消费端是零代码的。
**可替换性**：这是全清单里唯一以"协议"而非"框架"形态存在的条目。协议的性质决定了它不绑宿主。**但**：codex / Claude Code / opencode / DeepSeek harness / VSCode Copilot 各自对 MCP 的支持程度与配置格式，本轮**未逐个核对**——只核对到 Project ALICE 在生产里用它作 agent 间通信（§5.4），以及 Graphiti 与 Langflow 都提供 MCP server 出口。

### 4.2 Graphiti —— 记忆层（时序知识图），要外部数据库

逐字：

> "A framework for building and querying temporal context graphs for AI agents."

> "Each fact in a context graph has a validity window: when it became true, and when (if ever) it was superseded."

与 GraphRAG 的差别，工具抽取为：Graphiti 做 "continuous, incremental updates" 与 "explicit bi-temporal tracking with automatic fact invalidation"，GraphRAG 是批处理、静态文档取向。

**依赖**〔工具转述〕：Python 3.10+；图数据库 Neo4j 5.26+ / FalkorDB 1.1.2+ / Amazon Neptune / Kuzu 0.11.2（已弃用）；LLM API key（默认 OpenAI，也支持 Anthropic / Gemini / Groq / Azure OpenAI 及"any OpenAI-compatible `/v1` endpoint"）。
**代价（原文给出的两条）**：

> "Concurrency controlled by the `SEMAPHORE_LIMIT` environment variable. By default, `SEMAPHORE_LIMIT` is set to `10`"（防限流）

小模型有 JSON 抽取失败风险〔工具转述〕。查询延迟 "typically sub-second"（该项目声称的观察）。

**归位**：记忆层。**写多少代码**：自建要写 Python + 运维一个图数据库；**但它自带 `mcp_server` 目录**——这意味着可以只当 MCP server 接入，消费端零代码。
**可替换性**：**记忆层本身可替换**（Letta、宿主自带的会话记忆、甚至仓库里的一个 Markdown 文件都能占这个位），但一旦选了 Graphiti 就多一个数据库要运维。

### 4.3 Letta Agent SDK —— 记忆层，服务端形态

逐字：

> "The SDK for stateful agents: create an agent once, then resume it from anywhere."

> agent 保有 "its own identity and long-term memory, and keeps both across conversations, models, and the computers it runs on."

**部署**〔工具转述〕：cloud / local / remote 三种后端，可自托管。
**归位**：记忆层。**写多少代码**：SDK 调用，示例是 TypeScript（`LettaAgentClient`、`createAgent`、`resumeSession`）。
**可替换性**：它把 agent 身份本身托管到 Letta 侧。"跨 models 与 computers 保持记忆"是卖点，也是**耦合点**——本规范若采用，agent 的身份就不在仓库里而在 Letta 里。按本规范"载体不是语义"的口径，这属于**把语义押进了某个载体**，需要显式权衡。

### 4.4 LangGraph —— 编排框架，另起 runtime

逐字（片段）：

> "Low-level orchestration framework for building stateful agents."

> 提供 "low-level supporting infrastructure for *any* long-running, stateful workflow or agent."

> "Build agents that persist through failures and can run for extended periods, automatically resuming from exactly where they left off."

五条特性〔工具转述〕：Durable execution / Human-in-the-loop / Comprehensive memory / Debugging with LangSmith / Production-ready deployment。工具称 LangSmith 是 "complementary tool rather than a required coupling"〔这是工具的判断，不是原文断言，标未核对〕。

**归位**：编排框架。**写多少代码**：全部。节点、边、状态类型都要写 Python。
**可替换性**：不绑任何 AI 编程宿主，但**也不装进任何 AI 编程宿主**。用 LangGraph 意味着你在 Claude Code 之外另写一个程序。对本规范硬约束（必须在五种宿主上通用）的判读：**它既不违反也不满足**——它不在那个层面上。

### 4.5 Apache Burr —— 编排框架，主张"不告诉你怎么做别的"

逐字：

> "Apache Burr (incubating) makes it easy to develop applications that make decisions (chatbots, agents, simulations, etc...) from simple python building blocks."

> "With Apache Burr you express your application as a state machine (i.e. a graph/flowchart)."

> "Apache Burr will _not_ tell you how to build your models, how to query APIs, or how to manage your data."

> "A (dependency-free) low-abstraction python library that enables you to build and manage state machines"

> "A UI you can use view execution telemetry for introspection and debugging"

**归位**：编排框架 + 可观测。**写多少代码**：全部（`@action` 装饰器、`ApplicationBuilder`）。
**值得记的一句**：那句 "will _not_ tell you how to..." 是**边界声明**——库承载状态机结构，不承载业务判断。这与本规范"方法库承载方法约束、不承载执行边界"是同型的表述，可作一份旁证。

### 4.6 GPTSwarm —— 编排框架，且把图本身当作被优化对象

〔以下为工具抽取的引号片段〕：

> "a graph-based framework for LLM-based agents"，支持 "the customized and automatic self-organization of agent swarms with self-improvement capabilities"

> "within an agent, the edges are fixed, whereas the inter-agent connections are getting optimized"

> "edge optimization" — "updates edge probabilities toward improvement of the benchmark score"

论文 "Language Agents as Optimizable Graphs"，ICML 2024 Oral（"top 1.5%, 144 in 9,473"，该项目声称）。

**归位**：编排框架（研究原型）。**写多少代码**：全部，且需 `OPENAI_API_KEY`。
**为什么值得记**：它是清单里唯一把**图结构本身作为可学习参数**的。这对本规范"演进"一章是一个反面参照：**边概率朝 benchmark 分数优化 = 被评价者在改考卷方向上迭代**。本规范已有的"被评价者不能看见考题"直接适用于此。

### 4.7 AutoGen / GraphFlow —— **已进入维护模式，这是维护成本的最硬样本**

逐字要点〔工具抽取〕：三层 API——Core API "implements message passing, event-driven agents, and local and distributed runtime for flexibility and power"；AgentChat API "implements a simpler but opinionated API for rapid prototyping"；Extensions API。工具 AutoGen Studio "provides a no-code GUI for building multi-agent applications"，AutoGen Bench "provides a benchmarking suite for evaluating agent performance"。

**关键状态**〔工具转述〕：AutoGen 处于 **maintenance mode**，"will not receive new features or enhancements and is community managed going forward"；微软转向 Microsoft Agent Framework，后者被定位为 "the enterprise-ready successor to AutoGen"。

**另外**：README 把这一条写作 **"AutoGen/GraphFlow"**，但我抓的 AutoGen README 里工具明确报告 "The page does not mention GraphFlow or graph-based workflow systems"。**GraphFlow 的具体形态本轮未核对。**

**对本规范的意义**：一个被 2026 年的综述列为"System Intelligence 标准载体"的库，其上游已停止新功能。**这就是"载体会死、语义不会"的一手证据**，也是不把规范条文押在具体库上的直接理由。

### 4.8 Microsoft Agent Framework —— 编排框架，图式模式，双语言

逐字〔工具抽取〕：

> "Microsoft Agent Framework (MAF) is an open, multi-language framework for building production-grade AI agents and multi-agent workflows in .NET and Python."

支持 "graph-based patterns such as sequential, concurrent, handoff, and group collaboration"。工具报告 MAF README **未明写**取代 AutoGen/Semantic Kernel，只提供两份 migration guide；不强制 Azure，宣称 "provider flexibility so your architecture can evolve without major rewrites"。

**归位**：编排框架。**写多少代码**：全部。
**注意冲突**："successor" 的说法来自 AutoGen 侧，MAF 侧未自称。取用时按前者记录，并注明来源不对称。

### 4.9 Claude Agent SDK —— **绑宿主的明确样本**

逐字〔工具抽取〕：

> "Python SDK for Claude Agent."

> "The Claude Code CLI is automatically bundled with the package - no separate installation required!"

工具报告："The documentation makes no mention of compatibility with non-Anthropic models or non-Claude-Code hosting environments."

**归位**：宿主 SDK。**可替换性判定：不通用。**它把 Claude Code CLI 打包进依赖。本规范硬约束（五种宿主通用）下，**它可以是可选实现之一，不能是规范条文的落点**。
（对称地，OpenAI Agents SDK 与 Google ADK 未在本轮逐字核对，但按同型推定应作同样处理——标未核对。）

### 4.10 Langflow 与 Dify —— **两个"少写/不写代码"的可视化载体**

**Langflow**〔工具抽取〕：

> "Langflow is a powerful platform for building and deploying AI-powered agents and workflows."

> "Visual builder interface to quickly get started and iterate"；"Source code access lets you customize any component using Python."

> "Deploy as an API or export as JSON for Python apps"；"Deploy as an **MCP server** and turn your flows into tools for MCP clients."

依赖：Python 3.10–3.14 + uv。

**Dify**〔工具抽取〕：定位 "an open-source LLM app development platform"；核心能力含 "Workflow"（visual canvas）、"RAG Pipeline"、"Agent capabilities"（50+ built-in tools）、Observability（Opik / Langfuse / Arize Phoenix）、LLMOps、Backend-as-a-Service。部署最低 CPU ≥ 2 Core、RAM ≥ 4 GiB、Docker Compose v2.24.0+。许可："Dify Open Source License, based on Apache 2.0 with additional conditions."

**归位**：编排框架的可视化外壳。
**写多少代码**：拖拽为主。**这是本卡"不写代码能落地吗"问题的一个正面答案，但答的是错的那个问题**——它们让你不写代码地搭一个**新应用**，不是不写代码地把规范装进**已有的 AI 编程宿主**。Langflow 的 "Deploy as an MCP server" 是唯一把两者搭起来的出口。

### 5.2 SWE-agent：接口设计是变量，不是模型

逐字全文摘要（arXiv:2405.15793，2024-05-06）关键句：

> "we posit that LM agents represent a new category of end users with their own needs and abilities, and would benefit from specially-built interfaces to the software they use."

> "SWE-agent's custom agent-computer interface (ACI) significantly enhances an agent's ability to create and edit code files, navigate entire repositories, and execute tests and other programs."

> "Finally, we provide insight on how the design of the ACI can impact agents' behavior and performance."

数字（该论文在该时点声称的观察）：SWE-bench pass@1 **12.5%**，HumanEvalFix **87.7%**。

**提炼**：真实系统里"图工程"的第一层不是画图，是**给 agent 造界面**。ACI 这个概念对本规范的价值在于：它把"agent 能做什么"从模型能力里剥出来，变成一个**可设计、可版本化、可评测的工件**。

### 5.3 TDAD：清单里最接近 codegraph 的东西，且它的产物是一个文本文件

（这条不在 Applications 节，在 Research Papers / State Management 节。因为用户明确设想过"codegraph 工具"，单列。）

**TDAD: Test-Driven Agentic Development - Reducing Code Regressions in AI Coding Agents via Graph-Based Impact Analysis**（arXiv:2603.17973，2026-03）。摘要逐字关键句：

> "AI coding agents can resolve real-world software issues, yet they frequently introduce regressions -- breaking tests that previously passed. Current benchmarks focus almost exclusively on resolution rate, leaving regression behavior under-studied."

> "TDAD builds a dependency map between source code and tests so that before committing a patch, the agent knows which tests to verify and can self-correct. **The map is delivered as a lightweight agent skill -- a static text file the agent queries at runtime.**"

> "TDAD reduced regressions by 70% (6.08% to 1.82%) compared to a vanilla baseline. **In contrast, adding TDD procedural instructions without targeted test context increased regressions to 9.94% -- worse than no intervention at all.**"

> "When deployed as an agent skill with a different model and framework, TDAD improved issue-resolution rate from 24% to 32%, **confirming that surfacing contextual information outperforms prescribing procedural workflows.**"

条件（必须一并记）：SWE-bench Verified；两个开源权重模型在消费级硬件上（Qwen3-Coder 30B，100 instances；Qwen3.5-35B-A3B，25 instances）。样本量小，数字只作该论文声称的观察。

**这条对本规范有三个用处，且其中一个是警告**：

1. **codegraph 的最小可用形态是一个静态文本文件**，不是图数据库。"依赖图"落地不必上 Neo4j。
2. **它跨模型跨框架迁移过一次**（"a different model and framework"），是清单范围内唯一有跨宿主迁移证据的图工程部件。
3. ⚠️ **只给程序性指令而不给目标上下文，比什么都不做更糟**（9.94% > 6.08%）。用户当前阶段是"先不写代码、只出文档与规范"——**这条直接命中这个阶段的风险**：一份只讲"应该怎么做"的规范文档，若不同时规定"每一步该被喂进什么具体上下文"，在这个实验的条件下是负收益。

### 5.4 Project ALICE（IBM Research）：真实运维系统里的图长什么样

〔以下为工具抽取，含逐字片段〕：

> Short for "Agentic Logic for Incident and Codebug Elimination," it's a new multi-agent system born out of IBM Research designed to automate these sorts of IT challenges.

流水线：

> "First, it'll initiate the investigation with an incident analysis agent that will gather observability data. Next, a **code context agent will generate a dependency graph** for interconnected pieces of software, and determine which micro services in the application are most likely to be relevant to the problem. Then, a code analysis agent...will work to localize where the bug is."

> Agents "communicate through the open **Model Context Protocol (MCP)**, allowing them to work in concert."

数字（IBM 自报）："a 10% to 25% improvement in identifying root causes of issues with the addition of agentic code analysis in ALICE."

限制与在建：目前辅助人类工程师；长期目标才是自主修；团队在做一个 "undo button"，用于 "agents like ALICE that are still learning to find the best way to solve problems."

**提炼三条**：

- 真实系统里的"代码图"是**运行期动态生成的依赖图**，且只用来做**范围收缩**（定位哪些微服务相关），不是一个长期维护的知识库。
- **跨 agent 通信选了 MCP**——一份把 MCP 当作图工程通信底座的生产侧证据。
- **"undo button" 是与自主性同步在建的**，不是事后补的。这与本规范"权限边界须与授权同时存在"同型。

### 5.5 OpenHands：多 agent 委派 + 沙箱，且是有基准的平台

摘要逐字关键句（arXiv:2407.16741，2024-07-23 / 2025-04-18 修订）：

> "we introduce OpenHands (f.k.a. OpenDevin), a platform for the development of powerful and flexible AI agents that interact with the world in similar ways to those of a human developer: by writing code, interacting with a command line, and browsing the web."

> "We describe how the platform allows for the implementation of new agents, **safe interaction with sandboxed environments for code execution, coordination between multiple agents, and incorporation of evaluation benchmarks.**"

> "we perform an evaluation of agents over 15 challenging tasks, including software engineering (e.g., SWE-BENCH) and web browsing (e.g., WEBARENA)"；MIT 许可；"more than 2.1K contributions from over 188 contributors."

**提炼**：这是唯一把 **"新 agent 的实现" + "沙箱" + "多 agent 协调" + "评测基准内建"** 四件事写在同一句话里的平台。对本规范"评估与演进"章的意义：**评测不是外挂，是平台的一等公民**。

### 5.6 MetaGPT：SOP 就是文档

摘要要点（arXiv:2308.00352，2023-08-01 / 2024-11-01）：

> "encodes Standardized Operating Procedures (SOPs) into prompt sequences for more streamlined workflows."

> "utilizes an assembly line paradigm to assign diverse roles to various agents, efficiently breaking down complex tasks into subtasks."

问题陈述：复杂任务的解 "are complicated through logic inconsistencies due to cascading hallucinations caused by naively chaining LLMs."

**提炼**：MetaGPT 的核心资产是**流程规范本身**，代码只是把它喂进 prompt 序列的管道。**这是"不写代码也能有产出"的正面样本**——但要和 §5.3 的警告合起来读：SOP 有效的前提是它同时规定了每个角色的**输入与中间产物**（"verify intermediate results"），不是只规定顺序。

### 5.7 Cline 与 OpenCode：两种"多 agent"配置形态的直接对照

**Cline**（`docs.cline.bot/sdk/guides/multi-agent-teams`）〔工具抽取〕：

> "Coordinate multiple agents working together on complex tasks with delegation, shared context, and result merging."
> "The coordinator decides how to split work, which agents to create, and how to combine results."

启用方式：session config 里 `enableAgentTeams: true`，再用 `team_spawn_teammate`、`team_delegate_task`、`team_check_status`、`team_get_result`。
状态：**"Team state persists across sessions" in `~/.cline/data/teams/[team-name]/`**，含 `task-board.json`、`mailbox.json`、`mission-log.json`。
代价（逐字）：

> "Teams add overhead. Use them when: The task naturally decomposes into independent subtasks..."
> "for simpler cases, a single agent with good tools is usually more efficient than a team"

**OpenCode**（`opencode.ai/docs/agents/`）〔工具抽取〕：

> agents are "specialized AI assistants that can be configured for specific tasks and workflows."
> Primary agents："the main assistants you interact with directly."（Build / Plan，Tab 切换）
> Subagents："specialized assistants that primary agents can invoke for specific tasks."（General / Explore / Scout，`@` 调用）

配置两种形态：`opencode.json` 里的 `agent` 段（字段含 `mode`、`model`、`prompt`（可 `{file:./prompts/build.txt}`）、`permission`），或 **Markdown 文件**放在 `~/.config/opencode/agents/`（全局）或 `.opencode/agents/`（项目内）。字段：`description`（必填）、`mode`、`model`、`prompt`、`permission`、`temperature`、`top_p`、`steps`、`color`、`hidden`、`disable`。

**这组对照是本卡最有操作价值的一处**：

| | Cline | OpenCode |
|---|---|---|
| 多 agent 的启用 | **SDK 代码**（`enableAgentTeams`）+ 内建 team_* 工具 | **配置文件**（JSON 或 Markdown） |
| agent 定义在哪 | 运行时由 coordinator 动态创建 | **仓库里的 `.opencode/agents/*.md`** |
| 共享状态在哪 | `~/.cline/data/teams/` 下的三个 json（**用户目录，不在仓库**） | prompt 可 `{file:...}` 指向**仓库内文件** |
| 跨工具可搬 | 否 | **agent 的 prompt 与 description 可搬，字段名不可搬** |

**判读**：OpenCode 的形态（Markdown + 一份权限声明 + 一个 prompt 文件引用）与 Claude Code 的 subagent 形态同型〔Claude Code 侧本轮**未逐字核对**〕。**"agent = 一份带 frontmatter 的 Markdown + 一份权限清单"是当前最有希望的跨工具公约数**，但字段名各家不同，可搬的是**内容**不是**文件**。

## 6. 基准与数据集：哪些在评"系统/工程落地"，哪些在评"模型能力"

README 把基准按同样的三层切。**这个切法本身就回答了本规范"评估与演进"章的核心问题**。

### 6.1 Model Intelligence 层（11 项）——**全部是评模型的，本规范不用**

### 6.2 Individual Intelligence 层（27 项）——**混合，需逐个判**

AgentBench · GAIA · AgencyBench · WebArena · OSWorld · **SWE-bench** · AppWorld · $$-bench · ToolSandbox · **AgentDojo** · **Harness-Bench** · Skill-Use · LongMemEval · MemoryAgentBench · MemoryArena · GateMem · MemSyco-Bench · Mem2ActBench · LongDS-Bench · **EvoMemBench** · Trainee-Bench · SEA-Eval · **Evo-Bench** · OpenClawBench · BenchTrace · **TheAgentCompany**

### 6.3 System Intelligence 层（28 项）——**这一层才是评系统的**

TaskBench · WorFBench · FlowBench · ComfyBench · TPS-Bench · JourneyBench · ETOM · LLM-Coordination · VillagerBench · MultiAgentBench · AgentsNet · DBS · SILO-BENCH · CoLLAB · Collab-Overcooked · MAS-BENCH · DPBench · CalBench · TAMAS · SyncBench · **MAST** · TraceElephant · MP-Bench · R2Act · MAFBench · MASEval · MAS-PromptBench · BenchAgent

### 6.4 五个可直接用来验一套开发工作流的基准（精读）

#### (1) Harness-Bench —— **本卡为本规范找到的最直接对口的基准**

**Harness-Bench: Measuring Harness Effects across Models in Realistic Agent Workflows**（arXiv:2605.27922，2026-05-27）。摘要逐字关键句：

> "performance depends not only on the base model, but also on **the harness: the system layer that manages context, tools, state, constraints, permissions, tracing, and recovery.**"

> "existing benchmarks typically abstract away execution, compare complete agent systems, or hold the harness fixed, making execution-layer variation difficult to study."

> "Harness-Bench evaluates representative harness configurations across multiple model backends under shared task environments, budgets, and evaluation protocols, **while preserving each harness's native execution behavior**."

> "The benchmark contains 106 sandboxed offline tasks constructed from practical agent-use patterns and manually reviewed for realism, solvability, oracle-checkability, and integrity."

> "Across 5,194 execution trajectories, we observe substantial variation in completion, process quality, efficiency, and failure behavior across model-harness pairings. **These results suggest that agent capability should be reported at the model-harness configuration level rather than attributed to the base model alone.**"

> "Our analysis further identifies recurring **execution-alignment failures, where plausible reasoning becomes decoupled from tool feedback, workspace state, evidence, or verifiable output contracts.**"

**为什么重要（三条）**：

- 它对 harness 的定义——**"context, tools, state, constraints, permissions, tracing, and recovery"**——几乎就是本规范正文的章节目录。这是一份外部、独立、以基准形式给出的**部件清单**。
- **"报告应在 model-harness 配置级别，而非归因于基座模型"** 是本规范"模型是可替换组件"的一份基准侧支撑。
- **"execution-alignment failures：看似合理的推理与工具反馈/工作区状态/证据/可验证输出契约脱钩"** ——这是一个可以直接进正文的失败模式命名，且它把"可验证输出契约"点了名。

#### (2) SWE-bench —— 评"能不能改对代码"，仍是模型/agent 层

摘要逐字：

> "an evaluation framework consisting of $2,294$ software engineering problems drawn from real GitHub issues and corresponding pull requests across $12$ popular Python repositories."

> "Resolving issues in SWE-bench frequently requires understanding and coordinating changes across multiple functions, classes, and even files simultaneously, calling for models to interact with execution environments, process extremely long contexts and perform complex reasoning that goes far beyond traditional code generation tasks."

> "The best-performing model, Claude 2, is able to solve a mere $1.96$% of the issues."（2023 年数字，仅作历史观察）

**判读**：SWE-bench 评的是**结果**（issue 解没解），不评**过程**。它对本规范的用处是**做基线与回归**，不是验工作流。TDAD 那句 "Current benchmarks focus almost exclusively on resolution rate, leaving regression behavior under-studied"（§5.3）正是对它的批评。

#### (3) TheAgentCompany —— 评"一个公司里的活能不能干完"

摘要逐字：

> "an extensible benchmark for evaluating AI agents that interact with the world in similar ways to those of a digital worker: by browsing the Web, writing code, running programs, and communicating with other coworkers."

> "We build a self-contained environment with internal web sites and data that mimics a small software company environment"

> "the most competitive agent can complete 30% of tasks autonomously... in a setting simulating a real workplace, a good portion of simpler tasks could be solved autonomously, but **more difficult long-horizon tasks are still beyond the reach of current systems.**"

**未核对**：任务总数、自托管组件（GitLab / ownCloud / Plane / RocketChat）、模拟同事、checkpoint 部分给分机制——abs 页不含，本轮未取。

**判读**：这是清单里最接近"验一整套工作流"的环境型基准，因为它**同时含代码、浏览、程序执行与同事沟通**，且是自托管可复现的。

#### (4) MAST —— 失败模式的分类学，可直接当检查表

**Why Do Multi-Agent LLM Systems Fail?**（arXiv:2503.13657，2025-03-17 / v3 2025-10-26；README 链的是 NeurIPS 2025 D&B Track 页）。要点〔工具抽取，含逐字片段〕：

> "the first Multi-Agent System Failure Taxonomy (MAST)"，含 **"14 unique modes, clustered into 3 categories: (i) system design issues, (ii) inter-agent misalignment, and (iii) task verification."**

规模："1600+ annotated traces collected across 7 popular MAS frameworks"；深析 150 条 trace；一致性 **kappa = 0.88**。
结论〔工具转述〕："identified failures require more sophisticated solutions"——**不是靠改 prompt 或调编排就能解决的**。

**判读**：三大类里第三类直接叫 **task verification**。这与本规范"验证者独立于生产者"是同一个位置的问题。**14 个具体模式本轮未取到条目名，标未核对**——若要进正文当检查表，须补读。

#### (5) Evo-Bench —— 评"系统能不能改进自己的 harness"

**Evo-Bench: Can Language Models Improve Agent Harness?**（arXiv:2608.09096，2026-08）。逐字关键句：

> "An emerging frontier is harness evolution---the agent's capacity to autonomously optimize its own operating harness."

> "existing evaluations fail to **isolate harness improvements from base model strength, prevent task-specific overfitting, or capture long-horizon iterative research.**"

> "while autonomous evolution outpeforms artificial harness in General tasks and excels in Search tasks, it **struggles in Office tasks that demand highly specific processing workflows.**"

> "our analysis exposes critical **temporal anomalies like early saturation**, while demonstrating that the synthesized harnesses act as highly transferable reasoning structures"

（"outpeforms" 为原文拼写，逐字保留。）

**判读**：两条可用——(a) 自动演进在**要求高度特定流程的任务上反而吃力**，这正是本规范的目标域（软件工程流程恰恰"highly specific"）；(b) **early saturation**（早期饱和）是一个演进机制的已知时间异常，本规范"演进"章需要一条对应的停机判据。

#### (6) 其余按用途归档（未逐个精读，标未核对）

- **安全/注入**：AgentDojo（"A Dynamic Environment to Evaluate Prompt Injection Attacks and Defenses for LLM Agents"；任务数量未核对）、TAMAS
- **记忆**：LongMemEval · MemoryAgentBench · MemoryArena · GateMem · MemSyco-Bench · Mem2ActBench · EvoMemBench
- **多 agent 协作/失败**：MultiAgentBench · Collab-Overcooked · SyncBench · MAFBench · TraceElephant · Who & When
- **工作流结构**：TaskBench · WorFBench · FlowBench
- **BenchTrace（arXiv:2605.29225）：抓取返回"PDF 为空"，完全未核对。**

## 7. 部件 → 可选载体 → 是否跨工具通用 → 是否需要写代码

判定口径：**"跨工具通用"= 同一份东西能在 codex / Claude Code / opencode / DeepSeek harness / VSCode Copilot 五者下都起作用**。"内容可搬、文件不可搬"单列，因为它是最常见的真实情况。

| 部件 | 可选载体（按代价从低到高） | 跨工具通用 | 需要写代码 |
|---|---|---|---|
| **阶段/任务图** | ① 仓库内一份 Markdown（阶段+依赖+每阶段输入产物）<br>② MetaGPT 式 SOP 文档<br>③ LangGraph / Burr / MAF 的图代码 | ①② **是**（纯文本）<br>③ 否（另起 runtime） | ①② **不用**<br>③ 全写 |
| **agent 角色定义** | ① 带 frontmatter 的 Markdown（OpenCode `.opencode/agents/*.md`；Claude Code subagent 同型〔未核对〕）<br>② `opencode.json` 的 `agent` 段<br>③ Cline SDK `enableAgentTeams` | ① **内容可搬、字段名不可搬**<br>② 否<br>③ 否 | ①② **不用**<br>③ 要 |
| **代码图谱 / 影响面** | ① **TDAD 式静态文本依赖图**（源码↔测试）<br>② 运行期动态生成的依赖图（Project ALICE 的 code context agent）<br>③ 图数据库（Neo4j 等） | ① **是**（就是个文件）<br>② 取决于宿主<br>③ 经 MCP 可 | ① **生成要，消费不要**<br>②③ 要 |
| **上下文装配 / 工具接入** | ① **MCP server**（消费端一段 JSON）<br>② 宿主自带的文件读取<br>③ 自建检索服务 | ① **是（当前唯一的真协议）**<br>② 否<br>③ 经 MCP 可 | ① **消费端不用，产端要**<br>③ 要 |
| **记忆 / 跨会话状态** | ① 仓库内的状态文件（决策记录、待办、已知失败）<br>② Graphiti（图库 + 双时序）<br>③ Letta（托管 agent 身份） | ① **是**<br>② 经 MCP 可<br>③ 否（绑 Letta） | ① **不用**<br>②③ 要 + 运维 |

| **评测** | ① 选定基准 + 判定口径的一份文档<br>② SWE-bench / TheAgentCompany 跑起来<br>③ Harness-Bench 式配置级对比 | ① **是**<br>②③ 需环境，不绑宿主 | ① **不用**<br>②③ 要 |
| **追踪 / 可观测** | ① 宿主自带日志<br>② Burr UI / Dify 的 Langfuse 等<br>③ 自建 trace | ① 各家格式不同<br>②③ 否 | ① 不用<br>②③ 要 |

**读表的一条结论**：每一行的 ① 都是"不写代码 + 跨工具通用"，且每一行的 ① 都存在。**这不是巧合，是因为 ① 全部是"仓库里的一份文本"。**"仓库内的纯文本"是这份材料范围内唯一一个在所有部件上都成立的跨工具载体。

## 8. 落地需要哪几件基础设施：给判据，不给清单

不给清单的理由：清单会随载体死亡而失效（AutoGen 已是样本）。以下三条是判据。

### 判据 A（必需性）：**没有它，某条规范条文就无法被判定为"已执行"或"已违反"**

满足 A 的即为必需。按此判，必需的只有三件，且三件都能是纯文本：

1. **可寻址的阶段边界**——没有它，"某阶段的产物须经验证"这类条文指向不了任何东西。最小形态：一份写明阶段、依赖、每阶段输入与产出的文档。
2. **跨会话可读回的状态载体**——没有它，"驳回原因须作为下一轮必需输入"无法执行。最小形态：仓库里一个文件。
3. **一个已知答案的验证参照**——没有它，"完成"不可判，"验证者独立"也无从谈起。最小形态：现有测试套件 + 一份判定口径文档。

Harness-Bench 对 harness 的定义（"context, tools, state, constraints, permissions, tracing, and recovery"）比这三件多，但那是**评测者**需要区分的维度，不等于**落地者**都得先建。

### 判据 B（可选性）：**它是否只是把仓库里已有的信息重新组织了一遍**

是 → 可选，属优化。图数据库、向量库、记忆服务、可视化画布全部落在这里：依赖关系本来就在代码里，历史决策本来就在 git 里。TDAD 是这条判据的实证——**依赖图落成一个静态文本文件就已经拿到大部分收益**（该论文在其条件下声称的观察）。

### 判据 C（引入门槛）：**它是否引入了新的失效面而没有自带独立探测**

引入即须配探测，否则不装。按此判：

- Graphiti 引入图库与限流（`SEMAPHORE_LIMIT` 默认 10）、小模型 JSON 抽取失败；
- Letta 引入"agent 身份不在仓库里"；
- Cline teams 引入 `~/.cline/data/teams/` 这个**在用户目录、不在仓库、不进版本控制**的共享状态；
- 任何编排 runtime 引入一整个新进程模型。

**这条判据也解释了为什么 AutoGen 的"维护模式"是一等信息**：一个库的上游停更本身就是一个失效面，而它不自带探测。

### 一个反判据（必须写下来）：**规范文档本身可以是负收益**

TDAD 的对照组：加了 TDD 程序性指令但不给目标测试上下文，回归率从 6.08% 升到 **9.94%**，比不干预更差；作者的结论是 "surfacing contextual information outperforms prescribing procedural workflows"。

**推论**：本规范每写一条"应该怎么做"，都必须同时回答"执行它的那一步会被喂进什么具体上下文"。只有前者、没有后者的条文，在这个实验的条件下应被视为**有害而非中性**。（该结论的条件：SWE-bench Verified，两个开源权重模型，125 个实例，样本小。不作强论据，作强提醒。）

## 9. 不写代码能落地到什么程度：明确的边界

**能（全部是"仓库里的文本"）**：

- 阶段与依赖的显式化（判据 A 第 1 件）
- agent 角色定义的**内容**（OpenCode 的 Markdown 形态已证明这条路存在；跨工具时搬内容不搬文件）
- 每阶段的输入上下文规定（TDAD 证明这比规定流程更有效）
- 权限边界的**语义**（"这一步不得写生产分支"）——各宿主的写法不同，语义可统一
- 评测口径：选哪个基准、以什么算通过、什么算回归
- 失败模式检查表（MAST 三大类可直接用；14 个具体模式待补读）

**不能**：

- 依赖图/影响面的**生成**（TDAD 的那个静态文本文件得有工具产出它）
- 跨会话状态的**读写机制**（文件能存，但"谁在什么时候写、下一轮谁读"要宿主支持）
- 沙箱与回滚
- 任何多 agent 的 mailbox / task-board（Cline 有，OpenCode 靠 subagent，两者不通）
- MCP server 的**服务端**

**边界的一句话**：不写代码能把**语义、判据、口径**全部落地；不能把**产出这些信息的机制**落地。而按判据 B，产出机制在第一阶段大多可以由人代劳一次，先验证语义对不对。

## 11. 对本规范的可取用点 / 不可取用点

### 可取用（按可取用强度排序）

1. **Harness-Bench 对 harness 的七维定义**——"context, tools, state, constraints, permissions, tracing, and recovery"。这是一份外部独立给出的部件清单，可用来**自检本规范的章节是否有缺项**，尤其 `tracing` 与 `recovery` 两项。
2. **"能力应报告在 model-harness 配置级别，而非归因于基座模型"**（Harness-Bench）——本规范"模型是可替换组件"的一份基准侧支撑，且给出了它的**评测形态**。
3. **"execution-alignment failure" 这个命名**——"看似合理的推理与工具反馈、工作区状态、证据、可验证输出契约脱钩"。这是一个比"幻觉"精确得多的失败模式名，且它把**可验证输出契约**点了名。
4. **TDAD 的反例**（§8 反判据）——程序性规范无上下文时是负收益。**这条应当直接影响本规范每一条条文的写法**：条文须成对出现（做什么 + 喂什么）。
5. **codegraph 的最小形态是一个静态文本文件**（TDAD），且它跨模型跨框架迁移过一次。这是对用户"codegraph 工具"设想的**降规格建议**：不必上图数据库。
6. **OpenCode 的 agent = Markdown + 权限字段 + prompt 文件引用**——当前最有希望的跨工具公约数形态，**搬内容不搬文件**。
7. **AutoGen 进入维护模式**——"载体会死"的一手样本，是不把条文押在具体库上的直接理由。
8. **MCP 是清单范围内唯一的真协议**，且有生产侧使用证据（Project ALICE 的 agent 间通信）与三个出口（MCP SDK / Graphiti mcp_server / Langflow 导出）。**消费端只写配置。**
9. **Apache Burr 的边界声明**——"will _not_ tell you how to build your models, how to query APIs, or how to manage your data"，与本规范"方法库不承载执行边界"同型，可作旁证。
10. **MAST 的三大类**（system design / inter-agent misalignment / task verification）可直接用作失败检查表的顶层分类。

### 不可取用

1. **整份清单不能当作选型依据。** 它没有筛选标准说明，收录不代表推荐，且已含一个上游停更的条目。
2. **所有百分比不得进正文作论据。** SWE-bench 的 1.96%、TDAD 的 70%、ALICE 的 10–25%、TheAgentCompany 的 30%，条件各异、样本各异、时点各异。
3. **"System Intelligence" 那 9 个编排框架不能作为本规范的落点。** 它们不在 AI 编程宿主内运行，采用其中任何一个都等于放弃"五种宿主通用"的硬约束。它们最多是**可选实现之一**。
4. **Claude Agent SDK 明确不可作条文落点**（绑 Claude Code CLI）。OpenAI Agents SDK 与 Google ADK 按同型推定同样处理，但**本轮未核对**。
5. **Letta 式的"agent 身份托管在服务端"与本规范"语义在仓库里"相冲**，不宜采用。
6. **这份材料的"图"不包含代码图。** 不能引用它来支持"codegraph 是图工程的公认部件"——恰恰相反，35 人署名的综述资源库里没有这个条目。
7. **Langflow / Dify 的"无代码"不解决本规范的问题。** 它们让你不写代码搭一个新应用，不是不写代码把规范装进已有宿主。
8. **GPTSwarm 的"边概率朝 benchmark 分数优化"是反面参照**，不可取用为演进机制——它等于让被评价者朝考卷方向迭代。
