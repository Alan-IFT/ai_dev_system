## 1. 文章在讲什么
WeTV 多端 Web 团队（V 站 SSR / M 站 CSR / Linux TV / Roku TV）在 2025 年初两个从 0 到 1 项目上开始用 AI，发现把规范放进"memory/上下文"会腐化（规则被忘、范式丢失、有 SDK 仍重写）。解法是把规范"外置"为机器可读契约：一份平台无关的四层领域模型（pages / ui-modules / data-layer / api-layer）+ 术语表，用 `_DETECTION_HINTS` 在初始化时探测各端真实文件生成映射，用 `_PLATFORM_PROP_VARIATIONS` 标注端差异。围绕契约编排一条 8 步流程（初始化 → 需求拆分 → 红队 → 验收标准 → 方案 → 编码 → 审查 → 本地门禁 + L0-L4 → 效果追踪），角色为 Command（入口）/ Skill（工具）/ Agent（reader、planner、executor、reviewer，图中另有 rendering-advisor 与 tester）。管理侧用自研 CLI 把 harness 源仓库分发到各项目并声明编辑边界。作者声称的结果只有一张仪表盘：首次通过率 80%、返工 0、门禁 88/100。

## 2. 核心主张
- **C1** 规范放在会话记忆里会随体量腐化；应外置为机器可读契约，让 AI"查"而不是"记"。｜支撑：三条失败现象（规则冲突/范式丢失/复用不识别），无量化｜适用：多端前端，已有多年沉淀的范式｜位置：1.2.1–1.2.2
- **C2** 通用契约定义"是什么"，映射文件定义"在哪、怎么实现"；路径不硬编码进契约，由探测生成，重构后重跑探测即可。｜支撑：路径硬编码失效的踩坑｜适用：多端同构业务｜位置：2.1、4.2（前三轮已吸收）
- **C3** 领域映射每层都要人确认，因为映射错则后续全部生成跟着错。｜支撑：推理｜位置：5.1.1
- **C4** 需求侧先做"红队"对抗（数据/交互/环境三类边界），把遗漏场景补回拆分文件，再从拆分 + 契约推导验收用例。｜支撑：图 005 一次真实报告（14 个遗漏场景）｜位置：5.2.4–5.2.5
- **C5** 验收标准是"TDD 契约"，用户确认后开发期间不得修改用例语义（图 007）。｜支撑：无（设计声明）｜位置：5.2.5 图
- **C6** 编码前拆成只读情报（reader）→ 方案（planner）→ 人审批 → 执行（executor）→ 独立审查（reviewer）；reader/planner/reviewer 都不改源码，executor 不自己发挥。｜支撑：早期"一口气干完"混乱的经验｜位置：5.3–5.4
- **C7** 所有用户交互必须在主面板，子 agent 只执行不交互。｜支撑：子 agent 弹窗导致主面板死锁，修两轮｜位置：03
- **C8** 五层门禁 L0-L4 各 20% 权重，≥70 通过，不通过打回。｜支撑：**无；实测截图（图 014）显示 L0-L3 未能运行、L4 跳过**｜位置：5.5.2
- **C9** 观测回收要记首次通过率、返工次数、任务完成数、红队发现数、变异测试评分。｜支撑：一张仪表盘（Token 栏为 N/A）｜位置：5.5.3
- **C10** Harness 源仓库是唯一真相源，项目内是分发副本；升级只覆盖通用文件，项目私有配置/工作流数据保留；孤儿文件必须检测处理。｜支撑：旧命令残留导致 AI 调错命令｜位置：6.3–6.5（编辑边界前三轮已吸收）
- **C11** 不用 Git Submodule 做分发（副本不是独立仓库、版本锁在父仓库、CI 拉不到）。｜支撑：踩坑列表｜位置：6.4
- **C12** 与 Copilot/Cursor/Devin/OpenHands 相比，本方案的差异是"多角色固化在流程里 + 领域模型注入"。｜支撑：一张对比表，无实测｜位置：03

## 6. 建议采纳（候选语义）
- **S1** 对抗性分析的每条被接受发现，必须转化为带稳定标识的验收条目，而不是停留在报告里。｜落地 A（外部状态存储）：验收清单文件中新增条目并回链发现编号｜落地 B（检查器）：状态转换前校验"已接受发现集合 ⊆ 验收条目引用集合"，缺失即阻断｜防御的失败：红队报告被确认后无人跟进，发现与验收脱钩（图 005→007 显示作者也只把 3/14 转成 AC）｜删除条件：模型能在生成验收时自动穷举并稳定覆盖边界场景，且回归评估证明对抗阶段无增量
- **S2** 验收条目确认后即冻结语义；实现期间任何修改验收条目的动作必须显式记录为"验收变更"并重新经原批准人确认。｜落地 A（人工检查点）：变更验收前必须回到提出验收的人｜落地 B（运行时拦截）：对验收工件的写操作在实施阶段被拦截并要求变更记录｜防御的失败：实现者通过弱化验收让自己通过（05 章 §6 已提，本文给出"冻结"这一具体形态）｜删除条件：写不出（责任判据：验收归属于人）
- **S3** 验证层未执行（脚本失效、依赖缺失、环境不可用、被跳过）必须与"执行且失败"区分，且未执行不得计入任何通过分数；含未执行层的完成判定为 UNDETERMINED。｜落地 A（检查器）：每层输出三态 PASS/FAIL/NOT_RUN，聚合器遇 NOT_RUN 不产生数值分｜落地 B（人工检查点）：完成声明模板要求逐层填写"执行了吗"，空项禁止签字｜防御的失败：图 014/015——五层未跑，综合分 88，宣布可提交｜删除条件：写不出（这是 D-014 空集合条款的推论，与模型能力无关）
- **S4** 检查器本身受"与被检对象一致"约束：检查器对项目结构/格式的假设过期时，应作为检查器故障上报并阻断，而不是降级为警告。｜落地 A（检查器）：检查器自检——其假设的路径/格式不存在时退出码为"配置失效"而非"通过"｜落地 B（条件加载规则 + 人工）：项目结构变更的评审清单包含"受影响检查器"一项｜防御的失败：图 014 L0/L1"脚本要求 src/modules/，项目用 src/pages/（已有问题）"长期存在｜删除条件：检查器能从项目当前结构自动推导其假设（即检查器不再含硬编码结构假设）
- **S5** 角色间交接产物有显式长度/内容预算，且下游只消费交接产物而不重读上游全部上下文。｜落地 A（静态指令）：角色定义中声明输出上限与必含节｜落地 B（检查器）：交接消息超限或缺必含节即拒收退回｜防御的失败：多角色链条中上下文取并集、每个角色重新发现同一信息（ATT-L 已述，本文给出 ≤500/≤400 字的实例）｜删除条件：模型的有效上下文与检索使"重读"成本可忽略，且评估证明摘要不丢关键约束
- **S6** 自动返工循环有上限，达上限后必须升级到人而不是继续；每轮结果写入可恢复的状态工件。｜落地 A（外部状态存储）：状态工件记录轮次，超限置 BLOCKED｜落地 B（运行时拦截）：第 N+1 次同类修复动作被拦截并要求人工决定｜防御的失败：审查-修复无限循环｜删除条件：D-003 的"无新证据即停"能被可靠机械判定时，本条被 D-003 覆盖
- **S7** 人工检查点必须出现在人能看见并能响应的交互位置；后台执行单元不得发起需要人响应的等待。｜落地 A（权限与隔离配置）：子执行单元无交互能力，只能返回｜落地 B（静态指令 + 人工流程）：角色约定"提问只由主控发起"，子单元遇需确认项即返回并标注｜防御的失败：C7 死锁（修两轮）｜删除条件：执行环境保证任何子单元的提问都路由到主交互面
- **S8** 分发型规范资产中区分"组织级（随分发覆盖）"与"项目级（分发不触碰）"两种所有权，升级操作只作用于前者并必须处理源端已删除项。｜落地 A（外部状态存储）：清单文件标注每项所有权，同步工具按清单覆盖/保留/清理｜落地 B（人工流程）：升级由维护者按变更摘要手工合并，同时核对废弃项｜防御的失败：孤儿旧命令被 AI 误调（C10）；项目经验被升级覆盖｜删除条件：规范资产改为运行时按版本拉取而非落地副本时

## 8. 该文暴露的失败模式
- **F1** 检查器结构假设与项目漂移（脚本期望 src/modules/，项目用 src/pages/；解析器不兼容新格式）→ 检查器报"脚本配置问题"而非 FAIL → 文章处置：无（标注"已有问题"后继续）→ 可构造回归 Case：故意重命名目录后运行门禁，期望结果为阻断而非提示。
- **F2** 五层验证层全部未执行（依赖缺失/被跳过）→ AI 仍输出"可以提交代码了"，仪表盘给出 88/100 → 处置：无 → 可构造：门禁全部置为 NOT_RUN，检查完成声明是否被拦截（D-014 空集合条款的直接测试）。
- **F3** 确定性检查该拦的问题流到了人工/模型审查（缺 import 的编译错误、error 级 lint 由 reviewer 发现）→ 说明前置门禁未真正运行或顺序未被执行 → 处置：reviewer 标 Blocking → 可构造：注入一个 tsc 必报错，观察是在门禁还是审查阶段被发现。
- **F4** 规则文本与执行流程分叉（正文"Lead 触发 reviewer" vs 流程图"executor 自己调用"）→ 读者/执行者不知以何为准 → 处置：无（作者未察觉）→ 可构造为规范自检 Case：抽样规则句，核对是否有对应执行路径。
- **F5** 子执行单元发起人工确认 → 主控看不见 → 死锁 → 处置：铁律"交互只在主面板"，修两轮 → 可构造：在子单元中触发一次提问，检验是否被路由或阻断。
- **F6** 分发只增不删 → 新旧命令并存 → AI 调用旧命令 → 处置：升级时检测孤儿文件三选一 → 可构造：源端删除一条命令后升级，检查副本中是否残留且是否可被调用。
- **F7** 观测指标与过程记录矛盾（返工 0 vs 同需求 NEEDS_REWORK；发现 13 vs 14；各阶段"首次通过" vs 门禁未跑）→ 指标由自报或部分采集而非事件推断 → 处置：无 → 关联 ATT-E"状态由事件推断"；可构造：比对 trace 中的 rework 事件数与仪表盘数值。
- **F8** 人读副本与机器读源并存（rules/domain-mapping.md vs config/domain-mapping.json；dev-tracker.md vs session-state.json）→ 潜在第二事实来源 → 文章未报告失败 → 可构造：只改一方后检查执行者读的是哪一方。
