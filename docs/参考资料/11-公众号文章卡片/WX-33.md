# WX-33 任何错误只犯一次：TencentDB Agent Memory 的团队记忆实践

## 0. 验证边界
- 材料性质：腾讯云数据库团队对自家开源产品（TencentDB Agent Memory，MIT）的一手叙述。三块"证据"全部为内部数据：2,600 个 Session 的离线分析、7 位研发访谈、35 个 Redis TAPD 工单构造的检索环境、SWE-bench 两轮评测。**没有任何一处给出样本数、重复次数或置信区间**；作者自己在 §5.3 承认这一点。
- 分析管线的"生产和审计都使用模型完成，并不是人工金标"（§3.3 原话）——所有 Relation/卡点数字是模型判模型，只反映内部自动化流程的自洽度。
- SWE-bench 60%→80%：条件是"相关 Case"子集（同仓库或确有关系），未给出 Case 数、模型版本、基线 Agent；对照存在（有/无团队记忆），但无重复运行。§5.1 的实验设计图与 §5.2 的两张结果截图在发布稿中**缺失**（见 §3），所以"前序学习/后序验证"的具体流程只能按文字理解。
- §5.2 的 17%→20%：50 题中 17% 不是整数（8.5 题），疑为四舍五入或口径不同；成本 $887.64→$717.78（−19.1%）与"turn 数降低近 19%"是两个数字碰巧相近，文中未分开解释。
- GitHub 仓库：`main` 分支为 v0.3.6（2026-05-27，OpenClaw 个人记忆插件），`master` 分支为 v2.0.0 Team Memory Beta（ROADMAP 标 v2.0.1-beta.1）。文章描述的 Memory Hub/Wiki/CodeGraph/Skill 只在 `master` 有；**文中的 60%→80% 不出现在任何一版 README**（README 只报 PersonaMem 48%→76%；旧版 README 另报 SWE-bench 58.4%→64.2%，条件是每 Session 连续 50 题、短期记忆压缩）。星数（首次抓取显示 25.4k）未能经 API 核实。
- 超出可核实范围：访谈原始记录、Redis 工单内容、2,600 Session 的来源与脱敏方式、"Top 50 最难题"的选取标准。

## 1. 文章在讲什么
问题：Agent 让个人执行能力猛增，但多人/多 Agent/多分支/多权限域环境下真正稀缺的是"协作带宽"——能在正确权限边界内被理解并直接用于任务的有效上下文。作者以 OPC（一人公司）为参照，把孙天祥"公司变成 GitHub 模式"的三层组织架构翻译成"上层治理边界 / 中层任务现场 / 底层可继承资产"。解法是 TencentDB Agent Memory：把 Session、文档、代码转成四类资产（Chat Memory L0-L3、Wiki、CodeGraph、Skill），由 Memory Hub 治理（Owner/Scope/Version/ACL/证据/状态），按"身份与 ACL → 固定绑定 → 浮动召回（BM25+向量+RRF）→ 装配（版本锁定、Token 预算）"生成 Memory Pack 送入任务，任务结束后候选资产经审核回流。证据链：2,600 Session 分析得出"相关≠可复用"（48,114 候选 → 231 强关系）与"逻辑返工 1,350 远多于缺少上下文 269"；访谈得出设计与 Review 比写代码更贵；Redis Case 得出 Scope 必须细到 Branch/Path/时间；SWE-bench 相关 Case 60%→80%，超长任务 17%→20% 且成本 −19%。结论：团队记忆首先是治理系统，"任何错误只犯一次"是带宽提高后的结果而非承诺。

## 2. 核心主张
- **C1** 协作带宽 = 单位时间内、在正确权限边界下、能被相关人或 Agent 正确理解并直接用于任务的有效上下文；会议/群聊/文档数量不是带宽。｜支撑：推理 + 协作成本公式（交接次数×单次成本 + 冲突消解 + 权限合规）｜适用条件：多人多 Agent 企业团队｜位置：§1.2
- **C2** 最危险的不是明显相反的习惯，而是高度相似资产间的细微差别（config/prod vs conf/prod；×0.5 vs ×2）；按语义相似度选"质量最高"会流畅地执行错误流程。｜支撑：构造案例，无实测｜位置：§1.2
- **C3** 三层组织架构不能只取"branch"比喻，必须补上 GitHub 真正支撑协作的版本、权限、Review、合并、冲突处理和回滚；"轨迹可见 ≠ 结论可信 ≠ 所有人都该看到"。｜支撑：推理｜位置：§1.3
- **C4** Spec 让一次任务的状态可表达，团队记忆让经过验证的任务状态可继承；Spec 不回答"类似问题是否发生过、某方案为何放弃、与另一分支规则是否冲突、是否有权进入当前任务"。｜支撑：推理｜位置：§1.4
- **C5** 团队记忆的定义：把背景、知识、代码关系、工作方法转为可检索、可组合、可追溯、可授权、可持续更新的资产并按需装配；比 RAG 多回答"属于谁、哪个版本成立、谁有权用、装配给谁、用后怎么修正"。原则："完整属于资产池，相关属于当前任务"。｜支撑：产品设计｜位置：§2.1、§2.4
- **C6** 内容分层 L0 原始对话→L1 原子→L2 场景→L3 画像，每层提炼但**不取代**上一层；高层减少阅读量，低层防止多轮总结失真。｜支撑：产品设计；README 称"没有任何摘要是不可逆黑盒"｜位置：§2.3.1
- **C7** 路由分层：先按 Team/User/Agent/Task/项目/可见性/ACL 缩小候选池（无权资产不进候选，而不是召回后再删）→ 人明确绑定的固定资产直接进入且不被相似度排序覆盖 → 权限内浮动召回 → BM25（错误码/文件名/符号）+向量（意图/故障模式）+RRF → 按角色/优先级/绑定方式/版本/Token 预算装配，任务期间可锁定资产版本。｜支撑：产品设计（图 007）｜位置：§2.3.2
- **C8** 渐进式暴露：Prompt 只说"有什么、为什么可能有用"，细节靠工具调用按需取（tools/list → tools/call）；受条数、单项长度、总字符、超时限制。｜支撑：产品实现｜位置：§2.3.3
- **C9** 资产跟着 Team 走而不是跟着 Agent 走；留在某账号/对话格式/框架缓存里的经验是私人缓存不是团队资产；框架中立的目的是"从宿主解耦"，不是兼容更多工具。｜支撑：推理｜位置：§2.4
- **C10** 资产形成四步：证据切分（可定位的 Task/Turn/页面/符号/提交）→ 候选抽取 → 作用域绑定（Owner/Team/Repo/Branch/Path/Version/Time/ACL/来源，"与正文同样重要"）→ **验证后升级**（未验证轨迹为低权重背景；被测试、提交或人工 Review 支持的才进入场景记忆或共享 Skill）。判断标准："能否降低下一次任务的不确定性"。｜支撑：产品设计｜位置：§2.5
- **C11** 模型容易发现两个任务有关系，很难判断是同一工作项/同一问题/可迁移 SOP："关联≠复用，复用≠可直接执行"；资产库不能只有保留/删除两态，需要强资产/弱提示/背景参考多置信层级并允许升降撤。｜支撑：内部数据：same_problem 精确类型正确率 38% 但"存在某种关系"95%；22,361 canonical 中仅 231 强关系（抽样有效率 95.24%/69.00%/83.33%）｜位置：§3.2
- **C12** 团队记忆应优先解决的损耗是逻辑返工而非找资料：卡点 2,203 个中逻辑返工 1,350、缺少上下文 269、重复失败 145、状态丢失 74；"找到很多相关内容仍重复同样的推理错误"，所以要存决策理由、失败路径、适用条件、验证方式。｜支撑：内部模型标注（审计精度 84%，非人工金标）｜位置：§3.3
- **C13** 访谈五点：设计与 Review 比写代码贵；人际共做小任务在减少、同步集中到评审/接口/合并，上下文恢复压力被推迟到 Review 和维护；存量代码的"为什么"最缺；新鲜度/来源/版本/调用透明度决定信任，静默注入"看起来合理"的文本会让人分不清模型判断与团队事实；Memory 管任务前的风险与背景，确定性工具（脚本/测试/检查项）管任务后的验证，二者不能互替。｜支撑：7 人访谈，脱敏｜位置：§4.1
- **C14** 产品顺序：先证明个人和项目内的即时价值（恢复状态、减少 Review 解释、生成更完整 Spec），再等团队复利；只靠"未来同事恰好遇到同类问题"冷启动不成立。｜支撑：访谈推论｜位置：§4.1
- **C15** 企业 Memory 的核心困难是"适用性判断"而非生成漂亮总结：Scope 细到 Branch/Path/配置/工单/版本/时间；强/弱/Shadow 不混用；禁止未来信息泄漏；每条结论必须回到原文；需要负例学习触发边界。｜支撑：35 个 Redis 工单 → 12,574 候选 → 57 相关（32 强/10 弱/15 背景），范围外与时间无效均为 0｜位置：§4.2
- **C16** 评测要问"Agent 能否从已完成任务学习并在后续相关任务表现更好"，不是"存了多少条"；三个约束：只在同仓库/确有关系任务间迁移、严格时间顺序、成功由任务测试判定而非模型自评。｜支撑：SWE-bench 相关 Case 60%→80%（无 n）；Top-50 超长单 Session 17%→20%、$887.64→$717.78、turn −19%｜位置：§5
- **C17** 六条设计原则：目的是继承状态非保存历史；价值是降低下次不确定性；抽象与证据同时保留；原子化可组合按任务装配（原子化≠越碎越好，而是清晰触发条件、单一责任、独立验证）；必须有生命周期（新增/Review/发布/Fork/合并/降权/锁定/过期/删除，人的负反馈必须改变后续路由）；与模型和框架解耦。｜支撑：综合｜位置：§6.1
- **C18** 多人环境六类工程问题：冲突（作用域过滤+版本优先级+冲突检测+人工确认）、新鲜度（valid_from/valid_to/最后验证时间/代码版本）、权限（先 ACL 后检索，引 NIST 零信任）、溯源、负反馈（标记/降权/撤回并影响相似资产触发规则）、成本。"没有治理，信息带宽提高的同时错误信息传播的带宽也一起提高。"｜支撑：推理；仓库现状见 §4/§9｜位置：§6.2
- **C19** "任何错误只犯一次"不是起点也不是承诺，而是有效上下文能安全准确流动后的结果；Memory 有明确边界：首次出现的引擎 Bug 历史无证据时不能替代新的调试；历史规则过期时必须靠版本/来源/测试结果降权或撤回。｜支撑：推理｜位置：§2.7 末、结语

**冲突展开（D-007 与"验证后升级"/自动写入）**
- 冲突在哪：D-007 要求"AI 只能提出候选，默认由所有者审批后写入"；本文/仓库是 AI **自动**把对话提炼为 L1-L3 并写入该 Agent 的 private 记忆，自动抽取 Skill（`mem:create-skill` 异步），并在下一次任务中默认注入。人的审批只出现在 **private→team 的共享边界**（"after review, they can be shared"）和 Hub 的"审核"动作。此外 §2.5 设想"被测试/提交支持的内容逐步进入共享 Skill"，即部分晋升可由机器证据触发。

## 6. 建议采纳（候选语义）
- **S1** 记忆资产进入任务前先按身份与作用域过滤，再做相关性检索；无权访问的内容不得进入候选集合（而非召回后剔除）。｜落地方式 A（权限与隔离配置）：检索接口以调用者身份/租户/项目为强制过滤参数｜落地方式 B（人工检查点＋外部状态存储）：无自动 ACL 的项目中，记忆文件按可见范围分目录存放，跨范围引用须人工确认｜它防御的失败：相似度最高但属于其他分支/租户的资产被流畅执行（C2、F1）｜删除条件：写不出（责任类约束，不随模型能力消解）
- **S2** 人明确绑定的规则/资产与自动召回的资产在装配中分属两类；前者不因相似度排序而被挤出。｜落地方式 A（静态指令）：会话起始固定加载清单与按需检索结果分区呈现｜落地方式 B（检查器）：装配结果校验"必需项全部在场"，缺失即失败｜它防御的失败：组织事实被一次相似度排序覆盖｜删除条件：模型能可靠区分"组织规定"与"相关参考"并自行保证前者在场（目前无证据）
- **S3** 同一任务执行期间，其依赖的规则与程序资产版本保持一致；任务中途不得读取到同一资产的不同版本。｜落地方式 A（外部状态存储）：任务记录中固化所依赖资产的版本标识，读取时按该标识取｜落地方式 B（人工流程）：任务开始时人工冻结相关规则的修改，结束后再合并｜它防御的失败：任务前后读到不一致规则导致局部修改互相矛盾｜删除条件：写不出
- **S4** 长期记忆条目按置信层级区分"可驱动执行 / 仅提示风险 / 仅帮助发现背景"，而非只有"保留/删除"两态；低层级条目不得单独作为执行依据。｜落地方式 A（外部状态存储）：条目元数据带置信层级字段，装配时按层级决定注入位置与措辞｜落地方式 B（条件加载规则＋人工检查点）：低层级条目只在人显式要求时加载｜它防御的失败：模型把"相关"当"可复用"（C11：精确类型正确率 38% vs 关系存在 95%）｜删除条件：模型判断"同一问题/可迁移 SOP"的精度经评估稳定高于人工阈值
- **S5** 从经验中提炼的记忆必须保留回到原始证据的链路；抽象层不得替代或删除其来源层。｜落地方式 A（外部状态存储）：每条摘要带来源定位（会话/工单/提交/测试）且来源不可被摘要覆盖｜落地方式 B（检查器）：晋升前校验来源可解析｜它防御的失败：多轮总结后失真、无法核对原话（C6、C15）｜删除条件：写不出（与 D-023 现实锚点同类）
- **S6** 记忆资产的晋升评估必须遵守时间顺序：目标任务之后产生的结论不得作为该任务的"历史经验"；有效性由任务的机器验证结果判定，而非模型自评。｜落地方式 A（检查器）：评估集按时间戳切分，泄漏即判无效｜落地方式 B（人工流程）：评估设计评审时逐条核对经验来源时间｜它防御的失败：评估结果虚高（未来信息泄漏）、"看起来有帮助"的自评｜删除条件：写不出
- **S7** 记忆晋升的优先目标是决策理由、被排除的路径、适用条件与验证方式，而非孤立事实。｜落地方式 A（静态指令/模板）：候选记忆的必填槽位含"为什么/排除了什么/何时适用/如何验证"｜落地方式 B（人工检查点）：审批时缺任一槽位即退回｜它防御的失败：找到很多相关内容仍重复同样推理错误（C12：逻辑返工 1,350 vs 缺上下文 269，内部观察）｜删除条件：写不出
- **S8** 记忆被使用时必须可见：使用了哪条、来自哪个任务、影响了哪一步。｜落地方式 A（运行时拦截/轨迹）：装配与调用记录进入 Trace｜落地方式 B（静态指令）：要求 Agent 在计划中引用所用记忆的标识｜它防御的失败：静默注入使人分不清模型判断与团队事实（C13）｜删除条件：写不出
- **S9** 首次出现、历史无证据的问题不得由记忆替代新的排查；记忆只提供任务前的风险与背景，验证由确定性程序承担。｜落地方式 A（静态指令）：召回为空时明确声明"无历史经验"｜落地方式 B（检查器/Gate）：完成判定只认测试与回读结果｜它防御的失败：把过期或不相关经验当作答案｜删除条件：写不出

- 三层 AI 组织架构与 OPC 叙事——组织形态论述，超出本规范作用域（D-022 只登记组织摩擦为观测维度）。

## 8. 该文暴露的失败模式
- **F1** 两份部署 Skill 描述几乎相同，一份读 config/prod/ 一份读 conf/prod/（或参数 ×0.5 vs ×2），系统按语义相似度取"质量最高" → 流畅执行完整流程但写错目录/污染环境/服务不可用 → 作用域过滤+版本优先级+冲突检测+人工确认 → **可构造**：两条仅一处路径不同、分属不同分支的资产，检查装配是否按当前分支选取并标出冲突。
- **F2** 新 Session 给 CodeGraph 加 impact 工具时只改工具定义数组，漏掉短名→内部名映射或绕开统一路由 → 工具可被发现但调用 403 unknown tool；或漏掉租户隔离/参数白名单/ready 状态 → Memory Pack 提供历史决策+调用链+检查清单，Agent 先出仓库级计划 → **可构造**："局部修改正确、系统行为不完整"的跨文件一致性 Case，验收含未知工具 403、跨租户 404、非 ready 空结果。
- **F3** 模型把"有关系"的历史任务判为"同一问题/可迁移 SOP"（精确类型正确率 38%）→ 错误 SOP 驱动执行 → 强/弱/Shadow 分级，只有强关系进入计划 → **可构造**：给定相关但不可迁移的历史 Case，检查 Agent 是否把它当作执行依据。
- **F4** 评估时把目标任务之后的修复结论当作历史经验 → 效果虚高 → 严格时间锚定、TAPD ID 确定性锚定 → **可构造**（评估集时间泄漏检查）。
- **F5** 找到大量相关资料后仍重复同样的推理回退（逻辑返工占卡点 61%）→ 保存决策理由/失败路径/适用条件/验证方式 → **可部分构造**：给 Agent 只含事实不含"为何放弃"的记忆 vs 含理由的记忆，比较是否重走被排除路径。
- **F6** 历史上正确的规则因接口升级/配置迁移失效仍被召回 → 错误执行 → valid_from/valid_to、最后验证时间、代码版本、降权撤回（本文列为需求，仓库未见实现） → **可构造**：过期规则与新版契约并存，检查是否按版本降权。
- **F7** 系统静默注入"看起来合理"的记忆文本 → 用户无法区分模型判断与团队事实，长期信任崩塌 → 调用透明、来源与版本可见 → **可构造**：检查计划/输出是否引用记忆标识与来源。
- **F8** 换人/换 Session/换 Agent 后只剩结论、文件或 Diff，缺背景与被排除路径（状态丢失 74、Review 需恢复背景）→ 从头理解 → Chat Memory+Spec+CodeGraph 同入任务包 → 与本规范 D-016 交接 Case 同类。
- **F9** 评估以"存了多少条 Memory/生成了多少 Skill"或模型自评"是否被帮助"为指标 → 指标上升而目标未改善 → 只认任务测试 → 属 D-023"指标被满足而目标被背叛"的记忆版。
