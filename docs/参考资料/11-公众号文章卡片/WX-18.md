# WX-18 Token降本50%：Harness工作流的成本优化实践

## 0. 验证边界
- 一手实践报告（腾讯内部团队、CodeBuddy 内网版 + AgentLens 平台）。全部数字来自作者团队内部度量平台的截图或作者转述；无外部可复核的原始数据，无重复运行，无消融。
- 对照形态：(a) 代码图谱有一组"同任务开/关"对照，各 1 次运行；(b) 子 Agent 化有一组"同工作流改前/改后"对照，各 1 次；(c) 主 Agent 端到端 708,783→315,266 是**全部十项改造叠加**后的前后对比，无法归因到单项；(d) rtk 只有组件级 `rtk gain` 统计，作者自述放弃端到端 A/B；(e) 模型分层的 -64% 是价格比换算（1−36%），不是测量；(f) "50%~65%"是作者按分项降幅反推，标题"降本 50%"即来自此反推。
- 超出可核实范围：AgentLens、CodeBuddy TeamCreate、CodeBuddy Hook 字段名（内网/厂商细节）；GLM-5V 相对 Sonnet 的价格比；作者所用模型/版本未说明（Fig 012 暗示主用 Claude Sonnet）；任务规模"中等需求"无定义。
- 与 ATT-L 相比，本文新增可核实的部分只有图中数据；这些数据的**测量条件**是本卡重点。

## 1. 文章在讲什么
作者团队用一个调度 Agent（tech-leader）+ 6 个短生命周期子 Agent 跑前后端全流程（需求分析→前后端并行编码→审查→测试→视觉校验→评测）。跑起来后成本不透明，先用内部平台按 Wave/Session 拆出消耗分布（测试 Wave 最贵、调度 Agent 次之，缓存命中率已达 93.5%），把消耗归为六类来源（系统提示词、工具返回、读取文件、长期记忆、历史消息、用户提示词）。围绕"只看当前需要的 / 减少无关的 / 减少重复的"三原则做了十个方向的改造：渐进式披露、确定性操作脚本化、外部数据获取子 Agent 化、长期记忆索引化、单 Agent 拆多 Agent、Agent 专属工具白名单+模型分层、代码图谱、稳定前缀+状态外化、避免重复加载 Skill、CLI 输出压缩、无依赖调用并行。作者报告：主 Agent 端到端 token -55.5%（轮次 17→9）、子 Agent 化后单会话 input -38.4%、代码图谱总 token -22.7%、SKILL.md 正文 -35%，并据此反推全流程可降 50%~65%；同时承认尚未做端到端 A/B 复核。

## 2. 核心主张
- **C1** 没有按执行单元拆分的消耗观测就无法优化；先建度量。｜支撑：Fig 003（按 Wave 聚合）｜适用条件：有 trace 上报平台｜文中位置：1.3
- **C2** 消耗可归为六类来源，其中历史消息是"真正的大头"，append-only 且滚雪球。｜支撑：Fig 002 表（推理性分类，无各类占比数据）｜适用条件：多轮多 Agent 工作流｜位置：1.2
- **C3** 拆多 Agent 本身不省钱（6 份系统提示词并行计费），收益是切断滚雪球并为后续优化打开空间；因此先做规模预判，小需求不拆。｜支撑：推理 + Fig 008 注释｜适用条件：需求规模可预判｜位置：2.1、3.2.1
- **C4** 条件性内容与步骤详情外移到资源层，正文只留"决定下一步走哪"的骨架。｜支撑：SKILL.md 198→128 行（静态体积）｜位置：3.1.1
- **C5** 确定性环境操作封装为脚本，模型只提供参数不拼命令；能用 CLI 就不用 MCP，因为每次 MCP 调用是一次完整推理轮次 + Schema 常驻。｜支撑：定性经验（拼错 DB 参数、绕过编译）、Playwright MCP→CLI 的三个问题（每步一次推理、不可重跑、不可并行）；无数字｜位置：3.1.2
- **C6** 大体量外部数据（需求全文、设计稿节点树）不应进入最长生命周期 Agent 的上下文，应由短生命周期子 Agent 获取并只回传结构化摘要。｜支撑：Fig 007，单会话 input 1,030,000→634,905（-38.4%，n=1）；作者指出首次调用两者相当，收益全在后续轮次｜位置：3.1.3
- **C7** 长期记忆先查索引再读正文，低于相关度阈值的文档从一开始不进候选。｜支撑：流程描述，无数字｜位置：3.1.4
- **C8** 每个角色只暴露自己需要的工具，未列出的工具不可见；稳定指令迁入子 Agent 系统提示词后派发提示词只剩动态内容。｜支撑：配置示例；派发提示词 10-15 行→2 行｜位置：3.2.2
- **C9** 轮次最多、推理要求低的角色（测试/视觉）换低价模型，节省随修复轮次倍增。｜支撑：价格比 36% → "-64%"（换算非测量）｜位置：3.2.2
- **C10** 代码图谱减少探索轮次，总 token -22.7%。｜支撑：Fig 009（n=1 对照，见 §3 对该表的重新计算）｜位置：3.2.3
- **C11** 前缀稳定才能命中缓存：动态内容后置；进度状态外化到文件而不在历史里累积输出；被唤醒先读进度文件而非回放历史，顺带获得中断恢复能力。｜支撑：原理说明 + 做法，无缓存命中率前后数据｜位置：3.3.1
- **C12** 信息在最上游收集一次、通过文档传给下游，下游不重新触发同一 Skill。｜支撑：前端 Agent 排查案例｜位置：3.3.2
- **C13** CLI 输出压缩的效果应用组件级可复现统计评估，因为端到端路径噪声比效果大；压缩幅度因命令而异，不能拿区间当固定值。｜支撑：Fig 011；作者自述 A/B 失败的经历｜位置：3.3.3
- **C14** 无数据依赖的调用应在同一轮内并行发起，省下的是历史被重复打包的轮次而非等待时间；"沉默的串行"藏在顺序思维里，需专门排查。｜支撑：TAPD/Figma 并行、Playwright 多 worker；无数字｜位置：3.3.4
- **C15** 落地优先级：规模预判+拆分（前提）→ 度量+重排+全局压缩（一个下午）→ 条件内容外移+状态外化+并行排查 → 图谱/CLI 替代 MCP/工具裁剪/子 Agent 化/记忆索引化（中长期）。｜支撑：作者经验排序｜位置：05

**冲突二：rtk 可以只做组件级对照（C13 vs ATT-F/D-025）。** 本文的论据是"rtk 压缩是纯文本过滤，跟大模型决策无关，100% 可复现"。ATT-F 用 24 组 pair、48 次运行 + 10 次重复测得：rtk 使终端字符 -40%，但命令事件 345→441、测试失败 31→56、总 token +4.23%，且宽泛搜索中预标记线索 158/178 个被过滤归零——**压缩改变了模型看到的东西，因此改变了路径**。"过滤本身可复现"不等于"过滤对后续决策无影响"。谁更强：ATT-F。可否共存：可以，但要修正 C13 的适用条件——组件级对照只证明局部层，路径层需要用轮次/工具调用数/失败重试数另测；D-025 的"退回组件级对照"须写明退回后**只能对局部层下结论**。

## 6. 建议采纳（候选语义）
- **S1** 成本优化的提案与报告必须以按执行单元拆分的消耗观测为基线，且报告口径须按计费类别加权（至少区分缓存读、未缓存输入、输出），不得只报原始 token 计数。｜落地方式 A（外部状态存储）：运行轨迹按会话/角色/阶段记录各类 token 并可事后聚合｜落地方式 B（人工检查点）：无分单元、无加权口径的优化提案不进入评审｜它防御的失败：F9（计数降 22.7% 而成本降约 7%）、优化针对了并非最贵的单元｜删除条件：执行平台原生给出成本加权的分单元报表且评审默认读取它。
- **S2** 大体量外部数据的获取与消化应由短生命周期执行单元完成，进入长生命周期单元的只能是结构化摘要；原始数据随短单元结束而离开上下文。｜落地方式 A（权限与隔离配置）：长生命周期角色不持有直接读取外部数据源的工具｜落地方式 B（静态指令/工作流合同）：把"获取并摘要"定义为独立子任务，其输出契约只允许摘要｜它防御的失败：F1｜删除条件：运行时能自动把历史中已消化的工具输出从后续轮次中移除且保持决策质量（供应商侧上下文编辑成熟并经评估）。
- **S3** 组装每次推理的输入时，稳定内容在前、易变内容在后；易变的进度/执行状态存于会话外可重读的记录，会话内只留最小变更行；恢复靠读记录而非回放历史。｜落地方式 A（静态指令）：派发模板固定"稳定块→动态块"顺序｜落地方式 B（检查器）：对派发内容或轨迹检查动态片段是否出现在稳定块之前、进度看板是否被重复输出｜它防御的失败：F2（缓存前缀被破坏、历史不可压缩、中断后无法恢复）｜删除条件：推理服务的缓存不再依赖前缀顺序，且会话恢复不再依赖历史回放。
- **S4** 无数据依赖的多次调用应在同一决策轮内发起；工作流定义完成后须专门审计"沉默的串行"。｜落地方式 A（静态指令）：派发规则声明可并行的调用集合｜落地方式 B（检查器）：在轨迹上检测"后一调用的输入不含前一调用的输出"却顺序发起的模式｜它防御的失败：F3｜删除条件：模型默认能识别独立调用并自行并行（可用轨迹上串行独立调用的出现率判断）。
- **S5** 对某机制的评价须先判定它是否影响模型的决策路径：只有与决策路径无关（输入输出可离线复现且不改变模型所见信息）的机制，才允许仅以组件级对照下结论；凡改变模型所见信息的机制，即使组件层可复现，也必须另报路径层指标（轮次、工具调用数、失败重试数）。｜落地方式 A（人工检查点）：评估评审先回答"该机制改变了模型看到什么吗"｜落地方式 B（检查器）：eval manifest 中缺路径层指标而机制类型标为"改变模型所见"时拒绝｜它防御的失败：F5 与冲突二（把可复现误当成路径中性）｜删除条件：写不出（这是评估方法论，不依赖模型能力）。
- **S6** 引用工具或厂商的效果数字时，必须标注该数字所在的评价层（局部输出/行动路径/整体结果）与测量条件，且不得跨层引用。｜落地方式 A（静态指令/写作规范）：来源登记表增加"评价层"字段｜落地方式 B（人工检查点）：评审核对引用数字与被支持结论是否同层｜它防御的失败：F10（用 71.5×/单次查询 支持端到端结论）｜删除条件：写不出。
- **S7** 拦截或改写类机制的"已配置"不等于"已生效"；接入后必须有一次生效回读（观察到至少一次实际拦截/改写及其效果），静默失效视为未接入。｜落地方式 A（检查器）：接入后运行探针命令并比对改写前后输出｜落地方式 B（人工检查点）：验收要求附一条真实轨迹证明拦截发生｜它防御的失败：F4（字段名不一致、不报错不生效）｜删除条件：执行平台对拦截器注册做强校验并对无效返回报错。
- **S8** 多执行单元拆分的升级理由中应显式包含"需要上下文重置时机"（生命周期可切段），拆分的成本（并行的固定开销）与收益（切断累积）都须在提案中列出。｜落地方式 A（人工检查点）：D-010 升级评审增加这一项｜落地方式 B（检查器）：轨迹统计单会话历史长度增长曲线，作为是否需要切段的信号｜它防御的失败：F11（单体 Agent 历史无限累积）或反向失败（为不需要切段的小任务付并行固定开销）｜删除条件：运行时能在单会话内安全重置上下文并保持任务连续性。

## 8. 该文暴露的失败模式
- **F1** 长生命周期调度者直接获取大体量外部数据 → 原始负载在其后每一轮重复进入输入（作者报告 50+ 轮）→ 改为短生命周期单元获取并只回传摘要 → **可构造**：同一任务两种获取方式，度量获取后第 N 轮的输入量增长曲线（N≥10 才能看出差异，作者指出首轮相同）。
- **F2** 每次阶段切换在会话内输出完整进度看板 → 前缀不再稳定、历史不可压缩、中断后只能回放历史 → 状态外化到文件 + 单行变更输出 → **可构造**：对比两种做法的缓存命中率与中断恢复成功率。
- **F3** 两个无数据依赖的子任务被顺序派发（顺序思维） → 多一轮历史打包 → 同一轮并行发起 → **可构造**：轨迹检查器识别"独立调用顺序发起"模式。
- **F4** 拦截器输出字段名与宿主要求不一致（updatedInput vs modifiedInput） → 不报错、不生效、无人察觉 → 加转换脚本 → **可构造**：接入任何拦截器后无生效证据即判为未接入（对应 D-023 现实锚点：配置存在不是观察）。
- **F5** 用"同一需求跑两遍完整工作流"评估单项机制 → 路径波动（探索轮次、重试）大于效果 → 退回组件级对照 → **可构造**：D-025 验证 Case；但注意冲突二——退回后不得对路径层下结论。
- **F6** 模型自行拼接环境命令（数据库连接参数、启动命令） → 拼错、绕过编译、反复查找参数 → 封装为参数化脚本 → **可构造**：统计同类任务中环境类命令的失败重试次数。
- **F7** 下游角色重新触发上游已执行过的知识加载 → 同一资源在多个角色的上下文中重复常驻 → 上游写入文档、下游只读文档 → **可构造**：轨迹上同一资源被 >1 角色加载即告警。
- **F8** 所有子 Agent 默认继承全部已注册工具的 Schema → 每轮固定开销与角色无关（作者估 10-15KB/40 工具） → 角色工具白名单 → **可构造**：对比同一角色两种工具集下的单轮固定输入。
- **F9** 用原始 token 计数报告"降本" → 缓存未命中上升被掩盖，成本降幅远小于计数降幅（图 009：-22.7% vs 约 -7%）→ 文章**未察觉、未处置** → **可构造**：任何成本报告须能通过"按计费类别加权后结论是否不变"的复核。
- **F10** 引用工具官方的单次查询倍数（71.5×）支持端到端结论 → 端到端实测相差一个数量级 → 文章未讨论落差 → **可构造**：来源登记时核对评价层。
- **F11** 单体 Agent 全流程一条会话 → 各领域规范混入同一历史、无重置时机、越跑越贵 → 拆为调度者 + 短生命周期角色 → **可构造**：单会话历史长度增长曲线作为切段信号。
- **F12** 十项改造叠加后用单次前后对比归因各项 → 无法分离单项贡献，且反推全流程降幅被用作标题 → 作者自述待补端到端 A/B → 对应 D-025 与 06 章"先写成功标准再运行"。
