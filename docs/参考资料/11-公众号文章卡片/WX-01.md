## 1. 文章在讲什么
问题：Claude Code 用户如何从"能用"走到"用得好"。解法：把作者 11 个月的个人经验整理成 42 条技巧，按基础（1–10）/进阶（11–25）/高阶（26–42）分级，最后给一条一键配置脚本。作者声称的结果：无量化结果，只有"效率上一个台阶"、"顶尖 1% 的玩法"等主观表述。技巧覆盖四类东西：终端人体工学（状态栏、别名、快捷键、语音）、上下文管理（新会话、compact、handoff、half-clone、精简 CLAUDE.md、按需加载）、执行与权限（容器、免审批、审计已批准命令、后台任务、worktree）、验证与迭代（写-跑-验循环、TDD、草稿 PR、自我复核、简化代码）。对本项目的价值不在任何单条技巧，而在于它给出了一份**"个人级 Harness"的完整清单**，可用来检验本规范的层/闭环是否覆盖了实践者真实在做的事，以及哪些被文章当成"技巧"的东西其实是本规范意义上的语义不变量。

**最有价值的三个引用：**
1. **review-claudemd skill**：把"改进闭环"落成了可执行步骤——从最近 N 个会话记录里提取用户/助手消息，分批给子代理，对照现有入口指令输出四类信号：被违反的指令、该加到项目级的模式、该加到全局的模式、疑似过时条目。这是本规范 D-013 Add/Thin 和 D-021"规则绑定失败"缺少的**信号来源**：违反记录 = 该规则"只写成提醒不够"的证据（应下沉为拦截或删除），无消费记录 = 可删候选。
2. **gha skill 的调查协议**：先区分致命错误与非致命警告，再查**同一 job**（不是整个 workflow）的 10–20 次历史判 flaky，再定位破坏提交并要求"之前全过、之后全挂"的双向验证，最后查是否已有修复 PR。这是"先找最早偏离点、用真实运行结果驱动排查"（06 §5、ATT-K）的一份具体 Runbook，且内置了对"模型看到任何错误就当根因"这一失败的防御。
3. **check-context.sh + half-clone**：作者明确选择"确定性截断（保留原文后半段）"而非"摘要压缩"，理由是截断快、确定、不改写原话。这给本规范 03 §8"压缩与外部化"补了一个被忽略的选项：压缩策略至少有清空/截断/摘要/外部化四种，各有信息损失形态；截断保真但丢早期决策，摘要保决策但可能改写事实。

## 6. 建议采纳（候选语义）
- **S1** 累积授予的免审批权限是一个会漂移的集合，必须可枚举、可机械扫描、有复审周期；单次交互审批不得直接沉淀为永久授权。｜落地方式 A（检查器）：定期对权限配置跑危险模式扫描并输出分级报告｜落地方式 B（权限与隔离配置）：把高风险操作放进隔离环境，使 allowlist 无需包含它们｜落地方式 C（人工检查点）：每次新增永久授权需独立于当次任务的复核｜它防御的失败：审批疲劳把 `rm -rf`/`sudo` 沉淀为永久授权，后续会话在无人看时执行（Reddit 清空 home 事故）｜删除条件：执行环境默认对不可逆操作强制隔离或幂等，使 allowlist 不再承载危险动作
- **S2** 上下文压缩策略是显式选择，至少区分：清空、确定性截断、摘要、外部化为交接件；每种要声明丢失什么、保留什么，且压缩后必须重新核对状态源。｜落地方式 A（外部状态存储）：交接件承载目标/进展/失败尝试/下一步，新会话只加载它｜落地方式 B（运行时拦截）：用量越过阈值时阻止继续并强制切换｜落地方式 C（人工检查点）：关闭自动压缩，由人决定时机并复核交接件｜它防御的失败：摘要改写或遗漏已失败的尝试，新会话重复试错；自动压缩在错误时机触发丢掉中间状态｜删除条件：模型在满窗口下无质量退化，或工具的压缩可被证明不丢失状态字段
- **S3** 会话启动时的固定上下文开销（系统级指令 + 能力/工具描述）是可测量的预算项；能力描述应按需加载而非全量常驻。｜落地方式 A（条件加载规则）：工具定义在被检索到时才注入｜落地方式 B（权限与隔离配置）：按项目只启用需要的能力集合｜落地方式 C（检查器）：启动后测量固定开销占比并在超预算时告警｜它防御的失败：可用工作窗口在动手前已被占去可观比例，长任务更早触发压缩｜删除条件：上下文窗口足够大或工具描述由模型内化/延迟解析成为默认
- **S4** 验收标准（测试）在实现之前固化并版本化；实现过程对验收标准的修改必须被检测并单独审批；人要检查验收标准不是恒真。｜落地方式 A（外部状态存储）：先提交测试再实现，基线可回溯｜落地方式 B（检查器）：比对实现提交与基线，验收文件变更即失败或要求说明｜落地方式 C（人工检查点）：合并前人工审阅测试本身｜它防御的失败：实现者通过弱化/改写测试自证完成；测试直接返回 true｜删除条件：写不出（责任判据：验收由谁定义不可转移）
- **S5** 从执行轨迹中定期提取三类信号反哺入口指令：被违反的指令、反复出现的人工纠正、无消费的条目；违反记录是"该要求不能只写成提醒"的证据，触发下沉为拦截/检查器或删除。｜落地方式 A（检查器）：脚本抽取近期会话与入口指令做对照并产出报告｜落地方式 B（人工检查点）：定期人工复盘纠正记录｜落地方式 C（条件加载规则）：按触发条件加载的复盘方法｜它防御的失败：入口指令只增不减（ATT-N 膨胀机制）；提醒被忽略却无人发现｜删除条件：写不出（Thin 的依据必须来自观察，不随模型变强消失）
- **S6** 并行会话数量的上限取自人的跟踪与复核能力，而非工具并发能力；隔离技术（独立工作树等）是并行的前提，不是并行的理由。｜落地方式 A（人工检查点）：约定同时在跑的任务数上限并在看板可见｜落地方式 B（权限与隔离配置）：在启动器上设并发容量上限｜它防御的失败：多会话互相踩踏、人对任一会话都失去审查（D-024 的并行版）｜删除条件：可靠的自动验证覆盖到每条并行链，人的跟踪不再是瓶颈
- **S7** 等待外部长任务时，观察频率应随等待时间递减，每次观察只取状态摘要而非全量日志。｜落地方式 A（静态指令）：告知执行者退避策略｜落地方式 B（检查器/工具）：提供阻塞式"等待直到完成并返回摘要"的工具｜落地方式 C（外部状态存储）：任务完成事件写入可轮询的状态记录｜它防御的失败：流式日志灌满上下文；频繁轮询消耗预算｜删除条件：工具原生提供事件通知
- **S8** 失败分类补一项：产物范围蔓延——执行者做了未被要求的改动或引入了非必要复杂度；处置是定期以"每处改动的理由"为问题做简化审查。｜落地方式 A（检查器）：变更范围与工作项声明的文件/模块集合比对｜落地方式 B（人工检查点）：审查时要求逐处说明改动理由｜它防御的失败：改动难审、隐藏回归｜删除条件：模型的最小改动偏向可被评估证明

## 8. 该文暴露的失败模式
- **F1** 用户在多个项目多次点"总是允许" → allowlist 累积 `rm -rf`/`sudo`/`Bash` 通配 → 某次 `rm -rf ... ~/` 清空 home（Reddit 事故）→ 文章处置：cc-safe 扫描 → **可构造**：给定含危险模式的权限配置，检查器必须分级报出；给定容器内命令应跳过
- **F2** 自动压缩在任务中途触发 → 摘要丢失"已尝试且失败"的路径 → 新会话重复同一失败尝试 → 处置：手写交接件含 What didn't work，关闭自动压缩 → **可构造**：压缩后向执行者提出同一问题，检查是否重走被记录为失败的路径（与 D-003 Case 合并）
- **F3** 长会话跨多个不相关话题 → 输出质量下降、忽略早期指令 → 处置：/clear 或新会话 → 可构造但噪声大：同一任务在干净/污染上下文下的通过率对比（需多次重复，见 D-025）
- **F4** 让模型"看 CI 为什么挂" → 模型把第一个看到的 warning 当根因 → 处置：gha 协议先分辨致命/非致命，再查同一 job 历史 → **可构造**：日志中含非致命错误在前、真实失败在后的 CI 记录，检查报告是否指向真实触发点
- **F5** 等待构建时持续 `gh run watch` → 流式日志灌满上下文 → 处置：指数退避 + grep 状态行 → 可构造：测量等待期间上下文增量
- **F6** 模型写的测试恒真 → 实现"通过"→ 处置：人工审阅测试 → **可构造**：注入恒真测试，检查器/审查是否拦下（变异测试可自动化）
- **F7** 模型对无法访问的来源（Reddit 403）不报告不可达而是编造/放弃 → 处置：兜底抓取路径 → **可构造**：给不可达 URL，要求输出必须标注"未能获取"（对应 D-023 现实锚点）
- **F8** 对工具内部（bundle）打补丁的补偿措施 → 工具自动更新后补丁失效或行为异常 → 处置：关闭自动更新 → 不宜作回归 Case，但是 D-021"补偿面过期"的现成实例：该技巧在原仓库后续版本被作者自行删除
- **F9** 跨目录/多 worktree 时给相对路径 → 改错文件 → 处置：realpath → **可构造**：两个同名文件在不同工作树，检查执行者是否核对工作区身份（对应 03 §2 工作区身份）
- **F10** 模型做未要求的改动、过度抽象 → 审查困难、隐藏回归 → 处置：定期简化审查 → **可构造**：diff 触及工作项范围外文件时告警
