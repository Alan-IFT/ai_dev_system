## 1. 文章在讲什么
问题：Agent 的"理解业务"（意图识别）常被当成 Prompt/Few-shot/RAG 的选型问题，作者认为应先回答四个业务问题——意图数量、标签是否常变、标注数据是否充足、一次判断需要几轮上下文——再决定技术路线。解法：把意图识别拆成随业务复杂度递进的分工：规则接住确定流量 → 分类器处理高频稳定意图 → Embedding 缩小候选 → LLM 处理模糊长尾 → 意图 RAG 动态供给业务定义与案例 → 多轮状态跟踪 → 规划器拆解复合任务；生产上用级联把它们串起来，并在识别之外单独设权限层与执行层，给每次判断保留执行/追问/拒识/确认四个出口。作者声称的结果：这套分工能随业务复杂度持续升级、按请求难度分配算力、每层可单独监控替换回滚。**无任何量化结果。**

## 2. 核心主张
- **C1** 选型前先回答四个业务问题（意图数量、标签变动频率、标注数据量、所需上下文轮数），答案基本决定技术路线。｜支撑：推理｜适用条件：对话式业务 Agent｜文中位置：引言
- **C2** 规则应只守"高频、确定、风险敏感"的流量；规则数量增加后冲突、优先级和维护成本快速上升，其余交给统计模型。｜支撑：举例（"退款/取消订单"）+ 推理｜适用条件：业务启动期｜位置：第一节
- **C3** 离线准确率高的分类器会在促销、新产品、新政策上线后快速退化，因为它只学了历史分布。｜支撑：推理，无数据｜适用条件：标签稳定、有标注语料的场景｜位置：第一节
- **C4** 语言相似 ≠ 业务动作相同（"怎么取消订单" vs "为什么订单被取消"），因此 Embedding 只适合召回候选，最终判断交给分类器或 LLM。｜支撑：反例｜适用条件：冷启动/少样本｜位置：第一节末
- **C5** 把全部意图定义和案例塞进 Prompt 会带来上下文膨胀、标签混淆、成本和维护困难；系统应自然演进到"先缩小范围，再判断"的两阶段架构（意图 RAG）。｜支撑：推理｜适用条件：意图数量增长到几十个｜位置：第二节
- **C6** 两阶段架构必须**分别评估召回层与判断层**：目标未进 Top-K 则下游无法补救；已召回却选错，问题在意图边界、案例质量或判断提示词。｜支撑：推理｜适用条件：任何检索+判断结构｜位置：第二节
- **C7** 意图库除标准定义外，还应收录口语表达、相邻意图、混淆反例、业务前置条件、历史误判；LLM 合成同义句只补长尾，**线上真实请求才是最重要的更新来源**。｜支撑：推理｜适用条件：意图库运营｜位置：第二节末
- **C8** 多轮场景要判断的是"状态"不是"一句话"：把历史整理成结构化状态（当前任务、已确认槽位、待补槽位、上一步工具结果、最近一次用户修正），识别目标设计为一次**状态更新**（延续/切换/取消/完成 + 参数修正），减少旧意图残留。｜支撑：JSON 示例｜适用条件：多轮任务型对话｜位置：第三节
- **C9** 复合请求应输出命令序列或执行图而非单标签；此时意图识别已扩展为语义解析、任务拆解和规划，并需识别高风险步骤。｜支撑：例子 + 图 003｜适用条件：复杂 Agent｜位置：第三节
- **C10** 生产级采用级联：规则（确定性命令与安全拦截）→ 轻量分类器 → Embedding 召回 → LLM → RAG → 规划器，每层保留拒识、追问、升级通道；收益是按难度分配算力，每层可单独监控、替换、回滚，新增意图只改相关分支。｜支撑：图 004｜适用条件：生产环境｜位置：第三节
- **C11** 识别之后单独设权限层与执行层：意图层答"想做什么"，权限层答"能否做"，执行层答"是否应立即发生"；三者分开以避免模型把"理解成功"误当"授权完成"。｜支撑：推理 + 例子（删数据/转账/发外部消息需二次确认）｜适用条件：有不可逆动作的 Agent｜位置：第三节
- **C12** 完整意图系统要有四类出口：执行、追问、拒识、确认；缺信息追问、置信不足拒识、高风险进确认，条件充分且权限通过才调用工具。｜支撑：推理｜位置：第三节
- **C13** 评估要超越整体 Accuracy：不均衡用 Macro-F1、相邻意图看混淆矩阵、召回层看 Recall@K、槽位看字段级 F1、多轮看切换与状态更新准确率；生产还看拒识率、追问率、工具调用成功率、端到端完成率、延迟、单次成本。｜支撑：无（清单）｜位置：第三节
- **C14** 系统能力越强，对"不确定性"的管理应越精细：何时直接行动、何时升级模型、何时停下追问。｜支撑：观点｜位置：结尾

## 6. 建议采纳（候选语义）
以下全部为**类比外推**（对话 Agent → 编码 Agent），每条都标注了外推的等价物。

- **S0** 领域/业务知识是**受治理的知识资产**（有 owner、结构、更新来源、可单独评估），Prompt 只是把其中一部分装入当前推理的通道；不得让 Prompt 成为业务知识的唯一存放地。｜落地方式 A（外部状态存储）：业务定义、边界、反例以条目形式存于项目知识库，按任务检索装入｜落地方式 B（静态指令）：会话入口只写"去哪里找业务定义"的地图，不内联定义本身｜落地方式 C（检查器）：检测入口指令中内联的业务定义条目数超过阈值即告警（阈值为项目参数）｜它防御的失败：业务知识散落在多个 Prompt 副本中互相打架、无人拥有、无法单独评估（F5，与 D-015 "多份默认入口取并集"同族）｜删除条件：写不出——这是治理归属问题，不随模型能力消解。
- **S1** 进入 Agent 的领域知识条目不应只有"定义"，还应绑定**真实样例、相邻易混项、反例（明确不属于此项的表达）、适用前置条件、历史误判**。｜落地方式 A（外部状态存储）：项目知识条目的结构包含上述字段，缺失字段显式标空｜落地方式 B（检查器）：知识晋升时检查条目是否带至少一个反例或来源事件，否则拒绝晋升或标"待补"｜落地方式 C（人工检查点）：知识 owner 审批时按此清单核对｜它防御的失败：模型把表面相似的请求映射到错误的业务动作/错误的规则（F2、F1）｜删除条件：在代表性 Case 上，去掉反例与误判字段后模型的边界判断错误率无可测差异。
- **S2** 上下文装配的"检索/路由"环节与"判断/生成"环节必须可**分别评估**：先测正确来源是否进入工作集，再测在工作集内是否选对。｜落地方式 A（检查器 + 轨迹记录）：每次任务记录实际加载集合，与该 Case 标注的必需来源比对，得到召回是否命中｜落地方式 B（人工检查点）：失败复盘时先问"对的材料在不在上下文里"，再问"看到了为什么还错"｜它防御的失败：正确来源未进入上下文，团队却在下游无限追加 Prompt（06 §5 的反例；F1）｜删除条件：写不出——只要存在"按需加载"，该层就存在。
- **S3** 理解层的输出**不得直接触发**不可逆动作；意图确定、权限校验、风险分级、执行是四个独立判定，前者通过不蕴含后者。｜落地方式 A（权限与隔离配置）：执行能力由工具侧策略决定，与模型对指令的解读无关｜落地方式 B（运行时拦截）：不可逆动作发生前按风险等级要求二次确认｜落地方式 C（人工检查点）：高风险动作由指名责任人确认｜它防御的失败：模型把"用户说了要删"当作"已授权删"（F4）｜删除条件：写不出——责任不可转移（D-020 责任判据），不随模型能力消解。
- **S4** 每个需要判断的环节保留四类显式出口：**执行 / 追问（信息缺失）/ 拒识（置信不足，拒绝猜测）/ 确认（高风险）**；输出必须声明走了哪个出口。｜落地方式 A（静态指令 + 输出结构）：要求判断结果带 next_action 类字段且取值限定在四类｜落地方式 B（检查器）：输出缺少出口声明或在"拒识/追问"状态下仍出现执行动作，判为不通过｜它防御的失败：信息不足时模型强行选一个解释并执行（F5）｜删除条件：eval 显示模型在无此要求下的自发追问/拒识行为与有要求时无差异。
- **S5** 领域知识条目的**更新来源以真实误判事件为主**；每次晋升知识必须引用触发它的事件；合成/推测的样例只能标为"补充"，不得作为唯一依据。｜落地方式 A（外部状态存储）：知识条目带 source_event 字段，指向 Case 注册表｜落地方式 B（人工流程）：知识 owner 定期用真实失败清单核对知识库，而非凭想象补写｜它防御的失败：知识库只反映设计者想象的分布，线上分布变化后静默失效（F6）｜删除条件：写不出——这是数据来源纪律，不依赖模型能力。
- **S6** 长任务/多轮交互中，对新指令的识别目标是**状态更新**而非孤立分类：必须显式判定新指令相对当前工作项是延续、切换、取消还是完成，并记录被修正的参数。｜落地方式 A（外部状态存储）：工作项状态携带"最近一次用户修正"与转移类型｜落地方式 B（静态指令）：会话协议要求 Agent 在处理新指令前先声明其与当前工作项的关系｜落地方式 C（检查器）：状态转移不在合法集合内时阻断｜它防御的失败：旧任务上下文残留导致新指令被套到旧任务上（F3）｜删除条件：长会话 eval 中旧意图残留错误率降至与短会话无差异。

- **S7**（弱候选）为领域知识选择进入 Agent 的机制（内联指令 / 按需检索 / 条件加载 / 训练）之前，先记录四个量：知识条目数量、条目变动频率、可用真实样例量、单次判断需要的上下文跨度；机制随这四个量的变化而重选，而非一次定型。｜落地方式 A（人工检查点）：知识入口设计评审按此四问核对｜落地方式 B（外部状态存储）：知识库元数据记录条目数与最近变更时间，超出上次选型时的假设范围即触发复查｜它防御的失败：知识量增长后仍沿用"全部内联"的初始方案（F5 的前置）｜删除条件：写不出（这是选型纪律，不是模型能力补偿）。本条外推自 C1，证据仅为作者推理，标为弱候选。

## 8. 该文暴露的失败模式
- **F1** 正确来源未进入工作集（检索/路由失败）→ 模型基于错误候选自信地给出判断 → 文章：分开评估召回层与判断层，失败回流修库 → **可构造**：为某任务标注必需的 source of record，故意让路由不命中，观察 Agent 是否报"信息不足"还是用相近但错误的来源作答。
- **F2** 表面语言相似但语义/动作相反（"怎么取消订单" vs "为什么订单被取消"）→ 向量召回把两者当近邻，单纯相似度检索选错 → 文章：Embedding 只召回，判断交给更强的判断者；意图库收混淆反例 → **可构造**：准备两份措辞相近但功能相反的文档/函数（"如何启用 X"与"为何禁止 X"），观察检索与最终选择。
- **F3** 多轮中旧意图残留（"换成明天吧"被套到上一个任务）→ 参数被写到错误的工作项 → 文章：识别目标改为状态更新，显式判定延续/切换/取消/完成 → **可构造**：会话中切换工作项后发出省略主语的修正指令，检查修正落到哪个工作项。
- **F4** 理解成功被当成授权完成 → 高风险不可逆动作在无确认下执行 → 文章：意图/权限/执行三层分离，高风险进确认流程 → **可构造**：用户以自然语言要求删除/发送外部消息，观察 Agent 是否在权限校验与确认前动作。与 D-027/D-028 Case 同族。
- **F5** 意图定义与案例全部塞进 Prompt → 上下文膨胀、标签混淆、成本上升、维护困难 → 文章：两阶段召回 + 判断 → **可构造**：规则/知识条目数递增，测量遵循率与混淆率变化（与 ATT-N 的 Case 同构）。
- **F6** 离线表现好的判断在新产品/新政策上线后退化 → 知识落后于业务变更，静默失效 → 文章：意图库以线上真实请求持续更新 → **可构造**：变更产品定义后不更新知识条目，观察 Agent 是否沿用旧定义（对应 D-005 版本错配 Case）。
- **F8** 复合指令被当单标签处理（"查余额，够的话转 500，再把结果发我"）→ 任务结构（顺序、条件、依赖）丢失，只执行其一或顺序错乱 → 文章：输出命令序列/执行图，标出高风险步骤 → **可构造**：给出含条件分支与依赖的多步请求，检查 Agent 是否先拆解并标出不可逆步骤（对应 ATT-K "先规划后行动"）。
- **F7** 规则数量增长后规则间冲突与优先级不清 → 维护成本上升、结果不可预测 → 文章：规则只守最确定的流量 → 可构造性一般：与 ATT-N "隐性冲突静默择一"合并处理。
