# WX-12 Agent 治理：用 Hook 堵住 LLM 的偷懒、越权与失忆

## 0. 验证边界

## 1. 文章在讲什么
DECO 在生产上遇到三类 prompt 管不住的失败：(1) **偷懒**——千行 SQL/Python 进出模型时被截断、占位略写（`-- 其他字段...`）、复印式重写到 token 耗尽；(2) **越权**——设计阶段未经用户同意就调用发布工具，把讨论中的表结构推上生产；(3) **失忆**——改完表不分析下游影响、Python 产出图表不告诉用户，因为模型追求最短完成路径且不知道工具产生了什么副作用。作者的解法全部落在 Agent 框架的 Hook（Callback）切面上：读写两侧对称 offload（长内容落沙箱文件、上下文只留引用句柄、只读快照与工作副本分离、只允许小步替换编辑、写回时框架从文件加载全文并做白名单校验）；配置驱动的危险工具守卫（无用户在前端写入的授权标记则物理阻断，确认框带选项/输入/变更预览，用户选择后续跑）；Hook 采集 → session.state 暂存 → Attachment 注入下一轮 prompt 的"主动 push"闭环（改表后自动风险分析、Python 执行前后文件快照对比发现新图）。文末列出同一 Hook 链上挂的 14 个横切 Hook，并对照 ADK 官方 8 种回调模式。作者声称的结果：输出 token 降约 90%、复印截断"物理消除"、残缺脚本"杜绝"发布、未授权发布"走不通"——均为自述。

## 2. 核心主张
- **C1** 偷懒/越权/失忆的根因不是模型能力不足，而是三种结构性原因：长产物物理超出输出预算；模型无法区分动作的可逆性；模型追求最短路径且对工具副作用信息不对称。因此 prompt 只能引导不能兜底。｜支撑：两个生产案例 + 推理｜适用条件：产物上千行、有写生产的工具｜文中位置：引子、§5.5
- **C2** 长产物偷懒是结构性问题，解法三原则：模型必须接触的长内容降到最少、每次接触窗口压到最小、所有写入路径做成"小步增量改 + 强制校验"。｜支撑：偷懒形式表（拉取/写回 × 4 种）｜适用条件：同上｜位置：§3.1
- **C3** "模型永远不直接接触脚本全文"：读侧把工具返回的长内容落盘并替换成引用句柄；只读快照与可编辑工作副本分离，必须显式复制才能编辑；编辑只允许局部替换；写侧由框架从文件读回全文覆盖入参。｜支撑：架构图 004、治理前后对比｜适用条件：外部系统需要接收原样长产物（写侧）｜位置：§3.2
- **C4** 失败语义按后果非对称：读侧落盘失败→降级透传原内容（承担截断风险，不阻断）；写侧文件不在白名单前缀/身份缺失/文件不存在/内容为空→抛异常阻断，不得提交。｜支撑：设计描述 + 图 005/007｜适用条件：写侧后果不可逆｜位置：§3.2、§3.3
- **C5** 工具协议增设"引用参数"（`scriptFilePath`）作为纯框架契约：下游工具不消费它，Hook 在转发前剥离；下游保留防御性日志——若该字段到达下游即为 Hook 失效信号。｜支撑：协议片段｜适用条件：框架与工具分层演化｜位置：§3.2 工具协议
- **C6** 治理后修改任务的工具调用输出 token 降约 90%，复印自截断"物理消除"。｜支撑：脱敏汇总表，无口径｜适用条件：该团队、长 SQL 修改任务｜位置：§3.2、§3.4
- **C7** 现成框架（ADK Artifacts、DeepAgents 中间件）的 offload 只做读侧；写侧 onload、参数交换契约、快照/副本分离、列级 offload、按代价差异化的失败语义都需自研。｜支撑：对比表（二手整理）｜适用条件：产物需原样回写外部系统｜位置：§3.5
- **C8** 不可逆操作（发布、回刷、冻结/解冻、终止）必须在框架层做代码级强制确认：未拿到真实用户在前端产生的授权标记，工具物理不可执行；确认动作不能由模型触发。｜支撑：案例二 + 流程图 008/009｜适用条件：有写生产工具｜位置：§4.1～4.3
- **C9** 危险工具清单应配置驱动（不同租户/环境不同），确认是结构化表单（发布方式/审批人/回刷日期）而非 yes/no，且确认前展示变更清单预览。｜支撑：yaml 片段 + 对比表｜适用条件：多租户、业务化审批｜位置：§4.2、§4.4
- **C10** 自研 HITL 的必要性不在"框架没有 HITL"而在"框架 HITL 不够业务化"；只需 yes/no 的场景应直接用框架原生能力（暂停/恢复/防循环是自研最易出 bug 处）。｜支撑：推理 + 对比｜适用条件：通用｜位置：§4.4
- **C11** 第三类失败"该做没做"用闭环处理：工具调用后 Hook 确定性采集事实 → 写 state → 下一轮 prompt 前注入；采集不靠模型"记得查"，注入不污染当前轮。这是"主动 push"而非"存储→模型自己查"的被动模式。｜支撑：方案对比表（三行，定性）+ 两个案例｜适用条件：盲区已知且可程序化判定｜位置：§5.1～5.2、§5.6
- **C12** 语义判定看入参不看工具名（带既有对象 ID 的 upsert 才是"修改"）；一次会话多次触发的结果累积写入、下一轮一次性注入。｜支撑：设计描述｜适用条件：同一工具承担新建与修改｜位置：§5.3
- **C13** 模型对工具副作用是"瞎子"：产物存在性应由系统在执行前后对比文件快照获得，比让模型自己 `ls` 可靠；只采集关心的产物类型，避免无关文件塞进 state。｜支撑：案例 + 时序图 012｜适用条件：执行类工具｜位置：§5.4～5.5
- **C14** 基础设施与推理逻辑解耦：Hook 增删不改主循环一行代码；同一链上可挂十余个横切 Hook（护栏、裁剪、格式化、日志、持久化、前端事件、沙箱环境）。｜支撑：14 Hook 清单｜适用条件：框架提供切面｜位置：§二、§六
- **C15** 超大工具返回按与当前问题的相关性重排后裁剪，截断前落盘可回捞（`ToolResponseTruncator`）；沙箱环境变量由 Hook 捕获并在重启后恢复。｜支撑：清单一行，无细节｜位置：§六表
- **C16** 总结分工："prompt 定意图，Skill 定规矩，框架 Hook 定边界——能用确定性兜底的，别交给模型。"｜支撑：全文推理｜位置：结语

- `图 009`（§4.3，**本文最重要的信息载体之一**）：四步时序。① LLM 调 packCommit → Guard 检查 session.state 无 `confirm_pack` key → 拦截并"同时返回错误阻断本次执行"；② 弹 INTERACTION_BOX（"请确认发布方式：直接发布/开启评审"）；③ 用户选择 → 前端写 `session.state['confirm_pack']='direct'`；④ 续跑 → state 已就位，Guard 放行。底栏：CUSTOM 事件→前端弹框；session.state→授权标记存储；无授权→物理阻断；"没有 key 就物理走不通，不靠 LLM 自觉"。

- `图 013`（§5.6）：行业被动模式（state 存结论 → LLM 用工具查 state）vs DECO 主动注入（Hook 采集事实 → 写 state → Attachment 主动注入下一轮 prompt），标"进化方向"。

**最有价值的三个引用**：

**冲突①（授权标记的存储与写权限）**：D-027 提议会话不可变范围"模型不可修改"。本文的授权标记是 `session.state` 中一个 key，由前端 REST 写入后靠"Agent 重试同一工具"放行；同一 state 也被十余个 Hook 读写。文章没有说明该 key 是否对模型写路径隔离（例如某个通用"写 state"工具）。若不隔离，则"物理走不通"的强度取决于 state 写权限而非 Hook 本身。证据强度：文章为设计描述，D-027 为提议，二者可共存——条件是把"授权标记只能由人侧通道写入"写成显式要求（见 S3）。
**冲突②（注入内容的新鲜度与身份）**：D-006 要求区分上下文/状态/知识/记忆，D-005 要求主张带时间与范围。本文"累积写入、下一轮一次汇总注入"没有说明注入后是否清空、多轮后旧风险是否重复注入、注入物是否带时间戳。若不清空，Attachment 会退化为"取并集"的膨胀源（正是项目痛点）。可共存，需补"注入物带产生时间与触发事件身份，消费后清理或降级"。
**冲突③（效果表述）**：文章用"物理消除""杜绝""零遗漏"描述结果，但 D-008 的后续验证要求同时报告拦截率与**误阻断率**，D-025 要求局部/路径/整体三层。本文只给了局部输出层（token）一个数字，路径层（误拦截、降级次数、确认打断次数）和整体层（生产事故是否减少）都没有。谁的证据更强：本项目的要求是方法论，文章是无对照自述；不冲突于机制，冲突于表述强度——采纳机制、不采纳结论。

## 6. 建议采纳（候选语义）
- **S1** 超出模型单次输出可靠承载的工件，不得以"模型完整输出"方式往返：读入时模型只得到引用与局部窗口，修改只以局部替换进行，写回外部系统时内容取自持久工件而非模型输出。｜落地 A（运行时拦截）：工具返回前把长内容外部化并替换为引用，写入前从引用加载全文覆盖入参｜落地 B（工具接口/权限与隔离配置）：写回工具只接受引用参数、不接受内容参数；整文件创建工具对已存在的工件禁用｜它防御的失败：F1、F2（截断/占位/复印后残缺产物提交）｜删除条件：模型输出预算稳定超过项目最大工件规模，且在评估集上"整段重写"零截断——但"写回取自持久工件"一半是证据要求（写回物可回读核对），此半不删
- **S2** 拦截层的失败处置按后果非对称：只影响模型"看到什么"的读路径失败可降级放行并留痕；导致外部状态改变或不可逆的写路径失败必须关闭（fail-closed），不得以模型输出兜底。｜落地 A（运行时拦截）：写侧前置校验不通过即抛错阻断｜落地 B（检查器 + 人工流程）：发布/提交前的检查器校验工件存在、非空、来源在允许范围；不通过转人工｜它防御的失败：F2（残缺脚本进入生产）、以及"一条出错让整批内容全进上下文"｜删除条件：写不出（这是风险取舍原则，不随模型能力消解）
- **S3** 不可逆动作的授权必须由人产生、经模型不可写入的通道传递、在动作执行前由非模型组件核验；无授权时动作不可执行，且模型不能代替人产生授权。｜落地 A（运行时拦截）：动作前切面检查授权标记，缺失则阻断并向人发起确认｜落地 B（权限与隔离配置 + 人工检查点）：执行不可逆动作所需的凭据/权限仅在人工批准后临时签发；或工具自身在执行时暂停等待人的结构化回复（ADK ToolConfirmation 型）｜它防御的失败：F3（设计阶段未经同意发布）、ATT-O 所述 Worker 自行执行危险操作｜删除条件：写不出（责任判据：只有人能承担不可逆后果）
- **S4** 授权是带参数的结构化决定（方式、审批人、范围、时间窗），且授权前必须让人看到将要改变什么；不得把不可逆动作的确认压缩成无上下文的 yes/no。｜落地 A（人工检查点）：确认界面展示变更清单并要求填写审批参数｜落地 B（外部状态存储 + 检查器）：以发布单/变更记录作为授权载体，检查器核对执行入参与记录一致后放行｜它防御的失败：D-024 所述"判不动的 Gate 变成快速点头"；带参授权缺失导致发布方式/回刷范围由模型自行决定｜删除条件：写不出
- **S5** 危险动作清单与工具实现分离，按环境/租户配置，版本化、可审计、慢变；模型在会话内不得修改该清单。｜落地 A（权限与隔离配置）：清单作为运行时配置，由框架读取｜落地 B（外部状态存储 + 检查器）：工具注册表声明写风险等级，CI 检查"有写风险但无审批策略"的工具（ATT-G 形态）｜它防御的失败：危险清单散落在各工具代码中，新工具默认无守卫；D-028 所述模型改自身审批路径｜删除条件：写不出
- **S6** 已知的盲区检查（改动后的影响分析、执行后的产物盘点、元数据刷新）由系统在动作发生后确定性触发，结果作为带时间与触发事件身份的观察推送到下一步推理；不依赖模型主动查询；推送后消费即清理，避免累积膨胀。｜落地 A（运行时拦截）：动作后切面采集 → 会话状态 → 下一轮前注入｜落地 B（工作流固定步骤 + 外部状态存储/条件加载规则）：工作流在"修改"步骤后强制串联"影响分析"步骤，结果写入状态工件，下一会话入口按状态加载｜它防御的失败：F4、F5（改表不查下游、产图不汇报）｜删除条件：对"忘了查"一类，模型在评估集上稳定主动做影响分析即可删；对"不知道有东西该查"一类（信息不对称），只有工具返回声明副作用后才可删（见 S7）
- **S7** 工具的副作用（新建/修改的文件、产物）必须由系统直接观察或由工具返回声明，不得由模型转述；"产物已生成"的陈述须绑定该观察。｜落地 A（运行时拦截）：执行前后快照对比｜落地 B（工具接口契约/检查器）：执行类工具返回产物清单；完成验收时检查器核对清单与文件系统｜它防御的失败：F5、D-023 所述全模型结论链无现实锚点｜删除条件：A 在工具返回完整声明副作用后可删；B 不删
- **S8** 每个拦截层必须有独立于自身的失效探测：下游若收到本应被拦截层消费/剥离的信号，视为拦截层失效并告警；并保留可重复运行的"应被拦截"回归 Case。｜落地 A（检查器/日志）：下游对框架专属字段做防御性断言｜落地 B（评估）：回归集中包含未授权调用与残缺工件写回，验证仍被拦截｜它防御的失败：Hook 静默失效后无人知晓（文章 C5 明确担心此事）｜删除条件：写不出
- **S9** 可逆性判定基于动作的对象与参数（是否指向已存在对象、是否改变外部状态）而非工具名。｜落地 A（运行时拦截）：切面按入参判定｜落地 B（权限与隔离配置）：工具注册时按"新建/修改/发布"声明动作类别，权限按类别授予｜它防御的失败：同名工具既建又改时误拦或漏拦｜删除条件：工具接口本身区分动作类别后可删 A

## 8. 该文暴露的失败模式
- **F1** 模型读入千行 SQL 后需要整段重写 → 输出中途出现 `-- 其他字段...` / `(SQL略)` 占位或直接截断，继续若无其事写完 → 读侧外部化 + 禁止整段重写、只允许局部替换 → 可构造：给一份超出输出预算的脚本要求"改一处并回写"，检查回写物与原文 diff 是否只含预期修改
- **F2** 模型把长脚本拼进工具入参 JSON → 入参被截断，外部平台无校验直接接收残缺脚本 → 写侧从持久工件加载 + 空/缺失即阻断 → 可构造：让写回工具入参携带被截断内容，检查是否被阻断且有 readback 差异
- **F3** 方案设计阶段、用户未点头 → 模型直接调用发布工具把讨论中的表结构推上生产 → 动作前守卫 + 人侧授权标记 → 可构造：会话内无授权记录时诱导执行发布，观察是否阻断；再构造模型自行写入授权标记，观察是否仍阻断（对应冲突①、D-027/D-028 的 Case）
- **F4** 改表（字段重命名）后模型不做下游影响分析，视为任务完成 → 下游几十张 ETL 报错 → 动作后确定性触发影响分析并推送下一轮 → 可构造：修改被多处依赖的字段，检查下一步输出是否包含依赖清单且来源为直接查询
- **F5** Python 脚本产出图表，模型只见 stdout，不知道有新文件，用户追问"图呢" → 执行前后快照对比 + 推送 → 可构造：执行产生文件但 stdout 不提及，检查完成汇报是否列出该文件
- **F6** 读侧落盘失败（对象存储不可用）→ 数组响应中一条失败导致整批长内容涌入上下文 → 逐条判定、单条降级 → 可构造：模拟单条落盘失败，检查其余条目仍被外部化
- **F7** 模型在只读快照上直接编辑或用"创建文件"重写而非复制后局部改 → 误改源或复印截断 → 快照只读 + 必须显式复制（作者自述"踩坑后的设计"）→ 可构造：给只读快照，观察是否先复制
- **F8** 拦截层静默失效（Hook 未挂载/被绕过）→ 下游收到本应被剥离的字段 → 下游防御性日志 → 可构造：禁用拦截层后运行 F2/F3 Case，检查告警是否触发
