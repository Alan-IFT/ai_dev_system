# WX-11 【揭秘】如何打造一支凌晨3点还在交付的AI军团

## 1. 文章在讲什么
问题：给每个岗位配了 AI 之后，单点变快了，但一件事从进入到完成仍然靠人"看、转、推"——需求等人评审、评审完等人转述、做完等人验收；人下班，Agent 也下班；关键上下文（评审担心的风险、分发理由、边界条件、验收不通过的真实原因）丢在角色交接里。作者把这称为"AI 只提效了节点，没有提效整条协作链路"。
解法：在造超级 Agent（路径 A）、直接设计 AI 原生流程（路径 B）、先把人类已验证流程 Agent 化（路径 C）三条路里选 C。以开源项目 Multica 为底座，补出三根骨架——Agent 能力池与路由、可运行的工作流（模板/节点/边/步骤实例/终点/验收）、与外部系统的 Hook/Callback 交接——再从真实运行中补出六类能力：结构化准出字段与 Verdict、Fan-out 并行与收敛、通知/验收/定向返工、Sweeper 自愈与显式阻塞、失败诊断信息、事件驱动的四层指标。
声称结果：一段边界清晰、可验收的工作可以由系统在无人在线时接手推进；多 Agent 可以按流程接力；上下文可以在系统里以结构化字段传递；异常可以显式暴露；执行完成后能进入验收与返工。已在标准需求、Bug Fix、平台自我迭代、历史问题池四类场景运行，集中管理 30+ Agent。作者把这套东西命名为"组织级 Loop Engineering"，并把"从 Prompt → Personal Loop → Work Loop"作为方法论层级；下一阶段是把底座做稳（Temporal、节点画布、Agent 标准协议、事件接入标准化）、补观测诊断，再用运行数据去回答"哪些节点只是人类角色分工的遗留"，走向 AI 原生流程。

## 2. 核心主张
- **C1** 个体提效不会自动变成链路提效；真正消耗时间的是节点之间的等待、转述、确认和返工，而不是某一步的执行。｜支撑：推理 + 图 005 示意，无数据｜适用条件：多角色接力的研发交付链｜文中位置：一
- **C2** 旧模式下 Agent 的启动、衔接、推进、验收都依赖人的在线状态，这是"人下班 Agent 也下班"的本质；解法是让外部事件触发系统接手，而不是让 Agent 更强。｜支撑：推理｜适用条件：同上｜文中位置：一、二
- **C3** 先把人类已验证的流程 Agent 化（路径 C），因为它最接近原流程、责任边界易对齐、能最快暴露真实问题并积累运行数据；AI 原生流程（路径 B）没有数据支撑就是拍脑袋。｜支撑：三路径权衡推理｜适用条件：第一阶段｜文中位置：二、七.3
- **C4** Agent 协作系统必须先回答三件事：平台能否调得动 Agent（能力池 + 四种路由：指定/上一步指定/能力匹配/兜底解析）、能否表达一条工作流、能否与外部系统交接（进入/通知/验收回写/进度可读）。｜支撑：系统实现描述 + 图 007/008｜适用条件：Agent 来源分散（本地/云主机/外部平台）的组织｜文中位置：三
- **C5** Agent 节点输出不稳定，工作流不能假设节点天然可靠；每次执行落成一次 Submission，用结构化准出字段约束——业务产物 + 流程裁定（pass/fail/blocked）+ 根因解释 + 置信度——系统派生统一 Verdict，下游只消费 Verdict 与字段，不解析自然语言，且与是哪个 Agent 无关。｜支撑：设计描述 + 图 010/011/013 截图｜适用条件：多 Agent 接力｜文中位置：4.1
- **C6** 复杂工作要 Fan-out：上游拆子任务、系统动态创建并行子步骤、各自独立 Issue/Agent Task、全部完成后 AND 收敛；子任务失败时用 fail/blocked/rework 策略决定兄弟任务命运。｜支撑：设计描述，无数据｜适用条件：涉及前端/后端/配置/模板/测试多方向的需求｜文中位置：4.2
- **C7** Agent completed ≠ business completed：到达终点节点后必须通知负责人并进入 Acceptance；验收可由人或外部系统 Callback 完成；驳回必须定向到真正出问题的节点，并把驳回原因作为 rework context 带入下一轮，而不是全链路重跑、不是让人重新解释一遍。｜支撑：设计描述 + 图 012/013｜适用条件：所有进入系统的工作｜文中位置：4.3
- **C8** 无人盯守时最怕的不是失败而是静默卡住；需要巡检与自愈：Runtime 掉线标记、长时间 running 重置、孤立任务重分发、活跃 Step 无对应 Agent Task 时重新激活、Agent 主动 blocked 时暂停并通知人。目标不是永不失败，而是失败可见、可恢复、可交人。｜支撑：设计描述 + 表格 + 图 014｜适用条件：长时间无人值守运行｜文中位置：4.4
- **C9** 链路变长后"task failed"不够，至少要记录：失败在哪个 run/step/agent task、调了哪个 Agent 或工具、失败类型、failure reason、stderr/stdout 摘要、是否重试、终态是 fail/blocked/待人工。｜支撑：需求清单，作者标注为"后续要增强"｜适用条件：接入外部 Agent/CLI/MCP 的系统｜文中位置：4.5
- **C10** 指标应从事件（Step/Agent Task/Verdict/Acceptance/Rework）自然沉淀，分四层：Agent 层（成功率/blocked 率/超时率）、工作流层（完成率/一次通过率/耗时/返工率）、节点层（blocked 分布/失败原因/驳回原因）、场景层（场景通过率/人工介入率/采纳率）；个人用 Agent 时人会默默补掉失败，系统看不见。｜支撑：指标表 + 图 015/016｜适用条件：同上｜文中位置：4.6
- **C11** 只要一件事有明确输入、处理路径、结果验收，就能进入同一套机制；四类场景底层同构：进入 → 匹配路径 → Agent 协作 → 通知/验收/返工 → 状态与指标沉淀。｜支撑：四个场景的定性描述，无样本数｜适用条件：作者团队｜文中位置：五
- **C12** 平台可以用自己组织起来的 Agent 建设自己（发现问题 → 分析 → 方案 → 实施 → 验证 → 人工确认）；能自建才可能持续进化。｜支撑：图 003/017 截图（多为"[演示]"项）｜适用条件：平台团队｜文中位置：5.3
- **C13** 人的位置上移：单条工作流里人管目标/边界/验收（控制面），Agent 是执行面，工作流是协调层；能力体系里人把隐性经验沉淀为 Agent/Skill/工具/模板/准出字段/自动验证；组织层面人选择哪些工作（高频、低风险、可验证）进入。｜支撑：推理｜适用条件：通用主张｜文中位置：六.1–6.4
- **C14** Prompt Engineering 问"怎么写好一句指令"，Loop Engineering 问"怎么设计一套让 Agent 持续推进、验证、纠偏和停止的系统"；组织级 loop = 事件进入 → 工作流接手 → 协作执行 → 状态判断 → 验收/返工 → 指标沉淀 → 下一轮优化。｜支撑：概念定义 + 图 018｜适用条件：通用主张｜文中位置：6.5
- **C15** 用第一阶段运行数据（哪些节点常 blocked、常返工、一次通过率高）反过来判断哪些节点只是角色分工或人类交接的遗留，可由系统直接传递或规则自动完成，哪些验收必须留给人；由此走向"目标理解 → 约束抽取 → 计划生成 → 工具执行 → 自动验证 → 风险判断 → 人类验收"的 AI 原生结构。｜支撑：规划，无数据｜适用条件：第二阶段｜文中位置：七.3

## 6. 建议采纳（候选语义）
- **S1** 任何工作单元在被交给下一环节前，必须产出一份**与执行者无关的结构化裁定**，至少包含：交付产物、三态结果（通过/失败/阻塞）、判断依据、置信度；下游只消费裁定，不解析自由文本。｜落地方式 A（检查器）：提交时校验字段完备性与三态取值，缺失即拒收｜落地方式 B（人工检查点）：交接评审只看裁定包，不接受口头/聊天转述｜它防御的失败：F6（输出含糊导致下游猜测、blocked 被当成 fail 或 pass）｜删除条件：模型能稳定自发产出可机读裁定且多模型互操作性可测——目前写不出何时。
- **S2** "执行完成"与"业务完成"是两个必须分开记录的状态；进入业务完成必须经由一个独立于执行者的验收动作（人或外部权威系统的回写）。｜落地方式 A（外部状态存储）：工作项状态机中两状态不可合并，验收结果由外部系统回写｜落地方式 B（运行时拦截）：执行者自报完成时拦截，转为"待验收"而非"完成"｜它防御的失败：Agent 自封完成（D-017 已列）｜删除条件：写不出（责任不可转移）。
- **S3** 验收驳回必须**定向**回到出错环节，并把驳回原因作为该环节下一轮的必需输入；返工轮次必须有上限，超限转为阻塞并升级给人。｜落地方式 A（外部状态存储）：驳回记录含目标环节与原因，重跑读取之｜落地方式 B（检查器）：轮次计数器超限即阻断并通知｜它防御的失败：F1/F2（无上限返工回环、返工时下游旧任务未撤销）｜删除条件：写不出——上限是人侧成本约束，与模型能力无关。
- **S4** 无人值守运行的系统必须有**活性不变量**：每个处于"进行中"的工作单元必须绑定一个可探活的执行者且有新鲜度信号；失去绑定或超期即转为显式失败/阻塞并通知，而不是保持"进行中"。｜落地方式 A（运行时拦截/定时巡检）：周期扫描孤儿任务、掉线运行时、超时步骤，重置或重派｜落地方式 B（人工检查点）：每日审视"超龄进行中"清单｜它防御的失败：F3/F4/F5/F10（静默卡住）｜删除条件：执行平台原生提供任务租约与心跳且可被工作流读取时，巡检可删；不变量本身不删。
- **S5** 失败记录必须能定位到"哪次运行、哪一步、哪个执行者/工具、失败类型、原因、是否重试、终态"，否则失败不可诊断，链路越长越退回"人凭经验猜"。｜落地方式 A（外部状态存储）：轨迹记录含上述字段｜落地方式 B（检查器）：失败事件缺字段时标记为"不可诊断失败"并计数｜它防御的失败：F7｜删除条件：写不出。
- **S6** 交付流的观测指标应由**流程事件自动派生**，并至少覆盖执行者、流程、环节、场景四个粒度；"人工介入率"与"验收队列长度/等待时长"必须是场景级指标，因为它们直接度量 D-024 的上界是否被突破。｜落地方式 A（外部状态存储 + 检查器）：事件流聚合｜落地方式 B（人工流程）：定期抽样人工统计人工接手的次数｜它防御的失败：F8/F9（验收积压不可见、指标口径漂移）｜删除条件：写不出。
- **S7** 把人类流程 Agent 化只是过渡形态；每个流程环节应带"存在理由"标签（为人类交接而存在 / 为验证而存在 / 为责任而存在），用运行数据定期审查为交接而存在的环节是否可删。｜落地方式 A（静态指令/文档）：流程模板中每个环节标注理由｜落地方式 B（人工检查点）：按周期用 blocked/返工分布复审｜它防御的失败：流程冗余只增不减（ATT-N 机制在流程层的翻版）｜删除条件：写不出（属 Thin 依据，与 D-013/D-021 配套）。

## 8. 该文暴露的失败模式
- **F1** 验收驳回触发返工时，下游仍在运行的旧任务未被撤销 → 新旧两轮任务并行、状态互相覆盖（图 017 HAP-72"Rework 下游清理缺失"标为 P0；图 013 同题修复自身 ≥6 次 blocked）→ 文章处置：作为平台缺陷修复，正文未提 → 可构造：驳回后断言下游无活跃任务。
- **F2** 返工无轮次上限 → 同一环节可能无限次重做（图 013/017 "max_rework_rounds 上限保护缺失" P0，13 天未解）→ 处置：节点配置"最大重做轮次"（图 009）→ 可构造：让验收连续驳回 N+1 次，断言第 N 次后转阻塞升级。
- **F3** Agent 进程退出但未提交流程结果 → 步骤永久"进行中"（图 013 "完善 Agent 退出时的 workflow submit 强制机制"）→ 处置：退出强制提交（规划）+ Sweeper 兜底 → 可构造：kill 执行者进程，断言步骤在阈值内转为失败/重派。
- **F4** Runtime 掉线 / Task 长时间 running / 孤立任务 → 静默卡住 → 处置：掉线标记、running 重置、孤立重分发（4.4 表）→ 可构造。
- **F5** 活跃 Step 没有对应 Agent Task（调用链不一致）→ 流程看似在跑实则无人执行 → 处置：重新激活 → 可构造：删除任务记录，断言巡检重建。
- **F6** Agent 输出格式不稳/失败表述含糊/blocked 未成状态 → 下游解析失败或误判 → 处置：准出字段 + Verdict → 可构造：注入缺字段/自由文本提交，断言被拒收。
- **F7** 外部 Agent/CLI/MCP 失败只有"task failed" → 无法区分能力/工具/权限/网络/输入不全 → 处置：4.5 字段清单（未实现）→ 可构造：注入各类失败，断言记录含分类。
- **F8** 每条流程终点都要人工验收，产生 49 项待审核、平均响应 0s、审核中 19（图 016/017）→ 验收 Gate 退化为积压 → 文章未处置 → 可构造：Gate 处理时长/队列长度监控，超阈值判 Gate 失效（D-024 Case）。
- **F9** 同一指标页两处"首次通过率"为 100% 与 50%；7 天完成 0 与 386 任务 98% 成功并存（图 016）→ 指标口径不稳定，无法用于优化决策 → 未处置 → 可构造：同一事件流两条聚合路径结果一致性断言（D-025）。
- **F10** 每日"系统健康扫描"任务 5–6 天停留"进行中"（图 017）→ 巡检器自身卡住、且 Sweeper 未把它们判为超时 → 未处置 → 可构造：巡检任务超龄检测（谁来巡检巡检器）。
- **F11** 自迭代流水线中实施与端到端验证由同一 Agent 完成，人工验收积压 → 无独立现实锚点（D-023）→ 未处置 → 可构造：生成者与验证者身份相同即判 UNDETERMINED。
