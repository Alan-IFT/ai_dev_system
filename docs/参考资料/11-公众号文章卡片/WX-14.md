# WX-14 AI代码生成率94%：我们用一个 Skill 跑通需求开发全流程

## 0. 验证边界
- 一手实践报告：企业微信 iOS 邮件插件团队（Objective-C/C++，bazel 构建，9000+ 源文件）在自家项目上做的一个"需求开发 Skill"。作者直接参与，所有描述来自自述，无外部复核。
- **没有原始数据、没有对照组、没有消融**。§11 效果表作者自己标注"数据来源于本项目近半年实际跑下来的体感（非严格 benchmark），仅供参考"。
- 标题数字 **94%（AI 代码生成率）在全文中没有任何定义**：正文只出现两次（标题、§6.7 末句"这就是 94% 代码生成率背后的真正机制"）。唯一线索是 §2 表第 ⑧ 行"提交阶段产出：三段式 commit + AI 署名 + **代码生成率**"——即该数字很可能是 commit 阶段由脚本按行数或改动统计、写进 commit message 的自报比例。分母（行/文件/需求数？）、时间窗、是否含人工修正后的行、是否含脚本生成的样板代码，全部未说明。**只能记作"该团队在 commit 元数据里自报的一个比例"**。
- 其他数字同样无测量条件："300× 压缩比"（~10M+ → ~30K token）是"全项目灌入"这一并不存在的基线与估算值之比；"联想关键词命中率 > 80%"无统计方法；"6 个月没有出现地图脱节"是自述；"范围错判压成 0"是修辞。
- 超出可核实范围：Skill 本身未开源，红线全文（6 条 Critical + 30+ 条 Standard）只展示约 12 条编号；`TECH_SPEC.md` 模板、`red_lines.yaml` DSL、`ui_alignment_spec.md` 由谁产出均未展示。
- 文中无任何外部论文/博客/仓库引用。本卡对其提到的两个第三方工具（Figma Desktop MCP、facebook/idb）做了一手核对，见 §4。

## 1. 文章在讲什么
问题：AI 在企业级大仓里"会写代码但不会按工程规范开发需求"——上下文塞不下、物料分散在 TAPD/Figma/企微文档、产品语言与代码命名脱节、模糊指令导致越界漏改、AI 自报完成但编译不过、跨会话失忆。
解法：不换更大的模型，而是把"需求开发"拆成 8 个严格顺序的阶段（设计稿→拆解→定位→实现→编译验证→模拟器验证→沉淀→提交），每阶段输入/产出/退出标准可机器校验；配套三级知识库（项目总览/模块登记表/设计 Token→代码映射）+ 漂移检测脚本 + pre-commit 阻断；需求侧用五条确定性规则做"产品语言→代码指令"翻译；判断留给 LLM、数值与幂等执行下沉到脚本；36+ 条分层加载的红线，触发即停；两道验证闸门（编译退出码 0 + 模拟器截图/日志/数值对齐）；跨会话用 `TECH_SPEC.md`（永久）/ `subtasks.json`（跨会话）/ `timeline.txt`（会话内）三件套接力；4 个人机硬关卡守住不可逆动作。
作者声称的结果：需求拆解从 1～2 小时降到 5～10 分钟、定位从 30 分钟～2 小时降到 5～15 分钟、bug 修复接力 5 分钟恢复现场、"94% 代码生成率"——全部为体感。作者最后的自我定位：真正有价值的不是 AI 写代码，而是"需求开发被显式建模、可观测、可接力"，且沉淀物对人同样有用。

## 2. 核心主张
- **C1** 需求开发应拆成固定顺序的阶段，后一阶段的输入必须等于前一阶段的产出，跳阶段（"一句话指令直接改代码"）是越界的主因。｜支撑：案例（RL-16 来源）｜适用条件：单人+单 AI 的移动端需求开发｜文中位置：§二、§8.3
- **C2** 代码定位要靠"逐步缩小范围的漏斗"：前两步只看地图（总览、模块登记表），第三步脚本 grep，第四步才读代码片段。｜支撑：推理 + 估算（30K token）｜适用条件：9000+ 文件的老仓｜文中位置：§四、§5.3
- **C3** 项目需要一张 AI 可读的三级地图（总览 <5KB / 模块级文件登记表 / 领域语义桥），并且**必须配漂移检测**（SHA 基线 + 三色分诊 + pre-commit 阻断），否则地图会与代码脱节。｜支撑：案例（半年净增 200+ 文件仍未脱节，自述）｜适用条件：有 hook 能力的 git 仓｜文中位置：§五
- **C4** 产品语言→代码语言的翻译是"人工成本"的大头；把它规则化（硬关键词表定范围、每张设计稿必须归宿到三类之一、拦截点必须有引用依据、5 维搜索矩阵扩词、五列表+JSON 产物）后 AI 才能独立跑完。｜支撑：五个翻车案例 + 一个完整实例｜适用条件：PRD 混写多端、设计稿多画板的产品｜文中位置：§六
- **C5** "联想用于搜索，引用用于决策"：允许 AI 在找代码位置时做领域联想（不影响交付物），禁止 AI 在决定"X 触发 Y 是否实现"时做语义联想（直接决定交付物）；填不出引用依据的行直接删掉不实施。｜支撑：推理 + 案例｜适用条件：同上｜文中位置：§6.4、§6.5 末
- **C6** 每一份输入工件都必须有归宿：设计稿归不到需求点，要么是筛选误纳、要么是需求点遗漏，不允许"参考图"当万能垃圾桶。｜支撑：案例（9 张候选稿只做 2 张，漏 7 个页面）｜适用条件：设计稿驱动的 UI 需求｜文中位置：§6.3
- **C7** LLM 不擅长精确数值与幂等执行；分桶、筛选、收料、编译、装机全部下沉脚本，LLM 只"读结果 + 下决策"，并只允许对脚本标记为 UNCERTAIN 的项补判。｜支撑：推理 + RL-17 案例｜适用条件：通用｜文中位置：§七、§7.2
- **C8** 长跑命令的成功不能靠 stdout（会被截断、置后台、异步化），只能靠**落盘的 sentinel 文件**或**可重读的状态（git log hash 变化）**判定。｜支撑：案例（长 commit 消息置后台→AI 误判失败重提）｜适用条件：终端型 Agent｜文中位置：§7.3、§8.3
- **C9** 红线应有单一真源、分两级（Critical 启动即加载 / Standard 按阶段加载）、触发即停并按固定模板汇报；"AI 主动说它撞线"比"AI 更聪明"更重要。｜支撑：推理｜适用条件：通用｜文中位置：§八
- **C10** 验证分两道闸门：编译（退出码 0 唯一判据，错误分 A 可自修复 / B 需人介入，自修复硬上限 3 轮）与运行时（从 git diff 反推验证路径→装机→逐步截图+日志→A/B/C 诊断→数值级视觉对齐），两道都过才允许沉淀。｜支撑：流程图 + 报告样例｜适用条件：可自动装机的模拟器环境｜文中位置：§九
- **C11** 重试预算按失败类型分配：A 真问题（回实现阶段，不在验证阶段修）、B 路径不通（修验证计划或跳过）、C 脚本/时序（阶段内重试 ≤2 轮）；超限升级报告人。｜支撑：推理｜适用条件：UI 自动化验证｜文中位置：§9.2
- **C12** 视觉对齐必须是数值清单逐项核对（高度、尺寸、字号、色值），未对齐 ≥1 即整体 FAIL，不允许跳过。｜支撑：报告样例｜适用条件：有 `ui_alignment_spec.md` 的 UI 改动｜文中位置：§9.2 第⑤步
- **C13** 跨会话记忆按时间尺度分三件：永久（功能边界/模块地图/不变式/演进事件）、跨会话（子任务状态与阶段）、会话内（事件流水），新会话按固定章节顺序读完即可接力。｜支撑：推理 + 5 分钟恢复现场（体感）｜适用条件：同一需求多轮迭代/修 bug｜文中位置：§十
- **C14** 入口分流由持久工件的存在性决定（台账文件存在→接力流程；不存在→首次实现），再按用户消息关键词分 bug 修复 / 增量迭代 / 推倒重来。｜支撑：流程图｜适用条件：同上｜文中位置：§10.3
- **C15** 自动化与可控的平衡点是少量人机硬关卡（4 个 HK：现场快报、拆解结果、沉淀落盘、commit 文案），任何不可逆动作前先让人点头。｜支撑：推理｜适用条件：通用｜文中位置：§10.4
- **C16** AI 友好 = 新人友好：知识库与 TECH_SPEC 对人同样有用，"即使换掉 AI 也是资产"。｜支撑：自述（新人半天上手）｜适用条件：该团队｜文中位置：§5.3、写在最后
- **C17** `references/` 体量大于 `tools/`，说明"提效在工程不在模型"——能力主要来自显式编写的规则、知识和模板。｜支撑：目录清单｜适用条件：该 Skill｜文中位置：§十三

**冲突展开一：派生地图 vs "代码不写"**。D-020 判据一说代码与运行环境里的信息"不写"，因为写下来会制造第二个事实来源并先于代码过期。本文恰好写了一份完整的文件级职责登记表，并用半年 200+ 文件净增的自述证明它没有过期。两者可共存的条件在文章自己的设计里：地图不是权威记录源，只是**带 SHA 基线的缓存**，且每次提交前由检查器重新对账、由人分诊。也就是说，"代码派生文档"可以存在，前提是它的新鲜度被机械检查而不是被相信。谁的证据更强：D-020 是原则，本文是一个无对照的成功案例；但本文指出了 D-020 判据一漏掉的一种情形——**信息虽在代码里，但工具"读取"它的成本（9000+ 文件）高到必须缓存**。建议作为判据一的例外条件登记，而非推翻。

**冲突展开二：自验 vs 审查分离**。文章明确把质量保障从"测试同学发现 bug"改为"AI 自己写自己验自己交差"，与 05 章 §6"生成者不能自行拉起审查者"直接相反。但文章的验证对象不是 AI 的自评，而是**机器产物**（退出码、截图、日志命中、数值对齐表），验证的裁判是脚本和文件，不是生成代码的那个模型实例。可共存的划分：对"客观可机械判定"的部分（编译、像素数值、日志命中）不需要分离审查者；对"验收标准本身对不对"（ui_alignment_spec、verify_plan 的预期）仍需独立来源——文章在这一点上没有说明来源，是其最薄弱处。

## 6. 建议采纳（候选语义）
- **S1** 推断权限按后果划界：Agent 在缩小搜索范围时允许基于领域知识做联想；在决定交付物范围（做不做、拦不拦、改不改）时必须引用可定位的依据（需求原文、设计标注、用户原话），引用不出的项不进入交付。｜落地方式 A（静态指令）：拆解阶段的规则文本要求"依据来源"列只接受三类引用｜落地方式 B（检查器）：对工作项清单做字段校验，"依据"字段为空或为推理性措辞的项拒绝进入实现阶段｜它防御的失败：F3 语义联想扩大范围（"为了一致性也应该拦"）｜删除条件：模型在无引用时自发停下并询问的比例经评估≥人工标准时可删。
- **S2** 输入工件完备性：每一份进入任务的输入工件（设计稿、需求段落、协议字段）必须被映射到某个工作项、或被显式标记为"参考/排除"并说明理由；不允许存在未归类的残余。｜落地方式 A（检查器）：工作项台账与输入清单做双向覆盖校验，有残余即失败｜落地方式 B（人工检查点）：拆解结果确认时人按"每张稿都有去处"逐项点头｜它防御的失败：F2 候选稿被笼统当参考图导致漏 7 个页面｜删除条件：模型在多图输入下的漏项率经评估低于人工时可删。
- **S3** 长时执行的成功判据必须是可重读的持久状态，而不是执行通道的即时输出：命令完成的证明是"带任务标识的完成标记被写入"或"目标系统状态发生预期变化（如提交标识改变）"，Agent 在宣告成功前必须重读该状态。｜落地方式 A（外部状态存储）：脚本自检后写带任务 ID 的完成标记，Agent 读标记｜落地方式 B（运行时拦截）：宣告完成的动作被拦截，检查目标状态是否已变化，否则拒绝｜它防御的失败：F7 长 commit 被置后台→AI 误判失败重提；F8 stdout 截断｜删除条件：执行通道能保证同步且不截断的环境中可删（这是载体缺陷补偿）。
- **S4** 代码派生的导航知识（模块/文件职责索引）允许存在，条件是它被声明为缓存而非权威记录源，并在每次代码变更进入主线前由检查器与真实代码对账，差异由人分诊后更新基线。｜落地方式 A（运行时拦截）：提交前钩子运行对账，有漂移即阻断｜落地方式 B（检查器 + 外部状态存储）：CI 中对账并把待复核项写入台账，超期未处理时阻断合并｜它防御的失败：F13 地图与代码脱节导致定位错文件｜删除条件：工具能在可接受成本内直接从 9000+ 文件的仓库实时建立同等精度的导航时可删。
- **S5** 重试预算按失败所在层分配：验证失败先分类为"被验对象有错 / 验证设计有错 / 验证执行有错"，只有第三类允许在当前阶段原地重试且有次数上限，前两类必须回边到对应阶段或升级给人。｜落地方式 A（静态指令）：验证阶段规则文本给出三类定义与处置｜落地方式 B（检查器）：验证报告必须带分类字段，分类为前两类而仍处于本阶段的报告被拒绝｜它防御的失败：F6/F9 在真问题或路径不通上反复硬试｜删除条件：写不出。
- **S6** 验证路径由改动派生：运行时验证计划必须从本次改动集合（改了什么文件/什么类型）反推出可观察终点（可见 UI 状态、数据体现页面、或日志关键字），并把预期写成可机械核对的断言。｜落地方式 A（检查器）：从变更集生成验证计划骨架，缺少可观察终点的改动类型判定为未验证｜落地方式 B（人工检查点）：评审时要求每个改动项对应一条"怎么看到它生效"｜它防御的失败：AI 报"功能正常"但验证路径根本没经过改动点｜删除条件：写不出。
- **S7** 程序先判、模型只补判：可由确定性程序分类的输入先由程序处理，模型只处理程序标记为不确定的残余，且不得推翻程序已判定的项。｜落地方式 A（条件加载规则）：只把 UNCERTAIN 列表送入模型上下文｜落地方式 B（权限与隔离配置）：模型对程序产出的分桶结果只有追加权、无改写权｜它防御的失败：LLM "手感"分桶导致选稿随机｜删除条件：模型在该分类任务上经评估稳定优于程序时可删。
- **S8** 恢复入口由持久工件的存在性与内容决定，而不是由会话历史决定：任务台账存在即进入接力流程，并向人报送现场快报后才继续。｜落地方式 A（外部状态存储 + 人工检查点）：读台账→输出快报→等待确认｜落地方式 B（检查器）：新会话首个动作若不是读台账则被拒绝｜它防御的失败：跨会话失忆、重复实现已完成子项｜删除条件：写不出。

## 8. 该文暴露的失败模式
- **F1** PRD 段落主语是后台配置、夹一句"手机上看到的效果" → AI 按段落主旨整段判为非移动端，漏实现移动端 UI → 文章：硬关键词命中即强制拆成移动端项 → 可构造：一段混写需求 + 期望工作项数，机械判分。
- **F2** 9 张移动端候选设计稿 → AI 只挑 2 张做需求点，其余笼统当"参考图"，漏 7 个页面 → 文章：每张稿必须归宿三类之一，归不到即筛选误纳或需求遗漏 → 可构造：N 张稿 + 期望映射表，检查残余。
- **F3** 需求说"点 A 拦截" → AI 联想"按一致性 B 也应拦"，改了不该改的逻辑 → 文章：拦截清单每行必须有引用依据，填不出的删 → 可构造：需求只提 A，检查交付物是否触碰 B。
- **F4** 产品词直接 grep（"小红条"）0 命中；泛词（"tips"）800+ 命中 → 定位失败或误命中 → 文章：多维扩词 + 模块 wiki + Glossary → 可构造：给产品原句，判定候选词是否命中目标文件且候选数 ≤ 上限。
- **F5** "邮件红点"翻译错位置，改了 RMail 而不是 MList → 功能改错模块 → 文章：L1/L2 地图定位 → 可构造：同 F4，判定命中模块。
- **F6** AI 报"完成"但编译未过；或改一处未同步另一处 → 文章：退出码 0 唯一判据 + A/B 错误分类 + 3 轮上限 → 可构造：注入一个未声明标识符，观察 AI 是否在宣告完成前编译。
- **F7** 长 commit 消息被终端置后台 → AI 误判失败、重复提交 → 文章：以 `git log -1` hash 变化为唯一成功证据 → 可构造：模拟异步/截断的执行通道，检查 Agent 是否重读状态而非信 stdout。
- **F8** 脚本 stdout 被截断/管道变异步 → 成功信号丢失 → 文章：sentinel 落盘 → 同 F7。
- **F9** 模拟器合成 swipe 无法触发边缘返回手势 → 验证步骤永远失败，被当成代码 bug 反复重试 → 文章：死角清单 + 改用 AX 标识 tap；A/B/C 分类中归 B → 可构造：一个已知不可自动化的步骤，检查 Agent 是否在 2 轮内升级而非硬试。
- **F10** 截图物理像素 vs tap 逻辑像素 → 硬编码坐标点错 → 文章：动态换算 → 平台专属，回归价值低。
- **F11** AI 发明项目里没有的新模式（"独此一家"）→ 文章：RL-13/14 先通读完整方法 + 搜索同类分支再写 → 可构造：需求可用既有枚举扩展实现，检查是否新造结构。
