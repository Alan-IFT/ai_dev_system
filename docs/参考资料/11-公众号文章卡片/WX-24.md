# WX-24 AI Infra进阶：如何让大模型输出确定的结果

## 1. 文章在讲什么
问题：同一提示词、同一硬件、temperature=0 或锁定 seed，为什么大模型输出仍然不一样？作者先给出实验现象——单独请求时多次运行结果一致（run-to-run 确定），有其他并发请求时结果不一致（丧失 batch invariance）；根因不是请求间"污染"，而是推理引擎为填满 GPU 而**按 batch 形状动态改变规约树拓扑**（GEMM 的 Split-K/BLOCK_K、Attention 的 Split-KV、RMSNorm 的 block size、NCCL 的算法/Channel 切分），而浮点加法不满足结合律。解法是逐算子把规约结构与 batch 解耦：钉死 tile 配置、禁 Split-K、`num_splits=1`、钉死 block size、把 NCCL 锁到单通道 Tree+Simple 并禁用 custom all-reduce。作者声称的结果：开启 `VLLM_BATCH_INVARIANT=1` 后可跨 batch bit-exact，代价是小 batch 下 SM 利用率下降；并顺手修了 vLLM 中一个 RMSNorm 打破不变性的 bug。文章明确说 MoE 与 NCCL 深层机制未展开。

## 2. 核心主张
- **C1** temperature=0 或锁 seed 不能保证输出确定；确定性分两层：run-to-run（同负载重跑一致）与 batch invariance（不同并发负载下一致），前者成立不蕴含后者。｜支撑：作者自测（Qwen3-8B，无数据）+ TM 博客 1000 次实验｜适用条件：GPU 动态组批推理服务｜文中位置：背景
- **C2** 非确定性的根因是"系统按 batch 形状动态改变浮点规约拓扑"，而非请求间干扰或原子加本身。｜支撑：推理 + TM 博客｜适用条件：同上｜文中位置：背景、总结
- **C3** 并非所有调度参数都影响确定性：只切空间轴（BLOCK_M/N、Swizzle、chunked prefill、列并行）的参数安全；切规约轴（BLOCK_K、SPLIT_K、Split-KV、block size 影响归约树、行并行 AllReduce）的参数才破坏不变性。｜支撑：推理 + 图 031 分类｜适用条件：GEMM/Attention/RMSNorm/TP｜文中位置：Batch Invariance 的来源、图 031
- **C4** "确定性"是分路径、分架构、分精度、分执行模式（eager/compile）的**分级主张**：有的路径靠 API 契约保证（reduction mask），有的只靠"把 workspace 压到最小间接逼出 split-k=1"，有的只是防御性配置，有的依赖闭源库行为"基于测试"。｜支撑：图 021 的 ✓/⚠ 分级表 + 源码｜适用条件：vLLM 当前版本｜文中位置：vLLM 中 GEMM 的 Batch Invariance 支持
- **C5** 开了开关不等于走了确定性路径：torch.compile 模式下 CustomOp 默认关闭，batch-invariant dispatch 被"静默跳过"，最终依赖 Inductor 恰好生成不拆分的归约 kernel（条件是 hidden≤8192 且未配置 compile_ranges/sizes）。｜支撑：源码引用 + RFC #40628 原话｜适用条件：vLLM + Inductor｜文中位置：编译场景下 RMSNorm
- **C6** 任何关于底层算子行为的绝对保证必须严格限定在明确的软件版本与编译配置内。｜支撑：作者从版本/编译范围依赖推出｜适用条件：通用｜文中位置：编译场景下 RMSNorm 末段
- **C7** 确定性与吞吐是结构性 trade-off：每处修补都以牺牲并行度换规约顺序稳定（GEMM 禁 Split-K、Attention `num_splits=1`、NCCL 单通道）。｜支撑：推理 + vLLM 文档"may impact performance"｜适用条件：小 batch decode 最明显｜文中位置：各节末尾、总结
- **C8** 一处为性能而引入的"按 token 数选 block size"启发式（`num_tokens<256 ? 1024 : 256`）会让**同一个 token** 在不同 batch 里走不同归约树，从而打破不变性；修法是钉死 block size。｜支撑：作者自己的 PR #48391｜适用条件：vLLM RMSNorm CUDA kernel｜文中位置：RMSNorm 的 Batch Invariance、图 024
- **C9** 单卡与多卡问题同构：GEMM 固定 K 切分、Attention 固定 KV 切分、AllReduce 固定跨 rank 规约图/协议/通道数，解决的都是"阻止系统根据 batch shape 改变 Reduction Topology"。｜支撑：推理｜适用条件：TP 推理｜文中位置：NCCL 的 Batch Invariance
- **C10** 强化学习需要确定性 rollout 来保证可复现与训练稳定。｜支撑：转述 TM 博客｜适用条件：RL 训练｜文中位置：背景（一句带过）

**最有价值的三个引用**：

*Thinking Machines 博客*：本项目 06 章 eval manifest 有"随机性"字段但没有定义"随机性"由什么构成。TM 给出可操作的分解：采样随机性（temperature/seed 可控）、kernel 随机性（run-to-run，现代 kernel 基本已确定）、**负载随机性**（batch size 随并发变化 → 不同规约拓扑）。第三项在 API 服务下**用户完全不可控**，这意味着任何"同一 case 重复 N 次"的重复策略，若不声明是否在独占/固定负载下运行，测得的方差里混着与被测机制无关的噪声——这正是 D-025"效果量小于路径噪声时 A/B 不成立"的另一个噪声源，而且比 ATT-F 讨论的"模型探索路径波动"更底层。

*PR #27931 → PR #48391 的事实链*：一个合入时通过全部 CI 的性能优化，在 8 个月后被发现打破了一个已声明的系统级不变量；根因是回归集里没有**跨启发式阈值**的用例（255 vs 256 token）。修复 PR 的测试设计——"seed 扫描 + 显式构造跨阈值 case"——是 D-011"最小回归 Case"与 D-013"按真实失败 Add"的一个干净实例：不变量必须配一个专门沿"系统会切换策略的边界"取点的回归 Case，否则任何局部优化都可能无声地打破它。

*RFC #40628 与 Issue #39096*：前者说明"开关设了、路径没走"可以长期不被发现（因为恰好被另一个机制掩盖），后者说明当测试失败时，团队的即时处置是"在该硬件上关掉编译让测试过"——issue 本身承认这掩盖了生产 bug。两者合起来是 D-023"证据链需要直接观察节点"和"指标被满足而目标被背叛"的现成案例：绿色 CI 不等于不变量成立。

## 6. 建议采纳（候选语义）
- **S1** 评估的重复策略必须声明执行隔离条件（独占/固定负载 vs 与其他负载并发），"同输入同输出"类主张只在声明的负载条件下成立。｜落地方式 A（检查器）：评估记录的结构校验，缺少隔离条件字段即判 UNDETERMINED｜落地方式 B（人工检查点）：评审人拒收未声明重复条件的评估报告｜它防御的失败：F1（隔离重跑一致，生产并发不一致，被误判为"已确定"）｜删除条件：推理服务普遍提供并可验证 batch-invariant 保证，且评估集执行环境可证明与生产同构
- **S2** 任何"确定性/可复现"主张必须绑定其保证来源类型：接口契约保证、测试观察到、还是防御性配置；只观察到的不得写成保证。｜落地方式 A（外部状态存储）：证据包中"保证来源"为必填枚举字段｜落地方式 B（检查器）：对外声明"确定"的工件必须能指向一条契约或一个持续运行的回归 Case，否则降级为"观察"｜它防御的失败：F5（依赖闭源/上游行为的"保证"在升级后无提示失效）｜删除条件：写不出（这是 D-005 主张模型的一部分，不因模型能力变化而消解）
- **S3** 配置声明不等于执行路径；启用某种保证模式后，证据链中必须存在一个直接观察实际执行路径的节点，而不只是观察配置值。｜落地方式 A（运行时拦截）：启动或首次执行时断言实际选中的实现与声明一致，不一致即中止｜落地方式 B（检查器/回归 Case）：一个专门在"另一条路径"（如编译模式）下运行的用例，其通过与否独立于配置值｜它防御的失败：F2（开关已设、路径静默跳过）｜删除条件：执行环境本身能把"声明的模式"与"实际路径"绑定并对外暴露（当前不具备）
- **S4** 每个被声明的系统不变量必须配至少一个沿"系统会切换策略的边界"取点的回归 Case；任何以性能为目的的改动进入前必须运行这些 Case。｜落地方式 A（检查器）：不变量测试集在合入前自动运行，包含边界两侧取点｜落地方式 B（条件加载规则 + 人工检查点）：触碰含启发式分支的代码时加载"不变量清单"，评审人核对是否新增了依赖无关变量的分支｜它防御的失败：F3（局部优化 8 个月后被发现打破全局不变量）｜删除条件：写不出——只要系统含按输入形状选策略的启发式，这条就成立
- **S5** 用"关闭检查/跳过路径"让失败的验证通过，必须登记为带责任人和失效时间的豁免，不得写成修复。｜落地方式 A（外部状态存储）：豁免登记表，未登记的跳过标记在审计中视为缺陷｜落地方式 B（运行时拦截）：检测到跳过/禁用标记而无豁免标识时阻断合入｜它防御的失败：F4（workaround 掩盖生产 bug）｜删除条件：写不出（属责任判据，只有人能承担后果）
- **S6** 评估执行模式（确定性优先 vs 吞吐优先）是证据的环境字段之一；评估与生产模式不同时，证据的适用范围须显式排除生产模式。｜落地方式 A（外部状态存储）：证据包环境字段含执行模式｜落地方式 B（人工检查点）：验收时人工确认评估模式与目标环境一致或已声明差异｜它防御的失败：F1 的变体（评估在确定性模式全过、生产在性能模式抖动）｜删除条件：两种模式的差异被上游消除（TM 与 vLLM 均称性能损失可继续缩小，但未消除）

D-020 自检：S1～S6 均不含工具名、文件名、环境变量名；每条给出两种不同机制类型。S2、S5 的删除条件写不出，按 D-021 记为"责任类/结构类规则"。

## 7. 明确不采纳
- 全部 GPU 微架构与算子实现内容（Tiling、Split-K、Swizzle、寄存器/SMEM 约束、SM80 vs SM90 执行范式、FlashAttention/FlashDecoding、NCCL Ring/Tree/Channel）：**范围外**，属推理引擎工程，与开发规范无关；仅在 §3 登记图片信息。
- `VLLM_BATCH_INVARIANT=1`、13 个 NCCL/cuBLAS 环境变量、`num_splits=1`、block size 1024 等具体处置：载体绑定，且只对该引擎该版本有效（文章自己声明"必须严格限定在明确的软件版本与编译配置内"）。
- "温度=0 / 锁 seed 即可复现"作为评估规则：文章证明这是不充分条件；本卡片反过来也**不**把"必须开确定性模式"写成规则——是否需要 batch invariance 取决于评估的效果量与噪声比（D-025），不是普适要求。
- 2.1%、26s→55s→42s、5～30% 等全部数字：单模型单硬件单点观测，不外推。
- "确定性是科学进步的基石"（Reproducibility is a bedrock）作为立论：口号，不构成规则依据。
- C10（RL 需要确定性 rollout）：本项目不涉及训练。
- 作者的自测结论（Qwen3-8B 并发下不一致）：无样本数与版本，只作现象登记，不作证据。

## 8. 该文暴露的失败模式
- **F1** 评估在独占/串行条件下重复 N 次全一致 → 同一 case 在生产并发负载下输出分叉 → 文章的处置：区分 run-to-run 与 batch invariance 两个概念，并在引擎侧修补 → **可构造**：同一 prompt 在"独占"与"与随机负载并发"两种条件下各跑 N 次，比较唯一输出数（TM 实验的直接复用）
- **F2** 开启确定性开关，但在编译执行模式下分发逻辑被静默跳过，输出仍随 batch 变化 → 表现：配置显示已启用、行为不变 → 文章/上游的处置：RFC 重设计分发；短期靠 Inductor 恰好不拆分 → **可构造**："声明模式 X + 执行路径 Y" 的用例，断言实际路径而非配置值
- **F3** 性能优化引入按输入规模切换的启发式（阈值 256）→ 同一输入在阈值两侧走不同归约结构，不变量被打破，8 个月后才发现 → 处置：钉死参数 + 增加跨阈值回归 Case → **可构造**：对任何含 `x < 阈值 ? A : B` 分支的改动，取阈值两侧各一点验证目标不变量
- **F4** 不变量测试在某类硬件上失败、根因未定 → 处置：测试时在该硬件关闭编译让测试通过（上游 issue 承认掩盖了生产 bug）→ **可构造**："绿色 CI + 未登记的跳过标记"作为审计 Case（D-023 指标被满足而目标被背叛）
- **F5** 对闭源依赖的行为只能"基于测试"给出保证；依赖升级后保证可能无提示失效 → 表现：文档/注释仍写"确定"，实际不再成立（源码注释与实际机制已出现措辞漂移）→ 文章的处置：在图 019/021 中把保证分级并注明来源 → **可构造**：依赖版本升级后自动重跑不变量 Case，并要求"保证来源=测试观察"的主张标注测试所在版本
- **F6** 文档/图表/注释与实现不同步（注释说靠 workspace config，代码同时用 reduction mask；文章又只转述其一）→ 表现：读者按注释理解机制会错 → 无处置 → 可构造为"注释声明的机制 vs 实际调用链"一致性检查 Case，价值一般
