# WX-31 Agent的上限，可能不在模型，而在团队知识

## 0. 验证边界
- 材料性质：**一手实践报告**（腾讯安全中心团队自述），描述"AI 端到端研发平台"配套的知识供给系统。无对照组、无消融、无原始数据集；所有效果数字为该团队在 2026 年 5～7 月运营期内的自报观察，且多数没有基线测量方式说明。
- 数字来源分三类：(a) 正文陈述（99.7% 自动沉淀、审查 2-4 轮→1.1 轮、3.4 分钟、30 天→10 天、400→1,200 条/日、采纳率 92%、过期治理完成率 90.2%）；(b) 图 010 看板截图（1073 条资产、注入命中率 25.21%、代码采用率 78.85%、满意度 0%、点赞 0）；(c) 图 006 角标（知识复用率提升 80%+、问题解决效率提升 60%+，正文未提）。**正文与截图有多处不一致**（见 §3、§9），说明数字是不同时点快照，不能横向拼接。
- 文中唯一外部链接是腾讯内网 km.woa.com（403，未能获取）。MCP/RAG 只作术语解释，无论文或官方博客引用。
- 超出可核实范围：12 个 Agent 的实际行为、7 个知识库的内容、知识卡片字段结构（文中说"要根据场景设计"但**没有给出一张卡片样例**）、治理规则的具体实现。
- 本文的"必须/铁律/硬规则"是该团队对自身场景的表述（D-014），本卡一律先作`提议`处理。

## 1. 文章在讲什么
问题：团队上了 Agent 之后，知识供给成为瓶颈——知识散落在需求文档/评审记录/MR 评论/人脑里，同一个坑反复踩；Agent 面对上千篇长文时检索漂移、整篇注入浪费 token。作者的解法是把知识库从"仓库"改造成"供给系统"：先用四个问题定目标（场景/消费者/装什么/怎么算成功），把知识沉淀绑定到研发流程的五个必经节点上自动产出，用"已上线 + 已关联仓库"双门禁决定能否进入 Agent 引用池，按三层可信度分级，90 天到期重校验、零引用自动归档、有引用自动复活；分发侧改"Agent 自己搜"为"平台按场景主动注入并记账"，每个 Agent 只订阅自己的知识包。作者声称的结果：99.7% 知识由流程自动沉淀、交付从天级到小时级、代码审查轮次与耗时大幅下降、知识库"基本不需要人盯着"。文末给出 4 条反模式和"从一个场景闭环切入、别贪全"的建议。

## 2. 核心主张
- **C1** Agent 时代知识库的真正瓶颈不是"读不了长文"，而是**检索精度**和**注入效率**两件事；结构化卡片（适用条件/核心结论/应做/不应做）同时解决两者。｜支撑：推理 + 2000 篇文档的场景描述，无数据｜适用条件：知识规模上千、多 Agent 消费｜文中位置：为什么 AI 时代需要重新建知识库
- **C2** **人机共读**：不为 Agent 维护与人读版本分离的第二套知识；人看不懂的知识维护质量必然差、会腐败。｜支撑：类比（写得好的 Skill/Prompt 人也能读）｜适用条件：通用｜文中位置：同上
- **C3** 三大范式转变：人写人读 → 流程生产·Agent 消费·人纠偏；单一知识库 → 知识 + 数据双轮；静态存储 → 飞轮自增强（保鲜/退场/复活）。｜支撑：表格 + 图 002，无数据｜适用条件：通用｜文中位置：同上
- **C4** 动手前先答四问：服务什么场景、谁来消费怎么消费、装什么（L1～L4 四层盘点）、怎么算成功（可观测指标：注入命中率、画像覆盖率、盲搜下降率、返工下降率、对话采纳率）。｜支撑：作者团队对四问的回答｜适用条件：任何团队起步阶段｜文中位置：DEFINE THE SCOPE
- **C5** **"沉淀靠人一定失败"**，因此把沉淀绑死在研发流程五个必经节点（需求评审通过/方案评审通过/代码审查完成/需求上线/需求失败），知识成为流程副产品。｜支撑：99.7% 自动沉淀（自报）+ 图 003｜适用条件：有明确流程节点的研发/运营团队｜文中位置：DEFINE THE SCOPE、Step 4
- **C6** **准入双门禁**：没上线或没关联仓库的知识一律暂存，不进 Agent 引用池，上线后自动转正；否则知识库被半成品淹没。｜支撑：作者经验陈述，无对照｜适用条件：知识与代码仓库有对应关系｜文中位置：DEFINE THE SCOPE、Step 5
- **C7** 知识库应组合三种形态（文档型 / 结构化存储 / RAG 向量型），不要只建一个；工具层用适配层（MCP）按业务域拆成多个 Server，因为单 Server 工具数有上限、工具多耗 token、业务需隔离。｜支撑：作者选型经验｜适用条件：多业务域｜文中位置：Step 2、Step 3
- **C8** 四种生产模式并行：流程绑定自动沉淀 / 复盘 Agent 每周扫会话把未命中问题自动变成 Git MR / Agent 把事件背景转成结构化知识 + 准召评估 / 运营处置即时沉淀。｜支撑：自报数字（知识上线周期天级→30 分钟、最短 2 小时入库）｜适用条件：同上｜文中位置：Step 4
- **C9** 治理四件事：准入双门禁、三层质量分级（可直接使用/待确认/待验证，按可信度自动划分）、有效期保鲜（默认 90 天重校验，过期且零引用归档）、自动退场 + 复活兜底（仍有引用或被点赞的自动复活）。｜支撑：已归档 101 条、清理候选 11 条、过期治理完成率 90.2%（自报）｜适用条件：知识库规模持续增长｜文中位置：Step 5
- **C10** 分发改为**平台主动注入**：Agent 启动任务前系统按场景打包塞入，"100% 确定到达"，并且**注入即记账**（每条知识被谁用了几次自动记录）；每个 Agent 有自己的知识订阅，知识包分仓库专属包与公共包，不撒网推送。｜支撑：12+ Agent、40 个知识包（自报）｜适用条件：平台化多 Agent｜文中位置：Step 6
- **C11** 飞轮靠三个巧劲："用即积累"（对话未命中→自动 MR）、"注入即记账"、"**敢于不沉淀**"（系统判断无价值就跳过，异步蒸馏降噪，密度比体量重要）。｜支撑：O3 Buddy 月均 1,097 对话、采纳率 92%（自报）｜适用条件：通用｜文中位置：THE FLYWHEEL
- **C12** 让人参与靠工具而非管理手段：沉淀在与 AI 对话过程中被动发生并自动归属到人；贡献榜、可写入自评是"锦上添花"。｜支撑：图 009 贡献榜｜适用条件：该团队组织文化｜文中位置：THE FLYWHEEL
- **C13** 四条反模式：强压 KPI 逼贡献 / 只进不出无限膨胀 / 隐性知识无法显性化（专家离职带走 know-how）/ 贡献者与组织权责不对等。｜支撑：无｜适用条件：通用｜文中位置：避坑指南
- **C14** 价值四层：组织记忆、新人加速、知识平权、自增强飞轮；人从"知识搬运工"变成"知识质量把关人"，Agent 干 80% 重复、人做 20% 判断纠偏。｜支撑：自报数字（30 天→10 天、11+ 篇故障复盘）｜适用条件：该团队｜文中位置：WHAT CHANGED
- **C15** 从一个具体场景的闭环切入，跑通再横向扩展；"飞轮开始转比转得快重要"。｜支撑：无｜适用条件：通用｜文中位置：结尾

**冲突项展开（图 005 vs D-007 / 04 §4）**：
- 冲突在哪：D-007 与 04 §4 规定候选默认**审批后**才写入权威知识，quarantined 不参与默认检索。本文实际系统（图 005）中，需求复盘/技术方案在上线后**自动转正入引用池**，被引用 222 次后仍在"待审核"队列；人工审核是**事后**高价值复核，不是消费前置条件。文章正文"准入双门禁"用**客观信号**（上线、关联仓库）代替了人工审批。
- 谁的证据更强：本文有运营数据（几个月、上千条、数万次调用）证明"事后审核 + 客观门禁"能跑；D-007 的动机是防"模型推断和敏感信息污染"，本文用置信度标签（50%/60%/70%）和"陈旧"标记把风险显式化，但**没有报告误注入造成的损害**（无负向反馈数据，负向反馈 Tab 未展示内容）。两边都没有对照。
- 可否共存：可以，若把 D-007 的"审批"拆成两个正交维度——**入池条件**（可由客观交付信号自动满足）与**权威性**（仍需 owner 批准）。本文的"可直接使用/待确认/待验证"三级正是这一拆分：待确认的知识可被检索但**带可信度标签**，Agent 消费时须按标签降权。这对应本规范"召回结果只能提出线索"（04 §6），差别只在**待确认候选是否进默认检索**——本文说进（带标签），本规范说不进。建议作为 D-006/D-007 待决问题（待决策清单 A0-8）的一个实证输入。

## 6. 建议采纳（候选语义）
- **S1** 经验类知识候选的可信等级必须绑定它来自的交付链节点与客观信号（是否已通过验收/已生效、是否关联到具体工作区），不得由作者或模型自评。｜落地方式 A（外部状态存储）：候选记录携带"来源阶段"字段，状态由验收/发布事件推进｜落地方式 B（检查器）：晋升前检查候选是否链接到已生效的验收证据，缺失则拒绝｜落地方式 C（人工检查点）：验收会签时核对候选来源阶段｜它防御的失败：未验证的半成品经验进入默认检索并被当作事实（本文 F2）｜删除条件：写不出（属责任判据：知识是否已在真实环境生效只能由证据证明，不因模型变强消解）
- **S2** 知识与长期记忆条目在被加载进上下文时必须留下消费记录（被哪个任务/角色、何时加载），该记录是过期判定与 Thin 的输入。｜落地方式 A（运行时拦截）：注入动作发生时自动写记录｜落地方式 B（外部状态存储）：索引条目维护 last_used 与消费计数，由检索层更新｜它防御的失败：无人消费的条目无法被识别，知识库只增不减（F3）；D-013"按无消费删减"无数据可依｜删除条件：写不出（记账是可观测性要求，不依赖模型能力）
- **S3** 过期且零消费的条目默认退出检索但不删除；退出后仍被引用或被明确标记有用的条目自动恢复。｜落地方式 A（检查器）：周期性任务按到期 + 零消费归档，按引用信号恢复｜落地方式 B（条件加载规则）：检索索引排除 archived 状态，引用触发状态回迁｜它防御的失败：过时知识干扰决策（F3）与误杀有价值知识两者的对冲｜删除条件：当模型能在推理时自行判定条目时效性且误判率可评估低于归档误杀率时可删
- **S4** 知识与工具集按消费者角色/任务类型订阅，每类 Agent 只可见其订阅子集，而非全库可见。｜落地方式 A（条件加载规则）：按任务类型加载对应知识包｜落地方式 B（权限与隔离配置）：不同角色的 Agent 被授予不同知识源与工具集的访问权｜它防御的失败：上下文取并集、无关工具定义耗尽上下文（C7；Anthropic 博客同向）｜删除条件：当模型在超长上下文中的检索精度不随无关内容增加而下降（需在代表性任务上评估，对应 D-012）
- **S5** 经验候选的提取绑定到交付链的既有状态转换（评审通过、审查完成、发布生效、任务失败），作为转换的副产品自动发生，不作为额外人工动作。｜落地方式 A（运行时拦截）：状态转换事件触发提取器｜落地方式 B（人工检查点）：交接合同/验收清单要求填写"本切片的踩坑与决策"，缺项不得关闭｜落地方式 C（检查器）：合并请求模板校验"经验沉淀"段非空或显式声明"无可沉淀"｜它防御的失败：靠人主动写则不写，经验留在个人头脑（F1）——这是 D-020 判据一"必须写"的执行侧空缺｜删除条件：写不出（组织与人脑信息只能在发生时被捕获，模型无法事后凭空取得）
- **S6** 提取器必须允许输出"本次无可沉淀"，且知识库健康度按密度（被消费/被验证比例）而非条目数评估。｜落地方式 A（检查器/评估指标）：健康度指标不含总量项，只含消费率、验证率、过期率｜落地方式 B（人工检查点）：复核时可将候选整批拒绝而不需理由｜它防御的失败：只增不减的膨胀（ATT-N 机制；本文 F3）｜删除条件：写不出（与 D-026 同源）
- **S7** 不为 Agent 维护与人读版本分离的知识副本；同一条知识只有一个载体，人与 Agent 都从它读。｜落地方式 A（检查器）：Agent 加载清单中的每个来源必须也是人读文档的权威位置，出现"仅供 Agent"的副本即告警｜落地方式 B（人工检查点）：评审拒绝新增"AI 专用摘要文档"｜它防御的失败：第二事实来源腐败（ATT-H）；人看不懂的知识无人维护（C2）｜删除条件：写不出
- **S8** 知识供给类指标必须区分"到达"（被注入）与"有用"（被采纳/被验证/被正向反馈），只报告到达率的知识系统视为反馈环缺失。｜落地方式 A（检查器）：评估报告缺少采纳/反馈维度则判 UNDETERMINED｜落地方式 B（人工检查点）：复盘会议按两个维度分别审｜它防御的失败：命中率被满足而知识无用（D-023 目标失明；图 010 点赞 0 / 满意度 0%）｜删除条件：写不出

- 全部效果数字（99.7%、2-4 轮→1.1 轮、3.4 分钟、30 天→10 天、400→1,200、92%、90.2%/100%、80%+、60%+）—— 无对照、无测量条件、正文与截图互相矛盾；只作观察记录。

## 8. 该文暴露的失败模式
- **F1** 踩坑经验只存在于提 MR 那个人的脑子里 → 不同人反复踩同一坑；新人查一个模块的历史决策要翻 wiki/问人/刨 commit，一两天 → 文章处置：五节点自动沉淀 + 缺陷库/复盘库供审查 Agent 订阅 → **可构造回归 Case**：给定一个已在历史工作项中记录的失败决策，新任务触及同一模块时 Agent 是否召回并避免（对应 D-006/D-007 验证）
- **F2** 没有准入门禁 → 半成品、未上线方案、无效文档进入 Agent 引用池，Agent 引用了从未生效的方案 → 文章处置：已上线 + 已关联仓库双门禁，未满足者暂存 → **可构造**：投放一条"评审通过但未上线"的技术方案候选，检查它是否进入默认检索（S1）
- **F3** 知识只进不出 → 三个月后信噪比下降，过时内容干扰 Agent 决策 → 文章处置：90 天到期 + 零引用归档 + 复活兜底 → **可构造**：注入一条与当前代码冲突的过期规则，观察 Agent 是否按标签降权或报冲突（对应 04 §7 + 01 §4）
- **F4** 依赖 Agent 自己决定是否搜索知识库 → 不确定是否调用，找不到就白搭 → 文章处置：平台按场景前置注入 → 可构造：同一任务在"仅提供检索工具"与"合同预载知识包"两种配置下比较召回率（对应 D-001/D-015；须按 D-025 三层报告）
- **F5** 靠人主动写文档 / KPI 逼贡献 → 不写，或写出低质量、无人维护的知识 → 文章处置：流程副产品 + 激励为辅 → 难以构造为回归 Case（组织行为），可作 D-022 观测项
- **F6** 注入命中率随知识规模增长而下降（图 010，本人从截图推断，文中未承认）→ 知识越多、每次注入包里相关比例越低 → 文章未处置（反而把"知识月增速持续爬坡"列为正向指标）→ **可构造**：固定任务集，逐步扩大知识包规模，记录相关条目比例与任务结果（对应 D-023、D-026）
- **F7** 反馈环空转：点赞 0、满意度 0%、月 AI 调用人数 7（图 010）→ "反馈"环节没有输入，退场/复活依赖的"被点赞"信号实际为零 → 文章未处置 → 可构造为评估 Case：验证 S3 的复活规则在无人工反馈时是否退化为"只看引用次数"
