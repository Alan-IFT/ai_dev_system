## 1. 文章在讲什么
写代码不再是瓶颈后，交付会在三处断掉：Agent 读错事实（旧契约、旧文档）、规则只是提醒拦不住错误、任务中断后状态只在聊天记录里。作者把 Harness 定义为解决这三件事的环境：**可信上下文**（知识库是地图不是百科全书，三跳路由收窄问题空间；重要结论必须带 source/revision/scope/observed_at/verification；"存在"不等于"生效"），**可执行约束**（规则的约束力取决于违反后会发生什么；阶段之间的门禁检查"上一步是否真的完成"，动作之前的检查判断"这次操作是否允许"），**可恢复流程**（文档保存任务内容、State 保存任务位置、Workflow 规定交接合同；恢复的是任务不是会话）。第五部分讲 Harness 如何从一个真实任务长出来：先无脚手架跑基线，留下运行证据，Doctor 归因到最早偏离层，再决定 Add/Thin；跨项目能带走的是观测问题、状态语义、证据原则和方法，不能带走的是入口、节点、命令、证据位置和 Gate 实现。结语：Harness 组件隐含对当前模型能力的判断，不是永久资产；但不必定期专门证明某条控制是否还有用，Add/Thin 由日常任务观测决定。

## 2. 核心主张
- **C1** 代码是中间产物；"代码已改、测试通过"只说明 Agent 认为实现结束，交付还须回答读的是否当前生效、测试是否覆盖本次修改且跑对目录、有无可复查证据。｜支撑：推理 + Cursor 改鉴权读旧契约的假想例｜适用条件：持续迭代项目｜文中位置：§01
- **C2** Harness 的三件事是可信上下文、可执行约束、可恢复流程；它不是多写文档多加 Prompt，而是让 Agent"开始时不易读错、执行时不易跑偏、中断后能继续、说完成时拿得出证据"。｜支撑：图 004/005｜文中位置：§01
- **C3** 可信上下文是一条供应链而非知识库：真相源→索引→按任务检索→按 Authority/Freshness/Scope 筛选→组装→下钻→测试/契约/readback→经验回写；每段都不能被"知识已存在"替代。｜支撑：图 006 + 推理｜文中位置：§02 引言
- **C4** 长 Prompt/入口文件的四个结构性问题：占用窗口、容易过期、缺少优先级、drift 只能靠人偶然撞见。｜支撑：作者观察｜文中位置：§2.1
- **C5** 代码只能说明"现在怎么做"；"为什么这样设计、什么不能破坏、发布顺序为何不能反、怎样才算完成"是代码之外的意图，不写下来 Agent 和新人都只能猜。一份维护良好的文档目录就是高质量知识库。｜支撑：Wish 端间鉴权的五个问题（代码在哪/为何如此/边界/影响谁/何为完成）｜文中位置：§2.1
- **C6** 知识库是地图，设计重点在入口不在容量；三跳路由（项目身份与硬约束→任务关键词到模块→专题文档或源码）是三次收窄问题空间，不是三份缩短版百科；Context 是沿任务路径逐步组装的工作集。"好的 Context System 首先是 Navigation System，其次才是 Storage System"。｜支撑：图 007 + Wish 路径｜文中位置：§2.2
- **C7** 找到不等于可信：同一问题会同时搜到历史文档、当前代码、生成契约和运行记录，它们可能都真但描述不同现场；"某处已经存在"不能说成"当前已经生效"。｜支撑：ShoppingUI Nightly 案例（本地 f12e007 含修复，Public Contract 与 receipt 记录的输入仍是 9c044649）｜文中位置：§2.3
- **C8** 重要结论须带六个最小字段（claim/source/revision/scope/observed_at/verification），载体不限；只有项目真的遇到多来源冲突、多环境、时间失效、派生投影、新旧替代时，才逐项加 authority·owner / environment / valid_from·last_verified_at / derived_from·content_hash / status·supersedes。｜支撑：图 008/009｜适用条件："小项目做到六字段已足够"｜文中位置：§2.3
- **C9** 沉淀阶梯：一次问题先修复；重复出现的路径写 Runbook；频率继续上升做 Skill/脚本；能机械判断且失败后不应继续的部分最后下沉成 Gate。｜支撑：ShoppingUI 的 kb:context→回源码确认→kb:check:source→full/nightly 路径形成史｜文中位置：§2.4
- **C10** 发现值得沉淀的路径靠一条轻量"能力观察"规则：只在真实任务完成后、只在出现明确信号时、只输出证据最充分的**一项**，说明事实、为何重复、建议载体、最小内容和验证方式；无信号不输出不扩建；只建议不自动改，写入前须用户确认。｜支撑：规则原文（见 §3 图后说明）｜文中位置：§2.4
- **C11** 规则能否形成约束不取决于措辞强度，而取决于违反后会发生什么：条件不满足任务仍能继续的是提醒，下一步真的无法进行的才是约束。"分界点不在有没有脚本，而在脚本是否自动进入必经路径、失败是否改变后续状态"。｜支撑：图 010 四级阶梯｜文中位置：§03、§3.1
- **C12** 文档负责讲清为什么，脚本负责检查有没有做到；适合脚本的事实：报告是否生成、是否本次产生、测试目录与代码目录是否一致、必测场景是否覆盖、命令是否操作保护分支、上一步失败后是否还在写数据。设计取舍与业务边界仍交给人。｜支撑：列举｜文中位置：§3.1
- **C13** 两类检查位置回答不同问题：阶段之间——上一步是否真的完成，不通过则不进入下一阶段；动作之前——这次操作是否允许，不通过则不执行。｜支撑：图 011；Wish 进入 Review 前的五项检查（报告存在/本次生成/目录一致/调用规定入口/必测场景已生成且真跑）；MR 描述含字面量 `\n` 被创建前拒绝｜文中位置：§3.2、§3.3
- **C14** 自动化多仓任务把操作空间缩到当前任务允许的范围：只能用事先登记的命令和参数、每项修复只能改声明过的目录、前面的检查失败后后面的写入停下（barrier）。｜支撑：ShoppingUI Nightly｜文中位置：§3.3
- **C15** 可恢复流程 = 文档维护（内容）+ 工作流推进（交接合同）+ 状态存档（位置）；恢复的是任务不是会话，Session 恢复只能作辅助。交接合同三条：输入必须来自已确认事实或上一步产物，不能从聊天记忆里猜；输出必须落到文档、代码现场或报告；输出不满足下一阶段需要时流程停在当前节点。｜支撑：图 012/013｜文中位置：§04
- **C16** 可恢复性的检验问题："假设每个阶段结束后都立即换成一个全新的 Agent，它还能不能只靠项目里的状态、文档和真实工件继续工作？"不能则流程仍依赖对话，只是表面拆成了步骤。｜支撑：推理｜文中位置：§4.2
- **C17** Harness 从真实任务长出来：第一轮无额外脚手架建基线，保留自然产生的证据（diff、测试/构建结果、人工纠正、需人接管处、结果与预期差）；能可靠完成就不加机制；失败也不马上加多 Agent/长 Prompt/复杂工作流。"Harness 只应该解决已经出现或能够明确验证的问题"。｜支撑：图 015 循环｜文中位置：§5.1
- **C18** 观测整个执行链的四个面：输入（Agent 实际消费了什么）、过程（在哪阻塞或被人纠正）、结果（"完成"有无现实证据）、**Harness 自身**（哪些机制真的生效，哪些只是摆设或误伤：Skill 是否触发、脚本和 Gate 是否拦住真实问题）。第一版不需要观测平台，记录只是证据的索引。｜支撑：图 016｜文中位置：§5.2
- **C19** 出问题后不要继续改 Prompt（"下次请认真阅读文档"），而是 Doctor 四步：读输入/revision/worktree/命令/测试/人工纠正 → 沿执行链找第一个偏离点 → 区分已确认事实、合理推断、未验证信息并给 1～2 个修复方向 → 人与 Agent 定方案后**用原来的失败路径和一条正常路径验证**。无法复现或证据不足就继续观测，不急着改 Harness。｜支撑：Wish 测试报告与目标 worktree 不一致案例：回查 state.json/报告目录/脚本入口后才把一致性检查放进 verify-artifacts.sh｜文中位置：§5.3
- **C20** 跨项目可带走的是观测问题、状态语义、证据原则、任务模板、Doctor 原则和 Add/Thin 方法；必须在新项目重新生成的是任务入口、工作流节点、工具命令、证据位置和 Gate 实现。｜支撑：图 014 同三个问题在 Wish/ShoppingUI 的不同落点｜文中位置：§05、§5.2
- **C21** Harness 组件隐含对当前模型能力的判断，不是永久资产；但**不意味着要定期专门证明某条控制是否还在发挥作用**，Add/Thin 由日常任务观测决定：重复失败、缺证据、无法恢复→Add；长期无人消费、重复实现、频繁误伤、明显负收益→Thin；"已经不再影响结果的规则应该删掉，避免反过来成为瓶颈"。｜支撑：推理｜文中位置：§06

## 6. 建议采纳（候选语义）
- **S1** 每条重要结论必须携带最小字段（断言、原始证据、精确版本、适用范围、观察时间、确认方法）；权威归属、环境、有效期、派生来源、替代关系等字段只在项目观察到对应复杂度信号（多源冲突、多环境、时间失效、派生投影、新旧替代）时追加，且追加须登记触发信号。｜落地方式 A（外部状态存储）：结论记录的固定结构，项目自定载体｜落地方式 B（检查器）：对"已生效/已通过"类声明扫描缺失字段即拒收｜落地方式 C（人工检查点）：评审只接受带字段的结论｜它防御的失败：把"某处已存在"说成"当前已生效"（F1）；局部结论扩大为全局｜删除条件：写不出——这是信息完整性要求，不随模型能力消失；但字段集可随项目复杂度回落而收缩
- **S2** 自动化运行必须在运行前冻结并记录它实际消费的输入版本，"修复已生效"类主张只能对照该记录判定，不能对照工作副本。｜落地方式 A（外部状态存储）：运行回执含冻结的输入标识｜落地方式 B（检查器）：对比回执中的输入版本与声称已包含修复的版本，不一致则判"未消费"｜它防御的失败：本地已修、运行仍用旧版（F1）｜删除条件：写不出——运行与源之间的版本错配不是模型能力问题
- **S3** 规则的约束等级由两个独立维度定义：检查是否自动进入必经路径、失败是否改变后续状态；只有两者皆是的才可登记为 Gate，"自动运行但失败可继续"只能登记为警告并不得被引用为已通过检查。｜落地方式 A（运行时拦截）：检查失败即阻断转换或动作｜落地方式 B（外部状态存储 + 检查器）：状态工件记录每项检查的等级，验收时拒绝把警告级计入通过条件｜落地方式 C（人工检查点）：规则评审必答两个维度｜它防御的失败：虚假阻断——检查存在但从未拦住任何事（F3）；D-014 已识别的"空 Gate 集=通过"的邻近形态｜删除条件：写不出（责任类）
- **S4** 上游检查失败后，同一任务中所有后续写入动作必须停止，不得带着已知失败继续修改下游；失败回边不只回退本节点。｜落地方式 A（运行时拦截）：失败标记使后续写入命令被拒绝｜落地方式 B（工作流状态）：状态机进入阻塞态后不接受写入类转换｜它防御的失败：带病推进导致下游污染，返工范围扩大（F4）｜删除条件：写不出（与可逆性相关，不与模型能力相关）
- **S5** 可恢复性的验收标准：任意阶段边界处强制更换执行者且只允许读取项目内工件，新执行者仍能完成下一阶段；不能通过的流程视为仍依赖对话。｜落地方式 A（检查器/评估）：回归 Case 在每个阶段边界重置上下文并度量下一阶段完成率｜落地方式 B（人工检查点）：交接评审由未参与前一阶段的人只凭工件复述"凭什么开始"｜它防御的失败：表面分阶段、实际依赖聊天记忆（F5）｜删除条件：写不出——这是对工件完整性的要求；若工具提供跨会话完整记忆且被本规范承认为权威载体，则检验对象改变但要求不消失
- **S6** 改进闭环中"候选发现"是独立步骤且自带限流：只在真实任务结束后、只在出现明确信号时、每次最多提出一项证据最充分的候选，候选须含事实、重复原因、建议载体、最小内容、验证方式；无信号不产出；候选不得自动写入任何规则、技能或文档。｜落地方式 A（条件加载规则）：任务结束触发的观察步骤｜落地方式 B（人工检查点 + 外部状态存储）：候选进入待审队列，由人批准后才进入 D-019 晋升链｜它防御的失败：读到 bad case 即追加（WX-16 F1）；想象需求建平台｜删除条件：当写入端刹车（D-026 四要素）经评估证明单独足以阻止膨胀时，可放宽每任务一项的限流，但"只建议不写入"部分为责任类，写不出
- **S7** Harness 机制本身是被观测对象：每次任务须能回答每项机制是否被消费（文档是否被本次读到、技能是否触发、检查是否拦住真实问题或误伤）；连续无消费或只产生误伤是 Thin 的依据，但不作为静默过期规则的唯一依据（见冲突一）。｜落地方式 A（外部状态存储）：运行记录含机制触发/拦截/误伤事件｜落地方式 B（检查器）：按机制统计消费与误伤计数｜落地方式 C（人工检查点）：定期复查零消费机制｜它防御的失败：机制只是摆设却占用上下文与注意力（F6）｜删除条件：写不出（元规则）
- **S8** 每次根因修复必须同时用原失败路径和至少一条正常路径验证；诊断输出必须区分已确认事实、合理推断与未验证信息。｜落地方式 A（检查器）：Case 注册表要求每个修复引用一个失败 Case 和一个正常 Case｜落地方式 B（人工检查点）：修复评审拒绝只有失败复现的提交｜它防御的失败：修复引入误阻断（D-018 observability 字段所防的失败）；把推断当事实写进规则｜删除条件：写不出
- **S9** 外部写入的结果状态必须允许第三态"未知"，未知不得被记为成功或失败；解除未知只能靠回读，重试须有幂等标识。｜落地方式 A（外部状态存储）：写入记录状态枚举含 unknown｜落地方式 B（运行时拦截）：对 unknown 状态的写入禁止无幂等键重试｜它防御的失败：网络中断后重复写入或误报完成（F7）｜删除条件：写不出（环境不确定性不随模型消失）

## 8. 该文暴露的失败模式
- **F1** 本地工作副本含修复，自动化运行冻结的输入仍是旧版本 → 只看代码得出"修复已存在"，实际该次运行未消费 → 处置：以运行回执的 frozen SHA 为准，结论带 revision/scope → **可构造**：工作副本领先于运行输入一个提交，检查执行者是否声称"已生效"
- **F2** 代码改在 worktree A，测试在目录 B 运行，报告绿色 → 绿色报告不能证明当前代码通过验证 → 处置：不加提醒，回查 state/报告目录/脚本入口后把目录一致性检查放进阶段门禁 → **可构造**：D-009"worktree 错配 Case"的原型；本文提供了它的真实来源
- **F3** 检查脚本存在但要靠 Agent 想起来运行，或自动运行但失败不阻断 → 检查从未真正拦住任何事，却被当作"已有检查" → 处置：接入必经路径并让失败改变状态 → **可构造**：同一检查按图 010 四级各部署一次，注入必失败输入，统计放行率
- **F4** 多仓自动修复中上游检查已失败仍继续写下游 → 带着已知问题修改更多仓库 → 处置：barrier，失败后停止后续写入 → **可构造**：多步写入任务，第一步注入失败，检查后续步骤是否执行
- **F5** 多阶段流程表面分步，实际每步依赖上一段对话 → 换执行者后无法继续 → 处置："每阶段换全新 Agent"检验 → **可构造**：D-016 恢复 Case 的强化版，每个阶段边界重置上下文
- **F6** Harness 中的文档/Skill/Gate 长期无人消费或只产生误伤 → 占用上下文并成为瓶颈，但没有信号触发删除 → 处置：把 Harness 自身列为观测面 → **难以直接构造为回归 Case**，只能作观测指标（消费计数、误伤计数）；与 WX-26 F7 同类
- **F7** 外部系统写入（MR 创建、契约下发）结果不确定 → 被记为成功或失败之一，导致重复写入或漏发 → 处置：unknown 状态 + 幂等键 + readback → **可构造**：模拟写入超时，检查执行者记录的状态与重试行为
- **F8** MR 描述中写入字面量 `\n` → 页面显示错误，事后才发现 → 处置：创建前输入校验拒绝 → **可构造**：动作前 Gate 的最小样例，也是 D-018 execution point 字段的实例
- **F9** 出问题后在下游继续追加"下次请认真…"类 Prompt → 同类问题反复出现且规则集膨胀 → 处置：Doctor 归因到最早偏离层 → **可构造**：给定轨迹，比较"追加提醒"与"最早偏离层修复"两种处置的复发率（与 WX-16 F1 互为镜像）
- **F10** 把已成型项目的 Harness 整体复制到新项目 → 节点、Gate 条件、证据格式、权限边界全部错位 → 处置：只带走观测问题、状态语义、证据原则和方法，其余从第一个真实任务重生 → **可构造**：D-020 判据三的项目维度版本
