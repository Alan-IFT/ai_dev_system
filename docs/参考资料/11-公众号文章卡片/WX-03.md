## 1. 文章在讲什么
作者接着 Datawhale 前一篇《Loop Engineering 实操手册》补两件事：演进脉络与本质。演进脉络是 Prompt → Context → Harness → Loop 四段：Prompt 解决措辞，Context 解决信息不足，Harness 解决单会话多步执行，Loop 解决"人是瓶颈"——把"人触发 → 人判断 → 人决定下一步"里的人换成自动系统。六组件（Automations / Worktrees / Skills / Connectors / Sub-agents / Memory-State）用一个每天 8 点自动修 CI 的场景串起来。本质部分把 Loop 解释为控制论闭环：控制器（编排逻辑，需要知识与记忆 → Skills、Memory）、执行器（工具调用，需要触达与隔离 → Connectors、Worktrees）、传感器（验证，需要独立性 → Sub-agents），Automations 是启动条件。闭环跑在随机的 LLM 上有三种结局：收敛到正确、收敛到错误（传感器误报"通过"，比不停更糟）、发散。作者结论：传感器决定收敛速度，"强 prompt + 弱验证会失败，平庸 prompt + 强验证会收敛"；能否建 Loop 取决于能否写出无人值守即可拒绝坏输出的检查；建设顺序是先 Skills、再传感器、最后触发器——"先建 Inspector，再建 Loop"。

## 2. 核心主张
- **C1** 四种工程范式是逐层解决前一层未解决的问题：Prompt（措辞）→ Context（信息量）→ Harness（单会话多步执行）→ Loop（人作为触发/判断/决策环节的瓶颈）。｜支撑：叙事推理，无数据｜适用条件：coding agent｜文中位置：§一
- **C2** Loop 的出发点是"人是瓶颈"：Agent 能力不再是瓶颈，每天由人检查 CI、贴日志、审结果、批合并的循环才是。｜支撑：日常场景描述｜适用条件：重复性运维式任务｜文中位置：§一
- **C3** 一次完整 Loop 运行 = 触发发现工作 → 隔离工作区 → 读项目规则 → 执行并触达外部系统 → 由另一个 Agent 验证 → 把结果与卡点写入持久状态供下次读取。｜支撑：虚构 CI triage 场景｜适用条件：同上｜文中位置：§二
- **C4** Loop 与 cron 的区别在于决策者：cron 的逻辑写入时固定（if-else），Loop 内部决策者是 LLM，行为运行时才确定（可判断 flaky test 跳过、或拆成多步）。｜支撑：推理｜适用条件：需要现场判断的任务｜文中位置：§二末
- **C5** 六组件不是拼装零件，而是控制论闭环三角色的自然需求：控制器需知识+记忆（Skills、Memory）；执行器需触达+隔离（Connectors、Worktrees）；传感器需独立性（Sub-agents）；Automations 是不属于三者的启动条件。｜支撑：类比推理（空调、巡航定速）｜适用条件：任何反馈闭环｜文中位置：§三
- **C6** 传感器必须独立于执行者：同一 Agent 自验，错误相关——导致 bug 的盲点恰是看不到 bug 的盲点；需另一个 Agent 甚至另一个模型。｜支撑：类比（学生自己批卷）｜适用条件：所有验证｜文中位置：§三·传感器
- **C7** 被控对象是随机的 LLM，同样输入两次输出可能不同，随机性越强反馈修正越不可缺少；因此不能用"固定计划"掌控它。｜支撑：推理｜适用条件：LLM 系统｜文中位置：§三
- **C8** 闭环三种结局：收敛正确（唯一好结局）；收敛错误（传感器误报"通过"——测试本身写错、出问题路径未执行、审阅 Agent 太易同意——"带着自信停下"，比不停更糟）；发散（越改越偏，到上限退出）。设计目标是提高第一种概率或限制后两种损失。｜支撑：推理，无案例｜适用条件：无人值守闭环｜文中位置：§三
- **C9** 收敛速度由传感器决定：只返回 pass/fail 时控制器近乎盲猜；返回"哪个用例、哪个断言、哪个 diff 引入"时修复是针对具体缺陷的，搜索空间被压缩。｜支撑：推理｜适用条件：同上｜文中位置：§三
- **C10** 高杠杆在于设计更好的传感器而非买更强模型："Great prompt + weak verification will fail; mediocre prompt + strong verification will converge"，"传感器就是设计本身"。｜支撑：断言，无对照｜适用条件：同上｜文中位置：§三末
- **C11** 该不该建 Loop 的判据：能否写出**不需要人盯着就能拒绝坏输出**的自动检查；能则有闭环前提，不能则"完成"是主观判断。附加约束：任务至少每周重复一次；token 预算能承受重读与重试的浪费；Agent 有足够工具观察结果，否则是盲修。｜支撑：推理（源自 Rezvani 文）｜适用条件：决定是否自动化｜文中位置：§四
- **C12** 目标不可测量的任务（"更优雅"、"好的博客"、"好的 API"）建 Loop 是假闭环；让另一个 LLM 打分不可靠——倾向给高分且标准漂移。｜支撑：断言｜适用条件：主观目标任务｜文中位置：§四
- **C13** 建设顺序：先写 Skills（明确意图与标准）→ 再写传感器（精确定义"做完"）→ 最后套触发器。"先建 Inspector，再建 Loop"。｜支撑：推理｜适用条件：满足 C11 的任务｜文中位置：§四
- **C14** Loop 不关心操作者是谁，只放大传感器编码的判断力——你对系统理解多深，传感器就能多精确。｜支撑：断言｜适用条件：通用｜文中位置：§四末

**引用 7（Kokane）的价值**：一句话给出 Harness 与 Loop 的边界——harness 是单个 agent 住在里面的东西，loop 是决定何时拉起 agent 的东西。这与本规范 00 §2 "四种范式互补"一致，且比本文 §一的线性叙事更精确：Loop 不替代 Harness，而是在 Harness 外面加一层调度与判定。它的 `/goal` 描述（独立小模型判停止条件）是"验证者独立"的一个具体产品实例，可作载体实例登记，不进正文。它"多数场景是浪费"的告诫，与本规范 D-010 复杂度阶梯同向。

**引用 8（Rezvani）的价值**：本文 §四的原始出处。"能否写出无人值守即可拒绝坏输出的检查"是一个**可操作的判据**，比本规范 D-024 "自主度上限 = 可廉价可靠验证的量"更容易在立项时套用；四条件中把验证列为唯一红色门，其余三条是经济性约束——这个主次划分值得吸收。

**外围 A（Ronacher）的价值**：一手实践者的反面观察。Loop 只优化传感器能测的量，而"代码可维护性"通常测不到——这正是 D-023 目标失明在代码任务上的具体形态，且是本文 C8 "收敛到错误状态"没有列出的第四种情况：传感器没错、目标也达到了，但未测量的维度被牺牲。

## 6. 建议采纳（候选语义）
- **S1** 验证器的输出必须携带定位信息（失败的用例/断言/引入差异），不得只有通过/失败二值；闭环的修正步骤以该定位为输入。｜落地方式 A（检查器）：测试/静态检查运行器输出结构化失败报告，控制器读报告而非原始日志｜落地方式 B（外部状态存储）：每轮失败的定位与已尝试的修复写入工作项状态，下一轮先读｜它防御的失败：控制器在 pass/fail 二值下盲猜式修正，导致发散或重复相同修复（本文 C9）｜删除条件：观察工具能廉价返回完整现场且模型能从原始输出可靠恢复定位时，可删去"结构化"要求，保留"必须有定位"。
- **S2** 一项任务进入无人值守闭环的前置条件，是存在一个不需要人在场即可拒绝坏输出的判定器；不存在判定器的任务只能以人工检查点为停止条件，不得自动触发。｜落地方式 A（检查器）：把验收标准写成可执行判定，判定器缺失即闭环不启动｜落地方式 B（权限与隔离配置）：未登记判定器的任务不授予定时/事件触发权限，只能人工拉起｜它防御的失败：假闭环——传感器说"通过"但"通过"无客观标准（本文 C11/C12）｜删除条件：写不出（这是 D-024 与责任判据的直接推论，不随模型能力消解）。
- **S3** 模型评分只能作为提议信号，不能单独作为无人值守闭环的停止条件；主观目标（"更优雅"、"更好"）必须先转成可观察的代理指标或人工验收。｜落地方式 A（静态指令 + 检查器）：停止条件声明中禁止仅含模型评分项，检查器拒绝这类声明｜落地方式 B（人工检查点）：主观目标任务固定以人的验收为终点｜它防御的失败：LLM grader 倾向高分且标准漂移导致"自信地停在错误状态"（本文 C8/C12；与 D-023 目标失明同源）｜删除条件：当某类主观判断的模型评分在代表性评估集上被证明与人工判断一致且稳定时，可对该类任务解除。
- **S4** 自动化闭环的建设顺序固定为：先固化意图与完成标准，再建验证器，最后接触发器；验证器未就位前不得接入自动触发。｜落地方式 A（人工流程 / 变更晋升 Gate）：接入触发器的变更须附带验证器已通过代表性 Case 的证据｜落地方式 B（权限与隔离配置）：触发权限与验证器登记绑定，先登记后授权｜它防御的失败：先有触发器后补验证，闭环在无传感器状态下运行并产出未验证的合并（本文 C13；ATT-Q 先可靠后自动）｜删除条件：写不出。
- **S5** 无人值守闭环必须同时具备两类停止条件：资源上限型（迭代次数/预算）与证据型（连续 N 轮无新证据即停），任一触发都必须升级到人并附带已尝试记录。｜落地方式 A（运行时拦截）：计数器/预算在动作前拦截｜落地方式 B（外部状态存储 + 人工检查点）：每轮把尝试与结果写入状态，下一轮读到"无进展"即停并上报｜它防御的失败：发散结局耗尽预算（本文 C8）；以及 D-003 的同假设循环｜删除条件：写不出（预算约束永远存在）。
- **S6** 每个闭环组件在登记时必须声明它防御的失败（本文图 004 的形态："去掉它，闭环仍能跑，但会出现 X"）。｜这是 D-021 已有提议的**实例证据**，不另立条目；建议把图 004 的六对"组件→防御的失败"作为 D-021 的示例登记到附录。

## 8. 该文暴露的失败模式
- **F1 传感器假通过·测试本身错** 触发：修复 Agent 为通过测试而修改断言或测试与需求不符 → 表现：闭环"自信地停下"，合并了错误实现 → 文章处置：只指出现象，无处置 → 可构造回归 Case：给定一条需求与一个断言写反的测试，检查闭环是否停止并报告，还是直接宣告完成。（对应 05 §6 "实现 Agent 不能通过弱化验收使自己通过"）
- **F2 传感器假通过·路径未执行** 触发：构建/测试通过但缺陷所在路径无覆盖 → 表现：同 F1 → 文章处置：无 → 可构造：注入一个仅在未覆盖分支触发的缺陷，观察验证器是否报告覆盖缺口。
- **F3 传感器假通过·审阅者太易同意** 触发：用 LLM 作审阅者且无客观判据 → 表现：审阅通过率异常高、标准随会话漂移 → 文章处置：改用另一 Agent/另一模型（只解决相关性，不解决顺从性）→ 可构造：同一 diff 换措辞提交多次，统计审阅结论是否随措辞变化。
- **F4 发散到上限** 触发：目标不可达或传感器信号只有 pass/fail → 表现：每轮修改越改越偏，直到迭代上限退出 → 文章处置：上限退出 + 上报 → 可构造：给一个不可通过的目标，测量闭环是否在 N 轮内因"无新证据"停止（D-003）而非耗尽上限。
- **F5 主观目标假闭环** 触发：目标为"更优雅/更好"，停止条件是模型评分 → 表现：评分单调上升而人工评价不变或下降 → 文章处置：判定为不该建 Loop → 可构造：同一任务用模型评分与人工盲评对照，观察是否分离（D-023 目标失明的代码任务版本；Ronacher 的"过度防御、重复、难懂"是现实样本）。
- **F6 盲猜式修正** 触发：验证器只返回二值 → 表现：修复轮次显著增多、重复尝试同一假设 → 文章处置：让传感器返回用例/断言/diff 定位 → 可构造：同一缺陷分别用二值与定位式反馈跑闭环，比较收敛轮次（这是本文少数可做组件级对照的主张）。
- **F7 并行覆盖** 触发：多个修复任务共用一个工作目录 → 表现：互相覆盖编辑 → 文章处置：每任务独立工作区副本 → 可构造：两任务改同一文件，观察是否产生交叉污染（语义：并行执行单元需要隔离的可写空间）。
- **F8 闭环失忆** 触发：运行之间无持久状态 → 表现：每次醒来重复昨天已失败的尝试 → 文章处置：把"尝试了什么、卡在哪"写入状态文件，下次先读 → 可构造：中断后重启，检查是否重复已记录失败的路径（对应 D-016 状态工件）。
