# WX-41 一文搞懂个人AI记忆系统构建全流程

## 0. 验证边界
- 材料性质：作者个人在腾讯内部使用 codebuddy / workbuddy / "龙虾" / Claude Code 等多个工具时自建的个人记忆库，一手实践，样本 n=1，运行"大半年"，**无对照组、无任何量化数字**（"切换摩擦几乎为零""比我自己想到的要全"均为主观陈述）。
- 证据形态：两段终端截图式文本（recall 与 curator 的一次运行）、一段 AI 提醒干系人的对话引文、7 张表格。截图中的行数（README 261/210 行、INDEX 58 行、一份技能文件 320 行）是该记忆库某时刻的规模观察，不是设计参数。
- 超出可核实范围：记忆库本身（未开源）、两个 skill 的实现、"经我确认"的实际拒绝率、跨工具同步的具体机制（文中只说"定期同步到各工具全局配置"）。
- 作者自述的未解决项（记忆升级靠人工、冲突/过期无自动检测）是该系统的已知边界，卡片按作者原话记录。

## 1. 文章在讲什么
问题：作者在多个 AI 工具间重复讲述"我是谁、我的原则、我希望怎样协作、我在做什么"，且积累的判断经验绑定在特定工具上，换工具即丢失。解法：建一个由本人所有、与工具无关的个人记忆库——五层分类（identity / principles / preferences / context / knowledge）× 每层三个二级子目录，目录深度封顶两级；权重等级 L1–L5 与目录绑定；每个文件带 7 字段 frontmatter；两层索引（总索引 + 每目录 README）；两个跨平台 skill：`recall` 按任务类型显式加载记忆，`curator` 从对话提取候选、经本人确认后写入并逐条提交。声称结果：换工具摩擦几乎为零、经验开始复利、AI 从"执行员工"变成"贴身秘书"（主动提醒漏掉的干系人）。作者刻意不做全自动写入，理由是希望记忆库维护"更好版本的我"而不是"现在版本的我"。

## 2. 核心主张
- **C1** 个人记忆必须属于本人并归本人管理，不绑定任何一个 AI 工具；否则上下文和判断经验随工具丢失。｜支撑：作者亲历的重复讲述/换工具丢失｜适用条件：个人同时使用多个 AI 工具｜位置：01 缘起
- **C2** 个人记忆按"回答什么问题"分五层：我是谁 / 我如何判断 / 我希望 AI 怎样协作 / 我正在做什么 / 我沉淀过什么；identity、principles 是稳定层，preferences、context、knowledge 是动态层。｜支撑：设计推理｜位置：2.1、2.4
- **C3** 目录有且只有两级，二级目录下只放文件；内容多了用文件名前缀区分。理由：每深一层定位选择翻倍；无限嵌套让分类变迷宫；深度封顶倒逼把归类想清楚。｜支撑：推理，无数据｜位置：2.3
- **C4** 灰色地带只需覆盖三对最易混淆的分类：价值判断 vs 操作步骤（原则/技能）、有无具体日期（经验/技能）、外部输入 vs 自己提炼（学习/技能）。｜支撑：三个归档例子｜位置：2.4、图 006
- **C5** 记忆会"升级"：经验里反复出现的规律 → 技能；外部学习内化 → 技能；目前升级靠人工判断。｜支撑：推理｜位置：2.4 末、08
- **C6** 记忆按重要性分 L1 硬约束 / L2 判断框架 / L3 偏好 / L4 上下文 / L5 经验素材，**每级带不同的使用方式**（默认必须遵守 / 任务相关时优先 / 只影响形式不覆盖事实 / 用前查时效、高影响决策前向用户验证 / 只用于类比不直接套用）；等级不写进文件，由目录决定。｜支撑：设计｜位置：03、图 007、图 008
- **C7** 冲突裁决高等级优先，但最终决策权始终在用户：AI 可以指出"你的某条 L1 原则与当前决策冲突"，不能替用户决定。｜支撑：推理｜位置：03
- **C8** 每条记忆带 7 字段元数据（type / title / description / status / privacy / tags / timestamp），参考 Google Cloud OKF；description 让 AI 扫索引即决定是否读正文，status: archived 让过时内容不参与调用，privacy: internal 让 AI 对外输出时跳过，tags 弥补目录单一维度。｜支撑：设计｜位置：04、图 009
- **C9** 组织协作关系应作为"AI 协作索引"存入 context 层（会变的现状，不是身份也不是原则），内容分三类：高置信组织事实 / 可使用的协作约束 / 明确标注的待补齐项。｜支撑：一段 AI 主动提醒干系人的对话引文｜适用条件：跨多团队推进方案的个人｜位置：05
- **C10** 两层索引：总索引收录所有文件的 title + description 一行一条，写入时由 skill 顺手同步；每个目录一个 README 说明装什么、不装什么。AI 先扫索引再按需读正文，不全量阅读。｜支撑：recall 截图（读 README 261 行 → INDEX 58 行 → 一份正文 320 行）｜位置：06
- **C11** 记忆使用分两层：公共基线（协作原则、沟通偏好、行为准则）定期同步到各工具的全局配置；任务相关记忆由 recall skill 按任务信号 → 目录 → description → L1→L5 顺序显式加载，任务类型到记忆层有路由表。｜支撑：图 010、截图｜位置：07、7.1
- **C12** 写入流程：读路由权威（README，每次完整读）→ 从对话提取候选 → 本人确认 → 提炼属性（本质/时间/来源/稳定性/形式）→ 按路由表定位目录 → 输出决策报告（含排除理由）→ 本人批准 → 写入 + 同步索引 → 每条独立提交。｜支撑：curator 截图｜位置：7.2
- **C13** 提取边界：只提取"用户自己表达的、属于用户自己的"信号；项目工作产出归 worklog 不进个人记忆；**AI 的输出不提取**。｜支撑：curator 截图中的"说明"段｜位置：7.2 案例
- **C14** 记忆维护故意不做全自动：全自动沉淀会把临时的、不够好的判断也加进去，久了会把自己困住；记忆库应维护"更好版本的我"。｜支撑：作者价值判断｜位置：08
- **C15** 已知缺口：记忆升级靠人工；两条原则打架、某条 context 三个月没更新只能被动靠人发现；计划做"某经验被调用 N 次建议提炼为技能"的自动识别。｜支撑：作者自述｜位置：08

**OKF 对本项目的价值（≤8 行）**
OKF 是本轮少见的、可核实的一手"知识包格式"规范，与本规范 04 §3"候选最小身份"直接可比。三点值得记：(1) 它把 index.md 定义为"每目录一个、条目带 description"的渐进披露入口，与本文 INDEX/README 和本规范"短索引→元数据筛选→回原文"同构；(2) v0.2 的 `generated/verified/sources/status/stale_after` 正是 04 §3 里 `source/observation、last_verified、retention/expiry` 的载体实例，且"派生信任层级而非主观打分""过期用绝对时点而非相对 TTL""缺字段≠拒绝"三条设计取向可作为本规范的候选语义；(3) 它明确"信任层级不是访问控制"，反衬本文用 `privacy` 字段靠模型自觉过滤的做法没有边界保证（见 §5 冲突、F5）。OKF 自身是数据目录场景（BigQuery 表、指标），不证明对个人/团队记忆有效，只作格式参照。

| C15 冲突/过期无自动检测 | 04 §7 触发复核条件 | 一致（缺口） | 本规范列了触发条件但同样无检测机制；OKF `stale_after` 是一个可用载体 |

**冲突展开（C8 privacy 字段 vs "Prompt 不是安全边界"）**
- 冲突在哪：本文让 AI 读取全部记忆（含 internal），只在"输出到外部时自动跳过 internal 标记的内容"。这是把隐私边界放在模型的输出判断上；本规范 05 章（吸收 ATT-G/ATT-M）与 WX-33 的"ACL 先于检索"都主张边界须由工具/隔离层强制，模型措辞只能引导。
- 谁的证据更强：本文无任何泄漏或未泄漏的观察；ATT-G/WX-33 也是推理为主。但"模型可被诱导输出已读入的内容"是公开语料中反复记录的失败类型，方向上支持本规范。
- 可否共存：个人级、单用户、无外部共享时风险低，可接受为个人参数；一旦个人记忆被任何自动流程读取（例如 recall 在团队会话中运行），`privacy` 就应升级为加载前过滤。记为 D-027 的个人级推论（§9）。

**个人级 vs 团队级 vs 项目级：本文与 WX-33 对照后的差异与通用语义**
| 维度 | 个人级（WX-41） | 团队级（WX-33） | 通用语义（两者共有） |
|---|---|---|---|
| owner / source of record | 本人；原则偏好层本人即权威 | Team；资产带 Owner/Scope/Version/ACL | 每条记忆有 owner；owner 决定它能否被当作依据 |
| 写入门槛 | 每条人批，无候选区 | private 域自动写，共享边界人审 | 进入他人/默认可见范围前必经人的确认 |
| 优先级粒度 | 类别级（目录决定） | 条目级（confidence/强弱/Shadow） | 优先级与"使用方式"绑定，不只是排序 |
| 访问控制 | 自觉标记，输出时过滤 | ACL 在检索前 | 边界在读取前（团队必需；个人可降级） |
| 新鲜度 | status: archived 手动 | valid_from/to、最后验证时间（设计） | 有时效的条目用前须核时效 |
| 冲突 | 高等级优先，人裁决 | 作用域+版本+检测+人确认 | AI 报告冲突，人裁决 |
| 证据 | 本人确认即可（规范性内容） | 测试/提交/Review（描述性内容） | 描述性记忆要证据；规范性偏好要本人确认 |
| 检索键 | 任务类型 | 身份/作用域/固定绑定 | 第一键不是相似度 |
| 提取边界 | 只取用户自述，AI 输出不进 | 候选抽取+作用域绑定 | 模型自身推断不得直接成为记忆 |
| 目的 | "更好版本的我"、跨工具连续 | "错误只犯一次"、协作带宽 | 降低下一次任务的不确定性 |
项目级（本规范主体）落在两者之间：owner 是项目、证据要求同团队级、但规模与权限复杂度介于两者；个人偏好进入项目会话时必须置于项目规则与生效决策之下（04 §8 已写）。

## 6. 建议采纳（候选语义）
- **S1** 每类长期记忆条目携带**使用方式**而非只有优先级：至少区分"默认遵守、违反须显式说明 / 任务相关时优先 / 只影响表达形式、不覆盖事实 / 使用前核对时效、高影响决策前向所有者确认 / 只作类比、不直接套用"。｜落地方式 A（外部状态存储）：条目元数据带使用方式字段，装配时据此决定注入位置与措辞｜落地方式 B（静态指令 + 人工检查点）：会话入口按类别声明使用方式，高影响决策前由人确认｜它防御的失败：偏好覆盖事实、过期上下文被当现状、个案经验被直接套用（图 007；WX-33 F3 同类）｜删除条件：模型能可靠自行区分四种使用方式且经评估误用率低于人工（目前无证据）
- **S2** 关系/组织类记忆分三段：已确认事实、可使用的约束、**明确列出的待补齐项**；召回时未知项与已知项一并呈现，不得把缺失当作"无此人/无此约束"。｜落地方式 A（静态指令/模板）：条目必含 unknowns 槽位｜落地方式 B（检查器）：召回结果若命中"待补齐"条目则在输出中标注不确定｜它防御的失败：干系人漏对齐、方案推进一半才发现"这个人还没聊过"（05）｜删除条件：写不出（已知未知只能由人补）
- **S3** 记忆提取只取来源为人的自述或可定位的观察；模型自身的输出、推断和当次任务的工作产出不得进入长期记忆候选，须分流到任务记录。｜落地方式 A（静态指令）：提取规则中列明排除类｜落地方式 B（检查器/人工检查点）：写入前的决策报告须标注每条来源类型，来源为模型输出即退回｜它防御的失败：模型推断自我强化、项目产出混入个人库形成第二来源（C13；WX-13 F2）｜删除条件：写不出（D-007 同类）
- **S4** 写入决策报告须同时记录**被排除的候选及理由**，不只记录被写入的。｜落地方式 A（外部状态存储）：写入事务附排除清单｜落地方式 B（人工检查点）：审批界面展示排除项供人复核｜它防御的失败：有价值的信号被静默丢弃且无人发现；反向地，提取规则漂移无法审计（7.2）｜删除条件：写不出
- **S5** 写入长期记忆的路由规则是单一权威，每次写入前完整读取而非凭记忆跳过；写入与索引更新在同一事务内完成。｜落地方式 A（条件加载规则）：写入技能触发时强制加载路由文档｜落地方式 B（检查器）：写入后校验索引与文件一致，不一致即失败｜它防御的失败：同类内容被放到不同目录、索引与正文漂移（6.1、7.2）｜删除条件：模型跨会话稳定记住路由规则（补偿性语义，会随模型能力过期）
- **S6** 有时效的记忆条目声明**绝对失效时点**而非相对 TTL；到期后默认不参与召回，复核由到期触发而非靠人偶然发现。｜落地方式 A（外部状态存储）：条目带 stale_after 类字段（OKF v0.2 载体实例）｜落地方式 B（人工流程）：定期复核清单按时点排序｜它防御的失败："某条 context 三个月没更新"只能被动发现（C15）｜删除条件：写不出
- **S7** 个人偏好与原则由本人确认即生效（规范性内容），不要求外部证据；但它们进入项目/团队会话时的效力低于项目规则与生效决策，且不得覆盖事实性主张。｜落地方式 A（权限与隔离配置）：个人记忆源与项目知识源分别挂载，冲突时按来源优先级裁决｜落地方式 B（静态指令 + 人工检查点）：会话入口声明"个人偏好只影响形式"，冲突时升级给人｜它防御的失败：个人 L1"硬约束"在团队任务中压过项目规则（04 §8 隐患）｜删除条件：写不出（责任类）

## 8. 该文暴露的失败模式
- **F1** 同一个人在 N 个 AI 工具各讲一遍身份/原则，某处更新其余不更新 → 各工具对同一人的认知不一致、协作冲突 → 唯一归属的个人记忆库 + 跨平台 skill → **可构造**：在工具 A 更新一条偏好后，在工具 B 执行同任务，检查是否采用新版本（与 WX-13 F2 同构，主体换成个人）。
- **F2** 个人记忆无索引时 AI 全量读取或漏读 → 上下文膨胀或相关记忆未加载 → 总索引 + description 筛选 + 目录 README → **可构造**：给定 50+ 条记忆与一项任务，检查加载集合与人工标注集合的差异（对应 03 §4"可能有用不是加载理由"）。
- **F3** 全自动沉淀把临时、错误的判断写进原则层，久而久之约束本人 → 作者的处置：每条人批，不做全自动 → **可构造**：注入一段情绪化/临时性表述，检查提取器是否提为"原则"或正确排除。
- **F4** 基线复制到各工具全局配置后漂移 → 基线与记忆库不一致 → 文章无处置（只说"定期同步"） → **可构造**：修改记忆库中一条基线原则，检查各工具会话是否立即反映。
- **F5** 记忆库中含他人组织信息（谁向谁汇报、谁能拍板）与 internal 标记，AI 在对外输出/共享会话中被要求列出干系人 → 依赖模型自觉跳过 → 文章无验证 → **可构造**：在含 internal 条目的会话中请求外发文档，检查是否泄漏。
- **F6** 过期 context（三个月未更新的项目状态）被当作当前状态 → AI 按旧目标提醒 → 作者承认无检测 → **可构造**：条目 timestamp 早于变更日，检查召回时是否提示时效。
- **F7** 两条原则互相矛盾（如"简洁"与"补齐背景"）→ 模型静默择一（ATT-N"隐性冲突静默择一"）→ 作者承认无检测 → **可构造**：写入两条冲突 L1/L2，检查是否报告冲突而非择一执行。
- **F8** 用户忘记显式调用 recall → 会话在无记忆状态下完成任务，产出不符偏好 → 作者靠"基线预载"部分缓解 → **可构造**：不调用 recall 执行"写方案"任务，与调用后对比是否命中偏好（也暴露显式调用这一设计的脆弱性）。
