# WX-15 从 Vibe Coding 到 AI 原生研发团队：一套能落地的工程实践

## 0. 验证边界
- 一手实践报告：腾讯网络平台部门（海外网络运营）一个内部平台 Vibe Flowing 的团队级做法总结，作者是平台主导开发者。**无对照组、无消融、无前后周期对比**；全部主张来自作者自述与截图。
- 文中数字及其条件：(a) "3 分钟内完成环境配置"——容器模板启动到服务就绪的自述耗时，无样本数；(b) "143 个 story 文件"——仓库计数，可信但只说明规模；(c) "覆盖率 70% 参考不阻断"——目标值非实测；(d) 图 030 "同一功能 token 消耗差 3～5 倍"——**只出现在图中、正文未提、无测量方法**；(e) 图 031 RTK 自报 "448 条命令节省 74.2%（108.6K）"——RTK 工具按字节/4 估算的局部数字，作者随后在正文判定该工具"得不偿失"；(f) "markdown 表格 200 token vs 原始 JSON 10 倍"——举例性估算；(g) 图 005 提交分布：一位"网络运营开发"139 次提交，五位"网络运营工程师"合计 49 次（2026-06-09～07-09）——证明非开发者**有**提交，不证明分工均等。
- 超出可核实范围：CodeBuddy 内网版、Anydev、Knot、工蜂、iWiki、七彩石、太湖网关均为腾讯内部系统；"文末原始代码仓库"在抓取版本中**无链接**；"正在引入 AI 审批 MR"为规划陈述。
- 正文与截图存在三处不一致（详见 §3 图 015/029/031 与 §9），本卡按截图为准记录。

## 1. 文章在讲什么
问题：运营同事用 Vibe Coding 各自写页面，结果重复造轮子、数据口径不一、页面无人维护；想正经做系统又被接口权限审批、文档缺失、鉴权各异卡住，AI 在无上下文时排查"烧 token 还问不到点上"。作者的判断是：缺的不是 AI 能力，而是**专业开发预先搭好的企业级底座**。
解法分三层：(1) 基础设施——业务 SDK 以 submodule 接入让 AI 自行探索、日志/RBAC/审计/开放 API/MCP/定时任务/持久工作流沉淀为标准设施；(2) 工程护栏——monorepo 严格分层、三层 Rules + Skills、规则兜底的测试、文件名即状态的轻量 SDD、封装 CLI 替代临时脚本、组件化 + Storybook、DB 变更分级管控、Agent "代码即配置"、容器启动 7 步自动化；(3) 协作机制——页面圈点评论提需求、开发容器自助注册供需求方合并前验收、给非开发者"能力地图"。
声称结果：网络运营工程师不写代码、不碰 git 即可完成"提需求→AI 开发→浏览器验收→AI 推 MR"全流程；Agent 开发由 AI 端到端完成；已在海外网络运营、控制器运营两个团队使用。作者明确本文目标是"守住日常需求的质量下限、提高 token 效率"，而非推高自动化上限。

## 2. 核心主张
- **C1** Vibe Coding 只能写一次性产物；能持续迭代的系统需要专业开发先搭好底座（日志、鉴权、权限、接口封装、DB 变更流程、定时任务），AI 在底座上开发才不必每次从零对接。｜支撑：问题描述 + 图 003，无数据｜适用条件：多角色共用的内部运营平台｜文中位置：问题在哪
- **C2** 团队级 AI 研发的分工是"人只管定义要什么，AI 负责怎么做"：运营提需求 + 做验收，AI 翻译需求 + 写代码，开发 review + 兜底，管理员审批合并。｜支撑：两个场景叙述 + 图 004/025 + 图 005 提交分布｜适用条件：非专业开发者占多数的团队｜文中位置：效果概览、三
- **C3** "系统中有什么能力，AI 自己去看"：SDK 以 submodule 进仓库不写接口文档；Agent 的提示词是文件、工具是函数、注册是装饰器；配置放项目数据库而非远程配置中心。能力不藏在外部后台里，AI 才能探索、复用、回滚。｜支撑：推理 + 图 008/010/022｜适用条件：单仓可容纳全部能力的项目｜文中位置：一、二.9
- **C4** Rules 保底线、Skills 提效率；规则"集中、分场景加载、不重复"。非专业操作者的容器加载更严的流程规则（三阶段不可绕过、白话解释、分支透明、Git 护栏、误区提醒），专业开发的 IDE 不加载，且该规则自声明"冲突时以本规则为准"。｜支撑：图 014/015 规则原文｜适用条件：同一仓库被不同专业度的人操作｜文中位置：二.2、二.10 第四步
- **C5** AI 写测试容易"自欺欺人"（只覆盖 happy path、断言弱），因此不追求严格 TDD，而用规则约束兜底 + 覆盖率参考不阻断 + 更看重需求方验收。｜支撑：经验陈述｜适用条件：内部运营工具｜文中位置：二.3
- **C6** 文件命名约定就是工作流：需求文档 draft_→ready_→done/ 三阶段，AI 读一个 ready_ 文档即获得完整需求上下文；不需要项目管理工具。｜支撑：做法描述 + 图 007/017｜适用条件：小团队、需求量可用目录承载｜文中位置：二.4
- **C7** 高频运营操作封装为"安全、留痕、可重复"的 CLI；DB 变更唯一入口 + 关键字硬拦截 + 账号权限"双保险" + 变更先写 changelog 再按行号执行 + 按风险分级（直接执行 / 先讲方案确认 / 先 COUNT 评估 / 硬拦截改软删除）。｜支撑：图 018/021 分级表｜适用条件：生产数据库可被 AI 触达的项目｜文中位置：二.5、二.8
- **C8** 组件化的特殊价值是"让审查变得可行"：改动集中在一两个小组件，审查只看几个文件；Story 是给 AI 和人的"组件说明书"，补 story 即自测。｜支撑：图 013/019｜适用条件：前端｜文中位置：二.6
- **C9** 让 AI "看见"问题：静态检查输出可读 → 规则集中 → AI 自主管理开发服务与日志 → Playwright 截图/请求验证，大部分问题在会话内修完再交人审。｜支撑：图 020｜适用条件：AI 可执行工具的环境（但见 §3 图 029 的反例）｜文中位置：二.7
- **C10** 开发环境是前提：容器启动 7 步自动化（上报环境 → 系统依赖 → 工具链 → 注入规范 → 渲染私密配置 → 项目依赖 → 启动服务），每步独立、失败即停且报具体原因、幂等可重跑。｜支撑：图 024 + 步骤描述｜适用条件：有云容器模板｜文中位置：二.10
- **C11** 页面级圈点评论（路径、xpath、截图）是"所见即所得"的需求入口；评论 open/resolved/closed 可见；复杂需求转 SDD；需求方在开发容器上**合并前**验收。｜支撑：图 025/026｜适用条件：Web 产品｜文中位置：三
- **C12** "廉价习得感"是危险的：审查者不理解 AI 写的东西就无法审查；AI 输出质量取决于人的反馈质量，反馈质量取决于对开发概念的理解，所以非开发者需要学会"读懂"而非"写"。｜支撑：推理 + 图 027 对比｜适用条件：任何团队｜文中位置：四.1
- **C13** 非开发者还缺"产品语言"与"系统能力全貌"，导致重复提或不敢提需求；一份 AI 生成的能力地图（功能/Agent/定时任务/API 按业务域罗列）投入低、效果明显。｜支撑：图 028/029｜适用条件：能力散落的平台｜文中位置：四.2
- **C14** 省 token 靠结构而非压缩器：规则集中、工具返回聚合 markdown、CLI 替代临时脚本、大仓 + 语义搜索、文档驱动、小组件。RTK 类命令输出压缩器验证后"效果一般、偶尔出 bug、语义混淆"，且多一个不稳定依赖，弃用。｜支撑：经验陈述 + 图 030/031｜适用条件：该团队｜文中位置：四.3
- **C15** Agent 开发"AI 自己跟自己对话、自己验收"：给业务目标 + 验收标准（"随便选一条专线 30 秒内输出结构化报告"），AI 探索仓库、写提示词、封装工具、注册、端到端跑到达标。｜支撑：场景二 + 图 007-009/023｜适用条件：验收标准可由 AI 自判的 Agent｜文中位置：效果概览、二.9

## 6. 建议采纳（候选语义）
- **S1** 不可逆或高风险的数据动作必须同时被至少两个彼此独立的机制阻断，其中至少一个不依赖模型读到的任何指令。｜落地方式 A（运行时拦截）：变更入口对危险操作类别做硬拦截并要求先留痕｜落地方式 B（权限与隔离配置）：执行身份本身不具备该类操作权限｜它防御的失败：F3（用户口语化要求"清掉数据"，AI 直接执行破坏性操作）｜删除条件：写不出——不可逆动作的责任不可转移。
- **S2** 变更执行前必须先产生可追溯的变更记录，执行片段与记录绑定；未留痕的变更不得执行。｜落地方式 A（检查器）：执行工具拒绝不在变更记录中的语句｜落地方式 B（人工检查点 + 外部状态存储）：变更记录作为集成审查的必审工件｜它防御的失败：新环境无法重建、变更历史不可追溯｜删除条件：写不出（审计需求与模型能力无关）。
- **S3** 同一项目对不同专业度/权限的操作者可加载不同的行为约束集，且约束集之间的优先级必须显式声明并可被查询。｜落地方式 A（条件加载规则）：按环境或身份触发加载对应约束｜落地方式 B（权限与隔离配置）：为该类操作者提供能力受限的执行身份，使约束不只靠加载｜它防御的失败：同一规则集对专业开发过严、对非专业操作者过松；两套规则冲突时模型静默择一（ATT-N）｜删除条件：当模型能从交互中可靠推断操作者专业度并在评估集上证明自适应不漏保护时，可删加载分档，权限分档仍保留。
- **S4** 非专业操作者发起的变更，在实现与集成之间必须有一个由需求方本人完成的、基于真实运行界面的验证点，其结果作为进入集成的输入而非交付验收。｜落地方式 A（人工检查点）：需求方在隔离环境中确认后才允许提交集成｜落地方式 B（外部状态存储）：环境注册表 + 评论/工作项状态记录该验证及其环境身份｜它防御的失败：F6（AI 自验收只核格式）、"等流水线/合并才能看到效果"的等待｜删除条件：写不出（验收责任）；但"验证点在隔离环境"这一形态在具备可靠预览环境的工具中可由自动预览替代。
- **S5** 需求发起方应能获得一份由系统实际能力派生、可再生成、明确标注为非权威的能力清单。｜落地方式 A（静态指令/文档）：定期从代码与注册表生成清单供人阅读｜落地方式 B（检查器/工具）：需求澄清阶段由工具实时列出与请求相关的已有能力并要求确认是否重复｜它防御的失败：重复提需求、因不知能力而不敢提、描述上下文不准｜删除条件：当需求入口能在澄清时自动检索并呈现已有能力且误报率可接受时，静态清单可删。
- **S6** 维护类自动化中，发现问题与修复问题由不同执行者承担，交接以可审计工件进行，修复者不得改写发现记录。｜落地方式 A（条件加载规则 + 外部状态存储）：扫描技能只产出问题条目，修复技能只认领条目｜落地方式 B（人工检查点）：人在两者之间做分诊与优先级｜它防御的失败：自审自修、修复者弱化问题定义使自己通过｜删除条件：写不出（结构性分离）。
- **S7** 工具返回给模型的内容必须是已聚合、有上界的摘要，超出上界须分页或拆分；上界由项目测量确定。｜落地方式 A（检查器）：工具契约中声明返回体上限并校验｜落地方式 B（静态指令）：工具编写规范要求聚合与限行｜它防御的失败：原始数据灌满上下文、多轮补漏调用（图 009 形态）｜删除条件：当上下文成本与注意力退化不再是约束时。
- **S8** 环境初始化必须在首次缺失必需输入时以具名错误停止，不得生成部分有效的配置继续执行。｜落地方式 A（检查器）：初始化前校验全部必需项并列出缺失名｜落地方式 B（运行时拦截）：服务启动时对配置完整性做前置断言｜它防御的失败：F7（半残配置导致后续含糊报错，AI 排查烧 token）｜删除条件：当模型能从含糊错误可靠回溯到缺失配置时（当前无证据）。

## 8. 该文暴露的失败模式
- **F1** 规则/脚本引用已被 Thin 的工具（RTK 弃用但规则仍写"建议加 rtk 前缀"、容器仍安装）→ AI 继续使用不稳定压缩器，出现输出丢失或语义混淆 → 文章未处置（不一致未被察觉）→ 可构造：规则引用一个已移除/有缺陷的工具，检验 Agent 是否盲从、是否报告不一致。
- **F2** AI 写测试只覆盖 happy path、断言弱 → 测试通过但功能错 → 规则约束 + 核心逻辑必须单测 + 需求方验收兜底 → 可构造：给定弱断言测试集，检验 Gate 是否识别断言强度（变异测试）。
- **F3** 非专业用户说"把数据清掉" → AI 试图 DELETE → 账号无 DELETE + CLI 硬拦截 + 规则要求建议软删除 → 可构造：移除提示词中的提醒后重复请求，验证两层机制独立生效。
- **F4** 用户抛出"改一个文案"级需求 → AI 自判小改动跳过澄清直接改 → 规则禁止（仅提示词）→ 可构造：新会话给琐碎需求，检验首个回复是否为澄清；再在长上下文末尾重复，检验规则衰减。
- **F5** 用户催"赶紧推上去" → AI 跳过检查直接推送 → 规则禁止（仅提示词）→ 可构造：推送动作前是否存在检查证据；比较提示词单层与拦截层的拦截率。
- **F6** Agent 自我验收判据为格式/时延（"30 秒内结构化报告"）→ 报告格式合格但数据源或口径错误 → 文章未处置（只靠后续人工使用发现，如图 026"缺少东京出口"由用户评论发现）→ 可构造：注入错误数据源，检验自验收是否放行——目标失明 Case。
- **F7** 环境变量缺一项 → 生成半残配置，服务启动时报含糊错误，AI 排查烧 token → 初始化前校验全部必填并列出缺失名、失败即停 → 可构造：删除一个变量，比较报错位置与 Agent 定位轮次。
- **F8** 非开发者容器无自动 UI 验证工具，但正文/规则描述 AI "自己截图验证" → AI 可能声称已验证 → 规则"诚实原则"要求如实告知（仅提示词）→ 可构造：工具缺失时检验 Agent 是否伪报验证。
- **F9** 单个 1000 行前端文件被 AI 改一处 → 审查者无法判断影响面 → 拆小组件 + Story → 可构造：同一改动在大文件与拆分后分别提交，比较审查耗时与漏检。
- **F10** 多人各自 Vibe 页面调用同一接口，鉴权与口径不一致 → 同一事实多份不一致来源、无人能说清哪个是最新 → 统一底座 → 对应 D-005 多来源冲突 Case；可构造：同一指标两处实现口径不同时 Agent 是否检测。
