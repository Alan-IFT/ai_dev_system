## 1. 文章在讲什么
问题：日常工作里有大量"不值得专门开发工具"的小痛点（内部系统查询繁琐、调试链路长、手机代理配置、发布盯盘），过去因成本高被放弃。作者的解法：AI 把定制软件的成本压到"数小时"，于是把每个痛点都做成了一个个人工具（8 个，跨 Tauri/浏览器插件/VSCode 插件/移动 App/看板）；用 Yak Shaving（薅牦牛毛）和 Anthony Fu 的开源之路解释"痛点就是需求文档"；再讲三条 LLM 原理推出的 Prompt 技巧和三条开发技巧（先规划再行动 / Debug Mode 用真实日志排查 / worktree+tmux 并行）。作者声称的结果：单人业余时间完成跨多技术栈的全栈工具；Debug Mode 把"多轮对话修不好"的问题一次修好；未来是 Karpathy 所说的"即用即走"定制应用。**本文的独特价值不在技巧（已由 ATT-K 吸收），而在 §02 这份"个人级工具清单"——它是一个真实开发者在 AI 时代自己长出来的 Harness 组件目录，可用来检验本规范的层是否覆盖了实践者真正在造的东西，以及"造工具变便宜"对 D-013/D-026 意味着什么。**

## 2. 核心主张
- **C1** AI 重定义了工具开发的成本结构，过去"不值得做"的小工具现在值得一试。｜支撑：8 个自建工具案例；无成本数据｜适用条件：个人、单用户、低风险工具｜文中位置：01、02
- **C2** 痛点识别方法：把工作中"让你不舒服的点"（Yak Shaving 链条上的每一环）当作需求文档，用 AI 把阻力转化为工具。｜支撑：Anthony Fu 开源之路类比（i18n Ally→VueUse→composition-api→Vite）｜适用条件：个人开源/内部工具｜文中位置：03
- **C3** AI 暂时覆盖不到的领域（私有 DSL 高亮补全、内部广告调试、代理配置）同样适合让 AI 来**造**工具。｜支撑：DSL 插件、公众号开发者工具、Easy Proxy 三例｜文中位置：02
- **C4** LLM 是 Token 概率预测，无绝对数值概念；三条推论：用公开语料里的词而非私有黑话、单轮单任务、产出必须 Review。｜支撑：原理推理 + "0.11 vs 0.9"例子；无实验｜文中位置：04（已由 ATT-K 吸收）
- **C5** 复杂任务先让 Agent 充分理解需求再动手；三种规划方案中推荐 Superpowers，理由是**心智成本低**（只需记住"脑暴"，Skill 自动触发）。｜支撑：作者偏好；图 014 摘自 Superpowers README｜文中位置：05 技巧一
- **C6** 多轮描述式排查会陷入"修好了→还是不行"循环；Debug Mode 用"列假设→自动插桩→复现收日志→定根因→清理插桩"的闭环让 AI 掌握真实运行情况。｜支撑：作者自述"几次多轮修不好的问题一次修复通过"（无计数、无对照）；图 015–018 为一次真实排查截图｜文中位置：05 技巧二
- **C7** 等待 AI 是低效源；用 worktree（隔离目录）+ 多窗口（独立 Agent 上下文）+ tmux（服务器端会话不断线）并行推进多任务。｜支撑：作者经验｜文中位置：05 技巧三
- **C8**（引 Karpathy）"应用商店"模式在过时，未来是 LLM 编排传感器/执行器而成的高度定制、即用即走的应用。｜支撑：Karpathy 2026-02-20 推文｜文中位置：06
- **C9**（图 014 有、正文没有）Superpowers 是"强制工作流，不是建议"；分支隔离在设计审批后激活并**验证测试基线干净**；计划把任务拆成 2–5 分钟粒度，每个任务带验证步骤；代码审查"在任务之间激活"，Critical 阻断。｜支撑：README 原文｜文中位置：图 014
- **C10**（图 004/007/010 有、正文弱化）作者的内部工具里反复出现同一种结构：**自然语言 → 内部系统结构化查询**（广告日志"AI 查询"带 Debug 开关）、**在真实运行环境原地观察**（公众号页面长按弹开发者菜单、发布期看板对比一天前）。｜支撑：截图｜文中位置：02

**Superpowers 的价值**：它是本文推荐方案，也是一个已被多工具采用的"整条交付闭环写成 Skill"的实例：脑暴（意图澄清）→隔离工作区 + 干净基线（READY）→带验证步骤的小任务（带验收的工作项）→子代理两阶段审查（先 Spec 合规再代码质量，审查者与实现者分离）→TDD→严重级阻断→完成时给出 merge/discard 选项并清理。对本项目的意义有二：(a) 证明本规范的交付闭环可以被一个跨工具载体承载；(b) 它自称"强制工作流"，但强制手段是**指令文本**（Skill 说明），不是运行时拦截——按 ATT-G/M"Prompt 不是安全边界"，它的"强制"是提醒级，作者选它的理由（心智成本低）也印证它优化的是人的记忆负担而非执行保证。

**Cursor Debug Mode 的价值**：它把 D-003（两次无新证据就停）之后"该做什么"具体化了：先枚举可证伪假设，再让运行时给证据，且**人**执行复现。三处细节值得抽象：插桩带统一标记、写入独立采集端、修完必清——这使"临时观测代码"有明确的生命周期，不会残留成第二套日志。

**Anthony Fu Yak Map 的价值**：它是"Harness 应从任务中生长"（00 §7）的一张可视化证据——每个节点都由上一个任务的摩擦催生，没有一个是先建平台再找场景。

## 6. 建议采纳（候选语义）
- **S1** 一次性工件（为当次任务生成、用后即弃的脚本/查询/看板）不进入常驻 Harness；只有**同一类一次性工件被重复生成**时，才成为 Add 候选，且以"被重复生成的次数与场景"作为来源 Case。｜落地 A（外部状态存储）：记录每次即席生成的工件类型与触发场景，定期聚类找重复｜落地 B（人工检查点）：任务收尾时人回答"这次临时造的东西下次还会造吗"，是则登记候选｜它防御的失败：把每个即席脚本都固化进 Harness 导致膨胀；或反过来，同一脚本被手工重造十次却从未沉淀｜删除条件：写不出（这是治理规则，不依赖模型能力）
- **S2** 任务执行中遇到的、与当前工作项目标无关的阻力（Yak Shaving 环节），执行者应**记录为改进候选而非现场解决**；现场解决需要范围变更批准。｜落地 A（外部状态存储）：工作项附带"摩擦记录"，进入改进闭环｜落地 B（运行时拦截 / 检查器）：变更触及工作项声明范围之外的工件时阻断或告警｜它防御的失败：Agent 为修一个顺手看到的问题偏离切片，PR 混入无关改动、验收 ID 对不上｜删除条件：模型能可靠地自我判定范围并主动请求变更批准（当前无证据）
- **S3** 进入实施前，必须先在隔离的工作副本上取得并记录**验证基线**（当前哪些检查通过/失败），否则无法区分新引入的故障与既有故障。｜落地 A（检查器）：任务启动脚本运行现有验证并把结果绑定到工作区身份存档｜落地 B（人工检查点 / 静态指令）：执行者在 READY 转换记录里填写基线摘要，缺失则不得进入 IMPLEMENTING｜它防御的失败：把既有红灯当作自己造成的并"修复"，或把自己造成的红灯当作既有噪声忽略｜删除条件：工具能自动为每次改动给出"相对基线的差异"报告且被证明可靠
- **S4** 故障排查在止损触发后（D-003）必须转入**证据驱动模式**：(1) 先写出可证伪的假设列表；(2) 通过临时观测（插桩/日志/断点）获取运行时证据，临时观测必须**可识别、可机械清除**，修复确认后清除；(3) 复现步骤明示，由人或可信执行环境执行，不接受模型自述"已复现"。｜落地 A（运行时拦截 / 检查器）：产品内置的调试模式或提交前检查"无残留观测代码标记"｜落地 B（Runbook + 人工检查点）：排查 Runbook 规定三步顺序，人执行复现并判定 Fixed/Proceed｜它防御的失败：图 015 的"修好了→还是不行"循环；观测代码残留成第二套日志｜删除条件：模型能在无人参与下可靠复现并自证根因（D-023 现实锚点要求至少一个非模型节点，故此条只能部分删除）
- **S5** 私有领域词汇（内部 DSL、内部系统名、业务黑话）不能指望模型认识：要么映射为公开概念，要么作为带定义的项目知识供检索，且能用确定性工具校验其用法。｜落地 A（条件加载规则）：按文件类型/路径加载术语定义｜落地 B（检查器）：DSL 校验器/补全器给出"未知词"信号｜它防御的失败：模型把私有词按公开语料里的近义词理解（图 008 的 "Wecom: Unknown word" 即信号）｜删除条件：项目私有词汇进入模型可访问的检索并被证明召回可靠——只能删"映射"半边，"定义必须由人写"不可删（D-020 判据一）

## 7. 明确不采纳
- "交付周期从数周缩短到小时级"、"开发者 60% 时间读文档与调试"、"一次修复通过"——数字外推 / 无来源 / 无对照。
- Tauri、GeminiCli、Notion、Chrome 扩展、VSCode 插件、tmux、Git worktree、Superpowers/SpecKit/OpenSpec/Plan Mode 的选型——载体绑定。
- "推荐 Superpowers 因为心智成本低"——只适用于个人项目；团队项目的选型判据应是可审计与可验证，不是记忆负担。
- "不要用私有领域黑话"作为规则——只适用于可以自由选公开技术栈的个人小工具；大项目的私有词汇必须定义而非回避（见 S5）。
- "痛点就是需求文档"作为需求方法——对个人工具成立；对大型项目，痛点只是候选，仍需经意图层（目标/非目标/负责人）确认。
- Karpathy"应用商店过时"作为规范依据——观点评论，无证据。
- 8 个具体工具本身——全部为该作者在该内部系统上的私有工件。

## 8. 该文暴露的失败模式
- **F1** 用自然语言描述 bug 让 AI 修 → AI 连续三轮宣称"已修复/已明确根因"但错误依旧（图 015） → 文章处置：切换到 Debug Mode，先列假设再插桩取日志 → **可构造**：给定一个需要运行时状态才能定位的 bug（如竞态、选区覆盖），grader 检查执行者在第二次失败后是否产生新观察而非再次改代码。
- **F2** 私有 DSL 文件中的表达式（`$scope`、`$const`、`valueExpr`）无公开语料支撑 → 模型/编辑器把私有词标为未知或按近义理解（图 008） → 文章处置：造确定性补全/校验插件 → **可构造**：让执行者修改一段内部 DSL，grader 检查是否先检索术语定义或使用校验器，而非凭猜写表达式。
- **F3** 一次性脚本被反复重造（Genie"脚本大师"每次现写导出脚本） → 同类脚本第 N 次生成 → 文章无处置（视为正常） → **可构造**：轨迹级 Case，统计同一场景下即席生成同类工件的次数，超过阈值未沉淀即判失败（阈值是载体）。
- **F4** 排查用的临时插桩修完未清理 → 残留 `agent log` 写到本地端点 → 文章处置：Debug Mode 第 4 步清理 → **可构造**：提交前检查器扫描标记；grader 检查修复提交是否包含观测代码。
- **F5** 并行多个 worktree 时窗口/会话被关闭 → 对话上下文丢失 → 文章处置：tmux 常驻 → **可构造**：中断恢复 Case——杀掉会话进程后，执行者能否只凭持久工件恢复（本规范原则）而非依赖进程存活。
