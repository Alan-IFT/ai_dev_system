## 1. 文章在讲什么
问题：让 Agent 操作一个真实的数据平台（DES：工作流导入/调试/发布、DQC 规则、SQL 任务）时，prompt 约束是软的，Agent 会跳步、乱序、丢字段、误调高风险工具。作者的解法是四层叠加：MCP 层通过部门 MCP 市场把 72 个 REST 接口自动注册为工具（"能操作什么"）；Skills 层用 8 个 Skill、以 Mermaid 流程图写 SOP 并规定"写工具必须先走对应 Skill"（"怎么操作才对"）；Hooks 层在工具调用前/后/会话开始三个拦截点，用 ~170KB Python 脚本做四级安全分级、9 步校验流水线、tier 条件链字段校验与自动补全、审计与经验记录（"被允许怎么操作"）；多平台层用 Monorepo + symlink 让 Python（IDE）与 JavaScript（iMate 网页/企微机器人）两套 Hook 共享同一份 rules.json 与 context.md（"规则在哪生效"）。作者声称的结果：Agent 跳步乱序"显著减少"（主观）、安全边界不再依赖 prompt、规则改一处双平台生效；并提出把这套方法固化为"Agent Plugin Factory"元工具（尚在验证）。结尾引用"Prompt → Context → Harness → Loop → Graph Engineering"演进链并提出开放问题：Agent 是否知道自己知道多少。

## 2. 核心主张
- **C1** MCP、Skills、Hooks 分别回答三个不同问题：能操作什么 / 怎么组合调用才正确 / 被允许怎么操作（安全边界在哪）；三者是叠加而非替代。｜支撑：推理 + 图 001｜适用条件：Agent 操作一个有状态的业务平台｜文中位置：01、07
- **C2** MCP 三原语的加载策略不同：Tools 启动时批量注册并注入 system prompt，Resources/Prompts 惰性按需拉取；把大量只读参考数据（150+ 张表 schema）放 Resources 而不是 Tools，可避免 system prompt 被填满。｜支撑：对比表 + 图 002；无 token 数据｜适用条件：CodeBuddy 客户端的加载实现｜文中位置：2.1
- **C3** 自建 MCP Server 中间代理的真实成本不是"做不出来"，而是横切关注点（AOP/并发/异常）二次实现 + 独立服务的构建/部署/监控；用已有基础设施（上传 OpenAPI 自动注册）优于自建。｜支撑：团队亲历，图 003｜适用条件：后端已有 REST + Swagger｜文中位置：2.2、2.3
- **C4** 多步业务流程是有向无环图；靠 LLM 自由编排会跳步、乱序、遗漏错误处理；SOP 用 Mermaid 流程图比纯文本步骤列表更能让 Agent 理解顺序依赖、条件分支和回退路径。｜支撑：作者主观感受，明确无量化对照；图 004｜适用条件：5～6 步、有失败分支的部署流程｜文中位置：3.1、3.2
- **C5** "强制走链"（写工具前必须先走完对应 Skill）是**推理层纪律**，写在行为规范中，不由 Hook 代码拦截；Hook 只负责安全分级。｜支撑：设计陈述 + 图 005（图注"非 Hook 层代码拦截"）｜适用条件：该团队的分工选择｜文中位置：3.3
- **C6** Hook 是框架在 tool call → 实际执行路径上注入的同步拦截点，运行在 Agent 控制流之外的独立进程，Agent "无法绕过也无法说服"；返回结构化控制字段（放行/拦截、是否弹窗、改写入参）。｜支撑：机制描述 + 图 006｜适用条件：宿主框架提供该拦截点｜文中位置：4.1
- **C7** 安全分级应是渐进式四级（静默放行 / 静默审计 / 弹窗确认 / 不可逆标注+慎重确认），而非二元允许/拒绝；绝大多数调用零开销，只在少数关键节点打断人。｜支撑：图 007（5/31/40 工具分布）｜适用条件：查询类工具占多数的平台｜文中位置：4.2
- **C8** 校验逻辑与规则数据分离：9 步流水线代码不硬编码规则，全部规则外化到 18 段配置；新增规则只改配置。｜支撑：图 008、图 017｜适用条件：单团队维护｜文中位置：4.3、6.1
- **C9** 字段校验需要**条件链**（tier）：无条件必检 → 某字段满足条件时追加校验 → 再下探；区分"必填非空"与"必填可空"；批量工具在 tier 之上叠加逐元素校验；不做"万能校验引擎"。｜支撑：DQC 4 层 tier 表、图 009｜适用条件：嵌套、条件依赖的写接口｜文中位置：4.4
- **C10** 更新类工具在参数不完整时，不应直接放行也不应只拒绝，而应引导 Agent 先调用关联的读工具拉取当前对象状态再对比，避免"残缺参数覆盖完整数据"。｜支撑：`_get_tool` 机制描述 + 图 009｜适用条件：部分更新会整体覆盖的 API｜文中位置：4.4.2
- **C11** 多平台一致性不做抽象层，靠"单一配置源 + 文件系统级 symlink"保证；两套不同语言的 Hook 读同一份规则。｜支撑：目录树 + 图 016；Windows 需开发者模式、有复制 fallback｜适用条件：Monorepo、两个宿主｜文中位置：5.2、5.3、07
- **C12** 给任意 API 服务生成安全可控 Agent 插件的方法可以固化为元工具：解析 OpenAPI → 按 HTTP 方法自动分级（DELETE→blocked、POST→warned、GET→audit、其他→pass-through）→ 检测分页接口 → 模板生成双平台插件。｜支撑：设计陈述，作者自述"还在开发验证阶段"｜适用条件：REST + Swagger 服务｜文中位置：6.2
- **C13** 模型能力已过门槛，剩下的是工程问题（边界、流程、多平台同步）；"安全边界不靠 prompt 保证，靠工程架构保障"。｜支撑：全文推理｜适用条件：—｜文中位置：07

**冲突一（C5 vs D-008）**：文章把"写工具前必须先走完 Skill"这一**完全可判定**的前置条件（可以检查会话内是否执行过该 Skill / 是否存在其产物）有意留在自然语言规范里，理由是"Hook 层负责的是安全分级"。D-008 与 05 章 §1 的立场是可确定判断应下沉到程序或 Gate。谁的证据强：文章只有设计陈述，且图 013 恰好展示了推理层纪律失守的样子——模型知道"删除前通常需要先下线"却"先按你的要求来"。可否共存：可以，把它读成分层选择——纪律先放推理层（成本低、可观察违规率），当观察到跳链事故后再下沉为拦截（D-013 按真实失败 Add）。这不否定 D-008，而是给 D-008 补一个"下沉时机"问题。

**冲突二（fail-open 默认 vs 08 章保守默认）**：9 步流水线里"工具名无匹配 → 直接放行"，Plugin Factory 里"其他 HTTP 方法 → pass-through"。本规范 D-014 的反例推演把"空集合"判为 UNDETERMINED、08 章把默认值定为偏向阻断。谁的证据强：文章无事故记录，仅是实现选择；本规范的立场来自风险不对称推理。可否共存：文章的分级是"按工具名白名单"，本规范要求的是"未知动作不得被解释为已通过"——两者在"新增工具未登记"这一情形下直接对立，无法共存，应记为本规范的一个可构造 Case（§8 F3）。

**冲突三（自动经验写入 vs D-007）**：PostToolUse 自动把每个工具的执行经验写入 experiences/{tool}/（TTL 30 天），SessionStart 自动把 recent/、preferences/ 注入上下文——AI 观察未经任何人审批就进入下一会话的默认上下文。D-007 要求 AI 只能提出候选、由所有者审批后写入；04 章 §4 要求候选区与晋升分离。谁的证据强：文章对这一机制只有图注和配置段名（failure_tips 5 条、recent_categories 9 类、TTL 30 天），无失效或污染案例；本规范的立场也是推理。可否共存：可以按范围区分——文章写入的是"工具级操作经验 + 最近操作对象"，带 TTL、按工具隔离，接近 04 章的"情节记忆候选"而非"项目知识"；只要它不进入权威知识、且注入时标明来源为自动记录，与 D-007 不矛盾。需要在 04 章补一句"带 TTL 的自动情节记录允许免审进入按需上下文，但不得免审晋升"——这是待决策。

## 6. 建议采纳（候选语义）
- **S1** 对 Agent 的约束分三种性质：**能力目录**（Agent 可调用的动作及其副作用声明）、**方法约束**（正确的调用顺序、前置条件、失败分支）、**执行边界**（动作发生前后由模型不可影响的路径强制的放行/审计/确认/拒绝）。规范条文须声明自己属于哪一种，同一条要求可同时以方法约束和执行边界两种形态存在。｜落地方式 A（条件加载规则）：方法约束以按任务触发的操作说明加载，含顺序、分支与回退｜落地方式 B（运行时拦截）：执行边界在动作前介入，按动作风险等级决定放行/记录/人确认/拒绝｜它防御的失败：本文 3.1 的跳步、乱序、遗漏错误处理，以及 4.1 的丢字段、误调高风险工具｜删除条件：模型在无 SOP 情况下的多步业务流程跳步率与有 SOP 时无差异（需评估集）；执行边界部分不因模型能力删除（责任判据）
- **S2** 执行边界必须位于模型无法影响的路径上：拦截逻辑不与模型共享推理过程，其判定不接受模型的自然语言说服，其存在不依赖模型是否"记得"。｜落地方式 A（运行时拦截）：宿主在动作请求与实际执行之间的独立检查进程｜落地方式 B（权限与隔离配置）：目标系统侧的凭证范围/沙箱使不被允许的动作在协议层不可达｜它防御的失败：ATT-G/ATT-M 已述"prompt 约束被自信的 Agent 绕过"；图 013 模型知道前置条件仍按用户要求跳过｜删除条件：写不出（责任与不可逆授权不因技术进步消解，09 章 §2）
- **S3** 动作风险分级须是多档而非二元，且人工确认只保留给不可逆或高影响动作；每一档必须声明对人的打断形式（无、事后可查、事前确认、事前确认并标注不可逆）。｜落地方式 A（运行时拦截 + 人工检查点）：按动作类别在动作前弹出确认，确认框必须显示目标环境、受影响对象与不可逆性｜落地方式 B（权限与隔离配置 + 外部状态存储）：不可逆动作在默认凭证下不可用，需单独授权并留审计记录｜它防御的失败：D-024 所述"判不动的 Gate 等于没有"——若 72 个工具全部弹窗，人会全部点允许｜删除条件：写不出（同 S2）
- **S4** 未登记/未分类的动作不得默认放行：执行边界对未知动作的默认判定必须是"需要人确认"或"拒绝"，而不是"无匹配即通过"。｜落地方式 A（运行时拦截）：分级表以外的动作名一律进入确认档｜落地方式 B（权限与隔离配置）：目标系统侧只授予已登记动作的凭证，未登记动作在协议层不可达｜它防御的失败：§8 F3——新工具上线但规则未更新，模型调用后静默放行｜删除条件：能力目录与分级表由同一来源自动生成且有一致性检查时（本文 Plugin Factory 的方向），此规则可降为检查器
- **S5** 更新类动作在参数不完整时，边界层应引导先**回读目标对象的当前状态**再重新提交，而不是直接拒绝或直接放行；部分更新不得在未见当前状态的情况下整体覆盖。｜落地方式 A（运行时拦截）：拦截返回"缺少字段 X，请先读取对象 Y"，模型补齐后重试｜落地方式 B（检查器 / 工具接口设计）：写接口要求携带上一次读取的版本标识，版本不符即拒绝（乐观并发）｜它防御的失败：4.4.2 所述"残缺参数覆盖完整数据"，如 taskDefinitions 缺失导致画布清空｜删除条件：目标系统全部写接口为幂等的局部更新且带版本校验时
- **S6** 边界层对被拒绝动作的反馈必须是**可操作的结构化信息**（缺什么、应先做什么），使模型能在一轮内自行纠正；拒绝不是终点而是回边。｜落地方式 A（运行时拦截）：deny 附带缺失字段清单（图 012 一轮纠正）｜落地方式 B（检查器）：schema 校验失败输出到字段级的错误定位｜它防御的失败：模型面对无信息拒绝时反复试错（D-003 场景）｜删除条件：写不出（属 07 章 §6 ACI 的一般要求）
- **S7** 多宿主部署时，规则数据与执行代码分离：规则只有一个来源，各宿主的执行代码各自实现但读同一来源；分发副本与来源之间须有一致性检查。｜落地方式 A（外部状态存储 + 检查器）：单一规则文件/表 + 部署前一致性校验脚本｜落地方式 B（人工流程）：规则变更走单一评审入口，各宿主实现者按变更记录同步并签字｜它防御的失败：两个宿主规则漂移，同一操作在 IDE 被拦、在 IM 机器人放行｜删除条件：所有宿主共享同一执行运行时时
- **S8** 人工确认点必须向人展示**目标环境与受影响对象**，而非只展示动作名；环境标识来自目标系统地址等可观察事实，不来自模型陈述。｜落地方式 A（运行时拦截）：拦截层从调用目标推断环境并写入确认文案（图 008 S8）｜落地方式 B（外部状态存储）：会话创建时固化环境为不可变范围并在每次确认中回显（D-027）｜它防御的失败：人在确认框里看到"删除工作流"却不知道是生产还是测试｜删除条件：写不出（责任判据）

## 7. 明确不采纳
- 四级分级的具体档数与 5/31/40 的工具分布——只适用于该平台的接口构成（查询类占多数）；载体绑定。
- 9 步流水线的步骤划分、18 段配置的段名与分组、rules.json/context.md/audit_logs 等文件形态、Python/JS 双实现、symlink 与 init 脚本——全部为载体实例，可进附录。
- "Tools 启动时注入 system prompt、Resources 惰性"作为通用规则——这是 CodeBuddy 客户端行为，规范中 Prompts 为用户触发、Resources 为应用控制；且 MCP 2026-07-28 后加载/缓存语义已由协议的 ttlMs 决定。
- Mermaid 流程图优于文本 SOP——作者明示无对照；"图状 SOP 让分支显式"可作探测提示，不作要求。
- 按 HTTP 方法自动分级（DELETE→blocked 等）——动词不等于后果，无验证；与 D-021 "规则须绑定失败"不符。
- "Agent Plugin Factory"——作者自述开发验证阶段，无运行证据。
- 图 007 "95%+ 零开销"、截图中的 token/credits 数——无测量条件，不外推。
- "Prompt → Context → Harness → Loop → Graph" 演进链——003 §4 已判定不作分期标准。
- 结尾关于 Agent 群体智慧、"Agent 是否知道自己知道多少"的提问——开放式，无可采纳内容。

## 8. 该文暴露的失败模式
- **F1** 多步部署流程无 SOP、由模型自由编排 → 未调试即发布 / 先 publish 再 save_draft 触发状态机冲突 / debug 失败后卡住 → 文章处置：Mermaid SOP + 强制走链 → **可构造**：给定 6 步 DAG 与一个必须先于发布的校验步骤，统计模型在无 SOP / 文本 SOP / 图 SOP 三种条件下的跳步率（同时可验证 C4）。
- **F2** 更新类调用参数残缺（taskDefinitions 缺失）→ 平台以空定义覆盖，画布清空，后续 publish 失败 → 文章处置：tier required 校验 + `_get_tool` 先读现状 → **可构造**：对一个"部分更新即整体覆盖"的接口，让模型只提供变更字段，检查是否先回读。
