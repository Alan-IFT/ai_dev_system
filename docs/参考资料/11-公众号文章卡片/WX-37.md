## 1. 文章在讲什么
Agent 进入日常研发并规模化后，使用方关心的不再只是单次结果对不对，而是三件事：耗时花在模型推理还是工具执行、Token 集中在哪些会话/模型、失败与中断发生在哪一步且能否回溯。DSH 自带会话轨迹视图、事件流 zstd-JSONL 落盘与全文检索，但作用域是"本机、单会话、实时"，且事件流是按时间排列的序列而非带父子关系与时间区间的调用树。腾讯云 CLS 团队做了一个 DSH 原生插件：订阅生命周期事件 + 在 `llm/stream` 上包一层只读中间件，在插件内维护状态树，把散落事件还原成 entry/agent/step/chat/tool 五层 Span（声称遵循 OTel GenAI 语义约定），批量直传腾讯云（无 Collector、无 Sidecar）。接入后可看完整调用链、耗时分布（含 TTFT/P95）、Token 与成本下钻、失败按模型侧/工具侧/中断归类、按 Trace/Session 检索与告警。后半篇是安装步骤、配置表与其他接入方式（Coding Agent 本地采集器、Langfuse SDK OTLP 直传）。作者声称的结果只是"能看到这些视图"，没有任何效果数字。

## 2. 核心主张
- **C1** 规模化后的观测需求可归为三问——它慢在哪、它贵在哪、它做对了吗——分别需要"调用树与时间区间"、"分层用量归因"、"状态与内容可追溯"三种数据。｜支撑：图 4 表格（推理）｜适用条件：多机、多会话部署｜文中位置：二 2.2
- **C2** Harness 自带的观测（轨迹视图、事件落盘、检索）解决的是本机、单会话、实时的调试；一批任务的整体表现、一段时间的成本分布、复现几天前的失败，需要跨会话、跨机、可长期留存的结构化链路数据。｜支撑：对 DSH 能力的描述（无数据）｜适用条件：同上｜文中位置：一、七
- **C3** 时间排列的事件序列不等于调用关系；必须还原为"带父子关系与时间区间的调用树"才能做耗时占比和分层归因。｜支撑：推理｜文中位置：二 2.2
- **C4** Agent 的执行结构由模型运行时决定、层级深度不固定，而链路数据要求父子明确、区间完整；解法是状态树 + 延迟发射（SpanID 预分配、内容后补，父子关系先成立）。｜支撑：图 5 流程（设计说明）｜文中位置：三、图 5
- **C5** 观测以 Harness 原生插件形态挂载事件总线与流式管道：逐块观察不改数据、不插桩、不改代码；观测逻辑异常隔离，失败只告警不向宿主抛出。｜支撑：图 4 架构注记；源码已核（见 §4）｜适用条件：Harness 提供事件总线与可包装的流管道｜文中位置：三
- **C6** 一次 turn（一次用户任务）一条 trace，多轮通过 session id 横向关联，避免长会话产生无限膨胀的单条链路。｜支撑：设计说明｜文中位置：三 3.1
- **C7** 重试不合并：每次真实模型调用独立 chat span 并带尝试序号；中断也画完整：流未收尾、step 先于工具结束、用户中断均补发带错误码的 span。｜支撑：设计说明；源码已核｜文中位置：三 3.1
- **C8** 各层属性遵循 OpenTelemetry GenAI 语义约定，便于与既有可观测体系对齐，也便于后续接入其他 Agent 框架时保持同一套口径。｜支撑：声明；本卡核对结果为**部分成立**（§4）｜文中位置：三 3.1
- **C9** 上报直传、批量、有界队列（超限丢最旧）、4xx 丢弃并告警、5xx 退避重试。｜支撑：图 5、配置表；源码已核｜文中位置：三、五
- **C10** 失败定位靠每层 span 独立状态 + 可自定义错误类型，区分模型侧失败、工具侧失败与循环中断。｜支撑：控制台错误类型清单（图 7 左栏）｜文中位置：四
- **C11** 内容捕获（prompts、responses、tool 参数/结果）默认开启、可关闭；访问凭证不得提交到代码仓库。｜支撑：配置表｜文中位置：五
- **C12** 同一套数据模型可接多种来源（Harness 原生插件 / Coding Agent 本地采集器 / 应用内 SDK OTLP 直传），在同一控制台横向对比。｜支撑：图 11 表；腾讯云文档已核｜文中位置：六

**对本项目最有价值的两个引用**

*DSH 事件与遥测文档*：一手文档证实 DSH 的观测是"日志即事实源、一切派生"的形态——telemetry、UI、恢复、模型可见上下文都是同一只追加日志的投影。它还给出了一个本规范目前没有的**导出侧治理模型**：出站记录必须过脱敏 waterfall、规则出错时 fail-closed 扣留、后端必须披露"是否共享/怎么共享"、默认不共享、可选"用户反馈时才释放"。这与腾讯插件"默认全量捕获、直接订阅事件绕过 waterfall"形成同一 Harness 上两种相反的默认——正是 D-020 "载体默认假设会伪装成语义"的活例。

*插件源码与 CHANGELOG*：CHANGELOG 是全文唯一真正的"踩坑实录"，四条修复（进程退出丢尾批、体积拒绝误报网络故障、`sourceIp` 静默写入畸形值、初始化失败拖垮宿主）和一条设计变更（"裁剪后的内容与本来就短的 prompt 无法区分，因此宁可显式超限也不静默改写"）都可直接转成 §8 的失败 Case。源码还暴露了文章没写的两条丢数据路径：加载时不回放已有会话的历史事件；队列满时一次丢 10%。

**冲突展开**

1. **有损导出 vs 证据权威（C9 ↔ D-005/D-009）**。插件路径在五处丢数据：加载时不回放已有会话历史；队列满一次丢 10%；4xx/体积超限整批丢；5xx 重试耗尽即丢；进程退出竞态（0.1.0 前）。所有丢失只在宿主日志里告警，平台上的 trace 不带"此处缺失"标记。文章把平台定位为"长期留存"，但**能长期留存且无损的是本地 zstd 日志，不是平台**。谁的证据更强：DSH 一手文档（持久化"lossless"、遥测"派生"）+ 插件源码 > 文章措辞。可共存条件：平台只作分析与告警，验收证据引用必须可回溯到原始日志（S3）。
2. **span 状态 vs 任务正确（C10 ↔ D-023/D-025）**。图 7 中 14 条 trace 全 OK，但没有任何节点观察任务结果；"它做对了吗"在文章里被替换成"失败发生在哪一层"。这是 D-025 所说的只有局部输出/行动路径两层、缺整体结果层。可共存：把 C10 改名为"它错在哪一层"，"做对了吗"另由验收证据回答。
3. **内容捕获默认开 vs 默认不共享（C11 ↔ D-007/D-027，及 DSH 自身设计）**。同一 Harness 上，官方遥测缝默认 DISABLED、有 fail-closed 脱敏、有"用户反馈才释放"模式；第三方插件默认全量、绕过脱敏缝、README 用一段"隐私说明"提醒用户自己关。谁更强：DSH 的设计有明确的责任模型（后端必须披露 sharing），插件没有。可共存条件：由项目风险所有者显式决定默认值（S4）；规范不写具体开关名。

## 6. 建议采纳（候选语义）
- **S1** 轨迹记录必须能还原为带父子关系与时间区间的调用树（任务 → 推理轮 → 模型调用/工具调用/权限或审批点），每个节点带独立状态与用量，且可跨会话、跨执行环境聚合；纯时间序列不满足。｜落地方式 A（运行时拦截）：进程内订阅生命周期事件即时建树｜落地方式 B（外部状态存储 + 检查器）：从只追加日志离线重建树，检查器验证每个 start 都有配对的 end、每个子节点有父节点｜它防御的失败：慢/贵/错无法归因到层，只能整体重跑猜测；D-003 的重试次数不可数｜删除条件：写不出（可审计性要求，不随模型能力消解）
- **S2** 重试与中断是一等节点：每次真实调用一个节点并带尝试序号；未收尾的节点在上级结束时补齐并标明中断原因，不得合并、不得丢弃。｜落地方式 A（运行时拦截）：身份先分配、内容后补，上级结束时补发未闭合子节点｜落地方式 B（检查器）：对日志做平衡性校验，未闭合的任务/轮次标为 interrupted（DSH 持久化的"中断 turn 恢复"即此形态）｜它防御的失败：失败被重试静默吸收、"两次无新证据"无法判定、中断后的恢复起点不明｜删除条件：写不出
- **S3** 任何导出/聚合通道都是派生投影，不是权威记录；验收证据必须引用可无损回读的原始记录；导出丢失必须显式可见（计数、缺口标记或告警），不得静默裁剪或改写内容。｜落地方式 A（外部状态存储）：本地只追加日志为 source of record，导出带丢弃计数与序号缺口｜落地方式 B（检查器）：定期对账导出节点数与日志事件数，差异即告警｜落地方式 C（人工检查点）：用平台数据做验收前由责任人确认原始记录可回读｜它防御的失败：用有损平台数据当验收证据；裁剪后的提示词被当成原始提示词（CHANGELOG 0.1.0 原话）｜删除条件：写不出
- **S4** 含内容的轨迹（提示词、工具参数与结果、源码片段）跨越信任边界前，必须有显式开关、脱敏节点和"是否共享/如何共享"的披露；默认值由项目风险所有者决定，不继承工具默认。｜落地方式 A（权限与隔离配置）：导出默认关，需显式开启并声明范围｜落地方式 B（运行时拦截）：出站记录过脱敏链，规则出错则整条扣留（fail-closed）｜落地方式 C（人工检查点）：仅在人明确提交反馈时释放对应记录｜它防御的失败：凭证、源码、个人数据进入第三方日志主题；同一 Harness 上两个导出路径默认相反而无人察觉｜删除条件：写不出（责任不可转移）

## 8. 该文暴露的失败模式
- **F1** 观测插件在已有活动会话之后加载 → 不回放历史事件，该会话此前的轮次在调用树中缺失，且无缺口标记（源码注释）→ 文章未提 → 可构造：先起会话跑两轮，再装插件跑一轮，对账平台 span 数与日志事件数。
- **F2** 队列满 / 4xx / 体积超限 / 5xx 重试耗尽 → span 静默丢失（仅宿主日志告警）→ 文章以"超限丢弃最旧并告警"带过 → 可构造：断网或错误 topic 跑任务，检查平台 trace 是否显示不完整。
- **F3** 进程退出时 `flush` 已在进行则直接返回，`stop` 误判队列无进展提前结束 → 最后一批 span（通常含 entry/agent）丢失 → 0.1.0 修复 → 可构造：headless 一次性任务后立即退出，检查 entry span 是否到达。
- **F4** 上报层裁剪超长内容 → 被裁剪的提示词与本来就短的提示词在分析时不可区分 → 0.1.0 改为不裁剪、超限显式告警、超 SDK 上限则整个 span 丢失 → 证据"静默改写 vs 显式缺失"的典型取舍，可作 S3 回归 Case。
- **F5** SDK 本地体积拒绝抛 `InvalidLogSize` 无状态码 → 被记为 `send failed (unknown)`，看似网络抖动实为配置问题，重试永不恢复 → 0.1.0 单独识别 → 失败分类"环境 vs 配置"混淆的实例。
- **F6** `sourceIp` 字段"要求非空但不校验格式" → 无外部 IPv4 时写入主机名，被静默存为畸形 IP → 0.1.0 改回退值 → "检查器只验存在不验形态"失败模式，与 D-018 checker 定义相关。
- **F7** CLS 客户端构造时校验参数抛错 → 从插件 `apply` 抛出，拖垮宿主进程 → 0.1.0 降级为空操作并告警 → S5 的直接来源。
- **F8** 流未收尾 / step 先于工具结束 / 用户中断 → 未闭合 span 由上级结束时补发并标 `INTERRUPTED`/`ABORTED` → 文章作为设计点 → 可构造：任务中途中断，检查 step/agent/entry 状态与结束原因是否一致。
- **F9** entry/agent 输入混入 Harness 注入的合成上下文；chat span 重复携带前 turn 历史 → 成本与内容归因失真 → 0.0.4 修复 → 可构造：多轮会话后比较各 chat span 输入 token 之和与 agent 汇总值。
- **F10** 材料层面：标题承诺"踩坑实录"，正文零案例 → 读者据标题预期得到失败数据 → 提示本项目来源登记应记录"标题与内容类型不符"。
