## 1. 文章在讲什么
作者把 AI 应用工程史讲成三段叠加：Prompt Engineering 优化单次调用 → ReAct 让模型会用工具但对上下文"只进不出" → Context Engineering 管理上下文的整个生命周期（CE ⊇ ReAct ⊇ PE）。问题定义是：长任务里 Agent 的退化多数不是模型问题而是上下文问题，成因有三条"物理约束"——位置效应（Lost in the Middle）、上下文腐化（Context Rot）、注意力预算（n²）。解法分四块：(a) 用 Philipp Schmid 的七要素（指令 / 用户提示 / 状态与历史 / 长期记忆 / 检索信息 / 工具 / 结构化输出）把"上下文"拆成可分别设计的对象；(b) Anthropic 的三项长任务技术（压缩 / 结构化笔记 / 子 Agent）；(c) 从预加载到 JIT 检索与渐进披露；(d) 把 ReAct 的四个上下文陷阱（Observation 膨胀、规则漂移、错误轨迹污染、Thought 冗余）逐一映射到 CE 机制。最后把 CE 定位为"为什么和管什么"，把 Harness Engineering 定位为"怎样沉淀为团队资产"，并用一张 Claude Code 机制对照表收尾。作者声称的结果只有一张自拟表（表 20）：同一 50 轮任务，无 CE 在第 50 轮"实际已失败"，有 CE 则"质量与第 1 轮等同"——这是示意，不是实验。

## 2. 核心主张
- **C1** 三个范式是叠加关系而非替代：CE 包含 PE 的指令技巧与 ReAct 的工具循环，再加"整个信息生命周期管理"这一维度。｜支撑：推理 + 表 1｜适用条件：通用｜文中位置：01 §1.4
- **C2** ReAct 的设计盲点是"只进不出"：TAO 每轮都追加内容，没有任何机制决定何时移除或压缩什么；这是"Agent 用久了越来越差"的根因。｜支撑：推理 + 自拟 Token 累积表（表 17/18）｜适用条件：20～50 轮以上的长任务｜文中位置：07 §7.1–7.2
- **C3** 位置决定被看见的概率：最重要的系统级约束放系统指令开头，当前任务最关键的约束放用户消息结尾，检索文档中最相关的一篇放首或尾，关键规则不能夹在大量工具调用记录中间。｜支撑：Lost in the Middle 原图（一手）+ 作者推论（规则 1–4 本身是作者的，论文没有给出这些规则）｜适用条件：论文覆盖的是 2023 年模型的多文档 QA｜文中位置：03 §3.1
- **C4** 规则漂移（Rule Drift）：系统指令起初在开头，随着历史增长被"推入中间"，落进性能洼地；表现为前 10 轮遵守命名规范、20 轮偶尔出错、30 轮完全混用；工程师常误归因为"模型不稳定"。｜支撑：作者构造的 Go 重构场景，无实测｜适用条件：长任务｜文中位置：03 §3.2、07 §7.2 陷阱二
- **C5** 错误轨迹污染：失败的 Thought 和错误的 Observation 永久留在历史里，像"谣言"一样影响后续所有轮次；处置是压缩时只提取有效轨迹、过滤错误记录，把"经验"写入外部笔记而不留在主上下文。｜支撑：推理，无案例｜适用条件：工具失败/超时常态化的任务｜文中位置：07 §7.2 陷阱三、表 19
- **C6** 工具返回值是上下文的一部分：要设计输出格式而不只设计输入；返回精简结构化结果而非透传原始 API 响应；被消化后的原始结果应从历史移除或折叠为摘要（Anthropic 称为最轻量的压缩）。｜支撑：转述 Anthropic（已核实一致）｜适用条件：通用｜文中位置：04 §4.6
- **C7** 任务状态（当前目录、阶段、正在处理的文件等）归入"状态/历史"要素，遵循三原则：只注入决策必需的最小字段集；用引用（路径、ID）代替内容；阶段变化后主动更新或移除过时字段，防陈旧状态误导。｜支撑：推理｜适用条件：通用｜文中位置：04 §4.3
- **C8** 系统指令要在"太精细（枚举 180 条规则）"与"太宽泛（空洞角色描述）"之间校准，给原则不给枚举；且这不是固定答案而是每个业务场景反复校准出的动态平衡点。｜支撑：转述 Anthropic + 作者金融客服示例｜适用条件：通用｜文中位置：04 §4.1
- **C9** 压缩提示的调优顺序是先最大化召回（关键信息不丢）再提升精确率（去冗余）；压缩输出分两半——摘要负责"知道发生了什么"，最近访问的文件负责"知道正在看什么"。｜支撑：转述 Anthropic（两点均核实为一致）｜适用条件：编码类长任务｜文中位置：05 §5.1
- **C10** 结构化笔记是主动的（边做边写），压缩是被动的（满了才触发）；笔记分四类：进度、决策（含理由）、发现、策略（下一步）。｜支撑：转述 Anthropic + 作者分类｜适用条件：有里程碑的迭代任务｜文中位置：05 §5.2
- **C11** 子 Agent 架构源自 Building Effective Agents 的 Orchestrator-workers 模式，但在 CE 视角下额外获得了当年未被强调的价值——上下文隔离，阻止 Context Rot 在子任务间扩散；选择条件：子方向独立可并行、单路径消耗数千至数万 Token、深度优先于实时性。｜支撑：推理 + 自拟消耗表｜适用条件：多路径研究类任务｜文中位置：05 §5.3
- **C12** 检索到的不相关内容比不检索更糟：5 篇里 1 篇相关时全塞进去会触发中间遗忘，宁取 1～2 篇最相关。｜支撑：推理｜适用条件：RAG｜文中位置：06 §6.1
- **C13** 结构化输出是上下文要素之一：Agent 的输出多被下游系统而非人消费，格式不符则整条流程断链；schema + 示例比只说"输出 JSON"稳定 3～5 倍。｜支撑：无（3～5 倍无来源）｜适用条件：输出被程序消费的场景｜文中位置：04 §4.7
- **C14** Harness Engineering 是 CE 在 AI Coding 场景的工程化落地：Rules 沉淀规则、Memory/Cases 沉淀经验、Skills 标准化做法；CE 说"为什么管、管什么"，Harness 说"怎么沉淀成团队资产"。｜支撑：作者构造的映射表（表 22/23）｜适用条件：作者所在团队的术语体系｜文中位置：10
- **C15** 大窗口不淘汰 CE：稀释效应、n² 代价和信噪比问题在任何窗口大小都存在，CE 解决的不是"装不下"而是"在任何窗口里最大化信噪比"。｜支撑：转述 Anthropic（方向一致，引号内文字非原文）｜适用条件：通用｜文中位置：09 反模式 5、11 §11.3
- **C16** 是否需要完整 CE 体系按任务形态判断：单轮问答不需要，3～5 轮轻度需要，10+ 轮、长期代码维护、多路研究、24h+ 连续运行为"必须"。｜支撑：自拟判断表，无数据｜适用条件：作者经验｜文中位置：11 §11.1

## 6. 建议采纳（候选语义）
- **S1** 压缩、换会话或重新初始化窗口后，任务不变量（目标/范围、已生效决策、安全边界）必须被**重新锚定到高注意力位置**，而不只是"保留在摘要某处"。｜落地方式 A（静态指令 + 外部状态存储）：不变量存于独立工件，每次窗口重建时由执行者按合同重新载入首段｜落地方式 B（运行时拦截）：harness 在压缩事件后自动把不变量段前置/后置注入｜它防御的失败：规则漂移——规则随历史增长被推入中间，20～30 轮后遵从率下降却被误判为模型不稳定（F1）｜删除条件：所选模型在代表性长任务 Case 上位置效应不可测（原论文已显示 claude-1.3 近乎平直，故此规则可能对部分模型已可删）
- **S2** 状态字段有**失效责任**：任务阶段切换时，写入方必须更新或移除已过时的状态字段；读取方不得把"文件里还在"当作"仍然有效"。｜落地方式 A（人工流程 + 外部状态存储）：阶段转换清单含"清理过时字段"一项｜落地方式 B（检查器）：状态工件带阶段标记，检查器在阶段变更后对残留字段告警｜它防御的失败：陈旧状态误导——上一阶段的"当前文件/当前错误"在新阶段仍被注入，模型基于旧状态决策｜删除条件：状态载体本身支持字段级 TTL 或阶段绑定并被 harness 自动执行
- **S3** 压缩产物分两半：**叙事摘要**（发生了什么、决定了什么、剩什么）与**活动工作集原文**（正在编辑/验证的少量工件原样重载）；两者不得互相替代。｜落地方式 A（外部状态存储）：摘要写入交接记录，工作集以引用列表形式记录并在恢复时按引用重读原文｜落地方式 B（运行时拦截）：harness 在压缩时自动附带最近访问工件原文｜它防御的失败：摘要"知道发生了什么"但丢失"正在看什么"，恢复后重读错版本或重复审查已审文件｜删除条件：模型能从摘要中的引用自行可靠回源且成本可接受
- **S4** 失败尝试在离开工作上下文前必须被转换为**教训条目**（假设、证据、为何失败），原始错误轨迹不随历史携带也不进入长期记忆。｜落地方式 A（人工检查点）：执行者在放弃一条路径时写一条教训到工作项｜落地方式 B（运行时拦截 + 外部状态存储）：harness 在检测到重复失败模式（D-003 触发）时强制生成教训条目再清除轨迹｜它防御的失败：错误轨迹污染——失败的推理与错误观察持续影响后续判断，重复犯错（F2）；同时为 D-003"是否有新证据"提供判断依据｜删除条件：模型能在长轨迹中自行区分"已证伪假设"与"当前假设"且不受其影响（需 eval 证明）
- **S5** 用于评估 Harness 的 Case 与用于给 Agent 做示例的 Case 必须**分区**；评估 Case 不得被检索进被评估 Agent 的上下文。｜落地方式 A（权限与隔离配置）：评估集存放位置对运行时检索不可见｜落地方式 B（人工流程 + 检查器）：eval manifest 声明所用 Case ID，检查器比对运行轨迹中检索到的 Case ID，重叠即判评估无效｜它防御的失败：评估被示例污染——"通过率上升"只证明背过题（D-023 目标失明的一个实例）｜删除条件：写不出（这是评估方法论要求，不随模型能力变化）
- **S6** 输出格式约束（结构化输出 schema）是上下文要素之一：它占用注意力预算、且其失效会使下游解析断链，因此应与指令、工具定义一起纳入要素级审计与成本分项。｜落地方式 A（静态指令）：schema 与示例作为独立段落维护并计量｜落地方式 B（检查器）：下游解析失败率作为独立观测指标，反向要求 schema 段调整｜它防御的失败：输出被下游程序消费时格式漂移导致流程静默断链｜删除条件：所有消费方都能容忍自由格式（不现实）或工具层强制 schema 校验已普遍（此时 schema 从上下文迁移到运行时拦截，规则仍在但机制类型变化）
