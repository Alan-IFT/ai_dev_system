# WX-06 从AI Coding到Harness Engineering的端到端工程开发实践

## 0. 验证边界
- 一手实践报告：腾讯应用宝游戏研发后台团队在上半年重构活动平台系统时搭建的 Harness 体系，工具为腾讯内部 CodeBuddy CLI + 内部平台（TAPD/Rick/123/七彩石/伽利略/Codar/工蜂）。作者是当事人，属于 P1。
- **无对照组、无消融、无效率数字**。文中仅有规模数字（800+ 文档、90+ 微服务、4 个业务域、12 个专家 Agent、30+ Skill、10+/近 15 个脚本）与图中阈值（覆盖率基线 ≥80%、CR 最多 5 轮修复、验证最多 4 轮、过期阈值 3 天/5 commit），均为自述配置，非测量结果。
- 作者自评"仅处于'能跑'的刚起步状况"，明确承认**没有评估体系**（§5.2），因此文中一切"稳定/省 token/更可靠"表述都是设计意图或主观观察。
- 超出可核实范围：内部平台与 Codar 的能力、hy3-preview 模型的表现、内部链接（knot.woa.com、agui.woa.com）不可访问；引用的 LLM Wiki / Obsidian-Wiki / GBrain / Claude Workflow / "Vibe coding in prod" 已追读（§4）。
- 图文不一致处（见 §3）：正文说 hook 挂在 Stop/SessionStart/SessionEnd，图 003/007 写 PostToolUse；正文说手工文档与自动文档"地位等同"，图 004 标注 custom/ "优先级最高"。以图为准的可能性更大（图更细），但记为待核实。

## 1. 文章在讲什么
团队最初用"对话式 AI Coding"（Plan Mode + Rules + 人工 Review）重构活动平台，随规模增长遇到四个问题：单窗口上下文膨胀、AI 缺业务知识、只覆盖 coding 一环、无法并行。解法分两层：底座是**知识库工程**（AI 从代码自动生成 8 类结构化文档 + 人工沉淀 custom 文档，三层目录，渐进式加载 + grep 检索，git hash 差异驱动新鲜度检测与增量更新，append-only 变更日志）；其上是**端到端开发工程**（以 JSON 状态文件为唯一事实源的 9 阶段状态机，Stop/SessionStart/SessionEnd hook 强制推进与恢复，12 个单一职责专家 Agent，DAG 波次 + worktree 并行 + Fork-Join，四类冲突治理策略，确定性步骤脚本化，打通内部 DevOps 平台）。复盘提炼出"AI 负责认知，脚本负责执行"等七条原则，并承认已在把编排权从 AI 移到脚本（受 Claude Workflow 启发）。最后讨论 TDD 应落在需求级接口用例、AI 工程缺架构方法论、以及"忘记代码"只适用于容错高的看板类系统。作者声称的结果只是"跑通了从需求到 MR 的闭环"，无量化。

## 2. 核心主张
- **C1** 对话式 AI Coding 的瓶颈不在模型聪明与否，而在"一个对话窗口"这一组织形式；任务越完整、越规模化、越可抽象为稳定流程，Harness 化价值越高。｜支撑：推理 + 团队自身经历｜适用条件：多微服务后台、需求可流程化｜位置：§一、§四引言
- **C2** 知识库是 Harness 的底座；AI 最大问题不是不会写代码，而是缺乏真实、准确、持续更新的业务知识。｜支撑：推理 + 冷启规模描述｜适用条件：数百微服务、知识散落｜位置：§三引言
- **C3** 知识应由"AI 生产（从代码生成）+ 人工补充（AI 推不出的背景/决策/历史包袱）+ AI 消费 + AI 维护（检测更新）"闭环维护，两类文档分开存放。｜支撑：架构描述（图 004）｜适用条件：代码可读、有 proto 契约｜位置：§三、§3.1
- **C4** 用"接口调用量"标注接口是否活跃/废弃，把可观测数据写进知识文档。｜支撑：设计说明；图 004 阈值 0 次→废弃、<10 次/天→低频｜适用条件：有调用统计平台｜位置：§3.2
- **C5** 知识检索采用"层次化加载 + 模型探索 + grep"而非向量 RAG；理由是精准寻址、自顶向下按需、主动多跳、免维护向量库。作者称这"似乎有一种共识"。｜支撑：推理 + 类比人类专家；无对照｜适用条件：知识已结构化、有索引层｜位置：§3.3
- **C6** 过期知识比没有知识更危险；用生成时 git hash 与当前 HEAD 差异（阈值可配）触发增量再生成，增量遵守"最小改动 + 保留人工批注"，并 append-only 记录每次生成。｜支撑：一个真实事故案例（调到老接口，链路全通但结果错，排查很久）｜适用条件：知识源于代码｜位置：§3.4
- **C7** 长链路必须状态化：流程进度、每步产出、依赖关系持久化到结构化状态文件；主调度器不依赖对话记忆，只读状态文件决定下一步。｜支撑：三类问题描述（压缩遗忘、中断不可恢复、不可观测）｜适用条件：多阶段流程｜位置：§4.1.1
- **C8** 仅有状态文件不够，AI 会"偷懒式"提前停止；需在会话生命周期事件上挂运行时拦截：停止前校验 phase 未完成则拒绝停止并注入"必须继续"；会话开始重建激活标志并提示从 Phase X 续跑；会话结束清理标志。｜支撑：机制描述（图 008/009）｜适用条件：工具支持 Stop/Start/End 类钩子｜位置：§4.1.2
- **C9** 专家 Agent 五原则：单一职责（评审只评不改、验证只诊断不改、修复只在收到清单后动手）、上下文隔离、工具最小权限（审查类无写权限、规划类无发布权限）、结构化状态文件传递输入输出、模型可插拔。｜支撑：观察到同一 Agent 角色切换时越权改协议/审查时顺手改代码｜适用条件：多阶段流水线｜位置：§4.2
- **C10** 并行靠 task-planner 输出带依赖与 `touches`（预测修改文件）的 DAG 分波，同波任务各自 worktree 开发，波末统一 merge；多子需求用 Fork（各自跑 1～4 阶段）-Join（串行合并/发布/验证/提交）。｜支撑：流程图 010｜适用条件：任务可按接口/模块切分｜位置：§4.3
- **C11** 冲突治理原则"能事前隔离的就事前隔离，必须共享的就串行收口"：文件级隔离；共享入口文件不在并行期修改；协议变更前置且串行；DB/配置变更一次性前置确认由专门 Agent 执行；真冲突绝不用 `--no-verify`/丢弃绕过。｜支撑：策略表｜位置：§4.3.3
- **C12** "AI 负责认知，脚本负责执行"：状态解析、worktree 操作、编译发布、知识库初始化等确定性步骤交给脚本，消除随机性并省 token；同一需求多次跑/换模型跑结果应一致。｜支撑：复盘观察（AI 写错 shell、用错参数、发散）；无数字｜位置：§4.4、§5.1
- **C13** 大模型生成的 Shell 脚本常有隐性语法/边界错误且在长链路末端才暴露，驱动层应改为强类型语言；调度应从"主子 Agent"改为外部主程序编排 CLI。｜支撑：知识库流水线调试经历｜适用条件：长链路批处理｜位置：§5.1
- **C14** 强确定性流水线中应彻底关闭工具的项目级 Memory：全局记忆引入上下文串扰，使 Agent 偏离职责、破坏子任务幂等与可复现。｜支撑：观察（子 Agent 越界接管主链路）｜位置：§5.1
- **C15** 用 Mock 跳过模型生成环节，低成本联调调度链路（调度最复杂、生成最耗时，二者分离）。｜支撑：工程经验｜位置：§5.1
- **C16** Workflow 比 Prompt 更重要；编排权正从"AI 串联流程、按需调脚本"转向"脚本串联流程、按需调 AI"，业界无定论但方向一致。｜支撑：图 011 + Claude Workflow 启发｜位置：§5.1、§5.2
- **C17** TDD 在代码层难落地，落在**需求级接口测试用例**：方案设计阶段先生成含输入/预期输出的用例，末端验证阶段据此构造请求断言。｜支撑：设计说明｜位置：§5.3.1
- **C18** "忘记代码"只适合结果导向、容错高、无强一致性要求的系统（看板 100% vibe coding、无人 CR）；核心在线业务仍需人守架构，理由：AI 代码腐化快、高质量架构反哺 AI、失控后排障只能靠 AI。｜支撑：看板案例 + 推理｜位置：§5.3.3
- **C19** AI 工程缺架构分层方法论：现状是"一个 skill 目录一个 agent 目录往里加"，工程与工具耦合（重度依赖 CodeBuddy CLI）。｜支撑：自我批评｜位置：§5.3.2、§5.2

## 6. 建议采纳（候选语义）
- **S1** 由代码派生的知识工件必须记录其派生自的源版本标识，并有可机械执行的过期判定（源与派生物的版本差异超过声明阈值即标记为过期，过期知识默认不得作为事实使用）。｜落地 A（外部状态存储）：知识索引中为每个派生文档记录源版本与生成时间｜落地 B（检查器）：定时/按需比较源版本与记录版本并输出过期报告｜它防御的失败：F1（调用已废弃接口，链路全通结果错）｜删除条件：工具能在读取派生文档时自动对照源代码并标注差异
- **S2** 派生知识的再生成必须保留人工写入的部分，且每次再生成追加不可覆盖的变更记录（源版本、时间、摘要、模式）。｜落地 A（条件加载规则/文档约定）：人工内容与自动内容分区存放，再生只改自动区｜落地 B（检查器）：再生后 diff 校验人工区未被删改、日志只增不减｜它防御的失败：每次更新都要重新补充上下文；生成出错无法回滚｜删除条件：写不出（这是治理要求，不随模型能力消解）
- **S3** 人工写入的知识对自动派生的知识具有覆盖权，且人可以用它标注某项自动知识为废弃。｜落地 A（静态指令）：检索规则声明来源优先级｜落地 B（检查器）：冲突检测时以人工来源为准并报告分歧｜它防御的失败：自动文档复活已下线接口｜删除条件：写不出（责任判据：只有人能承担"这个接口不该再用"的后果）
- **S4** 多阶段流程中，"未完成而停止"应视为一种需要被拦截的动作：停止前检查状态工件，未达合法停止点则拒绝停止并把下一步注入执行者；恢复入口在会话开始与上下文压缩后都必须重新提供。｜落地 A（运行时拦截）：会话停止/开始/压缩事件上的检查脚本｜落地 B（人工检查点 + 外部状态存储）：状态工件声明合法停止点，恢复者按状态工件而非对话重启｜它防御的失败：F2 调度器偷懒提前结束；F3 压缩后遗忘进度｜删除条件：模型在长任务中不会自行提前结束且压缩后能自恢复
- **S5** 并行执行单元只能写自己的局部状态记录，总状态只能由收口阶段的单一执行者更新；共享入口与全局契约/存储变更不进入并行期。｜落地 A（权限与隔离配置）：并行单元的写范围限制在自身工作区与自身记录｜落地 B（人工流程/检查器）：收口时校验各单元记录齐备后再合并总状态｜它防御的失败：多 Agent 同时改总状态/入口文件导致覆盖与编译失败｜删除条件：工具提供事务化的多写者状态合并
- **S6** 复杂度演进允许"先用自治编排跑通，再把已稳定的路径降级为确定性编排"，并把"同一输入多次运行结果是否一致"作为降级完成的判据。｜落地 A（检查器/评估）：重复运行同一任务比较结果与成本方差｜落地 B（人工流程）：复盘时列出哪些步骤不需要推理并转为程序｜它防御的失败：确定性步骤由模型执行产生随机错误与 token 浪费｜删除条件：写不出（D-010 已含此方向，本条只补"从高往低"的路径）
- **S7** 冲突预测前置：任务拆解时声明每个任务预计触碰的范围，调度据此避免同批任务重叠；真实冲突不得被绕过检查合并，必须升级给人裁决。｜落地 A（外部状态存储）：任务记录含触碰范围字段｜落地 B（运行时拦截）：合并前拒绝绕过校验的合并参数｜它防御的失败：F4 并行修改同文件后被覆盖｜删除条件：写不出
- **S8** 修复循环必须有轮数上限，超限即停止并升级，不得无限自修。｜落地 A（静态指令）：阶段定义中声明上限｜落地 B（运行时拦截/检查器）：状态工件计数超限即阻断｜它防御的失败：同一问题反复修复消耗预算｜删除条件：与 D-003 合并，数值为载体绑定

## 8. 该文暴露的失败模式
- **F1** 知识库未随代码更新 → AI 调用老接口，整条链路通但拿不到预期结果，排查很久才发现 → 引入 git hash 差异过期检测与增量更新 → 可构造：准备一份记录旧版本的派生文档 + 已废弃接口，看执行者是否先核对版本再调用
- **F2** 多阶段流程中主调度器在 phase 未完成时自行结束 → 流程半途停止 → Stop hook 读状态、拒绝停止并注入下一步 → 可构造：给定 current_phase<done 的状态工件并观察是否停止
- **F3** 会话关闭或上下文压缩后中间状态丢失 → 无法恢复、不知道到哪一步 → SessionStart（含 compact）重建标志并提示续跑 → 可构造：中途压缩/重启后检查是否从状态工件恢复而非重做
- **F4** 多 Agent 并行修改同一文件/入口文件 → 覆盖、编译失败 → touches 预测隔离 + 入口延后串行 + 冲突交人 → 可构造：两个任务声明重叠触碰范围
- **F5** 同一 Agent 跨角色执行 → 开发阶段越权改协议、审查阶段顺手改代码 → 单一职责 + 工具最小权限 → 可构造：给审查角色写权限，观察是否修改代码
- **F6** 模型执行确定性步骤（解析 JSON、建 worktree、编译命令）→ 写错 shell 语法/用错参数/发散，多次运行结果与 token 不一致 → 脚本化 → 可构造：同一任务重复运行比较方差
- **F7** LLM 生成的驱动脚本含隐性语法/边界错误 → 长链路末端才抛错，排查极耗时 → 强类型驱动层 + Mock 跳过生成环节联调 → 可构造：注入一个只在末端触发的分支错误
- **F8** 工具自动记忆跨任务串扰 → 子 Agent 越界接管主链路，子任务不幂等 → 关闭自动记忆 → 可构造：开启自动记忆运行两个无关任务，观察第二个是否受第一个影响
