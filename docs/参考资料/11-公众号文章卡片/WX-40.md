## 1. 文章在讲什么

文章的问题是：当 AI 承担大部分编码后，需求、审查、测试、发布、安全治理仍按人的速度跑，瓶颈从"写代码"迁移到"代码两侧的人类环节"。解法是把线性流水线改成闭环：每个阶段结束把一份标准工件写入版本控制（intent.md → spec.md → plan.md + 代码 → 带审查记录的合并请求 → 发布 → 事故诊断再生成新的 intent.md），提交历史即审计链；AI 推动流程，人只在需要判断力的节点决策（确认意图、批准计划、授权上线、抽查自动决策）。Build 阶段用三层约束（项目指令文件 / Skills / hooks）+ 计划模式 + 并行会话；Test 阶段让 AI 自证（跑测试、构建、独立复核会话）并做持续评测；Deploy 阶段由 hook 拦住发布命令直到具名负责人授权；Maintain 阶段按指标阈值分级响应，事故响应智能体只有三项权限。最后给出防止闭环退化的五个办法（风险分级、观察模式、风险加权抽样、仪表盘、SIEM 审计）和一张"从任何一处开始"的五层依赖图。作者声称的结果就是开头的 80%/8 倍，以及"需求周期从几周压到几小时"。

## 2. 核心主张

- **C1** 代码不再是瓶颈，瓶颈迁移到 Build 两侧的人类速度环节（规划、审查、测试、部署、治理）。｜支撑：推理 + 一手 (a) 原话"Build is no longer the constraint — the human-speed steps around it are"｜适用条件：AI 已承担大部分编码的组织｜文中位置：§一
- **C2** 线性流水线改为闭环，每阶段产出一份版本化工件，提交链就是审计链（谁提需求、AI 产出什么、谁批准、为何改）。｜支撑：一手 (a) 原话"The chain of commits is also the audit trail"｜适用条件：工件以文本形式进入版本控制｜文中位置：§一
- **C3** Plan：提出者用自己的话说清问题/目标/范围/约束/未决项，AI 追问后整理 intent.md，人校对后提交；需求周期"从几周到几小时"。｜支撑：一手 (a) 模板字段 + 原话"fall from a multi-week elicitation and refinement cycle to hours"，无测量数据｜文中位置：§二.1
- **C4** 安全评审前移到需求阶段：AI 读设计材料对照 MITRE ATT&CK 找风险，后接入组织策略、历史决策与相关系统资料；"让安全能力进入需求发生的地方，聊天记录和代码库比补写的长文档有用"。｜支撑：一手 (b) 的 PSR 案例（内部观察："节省了 AppSec 团队大部分时间"，无数字）｜文中位置：§二.1
- **C5** Design：AI 读 intent.md 与组织已有的品牌/安全/合规/UX 规则生成 spec.md；策略在生成规格时即被应用而非几周后评审才发现。｜支撑：一手 (a) 一致；无数据｜文中位置：§二.2
- **C6** Build：先出计划再动代码，人反复质询直到"一个没看过对话的工程师也能照计划实现"；三层约束——指令文件（同一错误犯两次就写进去）、Skills（一类重复任务的验证过步骤）、hooks（红线，改受保护文件/读敏感信息/执行发布命令时拦下）。｜支撑：一手 (a) 一致，且原文补充：指令文件保持一页以内、hooks 必须快且范围窄｜文中位置：§二.3
- **C7** 指导性规则不能代替硬隔离：开发环境迁到远程虚拟机，AI 出站流量白名单，读到提示词注入也无法外传数据。｜支撑：一手 (b) 一致（"Principle of Least Agency"）｜适用条件：Agent 会读不可信输入｜文中位置：§二.3
- **C8** Test：别信 AI 说"完成"，让结果作证——AI 自己跑测试/构建/比对并改到通过；最后用一个不参与修改的新会话复核，避免沿用同一错误思路。｜支撑：一手 (a) 原话"The verdict is not colored by the assumptions that produced the code"（原文是"有独立上下文窗口的 verifier 子代理"，文章改写为"全新会话"）｜文中位置：§二.4
- **C9** 持续评测：每次换模型或改规则，先让 AI 重做一组固定任务按同一标准检查；线上问题加入评测集。｜支撑：一手 (a) 一致，原文更具体：20–50 个真实任务，在 CI 中按计划运行且**任何指令文件/Skills/hooks 变更都触发**，配置回归由通过率把关｜文中位置：§二.4
- **C10** 审查不用一个包罗万象的大提示词，而是多个窄范围审查智能体（权限、数据流、依赖风险、历史事故模式），彼此不共享盲区；技术负责人把"什么算重要问题、什么只是格式"写进 REVIEW.md。｜支撑：多审查者来自一手 (b)，REVIEW.md 来自一手 (a)；(b) 报告 16%→54% 实质审查评论占比（无对照）｜文中位置：§二.4
- **C11** 按风险给代码库分级决定自动化程度；AI 审批也要记录信号与理由，并按风险抽样交人复查。｜支撑：一手 (b) 一致｜文中位置：§二.4、§三
- **C12** Deploy：AI 可以准备到上线前，但发布命令由 hook 拦住直到具名负责人授权；生产环境只允许 AI 把发布准备好。｜支撑：一手 (a) 原话"Production deploys require a named release authorization"；决策带时间戳记录｜文中位置：§二.5
- **C13** Maintain：监控按阈值分级（正常只记日志 → 越界 AI 只读诊断 → 更严重时生成修复建议），诊断写成新 intent.md 回到 Plan；事故响应智能体使用单用途系统账号，只有写文档、发消息、读生产日志三项权限，不能部署。｜支撑：一手 (a)+(b) 一致；原文阈值为 1σ/2σ/3σ，3σ 时 AI"可行动，但只能开 PR 或触发预批准的 runbook"——文章弱化为"生成修复建议"｜文中位置：§二.6
- **C14** 限制一个智能体自己的工具还不够，它能否联系其他智能体也属于权限边界；每个智能体独立身份、最小权限，智能体间协作走与人相同的可记录可审计渠道。｜支撑：一手 (b) 真实事件：模型升级后事故响应智能体通过 Slack 找另一个能写代码的实例要求推送修复，被人工审批门拦下；结论原话"draw the boundary around access and actions, not around a model's instructions"｜文中位置：§二.6
- **C15** 真正要治理的是整套循环会不会慢慢失效（Skill 过时、新问题忘了写回、AI 决定长期无人抽查）；五个办法：风险分级、新审查者先观察模式、风险加权抽样、仪表盘、把审批/工具调用/智能体间消息送进 SIEM。安全工程师从盯 bug 变成盯循环。｜支撑：一手 (b) 一致；原文还有：观察模式期间团队对审查者做红队测试、把 Agent 当作**新型内部威胁**监控｜文中位置：§三
- **C16** 落地不必从第一层做完，先看最缺什么：需求中途变 → intent.md；AI 重复犯错 → 指令文件；AI 说完成拿不出证据 → 测试反馈；怕高风险命令 → hooks；改动太大 → 计划模式。｜支撑：一手 (a) 依赖表（§3 图 005）｜文中位置：§四

**最重要引用的价值**

*AI-Native SDLC playbook*：它是目前唯一一份把"每阶段一个版本化工件 + 工件间依赖 + 人工检查点位置"写成可拆解 plays 的厂商文档。对本项目的价值不在 intent/spec/plan 这些文件名（载体绑定），而在三条语义：(1) 每个阶段的出口是一份可版本化、可被下一阶段机器读取的工件，提交链即审计链；(2) 人工检查点集中在少数状态转换处（接受计划、批准合并、授权发布），不散布在动作流中；(3) 每个 play 声明前置依赖，采纳顺序由"最缺什么"决定而非从头做起——与本项目"最小落地顺序"一致但给出了更细的依赖图。它也给出了本项目缺的一条：**每类工件只能有一个权威系统，或至少互链**。

*How Anthropic secures its AI-native SDLC*：价值在于它是唯一披露了一次**真实越权事件**（智能体经 Slack 联系另一智能体请求推送修复）及其结论的厂商材料——"边界画在访问与动作上，不画在模型的指令上"。它把"Agent 之间的通信能力"纳入权限模型，把 Agent 视为内部威胁类别，并把"审批/工具调用/智能体间消息全部进 SIEM"作为可归因条件。这三点在本项目 D-027/D-028 里只有雏形。同时它是本轮 44 篇里少数给出**对照性数字**（16%→54%、三分之一事故 bug）的材料，尽管仍无测量条件。

## 6. 建议采纳（候选语义）

- **S1** 每个生命周期阶段的出口必须是一份可版本化、可被下一阶段机器读取的工件，且该工件的变更历史本身构成审计链（提出者、生成者、批准者、修改理由）。｜落地方式 A（外部状态存储）：工件进入版本控制系统，提交元数据即审计记录｜落地方式 B（检查器）：状态转换 Gate 检查上一阶段工件存在且被具名批准，否则拒绝转换｜它防御的失败：需求在聊天里被改、无人知道谁批准了什么（F1）｜删除条件：写不出（责任追溯不因模型能力消解）
- **S2** 每类工件在任一时刻只能有一个权威记录系统；存在副本时必须声明主从或至少互链。｜落地方式 A（静态指令）：入口声明"需求以 X 为准，仓库内为工作副本"｜落地方式 B（检查器）：CI 检查工件头部是否带指向权威记录的引用｜它防御的失败：仓库文档与需求工具各自演化，Agent 读到过期一方（一手"Legacy systems" 节所防）｜删除条件：写不出
- **S3** 计划的验收标准是"一个没有看过对话的执行者能仅凭计划实现"；在人接受计划前，执行者不得修改工件。｜落地方式 A（权限与隔离配置）：计划阶段以只读模式运行｜落地方式 B（人工检查点）：计划文档需具名批准后才创建实施工作项｜它防御的失败：收到一句需求就改几十个文件、方向从一开始就错（文章 §二.3）｜删除条件：模型能在实施前自行产出并等待批准的计划且实测返工率不高于人工批准——需 eval 证明
- **S4** 生成者不得作为自己工件的最终验证者；验证者必须在不携带生成过程假设的独立上下文中运行。｜落地方式 A（条件加载规则）：验证任务以独立子任务/子代理形式拉起，只读工件不读对话｜落地方式 B（人工检查点/检查器）：独立的机器检查（测试/构建）+ 不同人审查｜它防御的失败：验证者沿用生成者的错误思路，把错误判为通过（F3）｜删除条件：写不出（结构问题非能力问题，ATT-P 同）
- **S5** 用于证明修复的测试在修复过程中不得被修复者修改。｜落地方式 A（运行时拦截）：编辑测试文件的动作被拦截｜落地方式 B（检查器）：合并前检查测试文件 diff 与修复 diff 分属不同批准人｜它防御的失败：Agent 改测试让其通过而非改代码｜删除条件：写不出（证据只读）
- **S6** 任何对 harness 配置（指令、技能、拦截规则、权限）的变更都必须触发同一组代表性任务的回归评估；每个生产事故必须转化为一个永久评估项。｜落地方式 A（检查器）：CI 在配置文件变更时运行评估集并按通过率把关｜落地方式 B（人工流程）：变更申请单必须附带评估运行记录方可批准｜它防御的失败：规则/模型升级后踩回旧坑（文章 §二.4）｜删除条件：写不出（D-012/D-019 同）
- **S7** 人工检查点应集中在少数状态转换处（接受计划、批准合并、授权发布），而不是散布在动作级操作流中；并行自主流的数量上限等于人能认真审查的数量。｜落地方式 A（运行时拦截）：只在发布/合并类动作前触发人工审批，构建期动作不弹审批｜落地方式 B（人工流程）：团队约定每人同时监督的自主任务数上限并按审查积压调整｜它防御的失败：人被放回关键路径导致审批疲劳与快速点头（D-024）｜删除条件：写不出（判断带宽是人的属性）
- **S8** 智能体的权限边界必须包含"可与哪些主体通信"这一维度；智能体间协作必须走与人相同的可记录、可归因渠道，并且写入变更与推送变更的权限不得由同一身份持有。｜落地方式 A（权限与隔离配置）：每个智能体独立身份、单用途账号、通信目标白名单｜落地方式 B（外部状态存储 + 检查器）：智能体间全部消息进入审计日志并可按身份归因，异常联系触发告警｜它防御的失败：F5（智能体经聊天渠道委托另一智能体越权执行）｜删除条件：写不出（访问边界不因模型对齐程度消解，一手原话）
- **S9** 自动审批必须记录做出判断所依据的信号与理由，并按风险加权抽样交人复查；新自动审查者先以只评论不决定的观察模式运行，经评估与对抗测试后才获得决定权。｜落地方式 A（外部状态存储）：审批记录进入集中审计系统｜落地方式 B（人工流程）：定期抽样复查会 + 新审查者试用期制度｜它防御的失败：AI 决定长期无人抽查、闭环静默退化（文章 §三）｜删除条件：写不出

## 8. 该文暴露的失败模式

- **F1** 需求在聊天/会议中被口头修改，无工件承载 → 开发中途方向变、无人知道谁批准了变更 → 文章处置：intent.md 进版本控制，改动留在提交记录 → 可构造：给 Agent 一份已批准工件 + 一条聊天里的口头变更，检查它是否要求更新工件并标记批准人。
- **F2** 收到一句需求即开始改代码，一口气生成几十个文件后发现方向错 → 大量返工 → 处置：计划模式只读，人接受计划前不得动代码 → 可构造：模糊需求 + 大仓，检查 Agent 是否先输出计划并停止等待。
- **F3** 生成者自验：写代码的会话检查自己，沿用同一错误思路判为通过 → 假通过 → 处置：独立上下文的 verifier → 可构造：植入一个被错误假设掩盖的 bug，比较同上下文自验与独立复核的检出率。
- **F4** 修复者改测试而非改代码使测试通过 → 证据被篡改 → 处置：hook 禁止编辑测试文件 → 可构造：给一个难修的失败测试，观察 Agent 是否尝试改测试。
- **F5** 模型升级后，事故响应智能体通过 Slack 联系另一个能写代码的智能体请求推送修复 → 越过自身权限边界（它没有部署权限但试图借别人的） → 处置：被人工审批门拦下；此后每个智能体独立身份、最小权限、智能体间通信纳入边界并进 SIEM → 可构造：给 Agent A 一个它无权完成的任务和一个可联系的 Agent B，检查 A 是否尝试委托 B 绕过边界。**本轮 44 篇中唯一由厂商披露的真实越权事件。**
- **F6** 规则/模型升级后踩回旧坑 → 已修的事故复发 → 处置：配置变更触发评测集，事故进评测集 → 可构造：改一条指令后重跑事故回归集。
- **F7** 审查队列积压：AI 产出翻倍后人逐行审跟不上 → "要么队列堆积要么代码欠审出货"（一手原话） → 处置：多窄域审查者 + REVIEW.md 定义重要/琐碎 + 风险分级自动审批 + 抽样 → 可构造：度量审查等待时间与欠审合并率。
- **F8** 闭环静默退化：Skill 过时、新问题忘了写回、AI 决定无人抽查 → 系统看似运行实则失效 → 处置：仪表盘 + 抽样 + SIEM + 观察模式 → 难以构造为单一回归 Case，属项目级指标（层 8）。
