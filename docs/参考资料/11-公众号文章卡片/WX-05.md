## 1. 文章在讲什么
作者认为企业 Agent "Demo 惊艳、生产拉胯"的原因是用 Demo 阶段的工程方法解决生产阶段的系统问题。把 2022-2026 的范式演进整理为四层——Prompt（说清任务）→ Context（提供背景）→ Harness（可靠执行）→ Loop（持续自主），强调四层是嵌套而非替代：外层不取消内层，每层解决上一层的核心瓶颈同时引入新风险。对每层给出定义、技术手段、企业正面影响、天花板、成熟度定位。L3 与 L2 的本质区别是"基于验证"对"基于信任"：确定性约束替代概率性遵守。L4 引入三类新风险：成本组合爆炸、多 Agent/多 session 组合空间的可靠性、理解力负债与认知投降。给出四层故障诊断框架（先定层再修）、三阶段采纳路径（L1+L2 夯实 → L3 建设 → L4 试点）、"跳过 L3 直接 L4"反模式、金融/软件/客服三行业重心差异，结尾借 Osmani "Build the loop. Stay the engineer." 收束。作者声称的结果：企业瓶颈已从模型能力迁移到系统工程能力，2026 年应把主要精力放在 L3。

## 2. 核心主张
- **C1** 四层是嵌套关系而非替代：Context ⊃ Prompt，Harness ⊃ Context，Loop ⊃ 全部；外层不取消内层，内层质量差外层救不了。｜支撑：推理｜适用条件：通用｜文中位置：01 四层演进的时间线
- **C2** Prompt 层的三个天花板：信息孤岛、无记忆、人是瓶颈（Agent 吞吐量 = 人的带宽）。｜支撑：推理｜适用条件：单 turn 交互｜文中位置：02 L1
- **C3** Context Engineering 的核心是"token 配置"——什么放、什么不放、放多少、什么顺序、什么时候放；Context Rot 使更多 token 反而降低召回。｜支撑：引用 Anthropic 博客｜适用条件：长上下文｜文中位置：03 L2
- **C4** Context 层的天花板：模型的"手"不受控（看到规范仍可能选择性忽略）、错误不会自愈（没有拦截/门禁/反馈回路）、仍靠人触发人判断。｜支撑：推理｜适用条件：单 session｜文中位置：03 L2 天花板
- **C5** Harness = 模型之外的一切基础设施，五组件：Guides / Sensors / Enforcement / Context Pipeline / Observability；核心问题是"如何构建让错误结构性不可重犯的执行环境"。｜支撑：引用 Hashimoto、OpenAI、LangChain｜适用条件：跨 session 单任务｜文中位置：04 Harness 包含什么
- **C6** L2 是基于信任的策略（给正确信息期望正确行为），L3 是基于验证的策略（输出应用到真实环境前必须过外部检查）；确定性约束替代概率性遵守是 L2/L3 的本质区别。｜支撑：类比（教材 vs 阅卷系统）｜适用条件：可形式化验证的维度｜文中位置：04 L2 与 L3 的本质区别
- **C7** Guides 文件的每一行对应一个曾经的失败模式，是错误经验的结构化沉淀；增长模式是"新错误→根因→加规则或加 check→不再出现"，系统可靠性随时间单调递增。｜支撑：引用 Hashimoto 的 Ghostty AGENTS.md 经验｜适用条件：作者未限定｜文中位置：04 Harness 包含什么 / 正面影响
- **C8** Harness 的天花板：仍是人触发人收尾、无跨 session 记忆、不能并行规模化。｜支撑：推理｜适用条件：单任务 harness｜文中位置：04 天花板
- **C9** Loop = 五个原语 + 一个状态存储：Automations（心跳）、Worktrees（隔离）、Skills（编码约定，消除"意图负债"）、Connectors、Sub-agents（写的人和查的人分开）、State（context window 之外的持久状态，是跨 run 连续性的唯一保障）；Codex 与 Claude Code 已独立收敛到同一架构。｜支撑：引用 Osmani｜适用条件：coding agent｜文中位置：05 Loop 的六个构成要素
- **C10** Maker-checker 分离改变信任模型：不信任任何单个 Agent 输出，信任验证流程；这是无人值守可行的基础。｜支撑：引用 Osmani + 推理｜适用条件：L4｜文中位置：05 正面影响 4
- **C11** L4 引入 L3 没有的三类风险：(1) 成本从"任务×执行×N turn"变为"心跳×M 子 Agent×各自迭代×工具调用"的组合爆炸，token 丰富与 token 贫困团队策略完全不同；(2) 可靠性面扩大——triage 误分类、子 Agent 死锁/循环依赖、State 损坏导致重复执行或遗漏、同模型 maker-checker 捕不到系统性偏差；(3) 理解力负债与认知投降。｜支撑：引用 Osmani + 作者推演｜适用条件：无人值守多 Agent｜文中位置：05 L4 引入的新风险
- **C12** 故障诊断先定层再修：症状→层→对应修复；修复施加在错误层则症状反复出现，团队对 Agent 失去信心；多数生产故障是 harness 层被误诊为 prompt/context 层。｜支撑：三个构造场景；"大量实践表明"无出处｜适用条件：生产 Agent｜文中位置：06 四层诊断框架
- **C13** 采纳顺序由内而外逐层验证，各阶段有退出标准；跳过 L3 直接 L4 是最危险反模式——每个 Agent 都不可靠的自动系统不会停下来等你修，人工善后成本可能超过手动执行，净效率为负。｜支撑：推理；引用 Cherny 案例的前提（自家模型+完善 harness）｜适用条件：企业采纳｜文中位置：07 企业采纳路径
- **C14** L4 最适合软件工程，因为代码有明确的验证手段（编译/测试/lint），maker-checker 有自动化基础；客服等响应式场景 L4 适用有限。｜支撑：推理｜适用条件：按行业｜文中位置：08 行业适配
- **C15** 每一层把人往更高层抽象推（管措辞→管信息→管环境→管编排）；可能的 L5 是 Agent 自己调整 Loop 配置（Meta-Loop），引 Meta-Harness 为概念验证。｜支撑：引用 Stanford/MIT 论文｜适用条件：展望｜文中位置：09 展望

- `图 006`（05 节，一个完整 Loop 的日常运行）→ 四泳道。Automation：定时触发（每日 9:00）→ 读取 State 文件了解昨日进度 → 调用 Triage Skill 扫描 CI 失败/Open Issues/新提交 → 生成今日待办列表写入 State → 循环取任务；不可自动处理的任务放入 Triage Inbox 等待人工审核。Builder：从 State 读第一个任务 → 创建独立 Worktree → 读取相关 Skills → 编码实现 → 根据 Review 反馈修正（"内部循环可能迭代 2-3 轮"）。Reviewer：在同一 Worktree 中 Review → 对照 Skills + Tests 验证 → 通过/不通过。Connector：开 PR → 更新 Ticket → 通知 Channel → 回到 State 标记完成。底部"Loop = 自动发现→执行→验证→交付→回流"。正文没有的信息：**State 既是任务队列又是进度记录，是 Automation 与 Builder 之间唯一的交接载体**；Reviewer 与 Builder 共享 Worktree。

## 6. 建议采纳（候选语义）
- **S1** 每条控制机制必须标注它属于"期望被遵守"（信息型：模型看到后自行遵守）还是"应用前被检查"（验证型：输出进入真实环境前由模型之外的检查器判定）；高风险边界不得只有信息型控制。｜落地方式 A（检查器）：为每条控制登记类型字段，检查器扫描高风险动作是否至少有一条验证型控制覆盖｜落地方式 B（人工检查点）：ADR/规则评审时人工填该字段，无验证型控制的高风险边界不予批准｜它防御的失败：F2（上下文中有正确信息，模型仍按训练先验行动）｜删除条件：写不出（这是"责任不可转移"类约束，与模型能力无关）
- **S2** 无人触发的运行（定时/事件触发）必须在启动前声明资源上限（预算、迭代轮数、并行子任务数）与超限行为（停止并升级人工），运行中超限即停，不得由运行自身放宽上限。｜落地方式 A（运行时拦截）：执行层计量 token/轮次，超限中止并写入证据｜落地方式 B（外部状态存储 + 人工检查点）：工作项中预先登记预算，调度前人工或程序核对，无预算不启动｜它防御的失败：F7（一晚烧掉一月预算）、子 Agent 循环依赖｜删除条件：模型能可靠估计并自限成本且该估计经评估证明与实测一致
- **S3** 验证者与生成者分离，且分离须覆盖**指令与偏差来源**：验证者不得复用生成者的指令，且高风险判定不得仅由与生成者同源的模型完成——须至少含一个确定性检查或不同来源的判断。｜落地方式 A（权限与隔离配置）：验证者以独立身份运行，对生成者输出无写权限｜落地方式 B（检查器）：门禁中至少一项为非模型检查（编译/测试/lint/契约校验）｜它防御的失败：F5（同模型 maker-checker 共享系统性偏差、错误通过）｜删除条件：能证明不同实例间偏差独立（目前写不出可验证的条件）
- **S4** 跨运行连续性只能依赖上下文窗口之外的持久状态；每次运行读取状态时必须校验其完整性与新鲜度，校验失败时停止而非猜测；状态记录必须能区分"已完成/进行中/待做"以防重复执行与遗漏。｜落地方式 A（外部状态存储）：状态带版本/校验和/时间戳，读取时比对｜落地方式 B（检查器 + 人工检查点）：启动前检查器验证状态一致性，不一致进入人工队列｜它防御的失败：F4（State 损坏→重复执行或遗漏）｜删除条件：写不出（跨会话遗忘是架构事实，不是模型能力缺口）
- **S5** 自动分流（triage）的结果是待验证主张：分流必须有默认的"不确定→人工"路径，分流决策及其依据须留痕，高优先级项被降级须可被事后审计发现。｜落地方式 A（条件加载规则/工作流）：分流规则显式列出可自动处理的类别，其余一律入人工队列｜落地方式 B（检查器 + 外部状态）：分流日志与事后实际优先级对账，误分类率进入评估指标｜它防御的失败：F6（高优先级 issue 被分成低优先级而被忽略）｜删除条件：分流误判率经评估长期低于人工分流
- **S6** 故障修复必须登记"施加在哪一层"；同一症状在某层修复后复发，即视为该层误诊的证据，下一次修复须换层诊断（诊断顺序由内向外，"模型能力不足"是最后而非最先的假设）。｜落地方式 A（外部状态存储）：失败 Case 记录带"修复层"字段与复发计数｜落地方式 B（人工检查点）：事故复盘模板要求回答"上次修在哪层、为什么复发"｜它防御的失败：F9（两周调 prompt 无效、问题在检索过期文档）｜删除条件：写不出（这是诊断纪律，与 D-003 同类）
- **S7** 自动生成产出与人类理解覆盖之间的缺口不会触发任何自动指标，须作为独立观测量定期采样（如对自动生成模块做人工走查并记录覆盖）。｜落地方式 A（人工检查点）：定期走查排期，未走查模块不得视为"已理解"｜落地方式 B（外部状态存储）：按模块记录"最后一次人类审读"元数据，超期告警｜它防御的失败：F8（理解力负债在跨模块 debug 时爆发）｜删除条件：写不出
- **S8** 规则集的增删速率是评估层观测量：只增不减是退化信号，"增长放缓"只能与"失败报告率未下降"同时成立时才作为覆盖充分的证据。｜落地方式 A（外部状态存储）：规则变更日志按周期统计增/删/改｜落地方式 B（人工检查点）：定期复查会同时看规则数与失败 Case 数｜它防御的失败：ATT-N 的 400→1500 膨胀、冲突一｜删除条件：写不出

## 8. 该文暴露的失败模式
- **F1** 知识库同时存在新旧两版政策文档，检索命中旧版 → Agent 用过期政策回答，改 prompt 两周无效 → 文章处置：文档版本管理，只检索最新版 → **可构造**：知识库放两版带日期的同主题文档，期望 Agent 引最新版或报告冲突（对应 D-005 记录源、06 失败分类"source of record"）
- **F2** 上下文含正确的新 API 文档，但训练语料中旧 API 频率更高 → 模型"习惯性"用废弃 API，塞更多文档只偶尔减少 → 文章处置：CI 中加 deprecated-API 检测器直接阻止 → **可构造**：给定新 API 文档 + 诱导旧 API 的任务，检查器必须拦下（对应 D-008）
- **F3** 积压 50 个 issue、每天只处理 5 个 → 误诊为模型慢，换模型只到 7 个 → 文章处置：自动 triage + 并行子 Agent，人只看 inbox → **可构造为度量 Case**：分别记录模型执行时间与等待人触发的时间（对应 D-022 等待时间可分离）
- **F4** State 文件损坏或不一致 → 任务重复执行或遗漏 → 文章只列风险未给处置 → **可构造**：人为损坏/回退 State 后启动 Loop，期望停止并升级而非猜测继续（对应 D-016、S4）
- **F5** Maker 与 checker 用同一模型 → 共享系统性偏差，错误输出通过 review → 文章只列风险 → **可构造**：注入一个两者都会犯的偏差（如对某 API 的错误假设），观察 checker 是否放行（对应 D-023 现实锚点、S3）
- **F6** 自动 triage 把高优先级 issue 分为低优先级 → 重要问题被忽略 → 文章处置：不可自动处理的进人工 inbox（但误分类不会进 inbox）→ **可构造**：投入一条措辞平淡的高危 issue，检查是否被降级且事后可发现（对应 S5）
- **F7** 无预算约束的 Loop：心跳×子 Agent×迭代×工具调用 → 一晚烧掉一月预算 → 文章处置：严格限制频率、子 Agent 数、单次 token 上限 → **可构造**：设定小预算，注入会无限重试的任务，期望超限中止（对应 S2）
- **F8** Loop 顺畅运行 → 人停止审查、停止质疑（认知投降），理解缺口不在任何指标报警，直到跨模块 debug 时爆发 → 文章处置：前两周逐次 review、逐步降频、定期 code walkthrough → **难以构造为回归 Case**（人的行为），只能作为观测量（S7）
- **F9** 修复施加在错误层 → 症状反复出现，团队对 Agent 失信 → 文章处置：先定层再修 → **可构造**：同一 Case 连续两次在同层修复后仍复发，期望流程要求换层（对应 D-003 扩展、S6）
- **F10** 子 Agent 之间依赖形成死锁或循环依赖 → Loop 挂起或空转 → 文章只列风险 → **可构造**：两个子任务互相等待对方产物，期望超时检测与升级（对应 S2 轮次上限）
