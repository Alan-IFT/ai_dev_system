# WX-36 靠这10个优化点，我们把Multi-Agent工作流成本降了50%以上

## 0. 验证边界
- 材料性质：一手实践报告的**公众号转载**（原发 WX-18，一个月后由腾讯技术工程重发）。作者团队用内网 CodeBuddy + AgentLens 度量；无外部可复核原始数据、无重复运行、无消融、无端到端对照（作者自述"后续将补齐严格的端到端 A/B 复核"）。

## 1. 文章在讲什么
与 WX-18 完全相同：1 个长生命周期调度 Agent（tech-leader）+ 6 个短生命周期子 Agent 跑前后端全流程；先按 Wave/Session 拆出消耗分布，把消耗归为六类来源；围绕"只看当前需要的 / 减少无关的 / 减少重复的"三原则做十个方向改造（渐进式披露、确定性操作脚本化、外部数据获取子 Agent 化、长期记忆索引化、单 Agent 拆多 Agent、角色工具白名单+模型分层、代码图谱、稳定前缀+状态外化、避免重复加载 Skill、CLI 输出压缩、无依赖调用并行）。作者报告主 Agent 端到端 token -55.5%、子 Agent 化后单会话 input -38.4%、代码图谱总 token -22.7%、SKILL.md 正文 -35%，并据分项降幅**反推**全流程 token 成本可降 50%~65%。本版标题把这一反推写成"成本降了 50% 以上"的既成事实。

## 2a. 专项审计："50%"到底是什么口径
| 问题 | 核查结果 |
|---|---|
| 标题"成本降了 50% 以上"的数字从哪来 | 4.2 末尾"全流程反推 50%~65%"。原发版标题"Token 降本 50%"，转载版改为"成本"，正文一字未改 |
| 是原始 token 计数还是成本加权 | **原始计数**。全文所有表格只有 token 数与百分比；没有按缓存读/未缓存/输出加权，没有货币或 Credit。作者引用的 GitHub Blog 恰好定义了加权口径（ET = m×(1.0×I + 0.1×C + 4.0×O)），文章未采用 |
| 有无端到端对照 | **无**。唯一端到端数字（主 Agent 708,783→315,266）是十项叠加后各 1 次运行，只覆盖 TL 一个 Session（图 003 显示最贵的是测试 Wave，不是 TL），且 TL 优化前 708,783 与图 003 中 TL 的 1,358.8k 不是同一次运行，基线本身漂移。作者明确写"后续补齐严格的端到端 A/B 复核" |
| 反推的输入本身可靠吗 | 分项区间中：-38.4%（n=1）、-22.7%（n=1 且成本加权后近零，见下）、-64%（价格比）、60%-90%（工具官方 bytes/4 估算）、-35%（静态行数，不是运行时 token）。五个输入没有一个是可复现的成本测量 |
| 缓存基线对结论的影响 | 图 003：优化前缓存命中率 93.5%，未缓存输入仅占 token 的 6.5%；按 0.1× 计，缓存读占**成本**约 59%、未缓存占 41%。因此"减少缓存读 token"对成本的贡献只有对计数贡献的 1/10；任何以原始计数报告的降幅都系统性高估成本降幅 |
| 代码图谱表按成本加权后 | 读者重算（缓存读 0.1×、输出 1×）：128,074 vs 137,194，**-6.6%**；按 GitHub ET（输出 4×）**-6.0%**；若按最新模型缓存读 0.025×（Anthropic 文档，Fable 5.1/Mythos 5.1），则为 **+6.6%～+8.8%，方向反转**。原因是缓存未命中 +24.8%——图谱查询结果是新内容，每次都按全价计费 |
| -55.5% 的构成 | 每轮均值 41.7k→35.0k 仅 -16%；-55.5% 的主体来自轮次 17→9。轮次减半来自并行化与子 Agent 化（结构改动），不是上下文瘦身；且未报告缓存命中/未命中拆分，无法加权 |
| 结论 | 标题数字 = 用 n=1 的原始 token 计数与工具官方估算反推出的区间，无对照、无加权、无重复。按 D-025，它既不是整体结果层的测量，也不满足端到端 A/B 成立条件；按本项目数字纪律，只能登记为"作者预估"，标题的既成事实表述属于转载时的措辞升级 |

**阿里技术文章的价值**：它解决了 WX-18 留下的"90% 从哪来"问题——不是作者编的，是二手综述加的，再被本文当一手转引。这是一个可复现的失败样本：**二手来源给概念配了数字，三手引用时数字和概念一起被归给一手**。对本项目来源矩阵的含义：登记引用时"概念出处"与"数字出处"要分列。
