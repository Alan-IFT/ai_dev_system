# WX-07 从Vibe Coding到Harness—— 一套大仓AI工程化实战

## 0. 验证边界
- 一手实践报告：腾讯内部 A/B 实验平台 TAB（30+ Go 微服务 + 10~12 个前端微应用 + 多端 SDK，多工作区多子仓库大仓）团队自述的 Harness 搭建与演进过程。作者即设计者，无第三方复核。
- 无对照组、无消融。全部数字（打回 1.8→0.4 次、集成测试一次通过率约 70%、代码审查阻塞率约 25%、端到端 30~75 分钟、人工按钮 2~3 次、"避免 80% 在错的子仓库里改"、"概率降低一个量级"、主 Agent 代码减少约 200 行、"80% 概率应该删掉"）均为作者在"跑了 50+ 真实需求"后的自述观察，样本量、统计方法、时间窗口均未给出；其中"80% 概率应该删掉"与"避免 80%"是经验性估计而非测量。
- 文中的覆盖率阈值在不同小节自相矛盾（§1.2"新增 ≥85%"、§2.1"服务层 ≥70%/数据访问层 ≥50%"、§2.2"增量 ≥80%"、§6.1 门禁表"全量 ≥40% 且增量 ≥85%"），说明这些是随时间变化的项目参数，不是稳定规则。
- 所使用的 IDE / Agent 产品全文未点名（只说"IDE 的 Team Mode"、"项目级自定义子 Agent"、"Are you sure you want to write to..."弹窗）。§7 的根因分析依赖该产品的内部消息路由机制，本卡片只能与 Claude Code 官方文档的 agent teams 机制作对照，**不能确认**文章所用的就是该产品。
- 内部系统（TAPD、iWiki、工蜂、Knot、企微）及其 MCP 均不可核实。文章未引用任何论文、外部博客或仓库；本卡片追读的是文中**隐含**依赖的一手资料（MCP 规范、agent teams/subagent 文档、YAGNI）。

## 1. 文章在讲什么
问题：在跨多子仓库的前后端大仓里，让 AI 从需求单开始独立跑完一个需求到 MR 提交，卡点不在模型写得不准，而在四件协作/流程/信任问题——PRD 不可信、方案对不上代码、改完没人验证、交付环节碎成一地。解法：先与团队磨出一份全链路 SPEC，再用六类资产（Rule / Skill / 子 Agent / Workflow / 门禁脚本 / MCP）搭 Harness；核心取舍是"能判定的规则全部下沉为脚本，能写成 bash 的不让 Agent 跑"，最终只留 11 个 Skill、4 个认知型子 Agent + 1 个总控、13 个阶段、7 道门禁（3 硬 4 软）、5 个人工关卡、5 个 MCP。文章用大量篇幅复盘撞墙：集成测试从后置改前置、Bug 复现从必走改可选、下游 Agent 偷改上游产物、弹窗审批密度、Team Mode 卡死三轮误修、AI 重复造轮子。作者声称的结果：50+ 真实需求上端到端 30~75 分钟、人工介入 2~3 次、代码审查打回从 1.8 次降到 0.4 次；并诚实列出限制（PRD 完整度强相关、≥3 子仓库变慢、前后端混合需求最难）。

## 2. 核心主张
- **C1** 大仓 AI 交付的瓶颈不是模型能力，而是协作、流程、信任与收口；Harness 主要是给团队用的，不是给 AI 用的。｜支撑：四个卡点的盘点（推理+案例）｜适用条件：多子仓库、多外部系统、多人并行的团队工程｜文中位置：§1.2
- **C2** Harness 落地第一步不是写 Rule 或拆 Agent，而是先形成团队共识的全链路 SPEC（子目标、AI 能跑完什么、人必须介入什么、一期完成定义）。｜支撑：推理（"没有 SPEC 会被搭歪"）｜适用条件：团队级 Harness｜文中位置：§1.3
- **C3** 自然语言 Rule 天然会被"解释性执行"（"这条不适用/我做了等价的事/这是历史问题"），因此凡是**有判定**的约束都下沉为 lint、脚本或静态扫描，独立 Rule 最少。｜支撑：四个下沉示例 + 三句典型借口｜适用条件：约束本身可机械判定｜文中位置：§2.1、§6.1
- **C4** Skill 的本质是注意力管理而非能力增强：把"具体怎么做"从主 prompt 拆出去按需加载，避免主 prompt 淹没需求上下文、避免改一条规矩要同步改每个 Agent。｜支撑：数据访问层规范手册的例子（推理）｜适用条件：分层规范多、Agent 多的工程｜文中位置：§2.2
- **C5** 子 Agent 只给认知型工作分工；流程调度、门禁、测试、提 MR 是纯确定性工作，下沉为总控状态机 + 脚本。"能写成 bash 的就别让 Agent 跑"是 Agent 数量的判断标准。｜支撑：4 个 Agent 的角色契约表（必读/必写/不许做）｜适用条件：链路中确定性环节占比高｜文中位置：§2.3
- **C6** Workflow 是"接力赛规则"而非流程图：每棒声明交付物、下一棒必读、打回规则、打回回到哪一棒，并且抽成可被脚本自检完整性的资产而非长文描述。｜支撑：13 棒定义 + 自检脚本（案例）｜适用条件：多阶段多角色｜文中位置：§2.4
- **C7** 阶段是否应独立只看两条：是否有独立的失败模式；失败时回退位置是否不同。两个都是才独立，否则合并。｜支撑：13 个阶段逐一过筛的表（案例+推理）｜适用条件：通用｜文中位置：§3.1、§3.4
- **C8** 便宜且快的验证必须排在昂贵验证之前（接口测试前置到代码审查之前并设为硬门禁）；同时"开发完成"的定义应包含验证手段本身——让产生问题的人同时产生验证手段。｜支撑：打回 1.8→0.4 次（无对照，且与"完成定义变更"同时发生）｜适用条件：存在成本差异悬殊的多道验证｜文中位置：§3.2、§4.4
- **C9** 流程要给"已经清楚的事"留快车道：强制所有需求走最严格路径等于惩罚准备充分的需求（Bug 复现从必走改为条件触发）。｜支撑：案例｜适用条件：输入质量差异大｜文中位置：§3.3
- **C10** 下游 Agent 不可直接修改上游产物，只能提阻塞项由总控打回上一棒——这是责任边界问题，比任何 prompt 调优都关键。｜支撑：方案 Agent 偷改验收标准导致审查时分不清谁要的（案例）｜适用条件：多角色链路｜文中位置：§4.2
- **C11** 收口角色必须与生成角色分离，且审查的第一维度是"方案一致性"，专抓 AI 顺手改设计的解释性执行。｜支撑：单 Agent 自审"几乎不会否决"的观察｜适用条件：通用｜文中位置：§4.1、§4.3
- **C12** 模型对自己或"自己人"生成的东西缺乏否决欲望，这是模型层面的偏置，prompt 控制不了；因此关键节点必须留人，半自动是当前唯一稳定可推广的形态。｜支撑：试过 Reviewer Agent 判断方案能否进开发，"99% 觉得挺好"（观察，无数据）｜适用条件：当前模型代际｜文中位置：§5.1
- **C13** 人工关卡有体感上界："让用户每分钟点一次以上"就是设计 bug；体感不对团队会绕过工具退回 Vibe Coding。｜支撑：5 个关卡的耗时/频率表 + 弹窗审批密度事故｜适用条件：团队推广场景｜文中位置：§5.2、§5.3、§7.6
- **C14** 硬门禁宁少不多：只有质量红线才阻断；软门禁失败不阻断但必须在门禁状态、审查结论和度量报告三处留"伤疤"——不能阻止 AI 偷懒，但可以让偷懒醒目。｜支撑：7 道门禁表（3 硬 4 软）｜适用条件：通用｜文中位置：§6.2、§6.4
- **C15** 基线对比反作弊：开发前冻结门禁失败集合 A，开发后得到 B，只有 B−A 阻断；目的是剥夺 AI 的"历史问题"解释权。｜支撑：设计描述 + "花了好几轮才意识到必须做"｜适用条件：存量仓库带历史失败｜文中位置：§6.3
- **C16** 当一个机制的存在主要是为了修复它自己引入的副作用，它大概率应该删掉（"复杂度自给自足"）；修 bug 前先确认自己是否真的用到了该机制的独有能力；YAGNI 在 Harness 设计里尤其重要。｜支撑：Team Mode 三轮误修后整体删除，辅助脚本 3→0（案例）｜适用条件：通用｜文中位置：§7.4、§7.5
- **C17** 大仓里 AI 缺"项目记性"会重复造轮子；解法是仓库内两层索引——由开发 Agent 维护的代码导航地图（讲"工程长什么样"而非文件列表）+ 由总控维护的跨需求任务看板；需求 Agent 启动先读两者再动手。｜支撑：三类重复造轮子现象 + "避免 80%"/"降一个量级"（自述估计）｜适用条件：多子仓库大仓｜文中位置：§8.1、§8.2
- **C18** 团队要对齐的东西必须落到仓库（可审计、可交接）；产品侧 Memory 只放纯个人偏好，否则多人 Memory 互相矛盾且无人知道哪个是真的。｜支撑：推理（4 名工程师并行场景）｜适用条件：多人团队｜文中位置：§8.3
- **C19** MCP 不是万能钥匙：外部交互收敛为有明确入参、语义和审计痕迹的方法；读多写少；写操作只在初始化与交付收尾两个阶段触发；写必须幂等；MCP 失败软降级只警告不阻断；先做开发闭环再接 MCP。｜支撑：5 个 MCP 的触发时点表 + 双通道（MCP + 子进程 OAuth2）排障不一致的教训｜适用条件：有多个外部写入系统｜文中位置：§9.2、§9.3
- **C20** Harness 由四块拼图组成：约束与流程、反馈、知识库、进化；缺任一块有对应的可观察症状。Harness 不是设计出来的，是哪儿痛补哪儿长出来的。｜支撑：缺块症状表｜适用条件：通用｜文中位置：§10.1、§10.3

**MCP Tools 规范对本项目的价值**：它把"人能否决工具调用"和"审计记录"写成了协议层的 SHOULD，而把幂等/只读写成不可信的注解——这恰好印证本项目"Prompt 不是安全边界、注解也不是安全边界"的立场：文章的读写分阶段、幂等判重、写入留痕都必须在服务端或 Harness 层实现，协议不替你做。可作为 05 章"高风险动作限制靠权限与工具层"的一手佐证。

**Agent teams 文档对本项目的价值**：官方自己列出的限制（无恢复、状态滞后、lead 固定、权限 spawn 时继承）与文章的撞墙高度对应，说明文章 §7 不是个例而是该类机制的结构性代价；同时官方"先看更轻的选项是否够用"与本项目 D-010 复杂度阶梯完全同向。

**冲突一：外部写入软降级 vs 完成必须绑定回读证据。** 文章规定 MCP 写失败只警告不阻断，"下一轮交付收尾自然补推"。本规范 D-009/D-017 要求"已发布/已验收"必须绑定目标系统回读；若 TAPD 状态未改成功而流程已宣告交付，状态源就分叉了。文章证据：只有"网络抖一下主流程整个挂掉"的体感理由，未描述未完成写入的登记与补偿机制。本规范证据更强（状态分叉是可复现失败）。可共存条件：软降级允许，但未成功的外部写入必须进入显式的待补偿记录，且"已交付"状态不得在补偿完成前宣告。
**冲突二：开发者自产验证手段 vs 实现者不得弱化验收。** 文章让开发 Agent 自己写接口用例与接口测试，本规范 05 §担心实现者写弱测试让自己通过。文章的缓解是审查 Agent 的"验收标准覆盖"维度 + 真实 HTTP 沙箱；但用例与实现同源的风险文章未讨论。可共存：产生者提供验证手段，但验证手段本身要被独立角色对照验收标准审查。
**冲突三（轻）：C2"先写 SPEC"与本规范§7"先跑真实任务"。** 两者都无对照证据；可共存——SPEC 划的是责任边界，真实任务建的是基线，顺序可由项目定。

## 6. 建议采纳（候选语义）
- **S1** 阻断条件只对"变更引入的新增失败"成立：验证前必须冻结变更前的失败集合并绑定其版本，阻断判定 = 变更后失败集合 − 变更前失败集合。｜落地 A（检查器）：门禁程序自带快照/差异两种模式，输出差异结果为证据｜落地 B（外部状态存储 + 人工检查点）：变更前把已知失败清单登记在状态工件里，验收人只对不在清单中的失败追责｜它防御的失败：AI 以"历史问题"为由让存量失败与新增失败混为一谈，人无法逐条核验｜删除条件：仓库主线达到零已知失败且持续保持时，基线恒为空，此规则退化为普通阻断。
- **S2** 一个流程阶段是否独立存在，须同时满足：它有与相邻阶段不同的失败模式；它失败后的回退目标与相邻阶段不同。不满足则合并。｜落地 A（静态指令 / 流程定义文档中的判据）：新增状态时要求写明两项｜落地 B（检查器）：对状态机定义做完整性校验，每个状态必须声明 failure_transition 且不得与相邻状态完全相同｜它防御的失败：阶段过多产生隐式分支与重复副作用（如需求打回时反复改外部单状态），阶段过少让不同失败共用一条回边｜删除条件：写不出。
- **S3** 每类工件只能由一个角色写入；其他角色对该工件的异议只能以阻塞项形式提出，并经流程回到该工件的所有者。｜落地 A（权限与隔离配置）：按角色限制可写路径/工件类型｜落地 B（人工检查点 + 检查器）：审查阶段对比上游工件在下游阶段是否被修改，修改即失败｜它防御的失败：下游角色顺手改上游验收标准，审查时分不清哪句是产品要的、哪句是 AI 加的（责任边界崩塌）｜删除条件：模型能可靠区分并标注"引用的意图"与"自己的推断"且下游可机械核验时。
- **S4** 多道验证按成本升序执行，便宜且快的判定必须先于昂贵判定，昂贵判定不得为便宜判定本可拦截的失败重复付费。｜落地 A（条件加载规则 / 流程定义）：阶段顺序声明中标注每道验证的相对成本并按序排列｜落地 B（运行时拦截）：昂贵验证的入口拦截器要求便宜验证的通过凭证存在｜它防御的失败：整段 diff 审查通过后被几秒钟的接口测试打回，审查全部重做｜删除条件：昂贵验证的成本降到与便宜验证同量级时。
- **S5** "实现完成"的定义包含该实现的验证手段（用例与可执行验证），由产生变更的角色一并交付；验证手段本身由独立角色对照验收标准审查。｜落地 A（检查器）：完成门禁检查验证工件是否存在且覆盖验收标准｜落地 B（人工检查点）：验收人拒绝没有附带验证手段的完成声明｜它防御的失败：验证被推到下游，下游成本高于上游且无法追溯｜删除条件：写不出。
- **S6** 非阻断的检查失败必须留下被下游必然消费的痕迹：至少进入状态记录、审查输入和最终交付报告三处之一以上，且跳过检查须留可见记录。｜落地 A（外部状态存储）：警告记录写入状态工件并被审查阶段必读｜落地 B（检查器）：交付报告生成器汇总所有非阻断失败与跳过项｜它防御的失败：软检查失败被静默吞掉，"跳过"与"通过"不可区分｜删除条件：写不出。
- **S7** 对外部系统的写操作只在显式声明的阶段窗口内允许，其他阶段只读；每次写操作必须幂等（重复执行无副作用）且在交付物中留痕（时间、对象、变更前后值）。｜落地 A（权限与隔离配置）：按阶段切换外部工具的写权限｜落地 B（运行时拦截 + 外部状态存储）：写调用前校验当前阶段，写后追加审计记录｜它防御的失败：AI 半路改坏外部系统状态；重跑交付阶段灌入重复关联；改错后无法定位｜删除条件：写不出（责任不可转移类）。
- **S8** 外部写入失败允许不阻断主流程，但未成功的写入必须进入显式待补偿记录，且依赖该写入的状态（如"已交付"）在补偿完成前不得宣告。｜落地 A（外部状态存储）：待补偿清单作为状态工件，交付收尾读取并重试｜落地 B（检查器 / 状态转换 Gate）：进入"已交付"前检查待补偿清单为空｜它防御的失败：外部状态源与内部状态分叉，"网络抖一下"变成静默的假交付｜删除条件：写不出。
- **S9** 人工检查点的密度有体感上界：设计时须记录每个检查点的预期人工耗时与触发频率，并把"人被高频打断"视为 Harness 缺陷而非人的问题。｜落地 A（人工检查点设计约束 / 静态指令）：检查点清单必须带耗时与频率字段｜落地 B（外部状态存储 + 检查器）：记录实际打断次数，超过阈值触发复查｜它防御的失败：团队因体感差绕过 Harness 退回无约束模式（采纳失败）｜删除条件：写不出。
- **S10** Thin 的新增信号：当某机制的维护工作主要在修复它自己引入的副作用、且其独有能力在真实轨迹中未被使用，应先删除该机制而非继续修补；修补前先核实独有能力是否被使用。｜落地 A（外部状态存储 / 轨迹）：统计各机制的能力使用记录｜落地 B（人工检查点）：复盘时先回答"我们用过它的什么独有能力"｜它防御的失败：三轮局部止血后根因未动，辅助脚本越加越多｜删除条件：写不出。
- **S11** 项目级"工程长什么样"的导航知识由改动者负责更新，跨任务的进行中状态由调度角色负责维护；新任务在理解阶段先读两者以判断影响范围与是否为旧任务延续。｜落地 A（外部状态存储 + 条件加载规则）：导航工件与看板工件作为需求阶段必读输入｜落地 B（人工检查点）：需求确认时人核对影响范围是否与地图一致｜它防御的失败：在错的子仓库里改、重复造轮子、新需求冲掉旧设计｜删除条件：工具能在会话内可靠检索全仓库结构并识别既有实现时。

## 7. 明确不采纳

## 8. 该文暴露的失败模式
- **F1** 单 Agent 跑全流程 → 分不清"需求单里写的"与"自己推断的"、自审不否决、主动找理由继续推进、上下文 1M 不够 → 拆为需求/方案/开发/审查四角色 + 总控 → 可构造：给单 Agent 一份含歧义的需求，检查产物中推断是否被标注为事实。
- **F2** 方案 Agent 顺手修改需求理解文档中的验收标准 → 审查时无法区分产品要求与 AI 增补 → 下游不可改上游产物纪律 → 可构造：上游工件的哈希在下游阶段前后对比。
- **F3** 接口测试置于代码审查之后 → 几秒可发现的路径/参数错误让整段审查重做，打回循环 → 接口测试前置为硬门禁，完成定义含接口测试 → 可构造：注入一个接口路径错误，测量到达审查阶段前是否被拦。
- **F4** 强制所有 bugfix 走沙箱复现 → 对已写清"请求/期望/实际"的单子浪费数分钟 → 改条件触发 → 可构造：高质量输入被强制走全路径的耗时对比（属误伤 Case）。
- **F5** AI 对门禁失败声称"历史问题/不是我引入的" → 人无法逐条核验 → 变更前基线快照，只阻断 B−A → 可构造：仓库预置一个存量失败 + 变更引入一个新失败，检查只有后者阻断且前者不能掩盖后者。
- **F6** 子 Agent 调起时未声明权限模式 → 每写一个文件弹一次确认，一次需求分析弹 3~5 次、开发几十次 → 半自动退化为全人工，团队体感崩 → 显式声明权限模式 → 可构造：统计单需求的人工确认次数与阈值对比。
- **F7** 人工关卡应答被路由到已结束本轮对话的主控收件箱 → 必现卡死、重启才恢复；三轮症状修复（清标记/改超时/改文本输入）全部无效 → 检查实际收件箱状态发现根因，整体删除该机制 → 可构造：在检查点后注入用户输入，验证存在活跃消费者且恢复不依赖会话存活。
- **F8** 双通道外部写入（MCP + 子进程 OAuth2）→ 审计与排障路径不一致、凭据依赖 → 收敛到单通道 → 可构造：同一外部写操作的审计记录是否唯一可追溯。
- **F9** 交付收尾重跑 → 外部系统被灌重复关联 → 写操作按 (仓库, 分支) 判重 → 可构造：交付阶段执行两次，外部记录数不变。
- **F10** 开发 Agent 不知仓库已有公共方法/错误码/数据访问方法 → 重复实现 → 仓库内导航地图 + 需求阶段先读 → 可构造：任务涉及已有工具方法，检查是否复用。
- **F11** 新需求在需求阶段未识别为旧需求延续 → 冲掉上一轮设计结论 → 跨需求任务看板 → 可构造：连续两个相关需求，检查第二个是否引用第一个的设计结论。
