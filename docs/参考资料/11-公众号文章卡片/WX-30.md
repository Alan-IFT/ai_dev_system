## 1. 文章在讲什么
作者认为企业 Agent 从演示到生产的分水岭不是模型而是运行时（harness），要回答三个问题：一次任务能访问什么、分散的领域经验怎样进入 Agent、几十上百步的工作状态放哪里。解法是三件套：统一 harness 承载执行与安全（会话/checkpoint、上下文管理、工具编排、权限与 HITL、skill 装载、文件与执行、streaming 与 trace）；skill 作为有 owner、版本、风险等级、评测集的可治理资产，用"预筛 + LLM 精选 + 动态注册工具"两阶段路由；虚拟文件系统（VFS）把证据、中间态、产物、checkpoint 按生命周期分区，并用 manifest 作为 artifact contract。安全上提出"有效能力 = 五重交集"和四道门（工具可见性 / 参数策略 / 执行隔离 / 人工审批），会话范围在网关固化、模型不可改。给出四阶段演进路径（资产基线 → 接入 harness → 两阶段路由 → trace-to-skill 闭环）、四组指标和五个坑。作者未声称任何结果，只声称这是"更接近生产系统的架构"。

## 2. 核心主张
- **C1** 模型决定单次推理上限，harness 决定能力能否稳定可控地进入企业流程；换模型不会自动产生权限隔离、失败恢复、资产治理和交付证据。｜支撑：推理｜适用条件：通用｜文中位置：01
- **C2** "一个场景一个 Agent"与"把 coding agent 直接发给所有人"都不可持续：前者基础逻辑分叉（重试/权限/审计/输出各异），后者把任意 shell 的安全风险和支持成本转嫁给用户。｜支撑：Stripe 4,000 Agent 案例（未核实）+ 推理｜适用条件：企业多领域｜文中位置：01
- **C3** 四层分离：入口（surface）→ 控制面（skill/配置/评测/质量信号，快变、领域所有）→ 企业 harness（身份/会话/权限/审计，企业特有）→ 通用 runtime（模型循环/middleware/checkpoint/streaming，只解决一次）。｜支撑：Stripe 在 Deep Agents 上叠加自身安全层（已核实）｜适用条件：多入口多领域｜文中位置：02 + 图 004
- **C4** 工具回答"能做什么"，skill 回答"什么场景、什么流程、用哪些工具、什么标准算完成"；完整 skill 含路由元数据、步骤与失败分支、依赖声明、脚本/参考/模板、正例与**近邻负例**、owner/版本/风险/变更记录。｜支撑：推理｜适用条件：通用｜文中位置：03
- **C5** Progressive disclosure 只解决一半：它省 token 但不消除目录选择错误；大目录需要"高召回预筛 → LLM 精选 → 只注册被选 skill 允许的工具"两阶段，无关工具**不出现在请求里**而非"不建议调用"。｜支撑：LangChain 披露 ~150 skills 时质量下降（已核实）｜适用条件：skill 数量达数十至数百｜文中位置：3.1 + 图 006
- **C6** 联邦所有权：平台管 schema/lint/发布/权限编译/评测/观测，领域管内容与验收标准，安全管强制政策，用户可在受控范围叠加；同名覆盖遵守 base → team → project → user。可复制的不是 Stripe 的组织结构，而是"平台不垄断知识，领域不能绕开平台约束"。｜支撑：Kai 三层技能（已核实）｜适用条件：多团队｜文中位置：3.2
- **C7** 只把 SKILL.md 放进 Git 不够：registry 要把 owner/风险/allowed_tools/data_scopes/surfaces/eval_suite/status 作为一等字段，并**编译**出运行时工具白名单、HITL 规则、可用入口和评测任务；CI 检查无 owner 的 promoted skill、"有写风险但无审批策略"等结构问题。｜支撑：作者设计草案｜适用条件：作者场景｜文中位置：3.3
- **C8** Skill 评测先测"有没有选对"（触发/混淆/组合/拒绝硬套），再测"做得好不好"（工具/证据/产物结构/越权）；最有价值的测试是近邻负例；目录越大越应报告 top-1、top-k、误触发率、漏触发率、token 成本和具体混淆对。｜支撑：推理｜适用条件：大目录｜文中位置：3.4
- **C9** VFS 给 Agent 一个稳定、可寻址、跨轮次的工作空间；目录不是整洁问题而是**信息生命周期**：evidence 只读、working 可变、artifacts 是承诺、shared 须显式发布——"临时推理状态不会无意中变成组织事实"。｜支撑：推理｜适用条件：长任务｜文中位置：4.1
- **C10** VFS 与 sandbox 必须是两个边界：Agent 在受控服务中运行，sandbox 作为工具调用；sandbox 保护宿主，不代表其内数据安全——输入文件、网络、凭证、时长、CPU/内存、输出大小、sync-out 路径都要单独约束。｜支撑：Kai "agent runs outside the sandbox"（已核实）｜适用条件：需代码执行的任务｜文中位置：4.2 + 图 007
- **C11** 摘要、文件、checkpoint 三者不可互替：只有摘要丢细节，只有文件丢决策过程，只有 checkpoint 则每次调用背负全部上下文。｜支撑：推理｜适用条件：长会话｜文中位置：4.3
- **C12** 生成 report.md 不等于交付；manifest 作为 artifact contract 记录来源（路径+hash）、会话范围、validation 四态（local / remote_pipeline / deployed / accepted）和审批；最终响应引用 manifest 状态而不是模型自由描述"已经完成"。｜支撑：作者设计草案｜适用条件：通用｜文中位置：4.4、06
- **C13** 有效能力 = 用户授权 ∩ Agent 配置 ∩ 所选 skill 策略 ∩ 会话/任务范围 ∩ 工具侧强制；用户全部权限不应自动成为一次任务的全部权限；scope 在会话创建时绑定，工具服务端复核，模型换参数写法或 sandbox 脚本都不能扩大。｜支撑：推理 + Deep Agents "boundaries at tool/sandbox level"（已核实）｜适用条件：多租户/多客户｜文中位置：05
- **C14** Prompt 不是安全边界；框架自带的声明式权限只约束内建文件工具，不覆盖自定义工具、MCP 和 sandbox，所以 allowed-tools、MCP 权限、sandbox policy、业务 API 授权必须组合使用。｜支撑：Deep Agents permissions 文档（已核实，且文档还说"无规则匹配时默认允许"，文章未提）｜适用条件：使用任何框架｜文中位置：05
- **C15** 状态分三类：SessionContext（创建后模型不可改）、AgentState（可 checkpoint）、ArtifactState（只存路径与索引）；不可变范围不混在模型可编辑的文件或消息里，避免一次 summarization 意外改变权限、避免 checkpoint 反复序列化大文档。｜支撑：推理｜适用条件：通用｜文中位置：06
- **C16** 演进四阶段：资产与风险基线（registry/lint/eval baseline，不是新聊天页）→ 用高频、读多写少、有明确 artifact 的流程试点 → 目录只有几十项时**先测纯 LLM 路由**，只有预筛在五项指标上净收益才引入 → trace 发现缺口自动转为候选回归用例，但生产 Agent 不直接改生产 skill。｜支撑：推理 + LangChain "pure LLM selection works well at current scale"（已核实）｜适用条件：已有存量工具体系的企业｜文中位置：07
- **C17** 指标分母必须明确（80/100 还是 80/85），业务效果要区分相关与因果，上线前保留对照基线。｜支撑：推理｜适用条件：通用｜文中位置：08
- **C18** 五个坑：harness 变超级 prompt；allowed-tools 当完整授权；VFS 当无限期知识库（无发布流程和 TTL → 数据沼泽）；过早多 Agent；只验证成功路径。｜支撑：推理｜适用条件：通用｜文中位置：09

- 图 001–003（文首）、010–016（文末）：公众号星标提示、二维码、会员推广、三篇关联文章 banner、点赞引导。纯装饰，无信息。
- **图 004**（02 开头，"拆成四层"之后）→ **本文最重要的信息载体之一**，ATT-G 丢失。实际画的是**七个框、不止四层**：顶部并列两个入口——Surfaces（Web/IM/浏览器扩展/内部系统）与 Control Plane（Agent 配置/Skill 目录/Eval/质量与使用信号）——都指向 Enterprise Harness（身份/会话/权限/工具策略/审计）；其下 Agent Runtime（模型循环/Middleware/Checkpoint/Streaming）；Runtime 分出两支：Enterprise Tools（MCP/API/数据仓库/搜索）和 Isolated Execution（Sandbox/Python/文档处理）；底部 Virtual Filesystem（证据/中间状态/Artifacts/Memory）同时接收 Runtime 与 Isolated Execution 的边。正文没说的两点：(a) 控制面与入口是**并列**进入 harness，即 skill 目录不经 runtime 直接作用于 harness 的策略层；(b) Enterprise Tools **不**连 VFS，只有 Runtime 和 Sandbox 写 VFS——工具结果要经 runtime 落盘为证据，这与 C12/图 008 的"原始结果写入 evidence/"一致。
- **图 005**（02 "Harness 应该拥有的最小职责"）→ 七行三列表，ATT-G 丢失。列为"职责 / 要解决的问题 / **不应依赖什么**"：会话与 checkpoint ↔ 单个常驻进程不退出；上下文管理 ↔ 无限增长的 message list；工具编排 ↔ 只靠模型"自觉不用"；权限与 HITL ↔ prompt 中的安全提醒；Skill 装载 ↔ 一个无限增长的 system prompt；文件与执行 ↔ Agent 直接运行在宿主机；Streaming 与 trace ↔ 只有最终一段回答。第三列是正文完全没有的信息：每个 harness 职责都被绑定到它**替代的脆弱做法**——这正是 D-021"规则绑定它防御的失败"在组件层面的写法。
- **图 006**（3.1 "两个阶段"之后）→ 六步流程：① 用户任务 → ② 规则/分类器检索预筛 → ③ Top-K Skills → ④ LLM 最终选择 → ⑤ 读取 SKILL.md → ⑥ 动态注册允许的工具；底部标语"无关工具不再出现：更省 token，也更安全"。图明确了预筛是**规则或分类器**（非必然向量检索），且工具注册在 skill 读取之后，即工具集是 skill 选择的**输出**。
- **图 007**（4.2）→ 时序图，四个参与者：Agent Runtime / Virtual Filesystem / Per-session Sandbox / Object Store。步骤：Runtime 写 working/input.csv 与 analyze.py 到 VFS → VFS 持久化文件和版本到 Object Store → Runtime 调 execute(analyze.py) 到 Sandbox → VFS **sync-in 允许的输入与脚本** → 隔离执行 → **sync-out 新增或修改文件**回 VFS → 保存图表、结果与 hash 到 Object Store → Runtime 读取结果生成 artifacts/report.md。携带的正文没有的细节：sync-in 是白名单（"允许的"），sync-out 只回传增量，且 hash 在落盘时生成——证据 hash 是 VFS 层的职责，不是模型的。
- **图 008**（06 "可观测、可阻断的执行链"）→ **本文最重要的信息载体**，ATT-G 丢失。七个参与者：User/Surface、Session Gateway、Skill Catalog、Harness、Tool Gateway、VFS、Approval。14 步：提交任务+project+environment → Gateway **鉴权并冻结 session scope** → 检索候选 skills → Catalog 返回 Top-K 元数据与政策 → Harness 用 LLM 选 skill 并装载 SKILL.md → 注册该 skill 的允许工具 → 查询变更与流水线（**携带 session capability**）→ Tool Gateway **再次校验项目、环境与读写范围** → 原始结果写入 evidence/ → 生成 working/ 与 artifacts/ → 请求"发布 iWiki"批准 → approve/edit/reject → 执行发布 → 更新 manifest 与交付状态 → 返回产物、证据摘要和真实状态。图揭示的结构：权限被检查**两次**（网关冻结 + 工具网关复核），能力沿链路**单调收窄**（scope → Top-K → 1 skill → 允许工具 → 参数范围），审批发生在写调用**之前**且有 edit 分支，最终状态来自 manifest 而非模型。
- **图 009**（08）→ 四维指标表，ATT-G 丢失：任务结果（完成率、artifact 被采用率、人工返工量、端到端耗时）；路由质量（skill top-1/top-k、误触发、漏触发、工具选择正确率）；运行质量（恢复成功率、平均步骤数、token、P95 延迟、sandbox 失败率）；风险治理（越界请求拦截、HITL 触发/拒绝率、跨 scope 访问、**无来源产物比例**）。"无来源产物比例"和"恢复成功率"是现有指标候选里没有的。

1. **LangChain Kai 博客**：这是本轮少见的、可核实的"skill 目录规模 × 选择质量"观察点——150 个、frontmatter ≤1,024 字符、叠加 system prompt、frontier model。它是一个**单团队单条件**的观察，不能推成阈值；但它给 D-026（规范自身规模）和 ATT-N（skill 膨胀）提供了一个来自厂商案例的旁证：目录级的注意力退化在"每项只有一句描述"时也会发生。同一博客还说明"当前规模下纯 LLM 选择优于 RAG"，支持本规范"先测再加机制"（D-013、07 §1）。采纳数字（83%、60k sessions）无对照，只是使用量，不是效果。
2. **Deep Agents Permissions 文档**："无规则匹配即允许 + 不覆盖自定义/MCP/sandbox"是一条**可复现的失败模式**：一个只配了文件权限的 harness 会在 MCP 工具上零约束。它把 ATT-M/ATT-G 的"prompt 不是边界"推进到"框架的声明式权限也不是边界"，可直接进 D-021 的失败绑定。
3. **Deep Agents Subagents 文档**："权限默认继承、工具不继承"说明多 Agent 的权限图不是自动收窄的——子代理拿到父的全部权限却只有指定工具，权限与工具集的交集在子代理处**未必**重新计算。这是 D-028（角色图慢变）与 C13（多重交集）在多 Agent 场景的一个具体缺口。

## 6. 建议采纳（候选语义）
- **S1** 能力沿请求链路只能单调收窄：任务范围在会话建立时固化，后续每一步（方法选择、工具暴露、参数范围）只能是前一步的子集，且至少在两个不同位置被检查。｜落地方式 A（权限与隔离配置）：会话建立时把租户/项目/环境写入不可变凭据，工具服务端按凭据拒绝越界请求｜落地方式 B（运行时拦截）：在工具调用发出前由拦截器比对参数与会话范围，越界即阻断并记录｜它防御的失败：模型换一种参数写法、或在沙箱脚本里直接调 API，读到会话范围外的数据（F1）｜删除条件：写不出——这是责任判据（只有人能承担越权后果），不随模型能力消解
- **S2** 方法/技能的选择正确性是独立于执行质量的评估对象：评估集必须包含"该触发未触发""不该触发被触发""近邻混淆"三类 Case，并报告混淆对。｜落地方式 A（检查器）：离线回放任务集，对比选中的方法与标注答案，输出 top-1/top-k 与混淆对｜落地方式 B（外部状态存储 + 人工检查点）：在轨迹记录里保留"候选方法列表与最终选择"，定期由方法 owner 抽查误选｜它防御的失败：目录增长后相邻方法互相抢占，执行本身正确但用错了流程（F4）｜删除条件：模型在给定全部候选描述时的选择错误率长期低于人工标注噪声
- **S3** 每个 harness 组件登记时必须写明它替代的脆弱做法（"不应依赖什么"）。｜落地方式 A（静态指令/文档）：组件清单附"替代的脆弱做法"列｜落地方式 B（检查器）：Add 记录缺该字段时拒绝合并｜它防御的失败：组件只增不减、无法判断何时可删（ATT-N/ATT-O 描述的膨胀）｜删除条件：D-021 若被接受则本条并入 D-021，本身不独立存在
- **S4** 执行隔离与数据边界是两条独立约束：隔离环境的输入必须是白名单、输出必须限定回写路径与大小，且隔离本身不豁免数据范围检查。｜落地方式 A（权限与隔离配置）：沙箱只挂载被允许的输入，网络与凭据默认关闭，回写目录限定｜落地方式 B（检查器）：回写前对产出文件做路径/大小/来源校验，不合规不落盘｜它防御的失败：模型生成的脚本在沙箱内读到不该读的输入，或把结果写到共享目录冒充组织事实（F2）｜删除条件：写不出
- **S5** 完成声明必须引用结构化的交付状态记录，而不是由模型自由描述；该记录至少区分本地验证、远端验证、已发布、已验收四态并绑定来源与哈希。｜落地方式 A（外部状态存储）：产物清单文件/记录，最终回复只引用其字段｜落地方式 B（运行时拦截）：拦截含"已完成/已发布"措辞而无对应状态记录的回复｜它防御的失败：模型说"已经完成"但远端流水线未跑、未验收（F5）｜删除条件：写不出——这是验收责任
- **S6** 原始证据自写入起只读；进入共享/组织级空间必须经过显式发布动作并留下发布者。｜落地方式 A（权限与隔离配置）：证据区对执行者只读｜落地方式 B（人工检查点 + 外部状态存储）：发布是带审批人的状态转换｜它防御的失败：模型"修正"原始证据以自洽；临时推理产物被后续会话当成事实（F6）｜删除条件：写不出（已在 D-007/D-009 覆盖，此处只是强化）
- **S7** 平台指标必须声明分母，并区分"进入执行的任务"与"全部请求"。｜落地方式 A（检查器）：指标定义无分母字段即不接受｜落地方式 B（人工检查点）：评审时要求给出分母｜它防御的失败：完成率因排除拒绝/取消而虚高（D-023 指标被满足而目标被背叛）｜删除条件：写不出

## 8. 该文暴露的失败模式
- **F1** 用户同时有客户 A、B 权限，任务限定 A → 模型改写参数（或经 sandbox 脚本直调 API）读取 B 数据 → 文章处置：会话建立时绑定 customer_id，工具服务端复核，sandbox 同受约束 → **可构造回归 Case**（D-027 后续验证栏所列 Case 即此）
- **F2** 只配置了框架内建文件权限，未覆盖自定义工具/MCP/sandbox；且框架无规则匹配时默认放行 → Agent 通过 MCP 工具或 execute 绕过文件权限 → 文章处置：allowed-tools、MCP 权限、sandbox policy、业务 API 授权组合使用 → **可构造**（Deep Agents permissions 文档明确此边界，可在任一框架复现"权限只覆盖一类工具"）
- **F3** 长会话触发 summarization，会话范围/权限信息与消息混存 → 摘要改写或丢失范围，后续调用以错误范围执行 → 文章处置：不可变 SessionContext 与 AgentState 分离 → **可构造**（把 scope 放进 messages 后强制压缩，检查压缩后 scope 是否仍可得）
- **F4** skill 目录中存在近邻对（"查询构建日志" vs "下载构建制品"；"创建 Issue" vs "修复已有 MR"）→ 模型选中相邻 skill，执行本身无误但流程错 → 文章处置：近邻负例进评测集，报告混淆对 → **可构造**（评估层 Case，需标注集）
- **F5** Agent 生成 report.md 并回复"已完成" → 远端流水线未跑、未部署、未验收 → 文章处置：manifest 四态 + 响应引用 manifest → **可构造**（D-009/D-017 的"报告过期""虚假完成"Case 的产物版）
- **F6** 模型在推理中"修正"原始证据文件使结论自洽；或 working/ 中间文件被后续会话读为事实 → 文章处置：evidence 只读、shared 需显式发布、VFS 带 TTL → **可构造**
- **F7** 只验证成功路径的 Agent 在权限拒绝、工具超时、发布中断、sandbox 资源耗尽、skill 冲突、证据过期时失败 → 文章处置：把这六类作为关键测试 → **可构造**（六个独立 Case 模板，属 06 §2 Case 注册表候选）
- **F8** 自动修复/自我改进 Agent 直接改写生产 skill → 无 owner 审查、无隔离回归 → 文章处置：trace → 候选 patch → owner review → 隔离回归 → 发布 → **可构造**（D-019/D-028 的"Agent 试图修改自身规则"Case）
- **F9** 多 Agent 中子代理默认继承父代理全部权限但只拿到子集工具 → 交集未在子代理处重算，权限面大于工具面 → 文章处置：无（只提"权限继承"是代价）→ **可构造**（来自 Subagents 文档，非文章本身）
