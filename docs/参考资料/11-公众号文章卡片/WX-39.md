# WX-39 从Prompt到Harness，给反馈分类装上方向盘

## 1. 文章在讲什么
AiSee 是腾讯内部面向多业务的用户反馈分析平台，反馈分类是其最基础、使用最频繁的能力，分类结果向下游驱动问题统计、任务归属和改进验证。早期用 Prompt 工程（分类树 + 角色 + 业务背景 + 判断要求 + 历史案例）跨过了"模型能不能分类"的门槛，但随着分类节点、判断条件和例外持续增加，Prompt 同时承担知识、边界、优先级、例外与输出约束，特殊情况又长出定制链路，出现"模型侧行为难控、工程侧系统难维护"。作者提出把系统拆成三方职责：业务定义分类方向（分类树节点定义 + 四种强度的规则），Harness 把业务定义组织成五步稳定流程（还原问题 → 执行规则 → 缩小范围 → 模型判断 → 复核记录），模型只做剩余的语义判断。作者声称某业务准确率从一度 60%+ 回升并稳定在 90%+，badcase 调试从"改 Prompt 再看模型学没学会"变成"先定位问题出在树边界 / 规则 / 输入 / 模型判断的哪一处"，并具备测试、灰度、回退能力。下一步计划做 Agent 平台把配置、验证、运营整合起来。

## 2. 核心主张
- **C1** 分类不是纯语义题：当多个分类在语义上都成立时，正确答案取决于业务当前的观察方向，这是模型无法从输入推出的。｜支撑：案例（"终端 A 批量提交任务时页面无响应"四个方向都成立）｜适用条件：多维分类树（功能 × 终端 × 阶段 × 现象）｜文中位置：§2.2、图 005
- **C2** Prompt 膨胀的机制：每条要求单独合理，累积后 Prompt 同时承担业务知识、分类边界、优先级、例外处理和结果约束；修一个节点的说明会改变其他节点的判断。｜支撑：推理 + 经验叙述，无数据｜适用条件：规则数持续增长的分类系统｜文中位置：§2.3、图 004
- **C3** 模型能理解"必须/优先/除非/仅当"，但不是严格的规则执行引擎；指令过长、多条件同时成立或规则冲突时不能保证每次完整稳定执行。｜支撑：经验断言，无量化｜适用条件：同上｜文中位置：§2.3
- **C4** "Prompt 越来越像一套业务代码，却没有代码的确定性、执行顺序、测试边界和变更治理能力"——这是从 Prompt 迁到 Harness 的判据。｜支撑：推理｜适用条件：通用｜文中位置：§2.3
- **C5** 过去正确的人工纠正案例会过期：分类树新增节点后，旧的 Few-shot 会持续把同一反馈拉回旧分类；"用户反馈没有变化，变化的是业务分类标准"。｜支撑：具体案例（"为什么没有 4K 选项" 从"清晰度差"迁到新节点"无4K/臻彩/1080p"）｜适用条件：分类标准会演化的任何系统｜文中位置：§2.4、图 006
- **C6** 三方职责划分：业务定义方向，Harness 组织稳定过程，模型在明确范围内做判断。｜支撑：架构陈述｜适用条件：作者平台｜文中位置：§3 开头、图 009
- **C7** 节点定义应包含正负边界：名称、描述、覆盖范围（归入条件）、排除范围（排除条件）、关键词（用户通常怎么说）、优先规则（多方向成立时走哪边）。｜支撑：产品截图（图 007）｜适用条件：相近分类共存的树｜文中位置：§3.1 案例 1
- **C8** 规则 = 触发条件 + 分类动作；按业务确定程度提供四级控制强度：定向归类（直接确定结果，跳过模型）→ 范围限定（模型只在候选集内判断）→ 优先推荐（全树判断但带倾向）→ 语义归类（默认，全量交给模型）。"业务判断越确定，规则介入越强；信息越模糊，留给模型的空间越大。"｜支撑：定义 + 同一案例四种处理 + 截图（图 008：三类规则各 10/10/3 条）｜适用条件：作者平台｜文中位置：§3.1 案例 2
- **C9** 分类过程拆成五步：还原用户问题（区分当前问题与历史背景）→ 执行业务规则 → 缩小分类范围 → 模型理解并选择 → 复核并记录（校验有效性、保留判断依据）。｜支撑：架构陈述 + 图 009｜适用条件：作者平台｜文中位置：§3.2
- **C10** Harness 把分类从"一次模型调用"变成运营闭环：调整树/规则 → 用典型反馈和历史数据验证 → 逐步发布 → 线上观察 → 再调整。｜支撑：陈述｜适用条件：作者平台｜文中位置：§3.2、图 009 右下
- **C11** 换更强模型、写更长 Prompt、加更多 Few-shot 只提高模型能力上限，不解决"规则严格执行、边界及时调整、经验过期、结果可测试可追踪"四个系统问题。｜支撑：推理｜适用条件：通用｜文中位置：§3.3
- **C12** 任务被合理拆分后，轻量模型也能胜任；"轻量模型不是引入 Harness 的前提，而是任务拆分后产生的工程收益"。｜支撑：无（未给模型、规模或对比数）｜适用条件：作者场景｜文中位置：§3.3
- **C13** badcase 调试应先定位来源——分类树边界 / 业务规则 / 输入信息 / 模型判断——再在对应位置修，而不是继续改 Prompt。｜支撑：陈述｜适用条件：作者平台｜文中位置：§4.2
- **C14** 分类结果附带判断依据（可解释），既让业务理解为什么这样分，也让研发定位问题发生在哪个环节；变更可灰度、可回退。｜支撑：陈述｜适用条件：作者平台｜文中位置：§4.2、图 009"输出可解释的分类结果"
- **C15**（效果）某业务准确率一度降至 60%+，升级后在终端 A/B 等多端稳定在 90%+ 并持续提升。｜支撑：自报数字；无样本量、无评测集说明、无同期对照；与树边界完善、badcase 治理同时发生｜适用条件：该业务、该时段｜文中位置：§4.1

## 6. 建议采纳（候选语义）
- **S1** 对模型的约束按"人对结果的确定程度"分级介入：完全确定的直接由系统决定并跳过模型；确定所属范围的只限定模型的候选集/可操作对象；只有倾向的以指导形式进入上下文；无把握的完全交给模型。介入强度必须与确定程度匹配，不得用最强档处理不确定的事。｜落地方式 A（检查器/运行时拦截）：确定项由程序判定或在动作前拦截；｜落地方式 B（权限与隔离配置）：范围限定项通过限制可访问文件、可用工具、可选分支实现；｜落地方式 C（静态或条件加载指令）：倾向项作为指导文本进入工作集｜它防御的失败：把"倾向"写成"必须"导致模型在合理例外上被误阻断，或把"确定"写成"提醒"导致规则被静默丢弃（ATT-N 隐性冲突择一）｜删除条件：写不出——这是治理侧的分档要求，不随模型能力消解
- **S2** 每条人工纠正、示例或历史判定必须绑定它成立时所依据的权威定义版本；权威定义（意图、契约、分类标准、架构决策）变更时，绑定旧版本的纠正与示例自动降级为待复核，不得继续作为示例或记忆参与推理。｜落地方式 A（外部状态存储）：示例/记忆条目携带 `authority_revision` 字段，检索时过滤或降权；｜落地方式 B（检查器）：权威定义变更的提交/发布触发对示例集的一致性检查，列出与新定义冲突的旧示例；｜落地方式 C（人工检查点）：定义变更评审时必须回答"哪些既有纠正案例将失效"｜它防御的失败：F1（旧 Few-shot 把结果拉回已废弃的答案）｜删除条件：模型能在推理时自行识别示例与当前定义冲突并主动弃用——可用"新增节点后旧示例仍在上下文"的回归 Case 检验
- **S3** 每个按条件触发的可复用单元（方法、规则、技能）除触发条件外还应声明排除条件（什么情况不该由它处理）；语义相邻的单元应共享同一排除条款，避免同一输入被两个单元同时认领或都不认领。｜落地方式 A（条件加载规则）：单元元数据中的 exclude 字段参与路由；｜落地方式 B（检查器）：对相邻单元做重叠检测，覆盖集交集非空而排除集未声明时告警；｜落地方式 C（人工检查点）：新增单元评审时必须列出它与哪些既有单元相邻及如何区分｜它防御的失败：过度触发/误触发（ATT-N 已观察到）｜删除条件：路由器能从描述自行推断边界并在评估集上不再出现相邻单元串扰
- **S4** 评测集中的每个样本携带其标注所依据的权威定义版本；权威定义变更后，旧样本不得直接用作新版本的通过依据，须重标或标记为过期。｜落地方式 A（外部状态存储）：Case 注册表增加 `labeled_under_revision`；｜落地方式 B（检查器）：eval 运行前校验样本版本与当前定义版本，不一致即判 UNDETERMINED 而非 PASS（与 D-014 空集合条款同构）｜它防御的失败：F3（用过期历史数据验证新定义，误判为回归或误判为通过）｜删除条件：写不出——数据与定义的版本对应是治理事实，不由模型能力决定
- **S5** 任何单次判断的输出必须附带可追溯的判断依据（命中了哪条确定规则、候选范围如何被缩小、模型在哪几个候选间选择），使 badcase 能定位到最早偏离的环节。｜落地方式 A（外部状态存储/轨迹）：结构化 trace；｜落地方式 B（人工检查点）：审阅时要求执行者陈述依据并与规则表核对｜它防御的失败：badcase 只能靠改 Prompt 试错（本文 §4.2 描述的旧状态）｜删除条件：写不出——与 06 §5 同源，属于可观测性要求
  （S5 与 06 §5、层 7 基本重合，列出是为了补"判断依据要能定位到规则/范围/模型三段中的哪一段"这层粒度；若主 Agent 认为重复可合并。）

## 7. 明确不采纳
- "60%+ → 90%+"及"效果仍在持续提升"：数字外推；无样本量、无评测集、无对照，混杂三个同期变化。
- "轻量模型同样能很好完成任务"：无证据（未给模型、规模、对比）；且与 ATT-O 补偿面迁移的方向需分开验证。
- 五步流程的具体顺序与"模型只在第④步"：只适用于单次无副作用的分类任务；编码任务含外部执行、多轮观察、不可逆动作，模型参与的位置远不止一处——载体绑定于该场景。
- 分类树、节点字段（名称/描述/覆盖/排除/关键词/节点类型）、四种规则的具体命名与 UI：载体绑定；只抽象为 S1/S3。
- "定向归类命中后不再进行后续语义匹配"作为通用做法：与参考资料 09 附件 D 边界"规则必须有不确定和人工升级出口"相悖；本文没有说明强规则误命中时的救济路径，不能采纳为无出口的硬规则。
- Agent 平台展望（§5）：尚未落地，无内容可评估。
- 把"Harness"一词按本文语义（规则引擎 + 编排 + 运营）采用：与术语表定义（含知识入口、状态、工具、权限、记忆、验证、观测）不等价，只登记为该团队用法。

## 8. 该文暴露的失败模式
- **F1** 权威定义（分类树）新增节点，但历史人工纠正案例/Few-shot 仍在上下文 → 同一输入被持续拉回旧的、已废弃的答案；输入未变，变的是标准 → 文章的处置：不再让模型在旧案例与新节点间自行权衡，而是新增节点时同时定义归入/排除/优先关系并通过测试后发布 → **可构造为回归 Case**：固定输入 + 定义 v1 下的正确纠正示例 + 定义 v2，期望输出为 v2 答案；grader 为精确匹配。可直接映射到编码场景：契约/ADR 变更后旧的 review 纠正示例仍在记忆中。
- **F2** 多条自然语言约束（必须/优先/除非/仅当）同时成立或相互冲突 → 模型不能每次完整稳定执行，为修一个节点加的说明改变其他节点结果 → 文章的处置：把确定的约束移出 Prompt 变成触发条件+动作的规则，按强度分档执行 → 可构造：同一 Prompt 内放入两条对某输入冲突的规则，多次运行统计择一比例（与 ATT-N"隐性冲突静默择一"同一 Case 族）。
- **F3**（作者未意识到，由 C5+C10 推出）用"历史数据"验证新定义 → 历史标签按旧定义标注，与新定义冲突的样本会把正确的新行为判为回归、或把沿用旧答案的错误判为通过 → 文章无处置 → 可构造：评测集含 v1 标注样本，定义升为 v2 后运行 eval，检查是否报告 UNDETERMINED/过期而非 PASS/FAIL。
- **F4** 规则表只增不减（图 008 已 23 条，含开关但无删减依据）→ 两条强规则同时命中时的优先级未定义、长期无命中规则无人复查 → 文章无处置 → 可构造：两条定向归类规则对同一输入同时命中，检查系统是否报冲突而非静默取先。
- **F5** 单一准确率指标 + 模型自我"复核" → 链内无现实锚点，可能出现"准确率上升但下游归属/任务流转仍错"（D-023 目标失明的形态）→ 文章处置：下游观察反馈是否下降（§1，间接）→ 构造难度高，需业务结果数据；登记为方向。
