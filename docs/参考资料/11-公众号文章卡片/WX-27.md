# WX-27 从胡言乱语到精准改代码：我是如何让 AI 读懂老项目的

## 0. 验证边界
- 一手实践报告：作者是微信小程序教育平台（edu.weixin.qq.com）前端重构的当事人，讲述"近半年"带 AI 重构一个历史包袱重的 WEB 项目的过程。短文（21KB），叙事为主，配置片段只有一段 AGENTS.md 节选。
- **无对照组、无消融、无量化数字**。全文唯一的效果表述是"从去年的每次发版必出核心链路的问题，到近几个月的发版基本很少用户反馈了，而用户量持续上涨"——无缺陷计数、无时间窗、无反馈渠道说明。作者自己在开头承认三个混杂因素同时存在：模型能力提升、重构本身提升了架构质量、上下文建设，**无法分离**。
- 两张"重构对比"架构图（004/005）作者注明是"AI 分析画的图"，即它们本身是模型对代码的派生描述，未说明是否经人工核对。本卡对图中内容只作"作者认可的项目自述"处理。
- 内部工具（工蜂 AI 评审、蓝盾流水线、司内 docker）不可访问；工蜂公网站点未提及 AI 评审能力（§4）。截图 008/009 是唯一可核对的功能证据。
- MR 自定义 AI 评审"刚补充上线，还没有运行足够时间验证"——作者自己标注为未验证。

## 1. 文章在讲什么
作者认为"AI 在老项目上没用"的根因不是模型弱，而是 AI 缺上下文；而这些上下文（业务历史、散落的文档、**哪些代码真的在运行**、哪些改造只做了一半）连本项目开发者也常常拿不到。解法是把重构过程当成给 AI 补上下文的过程：从根目录一份只做索引的 AGENTS.md 起步，把领域知识就近放到模块级 AGENTS.md，并要求对话里产生的可复用结论必须落盘。随后按五步治理"屎山"：删掉有引用但不运行的死代码（让"跑起来"和"看上去"一致）→ 做减法拆掉过度设计（OT 协同→HTTP，两轮重构中 AI 从"需引导"升级为"主导方案"）→ 与设计师定样式规范并让 AI 自查 + MR 检测 → 建单测/E2E/视觉回归/AI 评审四道 MR 门禁 → 把债务治理从专项改成日常顺手做。作者声称的结果是发版核心链路问题明显减少、自己不再需要发布前人工回归；结论是执行、沟通、沉淀可交给 AI，"唯独思考不可以"。

## 2. 核心主张
- **C1** 人与 AI 在老项目上的差距主要是上下文差距，具体四类：业务历史与协作关系、散落的需求/技术文档、真实运行情况（哪些链路真的在跑）、架构与半途而废的技术债。｜支撑：推理 + 本项目经历｜适用条件：历史债务重的迭代中项目｜文中位置：§业务瓶颈常在上下文
- **C2** "有引用"不等于"在运行"：环境判断、旧客户端兼容、迁走的 Agent 链路等使代码静态可达但运行不可达；AI 和开发都无法仅靠引用分析判断，需要真实运行情况和同事口述背景。｜支撑：四个本项目案例（客户端兼容 if/else、OT 未落地、WebIDE 残留的 N 种消息通道、Agent 新旧链路耦合）｜适用条件：多轮不彻底重构的项目｜位置：§一、§AI 上下文内容建设
- **C3** 重构是给 AI 补上下文的最佳时机；老项目"正适合带着 AI 重构"，产物是"AI 可维护的项目"。｜支撑：推理｜位置：§重构成为 AI 可维护项目
- **C4** 团队知识建设长期做不好是因为"看不出价值"；AI 上下文工程的价值定义为"同样的事只需跟 AI 强调一遍"。｜支撑：观察 + 推理｜位置：§AI 上下文内容建设
- **C5** 根入口只做索引（路径 + 1～2 句摘要），细节就近放在模块级入口，索引与模块冲突时**以模块内容为准**；对话中出现可复用规则/兼容性/排障结论/项目知识时必须就近落盘并同步索引；发现索引过期要主动修改。｜支撑：AGENTS.md 节选（作者注明来自同事 yuankai 分享）｜适用条件：上下文窗口有限的多领域仓库｜位置：§从 AGENTS.md 开始
- **C6** 屎山清理第一步是"让代码跑起来和看上去一致"：借 AI 快速找无引用代码，结合运行情况和背景删除死链路，并让 AI 把结论记录沉淀。｜支撑：本项目经历｜位置：§一
- **C7** 上下文积累有可观测的阶梯效应：同一模块第一次重构 AI"常常判断不准确，需要引导"，第二次重构 AI"主导方案，大多数情况分析准确"；差别归因于第一轮引导时补入的上下文。｜支撑：两轮重构对比表（自述，无计数）｜位置：§二
- **C8** 好架构"立足于现在"，过度设计（如无协同诉求却做 OT）是债务的主要来源之一；比过度设计更糟的是改造不彻底留下的层叠残骸。｜支撑：OT 案例 + 观察｜位置：§二、§五
- **C9** 样式规范落地 = 统一组件（把不合规设计稿收纳掉）+ 规范沉淀让 AI 自查 + MR 规则检测；规范存在才能长期收敛。｜支撑：方案描述｜位置：§三
- **C10** 前端过去不做大量用例是维护成本高；有 AI 后"用例维护成本只剩 AI 上下文维护和 token"，因此自动化测试工程"势在必行"。｜支撑：推理 + 四期建设表｜位置：§四
- **C11** 视觉回归必须分两层：整页大截图宽容差抓布局异常，组件级小用例严容差抓细节；目的之一是**即使 AI 为了让流水线通过而误改了别的样式，也能在 MR 上被发现**。｜支撑：图 007 实例｜位置：§视觉用例回归建设
- **C12** MR 需要 AI 评审新增代码是否遵循规范；规则文件放在仓库里由平台读取；合入条件是"AI 评审意见必须被响应"。｜支撑：图 008/009；作者注明尚未验证效果｜位置：§MR 自定义规则
- **C13** 债务治理应从周期性专项变为日常常规：规范里写明持续收敛方向，AI 在迭代时顺手治理，MR 评审拦新增违规。｜支撑：推理 + 对历史专项失败的观察｜位置：§五
- **C14** （观点）执行、沟通、沉淀可交给 AI，思考不可以；AI 写不出作者的思考，即使它读了全部代码文档并全程参与重构。｜支撑：无｜位置：§结束语

| C10 有 AI 后测试维护成本"只剩上下文维护和 token" | D-024 验证能力是自主度上界 | 一致 | 作者把测试建设视为放开 AI 改动的前提，与"自主度上限 = 可廉价验证的量"同向 |
| C14 思考不能交给 AI | 09 章责任判据 | 一致（观点） | 无证据，但与"只有人能继承后果"同向 |
| 前三轮/其他 WX 重合 | WX-06 C3/C6、ATT-I | 邻接 | 本文的知识来源是**对话沉淀**（经验型），WX-06 是**代码派生**（生成型），两者互补而非重复；见冲突 2 展开 |

**冲突 1：AI 直接落盘知识 vs D-007"AI 只能提候选、所有者审批后写入"。** 文章要求 AI 在对话中一旦出现可复用结论就"必须就近落盘"并改索引，没有候选区、没有审批环节。证据强弱：D-007 是提议，理由是防推断污染；文章无数据证明直接写入安全。但文章的做法有一个未言明的兜底——**知识与代码同仓，AI 写的 AGENTS.md 变更走同一条 MR**，因此"审批"实际发生在 MR 评审（图 009 门禁）而不是写入时。可共存：把 D-007 的"审批"从"写入前"放宽为"进入权威载体前"，只要知识载体的变更与代码变更受同一 Gate 覆盖；风险在 D-024——评审者是否真的读了文档 diff，文章未说。
**冲突 2：过期检测靠"AI 发现就改" vs WX-06 S1"派生知识绑定源版本、差异超阈值即过期"。** 两者并非同一类知识：WX-06 的知识是从代码**生成**的，源版本可机械绑定；本文的知识是排障结论、兼容性、口述背景，源是**一次事件**而非一个 revision，git hash 差异不能直接判定其过期（模块改了三次，某条兼容性结论可能仍成立）。因此 WX-06 S1 不能原样覆盖本文场景，本文也没给出替代机制——"主动修改"是自然语言提醒，按 D-008 属最弱载体。可共存方案：经验型知识记录 **scope（所属模块）+ 产生事件 + 产生时 revision**，模块变更触发"复核"而非"判过期"（04 章 §7 已有"关联代码变化触发复核"，本文补上"就近放置使触发范围可计算"这一环）。见 S3。

## 6. 建议采纳（候选语义）
- **S1** 入口是地图不是百科：项目级入口只含"去哪找 + 一句摘要"，领域细节放在离其作用范围最近的位置；索引与细节冲突时以细节为准，索引不具权威。｜落地 A（静态指令 + 条件加载规则）：根入口短索引，模块级说明按路径就近加载｜落地 B（外部状态存储 + 检查器）：知识库以索引页为入口，定期检查索引条目与目标内容的一致性并报告失配｜它防御的失败：F5（索引与细节漂移，AI 按过期索引行事）、上下文取并集｜删除条件：工具能在检索时自动汇总各处细节并标注来源，索引层不再需要人工维护
- **S2** 静态可达不等于运行可达：任何"这段代码/链路是否生效"的判断必须有运行观察或责任人背景支撑；确认不运行的链路应删除，暂不能删的须显式标注"不运行"及原因。｜落地 A（检查器 + 外部状态存储）：用运行覆盖/调用统计给模块打"活/死/未知"标签并存入知识条目｜落地 B（人工检查点 + 静态指令）：重构清单要求每条待改链路先由责任人确认运行状态，AI 对"未知"状态的链路默认不改只报｜它防御的失败：F1｜删除条件：工具能把生产运行可达性作为代码属性直接呈现给模型（此时规则退化为"读它"）
- **S3** 经验型知识（排障结论、兼容性、口述背景）落盘时必须带 scope（作用范围）、产生事件与产生时的版本标识；其 scope 内的源发生变化时触发复核，而非静默沿用或机械判过期。｜落地 A（外部状态存储 + 检查器）：知识条目带 scope/revision 字段，变更检测比对 scope 内改动并列出待复核条目｜落地 B（条件加载规则 + 人工检查点）：知识就近放在模块内，触碰该模块的任务默认加载并要求执行者确认"仍成立/已失效"｜它防御的失败：F5、WX-06 F1（沿用已失效结论）｜删除条件：写不出（"某结论在何范围内成立"来自人的判断，不随模型能力消解）
- **S4** 会话中产生的可复用结论必须在产生时被捕获并路由到其 scope 对应位置；它进入权威知识前须经过与代码变更同等级的审查 Gate（审批可发生在合入时而非写入时）。｜落地 A（静态指令 + 人工检查点）：指令要求就近落盘，知识变更随代码 MR 评审｜落地 B（运行时拦截 + 外部状态存储）：会话结束时拦截并提取候选，写入候选区，由所有者批量晋升｜它防御的失败：F6（同一件事反复向 AI 强调）、D-007 防御的推断污染｜删除条件：模型能在跨会话中稳定复用自身经验且可被审计时，捕获步骤可删；审查步骤不可删
- **S5** 修复检查失败的变更，其影响面必须由独立于修复者的检查确认；回归检查按检测目标分层设定灵敏度（粗粒度宽容差抓整体结构，细粒度严容差抓局部状态），避免单一阈值在稳定与灵敏之间二选一。｜落地 A（检查器）：合入前对未声明修改的组件/页面运行快照比对｜落地 B（运行时拦截 + 人工检查点）：限制修复类任务的可写范围，越界修改需人工放行｜它防御的失败：F3（为过流水线误改别处）｜删除条件：模型修复时能可靠自报影响面且自报可被验证——但"独立检查"本身对应 D-023，不可删
- **S6** 规范驱动的评审输出应可限定为"仅规则命中"以控制噪声；评审意见的合入条件可以是"每条已被响应"（响应含拒绝并说明），而非"全部采纳"。｜落地 A（检查器 + 人工检查点）：评审机器人只报规则命中，合入 Gate 检查每条评论有回复｜落地 B（静态指令 + 外部状态存储）：评审规则作为项目知识版本化，评审记录与响应存入工作项｜它防御的失败：F7（评审噪声导致人退化为快速点头，D-024）｜删除条件：写不出（人判断带宽是常量）
- **S7** 债务收敛方向作为项目知识的一部分写明；触碰相关代码的任务默认包含向该方向收敛的义务；新增违规被 Gate 拦截，存量违规只减不增（棘轮）。｜落地 A（静态指令 + 检查器）：规范写明方向，lint/评审对新增违规失败、对存量计数不得上升｜落地 B（外部状态存储 + 人工检查点）：债务清单带 owner，每个工作项验收时勾选"顺手收敛项"｜它防御的失败：F4（重构不彻底层叠成债）｜删除条件：写不出（组织行为问题）
- **S8** 上下文成熟度用"同类任务所需人工引导次数 / AI 承担的角色档位（辅助→主导）"作为观测指标，随时间记录。｜落地 A（外部状态存储）：工作项记录引导次数与角色档位｜落地 B（人工检查点）：阶段复盘按任务类型对比｜它防御的失败：上下文建设无法证明价值（C4）｜删除条件：有更直接的评估集时可替换

## 8. 该文暴露的失败模式
- **F1** 代码静态有引用但运行时永不到达（环境变量门控、旧客户端兼容、迁走的 Agent 旧链路） → AI 把死链路当活链路分析/修改，"沿用旧同步方案"（图 004 AI 易错点） → 文章处置：先用 AI 找无引用代码，再结合运行情况与同事背景删除，让 AI 记录 → **可构造**：仓库含两条同名功能链路，一条由环境变量关闭；任务要求改该功能；grader 检查 AI 是否先判定活链路、是否只改活链路
- **F2** 多场景共享一个入口并靠运行时状态隐式判断当前场景 → AI 误判当前场景、漏传课程上下文、误伤低频入口、修 UI 影响别处（图 004） → 处置：按场景分域 + 共享层按契约复用，上下文"只保留当前场景必需信息"（图 005） → **可构造**：三场景共享组件，任务只改其一；E2E 覆盖另外两场景作为 grader
- **F3** 视觉回归流水线失败，AI 为让流水线通过修改了无关组件样式 → 弹窗内元素整体位移（图 007） → 处置：整页 + 组件双层快照，未声明的影响面在 MR 被独立检查器抓到 → **可构造**：故意让一个基线失败，观察修复 diff 是否触碰其他快照；grader = 其他快照 diff 为零
- **F4** 多轮重构不彻底（WebIDE 未落地留 N 种通信方式、OT 未用留协同代码） → 债务层叠，连开发者也难辨哪套在生效 → 处置：治理常态化 + MR 评审拦新增 → **可构造**（弱）：以违规计数棘轮作为 grader，多轮任务后计数不得上升
- **F5** 根索引与模块知识漂移（文章自定"发现过期主动修改"说明发生过） → AI 按过期索引找不到或找错知识 → 处置：以模块为准 + 主动改 → **可构造**：索引条目指向已改名/已删模块，任务需该知识；grader 检查 AI 是否发现失配并报告而非沿用
- **F6** 同一件事需要反复向 AI 强调（作者定义的痛点） → 每次会话重复引导 → 处置：对话结论就近落盘 → **可构造**：两次独立会话执行同类任务，统计第二次所需引导次数（S8 指标）
- **F7** E2E 在真实环境运行产生测试数据（空项目）堆积触碰账号上限 → 流水线因配额失败 → 处置：测试后清理数据 → **可构造**：测试数据生命周期 Case，环境类失败
- **F8** 设计稿跨时期不一致导致同一内容多种样式，AI 与人都"照稿改坏" → 处置：与设计师定规范 + 统一组件 → 非 AI 特有，意图/权威层失败（source of record 不唯一）
