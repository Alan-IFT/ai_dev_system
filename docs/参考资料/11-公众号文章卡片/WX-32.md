# WX-32 Agent的命门是上下文：关键不在少给，而在给对

## 0. 验证边界
- 材料性质：一手实践报告，作者自己跑实验、自己报数。**有对照组**（Control vs 启用工具；改造前 vs 改造后），**无消融**，未公开原始日志、任务清单或统计检验。
- 样本规模逐项不同，必须分别看：CodeGraph 第一组 = 连续 5 轮一次 A/B；第二组 = 三种任务形态各**一次**；第三组 = 两轮对话**一次**；RTK 主实验 = 12 任务 × 2 pair = 48 次运行；RTK 复测 = 单任务 5+5 次；端到端改造 = **同一个需求**在两个模型上各跑改造前/后**各一次**。除 RTK 主实验和复测外，其余全部是 N=1 的观察。
- 数字来源：作者的账单/调用记录（CodeBuddy Credit、Token 计数）。"缓存输入/非缓存输入"的口径未定义（推测为 prompt cache 命中与否）。
- 本轮已与 ATT-F 转录逐段比对：正文无增删；**所有表格和图（图 005–010、012–018）是本轮新增信息**，其中图 016 的 GLM 总量、图 017 的 Main 阶段反增、图 015 的三档白名单、图 018 的收放条件，正文均未给出或只给一半。
- 超出可核实范围：作者对 Devflow 的私有改动（`devflow_state.py`、Hook、三档白名单）不在开源仓库 loopforge 中，无法查看实现；"CodeGraph"未指明具体实现；两个模型（GLM-5.2、Claude Opus 4.8）经检索确认存在于 2026 年，但其在 CodeBuddy 中的计费口径未核实。

## 1. 文章在讲什么
作者在腾讯云轻量云的多 Agent 开发工作流 Devflow（开源为 loopforge，按任务规模分流：小需求单 Agent，中大需求走需求澄清→方案设计→开发→审查→测试→知识沉淀六角色接力）上，接入两个"看起来都在做减法"的工具——CodeGraph（代码结构地图）和 RTK（终端输出压缩器）——结果一个中等需求耗 2480 万 Token、约 202 元，比接入前还贵 40 多元。作者把"省 Token"拆成局部输出 / 行动路径 / 整体结果三层重新测量：CodeGraph 在已知符号任务省 80%，在完整调用链和多点 path:line 任务反增 96%～153%，且第一轮省下的在第二轮被历史携带抵消；RTK 把终端字符压掉 40%，总 Token 却升 4%，命令、测试、失败事件全部增加，复测发现它把一个关键线索的 158/178 个命中全部过滤为零。作者据此不再"全局开工具"，而是重做信息流：交接拆成"短 Handoff + Artifact 路径"两层，CodeGraph 只在前段探索一次并沿角色复用，RTK 改成三档白名单 + 回退 + 熔断，状态迁移/路由/去重交给程序脚本，Main 不再每站醒来。改造后同一需求在 GLM-5.2 上总 Token −37.5%（步数不变、每步变轻），在 Claude Opus 4.8 上 −23.3%。结论：上下文信息密度 = 当前步骤真正相关、可执行、可验证的信息 ÷ 进入窗口的全部上下文；提高它靠"什么时候给、给谁看、保留多久"三个选择，而不是一味删。

## 2. 核心主张
- **C1** 评价任何"省 Token"机制必须看三层：局部输出缩短多少、行动路径多走/少走了哪些步、端到端 Token/时间/成本/质量最终升还是降；局部改善不蕴含整体改善。｜支撑：CodeGraph 与 RTK 两组反向数据｜适用条件：多 Agent 编码工作流｜文中位置：01、06
- **C2** CodeGraph 的成本方向由任务形态决定：图查询能替代后续检索时省（已知符号影响面 −80%）；只能提供导航、后面仍要逐点核对源码时反增（完整调用链 +95.8%，多点 path:line +152.9%，35 条图命令后仍要普通读取）。｜支撑：图 006，三任务各一次｜适用条件：陌生仓库、有结构查询工具｜文中位置：2.2 第二组
- **C3** 工具返回一旦进入历史就持续被携带；单轮节省不自动转化为会话净收益（第一轮 −42.5%，第二轮 3.46×，两轮合计 +31.6%）。｜支撑：两轮对话一次实验，作者自认"不足以证明必然反增"｜适用条件：多轮连续会话｜文中位置：2.2 第三组
- **C4** 非缓存输入下降不等于总输入下降（−35.5% vs −0.5%）：收益不会等比例传递到总量。｜支撑：5 轮 A/B 一次｜适用条件：有 prompt cache 的会话｜文中位置：2.2 第一组
- **C5** 命令输出是 Agent 观察环境的方式，压缩器过滤掉的东西会改变它下一步搜哪、改什么、测不测；终端短了四成不代表路径变短（命令 +27.8%、测试 +37%、失败 +80.7%、总 Token +4.23%，13 贵 11 省）。｜支撑：图 007–009，48 次运行｜适用条件：宽泛搜索占比高的任务｜文中位置：3.2
- **C6** 单个 Bad Case 复测（5+5）后差异只剩 +1.24%，但 RTK 组方差是 Control 的 2.36 倍；结论分三层：已确认（稳定压短输出；宽泛搜索中预标记的关键命中 158/178→0）、同时观察到（更多命令/测试/失败，波动更大）、尚未确认（过滤是否是总量上升主因；RTK 是否稳定省或稳定贵）。｜支撑：图 010｜适用条件：同上｜文中位置：3.3
- **C7** 交接拆两层：窗口内 Handoff（摘要、关键决策、文件、符号、风险、验收状态、下一步）让下一角色立即开始判断；窗口外 Artifact（完整方案、源码证据、diff、测试结果、阶段报告）保存事实、按路径回源。减少的是完整报告的重复传递，事实本身不丢。｜支撑：图 012–014 + 改造前后对比｜适用条件：多角色接力｜文中位置：4.1
- **C8** 结构探索只在前段做一次并写入 Handoff，后续角色复用定位结果，各自只针对自己的判断回源码（Architect 补缺口、Reviewer 只查核心公共符号的遗漏调用方、Test 在相同范围验证）。｜支撑：设计描述，无单独数据｜适用条件：需求已指向符号/路由/文件｜文中位置：4.2
- **C9** 有损压缩必须按场景启用并可随时退回：三档白名单（默认压缩 / 限定范围 / 保留原生）、回退条件（截断、异常为空、预期符号未出现、需扩大范围）、搜索熔断（第一次未命中即原生复核，需第二次宽泛搜索则后续全部切回原生）、最终审查与验收永远原生；Hook 记录采用/跳过/回退并按整任务评估。｜支撑：图 015、018；设计描述｜适用条件：同上｜文中位置：4.3
- **C10** 白名单升级判据：只有端到端总 Token、失败诊断保留、测试—修复路径、最终质量**一起**改善，才把命令从"限定范围"提升为"默认白名单"。｜支撑：作者规则，无数据｜适用条件：同上｜文中位置：4.3
- **C11** 如果 Main 仍在每个阶段之间醒来重读状态、理解报告、决定派发，下游省下的会在主会话里长回来；应把阶段开始/完成、路由校验、原子 claim、重复派发保护、计划边界检查交给程序，角色直接唤醒下一角色。｜支撑：设计描述；但见图 017 Main 阶段反增（§3）｜适用条件：固定路径的多角色工作流｜文中位置：4.4
- **C12** 改造效果：GLM 步数 221→220 不变、每步 Token 10.68 万→6.70 万，总量 −37.54%，Developer 阶段一项占净节省 74.5%；Claude 总 Token −23.34%，缓存输入 −25.23% 而非缓存输入仅 −0.36%，工具调用 258→200。｜支撑：图 016、017，同一需求各一次｜适用条件：该需求、该工作流｜文中位置：05
- **C13** 上下文信息密度公式与三选择（何时给 / 给谁看 / 保留多久）；给多了付携带费，给少了付补偿费（更多搜索、测试、修复）。｜支撑：推理 + 图 011｜适用条件：通用｜文中位置：06
- **C14** 诊断昂贵工作流的三问：成本最高阶段在推理还是在搬运历史；工具返回体有没有被反复携带或引发补偿性搜索；哪些长内容可换成"短摘要 + 路径"、哪些固定动作可交给状态机。｜支撑：推理｜适用条件：通用｜文中位置：06

## 6. 建议采纳（候选语义）
- **S1** 对 Agent 观察结果（命令输出、检索结果、日志）做**有损压缩**时，必须同时具备：(a) 可机械检测的损失信号（输出被截断、异常为空、预期目标未出现、一次查询后仍需扩大范围）；(b) 触发后自动回退到无损输出；(c) 验证、审查与验收环节不使用有损输出；(d) 压缩的采用/跳过/回退可被记录并按整任务评估。｜落地方式 A（运行时拦截）：命令执行前由拦截器决定是否改写为压缩版本，命中损失信号后重跑原生｜落地方式 B（人工流程 + 条件加载规则）：把"哪些场景允许压缩、哪些必须原生"写成分档清单，执行者按任务阶段选择，验收阶段清单强制原生｜它防御的失败：F1（关键命中 158/178→0 后绕路）｜删除条件：模型能从压缩摘要中识别"线索缺失"并主动请求原文，且成本不再按输入长度计费
- **S2** 工具返回体应有**存活策略**：进入窗口的工具输出默认只服务当前决策；决策完成后保留结论与回源位置，原文外部化；不得默认随历史逐轮携带。｜落地方式 A（外部状态存储）：工具原始输出落到可回读位置，窗口只留摘要 + 引用｜落地方式 B（运行时拦截）：harness 在下一轮组装上下文时把已消化的工具输出替换为引用｜它防御的失败：F2（第二轮 3.46×，两轮合计反贵 31.6%）｜删除条件：推理成本与注意力不再随历史长度退化
- **S3** 角色/会话之间的交接只传"当前判断所需的摘要 + 关键决策 + 精确回源位置"，完整产物在窗口外**完整保留且不改写**；接收方需要细节时按位置回源，而不是由发送方预先塞入。｜落地方式 A（文件约定 + 外部状态存储）：产物目录 + 短交接记录｜落地方式 B（任务系统字段/消息协议）：交接消息只允许引用型字段，产物存于任务系统附件｜它防御的失败：F3（完整报告在多个长期会话中反复占用上下文）｜删除条件：写不出（这是信息流结构，不随模型能力消失）；但 D-016 要求的身份/时间/版本字段必须补入，否则 F5 会出现
- **S4** 成本可观测性应同时按两个正交轴切分：按**来源**（WX-09 S6）和按**是否重复携带**（缓存命中 vs 新输入）；并**按阶段/角色**分别报告，禁止只报总量。｜落地方式 A（外部状态存储/日志）：从计费记录按阶段与缓存字段人工汇总｜落地方式 B（检查器）：轨迹分析器自动输出阶段 × 缓存二维表｜它防御的失败：F6（总量 −37% 掩盖 Main +64%；终端 −40% 掩盖总量 +4%）｜删除条件：成本不再是主要约束
- **S5** 任何"省成本"机制的晋升（从限定范围到默认启用）必须同时通过多项指标：端到端成本、失败诊断信息保留、修复轮次、最终质量；任一恶化即不晋升。｜落地方式 A（人工检查点）：晋升评审清单｜落地方式 B（检查器 + Gate）：eval manifest 声明四项阈值，任一不达即阻断｜它防御的失败：单指标晋升导致目标失明（D-023 的成本变体）｜删除条件：写不出（这是评估纪律，不随能力消失）
- **S6** 固定路径的多角色工作流中，**编排者的重新理解成本**应作为独立成本项计量；状态迁移、路由校验、去重、重复派发保护等可确定动作应由程序执行，角色可直接唤醒下一角色，编排者只在需要判断时介入。｜落地方式 A（外部状态存储 + 程序）：状态机脚本承担迁移与路由｜落地方式 B（人工流程）：由人按状态表手工派发，编排 Agent 不参与｜它防御的失败：F4（Main 每站重读，下游节省在主会话长回来）｜删除条件：模型能在极低成本下重建阶段状态（可用 Main 阶段占比在项目内实测）

## 8. 该文暴露的失败模式
- **F1** 通用压缩器处理宽泛搜索 → 预标记关键线索的 158/178 个命中全部归零，Agent 继续以更多命令/测试/失败去补（命令失败 +80.65%）→ 文章处置：三档白名单 + 损失信号回退 + 搜索熔断 + 验收原生 → 可构造：固定一个已知答案在宽泛搜索结果末尾，对比"原生 / 压缩 / 压缩 + 回退"三组的命中率、后续命令数与总 Token（组件级对照，与模型决策弱耦合）
- **F2** 第一轮图查询结果进入历史 → 第二轮即便限定"最多补读 3 文件 + 1 次图查询"，仍 3.46× → 处置：结论进 Handoff、原文外部化 → 可构造：两轮任务，第二轮固定只需第一轮结论，比较"原文留窗口 / 只留摘要 + 引用"两组的第二轮输入量
- **F3** 编排者把"需求 + 历史 + 完整报告"整包交给每个下游，下游再整包带回 → 同一报告在多个会话反复计费 → 处置：短 Handoff + Artifact 路径 → 可构造：三角色接力任务，比较整包传递与引用传递的各阶段输入量与最终验收通过率（ATT-F 警告：路径噪声可能大于效果量，需固定角色 prompt 与父提交并重复）
- **F4** 编排者在每个阶段之间醒来重读状态、理解报告、决定派发 → 下游节省在主会话长回来 → 处置：状态机脚本 + 角色直达 → 可构造：同一流程"经 Main 中转 / 直达"两组，记录 Main 阶段 Token 占比
- **F5** 结构工具用于要求大量精确 path:line 的任务 → 35 条图命令后仍要逐点读取，+152.9% → 处置：图 018 收放条件（Handoff 已给可信文件/符号或查询与复核重复时收起）→ 可构造：同一仓库三类任务各 N 次，检验"任务形态 → 工具收益方向"是否稳定
