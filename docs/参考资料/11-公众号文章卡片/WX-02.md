# WX-02 认知重建之后，步入Agentic Engineering的工程革命

## 0. 验证边界
- 一手实践报告：作者本人（腾讯活动业务后台）2026-01-02 至 03 月约两个月内把一个入口文件"长"成 22 Agent / 27（一处写 26）Skill / 28 命令的体系，并在"运营活动配置"场景端到端落地。**无对照组、无消融、无使用指标**；作者在 §9.2 自承"工具的实际效果缺乏量化验证……哪些工具真正提升了效率？我没有系统性的答案"。
- 文中全部数字均不可核实：人工配置"3-5 人天/活动、错误率 15-20%"（来源与统计口径未说明）；"目标缩短到分钟级"是目标不是结果；"数十亿 token"是作者自述；"46.9%"转引自 Cursor（见 §4，文章漏掉了测量条件）；Carlini 编译器实验数字已核对一手来源一致。
- 活动配置 Skill "仍在迭代中，尚未经过充分的生产验证"，代码审查/需求门禁的效果只有"感觉"；作者明确承认可能存在"每次都通过的摆设门禁"。
- 二手转述部分（Karpathy 推文、Anthropic+高盛驻场、WorkBuddy/Manus 被收购）未核实；参考资料列表把 Karpathy 两条推文写成同一 URL，属文章自身错误。
- 体系本身是 CodeBuddy/Claude Code 双产品实现，大量结论绑定 AGENTS.md / .codebuddy/ / Hook / MCP 载体。

## 1. 文章在讲什么
作者系列第三篇：前两篇建立"上下文工程 / 复利工程 / 极简主义"三认知并推翻了 DDD 式精密架构；本篇记录从一个 AGENTS.md 文件出发，被真实痛点逼出 context/ 与 requirements/ 目录、"文档即记忆"三层记忆、场景驱动路由架构（两周后因"路由机制本身成为最大噪音源"被推翻）、再转向 Command/Skill/Subagent 三级工具封装的全过程。随后给出方法论层（场景分析→工具设计规范→迭代 SOP 含四层自主权边界与六条工具化判据）、体系全貌（8 阶段需求生命周期 + 阶段门禁 + 上下文自动搜索 + 渐进式输出 + 六维评审 + 7 checker 并行审查 + 知识沉淀命令）、一个业务案例（Ralph Loop 驱动的 10 步活动配置生成，含 L1-L3 验证、Playwright 前端验证、MCP 直写、本地环境隔离）、团队推广四阶段（种子/扩散/加速/常态）、反思（规范膨胀、无量化、设计决策 context 未沉淀、过度信任）与对多 Agent 团队化的判断（"全能解但非最优解"）。作者声称的结果：体系能跑通 MVP、同事开始使用、知识随需求复利积累；未给出任何量化收益。

## 2. 核心主张
- **C1** Agent 的"接口"不是函数签名而是上下文窗口里的信息组合，是概率性的，无法用 DDD 式确定性边界约束；体系设计应围绕上下文的组织、流转与质量。｜支撑：v0.1～v0.7 七版 DDD 设计全部"Agent 不按设计边界行动"（叙述，无数据）｜适用：单人从零搭建 Agent 体系｜位置：§2.2
- **C2** 任何引入的"管理机制"都消耗上下文（=认知带宽），收益必须大于其消耗，否则净亏损；用动态路由实现"最小约束"的机制本身成了最大噪音源。｜支撑：三次路由叠加后 Agent 跳过必填项、格式串用的具体事故；Opus 4.5 下仍系统性退化（叙述）｜适用：场景与规范数量增长后｜位置：§3.5
- **C3** 上下文加载应从"推送"（每次交互塞入可能需要的规范）改为"拉取"（工具带描述自动匹配，调用后才加载内部知识）；入口文件只强化"何时用/如何用"。｜支撑：与 OpenAI progressive disclosure、Cursor 动态发现、Anthropic just-in-time 的一致性论证（图 004）｜适用：平台原生支持描述匹配的工具机制｜位置：§3.5、§3.6
- **C4** 工具封装"知识而非流程"：告诉 Agent 做什么和注意什么，不写第一步第二步；Command 只做预检+委托，Skill 主文件轻量+资源一跳可达，Subagent 只返回摘要且禁止嵌套。｜支撑：三类事故（单文件爆上下文、子代理回吐原始数据、命令复制步骤导致改漏）｜适用：同一领域多入口共享一套知识｜位置：§4.2
- **C5** 工具化有六条判据（高频重复、易错、强制约束、大量输出、专业知识、显式入口）；"易错 + 强制约束 → 工具化/门禁"是最常见升级路径；一次性约束、高度灵活任务、需人类判断的决策不工具化。｜支撑：追溯链检查从规范文本升级为 gate-checker 的案例｜适用：规范中的约束被 Agent 反复遗漏时｜位置：§4.3、图 007
- **C6** Agent 行为出错时先定位层级——能力缺失 / 越界（有功能无约束）/ 工具 bug——"定位错了，改完还会出问题"。｜支撑：推理，配安全检查遗漏示例｜位置：§4.3、图 006
- **C7** 四层设计层级对应变更风险梯度：设计指导（Why）Agent 不可改；功能预期（What）Agent 可提议需人确认；场景约束与工具 Agent 可自主改。｜支撑：推理｜位置：§4.3
- **C8** 消除幻觉的方法是"写任何内容前先搜索项目内真实上下文"，且写入文档的每条关键信息只允许三种状态：有项目内引用（文件:行号）/ 标记待用户确认 / 标记待补充并入待澄清清单——**不允许"没有来源但看起来合理"的第四种状态**；设计阶段禁用外部搜索。｜支撑：机制描述，无幻觉率数据｜适用：需求/设计文档生成｜位置：§5.1
- **C9** 文档类输出必须分步：先给 3-5 条摘要/决策点/待确认项，人确认后再出详情；否则人面对几千字会"看起来差不多就这样吧"，审查形同放弃。｜支撑：推理（人类阅读带宽）｜位置：§5.1
- **C10** 评审维度应由项目知识动态生成（固定核心维度 + 从项目上下文挖掘的约束 + 本需求特有关注点），而不是写死在模板里。｜支撑：QPS 限制示例｜位置：§5.1
- **C11** 验证要分层且每层要知道自己检测不到什么：结构校验（反序列化）通过不代表语义正确，string 类型字段任何值都能过；因此 S4 自检清单中 5 项明确标注"S5 无法检测"，必须在生成阶段拦截。｜支撑：日期格式、When 前缀、goods_id 类型三个真实坑｜位置：§6.4、§6.5、图 013
- **C12** 状态通过文件系统而非对话上下文传递；同一 Prompt 反复注入，Agent 每轮读状态文件决定下一步（Ralph Loop）；完成由 Agent 输出标记自判 + 最大迭代次数兜底。｜支撑：10 步流程在实际活动配置中跑通核心链路（无成功率数据）｜位置：§6.2
- **C13** Agent 的实验性写入必须与共享测试环境隔离（本地库 + 进程级代理，让"远程真实前端 + 本地实验数据"共存）；验证手段不可用时自动降级并把降级原因写入状态。｜支撑：6 种方案评估后选定 Whistle 代理｜位置：§6.6、§6.8
- **C14** 团队落地是双线：真实结果制造动机、分阶段可验证动作的学习路径降低门槛；停滞项目靠"已跑通的人嵌入式打穿第一个场景后撤出"；制度化 = 降低协作摩擦（context 轻量 Review、伴随式上手、PR 回流），不等于强制。｜支撑：叙述 + 类比 Anthropic 驻场高盛（未核实）｜位置：§7
- **C15** 体系预设"用户至少会与 AI 对话"，该前提在团队内不普遍成立——个体效率 ≠ 团队效率的一个具体原因是协作基本能力缺口。｜支撑：同事对着 `/requirement:new` 输入框发愣的观察｜位置：§2.3
- **C16** 反思：每次犯错就加一条规则会让 Skill 从"引导"膨胀成"操作手册"并重现走神；规则应回答"被违反的频率有多高"，只在极端边角生效的规则不应占用每次加载的空间；"不要为偶发性错误维护永久约束"。｜支撑：作者自身膨胀经历｜位置：§9.2
- **C17** 每个设计决策都应有对应的失败案例作为论据（"为什么用 Subagent？因为审查在主对话里跑输出爆了上下文"）；设计决策的 context 应沉淀进仓库而非口头传承。｜支撑：推理 + 团队成员问"为什么禁止嵌套"的经历｜位置：§9.1、§9.2
- **C18** 多 Agent 团队角色化是"全能解但非最优解"：并行前提是任务可分割；并行用于执行层不用于决策层；角色切换有上下文重建成本，文档交接有信息衰减；流程完备不能弥补单步质量——"地基是上下文，不是团队规模"。｜支撑：Carlini 实验（已核实）+ BMAD（部分核实）+ 推理｜位置：§10.3
- **C19**（观点）Token 消耗量与利用率将成为团队产能指标；企业级工具差异化在连通与生态而非功能。｜支撑：类比，无数据｜位置：§10.1、§10.2

**冲突一：Ralph Loop 的完成判定。** 文章机制：Agent 自认完成 → 输出标记 → Hook 放行；否则重注入直到最大迭代。本规范：完成必须绑定验收 ID、版本、环境、过程、结果（D-009），AI"不自封完成"（00 章 §6）。文章其实自己补了 L1-L3 验证与 S7-S9 校验节点，但它们在流程内部，Hook 只检查"有没有标记"。谁的证据强：文章无成功率数据；本规范也是提议。可共存的方式：循环退出条件从"Agent 声明完成"改为"检查器读取到全部验证节点的通过证据"，Agent 的标记只作为"请求判定"信号。文章 §9.2 承认的"过度信任 AI 输出"正是这种自判完成的后果。

**冲突二：文档即记忆 vs 第二个事实来源。** 文章：同一份 Markdown 人与 AI 共读，避免"人读的"与"AI 读的"两套漂移；且因 AI 每次任务都消费它，过时会立刻通过错误行为暴露。ATT-H/01 章：与代码并存的描述文档必然先于代码过期，是第二个事实来源。二者不完全对立：文章解决的是"人的文档 vs AI 的向量库"两套之间的漂移，ATT-H 讲的是"文档 vs 代码"的漂移。文章"高频消费即检测"的假设**无证据**，且与作者自述"context/ 里架构描述没更新比没有知识更危险""过度信任"自相矛盾——过时文档导致的错误未必立刻被人发现。可共存：文档作为知识载体可以，但其 owner/scope/last_verified 与"与代码冲突时以谁为准"必须声明（D-005/D-006），"被高频消费"不能替代校验。

## 6. 建议采纳（候选语义）
- **S1** 生成物中的每条关键陈述必须处于三种状态之一：绑定项目内可定位来源 / 显式标记待责任人确认 / 显式标记缺失并进入待澄清清单；不存在"无来源但合理"的第四态。｜落地 A（检查器）：对产出物做标注完整性校验，未标注的关键陈述判失败｜落地 B（静态指令 + 人工检查点）：写作规范要求三态标注，评审人只审"待确认"项｜它防御的失败：需求/设计文档中的虚构接口名、虚构业务规则一路通过评审到编码才暴露（§5.1）｜删除条件：模型能可靠自报每条陈述的来源置信并被外部校验证明误报率可接受。
- **S2** 每个验证层必须声明它检测不到的错误类别；上游生成步骤对声明的盲区承担拦截责任，"某层通过"不得被表述为"正确"。｜落地 A（检查器）：验证器输出附带 covered/not-covered 清单，证据包记录｜落地 B（条件加载规则）：生成阶段加载与本层盲区对应的自检清单｜它防御的失败：string 字段（日期格式、DSL 前缀）通过反序列化但运行时静默失效（§6.4）｜删除条件：端到端验证（实跑）成本低到可替代分层验证。
- **S3** 面向人的审查输出须先投放少量决策点/待确认项，得到确认后再展开全文；投放节奏以人的审查带宽为准。｜落地 A（静态指令）：输出规范要求分步｜落地 B（运行时拦截）：超过阈值的一次性输出被拦下并要求先给摘要｜它防御的失败：人面对整篇长文放弃审查，幻觉消除机制失效（§5.1）｜删除条件：写不出（这是人侧约束，责任不可转移）。
- **S4** 约束从自然语言升级为机械执行的触发信号：该约束不可跳过且被执行者反复遗漏；反向，一次性、需人判断或高度情境化的约束不机械化。｜落地 A（外部状态存储 + 人工检查点）：记录每条规则的违反次数，超过阈值进入工具化评审｜落地 B（检查器）：把被反复遗漏的检查项直接做成阶段转换前的检查器｜它防御的失败：追溯链检查写在规范里被反复遗漏（§4.3）；反向防御规则堆积（§9.2）｜删除条件：模型对规范文本的遵循率足够高以至于遗漏频率低于机械化的维护成本。
- **S5** 运行时的元机制（路由、场景识别、格式化返回）本身占用推理工作集，须与规则一样纳入 Add/Thin 评估；元机制的收益必须在真实任务上大于它消耗的上下文。｜落地 A（检查器/评估）：对比启用与禁用该机制时的任务结果与上下文占用｜落地 B（人工检查点）：新增元机制前要求写明预计占用与预期收益｜它防御的失败：为减少噪音引入的路由成为最大噪音源（§3.5）｜删除条件：上下文容量与注意力退化不再是约束。
- **S6** 长任务的状态与进度外置到跨轮可重读的持久记录；循环退出条件由外部检查器根据验证证据判定，执行者的"完成声明"只作为请求判定的信号。｜落地 A（运行时拦截）：退出前拦截并检查证据完备性｜落地 B（外部状态存储 + 检查器）：状态记录含各验证节点结果，检查器据此放行｜它防御的失败：执行者自判完成而隐蔽错误被放过（§9.2 过度信任）；会话中断后不知做到哪（§3.1）｜删除条件：写不出（完成判定的责任不可转移给执行者）。
- **S7** Agent 行为异常时先归因到层级——缺少能力定义 / 有定义但无约束（越界）/ 约束存在但执行器缺陷——再决定修改位置。｜落地 A（静态指令/Runbook）：改进闭环的归因步骤｜落地 B（外部状态存储）：失败 Case 记录必须填写归因层级字段｜它防御的失败：定位错层级，改完还会出问题（§4.3）｜删除条件：写不出。
- **S8** 验证手段不可用而降级时，降级事实与原因必须写入证据/状态记录，降级后的通过不得与完整验证的通过等价。｜落地 A（外部状态存储）：状态记录含 degraded 字段｜落地 B（检查器）：证据包缺少某验证层输出时标记为受限通过｜它防御的失败：前端验证不可用时 API 断言通过被当成全量通过（§6.6）｜删除条件：写不出。
- **S9** 执行者的实验性写入必须与共享环境隔离，隔离粒度至少到执行者进程；隔离方案应允许复用真实的只读部分。｜落地 A（权限与隔离配置）：执行者默认连接隔离数据面｜落地 B（运行时拦截）：对共享环境的写操作被拦截并要求授权｜它防御的失败：未验证数据污染同事的测试环境（§6.8）｜删除条件：写不出。

## 8. 该文暴露的失败模式
- **F1** 一次会话内多个场景规范被叠加加载（需求定义 + 代码探索 + 方案设计 + 横切规则）→ Agent 跳过需求阶段必填项、把方案格式套到需求文档 → 推翻路由机制转工具拉取 → **可构造**：给同一任务叠加 N 份互相独立的规范，度量必填项遗漏率随 N 的变化。
- **F2** 生成的配置中 string 类型字段值语义错误（日期 `2026-01-01` 应为 `2026:01:01`、DSL 前缀 `Ctx.` 应为 `FactModule.`、参数引号）→ 反序列化校验通过、运行时规则永不触发或崩溃 → 10 项自检清单中 5 项标"下游无法检测"，生成阶段拦截 + 修复重试 → **可构造**：构造仅在运行时暴露的 string 字段错误，验证分层验证是否声明盲区并在上游拦截。
- **F3** 规范文本要求"切换测试阶段前验证追溯链完整"→ Agent 经常遗漏 → 做成检查器，不通过阻止阶段切换 → **可构造**：同一约束以文本 vs 检查器两种形态各跑 N 次，比较遗漏率（D-008 验证）。
- **F4** 每次犯错加一条规则 → Skill 指令区从引导变操作手册 → Agent 再次走神（与 F1 同根因）→ 计划按违反频率瘦身，未实施 → **较难构造**（需要长期使用记录），可作 D-026 的观察指标。
- **F5** 会话中断/多次压缩后，领域细节（平台流程、DSL 格式、库存锁定顺序）丢失 → 下次从头问 → 进度与笔记外置到文件 → **可构造**：在压缩后询问早期出现的具体事实，度量召回。
- **F6** 多 Agent 并行处理不可分割任务（Carlini）→ 全部卡在同一 bug 互相覆盖，16 = 1 → 引入参照物拆成文件级子任务 → **可构造**（引用一手来源）：给并行 Worker 一个不可分割任务，观察冲突率。
- **F7** 子代理在主对话中执行审查 → 过程输出爆上下文 → 改为隔离上下文只回摘要 → **可构造**：对比主对话内执行与隔离执行的后续任务质量。
- **F8** 体系跑顺后使用者习惯性信任输出 → 审查放过"看似合理但有并发风险"的实现、需求文档中看似正确的逻辑漏洞 → **未处置**（作者承认无系统性清理机制）→ 对应 D-023"目标失明"的个体版本；构造需要种植隐蔽缺陷的评审 Case。
- **F9** 门禁"每次都通过"却无人知道它是否有价值 → 作者怀疑存在摆设门禁 → 未处置，计划统计拦截事件 → 对应 D-024/D-013 的 Thin 信号；**可构造**：统计每个 Gate 的否决率。
- **F10** 体系预设用户会与 AI 对话 → 新同事对输入框发愣，无法产生任务 → 编写学习体系 + 嵌入式推进 → 不可构造为回归 Case，属组织观测（D-022）。
- **F11** Agent 每个任务重新打开浏览器并重走多步登录 → 慢且脆弱 → 规则"不关浏览器用新 Tab"，但该规则放哪（入口/专项规范/手动提醒）作者未给出结论 → 反映"规则放置位置"本身缺判据；对应 S4/S10。
- **F12** 前端验证工具不可用 → 自动降级为 API 断言 → 降级原因写入状态 → **可构造**：禁用一层验证，检查证据是否标记受限。
