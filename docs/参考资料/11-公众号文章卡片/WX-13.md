# WX-13 驾驭AI Coding：一份面向团队的Harness Engineering落地规范

## 0. 验证边界
- 材料性质：一份**团队内部落地规范的公开版**，作者是规范制定者（腾讯某 Go 后端团队，工具栈为 CodeBuddy IDE + Knot 平台 + 工蜂/TAPD/iWiki/七彩石）。它规定"应该怎么做"，几乎不报告"做了之后发生了什么"——全文没有一个团队级的前后对照数据。
- 唯一的"结果"是§9.3 一份 `harness-audit` Skill 对单个项目（go_scaffolding_svr）的**AI 生成审计报告节选**：75/100、各维度得分、"最近 50 条 commit 中 30% 模糊描述"。这些数字由模型打分产生，权重是作者设定的，没有人工复核记录。
- Quick Wins 表中的"AI 写 SQL 准确率提升 30%+""Commit 规范率 70%→95%+"是**审计报告里的预计值**，不是测量；"索引通常在 24h 内完成""80,000+ 技能库"为产品说明式陈述。
- §1.1 的 OpenAI 数字（3→7 人、5 个月、100 万行、1,500 PR、10 倍）是转述，已核对一手来源（§4）。
- 超出可核实范围：CodeBuddy/Knot/工蜂/TAPD 等内部平台的行为；六大支柱图的来源文章（微信，robots 禁抓）；"Django 创始人"引语的出处（未能定位，见§4）。
- 文中全部"必须/严禁/红线"是该团队对自身的要求（D-014）。

## 1. 文章在讲什么
作者把 OpenAI 的 Harness Engineering 概念（Agent = Model + Harness）转成一份**团队可照抄的规范**：先用"六大支柱"（上下文/工具/编排/状态记忆/评估/约束恢复）给 MCP、Skills、Rules、知识库、Plan 模式、Memories 各自定位，再落成一张五层架构图（输入→工作台→MCP→输出→度量），然后给出三阶段路线（基础建设 1–2 周 → 工具接入 2–4 周 → 持续优化），每阶段附配置步骤与验收标准。日常部分给出三条 SOP（新需求 / Bug 修复 / AI CR）、五条团队红线、八条反模式。最后用一个自制的 `harness-audit` Skill 把整份规范变成"可执行的合规体检"：按七个维度打分（S/A/B/C/D）、诊断、开方。作者声称的结果只有一个：规范可以被工具自动检查，"Skill 就是规范的可执行版本"。核心口号："流水的工具，铁打的规范"。

## 2. 核心主张
- **C1** 团队规范的价值在于把"好代码"的标准写进系统而不是靠个人，因此每个成员必须遵循同一套规范。｜支撑：推理｜适用条件：人员流动的团队｜位置：引言
- **C2** 入口文件（AGENTS.md）应是 ~100 行的目录索引而非百科全书；需求与设计决策必须持久化进仓库，仓库知识是 System of Record，不依赖聊天历史。｜支撑：转述 OpenAI"巨型 AGENTS.md 失败"｜适用条件：通用｜位置：支柱一、§4.4、反模式 7
- **C3** 工具系统三分：MCP 连接外部事实（钥匙）、Skills 封装领域 SOP（进门后做的事）、知识库注入业务上下文（说明书）；三者缺一不可。｜支撑：比喻 + 场景表｜适用条件：有内部平台的团队｜位置：支柱二、图 003
- **C4** 执行编排是"3+1 Phase"多角色流：Planner 生成 requirements.md → 人工审核 → task.md → Generator 编码 → Evaluator 审查 → Archiver 归档并更新知识库；每个角色加载**不同的** Harness 子集；每个任务必须有验收标准。｜支撑：流程图｜适用条件：中等以上复杂度需求｜位置：支柱三、图 004/005
- **C5** 记忆四类：短期（会话）/中期（Memories 功能）/长期（Git 中的 Spec）/变更记忆（`changes/` Spec Deltas），用 Git 记录规范变更作为项目长期记忆。｜支撑：无｜位置：支柱四
- **C6** 评估分四层且机械化程度递减：L1 编译/Lint → L2 单测 → L3 规范合规（AI 检查）→ L4 架构（人 + AI）；代码写完自动编译自测闭环。｜支撑：图 006｜位置：支柱五
- **C7** 约束分三级：硬性红线（Rules）/软性约束（Skills）/安全策略（Safety 兜底）；恢复靠 Git 回滚 + Spec Deltas 可追溯 + 编译失败自动回退。｜支撑：无｜位置：支柱六
- **C8** Rules 按作用域三层：User（个人、全项目）/ Team（Knot 平台审批后下发）/ Project（仓库目录，always 或 manual）；Rules 变更走 PR → 团队 Review → 自动同步到各业务项目。｜支撑：图 008/009｜位置：§4.3
- **C9** 团队规范只有一个真实来源（team-harness 仓库），业务项目通过脚本/CI 拉取副本；项目级 Rules 必须入 Git，不允许本地私有。｜支撑：目录结构 + 脚本｜位置：§4.2、§七
- **C10** 需求按复杂度分流：> 半天走 Plan 模式（Spec → 人审 → task → 逐步执行，每步编译验证），< 半天直接 Agent 模式但仍受 Rules 约束。｜支撑：图 014｜位置：§5.5、§6.1
- **C11** Bug 修复红线：一个 PR 只修一个 Bug；必须先写能复现该 Bug 的测试；根因分析不合理时人工补充上下文重新分析。｜支撑：图 016/017｜位置：§6.2
- **C12** MCP 只在需要外部数据时接入；引入复杂度大于所解决的问题就不用；过度接入会使 Token 暴增。｜支撑：决策树 + 反模式 4｜位置：§5.1.1、§八
- **C13** 关键元数据（Schema、接口定义）优先通过 MCP 实时读取，不维护手工副本。｜支撑：无｜位置：§七"MCP 优先"
- **C14** 规范落地本身应可自动审计：`harness-audit` Skill 按 7 维度加权打分、诊断、按 P0–P3 开方；每个维度精确对应规范章节。但"审计报告是体检不是 KPI"。｜支撑：单项目报告节选｜位置：§九
- **C15** 度量层（AI 代码占比、交付量、Bug 率、Review 通过率）反馈到配置中心：Bug 率上升 → 检查是否要**补新 Rules 或优化 Skills**。｜支撑：无｜位置：§2.1
- **C16** 最终质量把关靠人：成本降了标准不能降，工具变强人的判断力要跟着变强。｜支撑：引语｜位置：§十

## 6. 建议采纳（候选语义）
- **S1** 团队级行为约束有且只有一个受治理的来源；任何执行环境中的副本必须能追溯到该来源的某个版本，且约束变更须经审查批准后才对团队生效。｜落地 A（外部状态存储 + 人工检查点）：版本库中的规范仓库，变更走评审合并｜落地 B（权限与隔离配置）：平台集中托管、审批后下发、成员本地不可改｜它防御的失败：成员各自维护私有规则，同一任务在不同人手里 AI 行为不同且无法审计｜删除条件：写不出（责任类规则，不随模型能力消解）
- **S2** 不同角色/阶段只加载与其职责相关的约束、知识和工具子集；审查者加载验收标准，不加载生成侧的操作手册。｜落地 A（条件加载规则）：按阶段/角色触发的加载清单｜落地 B（权限与隔离配置）：审查者以独立会话或独立权限集运行，只能读到工件与验收标准｜它防御的失败：审查者与生成者共享同一上下文，复述生成时的假设而非独立判断｜删除条件：模型在同一上下文内能被证明做到独立评价（需 eval 证据）
- **S3** 可由工具直接读取的事实（模式定义、接口契约、配置）不得在规范或上下文中维护人工副本；上下文应从事实来源按需读取。｜落地 A（运行时工具接入）：查询型工具实时读取｜落地 B（检查器）：检查规范文本中是否出现与源不一致的字段/接口描述并报错｜它防御的失败：AI 依据过期副本写出不存在的字段｜删除条件：写不出（这是"第二个事实来源"原则的推论，不依赖模型能力）
- **S4** 验证按确定性从高到低排序执行：先机械检查（构建/静态检查/测试），再模型判断，最后人工判断；低确定性环节不得替代高确定性环节。｜落地 A（检查器）：流水线固定顺序，前一级失败不进入下一级｜落地 B（人工检查点 + 静态指令）：评审清单要求先附机械检查结果再开人工审查｜它防御的失败：把"AI 审查通过"当成测试通过；人在能机械判定的项目上消耗判断带宽（D-024）｜删除条件：写不出
- **S5** 缺陷修复的交付单位必须包含一个能在修复前失败、修复后通过的可复现检查；修复与无关变更不得同批。｜落地 A（检查器）：合并前要求关联测试的新增/变更｜落地 B（人工检查点 + 外部状态存储）：工作项记录复现步骤与验证结果，审查者核对｜它防御的失败："修好了"无法证伪，同一缺陷回归｜删除条件：写不出
- **S6** 已完成工作项的规划工件必须归档而非删除或滞留在活跃区，且归档动作与"晋升为项目知识"是两个不同的动作，后者需要审批。｜落地 A（外部状态存储）：活跃/归档两区分离｜落地 B（人工检查点）：知识库更新走候选审批｜它防御的失败：活跃区堆积过期 Spec 被新会话误读；AI 生成摘要未经审核进入团队知识｜删除条件：写不出
- **S7** 规范自身应有一个可重复执行的对照检查，且检查结果只作诊断不作考核；检查项应偏向"规则是否有来源与消费"而非"工件是否存在/数量多少"。｜落地 A（检查器）：脚本或 Skill 扫描并出报告｜落地 B（人工检查点）：季度复盘按同一清单人工核对｜它防御的失败：规范写完无人执行；或反过来，为了得分堆工件（D-023）｜删除条件：写不出（"不作考核"是治理选择）。注：本文只做到了前半句，后半句是本卡片对其缺陷的修正。
- **S8** 外部能力接入以"是否需要该事实/能力"为前提，接入面受预算约束；接入的复杂度大于其解决的问题时不接入。｜落地 A（静态指令 + 人工检查点）：接入决策树与优先级清单｜落地 B（检查器）：统计各接入能力的调用频次与 Token 占用，无消费者的接入标记为待删｜它防御的失败：工具描述占满上下文、Token 暴涨｜删除条件：模型/工具能按需延迟加载工具描述且成本可忽略（部分工具已具备，需评估）

## 8. 该文暴露的失败模式
- **F1** 三个来源的 Rules（个人/团队/项目）同时 always 加载且无优先级 → 冲突时模型静默择一（ATT-N"隐性冲突"）→ 文章无处置 → 可构造：个人规则"回复用英文"vs 团队规则"注释用中文"vs 项目规则相反，观察模型选哪条并是否报告冲突。
- **F2** 项目事实（统一响应包）被写入个人 Memories → 成员 A 的 AI 与成员 B 的 AI 对同一规范给出不同代码；团队规则更新后个人记忆不更新 → 文章无处置 → 可构造：更新 Team Rule 后，用带旧 Memories 的会话执行同一任务，看采用哪个版本。
- **F3** 同步脚本把上游 Rules 复制进项目目录，与项目自有 Rules 混放且 CI 会覆盖 → 本地对同名文件的修改被无声覆盖，或上游删除的规则在项目里残留 → 文章仅"可选 CI 同步"，未声明编辑边界（ATT-P） → 可构造：上游删除一条规则后跑同步，检查项目副本。
- **F4** 用"问 AI 当前加载了哪些 Rules"验证规则生效 → 自报可能与实际注入不符 → 文章接受自报 → 可构造：故意放一个格式错误的规则文件，问 AI 是否加载。
- **F5** 合规审计按工件存在性打分（无 mcp.json → MCP 维度 0 分）→ 不需要外部数据的项目被扣分并收到"P0 接入 DB MCP"处方，处方还引用不存在的包 → 文章说"分数不是 KPI"但机制仍在 → 可构造：对一个纯算法库跑同类审计，看是否要求接 DB MCP。
- **F6** 改进闭环只有"补 Rules"一个方向，规则无失败绑定、无删除条件 → 规则集单调膨胀、遵循率下降（ATT-N 注意力 U 形）→ 文章无处置（月度 Review 只查"脱节"）→ 可构造：记录该团队 Rules 行数随时间的曲线；本项目内可用 D-026 的"每轮增删行数比"。
- **F7** Skill 晋升路径为"生成 → 人看清单 → 一句话试用 → 入库"，无 eval → 描述触发不准（过触发/漏触发）进入团队库 → 上游 skill-creator 的 eval 循环被删 → 可构造：对一个入库 Skill 用 10 个相邻但不该触发的请求测试误触发率。
- **F8** 红线"严禁无 Spec 直接编码"与 SOP"< 半天需求无需 requirements.md"并存 → 执行者无法判定哪条生效 → 文章未察觉 → 这是 D-014 所说"命令语气无法区分效力"的实例，可作为规范自检 Case。
