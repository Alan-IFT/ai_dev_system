# WX-28 重磅！Graph Engineering 实操手册公开

## 0. 验证边界

## 1. 文章在讲什么
问题：单体 loop 跑稳之后，怎样把多个 loop 组织成"能自己路由"的图，而不是把它们串成一条脆弱的线性脚本。作者先给四个门槛问题（能否拆角色、有无真并行、单上下文是否装得下、失败跳转是否负担得起）加一道附加题（有没有一个已跑稳的 loop），劝退大多数人。然后按 14 步展开：区分节点（工作单元）与边（数据依赖）；用 schema 给节点定契约、按数据给边命名；用扇出/屏障汇入/菱形做主力拓扑；用"模型分类、代码选边"做路由，在边上放验证器，用工作区隔离防并行写冲突；给循环加"连续 K 轮无新发现"的收敛条件并对"见过的一切"去重；给不同节点配不同档位模型；默认用无屏障的流水线而不是屏障；最后让模型自己写编排脚本并把脚本存档版本化。声称的结果：编排层不消耗模型上下文，一次运行可扩展到几十上百个子代理；Bun 团队"靠对抗式代码评审焊进循环"完成了运行时移植。全文无对照数据。

## 2. 核心主张
- **C1** 图是 loop 的组织方式而非替代品；先有一个跑稳的单体 loop，再谈建图；四个门槛问题（可拆角色 / 有真并行 / 单上下文装不下 / 失败跳转负担得起）任一答否就不建图。｜支撑：推理｜适用条件：作者面向"多数人 loop 还没跑稳"的读者｜文中位置：动手前
- **C2** 一张能跑的图 = 节点 + 边 + 共享状态 + 失败路由；"没有失败边的图只是流程图"；重试耗尽后控制权去哪（退回上一步 / 转备用节点 / 转人工）必须事先写明。｜支撑：定义｜适用条件：通用｜文中位置：四个核心构件
- **C3** 边是数据依赖，不是"然后"。判据：下游没真用到上游的数据，就没有边。线性脚本是退化的图；对每根箭头问"携带数据吗"，剪掉不携带的箭头，链就塌缩成"几个并行节点喂一个汇合节点"。｜支撑：推理 + 图 004｜文中位置：01–02
- **C4** 节点契约 = 显式输入（不能从共享窗口"蹭"）+ 可校验的输出形状 + 只干一件事；无法推理的节点无法并行。校验发生在工具调用层，格式不对模型自行重试，不把自由文本甩给下游解析。｜支撑：产品机制（一手核实一致）｜文中位置：03
- **C5** 边也是数据契约：按数据而非顺序命名边，就能看出边是否真实存在，并在形状不变时替换两端节点。归约（压平/去重/过滤）是普通代码，"很多人花模型 token 做的事其实是一条边，而边是免费的"。｜支撑：推理｜文中位置：04
- **C6** 扇出的两条稳定性细节：屏障等全部完成；单个失败解析为 null 而不拖垮批次，汇入必须容忍缺失输入。编排层活在代码里，主上下文从不同时装着 N 个信源，因此可扩展到上百子代理。｜支撑：产品机制（一手核实：并发上限 min(16, CPU−2)，单次调用 ≤4096 项，每次运行 ≤1000 个 agent——本文全部省略）｜文中位置：05–06、10
- **C7** 屏障只值得在"必须看到全集"的节点付出等待成本：跨集合去重、总数为零提前退出、prompt 需对照其他发现。"parallel → 无跨条目依赖的 transform → parallel"说明中间那道屏障是多余的。｜支撑：推理 + 图 014｜文中位置：06、13
- **C8** 菱形（拆分 → 并行 → 合并）即"派发 → 归约 → 合成"，是几乎所有正经 agent 图的主力骨架；真正可扩展的问题是"拆分点在哪、合并点在哪"。｜支撑：推理 + 图 008｜文中位置：07
- **C9** 路由：模型负责分类，代码负责选边；同一分类结果每次走同一条路；"跳过审计"必须是图里写明的边才可能发生。｜支撑：推理 + 代码示例｜文中位置：08
- **C10** 验证器蹲在结果放行之前，唯一工作是试图推翻它；三种打法（对抗式 / 多视角 / 评委制）。Bun 移植靠"对抗式代码评审焊进循环"做成。｜支撑：Bun 官方博客（一手核实见 §4）｜文中位置：09（三种打法 WX-21 C8 已记，此处不重复）
- **C11** 失败应被限制在节点内；并行写文件时用独立工作区隔离，只在真会并行写入的拓扑里用——"是安全带，不是每次运行都要交的税"。｜支撑：产品机制（一手：worktree 隔离"EXPENSIVE，仅在并行改文件时用"）｜文中位置：10
- **C12** 规模未知的探索用受控回边，收敛写法是"跑到干为止"：连续 K 轮无新发现才停。**去重必须对"见过的一切"，不能只对"已确认的"**，否则被否掉的发现每轮重新冒出，循环永不收敛，变成"专门花钱反复发现同一批死胡同的机器"。｜支撑：代码示例（与一手参考逐字一致）｜文中位置：11
- **C13** 不同节点配不同档位模型：重复性抽取/分类节点用便宜模型，合成/裁定节点用高档；子代理默认继承会话模型，大规模运行前须先确认档位。｜支撑：产品机制（一手措辞更保守："默认省略 model，只在高度确信时覆盖"）｜文中位置：12
- **C14** 拓扑就是成本和延迟：屏障让所有人等最慢者；无屏障流水线让每条数据独立流过各阶段。默认流水线，只有阶段需要全部前置结果时才用屏障。｜支撑：推理 + 图 014｜文中位置：13
- **C15** 无法提前规划的活，让模型自己写编排脚本（动态生成图）；跑得好就把脚本存档、版本控制、按名重跑，仓库克隆者可直接复用。｜支撑：产品机制（一手核实一致）｜文中位置：14
- **C16** 结语：两年来多 agent 的杠杆在单 loop（更好的 verifier、更稳的退出条件、更干净的状态文件）；现在"loop 怎么连"成了新护城河。｜支撑：无｜文中位置：结尾

**最有价值的三个引用：**
1. **workflow-authoring 一手参考**：它证明本文的"14 步"不是社区经验总结，而是**一份产品脚本参考的改写**——这决定了本卡片的采纳方式：可采纳的是参考里那些与产品无关的**结构判据**（边 = 数据依赖、屏障合理性三条件、对全部已见去重、静默截断警告、完整性批评者、预算硬上限），而不是任何 API 形态。它也暴露了转述链的损耗方向：每一手都丢掉"限制与警告"，保留"能力与技巧"。
2. **Bun 博客**：本轮唯一带一手数字的真实案例。对本项目的价值不在 64 个 Claude 或 $165k，而在三条方法：审查者只拿 diff 且被告知假定错误（对应 WX-21 S1 验证器黑盒，且比它更强——预设立场为否定）；出错时修生成流程而非手修产物（改进闭环"找最早偏离点"的实例）；"比 please 更强的隔离"（ATT-G/M"prompt 不是安全边界"的又一独立佐证）。条件：Bun 本身有百万断言的语言无关测试套件、操作者是该代码库作者、token 成本由 Anthropic 承担——三条缺一，案例不可外推。
3. **dynamic workflows 文档**：给出了"确定性编排"的具体代价清单——无中途人工输入、脚本内禁时间与随机数、失败重放会重跑已完成节点、预算为硬上限。这些是"把控制流放进代码"这条主张的**另一面**，本文一条都没写。

**冲突 1：汇入"容忍缺失"与"静默丢失"。** 本文 C6/C11 建议对失败节点的 null 做 `.filter(Boolean)` 后继续，把"容忍缺失"当作韧性。WX-21 F4 与 D-023 的立场是：扇入静默合并缺失分支，产出看似完整实则缺信源。本文的一手来源本身也站在 F4 一边——"No silent caps: log() what was dropped — silent truncation reads as 'covered everything' when it didn't"，且 `/deep-research` 把不可核验项标为 unverified。因此这是**转述失真造成的冲突**：一手要求"容忍 + 报告缺失"，本文只保留了"容忍"。证据更强的是一手；可共存的写法是：汇入节点允许缺失输入，但输出必须携带"缺失了什么"。
**冲突 2：恢复粒度。** WX-21 S3 依据 LangGraph "pending writes" 提出"一步内并行部分成功时只重跑失败部分"。Claude Code 工作流的一手文档明确：失败 agent **及其后启动的全部 agent** 重跑，"a failure in the middle of a fan-out reruns work that already finished"。两种产品的恢复语义不同，说明 S3 的"只重跑失败部分"是**某一载体的特性**而非普遍可得；语义层只能要求"恢复不得丢失已确认结果"，重跑范围属实现差异。S3 措辞需收窄。

## 6. 建议采纳（候选语义）
- **S1** 执行单元之间的依赖边只在"下游消费上游产出"时存在；把顺序脚本改为并行结构前，逐条依赖核查是否真有数据流过，不携带数据的顺序约束不构成依赖。｜落地方式 A（人工流程）：任务拆分评审时要求每条先后关系写出"传递了什么"，写不出的改为并行｜落地方式 B（检查器）：对声明的工作流/任务图做静态检查，报告无数据流的顺序边｜它防御的失败：把"然后"当依赖，独立子任务被串成单链，任一节点卡住则全链停摆（F1）｜删除条件：写不出（这是拓扑事实，不随模型能力变化）
- **S2** 汇合点允许部分输入缺失，但汇合输出必须显式携带"预期 N 路、实收 M 路、缺失哪些及原因"，下游与最终报告不得把缺失路视为已覆盖。｜落地方式 A（检查器）：汇合工件的 schema 含 expected/received/missing 字段，缺字段即失败｜落地方式 B（人工检查点）：验收清单要求汇总者列出未返回的信源/子任务｜它防御的失败：扇入静默吞掉失败分支，报告"审计了 18 个文件"实际 11 个（F2）｜删除条件：执行环境保证任一子任务失败必然使整体失败并显式报告（此时缺失不可能静默，但该保证仍是载体，语义不消失——写不出）
- **S3** 发现型循环的停止条件是"连续 K 轮无新发现"，且"新"相对于**全部已见项（含被否决项）**判定；被验证否决的发现必须进入已见集合，否则循环不收敛。｜落地方式 A（外部状态存储）：已见集合持久化并含判决状态，每轮先对它去重｜落地方式 B（静态指令 + 人工检查点）：探索任务立项时声明 K 与去重键，人工在复查时检查同一发现是否重复出现｜它防御的失败：只对已确认项去重，被否决项每轮重新出现，循环把预算花在反复发现同一批死胡同上（F3）｜删除条件：写不出（属状态定义而非模型能力）
- **S4** 同步点（等待全部前置完成）只在"某步必须看到全集"时设置：跨集合去重、总数为零提前退出、需对照其他结果作判断；"阶段在概念上分开"或"结构更清晰"不构成设置同步点的理由。｜落地方式 A（人工流程）：工作流设计评审对每个同步点要求写出"哪一步需要全集"｜落地方式 B（检查器/轨迹分析）：从轨迹统计各同步点的等待时间，长期无跨条目依赖的同步点报告为可删｜它防御的失败：所有分支等最慢者，快分支空转（图 014 "idle — wasted"）；D-022 所述等待时间在链内被制造出来｜删除条件：写不出（属调度事实）
- **S5** 绕过某个验证/审计步骤只能通过结构中**事先写明的条件边**发生，判定该条件的可以是模型，但选边与"是否存在绕过路径"必须由确定性逻辑决定；模型不能在运行中创造一条绕过边。｜落地方式 A（运行时拦截）：验证步骤由外部编排触发，执行单元无法自行跳过｜落地方式 B（人工流程 + 外部状态存储）：绕过路径作为工作项状态机的显式转换并记录触发条件，未定义的转换不得发生｜它防御的失败："模型自己决定跳过审计"（本文原话）；D-028 已登记的自改审批路径 Case｜删除条件：写不出（责任不可转移）
- **S6** 验证者的默认判决为否定：无法完成验证（超时、限流、证据缺失）时结论是"未核验"，不得计为通过，也不计为否决；最终报告须区分"通过 / 否决 / 未核验"三态。｜落地方式 A（检查器）：验证输出 schema 强制三态枚举，缺省值为未核验｜落地方式 B（人工检查点）：审查表要求每项勾选三态之一，空白视为未核验｜它防御的失败：验证器因环境故障静默返回空，被汇总当作"无问题"（F4）；D-014 空集合条款的同型失败｜删除条件：写不出
- **S7** 每个执行单元必须声明重试耗尽后的去向（退回上游、转备用单元、转人工），未声明去向的结构不视为可执行的工作流。｜落地方式 A（静态指令/模板）：工作流定义中"失败去向"为必填项｜落地方式 B（运行时拦截）：编排器在重试耗尽且无去向声明时强制暂停并升级到人｜它防御的失败："图在你看不见的地方卡死或乱跑"（本文原话，F5）｜删除条件：写不出
- **S8** 长时间自动化运行必须绑定**硬性资源上限**（执行单元总数、token/成本、轮数），达到上限时执行单元的创建失败而非仅告警；"大运行"提示只是辅助。｜落地方式 A（权限与隔离配置）：预算在会话/运行创建时固化（与 D-027 同型）｜落地方式 B（外部状态存储 + 人工检查点）：预算记录在工作项，超限转人工｜它防御的失败：不收敛的循环"直到预算耗尽才停"；一手文档 1000-agent 上限即为此设｜删除条件：写不出
- **S9** 出错时优先修改**生成产物的流程**（提示、结构、验证），而不是手工修补产物本身，并把该次修改与触发它的失败绑定记录。｜落地方式 A（人工流程）：复盘记录要求写"改了哪一步流程"而非"改了哪行代码"｜落地方式 B（外部状态存储）：流程版本与失败 Case 关联，可回溯｜它防御的失败：同类缺陷在下一批产物中重现，手修工作量随规模线性增长（Bun 博客"one prompt edit and a few hours later, these things stopped happening"）｜删除条件：写不出（属改进闭环的操作纪律）

## 8. 该文暴露的失败模式
- **F1** 独立子任务被写成顺序脚本（"总结文件然后查天气"）→ 任一节点卡住则后续全停，且上游产出被困 → 文章处置：逐箭头核查数据流，剪掉不携带数据的边 → 可构造：给定三个无数据依赖的子任务的顺序脚本，注入一处超时，比较顺序与并行结构的完成率与总时长
- **F2** 扇出中一路失败被解析为空并被过滤 → 汇合报告看似完整，实际少一路 → 文章处置：`.filter(Boolean)` 继续（**本身即失败**）；一手参考处置：log 被丢弃项 → 可构造：18 路扇出随机使 3 路返回空，检查最终报告是否声明"15/18"
- **F3** 发现型循环只对已确认项去重 → 被否决的发现每轮重现，"连续 K 轮无新发现"永不满足 → 文章处置：对全部已见项去重 → 可构造：固定一个必被否决的伪发现，观察循环轮数是否封顶
- **F4** 验证器因限流/错误未返回判决 → 若汇总把空判决当作"无异议"，未核验项流入结论 → 一手文档处置：标为 unverified → 可构造：使验证 agent 全部超时，检查报告是否把待验项计为通过
- **F5** 图中某节点重试耗尽而无失败边 → 运行在不可见处卡死或走向未定义路径 → 文章处置：每个节点事先声明退回/备用/人工 → 可构造：构造无失败边的两节点图，使下游节点持续失败，观察是否无限等待或静默结束
- **F6** 不必要的屏障 → 快分支等慢分支，端到端时长 = 最慢分支之和 → 文章处置：默认无屏障流水线 → 可构造：同一 5 路任务分别用屏障与流水线，分支耗时 1:3，比较总时长与空闲时间
- **F7** 并行执行单元写同一工作区 → 文件互相覆盖、git 状态被另一单元的 stash/reset 破坏 → 文章处置：按需 worktree 隔离；Bun 处置：禁止非提交类 git 命令 + cgroups 限资源 → 可构造：两单元并行改同一文件，有无隔离对照
- **F8** 大规模运行按会话档位计费而操作者未察觉 → 账单超预期 → 文章处置：运行前确认档位；一手文档处置：Large workflow 提示 + 硬上限 → 可构造：预算上限 N 时观察超限行为是抛错还是继续
- **F9** 手修生成产物而非修生成流程 → 同类缺陷在下一批重现 → Bun 处置：改提示/结构后"几小时后这类事不再发生" → 可构造：同一缺陷模式在两批次中的复发率（修产物 vs 修流程）
