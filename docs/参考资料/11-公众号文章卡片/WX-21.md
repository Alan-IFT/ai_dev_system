# WX-21 Loop Engineering 已死？ 一文带你了解Graph Engineering

## 1. 文章在讲什么
1. 2026-07-17 Peter Steinberger 一句"还在聊 loops 还是已转向 graphs"引爆讨论，"Graph Engineering"一词随之诞生；作者承认词是新包装，但主张"从编排一个智能体到编排一群智能体"的重心迁移是真的。
2. 作者把 Prompt → Context → Harness → Loop → Graph 摆成五层，声称每层解决上一层够不着的问题，Graph 建立在前四层做好的前提上。
3. 单循环（ReAct 型）有五个结构性缺陷（上下文腐烂、错误级联、工具过载、缺乏控制粒度、可观测性差）外加"目标失明"；这些不是"把循环做大"能解决的。
4. Graph 定义为 G=(V 节点, E 边, S 状态, P 策略)；三种拓扑（菱形扇出扇入、主管-工人、流水线）与 Anthropic 五模式对应。
5. 全文核心：图的价值不在智能体数量，在确定性——把"做判断"与"做验证"拆成独立节点，确定性工作交给代码，证据链必须有现实锚点。
6. 用"每日研究简报"例子对比臃肿 Loop 与三节点小图，给出决策规则：每天跑的任务值得付图的税，只跑一次的不值。
7. 转述 Anthropic 数据（90.2% / 15× / 80%）与三条多智能体判据，给出"任务会分叉、并行、要审批或跨天吗"的一问式判断。
8. 框架对比 + LangGraph 检查点机制 + LinkedIn/Uber 案例；结论：Graph 是"命名事件 + 视角上移"，形似老工作流但节点里住着自主智能体。

## 2. 核心主张
- **C1** 五层（Prompt/Context/Harness/Loop/Graph）是嵌套叠加而非替代，Graph 建立在前四层做好的前提上。｜支撑：推理｜适用条件：作者的概念框架｜文中位置：§02
- **C2** 单循环的五个缺陷是"循环"形状的必然结果：每轮把思考/调用/观察塞回同一窗口导致目标被淹没；同一推理链里难以自我跳出错误；15～20 个工具时选择准确率骤降；无法中途暂停审批、换模型、独立质检；只能看到"想了什么"看不到"为何在此分支"。｜支撑：推理 + 转述（工具数来自 Claude 博客）｜适用条件：单智能体长循环｜文中位置：§04
- **C3** 目标失明：循环只看见被赋予的指标，会用背叛指标初衷的方式移动它（客服案例：解决率涨五个月、续费流失翻倍）。｜支撑：无具名出处的案例｜适用条件：以单一代理指标驱动的自动优化｜文中位置：§04（ATT-J 已吸收）
- **C4** 可执行的图 = 节点（一进一出只干一件事，可为智能体或确定性步骤）+ 边（直通/条件/扇出/扇入/回环）+ 状态（沿边流动、共读共写，记录任务、证据、预算、产物、检查点）+ 策略（谁能创建节点、调工具、改图、产生副作用、必须等人批）。｜支撑：定义｜适用条件：通用｜文中位置：§05
- **C5** 流程图给人看，Graph 给机器跑：只有节点能独立执行、边携带明确状态、过程可检查/暂停/恢复/追踪，才算系统结构而非展示材料；它也不是知识图谱。｜支撑：推理｜文中位置：§05
- **C6** 三种拓扑可拼装嵌套；Anthropic 五模式是三形状的细化；先找最简单方案，多数应用单次调用 + 检索 + 少量示例即够。｜支撑：转述 Anthropic BEA（核实一致）｜文中位置：§06–07
- **C7** 图的杠杆是确定性而非智能体数量：模型"既当运动员又当裁判"是多数系统翻车的根子；应把判断与验证拆成两个节点，验证器用全新上下文只看最终结果与验收标准，专门试图推翻结论。｜支撑：推理 + Claude 博客的验证器模式（核实一致）｜文中位置：§08
- **C8** 验证力度按轻重分诊（Router），三种打法：对抗式（多个怀疑者分头驳，多数没驳倒才过）、多视角（正确性/安全性/可复现各查各的）、评委制（多方案并行打分选优并吸收亚军）。｜支撑：无（作者归纳）｜文中位置：§08
- **C9** 确定性工作（格式校验、跑测试、去重、排序、算预算）交给普通代码；"判断力落在节点上，可靠性落在边上"。｜支撑：推理｜文中位置：§08
- **C10** 现实锚点：所有节点互引模型结论而无一碰现实，就是"项目管理做得更好的更大幻觉"；锚点是测试真跑过、钱真到账、用户真留下；"更好"指什么必须由人定。｜支撑：转述 Towards AI 措辞｜文中位置：§08（ATT-J 已吸收）
- **C11** Loop→Graph 的全部决策是一笔摊销账：图要维护多份提示词、设计节点间状态结构、应对新失败模式（合并漏信源、路由死循环、状态泄漏）；每天跑的任务值，只跑一次的是纯税。｜支撑：每日简报例子（推理，无实测）｜文中位置：§09
- **C12** 多智能体更强但靠烧 token 换：90.2% / 15× / 80%；只值得用于价值足以覆盖成本的任务；三把尺子——上下文保护、可并行、专业化；单目标单领域有明确停止条件的任务用单循环最优。｜支撑：转述 Anthropic（数字核实一致，"1000 token"阈值未核实到）｜文中位置：§10
- **C13** 治理红线：工作图（任务怎么拆合）可快变；角色图（谁能改库、谁能绕审批）必须慢变、可审计，绝不让模型现场发挥。｜支撑：推理｜文中位置：§10（ATT-J 已吸收，D-028）
- **C14** 检查点让智能体从"能演示"到"能上生产"：每个超级步末存整图快照，带来人在回路、记忆、时间旅行、容错；"待写入"使同一步中失败节点的兄弟节点不必重跑。｜支撑：转述 LangGraph 文档（核实一致）｜文中位置：§11
- **C15** 图把智能体之间的"对话"变成"状态转换"，省掉互相转述背景的开销，因此同任务 token 远低于对话式框架。｜支撑：转述"DataCamp"表（**出处核实不符**）｜文中位置：§11
- **C16** Graph 与老工作流形似神不似：边和结构固定（可治理、可审计），节点内部自主（灵活）；是 Anthropic "workflow 预定义路径 / agent 动态决定"两定义的融合。｜支撑：推理｜文中位置：§12

## 6. 建议采纳（候选语义）
- **S1** 验证节点只接收待验工件与验收标准，不接收生成过程的上下文；验证输出必须能否决并触发回边。｜落地方式 A（人工检查点）：审查人只拿到 diff/产物与验收 ID 清单，不看会话记录｜落地方式 B（检查器/隔离配置）：在隔离的干净执行环境中以工件为输入运行验证，验证进程无法读取生成会话｜它防御的失败：作者在写出草稿的同一上下文里审查，几乎必然通过（F1）｜删除条件：模型在同一上下文内对自身输出的否决率与独立评审无统计差异（需 eval 证明）
- **S2** 验证深度随结论的影响范围分级：低影响结论快速核对，高影响（安全、数据、不可逆）结论须多视角或对抗式独立核验。｜落地方式 A（条件加载规则）：按变更触碰的范围/风险标签加载不同验证清单｜落地方式 B（运行时拦截 + 人工检查点）：高风险动作前强制第二审查者或人工批准｜它防御的失败：所有结论用同一浅层检查，高风险结论漏过（或全部深检使 Gate 数超出人能判断的量，D-024）｜删除条件：写不出
- **S3** 长任务的恢复粒度是"步"而非"会话"：每个步骤结束后持久化可重放的状态快照；一步内并行子任务部分成功时，保留已成功部分，恢复时只重跑失败部分。｜落地方式 A（外部状态存储）：工作项状态版本随每步递增并记录各子任务结果｜落地方式 B（人工流程）：交接合同要求列出每个子任务的完成/未完成状态，接手者按清单续做｜它防御的失败：环境中断（CI 抖动、冻结窗口）后从头重跑，浪费且可能产生与已完成部分不一致的结果｜删除条件：执行环境本身提供跨中断的透明续跑（该能力仍是载体，语义不消失，故写不出）
- **S4** 升级到显式多节点/状态机结构的判据中加入**执行频次**与**跨会话时长**：重复执行的任务允许承担结构成本，一次性任务默认用最简机制；任务预期跨越会话或需要中途审批时，必须有可恢复状态。｜落地方式 A（静态指令/人工流程）：任务立项时声明频次与预期时长，作为复杂度阶梯的输入｜落地方式 B（检查器）：对声明为一次性却引入多节点编排的方案发出告警｜它防御的失败：为一次性任务搭多节点结构，付出多份提示词、状态结构与新失败模式的税（F3）｜删除条件：写不出（这是价值判断而非能力缺口）
- **S5** 策略（谁能创建执行单元、调用哪些工具、修改编排结构、产生副作用、消耗多少预算）与编排结构分离声明，且策略不可由执行单元在运行中修改。｜落地方式 A（权限与隔离配置）：预算与工具白名单在会话创建时固化｜落地方式 B（外部状态存储 + 人工检查点）：策略变更走独立审批记录，运行时只读｜它防御的失败：模型现场扩大自身权限或预算（D-027/D-028 已有同类 Case）｜删除条件：写不出
- **S6** 比较多单元编排与单单元的收益时，必须在**等 token 预算**下对照，并单独报告 token 用量、工具调用次数与模型选择三个协变量。｜落地方式 A（检查器）：eval manifest 强制记录三协变量，缺失则报告无效｜落地方式 B（人工流程）：评审时要求给出等预算对照或说明为何不可比｜它防御的失败：把"多花 15× token"的收益误读为"结构"收益（F5）｜删除条件：写不出（属测量纪律）

## 8. 该文暴露的失败模式
- **F1** 生成者与审查者共享同一上下文（自审）→ 审查几乎总是通过，错误流入交付 → 文章处置：审稿节点用全新上下文只看简报与验收标准 → 可构造：同一有缺陷工件分别交"同上下文自审"与"仅工件 + 标准的独立审"，比较否决率
- **F2** 单循环上下文腐烂：每轮把思考/工具调用/观察回塞同一窗口（文章示例第 1 轮 2000 token、第 10 轮 1.8 万）→ 原始目标被自我推理淹没，模型对着自己的输出反复分析 → 文章处置：节点隔离，研究员只回传结构化笔记 → 可构造：多轮工具任务中注入原始目标偏移检测，观察第 N 轮后目标遵循率
- **F3** 为一次性任务搭多节点编排 → 多份提示词、状态结构设计、合并漏信源/路由死循环/状态泄漏等新失败 → 文章处置：只跑一次的任务用单循环 → 可构造：同一一次性任务分别用单循环与三节点图，比较总成本与缺陷数
- **F4** 扇入合并静默丢失一个分支的结果 → 汇总看似完整实则缺信源 → 文章仅列为"新失败模式"未给处置 → 可构造：扇出 N 路，随机使一路超时/空返回，检查扇入节点是否报告缺失而非静默合并
- **F5** 用不等预算的对照声称"结构带来收益"（80% 方差由 token 解释）→ 结论把算力收益误归于编排 → 文章未识别为失败（它本身犯了这个错）→ 可构造：同任务固定 token 预算对比单/多单元，观察差距是否消失
- **F6** 指标代理（工单解决率）被优化而目标（续费）受损 → 曲线上涨五个月才被发现 → 文章处置：现实锚点 + 人定"更好" → 已由 D-023 登记，本文补充"发现延迟"维度：锚点观测必须有时效要求
- **F7** 一步内并行子任务部分失败后整体从头重跑 → 已成功部分被重做，可能与先前结果不一致 → 文章处置：pending writes 保留成功写入 → 可构造：三路并行一路失败，恢复后检查成功两路是否重跑
- **F8** 权限/审批路径由模型现场决定 → 随时可爆的事故 → 文章处置：角色图慢变可审计 → D-028 已登记同类 Case
