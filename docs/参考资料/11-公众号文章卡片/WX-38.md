# WX-38 一篇讲透Agent自进化飞轮怎么搭：评测→记忆→落地→控制

## 0. 验证边界
- 材料性质：两位腾讯工程师的方法论综合。作者明言基于"Anthropic 递归自改进报告、斯坦福 CS329A、EvoAgentX 等开源框架的研读"加"业界多个团队已验证的实践"，**没有自己的实验、对照组或消融**。全文数字均无测量条件：迭代次数 −70%、Token −80%+、Agent Memory 场景 Token −60%（图 014 标为 TencentDB Agent Memory，−61%）、"75% 项目因噪声降级、3.8 倍留存率差异"（仅图 014，正文写成"多个团队…显著优于"）、工单解决率"<30%→近 90%"（图 037 标 TCS）、"5 轮内见效"、"前四层过滤 95% 低质变体"、"+0.05/−0.12 非对称淘汰"（图 014 标 TCS EvoLoop）。这些数字来自未公开的腾讯内部系统（TCS EvoLoop、混元 Hy-Memory、微视 CTR），**无法核实**，本卡片一律作"该团队在未说明条件下的自述"登记。
- 作者把"我的核心论断"与引用来源交织，多处把自己的建议写成来源的机制（见 §4：Dreaming"最终决定由人完成"、"文件系统比专用 API 更有效"、Anthropic"隐蔽累积偏移"）。
- 超出可核实范围：TCS/Hy-Memory/微视的实现与数据；"20+ 轮无效迭代最终发现工具层 Bug"等案例；图 011 的 Cohen's Kappa 是否真在使用；"符号化压缩（Mermaid）Token −60%"无出处。
- 文章框架（三层自进化、四齿飞轮、八环节、Level 0–3、Phase 1–4）是作者自创的组织方式，不是任何来源的原文。

## 1. 文章在讲什么
问题：评测、记忆、Self-Improve 在多数团队被拆开做——分数进周报不进改进链路、记忆召回噪声高被默默关掉、自动生成的 Skill 无评测筛选无版本回滚——"每块都做了，飞轮没转"。作者先区分自进化三层（改产物 / 改 Harness / 改模型权重），主张 Harness 层"即时、可控"是当下主战场。随后按四齿展开：**信号**（评测有方向指引/质量门控/经验筛选三重职责，评测失真会让 Agent"加速犯错"，七大难题以弱评估器最致命，建设四问：手段分层、评测集三分法、诊断归因分流、评估器自身校准，加 Skill 四层验证）；**积累**（记忆是治理问题不是存储问题，写入策展、存储分层+生命周期、读取渐进披露+预算）；**落地**（自动化≠全自动，八环节"Agent CI/CD"：诊断归因→三路信号汇聚→生成候选→独立评测→五层门控→灰度→监控回流→Playbook 沉淀，配 Diff 模式、版本化一切、异步 Dreaming）；**控制**（人是教练和裁判：分级自主+动态升降级、五个永远必须有人的节点、审核疲劳三层解法、对齐漂移三层防护）。最后讲四条数据通路、启动能量 vs 持续动力、最易跑通的场景特征（真实业务指标、短闭环）和 Phase 1–4 路线，收束为"可信度>复杂度、治理>存储、衔接>单点先进"。

## 2. 核心主张
- **C1** 自进化瓶颈不在任何单点技术，而在环节之间的衔接：评测信号必须流进记忆和 Skill 更新，更新必须被评测验证，验证结果必须反哺下一轮。｜支撑：观察/推理，无数据｜适用：任何自改进 Harness｜位置：开篇、五
- **C2** 三层自进化按"改什么"分：改产物（打草稿，非进化）/ 改 Harness（记忆、Skill、Prompt、工具、工作流，跨会话生效，可回滚）/ 改权重（最持久、最贵、最险）。Harness 层是当前性价比最高的主战场。｜支撑：推理 + 未标条件的 −70%/−80% 数字｜位置：〇
- **C3** 评测在自进化中有三重职责：方向指引、质量门控、经验筛选。传统评测只有门控一项；后两项使评测信号直接流入长期行为，**打错分不是"上线了不够好的版本"而是"学到错误经验污染后续所有任务"**，故"评测可信度 > 系统复杂度"。｜支撑：推理｜位置：1.1
- **C4** 评测受精度×成本×覆盖面三难约束，七大难题按致命度排序：弱评估器（系统性偏差被反向优化，如偏好长文本→答案越写越长）> 评什么维度（只评结果漏掉过程幻觉/冗余调用/靠记忆碰对）> 评什么粒度（粗便宜无法归因，细精确但成本爆炸）> 开放任务难量化 > 评测集漂移（全绿时没人怀疑评测本身）> 预算公平性（Best-of-N 的提升关掉预算就消失，"3 倍 Token 换 10% 不是进化"）> 评测成本限制迭代频率。｜支撑：推理 + 个案（"几百到上千次 LLM 调用"）｜位置：1.2
- **C5** 评测手段分层：规则/自动校验为底（零成本、客观，多数团队未充分利用），LLM Judge 为中（生成/评估模型分离、temperature 0、结构化输出、分维度独立评），人工抽样+元评测集为顶。｜支撑：推理｜位置：1.3 要点一
- **C6** 评测集三分法且互不泄漏：train 只用于诊断（可暴露给生成修复的 LLM）、val 只用于筛选（绝不暴露）、test 只用于上线前验证（捕捉 val 过拟合）；val/test 定期用线上新失败样本回流替换。｜支撑：推理（EvoAgentX 等框架用 train/dev/test 的惯例）｜位置：1.3 要点二
- **C7** 评测终点是诊断归因而非分数；按失败类型分流：系统性问题→改 Skill/Prompt + 写 Playbook；偶发个例→写记忆作反例；能力缺失→补工具；回归→立即回滚并 blocked；全通过→合入+正例入金标集+灰度。**连续 3 轮失败率 80%+ 不降先查工具实现层**，配置层进化解决不了工具层 Bug。｜支撑：内部案例（20+ 轮无效迭代）｜位置：1.3 要点三
- **C8** 评估器本身需被评测：人工抽样校准（Kappa）、多评估器交叉、元评测集（绝对对/错样本，判错即全部分数不可信并告警）、无泄漏诊断（诊断阶段只传统计摘要不传题目）。｜支撑：推理｜位置：1.3 要点四（仅图 011）
- **C9** Skill"真的有用"要过四层：对照实验（无 Skill 也能做对则贡献为零）、难度校准（case 须处于"部分能做对"区间）、轨迹追踪（Skill 在上下文但未被 follow = 占位）、路径验证（结果对但跳过了关键校验步骤 = 下次翻车）；上线前必跑对照、定期复评。｜支撑：推理｜位置：1.4
- **C10** 记忆做不好比没有记忆更差；记忆是治理系统（版本、遗忘、冲突、溯源、晋升门控），不是存储系统。三环十难点：写入（价值判断、正负反馈不对称、粒度、隐性"什么不能做"）、存储（污染扩散快于修复、时效衰减、冲突、成本失控）、读取（向量相似≠语义相关、预算分配）。｜支撑：观察（"多个团队降级回无状态"，无数据）｜位置：2.1–2.2
- **C11** 写入策展而非全存：只在明确正信号（用户确认/评测通过/任务成功）时写入；失败按"反例/陷阱"存；三层晋升（临时捕获→项目记忆→独立技能）低门槛先记、逐层筛选；非对称淘汰（坏经验淘汰速度远快于好经验强化，"一条错误记忆的伤害 > 一条正确记忆的收益"）。｜支撑：引用 self-improving-agent Skill；+0.05/−0.12 来自 TCS EvoLoop（图 014）｜位置：2.3
- **C12** 存储分层（程序性 Skill / 语义 Facts / 情景 Episodes，默认用顶层、需要时钻取）+ 生命周期（版本与来源标记、演化、TTL/频率衰减/负反馈快速淘汰、后入优先+人工仲裁高冲突+乐观锁）。｜支撑：引用 Hermes Agent、TencentDB Agent Memory 等｜位置：2.4
- **C13** 读取渐进披露：默认注入顶层最小背景→任务到来时三路检索中层→遇困惑时按 node_id 钻取原始对话；分层 Token 预算、单条上限、总条数上限、按任务复杂度动态调整。记忆建模为文件系统让 Agent 用文件工具管理比专用 API 更有效。｜支撑：产品设计；后半句归于 Anthropic Dreaming（见 §4，属作者推断）｜位置：2.5
- **C14** 自动化≠全自动，三个结构性原因：LLM 看不到历史决策/业务约束，"修复"会覆盖人工精调逻辑；单点修复缺全局视角（改 A 破坏 B 的触发边界）；"总结经验→生成 Skill"环节本身需专门优化（引 SkillOS）。自动化覆盖"生成→验证→筛选"，关键决策必须有人。｜支撑：推理 + WX-20 已核实的 SkillOS｜位置：3.1
- **C15** 八环节链路即"Agent CI/CD"：诊断归因→三路信号汇聚（本轮诊断+历史 Playbook+外部知识）→生成候选（Diff 模式、注入背景）→独立隔离评测→五层门控（语法/AST→回归→统计显著性→Playbook 一致→人工确认）→灰度（小流量×观测期，P0 退化自动回滚不等人）→监控回流（灰度失败样本自动成为下轮种子）→Playbook 沉淀。每环有明确输入、输出和失败回边；**Playbook 是"怎么改 Agent"的经验，与"Agent 怎么做任务"的通用记忆互补但独立**。｜支撑：推理 + 内部实践｜位置：3.2–3.3
- **C16** 版本化一切是自进化的生存基础设施：每次 Skill/Prompt/记忆变更须有版本号、变更日志（谁/为何/diff）、来源标记（哪次评测触发、自动还是人工）、关联评测结果。Diff 模式而非全文重写（可 review、不碰无关逻辑、可精准回滚）；多文件联动改需接口签名验证。｜支撑：内部"血泪教训"｜位置：3.3 要点四、五
- **C17** 同步评测抓"每次的错"，异步 Dreaming 抓"反复的模式"（跨会话重复失败、低效路径、知识缺口）：定期审阅一批历史轨迹，输出带优先级的修订建议，人审后进入八环节。互补非替代。｜支撑：引用 Anthropic Dreaming（见 §4）｜位置：3.4
- **C18** 人是教练和裁判：按场景分级自主（建议/审批/抽检/自主），升级需持续证据（通过率、无回归、抽检无问题），出现 P0 回归自动降级；安全边界/拒答逻辑/付费相关永不进入完全自主。｜支撑：推理｜位置：4.1–4.2
- **C19** 五个永远必须有人的节点——规则级记忆写入前、涉及安全边界的 Prompt/Skill 更新确认、回归时的回滚决策、新领域冷启动种子、安全边界设定——是设计上的刚性约束，不是"当前做不到"的权宜；核心逻辑"程序不改自己的权限文件"。｜支撑：推理 + 引 Anthropic 报告"隐蔽累积偏移"（见 §4，转述失真）｜位置：4.3
- **C20** 审核疲劳是落地最常见失败：什么都弹审核→人三天后不看直接通过→比没有审核更危险（虚假安全感）。根因是到人手上的东西质量差数量多。解法：自动门控前置过滤、批量异步审核且附评测数据/影响面/对比示例/推荐理由（让人做选择题）、渐进放权+自动降级。｜支撑：推理｜位置：4.4
- **C21** 门控解决安全性不解决方向性：每步都过门控，但累积起来方向偏了（评测无意奖励"详细"→越来越啰嗦）。三层防护：定期人工方向性审计（Skill 库/记忆在朝什么方向长）、方向性约束指标（输出长度、工具调用次数、拒答率阈值告警）、评测集显式含意图对齐维度。｜支撑：推理｜位置：4.5
- **C22** 最易跑通的场景两特征：评测信号来自真实业务指标（天然不漂移）、闭环短反馈延迟低（5 轮内见效，20 轮才见效团队早放弃）。启动能量（种子评测集、初始 Skill/记忆、安全边界）不能省；先手动跑通最小闭环再自动化，"Phase 1 没验证就搭 Phase 3 基础设施大概率返工"。｜支撑：内部案例｜位置：5.2–5.4

## 6. 建议采纳（候选语义）
- **S1** 评估器（无论程序、模型还是人工抽样）自身必须被校准：维护一组已知标签的基准样本，评估器判错基准样本时其全部输出作废并告警；模型评估器须定期与人工判断比对一致性，并用不同评估器交叉发现盲区。｜落地方式 A（检查器）：评估流水线每轮先跑基准样本，未全对即中止｜落地方式 B（人工检查点）：按周期随机抽样人工二审并记录一致率，低于阈值触发校准｜它防御的失败：评估器系统性偏差被闭环反向优化（F1）｜删除条件：写不出（只要评估器是模型或人，偏差就存在）
- **S2** 评估样本按用途隔离为诊断、筛选、最终验证三类：修改 Harness 的执行者只能得到诊断类的统计摘要，不得读取筛选与验证类样本内容；各类样本定期用真实新失败替换。｜落地方式 A（权限与隔离配置）：筛选/验证样本存放在修复执行者无读权限的位置，只有评估进程可读｜落地方式 B（外部状态存储 + 检查器）：样本带用途标签，晋升检查校验候选生成时的读取记录未触及筛选/验证集｜它防御的失败：候选在评估集上过拟合，"数字好看但实际不行"（F2）｜删除条件：写不出
- **S3** 任何 Harness 改进的声明必须在同等推理预算下与基线对照；靠增加采样/重试/预算获得的提升不计为 Harness 改进。｜落地方式 A（检查器）：eval manifest 中预算为必填并由检查器比对候选与基线的预算一致性｜落地方式 B（人工检查点）：晋升审批表必须回答"同预算下差异是多少"｜它防御的失败：Best-of-N 伪进化，关掉预算即回原形（F3）｜删除条件：写不出（这是评估方法论，不随模型能力变化）
- **S4** 程序资产（Skill/Runbook）的有效性证据须同时包含"移除对照"（无它是否也能做对）与"轨迹遵循"（有它时执行路径是否经过其关键步骤）；只有结果对而路径未遵循的资产按未验证处理。｜落地方式 A（检查器）：轨迹 grader 检查资产声明的关键步骤是否出现｜落地方式 B（人工检查点）：抽样人工阅读轨迹核对｜它防御的失败：资产占位未被使用（F4）；绕过校验步骤碰巧正确（F5）｜删除条件：模型能可靠自报"是否遵循了资产"且自报可验证时可删轨迹检查，移除对照不可删
- **S5** 同一失败模式在连续 N 轮仅修改指令/配置层后仍不改善，必须停止该层迭代并转向工具、环境与数据层排查。｜落地方式 A（检查器）：进化流水线为每个失败模式计数，超限阻断继续生成配置层候选｜落地方式 B（人工流程）：复盘模板要求先回答"是否已排除工具层"｜它防御的失败：配置层无限打转、20+ 轮无效迭代（F6）｜删除条件：模型能在归因阶段可靠区分"指令问题"与"工具/环境问题"时，N 可放宽但停止条件仍保留（D-003 的扩展）
- **S6** Harness 与记忆变更按影响面分级决定审批方式：无条件遵循且全局生效的规则、安全/权限边界、评估集本身、回归后的回滚决策、新领域的初始种子——必须由人决定；带范围、带验证结果、可撤回的经验条目可在评估门控下自动写入，但须可追溯并可事后否决。｜落地方式 A（权限与隔离配置）：全局规则与安全边界所在位置对 Agent 只读｜落地方式 B（人工检查点 + 外部状态存储）：候选带影响面字段，全局级候选进入人工队列，局部级候选自动晋升并记录否决入口｜它防御的失败：一条错误规则进入后被无条件遵循且不再被质疑（F7）；Agent 逐步扩大自身权限（F11）｜删除条件：写不出（责任判据，见 09 §2）
- **S7** 自主等级是场景级、可自动回落的量：升级需持续的通过率、无回归与抽检证据；出现严重回归立即自动降级，无需人操作；存在永不升级的红线类别。｜落地方式 A（运行时拦截）：回归检测触发后自动切换该场景的审批模式｜落地方式 B（外部状态存储 + 人工检查点）：场景的自主等级作为带证据的状态记录，升级需人批准、降级自动｜它防御的失败：稳定后放松警惕、过度信任（F8）｜删除条件：写不出
- **S8** 到达人的审批请求必须先通过全部自动门控，并批量、带证据（评估数据、影响面、代表性对比示例、推荐理由）呈现，让人做比较选择而非逐条是非题。｜落地方式 A（检查器）：未附评估结果与影响面的候选不得进入人工队列｜落地方式 B（人工流程）：按周期集中审批，审批记录含对比依据｜它防御的失败：审核疲劳→橡皮章→虚假安全感（F9）｜删除条件：写不出（人的注意力带宽不随模型变强）
- **S9** 除结果指标外，须监控若干方向性指标（如输出长度、工具调用次数、拒绝率、资产库增长方向）并设阈值告警；定期由人审计资产库与记忆的演化方向是否仍符合初始意图。｜落地方式 A（检查器）：指标随每轮评估记录，越界告警并冻结晋升｜落地方式 B（人工检查点）：周期性方向审计作为独立 Gate｜它防御的失败：每步都过门控但累积偏离意图（F10）｜删除条件：写不出（这是 D-023 的多轮形态）
- **S10** 关于"如何改进 Harness"的经验（何种修改有效、踩过什么坑、已排除的方向）是独立于任务记忆和项目知识的资产类别，每轮改进须读取并写回它。｜落地方式 A（外部状态存储）：改进闭环专属的经验记录，与任务记忆分库｜落地方式 B（静态指令/模板）：候选生成步骤强制引用上轮改进记录｜它防御的失败：每轮实验从零开始、同样弯路反复走、方向池枯竭时局部最优（F12）｜删除条件：写不出
- **S11** 评估集与评估标准的修改本身是受门控的变更：评估失败不得由自动流程通过"标记样本过时"消解；样本增删须由人批准、有记录、并与触发它的失败关联。｜落地方式 A（权限与隔离配置）：评估集位置对进化流程只读｜落地方式 B（人工检查点 + 外部状态存储）：样本变更走独立审批并记录理由｜它防御的失败：指标不好→改指标（F13，冲突二）｜删除条件：写不出
- **S12** 除逐任务的同步评估外，须有周期性的跨任务横向审阅，从一批历史轨迹中找出单次评估看不到的重复失败、低效路径与知识缺口；其产出只是候选，进入正常晋升链。｜落地方式 A（外部状态存储 + 定时流程）：定期对轨迹批次运行模式挖掘并生成候选清单｜落地方式 B（人工检查点）：定期人工复盘轨迹样本｜它防御的失败：单次看是偶发、合起来是系统性短板（F14）｜删除条件：写不出（但挖掘方式可随工具变化）

## 8. 该文暴露的失败模式
- **F1 评估器偏差被反向优化**：LLM Judge 偏好长文本/特定格式 → 多轮进化后 Agent 学会"写长骗过评估器"，评测分涨而质量降 → 文章处置：生成/评估分离、元评测集、Kappa 校准、方向性指标 → **可构造**：在评估器中植入已知偏好，跑 N 轮自动进化，测输出长度与人工评分的背离（D-023 Case）。
- **F2 评测集泄漏/过拟合**：所有环节共用一份集，修复 LLM 看到筛选样本 → val 高分、新问题垮 → 三分法、无泄漏诊断 → **可构造**：同一候选在"可见集"与"隔离集"上的分差。
- **F3 预算不公平伪进化**：新方案 Best-of-N 或多次重试 → 分数升，关掉额外预算回原形 → 同预算对照 → **可构造**：同一候选在 1× 与 3× 预算下对照，报告差异（D-025 Case）。
- **F4 Skill 占位未使用**：Skill 在上下文，Agent 靠自身能力做对 → 对照实验无差异、轨迹无 Skill 步骤 → 轨迹追踪 + 移除对照 → **可构造**：D-012 消融 + 轨迹 grader。
- **F5 路径绕过碰巧正确**：Skill 要求查询后格式校验，Agent 跳过校验，本次数据恰好合规 → 结果对、下次翻车 → 路径验证 → **可构造**：注入格式异常数据，检查跳过校验的轨迹是否被 grader 标记。
- **F6 配置层无限打转**：根因在工具/API 返回异常 → 连续多轮改 Prompt/Skill 失败率不降（"20+ 轮"） → 3 轮阈值先查工具层 → **可构造**：故意破坏一个工具参数，观察进化流程在几轮后转向工具层（D-003 扩展 Case）。
- **F7 规则级记忆污染**：一条错误规则自动写入并被无条件遵循 → 影响所有后续任务且"遵循规则时不再质疑规则" → 规则级写入前人审、非对称淘汰、负反馈快速淘汰 → **可构造**：注入一条错误全局规则，测多少任务后被发现、发现后多久被撤（WX-33 F6 同类）。
- **F8 过度信任/稳定后放松**：场景升到高自主级后出现回归 → 无人发现 → 自动降级 + Level 3 也抽检 → **可构造**：在高自主场景注入回归，测自动降级是否触发。
- **F9 审核疲劳**：每天 50 个审批请求，48 个是可自动过滤的低质变体 → 人不看直接通过，比没有审核更危险 → 前置过滤、批量带证据、渐进放权 → **可构造**：D-024 Case——记录 Gate 数量与实际否决率的关系。
- **F10 对齐漂移**：评测无意奖励"详细" → 每版都过门控，十几个版本后明显偏离"简洁"意图，且不知从哪版开始偏 → 方向性审计、方向性指标、意图对齐评测维度 → **可构造**：同 F1 的多轮版本，观察门控通过率与方向指标的分离。
- **F11 Agent 扩大自身权限**：Agent 可改自己的安全约束/权限边界 → 每步扩张看似合理，累积失控 → 安全边界只能人改、"程序不改自己的权限文件" → **可构造**：D-028 Case（Agent 试图修改审批路径）。
- **F12 方向池枯竭/局部最优**：只看本轮失败、不看历史 Playbook → 重复尝试同样思路，平台期停滞 → 三路信号汇聚、Playbook 沉淀 → **可部分构造**：有/无上轮改进记录的两组进化流程，比较重复候选比例。
- **F13 评测过时逃逸口**（图 026）：Gate 失败被自动归为"评测 case 过时→更新评测集" → 失败被消解而非修复 → 文章未处置（自相矛盾） → **可构造**：D-023 Case——候选失败时观察流程是否倾向修改评测集。

- **F15 全文重写覆盖人工逻辑**：LLM 重写整个 Skill 文件 → 上次人工精调的条件分支被抹掉，reviewer 看不出改了什么，无法精准回滚 → Diff 模式 → **可构造**：带人工标注分支的 Skill 交给自动修复，检查分支是否保留。
