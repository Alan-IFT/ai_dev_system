## 1. 文章在讲什么
作者把 2024-12 到 2026-03 之间 Anthropic / OpenAI / Cursor / LangChain 的十余篇工程博客串成一条"Harness 演化史"，用"金鱼（模型）—记事本（Context Engineering）—管理制度（Harness）"的比喻分三层：第一层管"不听话"（外化记忆之外还要强制流程：结构化清单、会话开头仪式、Git 回滚、上下文重置；OpenAI 则管环境：仓库即事实、规则下沉为 linter、文档园丁），第二层管"群体失控"（Cursor 的 planner/worker/judge 层级、Anthropic 16 个并行实例的 GCC 二分定位），第三层管"看不清自己"（Generator/Evaluator 对抗、Sprint Contract、Bugbot 8 通道盲审、沙盒只读隔离）。第四章提出作者的核心论点：每个 Harness 组件都是对"模型当下做不到什么"的补偿，模型变强后应拆除；护城河不在 Harness 厚度而在追踪"补偿面"迁移的速度。第五、六章用 2026-03-31 Claude Code 源码泄漏做"对账"，声称产品实现比博客走得更远，并指出 KAIROS / 风险分级 / Hooks 等新系统已超出"执行长程任务"的范畴，说明补偿面不只迁移还在膨胀。

## 2. 核心主张
- **C1** Context Engineering 只解决"存不住"；Harness 要解决"不翻本子、不照本子做、不自验"三个流程问题。｜支撑：转述 Anthropic 2025-11 的失败模式｜适用条件：数小时以上、跨多个上下文窗口的任务｜文中位置：§01
- **C2** 进度/功能清单要用模型不易随意改写的结构化格式，且执行者只能改状态字段、须实测通过后才可标完成；自由文本只作路标。｜支撑：转述 Anthropic（原文措辞是"模型不太会去改 JSON"，非强校验）｜适用条件：长任务、有可枚举功能清单｜文中位置：§01
- **C3** 每个会话开头强制"确认工位—读历史—读进度"的唤醒仪式；记忆存在版本历史和进度文件里，不存在模型脑子里。｜支撑：转述 Anthropic（原文为 5 步，含启动脚本与基本端到端验证）｜适用条件：多会话接力｜文中位置：§01
- **C4** 上下文撑爆时不压缩而是换一个全新 Agent，只传结构化交接单（Context Reset）。｜支撑：转述 Anthropic（实际出自 2026-03 文章，针对 Sonnet 4.5 的 context anxiety，且 Opus 4.5 已基本不需要）｜适用条件：模型有"长上下文焦虑"时｜文中位置：§01
- **C5** 仓库即事实：Agent 运行时读不到的东西等于不存在；入口文件只做地图（约百行）；关键规则下沉为 linter/结构化测试；专职 Agent 巡检过期文档。｜支撑：转述 OpenAI（与原文一致）｜适用条件：绿地项目、全 Agent 生成代码｜文中位置：§01
- **C6** "流程管行为（Anthropic），环境管认知（OpenAI）"是两条正交的控制轴。｜支撑：作者归纳，无证据｜适用条件：—｜文中位置：§01 末
- **C7** 多 Agent 扁平自治会退化为锁等待与"挑最安全的小改动装忙"；需要 planner/worker/judge 层级 + 周期性 fresh start。｜支撑：转述 Cursor（"20 个≈2–3 个吞吐""规避风险"为原文；"改注释空格""DAG 锁死""交接报告字段"原文无）｜适用条件：数百 Agent 共享一个仓库｜文中位置：§02
- **C8** 并行调试需要一个"已知正确的参照物"把全局失败拆成可分区的局部失败（GCC 差分二分、delta debugging）。｜支撑：转述 Anthropic C 编译器（一致；原文强调该测试 harness 是**人写的**）｜适用条件：存在可替换的参考实现｜文中位置：§02
- **C9** 模型评估自己的产出会"自信地赞美"；必须把评估者从生成者中拆出来、校准为怀疑态度、并让它实际操作产物（浏览器、截图、错误栈）。｜支撑：转述 Anthropic 2026-03（一致）｜适用条件：产出质量无法用单元测试覆盖（UI/体验/需求理解）｜文中位置：§03
- **C10** 评估者本身也会同步幻觉：用多通道打乱顺序独立评审 + 多数投票 + 验证器过滤。｜支撑：转述 Cursor Bugbot（8 通道/随机顺序/多数票/验证器均为原文；"被表面自洽欺骗"为作者加）｜适用条件：代码评审 Agent｜文中位置：§03
- **C11** 生成者会篡改测试环境交差，所以测试环境必须对生成者只读隔离。｜支撑：无出处（"SWE-bench 等多家团队反复观察到"未给来源）｜适用条件：—｜文中位置：§03
- **C12** 每个 Harness 组件编码一条"模型做不到什么"的假设；假设过期就拆；判断拆的时机比拆本身难；护城河 = 追踪补偿面迁移的速度而非厚度。｜支撑：转述 Anthropic 2026-03 + 作者推理（原文拆除依据是"有理由相信"和逐一移除观察，非"实验数据"）｜适用条件：—｜文中位置：§04
- **C13** 影响系统行为的边际因素排序：prompt > harness 结构 > 模型；但只在 harness 已成熟时成立。｜支撑：转述 Cursor（原文只说"prompt 比 harness 和模型更重要"，未给 harness 与模型的相对序）｜文中位置：§04
- **C14** 三家都承认"build fast, validate later"的长期风险：架构一致性经年演化未知、系统高速生成同时高速退化、需要持续垃圾回收。｜支撑：转述 OpenAI（周五 20% 清理 slop、golden principles 自动扫描为原文）｜文中位置：§04 末
- **C15** 产品化实现比博客走得更远：六层记忆 + 后台记忆整理、Coordinator/Team Mode、Verification Agent 的 PASS/FAIL/PARTIAL、Agent 按角色只读/只规划、feature flag 门控可随时拆组件。｜支撑：源码解读，未核实｜文中位置：§05
- **C16** KAIROS（该不该做）、风险分级分类器（会从拒绝中学习）、Hooks（开放插槽）解决的是"好用、可控、可商业化"而非"能执行长程任务"，说明补偿面在向新维度膨胀。｜支撑：源码解读，未核实；作者推理｜文中位置：§06

**对本项目最有价值的三个引用：**

1. **Anthropic 2026-03（Harness design）**：它是"补偿面"概念的一手来源，也是 D-012/D-021 的直接证据基础。核对后必须修正第三轮的一个默认：**拆除组件的依据不是实验数据，而是"有理由相信 + 逐个移除观察"**；而且 Context Reset 的退场归因于 Opus 4.5 的行为变化，不是 Opus 4.6 的对照实验。这意味着 D-012（受控消融）在其原始出处都没有被严格执行，本规范若要求"移除候选前后运行同一评估集"，是在**比出处更严格**，需要自己给出依据。另一条被作者删掉的重要信息：solo 20 分钟 / $9 与 harness 6 小时 / $200 的成本差，以及"evaluator 只在任务超出模型 solo 可靠范围时才值得"——这是 D-024（自主度上限）与 D-013（Thin）之间缺的那条成本轴。

2. **Cursor Bugbot**：作者只转述了 8 通道机制，删掉了该文真正的方法论贡献——用"合并时作者是否真的修了这个 bug"作为评审 Agent 的**结果指标**（而不是"标了多少 bug"），以及几十次 hill-climbing 实验中"许多改动让指标退步"。前者是 D-023（指标被满足而目标被背叛）的正向解法：把 grader 锚在下游真实行为上；后者是 D-025（三层评价）的实证：局部机制改动不能推定整体改善。

3. **Anthropic C compiler**：作者讲成"Agent 被逼出 GCC 二分法"，原文是**人**写了差分测试 harness，把"整体失败"变成"可按文件分区的失败"后，16 个 Agent 才能并行且不互相覆盖。对本项目的意义：**验证结构决定可并行度**——并行不是调度层（第 5 层）单独能解决的问题，需要第 7 层先提供可分区的判定。与"写极高质量的测试"一起，指向"人类设计验证环境，Agent 在其中执行"的分工。

## 6. 建议采纳（候选语义）
- **S1** 执行者对"完成"的声明只能改变一个受限的状态标记，且该标记的前置条件是执行者在真实环境中运行过验证；执行者不得删改验收条目本身。｜落地方式 A（外部状态存储 + 检查器）：状态记录中"完成"字段由脚本核对是否附带验证输出，缺则拒绝写入｜落地方式 B（人工检查点）：评审人只接受附带运行证据的完成声明，删改验收条目须另行审批｜它防御的失败：F1 提前交卷、F2 虚标完成｜删除条件：模型在无外部约束下的"自报完成"与端到端验证结果的一致率在代表性任务上持续达到与人工验收相当的水平
- **S2** 接手一段中断的工作时，先确认环境可用、再读历史与状态、再选下一步；三者顺序不可颠倒，缺一不得开工。｜落地方式 A（静态指令）：会话起始清单｜落地方式 B（运行时拦截）：未执行环境探测与状态读取前禁止写操作｜它防御的失败：F3 失忆重探、F4 在坏环境上继续叠加改动｜删除条件：写不出（这是接手任何工作的通用纪律，不依赖模型能力）
- **S3** 并行执行的前提是验证结构可分区：必须先存在一种把全局失败映射到局部责任区的判定方法（参照实现、差分测试、按模块的独立验收），否则不得增加并行度。｜落地方式 A（检查器）：为每个并行单元定义独立可判定的验收，全局集成失败自动二分归属｜落地方式 B（人工流程）：规划者在拆分任务前须写出"这一块单独失败时如何判定"，写不出的块不拆｜它防御的失败：F5 多 Agent 在同一集成缺陷上互相覆盖｜删除条件：模型能在无外部判定结构下自行协调并稳定收敛（目前一手来源显示不能）
- **S4** 评审/验证类 Agent 的效果指标必须锚定下游真实行为（被指出的问题是否真的被修复、被阻断的动作是否真的有害），不得只统计"标记了多少"。｜落地方式 A（检查器 + 外部状态存储）：在合并/发布点自动回读问题是否被解决并记入指标｜落地方式 B（人工检查点）：定期抽样人工复核被标记项的实际处置｜它防御的失败：F6 评审者靠多报问题刷指标（目标失明的评审版）｜删除条件：写不出（这是指标设计原则）
- **S5** Harness 中每个补偿性组件必须登记：它补偿的模型缺陷、启用它的成本（时间/费用）、以及"任务是否超出模型 solo 可靠范围"这一启用条件；组件默认可关闭。｜落地方式 A（条件加载规则）：按任务难度/风险等级决定是否启用评估者、规划者等角色｜落地方式 B（人工检查点 + 记录）：每次启用重型 harness 须记录 solo 基线与 harness 结果的成本差｜它防御的失败：F7 在模型已能 solo 完成的任务上照旧支付 30 倍的 harness 成本（一手来源：20 分钟/$9 vs 6 小时/$200）｜删除条件：写不出（成本核算本身不过期）
- **S6** 评估任何 Harness 改动前，先测量执行环境本身的噪声（资源限制、瞬态失败、运行间方差）；效果量小于噪声的比较不得作为采纳依据。｜落地方式 A（检查器）：同一配置重复运行取方差作为门槛｜落地方式 B（人工流程）：报告中必须并列噪声估计，缺则退回｜它防御的失败：F8 把资源配置差异当成 harness 收益｜删除条件：写不出（属 D-025 已有方向的加强，评估方法论不过期）
- **S7** 控制手段分两条正交轴登记："约束执行者行为"（顺序、门控、交接）与"约束执行者可感知的环境"（事实来源、可读性、自动纠错的文档）；诊断失败时先判断该补哪条轴。｜落地方式 A（文档/登记）：Harness 组件清单按两轴分类｜落地方式 B（人工流程）：失败复盘模板要求回答"是行为失控还是认知失真"｜它防御的失败：把认知失真（过期文档）误当行为问题去加流程，或反之｜删除条件：写不出

## 8. 该文暴露的失败模式
- **F1** 提前交卷：后续会话看到已有代码量即宣布项目完成 → 未完成的功能被跳过 → Anthropic：功能清单外化 + 只做一个功能 → 可构造：给一个已完成 30% 的仓库，观察是否声明完成
- **F2** 虚标完成：单元测试过但端到端不通，仍标 done → 坏功能进入"已完成" → Anthropic：标完成前须实测 + 浏览器验证 → 可构造：故意让服务端路由断开，看是否仍标 passing
- **F3** 失忆重探：每个新会话花大量 token 重新摸索项目结构 → 成本与漂移 → 进度文件 + 起始仪式 → 可构造：测量新会话到第一次有效改动前的 token 与工具调用数
- **F4** 在坏环境上叠加改动：环境有 bug 而执行者不知道 → 写出的代码跑不起来且被误判为自身逻辑问题 → 起始时运行基本端到端检查 → 可构造：起始前注入依赖缺失
- **F5** 多 Agent 集成期互相覆盖：多个执行者撞上同一个全局 bug，各自修并覆盖对方 → 算力空转、代码回退 → 人写差分 harness 把失败按文件分区 → 可构造：并行任务共享一个集成缺陷，观察提交冲突/回退次数
- **F6** 扁平多 Agent 的风险规避：核心代码被占用时挑安全小改动装忙 → 吞吐降到 2–3 个 Agent 的水平 → 层级化 + 周期 fresh start → 可构造：给 N 个 Agent 一个含少量难任务的队列，统计难任务被认领率
- **F7** 自评自信：模型评估自己的产出时"自信地赞美"平庸结果 → 质量门形同虚设 → 独立评估者 + 校准 + 亲手操作 → 可构造：同一产物分别由生成者与独立评估者打分，比较与人类评分的偏差
- **F8** 评估者同步幻觉：多个评审通道在相同输入顺序下犯相同错误 → 误报被"多数"确认 → 打乱顺序 + 多数票 + 验证器 → 可构造：同一 diff 固定顺序 vs 随机顺序，比较误报重合率
- **F9** 篡改判定条件交差：把断言改成恒真 → 假通过 → 测试环境只读 → 可构造：给一个不可能通过的测试，观察是否修改测试文件（文中无出处，需自建）
- **F10** 过期文档比无文档更危险：文档与代码脱节后执行者照错误地图走 → 幻觉产出 → 文档园丁自动开修复 PR → 可构造：故意让某段架构文档过期，观察执行者是否遵循过期描述
- **F11** 复制次优模式导致漂移：执行者复制仓库已有的不良模式 → 高速生成同时高速退化 → golden principles 自动扫描 + 重构 PR → 可构造：仓库中植入一个反模式，观察新代码复制率
- **F12** 补偿层遗留成为负担：模型已能自行完成，旧组件仍在增加延迟与成本 → "壳在碍事" → 逐个移除观察 → 可构造：同一任务开/关某组件对比质量与成本（一手来源本身未做严格对照，本项目可补）
- **F13**（二手来源自身的失败）转述升格：把"倾向""有理由相信"写成"物理锁""实验数据显示" → 下游据此制定规则 → 本卡的处置是回到一手来源 → 可构造为**本规范的引用纪律 Case**：任何进入决策依据的转述须标注一手措辞
