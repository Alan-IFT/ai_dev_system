# WX-04 开启Harness Engineering探索之旅

## 0. 验证边界
- 材料性质：单团队（腾讯电竞）、单工具栈（CodeBuddy IDE + 自研 SpecWorker Skill 体系）的一手实践报告；序章的概念史部分是对五个外部来源的二手转述。
- 无对照组、无消融、无样本量。正文几乎不给效果数字；图 015 是一次真实 change 的评分截图（n=1），图 017 含四个运营轨道数字（78.4% 命中率、89.61 相似度、95%/93% 准确率、20min→1min），均未给测量条件与对照。
- 作者自己列出六项"没做对"（评分与下游脱钩、知识库老化无机制、运营轨道跨项目复用未验证、老项目初始化靠人陪跑、AI 测试可信度未解决），这部分比正文的"做法"更可信。
- 超出可核实范围：SpecWorker 内部 Skill/SubAgent 的真实行为、评分 Skill 的打分口径、"95 分门槛"是否真的阻断过、hook_events 表的数据。文中两处自相矛盾（见 §9）说明正文与图是分别整理的，细节可信度打折。

## 1. 文章在讲什么
问题：团队"AI 出码率"一路走高，但版本节奏没同步变快——出码率与提效之间"裂开一道缝"。作者归因为三点：研发瓶颈从来不在写代码而在理解/对齐/追溯/沉淀/验证（引 Brooks 本质复杂度）；局部加速只让瓶颈转移；AI 看不见工程体系里的隐性约束。解法：把这一层命名为 Harness Engineering，落成"两条轨道 + 一个长期记忆"——轨道一是研发端到端交付（协议层/管线层/纪律层三层叠加，P0～P6 七阶段，前后端双流程），轨道二是线上运营自愈（告警→证据→根因→修复→回归→归档七步），长期记忆是五层单向依赖的知识库，并配三维可监测性（追踪/回溯/度量）。声称的结果：没有给出整体提效数字，只给出一次 change 全流程评分截图和运营轨道的几个未标条件的数字；作者更强调"四件事都在做同一件事：把 AI 看不见的东西挪到它一定看得见的地方"，并坦承六项未解决问题。

## 2. 核心主张
- **C1** 出码率与研发提效脱钩，根因是 AI 只压缩了附属复杂度，本质复杂度（理解、对齐、追溯、沉淀、验证）一分没少，且下游 review/维护反而更重。｜支撑：推理 + Brooks 引用，无数据｜适用条件：多人协作、存量系统｜文中位置：0.3
- **C2** Harness 是继 Prompt、Context 之后的第三站，三层叠加不替代；Harness 时代到来意味着前两层已基本成熟。｜支撑：五个外部来源的时间线转述｜适用条件：概念史｜位置：0.1–0.2
- **C3** 人与 AI 协作必须靠契约而非默契：每一步产出格式固定、用标准模板、机器自动校验、变更只记增量。｜支撑：设计描述，无对照｜适用条件：长链多阶段交付｜位置：2.1.1
- **C4** 需求口径必须在第一阶段钉死：原始口径只允许引用不允许 AI 复述；验收标准写成 WHEN→THEN(SHALL) 可测形式；测试用例与需求共用同一份 AC 列表，下游不得再"理解一遍需求自己写测试"。｜支撑：设计描述｜适用条件：有需求管理系统的团队｜位置：2.1.2.1
- **C5** 设计文档不是给人读的说明而是机器可读契约（接口签名/错误码/状态机/必填项），"等实现时再说"必须显式标注待澄清，不允许暗藏。｜支撑：推理（否则 P3 会自己发明一套、reviewer 无从比对）｜位置：2.1.2.2
- **C6** 审查只看契约一致性与覆盖度、不看风格（风格交给 lint），问题分三档：Critical 必须人审签字留痕、Important 可绕但必须标注偏差写入日志、Suggestion 自由处置。｜支撑：设计描述｜位置：2.1.2.3
- **C7** 测试失败后的根因收敛不能靠人：按写死的 SOP（trace-id→日志→数据行→缓存状态）自动取证出诊断报告，回给实现者修，同一用例 3 轮不通则停并标"需人工介入"。｜支撑：设计描述；边界：日志没打时无效｜位置：2.1.2.4
- **C8** 任何数据库 DDL/DML 不允许 AI 自动执行，必须拼成可读 diff 由人 yes/no——"即使是 Critical 修复也不例外"；灰度与回滚决策归 SRE。｜支撑：作者自述"踩过线上事故后立的硬规矩"（案例未展开）｜位置：2.1.2.5
- **C9** 归档是复利不是留资料：变更以 ADDED/MODIFIED/REMOVED/RENAMED 四类差异增量合并进项目知识库，避免全量复制导致膨胀；不归档，下一个 change 起不来（硬门禁）。｜支撑：推理｜位置：2.1.2.6、2.3.2
- **C10** 可监测性是"信任 AI 的工程前提"而非运维锦上添花，分三维递进：可追踪（每阶段机器可读证据，由钩子自动采集不靠 AI 自觉）→ 可回溯（按失败类型配套反馈回路）→ 可度量（token/耗时/重试/改动量中央聚合）。｜支撑：设计描述 + 图 015 一次 change 截图｜位置：2.1.2.7
- **C11** AI 有五种天然"偷懒模式"（跳过测试、猜着修、没验证就说完成、偏离设计、自评偏高），每种对应一道硬编码门禁（TDD/Debug/Verify/Review/Evaluate），触发否决直接阻断。｜支撑：断言，无频次数据｜位置：2.1.3
- **C12** 知识库按变化频率五层分层、依赖严格单向向下；检索只允许索引→相关 spec 两跳，禁止全局通配；术语与接口契约各只有一个事实来源。｜支撑：设计描述｜位置：2.3.1
- **C13** SubAgent 不是节省上下文的银弹而是另起一份独立计费的账——主 Agent 对子 Agent 读全文件的消耗毫无感知。｜支撑：作者核对 token 账单后的观察（无数字）｜位置：2.3.3
- **C14** 工作流编排追求确定性而非自由发挥：状态经共享持久文件传递而非 Agent 间直传；程序化门禁不依赖 AI 自判；确定的事用脚本、不确定的事用 AI。｜支撑：推理｜位置：二·原则 1、4
- **C15** AI"不听话"多数是"真的没看见"（压缩 + 注意力衰减），治理指令遵循是把指令搬到它一定看得见的地方，而不是反复强调。｜支撑：推理｜位置：二·问题 1
- **C16** 当 A→B 一步到位很差时，插一层结构化中间产物 A→C→B（Figma→html/css/切图→代码）。｜支撑：D2C 场景经验｜位置：二·问题 3
- **C17** 评分机制与下游真实消耗尚未耦合：P2 得 90 分但 P3 翻车，scorer 仍只看本阶段产物。｜支撑：作者自承的未解决问题｜位置：三

## 6. 建议采纳（候选语义）
- **S1** 验收标准与验证用例必须从同一份条目列表派生，下游验证环节不得重新解释意图。｜落地 A（外部状态存储）：验收条目带稳定 ID，测试用例引用 ID 而非复述条目｜落地 B（检查器）：验收前比对"验证用例覆盖的 ID 集合"与"验收条目 ID 集合"是否一致｜防御的失败：下游"自己再理解一遍需求写测试"，测试与需求各自漂移（F2 变体）｜删除条件：写不出（属于意图一致性要求，不随模型能力消解）
- **S2** 评估者与被评估者分离，且评估者的推理来源应与生成者不同（不同模型或不同上下文），评估者持有否决权。｜落地 A（检查器）：评估由独立进程/独立模型执行，输入只含产物与标准｜落地 B（人工检查点）：由非作者的人按同一评分标准复核｜防御的失败：F3 自评偏高、"你说得对"式认同｜删除条件：当同一模型自评与独立评估在代表性任务上的分歧率降到与人际分歧同量级时可删——需先测量
- **S3** 证据包不完整时评估结果只能是"不可判定/不通过"，不得给出通过。｜落地 A（检查器）：评分前校验必需证据字段存在，缺失即输出 UNDETERMINED｜落地 B（人工流程）：评审表规定"无运行证据附件不得签字"｜防御的失败：F2 无证据的完成声明被放行｜删除条件：写不出；与 D-014 空集合条款同源
- **S4** 自动修复循环必须同时受轮数上限与进展停滞两种条件约束，触发任一即停止并升级人工，且每轮指标须被记录。｜落地 A（运行时拦截）：循环控制器统计轮数与指标增量｜落地 B（Runbook + 人工检查点）：要求每轮记录指标，连续无提升时人工决定继续/回退/跳过｜防御的失败：F4 修复循环在无进展中耗尽预算｜删除条件：模型能自行识别"我的修改没有改善指标"并主动停止——当前无证据
- **S5** 处于自动修复或自愈路径中的动作不得继承任何人工确认豁免；不可逆动作（数据变更、发布、权限）在自动路径中与在人工路径中要求相同的显式确认。｜落地 A（权限与隔离配置）：自动执行者不持有数据变更权限｜落地 B（人工检查点）：变更以可读 diff 呈现并等待显式确认｜防御的失败：F5 "为了修 Critical"绕过确认直接改库｜删除条件：写不出（责任不可转移）
- **S6** 阶段级过程度量（耗时、消耗、重试、改动量）由运行时事件自动采集，不由执行者自报；采集失败时本地保留可补传。｜落地 A（运行时拦截）：阶段开始/结束事件触发采集｜落地 B（外部状态存储 + 检查器）：流水线每步产出带时间戳的记录，事后由脚本汇总｜防御的失败：执行者漏报、美化或"忘了"；ATT-E 的"人工汇报状态失真"｜删除条件：写不出
- **S7** 任何委托出去的子执行者的上下文消耗必须计入任务总成本并对委托方可见；委托不视为节省。｜落地 A（外部状态存储）：成本表按执行者层级汇总｜落地 B（人工流程）：任务报告必须含子执行者消耗字段｜防御的失败：F1 子执行者读全文件而主执行者无感｜删除条件：当运行环境原生提供跨层级成本归集时，规则由环境承担

## 8. 该文暴露的失败模式
- **F1** 子执行者被设计为"读全文件做审查" → 主执行者不感知、总成本上升，账单核对才发现 → 改为优先读差异、仅在差异过大时读全文 → 可构造：同一审查任务两种输入策略下的分层 token 计量（D-025 组件级对照）
- **F2** 测试/验证环节 AI 一句"已通过"敷衍 → 假完成进入下游 → Verify 纪律：无运行证据不得声明；评估证据不完整不得通过 → 可构造：给出无证据的完成声明，Gate 应拒绝
- **F3** 生成者自评打分偏高 → 质量假象 → 独立评估 Skill + 不同模型 + 否决权 → 可构造：同一产物自评 vs 独立评分的分歧率
- **F4** UI 修复循环多轮无实质进展 → 消耗预算 → 5 轮上限 + 连续 3 轮无提升停滞询问 → 可构造：注入不可修复差异，观察循环是否在预算耗尽前停止
- **F5** 数据库变更被自动执行（作者称踩过线上事故，细节未给） → 线上事故 → 任何 DDL/DML 强制人工 yes/no，Critical 修复不例外 → 可构造：Agent 在自愈路径中生成 SQL，应被权限层拦截而非仅靠提示
- **F6** 长会话被压缩 + 注意力衰减 → 关键步骤被跳过、门控未严格执行 → TODO 文件驱动、拆子 Agent、新 session、渐进披露 → 可构造：同一多步任务在不同会话长度下的步骤遵循率（与 ATT-N Case 合并）
