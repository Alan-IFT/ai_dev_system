# WX-25 Claude Code神级技巧：让AI编程更省心

## 0. 验证边界
- 材料性质：**一手个人实践笔记**（腾讯内部 Go/Bazel/gRPC 项目，单人、单团队、单工具栈），无原始数据、无对照组、无消融。全文唯一的量化倾向是"Token 消耗明显更少、一天下来差异可观"，**没有任何数字**，所以本卡没有数字外推问题，但也没有任何可核对的效果证据。

## 1. 文章在讲什么
作者在 Bazel 构建的 Go 后端项目上用 Claude Code 数月，总结七个方面：(1) 入口指令只写"AI 无法从代码推断、又反复影响协作"的规则，给出三条实际规则和三个"该写了"的触发信号，并区分常驻规则与按路径条件加载的规则；(2) "概率执行 → 强制执行"：凡是必须做/绝不能做的动作不靠指令靠事件拦截，例子是文件增删后自动跑 `gazelle`，以及拦截 `git add/commit/push`；(3) 两种上下文隔离原语——不带历史的子代理（只要结论）与带历史的分支会话（用完即弃）；(4) 把高频提示封装成可触发的技能，并用"加载时预执行命令、结果直接注入"取代模型逐轮调工具；(5) 列表式地把上述实践映射到 Token 节省；(6) 用一个普通 Git 仓库当私有插件市场分发团队的 Hook/MCP/Skill；(7) 短板：IDE 集成弱、不能换模型。作者声称的结果全是定性的：返工少、不用手动补刀、长对话不飘、Token 明显更少。对本项目的价值不在具体技巧，而在于它用一个真实项目把"指令 vs 拦截"、"隔离 vs 继承"、"模型取数 vs 程序预取"三对区分讲清楚了，并提供了若干可构造的失败 Case。

## 2. 核心主张
- **C1** 入口指令只写"AI 无法从代码推断、且反复影响协作效率"的规则；技术栈之类可推断的信息不写。｜支撑：推理 + 作者实测"意义不大"（无数据）｜适用条件：成熟代码库；新项目例外｜文中位置：01 开头
- **C2** 遇到执行细节不明必须问人，且在问之前先把能从代码里查到的都查完，只问需要人决策的问题。｜支撑：两个案例（跳过跨目录依赖导致返工；反过来向人请示"能否看文件"，图 001）｜适用条件：交互式开发｜文中位置：1.1、1.2
- **C3** 把"人工负责/别的自动化负责"的操作显式标注给 AI（proto 生成物、迁移文件、审批配置、CI 部署），让它知道边界。｜支撑：案例——Bazel 环境下 AI 自作主张跑 `go build` 失败；改 `.proto` 后手改生成的 `.pb.go`｜文中位置：1.3
- **C4** 三个"该把规则持久化"的信号：同一错误第二次出现；Code Review 发现 AI 本应知道的项目规范；发现自己在重复上次会话说过的话。｜支撑：作者归纳（与官方 memory 文档的"When to add"四条几乎逐句一致，见 §4）｜文中位置：1.4
- **C5** 规则按加载时机分两层：常驻（每次会话全量加载，始终占 Token）与条件加载（操作到匹配文件才生效，不匹配时完全透明）；规则少全放常驻，多了把"特定文件类型的规范"迁到条件层；条件规则可递归按模块目录组织、由不同团队各自维护。｜支撑：图 002 表 + 两个示例（测试文件命名/三段注释/mock 位置；迁移文件只增不改且必须含回滚）｜文中位置：1.5
- **C6** 指令是"建议"，Hook 是"强制"：必须在特定操作后立即执行的动作、绝不能执行的操作，不能靠模型的记性，要靠事件拦截。作者用一句话总结：**行为规范放指令，确定性操作放 Hook**。｜支撑：作者自述"我试过（用指令），效果不稳定"+ 三条原因（长对话注意力被占、安全类规则一次遗忘即不可挽回、指令执行依赖理解判断而 Hook 是事件触发）｜文中位置：02 开头、2.3
- **C7** 动作后自动补做：文件创建/删除后自动更新构建配置；删除检测用两层过滤（命令含 rm + 路径在监听范围）避免误触发。｜支撑：完整脚本｜适用条件：Bazel + gazelle｜文中位置：2.1
- **C8** 动作前拦截：`git add/commit/push` 必须由人执行，Hook 拦截并回显原因；即使 AI "忘了"规则，系统层面也挡下。｜支撑：图 003 截图（AI 在 `git add .` 被拒后改为提示用户手动运行）｜文中位置：2.2
- **C9** 用"状态"间接判断"事件"会误触发：CodeBuddy 无文件创建事件，用 `git ls-files` 判断是否新文件，结果未 commit 前每轮都被当成新文件、重复执行。｜支撑：作者在另一工具上的经历（未核实）｜文中位置：2.4
- **C10** Hook 覆盖整个会话生命周期，可在会话开始、提交提示前、工具前后、一批并行工具后、一轮响应结束、子代理结束、监视文件变更、压缩前、会话结束各点介入。｜支撑：图 004 表（事件 + 作者给的典型用途）｜文中位置：2.5
- **C11** 长会话的两个问题是 Token 暴增与注意力稀释；很多信息只在某节点有用，应主动隔离。两种隔离原语：**子代理**——不带主会话历史、只回传结论、可路由到更便宜模型；**分支会话**——继承全部历史、产物不回流、用完丢弃。选择依据是"任务是否依赖已有上下文"。｜支撑：图 005 表 + 三个场景（评估改动影响面；生成 commit 命令；用历史上下文生成接口文档；试探不确定方案）｜文中位置：03
- **C12** 高频提示封装成可显式触发的技能，绑定"在隔离上下文运行 + 用轻量代理 + 禁止自动触发"三个属性，只把一行结果返回主会话。｜支撑：`/build-commit-msg` 完整配置｜文中位置：4.1
- **C13** 技能加载时预执行命令、把输出直接注入，比让模型逐轮"想命令 → 调工具 → 等结果"省 Token 且更快。｜支撑：两种写法对比（无数据）｜文中位置：4.2
- **C14** Token 节省是"工具底层优化（自动压缩、按行读、差异编辑、缓存）+ 上述实践"的叠加效果，不靠单一技巧。｜支撑：图 006 表，全部为推理，无测量｜文中位置：05
- **C15** 团队共享配置：一个按约定目录组织的 Git 仓库就是插件市场；两条命令安装 Hook+MCP+Skill；`git pull` 就是更新机制，无需服务。｜支撑：目录树 + marketplace.json｜文中位置：06
- **C16** 短板：终端工具的 IDE 交互弱于 IDE 原生插件（有官方 IDE 插件补救"选中代码→发送"）；只能用一家模型。｜文中位置：07

## 6. 建议采纳（候选语义）
- **S1** 执行者向人提问前必须先穷尽环境中可直接读取的事实；提交给人的问题只应是价值排序、范围边界、权限授予或不可逆选择这四类；能从代码/配置/运行环境得到答案的问题不得上交。｜落地方式 A（静态指令）：会话级行为约定"先查后问、只问决策"｜落地方式 B（人工检查点 + 检查器）：提问模板要求附"已查证的事实"与"待人决定的选项"两栏，缺前者的提问由审阅者退回｜落地方式 C（权限与隔离配置）：默认授予只读探索权限，使"能否看文件"不再成为问题｜它防御的失败：F1（跳过已发现的依赖导致返工）与 F2（向人请示本可自查的事实）｜删除条件：模型在评估集上稳定做到分流（未被问过的可查事实提问率≈0），且跳过依赖类返工在轨迹中消失
- **S2** 每个派生工件必须能追溯到其生成器与输入；执行者只修改生成器输入，不直接编辑派生物；哪些动作由人、由 CI、由其他自动化负责，作为责任归属显式声明。｜落地方式 A（静态指令/条件加载规则）：在触及该类文件时告知"只改源、生成由 X 负责"｜落地方式 B（运行时拦截或检查器）：对派生物路径的直接编辑予以阻断，或在提交前比对派生物与重新生成结果｜落地方式 C（外部状态存储）：仓库内维护生成器清单（源 → 生成命令 → 产物）供任何工具读取｜它防御的失败：F3（手改生成代码被下次生成覆盖；用错误的构建方式验证）｜删除条件：工具能从构建系统元数据可靠识别派生物并拒绝直接编辑
- **S3** 源工件变更后必须再生的派生配置（构建清单、索引、锁文件等），其再生应绑定到变更事件自动执行，而非依赖执行者记得；触发条件应绑定事件本身，若只能从状态推断则动作必须幂等。｜落地方式 A（运行时拦截）：文件创建/删除事件后自动运行再生程序｜落地方式 B（检查器）：提交前/CI 中比对派生配置是否与源一致，不一致即失败｜落地方式 C（人工检查点）：Review 清单含"派生配置已再生"一项｜它防御的失败：F4（忘跑再生命令直到服务起不来）、F5（状态反推事件导致重复触发）｜删除条件：构建系统自身在读取时动态推导派生配置，不再需要落盘产物
- **S4** 上下文隔离至少区分两种原语并按"任务是否依赖已有上下文"选择：(a) 不继承历史、只回传结论的委托；(b) 继承全部历史、产物不回流主线的分叉试探。试探性方案与一次性产出默认走 (b)，独立的高输出操作默认走 (a)。｜落地方式 A（权限与隔离配置）：工具提供独立上下文的子执行者与可丢弃的会话分叉｜落地方式 B（外部状态存储 + 人工流程）：无分叉能力的工具下，用独立工作区 + 交接件承载试探，结论人工回写主线状态｜落地方式 C（条件加载规则）：把一次性任务封装为在隔离上下文运行的技能｜它防御的失败：F6（试探失败的大段代码与分析污染主线，回到正轨后模型受干扰）、F7（git diff 等大输出留在主会话）｜删除条件：模型在满窗口噪声下无可测退化（与 WX-01 S2 删除条件同）
- **S5** 隔离执行的委托必须显式声明它**是否继承治理规则**（项目入口指令、权限边界）；为减小上下文而跳过治理规则的执行者，只能被授予只读或纯输出型任务。｜落地方式 A（权限与隔离配置）：轻量代理类型默认只读工具集｜落地方式 B（检查器）：委托合同校验"任务副作用等级 ≤ 代理的规则继承等级"｜它防御的失败：F8（forked 技能在无项目规则的上下文中执行有副作用的动作）｜删除条件：写不出（责任判据：权限继承是治理问题，不随模型变强消解）
- **S6** 任务所需的固定观察集（分支、变更、状态、日志摘要）由确定性程序在推理前采集并注入，或在执行时由程序过滤后再交给模型；不让模型逐轮决定"取什么、怎么取"。注入内容必须有大小上限与截断规则。｜落地方式 A（条件加载规则）：技能/Runbook 加载时预执行命令并内联结果｜落地方式 B（运行时拦截）：动作前改写命令使其只输出高信号部分（官方例：测试输出只留失败）｜落地方式 C（外部状态存储）：CI 把摘要写入固定位置，执行者只读摘要｜它防御的失败：F9（多轮"想命令→等结果"消耗 Token 与时间）、F10（无上限的注入把上下文撑爆）｜删除条件：工具原生提供结构化、可裁剪的观察接口，模型的取数决策成本可忽略
- **S7** 上下文压缩与会话结束是可拦截的生命周期事件；关键状态的外部化应绑定到"压缩前"事件强制执行，而不是依赖压缩摘要保留。｜落地方式 A（运行时拦截）：压缩前事件触发写交接件｜落地方式 B（人工检查点）：关闭自动压缩，由人在压缩前确认状态已落盘（WX-01 S2 方式 C）｜落地方式 C（检查器）：压缩后核对状态源与摘要的一致性｜它防御的失败：压缩摘要丢失未解决错误/失败尝试（与 WX-01 F2 同源）｜删除条件：压缩可被证明不丢失状态字段
- **S8** 团队级 Harness 配置（拦截规则、技能、能力接入）是有版本、有 owner 的可分发工件；安装与更新必须原子、幂等、可追溯到版本；项目专属规则不得放在个人全局配置中。｜落地方式 A（外部状态存储）：配置随仓库版本化，信任项目即自动生效｜落地方式 B（人工流程 + 检查器）：无插件机制的工具下，用安装脚本 + 版本标记文件，会话开始时校验版本一致｜它防御的失败：F11（每人手配一遍导致规则不一致；作者把带项目路径的 Hook 放在用户级配置，换项目即失效或误触发）｜删除条件：写不出（分发与版本归属是组织问题）

## 8. 该文暴露的失败模式
- **F1** 指令"重写该目录代码"，模型发现跨目录依赖 → 判定"不在范围内"跳过，按旧接口完成 → 人 Review 才发现接口对不上，追加多轮 → 文章处置：写"不明确必须问"规则 → **可构造**：给定一个带隐式跨目录依赖的重构任务，检查执行者是否在动手前上报该依赖并请求范围决定（不上报即失败）
- **F2** 模型已有读权限仍请示"能否查看某文件"（图 001） → 打断人 → 处置："问前先查"规则 → **可构造**：统计一段轨迹中"答案可从环境读到"的提问数，目标为 0
- **F3** Bazel 项目中模型用 `go build` 验证（跑不通）；改 `.proto` 后手改生成的 `.pb.go` → 白费一轮/被覆盖 → 处置：声明"生成由人/工具负责，只改源" → **可构造**：仓库含生成器与产物，给出需改产物的任务，检查是否只改源；给出验证任务，检查是否用项目声明的构建方式
- **F4** 文件增删后忘跑 `gazelle` → 启动服务才报错 → 处置：PostToolUse 自动跑 → **可构造**：新增文件后立即检查派生配置是否已更新（检查器形态）
- **F5** 用 `git ls-files` 判"是否新文件"代替创建事件 → 未 commit 前每轮重复触发 → 处置：换支持事件的工具 → **可构造**：连续两次编辑同一未提交新文件，触发动作应只执行一次或幂等
